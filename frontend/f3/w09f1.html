家庭上下文与切换家庭

这是 F3 的最后一张卡，也是前端第一次碰到多租户这个真问题。前两解决了「你是谁」和「你能不能进」，这一张解决「你现在在哪个家庭里」——以及一个看起来很小、实际上是全站最危险的动作：切换家庭。

先说结论，后面全是它的理由：切换家庭 = 服务端重新签发 token，不是前端改一个 id。切完之后，前端必须把所有已经缓存的业务数据整体作废，因为那些数据属于上一个家庭。忘做这一步的后果叫串户——用户在 A 家庭的界面上看到 B 家庭的账。这是这个项目里最严重的一类 bug，没有之一：它不报错、不崩溃、界面一切正常，只是数据是别人家的。

今日目标

判据照旧：切换家庭的界面 agent 已经写好了，点一下确实能切。你要能回答的是「切的那一瞬间前端做了哪四件事、少做一件分别会看到什么现象」，以及「列表里出现旧家庭的数据，怎么区分是前端没清干净还是服务端没换 token」。不许拿「切完界面变了」当自己通过了。

1. 「当前家庭」是谁说了算：token 里的 fam

服务端签发的 access token 里带着这几项（服务端 S4 建立的 Claims 口径）：

字段含义前端读它做什么
uid账号 id显示「我的」；跨家庭不变
mid当前会话家庭里的成员 id流水的作者、待办的负责人；换家庭就变
fam当前会话家庭 id服务端每条查询的 WHERE family_id = ? 用的就是它
role角色快照（1 owner / 2 member / 3 ward / 4 guest）入口可见性（上一张卡）；换家庭就变
pver权限版本；角色一变就 +1，旧 token 当场失效前端不读它，但要认得它造成的 401 + 1005

关键：服务端只信 token 里的 fam，不信请求体或 query 里的 family_id。这正是「每条查询都带 WHERE family_id = ?，而这个值由平台层从上下文注入、handler 不许自己写」这条服务端纪律的意义所在。所以前端想「切家庭」，唯一有效的办法是让服务端换一张 token——你自己在请求里塞 family_id，好一点是被忽略，坏一点是变成越权尝试（返回 404 + 1001 或 404 + 3001，与「不存在」同形）。

于是「当前家庭」这份状态在前端的正确放法是：只存一份、只有一个写入点。它存在 familyStore 里（这就是「家庭上下文」这个 store 的本职），而唯一能写它的入口是 authStore.applySession()——因为家庭身份与 token 是同一次服务端响应里一起下发的，同生同灭。任何页面都不许自己去改 current。

片段 · src/stores/family.jsimport { defineStore } from 'pinia'
import { ref, computed } from 'vue'
import { http } from '@/api/http'
import { useAuthStore } from '@/stores/auth'
import { useShellStore } from '@/stores/shell'
import { clearAllCaches } from '@/stores/cache'

export const useFamilyStore = defineStore('family', () => {
  const current = ref(null)      // 当前家庭上下文：全站只有这一份，只由 applySession 写
  const list = ref([])            // 我所在的全部家庭
  const switching = ref(false)    // 防连点：并发切换会让「最后停在哪个家庭」变得不确定

  const familyId = computed(() => (current.value ? current.value.id : 0))
  function setFamily(f) { current.value = f }   // 唯一写入口，被 authStore.applySession() 调用

  async function loadList() {
    const data = await http.get('/homeos/families')
    list.value = data.list
  }

  async function switchTo(id) {
    if (switching.value) return
    switching.value = true
    try {
      // ① 服务端重签发 token；返回的字段与登录响应完全一致
      const session = await http.post('/homeos/families/switch', { family_id: id })
      // ② 换掉凭证与身份快照：fam / mid / role 全变了，并落盘
      //    applySession 内部会调 setFamily(session.family) —— 家庭上下文只在这一步被写
      useAuthStore().applySession(session)
      // ③ 作废所有已缓存的业务数据（属于上一个家庭的全部不能留）
      clearAllCaches()
      // ④ 时间窗回默认档、未读计数归零
      useShellStore().reset()
      // ⑤ 清栈回首页：不能把用户留在上一个家庭的内页上
      uni.reLaunch({ url: '/pages/homeos/home/index' })
    } finally { switching.value = false }
  }

  return { current, list, switching, familyId, setFamily, loadList, switchTo }
})

「切换家庭只归 shell」这条口径的意思：切换入口在界面上只出现一份——壳的家庭切换器（顶栏那一处）。各个面的页面不许自己再做第二个「切换家庭」按钮。理由不是审美：切换这个动作要连着做五步（换 token、清缓存、重置时间窗、清栈、跳首页），入口多一份就多一份实现，漏掉任何一步就是串户。所有入口都调 familyStore.switchTo() 这一个函数，五步就只有一份。

五步的顺序不能换，这个顺序本身就是今天的知识点之一：先拿到新 token（①②），再清缓存（③④），最后清栈跳首页（⑤）。反过来做（先跳首页再换 token）会出现「首页用旧 token 拉了一次数据」，那一次拉的就是旧家庭的数据，而且它会在新 token 生效之后才回来——正好是下面定位题的第三个分支。

2. 切换家庭为什么必须是服务端重签发 token

理由展开
① 隔离条件的值只能来自凭证服务端每条查询都带 WHERE family_id = ?，这个值由平台层从 token 注入。如果它来自请求参数，那「我能看谁的数据」就由客户端说了算——多租户隔离当场归零
② 角色是家庭内的快照同一个人在 A 家庭是 owner、在 B 家庭可能是 member。换家庭必须连 mid 与 role 一起换，而这些都在 token 里，所以只能重签
③ 服务端保持无状态「当前家庭」不做成进程内的会话上下文，而是每张 token 自带。这样任何一个服务实例都能处理任何一个请求，横向扩容不需要会话粘连；旧 token 也不会因为「切走了」而需要额外失效机制

如果前端只是改一个 id 会发生什么——三种结局，都比报错更糟：

前端做法结果
只改本地 family.id，token 不换界面上的家庭名字变了，请求带过去的还是旧 token，服务端继续返回旧家庭数据。用户看到的是「标题写着 B 家庭，账目是 A 家庭的」——串户，且不报错
把 family_id 塞进请求参数服务端按纪律忽略它（或直接拒绝）。表现与上一种一样，或者拿到 1001 / 3001
正确做法：调切换接口，用返回的新会话整体替换token、成员、角色、家庭一起换；旧 access token 因为 fam 不同而自然指向另一个家庭，不存在「半新半旧」的中间态

顺带把家庭相关的几个码认一下：3001 家庭不存在或当前账号无权访问（切换一个你已被移出的家庭会拿到它）、3002 邀请无效 / 已过期 / 已使用、3004 账号家庭数已达上限（≤5，创建家庭时可能撞上）、1010 业务状态不允许（比如唯一 owner 没转让就想退出、或想解散不该解散的家庭）。这四个码的中文文案都在 F2 第 2 张那张表里加。

3. 必须清掉什么：四类缓存 + 一类「还在飞的请求」

Pinia 的 store 是全局单例、跨页面活着的（F3 第 1 张那条）。这是它的优点，也是切换家庭时的全部麻烦：页面跳走了，store 里的数据还在。

要作废的东西不清会怎样
① 各面的列表数据（分类、账户、流水、成员、动态…）直接串户：新家庭的界面上显示旧家庭的账
② 游标分页的 next_cursor 与 has_more更阴的一种：首屏是新的，触底加载续读时把旧家庭的下一页拼进来，列表下半截是别人家的数据
③ 未读计数、角标、通知列表数字对不上；未读口径要求三个出口同源，混着旧家庭的计数就永远对不齐
④ 时间窗 period（回到默认档）「本季」这种选择在旧家庭有意义、在新家庭可能是空的；留着会让新家庭首屏直接是一个没有数据的档
⑤ in-flight 请求的响应切换那一刻还在飞的请求，是带着旧 token 发出去的。它在 clearAllCaches() 之后才回来，把旧家庭的数据又写进 store——清了等于没清，而且现象是偶发的

第 ⑤ 类最容易被漏，因为「清缓存」这个动作在直觉上只针对「已经存在的数据」。标准解法是世代号（epoch）：

片段 · src/stores/cache.js（世代号）与列表加载的用法let epoch = 0
export function bumpEpoch() { epoch += 1 }
export function currentEpoch() { return epoch }

// clearAllCaches() 做两件事：把各 store 的列表清空，然后 bumpEpoch()

// 每个列表加载函数都长这样：await 之前记世代，await 之后比世代
async function loadCategories() {
  const at = currentEpoch()
  const data = await http.get('/finance/categories')
  if (at !== currentEpoch()) return   // 期间切过家庭 → 这个响应属于上一个家庭，丢弃
  list.value = data.list
}

这与你在 React 里处理「组件卸载后 setState」是同一个问题的同一个解法（那边用 AbortController 或一个 cancelled 标志）。区别只在于：那边的失效单位是组件，这边的失效单位是家庭。判断标准也一样——响应回来时，发起它的那个上下文还成立吗？

还有一层：缓存键本身应该带上家庭。凡是「按家庭缓存」的数据，键里就该有 familyId（以及 period），这样即使清理漏了一处，读的时候也不会读到别人家的——清理是动作，键是保险，两道一起做才稳。

4. useShellStore：时间窗 period 全站唯一一份

片段 · src/stores/shell.jsexport const useShellStore = defineStore('shell', () => {
  // period = { type: 'month', code: 'YYYY-MM' }；type 只取 month / quarter / year 三档
  const period = ref(defaultPeriod())
  const unread = ref(0)

  function setPeriod(type, code) {
    period.value = { type, code }
    bumpEpoch()          // 换档也要作废已聚合的数据：报表是按 period 聚合的
  }
  function reset() { period.value = defaultPeriod(); unread.value = 0 }

  return { period, unread, setPeriod, reset }
})
问题答案
为什么必须全站唯一一份顶栏那个时间窗切换器改一次，所有跟着它变的东西都要一起变：财务概览与趋势、日历视图、动态流的当期筛选。如果每个页面自己存一份 period，切换之后各页会停在不同档上，用户看到的是「同一屏里两个数字互相矛盾」——这种 bug 极难定位，因为每个页面单独看都是对的
为什么编码不能自己造五档编码是服务端定的：YYYY-MM-DD / YYYY-Wnn / YYYY-MM / YYYY-Qn / YYYY。非法编码服务端返 1007，不会回落到默认档——所以前端拼错一个字符串，得到的是一个硬错误而不是「自动纠正」
为什么切换器只暴露三档壳的时间窗切换器只给月 / 季 / 年；服务端接受五档，多出来的日 / 周两档给财务面的日视图与周视图用。这不是矛盾，是两个不同的口径：壳管全局，面内可以有自己的更细粒度视图
它与家庭切换的关系切家庭时 reset() 把它拉回默认档；换档时 bumpEpoch() 作废已聚合数据。两个动作共用同一个世代号机制，这就是它放在 shell 这个「全站唯一」的 store 里的原因

定位题（前端三处 + 服务端一处）

现象：切换家庭之后，列表里显示的还是旧家庭的数据。

这是串户现场。先别改代码，先把「数据是哪来的」定下来——前端有三个可能的位置，服务端有一个，区分方法各不相同：

  1. 前端①：缓存根本没清。某个 store 或某个页面的局部 ref 里还留着上一个家庭的数组（clearAllCaches() 漏登记了它，或那个页面绕过了 store 自己存了一份）。判断：切换后立刻打日志看那个 ref 是不是空数组。是空的 → 不是这一处；还有数据 → 就是它。
  2. 前端②：清了，但页面没重新拉。列表数据是 onMounted 里拉的，而这一页还在页面栈里没被销毁（切换后没做 reLaunch，或用户按返回键回到了它）——onMounted 不会重跑（F2 第 1 张那条坑）。判断：看 onShow 有没有触发、Network 里切换之后有没有一条新的列表请求。没有新请求 = 页面压根没去拉，显示的自然是内存里的旧渲染。
  3. 前端③：in-flight 响应回填。切换那一刻有一个列表请求还在飞，它带着旧 token 发出，在 clearAllCaches() 之后才回来，把旧数据又写进了 store。判断（看 Network 的时间轴，这一处只能这么定）：找到那条列表请求，比较三个时刻——它的发起时间早于切换请求的响应时间，而它的响应时间晚于切换响应。成立就是这一处，解法是世代号（本页 §3）。它的特征是偶发：网络快的时候不出现，慢的时候必现。
  4. 前端④（变体）：游标没重置。首屏是新的、触底加载之后下半截变成旧家庭的数据。判断：下拉刷新一次（刷新会重置游标）——刷新后正常、续读后又乱，就是 next_cursor 没跟着家庭一起作废。
  5. 服务端：token 没换，或隔离条件没生效。切换接口没有重签发 token（或前端 applySession() 没把新 token 用上），服务端仍按旧 fam 过滤。判断（一步定论）：拿切换之后第一条列表请求的 Authorization 头，把 access token 中间那段 base64 解开（只解码，不用验签），看 fam / mid / role 是不是新家庭的。
    • 还是旧的 fam → 前端没把新会话用上（applySession 漏调、或请求层拿 token 的时机早于它），是前端问题；
    • 已经是新的 fam，返回的数据却仍是旧家庭的 → 服务端的家庭隔离没生效，属于必须立刻修的缺陷（某条查询漏了 WHERE family_id = ?，或跨模块直查了别人的表）。这时前端一行都不用改。

定论口径写进 notes/：先看「有没有新的请求」（分开①②与③④），再看「请求带的是哪张 token」（分开前端与服务端）。两刀下去，五个分支各自归位。串户这类 bug 的可怕之处不在于难修，而在于难发现——它不报错。所以每次动到家庭上下文，都要按这五步自查一遍。

毕业题的参考骨架（先自己讲，讲不下去再看）：① 页面 onShow 触发，守卫先判 isLoggedIn 与 role（不通过 → 登录页 / 403 页）；② 调 http.get('/finance/categories')，请求层拼 baseURL 成 /api/finance/categories，塞上 Authorization: Bearer …；③ 代理或 nginx 把它转到 Go 服务，中间件解 token 得到 fam 与 role，查询按 WHERE family_id = ? 过滤；④ 响应是信封 {code,message,data}，拦截器 code!==0 转成 BizError、成功只交出 data（401 会先走 refresh 与重放）；⑤ 页面把 data.list 赋给一个 ref（世代号要比对，.value 别漏）；⑥ 模板 v-for 渲染，字段名与层级对上才显示得出来。六段里前三段与后三段的责任边界，就是「前端还是服务端」这条判据的答案。

把这一段的三次定位笔记（登录态丢失、被踢回登录页、串户）与 F1/F2 那几份合并检查一遍。到 F3 结束，你的定位笔记应该已经覆盖了：路由层 → 请求层 → 状态层 → 身份层 → 租户层五层，F6 的硬判据就是拿这五层去接一个真 bug。

常见坑

坑现象正确姿势
前端改个 id 就当切了家庭标题变了、数据没变（串户），或拿到 1001 / 3001切换必须走服务端接口，用返回的新会话整体替换（token + member + family）
只清了一个 store 的列表有的页面新、有的页面旧清理集中在一处（clearAllCaches()），所有缓存型 store 都登记进去
切换后用 navigateTo 回首页页面栈里还留着旧家庭的内页，返回键一按就回去了用 reLaunch 清栈
不管 in-flight 响应清完缓存又被写回旧数据，偶发、网络慢时才出现世代号：await 前记、await 后比，不等就丢弃
next_cursor 不重置首屏正常，触底续读拼进旧家庭的数据游标与 has_more 随家庭与 period 一起作废
period 每页各存一份同屏数字互相矛盾，每页单看都对只放 shellStore，全站唯一一份

会话家庭一次会话只对应一个家庭；多家庭 = 多张 token，切换即换 token
重签发 token服务端用新的 fam / mid / role 重新签一张 access + refresh，字段与登录响应一致
串户（跨租户泄露）一个家庭的用户看到另一个家庭的数据；不报错、不崩溃，是本项目最严重的一类 bug
缓存作废把属于上一个上下文的列表、游标、计数、时间窗一次性清掉的动作
世代号（epoch）一个只增不减的整数；请求发起时记下，响应回来时比对，不等就丢弃——用来处理 in-flight 响应
in-flight 请求已经发出、还没收到响应的请求；它携带的是发出那一刻的凭证
缓存键「按家庭 / 按时间窗缓存」时键里必须带 familyId 与 period；清理是动作，键是保险
period（时间窗）{type, code}，五档编码由服务端定，壳只暴露月 / 季 / 年；非法编码返 1007 且不回落
单一数据源同一份状态只在一个 store 里存、只有一个写入点，其他地方读它或派生 computed，避免切换时漏改
reLaunch 清栈清空整个页面栈只留新页；退出登录与切换家庭都用它
防连点用一个布尔标志锁住异步动作，避免并发执行导致最终状态不确定
