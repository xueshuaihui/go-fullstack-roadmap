F3 · 状态与对接

这一段是前端第一次真的连上你自己写的那个 Go 服务。F2 之前，web/ 里的请求大多是空的或对着假数据；服务端 S4 把鉴权与家庭隔离建好之后，前端终于有一整套真接口可用：登录换 token、带 token 拉数据、token 过期自动续、切换家庭重新签发。所以 F3 的三张卡不是「学 Pinia 语法」，而是把一条真实的身份链路读懂——从登录页那次 POST 开始，到列表数据上屏为止，中间每一处都有前端与服务端的责任边界，而「能说清这条边界在哪」正是前端线第三条硬能力（能独立定位一个 bug 在前端还是服务端）的落点。

三张卡的顺序就是这条链路的顺序：①登录态存在哪（Pinia store 与 token 持久化）→ ②没登录的人怎么被拦住（守卫、来源页、403 页）→ ③在哪个家庭里、换一个家庭要做什么（家庭上下文与缓存作废）。第三张最难，因为它碰到多租户——那也是本项目里唯一一类「不报错但数据是别人家的」bug。

F3 的毕业现场：一条全链路

阶段判据里那条「第一次真对接」，具体指的是下面这条链路在浏览器里跑通，且每一跳你都能说出它为什么在那儿：

#动作接口哪张卡讲
1登录（密码或验证码）POST /api/homeos/auth/login（验证码登录先 POST /api/homeos/auth/sms-code）第 1 张
2把会话写进 store 并落盘—（前端动作：applySession() + persist()）第 1 张
3看自己在哪个家庭、什么角色GET /api/homeos/family、GET /api/homeos/permissions第 1、2 张
4没有家庭就建一个 / 有多个就选一个POST /api/homeos/families、GET /api/homeos/families、POST /api/homeos/families/switch第 3 张
5拉第一个真实列表GET /api/finance/categories第 3 张（缓存与世代号就靠它演示）
6成员与入口按角色显隐GET /api/homeos/members + token 里的 role第 1、2 张
7退出登录POST /api/homeos/auth/logout，前端清会话 + reLaunch 回登录页第 1、2 张

这条链路上的接口全部是服务端 S4 那 24 条里的成员（认证 7 + 家庭 7 + 成员与邀请 10），分类那一条是 S2/S3 就走通的老朋友。所以 F3 期间不会出现「前端要一个服务端还没有的接口」这种情况——服务端先定契约、前端服从服务端，字段对不上时改前端。

为什么判据还是「能讲清 / 能改」

这一段最容易骗过自己：链路跑通了、登录成功了、家庭也切了，看起来什么都会了。但代码不是你写的。F3 的判据是两句话：① 能指出 401 时前端该做什么、不该做什么（该走 refresh 与重放，不该直接清登录态、不该无限重放、不该把 1003 也当成未登录）；② 能说清 token 存在哪、为什么（存两个凭证、不存身份快照、绝不存密码；写在 action 里、读在 onLaunch）。完成检查里没有一条是「登录跑通了」——不许拿「页面能跑」当自己通过了。

三张周日卡

卡知识点动手改 / 定位题
F3 第 1 张Pinia 与 token 持久化：useAuthStore 的 state / getters / actions 三块、与 useState + Context + Redux 的对照（store 是全局单例、不需要 Provider）、uni.setStorageSync 与 localStorage 的差别、为什么不能存明文密码加一个 isGuest getter（role === 4）并用它隐藏导出按钮 / 「刷新后登录态丢了」：没持久化还是持久化了没读回来
F3 第 2 张路由守卫与登录态：没有 beforeEach 时的两层写法（uni.addInterceptor 拦跳转 + 页面 onShow 兜底）、记住来源页与开放重定向、403 页（对应服务端 1003）、四种角色看到的入口差异把一个 owner 专属入口按 role === 1 收起并给页面装守卫 / 「明明登录了还被踢回登录页」：一次 Network 面板定论
F3 第 3 张家庭上下文与切换家庭：useFamilyStore、切换 = 服务端重签发 token、切换后必须清掉所有已缓存列表数据（串户）、in-flight 响应与世代号、useShellStore 的时间窗 period 全站唯一一份 + F3 收口在切换成功后补「清空缓存 + 重置时间窗 + reLaunch 回首页」并给列表页加世代号 / 「切换家庭后列表还是旧数据」：前端三处 + 服务端一处

同期服务端在 S4（鉴权与家庭隔离，18 张卡）：JWT 与双密钥、认证中间件、家庭与成员、邀请与角色变更、幂等键。前端这一段消费的正是它刚建好的能力，所以两张线在同一个日历周里是「工作日建、周日读」的关系；周日前半走前端卡，周日后半照旧复盘与提交。

本阶段不做什么（明确划掉，免得手滑）

  • 不做游标分页的前端侧（下拉刷新重置游标、触底续读、不重复不漏）——那是 F4；这一段只要认得信封形状与「游标不透明、不得自造」
  • 不做图表、深色主题、样式令牌体系——那是 F4；这一段改样式只允许动一处 v-if 级别的显隐，不碰颜色
  • 不做壳的底部五项、顶栏一行制、分包与按需加载、PIN 应用锁——那是 F5；这一段只需要知道「底栏由 shell 自绘，所以 pages.json 里没有 tabBar」
  • 不在客户端硬编码面清单、不做二次裁剪；F3 的入口显隐靠 token 里的 role 快照，等服务端把面配置建好后改为完全由服务端下发（对应服务端 S7）
  • 不把「前端藏了入口」当安全措施——门禁只在服务端那一份权限判定里；前端镜像不一致时以服务端为准，改前端
  • 不引入持久化插件、不引入 axios、不改 baseURL、不写死任何色值；React 只作为概念对照出现，不作为要写的东西
