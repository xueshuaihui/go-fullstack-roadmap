路由守卫与登录态

上一张把登录态放进了 store 并且能刷新不丢。这一张解决下一个问题：没登录的人、角色不够的人，怎么被拦住。在 React 里你会包一层 <RequireAuth> 或者在路由表里挂 loader；在 Vue 的 SPA 里你会写 router.beforeEach。uni-app 里这三样都没有——因为路由表是 pages.json 这个静态 JSON（F2 第 1 张讲过），配置里根本没有「钩子」这个位置。所以守卫要自己搭，而且必须搭两层。今天还要处理第二个维度：登录了但角色不够，那是 403 页而不是登录页，两个页面弄混是这一段最高频的 bug。

今日目标

判据照旧：守卫代码是 agent 写的，页面也确实拦得住人。你要能回答的是「为什么单靠拦截器不够」「1003 和 1005 分别该把人送到哪一页」「前端把按钮藏起来算不算安全」。不许拿「未登录确实跳到了登录页」当自己通过了——那只能证明代码在跑，不能证明你读得懂它。

1. 两层守卫：拦截器管跳转，页面管自己

先认清一件事：uni-app 里「进入一个页面」有两条完全不同的路。第一条是代码里调 uni.navigateTo 之类的 API；第二条是不经过任何 API——H5 端用户在地址栏直接输 URL、按浏览器后退、按 F5 刷新，App 端从推送通知或深链直接落在某个内页。拦截器只能拦第一条。所以：

层写法覆盖不覆盖
① 全局跳转拦截uni.addInterceptor('navigateTo', …)所有走 API 的跳转，在跳转发生前就拦下来（体验好：不会闪一下目标页）直接落页：地址栏、刷新、后退、推送深链
② 页面级兜底页面的 onShow 里判一次（抽成 composable，每页顶层调一行）任何方式进入该页面都会经过，包括首次冷启动落内页它是「已经进来了再赶出去」，会有一帧闪烁

只做第 ① 层是这段最贵的错。H5 端联调时你会发现「登录守卫好像时灵时不灵」：点着进去的页面拦得住，F5 刷新的页面拦不住。原因是刷新时页面直接挂载，navigateTo 压根没被调用过，拦截器没有任何触发机会。② 是安全网，① 是体验优化，两者不能互相替代。

片段 · src/guard.js（第 ① 层：拦跳转 API）import { useAuthStore } from '@/stores/auth'

const WHITE_LIST = [
  '/pages/homeos/auth/login',
  '/pages/homeos/auth/register',
  '/pages/homeos/error/forbidden',
]

function guardRoute(url) {
  const auth = useAuthStore()
  const path = (url || '').split('?')[0]
  if (WHITE_LIST.includes(path)) return true   // 登录页自己必须在白名单，否则死循环
  if (!auth.isLoggedIn) { toLogin(url); return false }  // invoke 返回 false = 终止这次跳转
  return true
}

export function installGuard() {
  // 每个导航 API 都要各注册一次：漏掉哪个，那个跳法就绕过守卫
  ;['navigateTo', 'redirectTo', 'reLaunch'].forEach((api) => {
    uni.addInterceptor(api, { invoke(args) { return guardRoute(args.url) } })
  })
}
片段 · src/composables/useRequireAuth.js（第 ② 层：页面兜底）import { onShow } from '@dcloudio/uni-app'
import { useAuthStore } from '@/stores/auth'

// 页面里只写一行：useRequireAuth()  或  useRequireAuth({ role: 1 })
export function useRequireAuth(options = {}) {
  const auth = useAuthStore()

  function check() {
    if (!auth.isLoggedIn) { toLogin(); return false }
    if (options.role && auth.role !== options.role) { toForbidden(); return false }
    return true
  }

  onShow(() => { check() })   // 不是 onMounted：从下一页返回时也要重新判
  return { check }
}

两个细节值得单独记：

  • 为什么用 onShow 不用 onMounted：上一页组件被盖住时并没有销毁（F2 第 1 张那条坑），所以「从详情页返回时登录态已经在别处被清掉了」这种情况，只有 onShow 能发现。
  • 为什么守卫要抽成 composable 而不是写在每页：配置式路由没有集中的钩子位置，所以只能「每页自己判」。抽成 useRequireAuth() 之后，每页只多一行，规则只有一份——这是把「配置式路由的缺陷」补回来的标准做法，与 F1 第 4 张讲的 composable 是同一个思路。

2. 记住来源页：一来一回怎么接

片段 · 去程与回程// 去程：守卫把「本来要去哪」编码进 query
function toLogin() {
  const pages = getCurrentPages()          // 当前页面栈，最后一项就是现在这一页
  const cur = pages[pages.length - 1]
  const query = cur.options ? Object.keys(cur.options)
    .map((k) => k + '=' + cur.options[k]).join('&') : ''
  const back = '/' + cur.route + (query ? '?' + query : '')
  uni.redirectTo({ url: '/pages/homeos/auth/login?redirect=' + encodeURIComponent(back) })
}

// 回程：登录成功后，在登录页的 onLoad(options) 里取出来
const HOME = '/pages/homeos/home/index'
function safeRedirect(raw) {
  if (!raw) return HOME
  const url = decodeURIComponent(raw)
  // 只接受站内路径：必须以单个 '/' 开头，且不带协议与双斜杠 —— 防开放重定向
  if (!url.startsWith('/') || url.startsWith('//') || url.includes('://')) return HOME
  return url
}
// 登录成功：uni.reLaunch({ url: safeRedirect(redirect) })
问题答案与理由
去登录页用哪个导航 API？redirectTo（或 reLaunch）。不能用 navigateTo：那会把登录页压在业务页上面，用户在登录页按返回键会回到那个「他无权看的页面」，然后又被守卫弹回来——来回循环，页面栈还一直变深
登录成功回去用哪个？reLaunch。清掉整个栈，让首页/来源页成为新的栈底；返回键此时应该退出应用，而不是一路退回登录页
redirect 为什么必须校验？不校验就是开放重定向：构造一个 ?redirect=https://… 的链接，用户在你的登录页输完密码就被送到钓鱼站。校验口径：必须以单个 / 开头、不含协议、不含 //；更严的做法是再比对一次 pages.json 的注册表
来源页的参数怎么办？一起编码进 redirect（上面的 cur.options）。只记路径不记参数，回去之后详情页会拿不到 id

3. 1005 与 1003：两个码，两个页面

服务端把「你是谁」和「你能不能干这件事」分成了两个码，前端必须分开处理：

业务码HTTP含义前端处置
1005401未认证 / token 无效或过期 / 权限版本已失效先交给请求层的 refresh 链路（F2 第 2 张）；刷新也失败才清登录态并送登录页，带 redirect
1003403权限不足：角色矩阵拒绝、面未启用、字段不可见、非作者改他人数据送 403 页（pages/homeos/error/forbidden），文案是「你的角色不能做这个操作」。送登录页是错的——他登录着，再登一次也还是不够权限，用户会陷入「登录 → 被踢 → 再登录」的死循环
1001404资源不存在，越权读也返回本码（与「真不存在」同形，不泄露存在性）就当成「找不到」显示：空列表或详情页的「不存在或无权查看」。不要跳 403 页——那等于告诉用户「这条数据存在，只是你没权限」，正是服务端刻意避免的信息泄露
1002401认证失败（凭证错误）留在登录页红字提示，不要区分是手机号还是密码错（防枚举，服务端已经统一成这一个码了）

「越权读 404、越权写 403」是刻意设计的不对称，前端要跟着这个不对称走：读不到 → 表现成不存在；写不了 → 明确拒绝。看到某处把 1001 也导向 403 页，那是前端 bug，报给 agent。判定逻辑集中在一处（一个 handleBizError(e) 之类的 helper），别散在各页面的 catch 里。

四种角色看到的入口不同——这张表是服务端角色矩阵的镜像，不是权威：

入口 / 能力owner（1）member（2）ward（3）guest（4）
成员管理、邀请、改角色可见可用不可见不可见不可见
面配置（启用 / 停用）可见可用不可见不可见不可见
转让 owner / 解散家庭可见可用不可见不可见不可见
记一笔 / 编辑流水可可有限（仅自己创建的）只读，入口隐藏
导出可可不可见不可见（限时只读，明确不可导出）
退出家庭不可（须先转让）可可可（且可被撤销）

前端隐藏入口只是 UX，不是安全。把按钮 v-if 掉，拦不住任何人——他可以直接发一个请求，服务端如果没拦就真的过了。权限判定在服务端只有一份实现（platform 里的 authz 模块，对应服务端 S4），业务 handler 不许自己写角色分支。所以这张表的正确读法是：「服务端会拒绝的事，前端提前别让他点」，两边必须一致；不一致时以服务端为准，改前端。反过来说，如果你在页面上看到某个入口对 guest 可见，那要么是前端漏了镜像，要么服务端矩阵有洞——两种都是缺陷，但只有后者是真漏洞。

还有一条前瞻：现在这张表靠 token 里的 role 快照在前端镜像。等到壳基座服务端把面配置与首页聚合建好（对应服务端 S7），「有哪些入口」将完全由服务端下发的面清单决定，客户端不做二次裁剪也不硬编码——那时这张表会从代码里消失，变成数据。今天的写法是过渡形态，别把它当终局。

验收方式：口述三条路径各自会发生什么——① member 角色在首页（入口应该已经不见了）；② member 角色直接在地址栏输 /pages/homeos/member/list（onShow 兜底应该把他送到 403 页）；③ 未登录直接输同一个地址（应该被送到登录页，且 redirect 里带着这个地址）。三条都讲得出来，这张卡的「能改」判据就过了。真跑不通没关系：第 ② ③ 条要等服务端鉴权中间件就位才看得到完整效果（对应服务端 S4）。

定位题（一次 Network 面板定论）

现象：某个页面明明登录了，一进去就被踢回登录页。

两个候选成因——前端守卫判错，或服务端返了 1005。用一次 Network 面板就能定论，但有一个前提动作，不做就什么都看不到：

  1. 先勾上 Network 面板的 Preserve log（保留日志）。被踢回登录页时页面栈会被清（reLaunch / redirectTo），日志默认跟着一起没了——不勾这一项，你看到的永远是一片空白，然后误判成「没发请求」。勾好之后复现一次。
  2. 看被踢那一刻之前最后几条 /api 请求的状态与响应体。三种结果，指向三个不同结论：
    • 没有任何失败请求（全是 200 + code:0，或者压根没发请求）→ 前端守卫判错。三个高频原因：hydrate() 的时序（守卫比 onLaunch 里的读回先跑，上一张的定位题）；isLoggedIn 的判据写错（判的是 user 而不是 accessToken，而 user 是不持久化的，刷新后必然为 null）；role 比较类型不符（'1' !== 1，接口给字符串而 token 里是数字）。
    • 有请求返回 401 且响应体 code: 1005 → 服务端的结论：这个 token 无效。接着看有没有紧跟一条 POST /api/homeos/auth/refresh、它返回什么。刷新都没发 → 前端漏了刷新链路；刷新也 401 → token 真过期或权限版本 pver 已失效（角色被改过）或服务端重启换了 JWT 密钥。这几种都不是守卫的错。
    • 有请求返回 403 且 code: 1003 → 不是「没登录」，是「角色不够」，前端把它当未登录处理了（错误分支写混）。该去 403 页，不该去登录页——这个 bug 的用户体验是「反复登录都进不去」。
  3. 加一行日志把两边对上。在守卫的判定处打 isLoggedIn / accessToken 前 8 位 / role，同时看 Network。日志说「未登录」而 Network 里没有任何失败请求 = 前端；日志说「已登录」却仍被踢 = 看是谁调的跳转（可能是 1003 分支，也可能是某个页面自己写的 if (!auth.user)）。
  4. 排除「假踢」。还有一种情况看起来一模一样：用户其实没被踢，是登录成功后的 reLaunch 把他送到了首页，而他以为自己还在原来那页。区分方法：看地址栏 / 页面栈有没有经过登录页，以及 Network 里有没有 /homeos/auth/login 的成功响应。

定论口径写进 notes/：「被踢之前有没有一条 401/1005」这一刀，就把前端与服务端分开了。没有 → 前端的守卫或持久化；有 → 服务端对 token 的判定（以及前端有没有正确执行 refresh）。这一刀比任何猜测都快，代价只是勾一个 Preserve log。
