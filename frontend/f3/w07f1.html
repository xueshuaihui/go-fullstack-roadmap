Pinia 与 token 持久化

F2 让你读通了工程与请求层，那两张卡里所有请求都是无身份的。这一段不一样：服务端 S4 把鉴权与家庭隔离建好了，前端第一次真的连上你自己写的那个 Go 服务——登录换 token、带着 token 拉数据、token 过期自动续。三张卡的分工：这一张讲「登录态存在哪、刷新后怎么还在」，下一张讲「没登录的人怎么被拦住」，第三张讲「换一个家庭时前端要做多少事」。

今天的主角是 src/stores/auth.js，一个 Pinia store。你写过 Redux 或 Context，所以概念不新，但有三处会让你按老习惯写出 bug：store 是全局单例、不需要 Provider；改状态直接改（没有 reducer）；跨页面共享同一份，所以「谁改的」比 React 里更难追。

今日目标

判据照旧：登录页能跑起来是 agent 的功劳。你要能回答的是——「刷新之后登录态为什么还在？谁把它写进去的、谁把它读回来的、读回来那一刻页面在哪一步？」以及「为什么 store 里绝不能有明文密码」。完成检查里没有「登录成功了」这一条，不许拿「页面能跑」当自己通过了。

1. 一个 store 的三块：state / getters / actions

片段 · src/stores/auth.js（setup store 写法；关键结构，工程内实现更长）import { defineStore } from 'pinia'
import { ref, computed } from 'vue'
import { http, rawRequest } from '@/api/http'

const SESSION_KEY = 'hc.session'

export const useAuthStore = defineStore('auth', () => {
  // ———— ① state：这个 store 拥有的可变数据。一律用 ref ————
  const accessToken  = ref('')
  const refreshToken = ref('')
  const user   = ref(null)   // 账号本身：id / phone / name / avatar
  const member = ref(null)   // 当前家庭内的身份：id / name / relation / role / guardian_id
  const family = ref(null)   // 当前会话家庭：id / name / timezone / currency（第三张卡会把它搬进 familyStore）

  // ———— ② getters：由 state 算出来的值，用 computed 写，惰性 + 缓存 ————
  const isLoggedIn = computed(() => !!accessToken.value)
  const role    = computed(() => (member.value ? member.value.role : 0))
  const isOwner = computed(() => role.value === 1)
  const isWard  = computed(() => role.value === 3)
  const isGuest = computed(() => role.value === 4)

  // ———— ③ actions：唯一允许改 state 的地方，可以是 async ————
  async function login(phone, password) {
    const data = await http.post('/homeos/auth/login', { phone, password }, { noAuth: true })
    applySession(data)          // 登录与刷新走同一个入口，字段口径完全一致
  }

  function applySession(data) {
    // 服务端给的形状：{ user, member, family, access_token, refresh_token }
    accessToken.value  = data.access_token
    refreshToken.value = data.refresh_token
    user.value = data.user; member.value = data.member; family.value = data.family
    persist()                     // 只在这里落盘，别处不许写 storage
  }

  async function refresh() {
    const res = await rawRequest({ url: '/homeos/auth/refresh', method: 'POST',
      noAuth: true, data: { refresh_token: refreshToken.value } })
    const body = res.data || {}
    if (body.code !== 0) throw new Error(body.message)
    applySession(body.data)      // refresh 是轮换的：旧 refresh token 当场作废
  }

  async function loadSession() {
    // 用凭证换回身份快照：user / member / family 一律不持久化，每次启动重新拉
    const data = await http.get('/homeos/family')   // → { family, member }
    family.value = data.family
    if (data.member) member.value = data.member
  }

  function persist() {
    uni.setStorageSync(SESSION_KEY, { a: accessToken.value, r: refreshToken.value })
  }
  function hydrate() {
    const s = uni.getStorageSync(SESSION_KEY)
    if (s && s.a) { accessToken.value = s.a; refreshToken.value = s.r }
  }
  function clearSession() {
    accessToken.value = ''; refreshToken.value = ''
    user.value = null; member.value = null; family.value = null
    uni.removeStorageSync(SESSION_KEY)
  }
  async function logout() {
    try { await http.post('/homeos/auth/logout') } catch (e) { /* 撤销失败也要清本地 */ }
    clearSession()
  }

  return { accessToken, user, member, family, isLoggedIn, role, isOwner, isWard, isGuest,
           login, applySession, refresh, loadSession, hydrate, clearSession, logout }
})

三块的规矩，用一张表钉住：

块用什么写允许不允许
stateref（本项目一律 ref，不用 reactive）被 action 改；被 getter 读；被模板读页面里直接赋值（auth.accessToken = 'x' 能跑，但绕过了 persist()，落盘就漏了）
getterscomputed纯计算：读 state，返回一个值发请求、改 state、写 storage——有副作用就不是 getter，该做成 action
actions普通函数 / async 函数改 state、发请求、读写 storage、跳页面返回值当响应式数据用（要返回值请用 getter）

为什么用 computed 写 getter 而不是写个函数：computed 惰性 + 缓存（F1 第 2 张讲过），依赖不变就不重算，模板里写 auth.isGuest 不用加括号，而且它的依赖是自动收集的——member 一变，所有用到 isGuest 的地方一起更新。写成函数就得在模板里 auth.isGuest()，每次渲染都重算，还断了依赖追踪。

role 那四个 getter 对应服务端的四级角色（S1·D3 定义的枚举，S4 开始写进 token）：1 管理员 owner、2 成人成员 member、3 儿童/老人 ward、4 访客 guest。角色是「家庭内」的快照——同一个人可以在 A 家庭是 owner、在 B 家庭是 member，所以 role 挂在 member 上而不是 user 上。这个细节是第三张卡（切换家庭）的全部前提。

关于 family 挂在哪：这张卡里它暂时放在 authStore，因为此刻工程里只有这一个 store。到了第三张卡引入 familyStore（家庭上下文 + 切换）时，这份 family 会搬过去而不是复制一份——applySession() 改成调 useFamilyStore().setFamily(data.family)，authStore 自己不再存家庭。搬完之后，「当前家庭」全站仍然只有一份、仍然只有一个写入点（applySession），这条纪律从现在起就成立。

2. 与 React 对照：单例、无 Provider、直接改

ReactPinia差别要点
组件内 useState组件内 ref这一层是一样的，都在组件私有
Context + useReducer 做全局状态一个 storeContext 要写 Provider、要处理 value 变化导致的重渲染范围；store 没有这两件事
Redux 的 statestore 的 state同名同职
Redux 的 selector（useSelector）store 的 gettersselector 每次调用重算（要靠 reselect 缓存）；getter 天生带缓存
action + reducer + dispatchstore 的 actions没有 reducer、没有 dispatch、没有 action type 字符串。action 里直接 x.value = …，改完就生效
<Provider store={store}> 包住整棵树app.use(createPinia()) 在 main.js 里执行一次之后任何文件 import { useAuthStore } from '…' 就能用，包括非组件文件（比如 api/http.js）
redux-persist 中间件自己在 action 里 setStorageSync没有生态依赖，持久化的时机与范围由你显式控制——好处是清楚，坏处是忘了写就真的没存（今天定位题的现场）

「不需要 Provider」到底意味着什么。React 的 Context 靠组件树传递：没有 Provider 在树上，useContext 只能拿到默认值，所以在工具函数、拦截器、普通 .js 文件里根本拿不到状态——你只能靠「把 store 实例挂到模块级变量上」这种绕法。Pinia 反过来：store 定义在一个模块里，同一个 defineStore('auth', …) 在整个应用里只会被实例化一次，谁 import 谁拿到的就是那一份。所以请求层能在拦截器里直接 useAuthStore() 读 token，不需要任何注入。代价是三条注意事项：① 必须在 app.use(createPinia()) 之后调用，所以不能在模块顶层求值；② 单元测试里每个用例要 setActivePinia(createPinia())，否则状态在用例之间串；③ 它是真的全局——A 页面改了，B 页面立刻看到，这一点在第三张卡会变成「切换家庭必须清缓存」的根因。

组件里怎么拿：

片段 · 页面里使用import { storeToRefs } from 'pinia'
import { useAuthStore } from '@/stores/auth'

const auth = useAuthStore()
const { isLoggedIn, isGuest, member } = storeToRefs(auth)  // ✅ state 与 getter 要解构就用 storeToRefs
// const { isLoggedIn } = auth                              // ❌ 解出来是普通值，响应性当场断
const { login, logout } = auth                             // ✅ action 是函数，直接解构没问题

这就是 F1 第 1 张那条坑（解构丢响应性）在 store 上的版本：值要 storeToRefs，函数可以直接解构。模板里也可以整对象用（auth.isGuest），那条路永远不会断。

3. 会话持久化：uni.setStorageSync 与 localStorage

需求只有一句：刷新页面（或杀掉 App 再打开）之后，用户还是登录着的。做法是把凭证写进端上存储，启动时读回来。

维度localStorage（你熟的）uni.setStorageSync
API 形态只有同步版同步版 setStorageSync + 异步版 setStorage({success,fail})；本项目一律用同步版（写两个 token，量小、不想处理回调时序）
数据落到哪浏览器同源存储按端不同：H5 → 就是 localStorage；App → 原生存储；小程序 → 各自的 storage。同一份代码三端通用，这是用它的唯一理由
能不能直接存对象不能，只有字符串，要自己 JSON.stringify / parse可以直接存对象（内部会序列化）。但约定只存可 JSON 序列化的纯数据：不要塞 ref、函数、组件实例进去
配额与作用域约 5MB，受同源限制各端配额不同，App 端不受同源限制。两端都不能当数据库用：只存凭证与少量偏好
过期机制没有也没有。要过期就自己在 payload 里存时间戳，读回来时判
谁能读走同源下任何脚本（XSS 一发就整包端走）H5 端与 localStorage 同等风险；App 端相对隔离，但设备备份/越狱仍可能带走

存什么、不存什么——这是今天最该带走的一条设计判断：

数据存不存为什么
access_token / refresh_token存它们就是「记住登录」这件事本身；refresh token 可撤销、会过期、服务端能作废
user / member / family不存这些是快照，会过期：角色可能在别的设备上被改（服务端 pver +1 会让旧 token 直接失效）、家庭可能被解散。启动时用 token 重新拉一次 /homeos/family，永远拿最新的那份
明文密码绝对不存见下
列表数据（分类、流水…）不在 authStore 存它们属于各自的面，且绑定家庭；换家庭必须整体清掉，第三张卡讲

store 里为什么不能直接存明文密码，五条理由，第一条就够： ① 没有任何用处。服务端只认 token，本地存着密码不会让任何一次请求更容易成功——它是纯粹的风险，零收益。 ② H5 端它就是 localStorage。一次 XSS 就能整包读走。密码是跨站复用的（很多人多处同一个密码），泄露一次的损失远超「一个会话被盗」。 ③ 它会跟着备份走。App 端存储进设备备份，换机、丢机、二手出售都可能把它带出去。 ④ 「记住登录」要的不是密码。要的是 refresh token：7 天有效、服务端可撤销、泄露了作废一个 token 就行；密码泄露了只能让用户去改密码，而且改之前的窗口期你无法控制。 ⑤ 连「临时存一下」都不行。密码只作为 login(phone, password) 的入参存在，函数返回就出作用域——不进 state、不进 storage、不打日志、不进错误上报。 项目里唯一允许的本地凭证类能力是 PIN 应用锁，而它存的是本地散列、不出端、没有任何服务端接口（对应服务端 S7 与前端 F5）。

什么时候读回来：App.vue 的 onLaunch——它早于任何页面的 onLoad（F2 第 1 张讲过这条时序）。放错位置的后果就是今天定位题的现象。

片段 · src/App.vue 的 onLaunchonLaunch() {
  const auth = useAuthStore()
  auth.hydrate()                       // ① 先把凭证读回内存
  if (auth.isLoggedIn) auth.loadSession()  // ② 再用凭证换回 user/member/family（GET /homeos/family）
}

定位题（是 store 没持久化，还是持久化了没读回来）

现象：登录成功、页面正常，刷新一次就回到登录页。

这个现象有两个完全不同的成因，用一个面板一步分开——devtools 的 Application（H5 端就是 Local Storage）：

  1. 刷新后立刻看存储里有没有那个 key（本工程是 hc.session）。没有 → 持久化那一步压根没发生，与「读回来」无关。三个高频原因：persist() 没有在 applySession() 里被调到（或登录走了另一条不经过 applySession 的路径）；key 名两处写得不一致（写用 hc.session、读用 hc_session，或多了一个环境前缀）；某处误调了 clearSession()——尤其是「401 就清登录态」写在了刷新链路之前（F2 第 2 张那条坑）。
  2. key 在、值里也确实有 access token → 写入没问题，是「读回来」的问题。查两件事：App.vue 的 onLaunch 里到底调没调 hydrate()；在 hydrate() 第一行打个日志，刷新一次看它跑没跑、读到了什么。日志没打出来 = 没调；打出来但值是空 = key 名或端不一致（App 端与 H5 端的存储不互通，别拿 H5 的存储去解释真机上的现象）。
  3. hydrate 跑了、store 里也有 token，页面还是被踢 → 这是时序或续期问题，不是持久化问题。两个分支：① 时序——守卫或页面的 onLoad 在 hydrate() 完成之前就判了登录态（把 hydrate 放进异步回调、或放在了页面的 onMounted 里而不是应用的 onLaunch）；② 续期失败——token 读回来了，但用它换会话信息那一步（GET /homeos/family）返回 401，refresh 又失败，于是 clearSession() 把登录态清了。
  4. 用一次 Network 面板把 ③ 的两个分支定论：刷新后看第一个业务请求。没有任何请求就被踢 → 纯前端时序问题（分支 ①）。有请求且返回 401 + code: 1005 → 服务端认为这个 token 无效：可能真的过期了（access 只活 15 分钟）、可能服务端重启换了 JWT 密钥、也可能你的角色被改过导致 pver 对不上。这一层是服务端的结论，不是前端 bug——接着看有没有跟着发 /homeos/auth/refresh，它返回什么，就知道该修哪一边。

把这条排查链补进 notes/。它的通用形状是：先看「数据有没有落到存储」，再看「启动时有没有读回来」，最后才看「读回来之后有没有被别的逻辑清掉」——三段各自独立，不要一上来就怀疑守卫。

常见坑

坑现象正确姿势
直接解构 store 的值const { isLoggedIn } = auth 之后视图不再更新值用 storeToRefs；action 可以直接解构；或整对象 auth.isLoggedIn
页面里直接改 state值变了但没落盘，刷新后又没了改状态一律走 action，persist() 只由 action 触发
把 user/member/family 一起持久化角色被改过、家庭被解散后，界面还显示旧身份只存两个 token，会话信息启动时用 token 重新拉
在模块顶层 useAuthStore()启动即报「没有活动的 pinia 实例」在函数体内取；模块顶层求值早于 createPinia()
hydrate() 放在页面 onMounted刷新后直接落内页时被判成未登录放 App.vue 的 onLaunch——它早于所有页面的 onLoad
getter 写成函数模板里要写 isGuest()，每次渲染重算用 computed；函数版只留给「需要传参」的查询
以为 store 是每页一份A 页面改了状态，B 页面莫名其妙跟着变它是单例，这是特性不是 bug；也正因如此，切换家庭必须显式清缓存（本段第 3 张）
把密码或整个登录响应体写进 storage安全风险 + 体积浪费，且没有任何功能收益只存凭证。密码只在 login() 的入参里活一次

术语一句话解释
PiniaVue 3 的官方状态库；一个应用装一次，store 是模块级单例
setup storedefineStore('id', () => { … return {…} }) 的写法：ref = state、computed = getter、函数 = action，return 出去的才对外可见
statestore 拥有的可变数据，只能由 action 改
getter由 state 派生的只读值，用 computed 写，惰性 + 缓存，不许有副作用
action唯一能改 state 的地方，可以异步、可以发请求、可以跳页面

refresh 轮换每次刷新同时下发新 refresh token，旧的立刻作废——所以并发刷新必须只发一次
