F5 · app 壳基座前端

前端辅线的第五段，与服务端 S7（壳基座服务端：面配置、首页合成、到期注册、通知、设置）并行。走到这里，财务面已经完整跑通：S6 的 30 条接口对着 F4 的页面，web/ 里有真实的请求层、Pinia store、路由守卫、图表与游标分页列表。F5 的主题是「壳」——那个承载所有业务面的外壳：顶栏一行、自绘底栏五项、面矩阵首页、分包，以及一道纯客户端的 PIN 帘子。壳学完，「一个家庭开哪些面、一个角色看哪些面、一个面的页面何时被下载」这条链你就全部能讲清了。

为什么 F5 值得单独一段

业务页面是「肉」，壳是「骨架」——骨架上挂着全站最硬的几条红线：pages.json 不得有 tabBar 字段（CI 第一查）、面清单只能来自服务端 faces[]（客户端不得二次裁剪、不得硬编码）、分包集合 = 已出生面域减去 homeos、PIN 是纯客户端能力零服务端接口。这些红线不是风格偏好，每一条背后都有一个历史反例或一次拍板决议。F5 的判据全是「你能不能讲清 / 能不能改」——不许拿「页面能跑」当自己通过了，壳是 agent 写的。

本阶段不做什么（明确划掉，免得手滑）

  • 不写服务端——S7 的 18 条接口是你亲手写的主线课，前端卡只消费契约；字段对不上时改前端，不改你的表结构与响应体
  • 不给 PIN 加任何服务端接口，不做 PIN 的多设备同步；不做 .wgt 远程下发的真实链路（分包清单接口只做契约）
  • 不动业务面页面本身——财务面的列表、表单、图表在 F4 已验收，F5 只改壳与面的「目录级」行为
  • 不引入新的状态方案或 UI 框架——壳级状态就三个 store（auth / family / shell），加第四个之前先来问自己为什么
  • 不学部署与联调工具链——那是 F6 的事（三段定位法、devServer 代理与 nginx 反代）
