面矩阵首页与 faces[] 唯一来源

上一张卡学了壳的骨架，今天学壳的中心：面矩阵首页——那个「这个家庭开了哪些面、你这个角色能看哪些面」的九宫格。它只有一条数据来源：GET /api/homeos/home/summary 返回的 faces[]。这张卡的红线是全站最硬的一条：面清单只能来自服务端 faces[]，客户端不得二次裁剪、不得硬编码一份「我知道有哪些面」的常量。这对应服务端 S7 阶段的面目录与首页合成课。

今日目标

判据提醒：这张卡的毕业标准是「能讲清面清单为什么不允许客户端二次裁剪」——这是 F5 阶段判据的原话。「首页能打开、九宫格能看到」不算通过，那是 agent 的功劳。

1. 首屏一个请求：home/summary

面矩阵首页不是一堆小请求拼出来的。GET /api/homeos/home/summary 单请求聚合了首页四个区 + 未读：

区字段说明
家庭区members[]（含 relation 与头像）+ 全量成员计数头像排溢出要用计数
今日区due_today（count 全量、items[] 只给前 3 条）「查看全部」再跳到期页
面矩阵区faces[]今天的主角
动态流区dynamics.items[]（前 20 条）续读走 GET /api/homeos/dynamics（游标分页，F4 学过的前端侧接法）
未读unread写进 useShellStore（上一张卡）

两条契约红线跟着这个接口走：客户端不得并行请求多个接口来拼首页；渲染面矩阵/导航不得额外请求 GET /api/homeos/family/modules——那个接口是给「面配置管理页」用的（它返回本家庭面配置 + 全量面目录，含未启用项），与 faces[] 由服务端同源合成、逐项一致（比对口径 enabled ∧ visible，owner 视角 visible 恒真——服务端有契约测试断言这一点）。

2. 四层合成：为什么只有服务端算得出 faces[]

一个面要不要出现在你的矩阵里，服务端要过四层：

层字段问的问题信息在哪
出生born这个面在这套部署里「出生」了吗（有没有对应的页面与能力）服务端部署形态
家庭启用enabled这个家庭开通了这个面吗家庭面配置（带乐观锁 version）
角色可见visible当前成员的角色能看这个面吗服务端权限矩阵的唯一实现（判定顺序：显式拒绝 > 角色默认矩阵 > 字段级可见性）
可用性availability面当前是否可进入（如维护态）服务端

四层里有三层的信息前端根本拿不全：权限矩阵只有服务端那一份实现（连同 pver 权限版本），出生与可用性也是部署侧的事实。这就是红线的第一条理由。完整背下来是三条：

为什么客户端不得二次裁剪、不得硬编码面清单——① 信息不全：四层口径的权威数据都在服务端，前端自己 filter 等于用残缺信息复刻一份权限判定，必然和真实现漂移；② 双份必漂：一旦前端存了一份「我知道有哪些面」的常量，服务端改了面配置（启用/停用/新面出生），常量不会跟着变，用户看到幽灵入口或丢失入口；③ 前端裁剪不是安全：真正的权限控制在服务端——就算有人绕过前端点进未启用的面，业务请求也会被拒（权限不足 403 + 1003；越权读同形于不存在 404 + 1001）。前端的 v-if 只负责体验（未启用的面零请求、零渲染），不负责安全。

React 对照：这就是 server-driven UI 的思路——导航配置不写死在客户端 bundle 里，而是每次从服务端拿。你在 React 里若把菜单硬编码成常量数组，加一个功能就要发一次前端版本；这里服务端改配置，客户端下一次拉 summary 就变。

3. 前端只干两件事：渲染与跳转

片段 · FaceMatrix.vue（首页九宫格的核心十几行）<template>
  <view class="face-grid">
    <!-- faces[] 的顺序 = 渲染顺序；不 sort、不 filter、不 map 改名 -->
    <view v-for="face in home.faces" :key="face.code"
          class="face-cell" @click="openFace(face)">
      <image class="face-icon" :src="face.icon" />
      <text class="face-name">{{ face.name }}</text>
    </view>
  </view>
</template>

<script setup>
import { useHomeStore } from '@/stores/home'
const home = useHomeStore()   // faces 唯一的赋值来源：home/summary 响应
function openFace(face) {
  // 路由三段式 pages/{code}/{feature}/{action}；面内首页路径由 code 拼出
  uni.navigateTo({ url: `/pages/${face.code}/home/index` })
}
</script>

注意这段代码里没有任何一个面的名字。「财务」「到期」这些字样如果出现前端常量里，就是违例。面是什么、叫什么、图标长什么样、排第几，全部是 face.* 字段。

面未启用时点进去看到什么？——先纠正问题本身：未启用的面不在 faces[] 里，压根渲染不出来，点不到。真正会出现「点进去」场景的是面配置管理页（数据来自 GET /api/homeos/family/modules，那里有全量目录含未启用项）。此时：

  • 非 owner：看到「未启用」说明页，零业务请求——用 v-if 整块不渲染业务区（F1·第 1 张讲过的纪律），不发任何该面的接口。
  • owner：多一个「启用」按钮，调 PUT /api/homeos/family/modules，请求体 {code, enabled, version}——乐观锁：版本不匹配返回 409 + 1009（前端要重新拉配置再试，不许吞掉冲突硬重试）；非 owner 硬发返回 403 + 1003；想停用到一个面都不剩，服务端拒：409 + 1010（业务状态不允许）。启用只写配置、不创建业务数据；停用不删数据。

定位题（必须只用 Network 面板走完）

现象：家庭成员说「财务面在首页矩阵里不显示了」。是服务端没返、前端过滤掉了、还是路由没注册？三步定论。

要求：全程只开 devtools 的 Network 面板（第 ③ 步允许补一眼 Console）。分界物就一个：响应里的 faces[]。

  1. 看响应：Network 里找本会话的 GET /api/homeos/home/summary（没有？说明首页压根没发请求——那是前端更上游的问题，先解决「为什么没请求」）。展开 data.faces[]，按 code 找 finance。不在 → 服务端没返：这不是错误码问题（面不显示不会有 404/403，它只是从列表里消失），对照 GET /api/homeos/family/modules 的响应看同一 code 的 born / enabled / visible 哪个是 false——大概率是家庭停用了该面，或当前角色不可见。结论出在服务端/配置侧。
  2. 响应里有、页面没渲染 → 前端问题：全局搜前端代码里对 faces 的 filter / slice / 额外 v-if（就像起点代码里的违例②），或绑定字段名写错（face.title vs face.name 这类）。判据：store 里的数组和屏幕上的格子数对不上，中间一定有一双手。
  3. 渲染了、点进去「页面不存在」 → 路由层：面在列表里说明服务端一切正常，是 pages.json（很可能是分包，下一张卡讲）没注册这个路径。Console 里 getCurrentPages() 加跳转报错信息可佐证。

结论句式：「faces[] 里有没有」分掉服务端；「有但没画出来」分掉前端渲染；「画出来但跳不动」分掉路由注册。把这条记进 notes/f5w2/。

常见坑

坑现象正确姿势
前端硬编码面清单「兜底」服务端故障时显示一排点了必失败的幽灵入口拉不到 faces[] 就显示错误态与重试，假列表比报错更糟
前端按角色再 filter 一遍与服务端权限矩阵双份实现，pver 变更后行为漂移只信 visible 字段；权限判定只有服务端一份实现
为渲染导航额外请求 family/modules首屏变两个请求，违反契约矩阵渲染只用 home/summary；modules 只给配置管理页
前端给 faces[] 重排序管理侧调整顺序不生效，两处顺序打架服务端返回顺序即渲染顺序
未启用的面点进去白屏/报错业务组件挂载即发请求，请求全被 1003 拒零业务请求的说明页；业务区 v-if 整块不渲染
把 1001 当「没权限」提示用户越权读与真不存在同形（故意的），文案写「无权限」会泄露存在性统一文案「不存在或无权访问」
PUT modules 吃 1009 后原地硬重试版本永远对不上，死循环1009 = 重新拉配置、给用户看新状态，再决定改不改

术语一句话解释
面（face）一个业务域（如财务）在 app 里的整体：一组页面 + 一组接口 + 一份家庭级配置
faces[]home/summary 返回的、当前家庭当前角色可渲染的面集合；前端面清单的唯一来源
born / enabled / visible / availability四层合成口径：出生、家庭启用、角色可见、可用——全部由服务端判定
同源合成faces[] 与 family/modules 由服务端同一份逻辑合成，逐项一致（口径 enabled ∧ visible），有契约测试断言
首屏单请求首页四区 + 未读一个 home/summary 拿全；客户端不得并行拼装
乐观锁 version写配置带上读到的版本号；不匹配返回 409 + 1009
1010业务状态不允许——例如停用最后一个已启用面会被拒
