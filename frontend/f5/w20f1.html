PIN 应用锁与 F5 收口

F5 的最后一张卡，两件事：① 学壳的最后一块——PIN 应用锁，一个纯客户端能力：本地散列存储、不出端、没有任何服务端接口；② F5 收口：四张卡的判据逐条自测。PIN 这块最好的教材不是代码而是边界感：什么该在端上做、什么不该、端上防御的诚实极限在哪。

今日目标

判据提醒：PIN 的页面 agent 早写好了。你的判据是能讲清它的存储边界与威胁模型——尤其是「换设备 PIN 失效」这种问题，能不能不翻代码就判定「是设计如此」并给用户讲明白。

1. 红线先行：PIN 没有任何服务端接口

本站接口清单锁死在 72 条，里面没有一条 PIN 接口——这是拍板过的决议，不是遗漏。所以第一个纪律：不许编一个 /api/homeos/pin 之类的东西出来，哪怕「为了多设备同步」。为什么不该有：

如果 PIN 出端…代价
服务端要存它它就成了「第二密码」：散列强度、重置流程、防枚举（1002 那一套）、审计，全都得再来一遍
网络要传它多一个被截获面；而它防的威胁（身边人拿起手机偷看）根本不需要网络参与
多设备要同步它「每台设备一道本地帘子」变成「一处泄露处处失守」

PIN 与登录密码的分工要能一句话说清：登录密码是「你是谁」，服务端验（auth 接口，跨设备有效）；PIN 是「这台设备现在能不能看」，本地验（设备级帘子，每台设备各挂各的）。

2. 本地存储：不明文、散列必加盐、诚实说极限

为什么不能明文存：本地存储不是保险箱——H5 端的 localStorage 在 devtools 里一眼可见；App 端的存储文件可能随备份导出，设备被 root/越狱后可直接读。明文存 PIN 等于把钥匙贴在门上。

为什么散列还不够、必须加盐：PIN 只有 4-6 位数字，全空间 104-106。不加盐的散列，同一个 PIN 在任何设备上都得到同一个摘要——攻击者拿预计算表（彩虹表）一查就反推出来，甚至不用在这台设备上算。加盐 = 设置 PIN 时随机生成一串 salt 与散列一起存，验证时 hash(salt + 输入) 再比对，让预计算表失效。

片段 · pin.js（核心三函数，散列实现用项目里选定的库）const KEY_HASH = 'pin_hash', KEY_SALT = 'pin_salt'

export function setupPin(pin) {
  const salt = randomSalt()                       // 每次设置都换新盐
  uni.setStorageSync(KEY_SALT, salt)
  uni.setStorageSync(KEY_HASH, sha256(salt + pin))  // 只存摘要，明文即弃
}
export function verifyPin(pin) {
  const salt = uni.getStorageSync(KEY_SALT)
  return sha256(salt + pin) === uni.getStorageSync(KEY_HASH)
}
export function hasPin() { return !!uni.getStorageSync(KEY_HASH) }  // 换设备后这里就是 false

诚实的极限，必须能讲出口：就算加盐，拿到设备的人仍可以在这台设备上把 104-106 个 PIN 全试一遍——盐防的是「预计算表与跨设备复用」，防不了「本机穷举」。PIN 的威胁模型是防身边人顺手偷看，不是防取证级攻击者。所以散列值本身也不能当密码用（谁拿到存储谁就能离线慢慢试，这正是次数限制与冷却要抬高的成本，见 §3）。把「防什么、不防什么」讲清楚，比把算法讲清楚更重要——这是今天定位题要考的能力。

3. 锁屏时机、解锁流程与次数限制

环节做法要点
锁屏时机冷启动且 hasPin() 为真；退后台超时（onHide 记时间戳，onShow 比对超过 N 分钟）；手动锁定用页面级 onShow/onHide（uni-app 提供），不是组件级 onMounted
锁的形态全局遮罩层（App 级组件，锁定时盖住一切页面）不要做成路由守卫的一个分支——直接 push 路由就绕过去了
解锁流程输入 → verifyPin 本地比对 → 过：清失败计数、撤遮罩；不过：计数 +1、统一文案全程零网络请求（没有接口可发，也不该发）
次数限制失败计数与 lockoutUntil 时间戳持久化在本地存储，超限进冷却期（如 30 秒 → 1 分钟 → 5 分钟递增退避）只放内存的话，杀掉进程重开计数就清零了
不自欺欺人承认：清缓存/重装可以清掉计数与冷却——客户端限制只能抬高成本，不能绝对兜底是「忘记 PIN → 重走账号密码登录」（用已有的 auth 接口，服务端验的是登录密码，依然不需要 PIN 接口），重新登录的流程里允许重设本地 PIN

React 对照：全局遮罩相当于在根组件挂一个顶层 modal + 全局 context 的 locked 状态；uni-app 里对应 App.vue 级别的挂载点。核心同构：锁的状态必须比路由层级高，否则任何深链都能绕过它。

动手改（今天的判据现场）

目标：把 PIN 的错误提示收敛到「除了第几次错，不泄露任何别的信息」。起点代码（agent 写的版本提示太热情了）：

片段 · 起点代码（三处泄密文案）function onPinSubmit(input) {
  if (!hasPin()) return toast('本机尚未设置 PIN，请先在设置中开启')   // 泄密①：暴露“没设 PIN”状态
  if (verifyPin(input)) return unlock()
  attempts.value++
  if (attempts.value >= 5) return toast('连续错 5 次将锁定 30 分钟，请小心')  // 泄密②：暴露阈值与冷却时长规则
  toast(`PIN 错误，还剩 ${5 - attempts.value} 次机会，错误将上报服务器`)       // 泄密③：谎称上报（根本没有接口），且报出剩余次数规则
}

验收口径：改完后，一个站在你身后看你解锁失败的人，从屏幕上只能得知「错了、第几次」——其余一无所知。能讲清这一点，才算过。

定位题（是 bug 还是设计如此？）

现象：用户换了新手机，登录同一个账号后，App 不再要求输入 PIN，而是要求「设置 PIN」。用户报障：「我的 PIN 失效了！」这是 bug 还是设计如此？怎么向用户解释？

排查（考的是能不能讲清本地存储的边界，不是能不能翻代码）：

  1. 确认现象的准确形态：新设备上是「输 PIN 报错」（验证失败），还是「直接进设置 PIN 流程」（本机从未设置过）？后者说明本地存储里根本没有 pin_hash 这个键——不是「验证不通过」，是「无从验证」。
  2. 对照存储边界：PIN 的散列与盐只存在旧设备的本地存储里；接口清单里没有 PIN，服务端不存、也从未收到过任何 PIN 数据。新设备登录拿到的是 token 与会话（服务端能力，跨设备有效），本地存储是全新的空房间——hasPin() 返回 false，走「设置 PIN」分支。结论：设计如此，不是 bug。
  3. 反向自检：如果旧设备上 PIN 也「失效」了呢？那才有排查空间：清过浏览器缓存/换过浏览器（H5 的 localStorage 按浏览器 + 域隔离）、卸载重装过 App、或系统回收了存储——机理相同：散列随本地存储一起没了。

给用户的解释（要求脱稿讲一遍）：「PIN 是这台设备的帘子，不是您账号的钥匙。钥匙（账号密码）在服务器上验证，走到哪台设备都好使；帘子是挂在每台设备本地的，新设备是新房间，得重新挂一道。这也是它安全的原因——PIN 从不离开您的手机，我们也从不保存它。」把这段与三步排查记进 notes/f5w4/。

今日名词卡

术语一句话解释
PIN 应用锁设备级快速锁：本地验证 4-6 位数字，防身边人顺手偷看；纯客户端能力
散列（hash）单向摘要：能从 PIN 算出摘要，不能从摘要倒推 PIN（不加盐时可被预计算表攻击）
盐（salt）随机串，与散列同存；让「同 PIN 同摘要」不成立，废掉彩虹表
本地存储uni.setStorage 一族；H5 落 localStorage（按浏览器 + 域隔离），App 落设备文件——都随设备/缓存存亡
威胁模型「防谁、不防谁」的明确声明；PIN 防偷看，不防 root 设备上的穷举与取证
冷却退避连续失败后逐次拉长的等待期（30s → 1min → 5min）；客户端限制，可被清缓存绕过，故需兜底
全局遮罩层挂在应用级、盖住一切页面的锁屏；层级必须高于路由，深链绕不过
重登录兜底忘记 PIN 的唯一出路：走账号密码登录（服务端验证的既有接口），流程中重设本地 PIN
onShow / onHide页面级生命周期：退后台/回前台的钩子，锁屏超时机器的计时点
