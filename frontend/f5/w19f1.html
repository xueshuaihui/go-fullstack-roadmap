subPackages 分包与按需加载

面矩阵能渲染了，下一个问题：点进一个面，那些页面从哪来？今天学 pages.json 的 subPackages 分包——本站纪律：分包集合 = 已出生面域减去 homeos。这条判据是 F5 阶段判据之一：「能在 pages.json 里配出一个分包，并说明它何时被下载」。对应服务端 S7 阶段的面配置与按需加载课。

今日目标

判据提醒：agent 早就把分包配好了。你的判据是能自己配一个、能讲清下载时机、能把挪包后的路径全部修对——不是「分包已经存在」。

1. 为什么分包：主包是有硬上限的

小程序平台对包体积有硬限制（以微信小程序的通行口径：主包不超过 2MB，整包上限大得多但也有限，具体以平台当期规则为准）。就算不触上限，主包越大，用户首次打开越慢——首次启动要把主包整个下下来。分包（subPackages）把「不是人人都要、不是每次都要」的页面拆出去：

问题答案
分包何时被下载？首次导航进入该分包内的任一页面时，由平台按需下载；下载完成前用户会感到一次短暂等待。之后走缓存
能提前下吗？能。preloadRule 可以声明「进入某页面时，在某种网络条件下预下载哪些分包」（比如进首页时仅在 wifi 下预载财务分包）
H5 端呢？H5 没有「包」的下载概念，subPackages 只影响目录结构与路由；H5 能跑不代表小程序能跑——分包问题几乎只在小程序端暴露

React 对照：这相当于 React.lazy + 路由级 code splitting——构建期切块、运行期按需拉取。差别在于：Web 的 chunk 是你自己的服务器发的，拉不拉得到看网络；小程序的分包是平台托管的，尺寸超限、路径没注册，平台直接拒。

2. 为什么按业务域分，而不是按页面数量分

本站的七类命名是同源的，分包边界必须落在这条同源链上：

片段 · 七类命名同源（一个业务域一个 code）服务/模块 svc-{code}   schema {code}   接口 /api/{code}/*   事件 {code}.*
表前缀 {code}_         迁移 {code}_{seq}_{desc}            页面 pages/{code} 分包

按业务域分包意味着：分包边界 = 服务端模块边界 = 接口前缀边界 = 表前缀边界。一个 bug 报上来，「财务分包里的页面报错」直接对应「/api/finance/* 接口、internal/finance 模块」，三段定位法（F6 正式练）的第一刀就切在这里。反过来，如果按页面数量分（凑满 15 页切一包），一个包里混着三个域的页面，命名同源断裂，「面出生 = 新增一个域」也没法映射成「新增一个分包」。面的出生与未出生是域级别的，所以分包也必须是域级别的。

3. 分包集合 = 已出生面域 − homeos

公式里那个减号有实打实的理由：HomeOS 的页面（登录、注册、家庭、成员、首页、通知、设置）是所有面的前置——任何面页面被打开时，用户必然已登录、已有家庭上下文。如果把这些前置放进分包，就会出现「进任何分包页面之前，得先保证 homeos 分包已下载」的循环依赖，主包反而空心化。所以 HomeOS 页面全部留在主包，财务面是第一个分包：

片段 · pages.json（分包配置的标准形态）{
  "pages": [                          // 主包：首页 + homeos 域页面
    { "path": "pages/homeos/home/index" },
    { "path": "pages/homeos/auth/login" },
    { "path": "pages/homeos/notify/list" }
    /* …其余 homeos 页面… */
  ],
  "subPackages": [
    {
      "root": "pages/finance",        // 分包根 = 业务域目录
      "pages": [
        { "path": "home/index" },     // 完整路由 = /pages/finance/home/index
        { "path": "tx/list" },        // 完整路由 = /pages/finance/tx/list
        { "path": "tx/edit" }
      ]
    }
  ],
  "preloadRule": {
    "pages/homeos/home/index": { "network": "wifi", "packages": ["pages/finance"] }
  }
}

两个必须盯住的细节：① 分包内 pages[].path 是相对 root 的，完整路由 = /root/path——把 root 前缀再写进 path 里（"pages/finance/tx/list"）是最常见死法；② pages.json 里依然不许出现 tabBar 字段，分包与否不改变自绘底栏的纪律（底栏五项全是 homeos 页面，都在主包，所以底栏切换永远不会触发分包下载）。

资源引用限制（小程序端硬规则）：

引用方向允许？说明
主包 → 分包资源禁止主包构建时不含分包文件，引用了直接编译失败或运行时报错
分包 → 主包资源允许公共组件放主包 components/、主题 scss 放主包 styles/，各分包共用
分包 → 另一分包默认禁止平台有「分包异步化」例外，本课程不用——需要共用的东西一律上提到主包

顺带认识一条接口：GET /api/homeos/app/bundles——服务端按面 codes 返回各分包的 version/url/sha256 等清单信息。但注意边界：真实的 .wgt 远程下发链路不在本课程范围内，我们的分包是本地构建期切分、由小程序平台按需下载，不是运行时从自己服务端拉的。这条接口只做清单契约。

挪包三连坑预警：静态图片跟着页面进了分包、却被主包某处引用（违反 §3 表格第一行）；路径大小写在模拟器能过、真机报错（真机文件系统大小写敏感）；只测了 H5 就宣布完成（H5 没有分包语义，什么都看不出来）。

定位题（三分法：源配置 → 构建产物 → 运行时）

现象：分包之后，点财务面入口报「页面不存在」（page not found）。是 pages.json 没注册、路径多写/少写了分包根、还是构建产物没更新？

三个候选按「从源头到运行时」的顺序判：

  1. 源配置：打开 web/src/pages.json，确认目标页面在 subPackages 对应条目的 pages 数组里，且 path 是相对 root 的。两种高频错：path 里重复带上了 root 前缀（拼出 /pages/finance/pages/finance/tx/list 这种双段路径）；或页面文件挪了、pages.json 忘了登记。手工拼一遍完整路由 = /root/path，和跳转代码里的 url 逐字符比对（包括大小写）。
  2. 构建产物：源配置没错还报不存在 → 怀疑跑的是旧产物。打开 dist/ 下对应平台的产物（小程序端是 app.json），搜这个路径在不在注册表里。不在 = 没重新构建 / 热更新失效，重跑构建命令（cd <你的学习仓根目录>/web 后按项目脚本执行）再看。
  3. 运行时路径：产物里也有、还是跳不过去 → 在 Console 里看报错原文与 getCurrentPages()：报错里的 url 就是运行时真实拼接结果，拿它和产物注册表比对，通常能看出跳转代码在某处动态拼串（比如 `/pages/${face.code}/…` 模板）拼少了一段 root。这类问题的修法是让跳转路径只从一个路由常量表出，不散落拼串。

结论句式：源配置定「注册与拼法」，构建产物定「跑的是不是新代码」，运行时报错定「实际拼出来的字符串」。三层各管一段，逐层向下。记进 notes/f5w3/。
