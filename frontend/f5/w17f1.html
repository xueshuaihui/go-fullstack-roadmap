壳的顶栏一行与自绘底栏

从今天起进入 F5：app 壳基座。此前 web/ 里已经有真实的财务面页面（列表、表单、图表、游标分页都是 F4 验收过的），F5 学的不是某个业务页，而是承载所有业务面的那个外壳——顶栏一行、自绘底栏五项、以及壳级状态 useShellStore。对应服务端 S7 阶段（面配置、首页合成、到期注册、通知、设置）。下文所有相对路径都从仓库根（你的学习仓根目录）起算。

今日目标

F 卡的判据是「你能不能讲清 / 能不能改」，不是「代码写没写出来」——壳的代码是 agent 写的。不许拿「页面能跑」当自己通过了：底栏显示正常不代表你讲得清它为什么必须是自绘的。

1. 壳是什么：顶栏一行 + 自绘底栏 + 页面容器

「壳」= 每个业务页面外面那一圈公共 UI：顶部一行（标题 / 家庭切换入口 / 未读铃铛）、底部五项（首页 / 面矩阵 / 到期 / 通知 / 我的）、以及页面内容区的容器约束（底部留白、安全区）。对照 React：你在 SPA 里会写一个 <Layout> 组件包住 <Outlet />，布局天然全局生效。uni-app 没有这个机制——每个页面是独立的页面实例，pages.json 只声明路由与窗口样式，不提供「全局布局组件」。所以壳只有两种落法：

方案做法本项目
原生 tabBarpages.json 里声明 tabBar 字段，底栏由平台渲染，切页走 uni.switchTab禁用（见 §2）
自绘壳组件壳是普通 Vue 组件（ShellTopBar / ShellTabBar），每个页面在模板里引用它，或用布局组件包一层采用

自绘的代价要先讲清：壳组件不是全局注入的，哪个页面忘了引用，哪个页面就没有顶栏底栏——这正是今天定位题的现场。React 开发者最容易在这里翻车：你以为布局是「框」，在 uni-app 里它是每页自己搬进来的「家具」。

2. 为什么 pages.json 不能有 tabBar 字段

这是一条历史反例：某个旧项目既在 pages.json 注册了原生 tabBar，又用自定义底栏组件接管导航，结果两套系统同时生效——

病症机制
双底栏原生 tabBar 由平台渲染在窗口底部，自绘底栏又是一个 fixed 组件，叠在一起
页面栈不可预期uni.switchTab 会关闭所有非 tabBar 页面并清空页面栈；自绘底栏若用 navigateTo/reLaunch，两套导航语义混用，返回键行为随机
有的页面有底栏、有的没有原生 tabBar 只出现在 tabBar.list 登记的页面上；自绘组件却可以出现在任何页面——两者集合不一致

那为什么不一开始就用原生 tabBar？因为本项目底栏五项与面矩阵都必须由服务端数据驱动：未读徽标要读 useShellStore、入口要按角色与面配置显隐，而原生 tabBar 是 pages.json 里的静态配置，改一项都要 uni.setTabBarItem 逐条命令式调用，与「面清单只能来自服务端 faces[]」的红线（下一张卡讲）天然打架。所以本站纪律钉死：pages.json 不得出现 tabBar 字段，底栏一律自绘；CI 第一查这条。

自绘之后，「五个 tab 页」其实只是五个普通页面。底栏切换用 uni.reLaunch（清栈重建，模拟 tab 语义），不能用 uni.switchTab——没有原生 tabBar 注册时 switchTab 直接报错。页面内的正常跳转仍用 navigateTo / redirectTo。

3. 顶栏一行制：放什么、不放什么

「一行制」是壳基座的产品纪律：顶栏只有一行，放三样东西，多一样都不行——溢出的入口收进「我的」页：

位置内容数据来源
左当前页标题页面传入（props）
中/右家庭切换入口（当前家庭名）useFamilyStore；切换动作调 POST /api/homeos/families/switch，服务端重新签发 token（F3 讲过：切换家庭 = 换 token，不是前端改个上下文变量）
右未读铃铛 + 徽标useShellStore.unread，点击进入通知页（GET /api/homeos/notifications）
片段 · ShellTopBar.vue（起点代码，动手改在这上面做）<template>

4. 未读计数：为什么全站只有 useShellStore 一份

未读的唯一真源在服务端：按当前成员聚合未读数。它有且只有三个出口，且必须同口径：

出口时机
GET /api/homeos/home/summary 的 unread进首页，随首屏单请求一起回来
GET /api/homeos/notifications 响应带的 unread进通知列表页
POST /api/homeos/notifications/read 响应带的 unread标记已读（含全部已读）之后

前端侧的对应纪律：这三个出口回来的数字一律写进同一个 useShellStore.unread，顶栏铃铛和底栏徽标都只读这一份。如果各页面各存一份（列表页一个 ref、首页一个 ref），必然出现：标记已读后顶栏还挂着旧数字、两个页面徽标不一致、或者为了同步而多发请求。React 对照：这就是「同一份服务器状态被复制进多个组件 state」的经典病，你在 React 里怎么用「提升到唯一 context / 单一 store」治它，Vue 里就怎么用 Pinia 治它——store 是全站唯一实例，任何组件 useShellStore() 拿到的是同一份响应式对象。

片段 · stores/shell.jsexport const useShellStore = defineStore('shell', () => {
  const unread = ref(0)          // 全站唯一一份未读计数
  const period = ref('')            // 时间窗，同样全站唯一（F4 讲过）
  // 三个出口，三个写入口径一致的 action——数字永远来自服务端响应
  function applySummary(data) { unread.value = data.unread ?? 0 }
  function applyNotifications(data) { unread.value = data.unread ?? 0 }
  function applyRead(data) { unread.value = data.unread ?? 0 }
  return { unread, period, applySummary, applyNotifications, applyRead }
})

前端永远不要自己算未读（比如「本地把数字减一」）。减一看似即时，实则口径漂移：服务端可能因为新通知到达、别的设备已读而变化。正确姿势是乐观更新可以，但以下一次响应为准——而 notifications/read 的响应本身就带 unread，直接用它是零成本的。

动手改（今天的判据现场）

在 web/src/ 里找到 ShellTopBar（§3 的片段就是它的骨架），给它加一个「成员管理」入口，并让它按角色显隐。改动直接落在学习仓里，改完要能跑给下一个判据看：

验收不是「按钮出现了」，而是你能讲清三句话：角色从哪来（会话快照）、为什么 v-if（零渲染）、前端显隐和服务端权限各管什么（体验 vs 安全）。

定位题（三分法：配置层 → 引用层 → 运行层）

现象：底栏在大多数页面正常，但在某几个页面「消失了」。

三个候选原因：① 页面没引壳组件 ② 分包页面路径不对 ③ 原生 tabBar 残留配置在生效。按这个顺序判，每一步都能排除一类：

  1. 先查配置层（10 秒钟）：打开 web/src/pages.json，搜 tabBar 字段。有 → 就是原因 ③：原生 tabBar 只渲染在它 list 里登记的页面上，没登记的页面「天生没底栏」，而且登记过的页面可能看到双底栏。删掉该字段重新构建。没有 → 排除 ③，继续。
  2. 再查引用层：打开消失底栏的那个页面文件，看模板里有没有引用 ShellTabBar（或被壳布局组件包裹）。自绘底栏不是全局注入的——哪页没引，哪页就没有。这是自绘方案最常见的死法，对应原因 ①。
  3. 最后查运行层：底栏组件引了却不显示？在 Console 里敲 getCurrentPages() 看当前页面实例的 route，和 pages.json（含 subPackages）里登记的路径逐字比对——分包页面的完整路径 = 分包 root + 页面 path，跳转串少写或多写一段都会落到「没被壳包裹的地方」，对应原因 ②。同时看 Console 有没有组件渲染报错。

结论句式：「pages.json 里有没有 tabBar」分掉配置层；「页面模板里有没有壳组件」分掉引用层；「getCurrentPages() 的路径和注册表对不对得上」分掉运行层。把这条三分法记进 notes/f5w1/——它是 F6 三段定位法在壳问题上的一次具体化。
