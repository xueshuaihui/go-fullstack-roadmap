F2 · uni-app 工程与路由

这一段有一个转折，先说清楚：从今天起你看的是真代码，不是我给你的片段。F1 那四张卡教的是日卡内嵌的 SFC 片段——那时 web/ 这个目录还不存在，练习文件全部放 notes/ 下、不进任何构建、也不要求跑起来。agent 在服务端 S3·D1 第一次介入，脚手架出 web/：一个 Vue 3 + uni-app 工程，外加一层 src/api/http.js 请求封装。所以 F2 起，你有真实的目录可以 cd 进去、可以全局搜索、可以在浏览器里点、可以用 devtools 看 Network。教材从「片段」换成「工程」，判据没换。

这一段两张卡，回答两个问题：一个 uni-app 工程该怎么读（哪个文件决定有哪些页面、哪个决定页面长什么框、哪个决定请求发到哪台机器），以及一个请求从页面出发到数据上屏，中间经过了什么。后者是「能不能独立定位一个 bug 在前端还是服务端」这条硬判据最有用的一课：请求层就是前后端的边界，边界读懂了，「数据是服务端没给，还是前端没接住」只需要看一个地方。

为什么判据还是「能讲清 / 能改」

工程能跑起来、页面能打开、请求能发出去——这些都是 agent 的产出，不是你的判据。F2 的判据是两句话：① 能讲清 pages.json 里为什么不能有 tabBar 字段；② 能把请求指向你本地的 Go 服务并看到响应，且说清这条响应经过了哪几次加工。完成检查里没有一条是「页面跑起来了」。工程现在能跑，恰恰是最容易骗过自己的时候——不许拿「页面能跑」当自己通过了。

顺带说清「指向本地服务」改的是哪里：不是 http.js 里的 baseURL（它固定是 '/api'，三种环境都不改），而是 H5 联调时的 devServer 代理。这条区分本身就是 F2 的判据之一。

不通过就原地重做，不跳阶段。F2 是 F3 的地基：F3 的登录态持久化要靠 App.vue 的 onLaunch 时机、路由守卫要靠这一段的页面栈与页面生命周期、401 重放要靠这一段的请求层。这三处跳过去，F3 会变成背结论。

本阶段不做什么（明确划掉，免得手滑）

  • 不学 Pinia、不碰登录态与守卫——那是 F3；这一段的 stores/ 目录只需要知道它存在、各文件管什么
  • 不配 tabBar、不写 switchTab、不在客户端硬编码任何入口清单（底栏由 shell 自绘，面清单只能来自服务端）
  • 不做分包与按需加载的深入配置——这一段只认「主包 = homeos，分包 = 已出生面域减去 homeos」这条口径，subPackages 的细节在 F5
  • 不做游标分页的前端侧（下拉刷新重置游标、触底续读）——那是 F4 兑现的伏笔；这一段只要认得分页信封 {list, next_cursor, has_more} 的形状
  • 不写死任何色值、不改 baseURL 成绝对地址、不引入 axios；也不把 React 代码搬进来当实现——React 在本段只作为概念对照出现
  • 不因为「工程能跑」就跳过动手改。练习页改完必须删干净，留在工程里就是「注册了但没用的假入口」
