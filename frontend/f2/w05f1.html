uni-app 工程结构怎么读：pages.json 与配置式路由

从今天起，你看的是真代码，不是我给你的片段。F1 的四张卡里，所有 SFC 都是日卡内嵌的练习文件，跑不起来也没关系——那时 web/ 这个目录根本不存在。agent 在服务端 S3·D1 第一次介入，脚手架出了 web/：一个 Vue 3 + uni-app 工程，加一层 src/api/http.js 请求封装。所以现在你手上有可以 cd 进去、可以 npm run dev:h5 起在浏览器里点、可以用编辑器全局搜索的真实工程。今天这张卡的任务是把这个工程的骨架读通：哪个文件决定「有哪些页面」、哪个决定「页面长什么框」、哪个决定「请求发到哪台机器」。

今日目标

判据没变。工程能跑起来是 agent 的功劳，不是你的。今天你要拿走的是三句话：① 「这个页面上不去，我该改哪个文件」；② 「这个入口是谁注册的」；③ 「这个 bug 是路由配置的问题，还是组件本身的问题」。完成检查里没有一条是「新页面跑起来了」——不许拿「页面能跑」当自己通过了。

四个「配置类」文件的分工，用你熟的话说：

文件管什么React 世界里最接近的东西
src/pages.json有哪些页面（路由表）、每页的窗口样式（标题栏、下拉刷新）、分包划分、全局窗口样式路由表 + 每个 route 的 layout 配置，但它是编译期读的 JSON，不是 JSX
src/main.js创建应用实例、装插件（Pinia）、挂载src/main.jsx 里的 createRoot().render()
src/App.vue应用级生命周期（onLaunch / onShow / onHide）与全局样式；它自己没有模板内容最外层 App 组件，但只管「应用整体出生/回前台/进后台」，不管页面渲染
src/manifest.json各端打包配置：appid、图标、vueVersion: "3"、H5 的 devServer.proxy没有单一对应物，约等于 vite.config 的 server 段 + 应用商店元信息

「改一件事该去哪个文件」是今天的实用产出：加一个页面 → pages.json + pages/ 下的 .vue；改某页标题栏文字 → pages.json 里那一页的 style；改全局标题栏配色 → pages.json 的 globalStyle（值写主题令牌，不写色号）；把请求指到你本地的 Go 服务 → manifest.json 的 H5 代理；改启动时做的第一件事（比如读回登录态）→ App.vue 的 onLaunch。

App.vue 没有 <template>——这是它与普通页面组件最大的区别。它不是一个「渲染出来的东西」，是应用本身。想找一个「所有页面共用的布局组件」，在 uni-app 里不是 App.vue，而是你自己写的一个 shell 组件（底部五项、顶栏一行都由它自绘），由各主页面包进去。

2. pages.json：配置式路由，以及那条不许碰的字段

片段 · src/pages.json（节选，注意没有 tabBar）{
  "pages": [
    { "path": "pages/homeos/home/index",
      "style": { "navigationBarTitleText": "首页" } },
    { "path": "pages/homeos/auth/login",
      "style": { "navigationStyle": "custom" } },
    { "path": "pages/finance/category/list",
      "style": { "enablePullDownRefresh": true } }
  ],
  "globalStyle": {
    "navigationBarBackgroundColor": "@bg-nav",   // @xxx = uni.scss 里的主题令牌
    "navigationBarTextStyle": "black"
  },
  "subPackages": [
    { "root": "pages/finance", "pages": [ /* … */ ] }
  ]
}

四条读法：

字段读法
pages[]页面注册表，数组第一项就是启动页（不是 / 匹配出来的，是「第 0 项」）。每项 path 不带前导斜杠、不带 .vue；style 是这一页的窗口配置
globalStyle所有页面的默认窗口样式，单页 style 覆盖它
subPackages[]分包：root + 分包内 pages[].path 拼出完整路径。本项目口径：主包 = homeos，分包集合 = 已出生的面域减去 homeos。分包与按需加载在 F5 展开，今天只认这条口径
easycom组件自动引入规则（符合目录约定的组件不用手写 import）。看到某组件「没 import 也能用」，答案在这里

为什么 pages.json 里不能有 tabBar 字段。三个理由，一个比一个硬： ① 会出现两个底栏。tabBar 一旦写上，框架就自己渲染一个原生底部栏；而本项目的底栏是 shell 组件自绘的（因为「哪几项可见」必须来自服务端下发的面清单，不是编译期写死的）。两份底栏叠在一起，视觉与点击区全乱。 ② 路由语义会打架。被写进 tabBar 的页面从此只能用 switchTab 跳，用 navigateTo 会静默失败；而 shell 自绘底栏走的是自己的跳转逻辑。同一批页面两套跳法，bug 会以「点了没反应」的形式出现，且不报错。 ③ 那是第二份页面清单。tabBar.list 里必须硬编码每一项的 pagePath 与文字，等于在客户端写死了一份「有哪些入口」——直接违背「面清单只能来自服务端、客户端不得二次裁剪也不得硬编码」这条纪律。 所以本项目把它当红线：CI 第一查就是这条。

三段式路径的每一段都是有含义的，不是随手起的目录名：

口径 · pages/{code}/{feature}/{action}pages/homeos/auth/login      code=homeos   feature=auth     action=login
pages/homeos/family/list     code=homeos   feature=family   action=list
pages/finance/category/list  code=finance  feature=category action=list
pages/finance/tx/create      code=finance  feature=tx       action=create

{code} 这一段与服务端的七类命名同源：路由分域 /api/homeos/* 与 /api/finance/*、schema homeos 与 finance、表前缀 homeos_ 与 finance_、分包目录 pages/homeos 与 pages/finance——同一个 code 在前后端指同一个业务域。看到一个页面路径，你立刻知道它的数据来自哪个域的接口，这在定位 bug 时能省一半时间（对应服务端 S2·D1 立下的路由分域）。

3. 配置式路由 vs React Router：差别在哪

维度React Router（声明式）uni-app（配置式）
路由表在哪JSX 里：<Route path element>，与组件同文件、可以是变量、可以运行时拼装pages.json 的 pages[]，编译期读的静态 JSON，不能写表达式
启动页由 path="/" 匹配决定由数组顺序决定：第 0 项就是启动页
怎么跳声明 <Link>，或调 navigate()只能调 API：uni.navigateTo 等。没有 <Link> 这种东西
路由守卫路由表里的钩子：loader / 包一层 <RequireAuth>配置里没有钩子的位置。只能全局拦跳转 API，或在每页自己的生命周期里判（F3 第 2 张整张卡讲这个）
参数路径参数 :id + useParams()路径里不放参数段，参数走 query：uni.navigateTo({ url: '…?id=3' })，页面在 onLoad(options) 里取
懒加载React.lazy + Suspense，你自己决定切分点按 subPackages 切，框架决定何时下载
URL 的地位URL 是状态源，可分享、可后退、可直接落内页页面栈是状态源；H5 端有 URL 但它是结果不是入口约定（不过用户仍然能刷新落在内页，守卫必须兜住这种情况）

页面栈与四个导航 API 的分工，这张表建议抄进 notes/：

API对页面栈做什么什么时候用
uni.navigateTo压栈（旧页留在栈里，可返回）绝大多数「进入下一级」：列表 → 详情、首页 → 记账
uni.navigateBack出栈返回上一页；delta 可以一次退多层
uni.redirectTo替换栈顶（旧页销毁，回不去）登录成功后跳到「记住的来源页」；向导的中间步
uni.reLaunch清空整个栈，只留新页退出登录、切换家庭（F3 第 3 张）、跳回首页
uni.switchTab跳到 tabBar 页本项目用不上——没有 tabBar 就没有它的目标。看到代码里出现它，当成缺陷报给 agent

为什么 shell 自绘底栏切主入口要用 reLaunch 而不是 navigateTo：底栏五项之间来回切，如果用 navigateTo，页面栈会一直变深（小程序端上限 10 层，超了跳转直接失败），而且返回键会变成「回到上一个主入口」这种诡异行为。reLaunch 每次清栈，语义就是「我换了一个大区」。

页面自己的四个生命周期钩子（来自 @dcloudio/uni-app，与 F1 讲的组件钩子是两套东西，同时存在）：

钩子时机典型用途
onLoad(options)页面创建时一次，能拿到 query 参数解析 options.id、决定要不要读登录态
onShow每次页面显示（含从下一页返回时）拉/刷新数据、守卫兜底判断
onHide页面被盖住（跳到下一页）暂停轮询
onUnload页面出栈销毁清定时器（与 F1·w04 的 onUnmounted 同理）

「从下一页返回，onMounted 不会再跑」——因为上一页组件根本没销毁，只是被盖住了。所以「返回后要看到最新数据」这件事必须写在 onShow 里，不是 onMounted。这是 React 开发者在 uni-app 里踩得最响的一脚，也是 F3 第 3 张「切换家庭后列表还是旧数据」定位题的一个答案分支。

定位题（两步定论：路由配置还是组件本身）

现象：跳转时报 page not found（H5 端表现为白屏或停在原页，控制台一行 Page[xxx] not found）。

不要开始乱改。这个报错只有两个来源，两步就能定论：

  1. 第一步：把报错里的路径与 pages.json 的 pages[].path 逐字符比对。四个高频差异点——前导斜杠（url 要带、path 不带）、.vue 后缀（path 不许带）、大小写、{code}/{feature}/{action} 三段顺序写反。路径不在注册表里 → 路由配置问题，与组件无关，组件写得再对也上不去。分包页还要多比一次：subPackages[].root + 分包内 path 拼出来是否等于你 url 里写的那串；同一个页面既在主包 pages 又在分包里注册，也算这一类。
  2. 第二步：路径确实在注册表里，去磁盘上找同名的 .vue。文件不存在、或大小写与注册表不一致（本机 macOS 大小写不敏感所以能跑，构建机与 CI 上就 page not found）→ 组件层面的问题（文件放错位置 / 名字不符）。文件确实存在且大小写一致 → 看编译输出：pages.json 本身有语法错（多一个逗号、引号不配对）会让整张注册表失效，此时的特征是「所有页面都跳不动，不只是新加的这一页」。「只有一页坏」与「全站都坏」是区分「我这一页配错了」和「整张表没生效」的关键一刀。

收尾一问：跳法对不对。目标页若被你当成 tabBar 页而用了 switchTab，本项目没有 tabBar，一定失败；若目标页在分包里而分包还没下载，表现也不是 page not found 而是首次跳转有一次可感知的延迟——这两种现象别混。

把这两步补进 notes/ 里的定位笔记。F1 练的四步法（Console → Network → 绑定 → 事件）从这一张起多了一个前置层：路由层——页面根本没上去的时候，谈绑定和请求都是空的。
