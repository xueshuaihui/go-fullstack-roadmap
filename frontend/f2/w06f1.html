请求层 http.js：baseURL、拦截器与 401 重放

上一张你读通了工程骨架，这一张读唯一一个所有页面都要经过的文件：src/api/http.js。它是 agent 脚手架 web/ 时一起产出的，也是你以后定位「数据没上屏」这类 bug 时第一个要打开的文件。今天把它拆成四件事：① URL 是怎么拼出来的（以及为什么不能拼出 /api/api/）；② 请求出去之前拦截器塞了什么；③ 响应回来之后信封怎么拆；④ 401 的时候那条「换新 token → 把原请求重放一次」的链路，包括并发请求同时 401 时为什么只能刷一次。

今日目标

这一张是 F2 的技术密度峰值，也是「能定位 bug 在前端还是服务端」这条判据最有用的一课：请求层就是前后端的边界。边界上的代码读懂了，你以后判断「数据是服务端没给，还是前端没接住」只需要看一个地方。判据依然是能讲清、能改——不许拿「请求发出去了」当自己通过了。

1. URL 是怎么拼出来的：两处各出一半

服务端的接口全部挂在两个分域下：/api/homeos/* 与 /api/finance/*（没有版本号段，健康检查 /healthz 连 /api 都不带）。请求层的 baseURL 是 '/api'，所以调用方只写后半截：

片段 · 调用方怎么写（页面或 store 里）import { http } from '@/api/http'

const family = await http.get('/homeos/family')              // → GET  /api/homeos/family
const cats   = await http.get('/finance/categories')          // → GET  /api/finance/categories
const sess   = await http.post('/homeos/auth/login', { phone, password })
await http.put('/finance/categories/12', { name, version })    // → PUT  /api/finance/categories/12

「不要叠出 /api/api/」：写成 http.get('/api/homeos/family') 会得到 /api/api/homeos/family，服务端没有这条路由，落到 NoRoute 上——你会看到 HTTP 404 + code: 1001。这个现象很有迷惑性：1001 的意思是「资源不存在」，你会以为是 id 传错了，其实是前缀叠了两层。记住这条口径：baseURL 出 /api，业务路径出 /homeos/… 或 /finance/…，两处各出一半，谁都不许写全。

那 '/api' 这个相对前缀最终打到哪台机器上？分两种环境，代码里都不写机器地址：

环境谁把 /api 转到 Go 服务
H5 本地联调Vite devServer 的代理（vite.config.js 的 server.proxy，把 /api 转到你本机 Go 服务的端口；端口以服务端 .env 里的 PORT 为准）。用 HBuilderX 口径的工程会把这段写在 manifest.json 的 h5.devServer 里，两者作用相同
真机 / 打包 / 部署同域部署 + nginx 转发 /api 到服务进程（服务端 S8 做这件事）

为什么代码里坚决不写 http://localhost:8080：① App 端与真机上的 localhost 指的是设备自己，不是你的开发机，一定连不上；② 换环境就要改代码、重新打包，而相对路径 '/api' 在三种环境下都对；③ 跨域问题由代理与 nginx 在传输层解决，业务代码不感知。所以本阶段的判据「能把请求层指向你本地的 Go 服务并看到响应」，改的是代理配置，不是 http.js。

2. 响应拦截器：拆信封，只把 data 交出去

服务端所有响应都是同一个信封：{"code":0,"message":"ok","data":{…}}（服务端 pkg/response 包负责，S1 就立下了）。请求层的响应拦截器只做一件事——把信封拆掉，让页面拿到干净的 payload：

情况拦截器怎么做页面侧的表现
code === 0resolve(body.data)await http.get(…) 直接拿到 data 里的东西，不用再 .data
code !== 0reject(new BizError(code, message, body.data))进 catch，e.code 是业务码，可查文案表
HTTP 401 / code === 1005先走 refresh 链路（见 §4），刷新成功就重放原请求页面通常感知不到：拿到的是重放后的正常结果
网络失败（fail，压根没响应）reject 一个网络错误与业务错误分开处理：这个能重试，业务错误重试没用

业务码与 HTTP 状态是两件事，都要会读：

codeHTTP含义前端该做什么
1001404资源不存在（越权读也返回本码，与「真不存在」同形）显示「找不到或无权查看」，不要断言是 id 错了
1002401认证失败（凭证错误，防枚举：「手机号不存在或验证码错」统一本码）登录页红字提示，不要告诉用户是手机号还是密码错
1003403权限不足（角色矩阵拒绝 / 面未启用 / 字段不可见）跳 403 页（F3 第 2 张）
1004400参数错误表单校验没拦住，按字段提示
1005401未认证 / token 无效或过期 / 权限版本已失效交给 refresh 链路；刷新也失败才清登录态
1008409幂等冲突：client_request_id 已用过且请求体不同说明重试时换了请求体或换了幂等键，前端 bug
1009409版本冲突（乐观锁不匹配，响应体带双版本 payload）提示「已被别人改过」并重拉，不要直接重试原请求
1010409业务状态不允许把服务端 message 讲给用户听
5000500服务器内部错误「稍后重试」+ 记下 request_id，这是服务端的活

3. 完整读一遍 http.js

片段 · src/api/http.js（关键结构；工程内实现更长，逻辑等价）import { useAuthStore } from '@/stores/auth'

const BASE_URL = '/api'       // 只出前缀；调用方只写 /homeos/… 或 /finance/…

export class BizError extends Error {
  constructor(code, message, payload) {
    super(message)
    this.code = code          // 业务码，用来查中文文案表
    this.payload = payload    // 1009 时这里面是双版本，能直接给用户看差异
  }
}

let refreshing = null          // 正在进行的那一次刷新；并发 401 共用它（见 §4）

// —— 请求拦截器：拼 URL + 塞头 ——
// 这一层是「裸出口」：不带 401 处理。刷新 token 的请求必须走它，否则会自我递归
export function rawRequest(options) {
  const auth = useAuthStore()          // 必须在函数体内调，不能在模块顶层（见常见坑）
  const header = { 'Content-Type': 'application/json' }
  if (auth.accessToken && !options.noAuth) header.Authorization = 'Bearer ' + auth.accessToken
  return new Promise((resolve, reject) => {
    uni.request({
      url: BASE_URL + options.url,
      method: options.method || 'GET',
      data: options.data,
      header,
      success: resolve,                // uni.request 的 success 只看「有没有响应」，4xx/5xx 也走 success
      fail: reject,                    // 只有网络层失败才走 fail
    })
  })
}

// —— 响应拦截器：拆信封 + 处理 401 ——
async function send(options) {
  const res = await rawRequest(options)
  const body = res.data || {}

  if ((res.statusCode === 401 || body.code === 1005) && !options.noAuth && !options._retried) {
    try { await onceRefresh() }
    catch (e) { throw new BizError(1005, '登录已失效，请重新登录') }
    return send({ ...options, _retried: true })   // 重放，且只重放这一次
  }

  if (body.code !== 0) throw new BizError(body.code, body.message, body.data)
  return body.data                                  // 成功：只把 data 交出去
}

export const http = {
  get:  (url, data, opts) => send({ url, data, method: 'GET',    ...opts }),
  post: (url, data, opts) => send({ url, data, method: 'POST',   ...opts }),
  put:  (url, data, opts) => send({ url, data, method: 'PUT',    ...opts }),
  del:  (url, data, opts) => send({ url, data, method: 'DELETE', ...opts }),
}

三个容易被忽略的细节：

  • uni.request 的 success 不代表请求成功，只代表「拿到了 HTTP 响应」——401、500 一样进 success。所以状态判断必须在 success 里自己做，这一点与 axios（非 2xx 走 catch）不同，与 fetch（res.ok 要自己判）相同。
  • 没有用 axios：小程序与 App 端没有 XHR，uni.request 是唯一的跨端出口。所以「拦截器」在这里不是某个库的功能，是这个文件里两个普通函数（rawRequest 与 send）。
  • 写请求的幂等键 client_request_id 由调用方生成、放进请求体，重放时必须原样带上——换了键，服务端的幂等保护就失效了（详见 §4 末尾）。

4. 401 → refresh → 重放一次，且并发只刷一次

背景（服务端 S4 建立的口径）：access token 只活 15 分钟，refresh token 活 7 天，两个密钥分开签。所以「用着用着就 401」是正常现象，不是 bug——前端的责任是让它对用户不可见。

片段 · 完整链路// 1. 某个请求回来 401 / code 1005
// 2. 走 onceRefresh：全局只允许一次刷新在飞
async function onceRefresh() {
  if (!refreshing) {
    const auth = useAuthStore()
    refreshing = auth.refresh()                       // POST /homeos/auth/refresh {refresh_token}
      .catch((e) => { auth.clearSession(); throw e })  // 刷新也失败 → 清登录态，交给守卫跳登录页
      .finally(() => { refreshing = null })            // 无论成败都解锁，下一次 401 才能再刷
  }
  return refreshing                                    // 后来者拿到的是同一个 Promise
}

// 3. auth.refresh() 内部：用 rawRequest 直发，不走 send()
//    理由：它自己就是「刷新」，再进 send() 的 401 分支就无限递归了
//    同时它带 noAuth: true —— 过期 access token 塞进去只会再添一个 401
async function refresh() {
  const res = await rawRequest({
    url: '/homeos/auth/refresh', method: 'POST', noAuth: true,
    data: { refresh_token: refreshToken.value },
  })
  const body = res.data || {}
  if (body.code !== 0) throw new BizError(body.code, body.message)
  applySession(body.data)     // 新 access + 新 refresh（轮换：旧 refresh 当场作废）+ user/member/family
}

// 4. 刷新成功 → send({...options, _retried: true}) 重放原请求，用的是新 token
// 5. 重放后仍然 401 → _retried 已为 true，不再刷，直接抛 1005，守卫把用户送去登录页

并发场景才是这段代码存在的理由。首页一次 onShow 可能同时发三个请求（家庭信息、成员列表、分类列表），access token 刚好过期时三个都会 401：

做法结果
各自刷一次（没有 refreshing 这个共享 Promise）refresh 是轮换的：第一个刷新成功后旧 refresh token 当场作废，第二、三个拿着作废的 token 去刷 → 必然失败 → 用户被莫名登出。这是最难复现的一类 bug：只在「多个请求同时撞上 token 过期」时出现
共享一个 refreshing Promise（本文件的写法）第一个 401 创建它，后面的 401 await 同一个 Promise；一次刷新，三个请求各自重放一次。finally 里置空，保证下一轮过期还能再刷

三条不能破的规矩：① 只重放一次——_retried 标记必须在，否则服务端持续 401 时你会做出一个无限循环；② 刷新请求自己不能走 401 分支（用 rawRequest 直发 + noAuth），否则递归；③ 刷新失败必须清登录态，不能留在「有 token 但 token 是废的」这个中间态——那个状态下每个请求都要走一遍 401 链路，页面表现为「一直转圈」。

重放与幂等键的配合：写请求（如 POST /finance/transactions）必须带 client_request_id。重放时原样复用同一个 id，服务端就能识别「这是同一次操作的重试」而不会记两笔账。如果你把「重试」实现成「重新生成一个 id 再发」，那就会真的写进两条流水；如果复用 id 但改了请求体，服务端返回 1008 幂等冲突。所以看到 1008，先查前端的重试逻辑，别先怀疑服务端。

动手改（今天的判据现场）

目标：给两个业务错误码加中文文案，并让它在页面上显示出来。服务端的 message 是调试口径（英文或短句，给开发者看），用户看到的中文文案归前端管——所以工程里有一张码到文案的表。今天你来补两条。

片段 · 起点代码 src/api/error-text.jsexport const ERROR_TEXT = {
  1001: '找不到这条记录，或你没有权限查看它',
  1002: '手机号或验证码不正确',
  1003: '当前角色不能做这个操作',
  1004: '填写的内容有误，请检查后重试',

}

验收方式：把三处改动的因果讲一遍——「服务端返回 4001 → 拦截器 reject 出 BizError → 页面 catch 查文案表 → toast 显示中文」。这条链讲得出来，请求层的判据就过了。不要求你真的触发一次 4001（那要等服务端记账接口就位，对应服务端 S6）。

定位题（四处依次检查）

现象：页面一直空白，Console 里没有任何报错，Network 里那个请求是 200，但数据没上屏。

「200 + 没报错 + 没数据」是请求层最典型的三不管地带。按这个顺序走，四处之内必定论：

  1. Network 的 Response 面板，看信封本身。三件事一起看：statusCode 是不是 200、body.code 是不是 0、body.data 里的字段名与层级长什么样（是 data.list 还是 data 直接就是数组？分页信封还有 next_cursor 与 has_more）。code 不是 0 就说明这其实是个失败响应，200 只是传输层的状态——这时它是服务端问题或参数问题，不是「数据没上屏」。data 里字段就缺 → 服务端，到此结束，别再看前端一行代码。
  2. 在 await http.get(…) 后面打一行日志，看页面到底拿到了什么。拿到 undefined → 拦截器剥信封剥错了层（成功分支 return body 而页面又 .data 了一次，或者反过来多剥一层）；拿到对象但字段与 ① 里看到的不一致 → 中间有别的代码改过它；拿到 完全没打日志 → 说明这一行压根没执行，跳去 ③。
  3. 赋值那一步，以及有没有被静默吞掉。四个高频死法：list.value = res.list 漏了 .value（F1·w01 讲过，值不更新且不报错）；赋给了一个普通变量而不是 ref；.then 里 return 了但外面没接；.catch(() => {}) 空 catch——这一条是「Console 干净」的头号原因，业务错误被吞掉后，页面就只剩初始值（空数组），看起来像「没数据」而不是「出错了」。
  4. 模板那一步。字段名对不对（服务端是蛇形 next_cursor、*_cents，模板里写成驼峰就是 undefined）；v-for 的源是不是那个 ref（解构过 store 的话响应性已经断了，F1·w01 那条坑）；有没有一个 v-if 把整块挡住了（v-if="loaded" 而 loaded 从没被置 true、或 v-if="list.length" 而列表确实是空的）；金额是不是忘了 / 100（服务端一律给 *_cents 整数）。

定论口径：① 与 ② 之间是前后端边界——① 里字段就缺，服务端；① 有而 ② 拿到的是 undefined，前端拦截器。③ 与 ④ 全在前端。把这条「四处顺序」写进 notes/，接在 F1 那份四步法后面：F1 那套从 Console 开始，这套专治「Console 什么都没说」。

今日名词卡

术语一句话解释
统一响应信封{code, message, data}；服务端每个接口都这么返，前端在拦截器里拆一次
业务码 vs HTTP 状态code 是业务结论（0 才算成功），HTTP 状态是传输层结论；判成功只看 code，判要不要刷 token 看 401
请求拦截器请求发出前统一加工：拼 baseURL、塞 Authorization、塞幂等键
响应拦截器响应回来后统一加工：拆信封、code!==0 转成异常、401 转成刷新流程
access token短命凭证（15 分钟），放在 Authorization: Bearer … 里，每个请求都带
refresh token长命凭证（7 天），只用来换新 token，且是轮换的——用一次就作废
重放（replay）刷新成功后把原请求原样再发一次，只重放一次，靠 _retried 标记兜底
单飞 / 刷新队列把「正在进行的那一次刷新」存成共享 Promise，并发请求都 await 它，保证只刷一次
BizError带 code 与 payload 的错误对象，让页面能按码分支处理而不是靠字符串匹配 message
client_request_id写请求的幂等键；重试与重放必须复用同一个，否则要么重复入账要么收到 1008
分页信封列表型 data 的形状：{list, next_cursor, has_more}；游标不透明，前端不得解析或自造
