组件拆分实战：把流水列表页拆成四块

F4 是全课程前端线最长的一段，对应服务端 S5（并发与工程化）+ S6（财务功能面 30 条接口）。和 F1 不一样：现在 web/ 里已经有真实页面了——F2 建好了工程与请求层，F3 建好了 Pinia store 与路由守卫，服务端也开始吐出真实的财务数据。F4 的主题只有一句话：把 agent 写出来的这些页面，变成你能拆开、能改、能调的东西。第一刀，砍在财务面最核心的页面上：流水列表页。

今日目标

判据提醒：F 段的判据全是「你能不能讲清 / 能不能改」，不是「代码写没写出来」——页面代码是 agent 写的。不许拿「页面能跑」当自己通过了。今天通过的标准是：对着拆好的四个文件，每个都能说出「输入是什么、对外发什么事件、状态归谁」。

1. 拆之前：这个页面长什么样、数据从哪来

流水列表页的路由是三段式 pages/finance/tx/list（F2 讲过的 pages/{code}/{feature}/{action} 约定）。它的数据来自 GET /api/finance/transactions，响应是全站统一的信封 + 游标分页结构（分页的前端侧是本阶段第 4、5 张卡的正题，今天只需要知道形状）：

片段 · 响应形状（字段以 agent 实现为准，这里是示意）{ "code": 0, "message": "ok", "data": {
    "list": [
      { "id": 1024, "type": "expense", "amount_cents": 3500,
        "category_name": "餐饮", "account_name": "零钱账户",
        "occurred_at": "…", "note": "午饭" }
    ],
    "next_cursor": "…", "has_more": true
} }

agent 最初交出来的版本，很可能是「一口锅」：请求、筛选状态、列表渲染、空态、金额格式化全部写在一个几百行的 list.vue 里。能跑，但你改任何一个字段都要在整口锅里找。今天的任务就是把它拆成四块：

片段 · 拆分目标（文件放在页面同级 components/ 下）web/src/pages/finance/tx/
├── list.vue                 // 页面（容器）：发请求、持有全部状态、组装
└── components/
    ├── TxFilterBar.vue      // 筛选条：时间窗 + 分类 + 账户
    ├── TxList.vue           // 列表：v-for 渲染 item，转发点击
    ├── TxListItem.vue       // 单行：金额、分类、账户、时间
    └── EmptyState.vue       // 空态：一张图 + 一句话 + 可选按钮

2. 边界怎么划：props 往下、emit 往上、状态留在页面

拆分的核心决策只有一个：状态归谁。答案沿用 F1 第 3 张卡立下的判据——「数据的家只有一个，其他人都是租客」。这个页面的所有数据状态（列表、筛选条件、加载态）都有多个消费者，所以全部留在页面（容器）里；四个子组件全是展示组件：只吃 props、只发事件、自己不发请求。

组件props（下行）emits（上行）本地状态
TxFilterBarperiod、categories（分类可选项）、accounts（账户可选项）apply（带新筛选条件）下拉面板开没开（只有它自己关心，放子）
TxListitems、loading、hasMoreitem-click（透传被点的 item）无
TxListItemitem（一行流水对象）click无
EmptyStatetext（提示语）无（或一个 action 按钮事件）无

展示组件的样板长这样（注意：没有任何 import http 的行）：

片段 · TxListItem.vue（展示组件的形）<template>
  <view class="tx-item" @click="emit('click', item)">
    <text class="tx-item__amount">{{ amountYuan }}</text>
    <text class="tx-item__sub">{{ item.category_name }}</text>
  </view>
</template>

<script setup>
import { computed } from 'vue'
const props = defineProps({ item: { type: Object, required: true } })
const emit = defineEmits(['click'])
// 金额是 *_cents 整数：显示时除以 100，绝不用浮点累加（F4 第 6 张卡展开）
const amountYuan = computed(() => (props.item.amount_cents / 100).toFixed(2))
</script>

页面这边只剩三件事：发请求、存状态、组装：

片段 · list.vue（容器：组装四块）<TxFilterBar :period="shell.period" :categories="categories" @apply="onFilterApply" />
<TxList v-if="items.length" :items="items" :loading="loading" @item-click="goDetail" />
<EmptyState v-else-if="!loading" text="这个时间窗还没有流水" />

对照 React：这就是「容器组件 + 展示组件」模式，一模一样——容器管数据与副作用，展示组件是准纯函数（props 进、事件出）。差别只有两处：① React 把回调函数当 props 往下传（onItemClick={fn}），Vue 用显式声明的事件（emit('item-click')）；② React 里你习惯把状态更新写成不可变替换，Vue 里直接 items.value.push(x)（F1 第 1 张卡讲过的心智模型差异）。

3. provide/inject：什么时候该用，什么时候不该

provide/inject 是 Vue 版的 React Context：祖先 provide(key, value)，任意深度的后代 inject(key) 直接取，跳过中间所有层。

片段 · provide / inject// 祖先（页面或布局组件）
import { provide } from 'vue'
provide('theme', themeTokens)

// 任意深度的后代
import { inject } from 'vue'
const theme = inject('theme')

启用它之前先问两个问题：

问题答案 → 决策
中间层组件消费这个值吗？消费 → 老老实实传 props（它本来就要拿到）；纯路过 → 才考虑 provide/inject
要穿过几层？两三层 → props 完全够，别引入魔法；四五层以上的纯透传 → provide/inject（或干脆进 Pinia）
这个值跨页面共享吗？是 → 不是 provide/inject 的活，进 Pinia store（比如 period 住在 useShellStore，F3 建好的）

套到今天这个页面：页面 → TxList → TxListItem 只有两层，而且每层都消费自己那份 props，所以整页不需要 provide/inject。它真正的用武之地是 shell 级的东西——主题令牌（下一张卡）、全局弹窗服务这类「谁都可能要、中间层不关心」的值。

坏味道路标：如果你在子组件里看到 inject('items') 这种「本该是 props 的业务数据」，说明有人为了省两行绑定把数据流藏进了暗道——排查时要多翻一层才找得到数据的家。业务数据走 props，环境级数据（主题、locale、当前家庭上下文）才走 provide/inject 或 store。

4. 拆完怎么确认没拆坏：假数据单独渲染法

拆分最常见的事故不是「编译不过」，而是「看着没变，其实某个绑定断了」。给你一个能跑的判断法，两分钟出结论：

  1. 假数据单独渲染：建一个临时调试页，把每个展示组件单独摆一遍，props 喂手写的固定假数据（三行流水、一个空列表、一个 loading 态）。四个组件各自都能正确渲染 → 组件自身的渲染层没坏。这一步把「渲染问题」和「数据流问题」切开了。
  2. 接回真实数据流：调试页没问题后回到真页面。真页面缺什么字段、显示什么怪值，问题必在容器到组件之间的那根线（绑定漏冒号、传错层级、拿 props 初始化本地副本后分家——最后这个是 F1 第 3 张卡定位题的老朋友）。
  3. 单点改动检查：拆分的收益要当场验收——随便改一个显示字段，git diff 应该只动一个文件。如果改一个字段要动三个文件，说明边界划错了（数据或逻辑放错了家）。

对照 React：这套方法和你在 React 里给展示组件写 Storybook story 是同一个思路——先用固定 props 证明组件是纯的，再谈数据流。本项目不引入 Storybook，一个临时调试页就够。

定位题（bug 在哪一层：F4 的第一道）

现象：流水列表里某一行的「账户名」显示成空白，Vue 模板对 undefined 不报错，就这么静静地空着。

三个嫌疑人：接口没返、props 没传、模板 key 写错。按数据的流向走，三步定论，每步排除一层：

  1. Network 面板：找 /api/finance/transactions 的响应体，list[] 的每个元素里有 account_name 这个字段吗？没有 → 服务端问题（字段没返、名字不一致、或者被外层 data 挡了一层没解开）。到这一步就可以停，前端无辜。
  2. Vue Devtools 选中 TxListItem 组件实例：看它实际收到的 props.item，字段在吗？响应里有、props 里没有 → 断在容器到组件的传线上：绑定漏了冒号（传成字符串字面量）、容器拿错层级（res.list 写成了 res）、或者中途被 map 成了新对象时漏掉了这个字段。
  3. props 里有 → 模板 key 写错：拼写（accountName vs account_name，服务端是 snake_case）、层级（item.account.name 写成了 item.account_name）。模板里读 undefined 的属性不抛错只显示空，所以这类错永远要靠肉眼比对 key，而不是等报错。

把这条「undefined 三步定论」记进 notes/f4/ 的定位笔记——它是 F1 四步法在「拆过组件的页面」上的升级版：多了第 2 步这个「组件边界」检查点。
