深色模式：CSS 变量、theme.json 与图表重绘

上一张卡立了纪律「颜色只能引用令牌」，这张卡收利息：令牌是怎么在一夜之间全站变色的。深色模式是检验主题体系成色的唯一标准——所有硬编码色值、所有没定义的深色分支、所有不吃 CSS 变量的 canvas 图表，都会在切换的一瞬间现出原形。今天你要能讲清整套机制，并亲手给一个页面补上它缺失的深色态。

今日目标

判据提醒：通过标准不是「深色模式看起来能用」，而是你能回答：切换主题的那一刻，值是从哪里改写的、谁收到了通知、谁收不到。收不到通知的那几位（canvas 图表、原生组件）正是这张卡最值钱的部分。不许拿「页面能跑」当自己通过了。

1. 机制：一套变量名，两套值，一次根节点切换

深色模式不是「再写一套深色样式」，而是令牌体系的第二次投影。全部机关就三行：

片段 · 主题切换的核心机制/* 浅色（默认）：令牌定义在根上 */
page, .theme-light {
  --hc-bg: #f5f6f8;  --hc-card-bg: #ffffff;  --hc-text: #1f2329;
}
/* 深色：同名令牌换一组值 */
.theme-dark {
  --hc-bg: #111318;  --hc-card-bg: #1c1f26;  --hc-text: #e6e8ec;
}
/* 业务组件永远只写这一种形式，切换时自动跟着变： */
.card { background: var(--hc-card-bg); color: var(--hc-text); }

切换主题 = 把根上的 .theme-light 换成 .theme-dark（或改 data-theme 属性，效果等价）。因为 CSS 变量是运行期求值的，所有引用处瞬间解析成新值——没有任何组件需要改代码。对照 React：等价于你在根节点换 theme provider 的 value，CSS-in-JS 全树重算；Vue 这套更省，重算发生在 CSS 层，JS 一行不动。

这正是上一张卡那条纪律的兑现现场：只要有人硬编码了一处 #ffffff，它就不在任何一套令牌里，切换时必然原地不动。深色模式 bug 的第一嫌疑人永远是硬编码。

2. uni-app 的两层：darkmode + theme.json 管原生，CSS 变量管页面

uni-app（编译到微信小程序）里深色模式是两层配置，各管各的地盘，初学者最容易把它们混为一谈：

层配置管什么跟不跟随系统
原生层manifest.json 里 "darkmode": true + theme.json 定义两套值，pages.json 里用 "navigationBarBackgroundColor": "@navBg" 引用原生导航栏、状态栏、窗口背景这些不属于页面 DOM 的部分自动（微信接管）
页面层上一节的 CSS 变量 + 根节点类切换页面内容的一切颜色由你的主题模块决定
片段 · theme.json（原生层，示意）{
  "light": { "navBg": "#ffffff", "navText": "#1f2329" },
  "dark":  { "navBg": "#1c1f26", "navText": "#e6e8ec" }
}

注意 theme.json 里的值和 CSS 令牌的值必须同源维护（改一处忘另一处，就会出现「导航栏深色、内容浅色」的分裂脸）。agent 的实现里通常有一个统一的主题配置文件同时生成两边——你要能读懂它，改动时两边一起动。

3. 三态设置：为什么「系统跟随」和「手动切换」要同时支持

主题设置不是布尔，是三态：system（跟随系统）/ light / dark。两条都要，因为两个真实场景缺一不可：

  • 只支持系统跟随：晚上躺床上系统自动切深色，但用户就想看浅色（或反过来）——没有手动开关，用户只能去改系统设置，体验不可接受。
  • 只支持手动切换：用户系统层面已经全局深色，进你的应用还要再手动切一次，而且换设备/重装后设置丢失——「跟随系统」是零成本的默认正确。

实现上三态收敛成一个函数：resolveTheme(setting) —— system 时读系统当前深浅（H5 用 prefers-color-scheme 媒体查询，小程序端用 uni-app 的主题事件），light/dark 时直接用手动值。系统主题变化时也要触发重算（监听主题变更事件），否则「跟随」只在启动时生效一次，之后系统切了你不切。设置项本身持久化在本地 storage；它的服务端落点是设置接口（S7 才建，F4 期间先存本地——这个「先本地后云端」的顺序是刻意的）。

4. ucharts：收不到 CSS 通知的那位

页面 DOM 全部自动跟随，但有一个东西不会：canvas 图表。原因一句话——canvas 是像素画布，不走 CSS 渲染管线，var(--hc-primary) 传进 ucharts 的配置里只会被当成一个无效字符串。图表颜色是JS 配置：建图时传什么色，画布上就是什么色，之后令牌怎么变它都听不见。

所以令牌必须有两个投影，且同源：

片段 · 令牌的 JS 投影 + 图表重绘（示意）// theme.js：与 CSS 令牌同名同值的一份 JS 常量表（按 light/dark 两组）
export const tokens = { light: { primary: '#3d7fff', … }, dark: { primary: '#5b93ff', … } }

// 图表组件：颜色从当前主题的 JS 令牌取；主题变了必须重画
const chartOpts = computed(() => ({
  color: [tokens[currentTheme.value].primary, tokens[currentTheme.value].danger],
  fontColor: tokens[currentTheme.value].textDim,
  // …categories / series 等数据配置（F4 第 6 张卡正面讲）
}))
watch(currentTheme, () => chart.updateData(chartOpts.value))  // 没有这行 = 深色下白底图表

这张卡最容易被忽略的一条：主题切换后图表不重绘，是深色模式验收时的必现 bug——DOM 全变深了，图表还是一块浅色矩形。排查时先问「这块是不是 canvas / 原生组件」，是的话直接去看「有没有监听主题变化并重画」，不用怀疑令牌。

定位题（bug 在哪一层：那块白底是谁的锅）

现象：切到深色后，页面大部分正常，有一块还是白底。

三个嫌疑人：令牌深色分支没定义、组件用了硬编码色值、缓存/画布没刷新。按这个顺序定论：

  1. 先看这块是什么元素：普通 DOM（view/text）还是 canvas/原生组件（图表、视频、地图）？是 canvas → 直接跳到第 4 步，它压根不走 CSS。
  2. DOM 元素：devtools 选中看 Computed，找到 background-color 的来源规则。规则里写的是 var(--hc-…) → 再看这个变量在当前深色根下的解析值：解析为空 / 回落到初始值 → 令牌深色分支没定义（有人定义了浅色忘了深色，或 var() 没给回落值）。
  3. 规则里写的是字面量色值（#fff、white）→ 硬编码，上一张卡的纪律被破了。全局搜这个色值，把所有出现处换成令牌——只修这一处的话，下一个深色 bug 已经在路上。
  4. canvas / 或修完仍不对：查「主题切换的通知链」——主题模块改根节点类了吗？图表组件 watch 了主题吗？watch 里调重绘（updateData 或重建实例）了吗？还有一种「假白底」：主题设置写进了 storage 但页面用的是启动时读一次的旧值——缓存没刷，重进页面就好，这类要在主题模块里把「持久化」和「响应式当前值」分成两个东西。

注意四步的层次：元素类型 → 令牌定义 → 硬编码 → 通知链/缓存。把「深色白底四步定论」记进 notes/f4/，它会在你验收 agent 的深色主题时反复用上。
