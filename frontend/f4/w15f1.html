ucharts 图表：把报表数据画对

报表页是财务面的脸面：趋势折线、分类饼图、预算对比，数据全部来自 GET /api/finance/reports/summary（服务端在 S5 用并发聚合、S6 补全四维）。图表是「画出来容易、画对难」的典型：单位差 100 倍、颜色不吃主题、「未设预算」被画成一条 0 线——今天把这三个坑全部正面讲掉。其中最后一个是红线。

今日目标

判据提醒：图表早就被 agent 画出来了。你的判据是：指着图上任何一个数字，你能说出它是响应里哪个字段、经过什么运算到这里的——每一步运算都报得出来，才算读懂。不许拿「页面能跑」当自己通过了。

1. 数据从哪来：报表接口的形状

报表接口按当前时间窗（period 参数，从 useShellStore 读——下一张卡正面讲）返回聚合结果。响应示意（字段名以 agent 实现为准）：

片段 · GET /api/finance/reports/summary 响应（示意）{ "code": 0, "message": "ok", "data": {
  "period": "2026-10",
  "trend": {                          // 趋势：本期按下一粒度展开的时间序列
    "buckets": ["10-01", "10-02", …],
    "expense_cents": [12500, 8800, …],
    "income_cents":  [0, 300000, …],
    "balance_cents": [450200, 741400, …]  // 累计余额：服务端逐期累加好的
  },
  "by_category": [                    // 分类维度：饼图的料
    { "name": "餐饮", "expense_cents": 86000 }, …
  ],
  "budget": { "budget_unset": true }   // 该周期未设预算 → 见 §4 红线
} }

注意 balance_cents：接口契约里写明累计余额由服务端逐期累加，前端二次累加须为 0——这条曲线你直接用，别自己再 reduce 一遍。自己累加不仅多余，还会把服务端的口径（比如是否含转账）悄悄换成你的口径。

2. ucharts 的胃口：categories + series

ucharts 吃所有图表类型的数据格式都是两件套：categories（x 轴刻度，字符串数组）+ series（每条线/每块饼，{name, data}）。映射关系一张表说清：

图表categoriesseries料从哪来
趋势折线图trend.buckets支出、收入（、累计余额）各一条线trend.*_cents 逐元素 ÷100
分类饼图各分类名（饼图里作用弱化）一条 series，data 是各分类金额by_category[] 的 name 与 expense_cents ÷100
片段 · 响应 → ucharts 配置的映射层（示意）const yuan = (cents) => cents / 100          // 唯一的一次除法，只在映射层

const lineOpts = computed(() => ({
  type: 'line',
  categories: trend.value.buckets,
  series: [
    { name: '支出', data: trend.value.expense_cents.map(yuan) },
    { name: '收入', data: trend.value.income_cents.map(yuan) },
  ],
  color: [tokens[currentTheme.value].danger, tokens[currentTheme.value].primary],
  pixelRatio: 1, animation: true,
}))
// 建图：new uCharts({ canvasId, context, width, height, ...lineOpts.value })
// 数据/主题变化：chart.updateData(新配置)——不重建实例（F4 第 3 张卡）

canvas 的老规矩在这继续生效：canvasId 要和模板里 <canvas> 的 id 对上；宽高必须显式传（canvas 不会自己撑开）；颜色从主题令牌的 JS 投影取（var(--x) 传进去是无效字符串）。这三条是「图表画不出来/糊成一片/深色下白底」的三大来源。

3. 金额纪律：整数进门，除法只发生一次

全站金额都是 *_cents 整数（服务端存 BIGINT，序列化原样给前端）。图表侧的纪律三条：

  • 显示才除：cents / 100 只发生在「映射进图表配置」这一层，且只除一次。原始整数在 store/页面里保持原样。
  • 不许浮点累加：任何求和（比如饼图某几类合并、tooltip 里的小计）都在整数域做完，最后一次性 ÷100。原因你写过 Go 就懂：0.1 + 0.02 在 IEEE754 里不等于 0.12，几十笔流水累加下来，图上会出现 3499.9999 这种数——而整数加法永远精确。
  • 格式化收口一处：yuan() 与 tooltip 的 format 回调都指向同一个格式化函数，显示两位小数。两处各写各的除法，就是定位题里「除了两次」事故的温床。

对照 React：和你在 React 里用整数分（cents）配 Intl.NumberFormat 的做法完全同构——「货币不进浮点域」是跨生态铁律，不是本站特产。

4. 红线：「该周期未设预算」不是错误

报表页有一块预算对比（预算 vs 实际）。当这个周期用户没设预算时，接口的行为是：

片段 · 未设预算时的响应（节选）// HTTP 200，code 0 —— 这不是错误，不许走 catch / 错误态
"budget": { "budget_unset": true }

图表侧的正确与错误画法，逐条对号：

画法判定为什么
预算区域显示「未设预算」文案 + 去设置的引导✅ 唯一正确如实传达「没有这个数」，用户知道该干什么
画一条 0 线 / 0 柱❌ 红线0 是一个数值断言（「预算为零」），和「没有预算」是两回事；用户会读成「我设了 0 元预算然后超支无穷大」
按日/月折算一个「等效预算」画上去❌ 红线接口契约明写不得返回折算值；前端更不许自己折算——无中生有的数比没有数危害大
把 budget_unset 当错误处理（弹 toast、错误态）❌200 + code 0 是正常响应；错误态留给真失败

这条红线值得背下来，因为它是「缺失值 ≠ 零值」这个通用数据建模原则在本站的具体化——和数据库里 NULL ≠ 0 是同一件事。以后你在任何图表上看到一条可疑的 0 线，第一反应就该是：这里是不是把「没有」画成了「零」？

动手改（今天的判据现场）

给趋势折线图加「点数据点 → 跳该周期明细」：

片段 · 起点（模板里的 canvas）<canvas canvas-id="trendChart" id="trendChart" @touchstart="onChartTouch" />

验收：从报表页点 3 月 12 日那个点，明细页的列表应该正好是那天的流水；再切回报表页，图表周期不应被这次跳转悄悄改掉之外的东西——如果整个 shell 的周期跟着明细走了，想一想这是不是「全站唯一一份」的正确行为（是——所以明细页要提供回到原周期的路，这是改动③要你说清的边界）。

定位题（bug 在哪一层：金额差 100 倍）

现象：图表画出来了，形状也对，但金额差了 100 倍——实际支出 35 元，图上标着 3500（或 0.35）。

三个嫌疑人：服务端单位错、前端少除一次、前端除了两次。一个数字 + 一次搜索就能定论：

  1. Network 面板看原始响应：找到 reports/summary 的响应体，看那个数据点的原始值。你确定真实金额是 35 元，那么正确答案只能是 3500（cents）。响应里就是 35 或 35.0 或 350000 → 服务端单位错（没按 cents 存/序列化时动过手脚），到此定论，去找服务端。
  2. 响应是对的（3500）→ 前端问题，数除法次数：图上显示 3500 → 少除了一次（映射层漏了 yuan()，或某条 series 没走统一映射）；显示 0.35 → 除了两次（映射层除过一次，tooltip/轴标签的 format 回调又除一次）。
  3. 交叉验证缩小搜索面：同一份数据在列表页显示正确（35.00 元）→ 服务端无辜、yuan() 函数本身无辜，问题锁定在图表链路独有的那几处：series 映射、tooltip format、y 轴 format。全局搜 / 100，出现在图表链路上的每一处都过一遍——两次出现在同一条数据通路上，就是「除了两次」的现场。

这题的通用收获：「差一个固定倍数」的 bug 几乎总是单位换算，而单位换算的证据永远在最原始的响应体里。先拿原始值对齐期望值，再数前端链路上的换算次数。记进 notes/f4/。
