游标分页的前端侧（下）：不重复、不漏、能续读

上一张卡让分页「跑起来」，这张卡回答更难的问题：怎么知道它跑对了？「能滚出下一页」和「滚出来的数据是对的」之间隔着三条判据——不重复、不漏、能续读。这也是 PLAN 里 F4 阶段判据的原文，今天把每条都变成你能亲手做的实验，而不是一句口号。

今日目标

判据提醒：这张卡的通过标准是三个实验你亲手做过、结论说得出——尤其第二个实验里「为什么游标不怕中途插入数据」的原理。不许拿「页面能跑」当自己通过了：能跑的分页照样可以又重又漏。

1. 三条判据，三个实验

判据含义亲手验证的实验
不重复连续续读，任何一条流水只出现一次实验 A + 实验 B
不漏刷新前已存在的数据，续读过程中一条不少实验 B + 实验 C
能续读has_more: true 时总能拿到下一页，直到翻完实验 A

实验 A（改每页大小）：临时把请求的 limit 参数改小（比如 20 → 5），页数立刻变多，两屏就能翻好几页。连续触底直到出现「没有更多了」，数一下总条数，和还原 limit 后一次刷新看到的量级对一下。这个实验同时压测「能续读」：每一次触底都必须真的前进一页，中途卡住（锁死、游标没更新）当场现形。做完把 limit 改回来——每页大小是接口约定，不是玩具参数。

实验 B（连续触底对 id）：翻完全部页后，把列表里所有行的 id 抄下来（devtools 里对 items 数组跑一句 items.map(i => i.id)，再看有没有重复：new Set(ids).size === ids.length）。相等 → 不重复成立。不等 → 拿着重复的 id 去 Network 面板对两次响应，这正是定位题的剧本。

实验 C（中途插数据再刷新）：翻到第二、三页时停下，另开一个入口（记账页）新记一笔流水，回到列表先继续触底续读旧页，再下拉刷新。观察两件事：① 续读旧页时，新数据不会把旧数据挤得错位——因为游标锚定的是「(排序键, id)」这个数据本身的坐标，不是「第几行」这个位置坐标；② 刷新后新数据出现在列表头部，且整份列表依然不重不漏。

实验 C 就是「为什么禁 offset」的答案：如果分页参数是「跳过前 40 条」，在你翻页期间头部插入一条新数据，所有旧数据整体后移一位——第二页开头就会重复上一页最后一条；反过来中途删一条就会漏一条。游标记的是坐标不是偏移，天然免疫插入与删除。你亲手做过实验 C，这条服务端设计决策才算真的懂。

2. key 的学问：为什么 index 当 key 会「重复渲染」

v-for 的 :key 是 Vue diff 算法认人的唯一凭证：新旧列表对比时，key 相同的节点被视为「同一个」，DOM 与组件状态原地复用。:key="index" 等于告诉 Vue「第 3 行永远是同一个人」——而分页列表里这话是假的：

  • 纯追加时侥幸没事：触底续读只在尾部加行，前面的 index 不变——所以 index key 的列表「平时看着挺正常」，这是它最阴险的地方。
  • 下拉刷新后头部插行：新数据顶进来，所有旧行的 index 全体 +1。Vue 按 index 认人，把「第 0 行」的旧 DOM（连同展开状态、动画、输入焦点）错配给新数据——看起来就像行内容闪跳、状态串行，配合过渡动画时甚至出现同一行视觉残留两次的重复渲染假象。
  • key 真撞了（两行数据给出同一个 key，比如拿「金额+分类」当 key）：Vue 直接警告 duplicate key，diff 结果不可预期——这才是字面意义的重复渲染事故。

正确姿势只有一条：:key="item.id"——数据库主键，全局唯一、终身不变，是唯一配得上「认人凭证」的字段。对照 React：key={index} 的反模式警告和这里一字不差，原理相同。

3. 四个 UI 状态：谁负责什么

一个分页列表页共四个非正常画面，分工必须清楚——状态机归页面（容器），画面归展示组件（上一张卡拆好的结构在这里收租）：

状态触发条件画面谁负责
骨架屏首屏加载中（items 还是空）几行灰色占位条，模拟列表形状页面判条件；骨架行是公共展示组件
空态加载完成且 items.length === 0插图 + 「这个时间窗还没有流水」+ 引导按钮页面判条件；EmptyState 渲染
错误态请求 reject（网络断、服务端 5xx、token 彻底失效）错误条 + 重试按钮；已加载的数据保留页面存 error 状态；错误条组件渲染
重试用户点重试错误条变回加载中；游标不动，重读同一页页面：再调一次 loadPage 而已

两条容易搞混的边界：① 骨架屏只属于首屏——续读时列表已有数据，尾部转圈就够，整页换骨架屏等于把用户已读内容闪没，体验倒退；② 「没有更多了」不是第五个状态，它是成功路径的尾部提示（上一张卡），和错误态互斥。

4. 请求失败后，游标该不该前进？——不该

把游标想成门票：请求失败 = 这一页你根本没读到，门票没被检过。此时正确动作是：拿着同一张票再排一次队（重试），而不是撕掉票往后走（前进）。写成代码就是三条纪律：

片段 · 失败分支的三条纪律try {
  const data = await http.get('/finance/transactions', { cursor: cursor.value, … })
  items.value.push(...data.list)
  cursor.value = data.next_cursor      // ① 只有成功才更新游标
  hasMore.value = data.has_more
  error.value = null
} catch (e) {
  error.value = e                      // ② 失败只记错误；items 不清、游标不动
} finally { loading.value = false }    // ③ 锁必放（上一张卡讲过为什么是 finally）

如果失败时把游标清了，用户点重试会从第一页重读——已有数据 + 第一页数据 = 一屏重复；如果把 items 也清了，用户已读的内容凭空消失，网络抖一下代价大到不可接受。失败的正确画面 = 旧数据还在 + 一条错误提示 + 一个重试按钮，重试成功后画面无缝接上，用户几乎无感。

动手改（今天的判据现场）

找到流水列表页的加载函数，把失败处理改造成「保留 + 重试」：

片段 · 起点（agent 常见的粗糙版失败处理）catch (e) {
  items.value = []                     // ❌ 一失败全清空
  uni.showToast({ title: '加载失败' })   // ❌ 只弹个 toast，没有出路
}

定位题（bug 在哪一层：一次 Network 面板定论）

现象：列表里出现了两条一模一样的记录（同时间、同金额、同分类）。

三个嫌疑人：服务端返回重复、前端把同一批拼了两次、渲染层 key 撞了。打开 Network 面板，一次定论：

  1. 先看数据层还是渲染层：devtools 里检查页面的 items 数组——那条记录的 id 在数组里出现几次？出现两次 → 数据层问题，走第 2 步；只有一次但页面显示两条 → 渲染层问题，直接跳第 4 步。
  2. 数据层：翻这两条 id 是从哪批响应来的。Network 里逐个看列表请求的响应体，搜这个 id：同一个 id 出现在两次不同请求的响应里 → 再对比这两次请求的 cursor 参数——参数不同但数据重复 → 服务端返回重复（游标编码或排序有 bug），带着两个请求的截图去找服务端；这是服务端问题，前端不该「帮忙去重」掩盖它。
  3. 两次请求的 cursor 参数相同 → 同一张门票用了两次 → 前端 concat 了同一批：十有八九是触底双触发（加载锁失效）或刷新与触底并发。证据就在 Network 的时间线上：两个几乎同时发出、参数完全一样的请求。
  4. 渲染层：查 :key。items 里明明只有一条，页面却显示两条 → 看 v-for 的 key 用的是什么：index？金额+分类拼的字符串？key 撞了会让 Vue 的复用错乱出重复幻影，控制台通常伴随 duplicate key 警告。修法永远是 :key="item.id"。

这套排查的核心动作只有一个：拿 id 当线索，在「响应体 → 请求参数 → 前端数组 → DOM」四层里找到重复第一次出现的位置——重复在哪一层第一次出现，锅就在哪一层。记进 notes/f4/。
