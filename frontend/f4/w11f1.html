样式与主题令牌：rpx、scoped 与「颜色只能引用令牌」

上一张卡拆的是结构，这一张拆的是皮肤。目标很具体：以后你看到 agent 写的任何一处样式，都能回答三个问题——这个颜色是从哪来的？这个尺寸为什么用 rpx？这条选择器在小程序端还生效吗？这三个问题也是「改样式而不动别的页」这条阶段判据的全部前置知识。

今日目标

判据提醒：这张卡的通过标准不是「样式改出来了」，而是你能讲清每一处颜色和尺寸的来源。改完却说不清「为什么这里必须用令牌」，等于没改。不许拿「页面能跑」当自己通过了。

1. 两套东西：scss 变量（编译期）与主题令牌（运行期）

这个项目里「变量」有两个体系，名字像、性质完全不同：

scss 变量 $x主题令牌 var(--x)（CSS 变量）
生效时机编译期：构建时被替换成字面量，产物里没有变量运行期：浏览器/渲染层实时求值，可以被 JS 和主题切换改写
能不能运行时换不能——换肤对它无效能——深色模式全靠它（下一张卡的正题）
典型用途间距阶梯、字号阶梯、圆角、断点所有颜色、以及随主题变的阴影/边框色

shell 在根部定义了一组主题令牌（示意，以 web/ 里 agent 的实现为准）：

片段 · 主题令牌的定义处（shell 全局样式）page {
  --hc-bg: #f5f6f8;        /* 页面底色 */
  --hc-card-bg: #ffffff;   /* 卡片底色 */
  --hc-text: #1f2329;      /* 主文字 */
  --hc-text-dim: #8a919f;  /* 次要文字 */
  --hc-primary: #3d7fff;   /* 主操作色 */
  --hc-danger: #e11d48;    /* 支出/警示色 */
}
/* 业务组件里只许这样引用： */
.tx-item__amount { color: var(--hc-danger); }  /* ✅ */
.tx-item__amount { color: #e11d48; }           /* ❌ 硬编码，CI 要拦的 */

为什么颜色只能引用令牌？因为要换肤。深色模式、以及日后可能的多套主题，实现方式都是「切换时改写根部这一组 --hc-* 的值」——所有引用令牌的组件自动全站跟着变。一处硬编码色值就是一块「换肤时永远不会变」的补丁：白天看不出来，一到深色模式就是一块刺眼的白斑（下一张卡的定位题就是抓这个）。所以这是纪律不是品味问题：色值只在令牌定义处出现一次，其他地方全是引用。

对照 React：这和你在 React 项目里用 CSS-in-JS 的 theme 对象、或 CSS Modules 配一套 design tokens 是同一件事——「单一事实源 + 全部引用」。差别是 Vue/uni-app 这套用原生 CSS 变量做运行期层，scss 只做编译期层，两层分工。

2. rpx 与 px：一个跟着屏幕走，一个钉死

rpx（responsive pixel）是小程序体系的相对单位：规定屏幕宽度恒等于 750rpx。375pt 宽的手机上 1rpx = 0.5px；414pt 宽的手机上 1rpx = 0.552px。uni-app 把它带到了全端。

场景用什么理由
组件宽高、间距、字号、圆角rpx随屏幕等比缩放，小屏不挤大屏不飘
1 像素细线（分割线、边框）px你要的就是「物理上一根细线」，不该随屏幕变粗
不想随屏幕放大的固定元素（如悬浮按钮尺寸有设计上限）px 或 rpx 配 max-width大屏上 750rpx 体系会把东西放得过大

换算心算式：设计稿按 750 宽出的，标多少写多少 rpx；按 375 宽出的，乘 2。本项目间距走 scss 的间距阶梯变量（$space-2 之类），阶梯的值本身用 rpx——所以「改间距」的正确姿势是改阶梯引用，而不是就地写死一个数。

3. scoped 与 :deep()：隔离是怎么做出来的

<style scoped> 的原理（F1 第 1 张卡提过一句，今天讲透）：编译器给本组件模板里的每个元素加一个属性（形如 data-v-7ba5bd90），并把每条选择器改写成带这个属性的形式：

片段 · scoped 的编译前后/* 你写的 */          .tx-item__sub { … }
/* 编译成 */          .tx-item__sub[data-v-7ba5bd90] { … }

于是同名类在不同组件里互不打架——相当于 React 里的 CSS Modules，只是自动的。但它带来一个经典麻烦：子组件的内部元素不带父组件的哈希属性，所以父组件的 scoped 样式选不中子组件内部。要穿透，用 :deep()：

片段 · :deep() 穿透/* 父组件里想改子组件内部某个类 */
.filter-bar :deep(.picker__label) { font-size: 26rpx; }
/* 编译后：.filter-bar[data-v-xxx] .picker__label —— 哈希挂在父级锚点上 */

老资料里的 >>> 和 /deep/ 都是 :deep() 的废弃前身，新代码一律 :deep()。另外记住穿透是有代价的：你在父组件里改子组件 internals，等于把子组件的内部结构写死在了调用方——子组件一重构你就断。能改子组件自己的样式就别穿透。

4. uni-app 里哪些 CSS 能力用不了（与浏览器 Vue 的差别）

同一份 .vue，H5 端跑在真浏览器里，什么 CSS 都能用；小程序端跑在受限渲染层里，CSS 是子集。这是「H5 好好的、小程序崩了」这类 bug 的总根源。常用能力清单：

能力H5小程序端替代姿势
通配选择器 *✅❌ 不支持逐个类名写，或挂在 page 上继承
属性选择器 [class^="x"]✅❌ 基本不可用加显式类名
标签选择器 div/span✅❌ 没有这些标签（是 view/text）模板里就用 view/text，样式只写类选择器
根元素 html/body✅❌ 对应物是 page全局样式挂 page
本地图片当 background-image✅❌ 不支持本地路径用 <image> 标签、或 base64、或网络图
复杂选择器链 a > b + c✅⚠️ 各小程序支持度不一拍平成单层类名（BEM 风格）
position: fixed✅⚠️ 可用但会被原生组件（canvas、video）盖住/穿透异常原生组件区域用 cover-view 或避开
CSS 变量 var(--x)✅✅ 主流小程序都支持——所以主题令牌方案全端成立

实在需要按平台分叉时，用 F2 讲过的条件编译（/* #ifdef H5 */ … /* #endif */ 在样式里同样可用）——但它是最后手段：每分叉一次，就多一份要双端各测一遍的样式。

动手改（今天的判据现场）

在 web/ 里全局搜一个十六进制色值（比如搜 # 开头的颜色，排除令牌定义文件本身），挑一处业务组件里的硬编码，做三处改动：

片段 · 起点（某业务组件里的两行）.summary__title { color: #8a919f; margin-bottom: 16px; }  /* ❌ 两处都违规 */

如果全局搜下来一处硬编码都没有——恭喜 agent 守住了纪律，那就反过来做：故意写一个硬编码色值，起 H5 看一眼，再想清楚它会在深色模式下变成什么样（下一张卡会把这颗雷引爆），然后删掉。

定位题（bug 在哪一层：双端差异）

现象：同一条样式，H5 里正常，小程序端不对（不生效 / 长得完全不一样）。

先分清两种可能：选择器问题（规则存在但没选中元素）还是平台能力问题（这条 CSS 能力小程序端根本没有）。判断顺序：

  1. 微信开发者工具 → WXML 面板选中该元素 → Styles/Computed：你那条规则出现在列表里吗？出现了但被划掉 → 是优先级/覆盖问题（scoped 哈希、选择器权重），不是平台问题。
  2. 规则压根不在列表里 → 看编译产物：这条选择器是不是用了小程序端不存在的形式——标签选择器（div）、*、属性选择器、html/body？是 → 选择器问题，改写成类选择器。
  3. 选择器没问题、规则也在，但效果不对 → 对照本课 §4 的能力表：本地 background-image、复杂选择器链、fixed 与原生组件的层叠——命中 → 平台能力问题，走替代姿势；确认双端行为无法统一时才用条件编译。
  4. 都排除后：检查是不是只在模拟器不对、真机对（或反过来）——开发者工具模拟器与真机渲染有版本差，换真机预览复测再下结论。

这一题的收获是排查工具切换：H5 用浏览器 devtools，小程序端用微信开发者工具的 WXML/Styles 面板——同一个「看 computed 样式」的动作，两个工具里各练一遍。把双端差异排查链记进 notes/f4/。
