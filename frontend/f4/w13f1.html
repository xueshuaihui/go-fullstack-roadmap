游标分页的前端侧（上）：下拉刷新与触底加载

这是一条埋了很久的伏笔：服务端在 S3 就把列表返回统一成了游标分页信封，今天兑现它的前端侧。财务面的每个列表——流水、账户、分类下的明细——都吃这一套。这张卡管「怎么跑起来」：下拉刷新重置、触底续读、两种加载状态；下一张卡管「怎么验证跑对了」：不重复、不漏、能续读。

今日目标

判据提醒：这个列表是 agent 写的、而且「能滚出下一页」大概率早就正常。你的判据是：能讲清游标在哪一步被清空、在哪一步被带回、为什么客户端永远不该理解它的内容。不许拿「页面能跑」当自己通过了。

1. 信封与三条禁令

所有分页列表接口（如 GET /api/finance/transactions）的响应都是这个形状：

片段 · 游标分页信封{ "code": 0, "message": "ok", "data": {
    "list": [ … ],            // 本页数据
    "next_cursor": "eyJvIjox",  // 下一页的门票；null/空 = 没有了
    "has_more": true          // 还有没有下一页
} }

三条禁令，条条都是红线：

  • 不解析：游标是服务端把「(排序键, id)」base64 编码后的产物，对客户端是不透明字符串。你解出来看了一眼？从此你的前端就和服务端的排序实现耦死了——服务端换排序键，你解出来的逻辑全错。
  • 不自造：不许自己拼一个「看起来像」的游标。造出来的游标服务端解不开，或者更糟——解开了但语义错误，返回错乱的数据。
  • 不修改：上次响应给的 next_cursor，原样带回下次请求，一个字符都不能动。

另外注意信封里没有什么：没有 total、没有 page、没有总页数。这不是漏了，是刻意设计——「共 137 条 / 第 3 页」这类 UI 在游标分页里根本不存在，你也没法跳页，只能顺序续读。如果你在哪个页面看到「上一页/下一页」按钮，那是对着错误契约写的 UI。

对照 React：这与 SWR 的 useSWRInfinite 是同一个心智模型——getFirstPageParam 返回首页参数（无游标），getNextPageParam 从上一页响应里取出下一页参数（next_cursor），size/setSize 控制读到第几页。「下一页的参数依赖上一页的响应」，两套生态殊途同归；差别是 React 里你自己管数组拼接，这里状态和加载函数由页面（容器）持有——上一张卡拆好的结构正好用上。

2. 两条路径：刷新重置，触底续读

整个分页前端侧只有一个核心函数和两个入口：

片段 · 页面（容器）里的分页状态机（示意，以 agent 实现为准）const items = ref([])          // 已加载的全部行
const cursor = ref(null)       // 下一页门票；null = 从第一页读
const hasMore = ref(true)
const loading = ref(false)       // 加载锁：防触底连发

async function loadPage() {
  if (loading.value || !hasMore.value) return   // 锁住 + 没票不发
  loading.value = true
  try {
    // 请求层（F2 建好）已拆掉外层信封，拿到的就是 data
    const data = await http.get('/finance/transactions',
      { period: shell.period, cursor: cursor.value, limit: 20 })
    items.value.push(...data.list)               // 续读 = 往后拼
    cursor.value = data.next_cursor              // 门票原样收下
    hasMore.value = data.has_more
  } finally { loading.value = false }           // finally：失败也要放锁
}

function refresh() {                              // 刷新 = 全部归零再读第一页
  items.value = []; cursor.value = null; hasMore.value = true
  return loadPage()
}

两个入口都是 uni-app 的页面级生命周期——不是 Vue 的组件钩子，写在页面（pages.json 注册过的文件）里才生效，且需要配置配合：

片段 · pages.json 里该页的配置 + script setup 里的挂钩// pages.json（节选）：两个开关都在这里
{ "path": "pages/finance/tx/list",
  "style": { "enablePullDownRefresh": true, "onReachBottomDistance": 80 } }

// list.vue（script setup）：从 uni-app 导入页面级钩子
import { onPullDownRefresh, onReachBottom } from '@dcloudio/uni-app'
onPullDownRefresh(async () => {
  await refresh()
  uni.stopPullDownRefresh()          // 不收，转圈永远不停
})
onReachBottom(() => loadPage())       // 滚动到距底 80px 内触发
入口对游标做什么对列表做什么直觉
下拉刷新重置：cursor = null清空重填「从头再读一遍最新的」
触底加载续：带上次的 next_cursor往后拼接「接着上次读到哪算哪」
首次进入初始即 null空 → 第一页等价于一次静默刷新

3. 两种状态：加载中 与 没有更多了

触底之后用户看到的必须是确定的反馈，只有三种合法画面：

状态条件UI 表达
加载中loading === true列表尾部的转圈 + 「加载中…」；首屏则是骨架屏（下一张卡展开）
没有更多了!hasMore && items.length尾部灰色一行「没有更多了」——告诉用户「到底了」不是「坏了」
（空列表）!loading && !items.length空态组件的活，不是尾部提示的活；此时不显示「没有更多了」

为什么「没有更多了」值得单独一行提示？因为触底是无按钮操作——用户滚到底没有任何可点的东西，如果既不出新数据也没有提示，他无法区分「加载完了」和「加载坏了」。状态可见，是可滚动列表的基本礼貌。

动手改（今天的判据现场）

找到流水列表页，看它的尾部：如果 agent 已经写了「没有更多了」，就按下面要求核对并改造它；如果没写，正好亲手加一个。

片段 · 起点（列表模板的尾部）<TxList :items="items" :loading="loading" />
<!-- 这里往后是空白：滚到底什么反馈都没有 -->

验证方式：H5 端把浏览器窗口拉窄、多滚几次；或临时把请求的 limit 参数改小（如 5），两页就能滚到底，看尾部提示是否按时出现。limit 改小只是实验手段，看完改回来——每页大小是接口约定，不是前端自由参数。

定位题（bug 在哪一层：滚到底没反应）

现象：列表滚到底了，不加载下一页——「触底没反应」。

三个嫌疑人：事件根本没触发、触发了但被前端逻辑拦住、页面配置没开。这个顺序排：

  1. 先证明事件层：在 onReachBottom 回调第一行加 console.log，滚到底。日志没出来 → 事件没触发，进入第 2 步；日志出来了 → 跳到第 3 步。
  2. 事件没触发的两种死法：① 绑错了地方——onReachBottom 是页面级钩子，写在子组件（比如拆出去的 TxList）里不生效；确认它写在 pages.json 注册过的页面文件里。② 页面配置/结构问题——该页 style 里 onReachBottomDistance 配置异常，或者列表被包在 scroll-view 里：scroll-view 内部滚动不产生页面级触底事件（页面本身没滚），这是 uni-app 最经典的触底失效原因。
  3. 事件触发了但没发请求：看 loadPage 入口的两个拦截条件——hasMore 已经是 false？打开 Network 面板看上一次响应的 has_more 字段，如果真是 false，那不加载是正确行为，你缺的只是「没有更多了」提示（动手改①就是治这个的）。loading 卡在 true？说明上一次请求失败后没放锁——检查是不是把 loading = false 写在了 then 而不是 finally。
  4. 请求发了但列表没变：这就进入下一张卡的领地（拼接与重复渲染）——先看 Network 里这次请求的 cursor 参数是不是和上次响应给的 next_cursor 一致。

这一题的分层价值：事件层（钩子/配置）→ 逻辑层（状态机拦截）→ 数据层（拼接），三层各有独立证据（日志、状态值、Network）。把「触底无反应排查链」记进 notes/f4/。

常见坑

坑现象正确姿势
在子组件里写 onReachBottom永远不触发，且无任何报错页面级钩子只写在页面文件里；组件事件靠 emit 上报
列表包在 scroll-view 里页面不滚动，触底事件无从谈起用页面自身滚动；确需 scroll-view 就监听它自己的 scrolltolower
下拉刷新忘了 stopPullDownRefresh顶部转圈永不停止刷新 Promise 结束后必收，失败分支也要收
把 loading = false 写在成功分支一次失败后加载锁死，列表永久瘫痪放锁一律写 finally
解码/拼接游标「看看里面是什么」服务端换排序实现后分页错乱三条禁令：不解析、不自造、不修改
UI 上画「第 N 页 / 共 M 条」数据根本不存在，只能造假游标分页没有总页数概念，UI 只有「还有 / 没有」两态
has_more: false 还继续发请求反复请求同一空页，浪费且可能报错请求前先看 hasMore，入口就拦

今日名词卡

术语一句话解释
游标分页信封{list, next_cursor, has_more}——全站分页列表的唯一返回形状
next_cursor下一页门票：服务端 (排序键, id) 的 base64，对客户端不透明，原样带回
has_more还有没有下一页；false 时前端必须停止续读
onPullDownRefreshuni-app 页面级钩子：下拉刷新触发；需 enablePullDownRefresh: true，完事必须 stop
onReachBottomuni-app 页面级钩子：页面滚动触底触发；子组件里写无效
onReachBottomDistance距底多少 px 就提前触发触底（默认 50）；配大一点体验更顺
加载锁loading 标志位：请求在途时拦截重复触发；放锁必须在 finally
重置 vs 续读刷新 = 游标归零清空重填；触底 = 带着门票往后拼——两条路径共用一个 loadPage
useSWRInfinite（对照）React 生态的无限加载方案；getNextPageParam 与 next_cursor 是同一心智模型
