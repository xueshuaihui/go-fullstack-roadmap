1. 五档编码与三档暴露

服务端接受的时间窗是五档，编码格式钉死：

档编码例谁在用
dayYYYY-MM-DD2026-10-13明细视图（点折线图某个日数据点跳过去的列表，上一张卡的动手改就是它）
weekYYYY-Wnn2026-W42
monthYYYY-MM2026-10shell 顶栏切换器暴露的三档：全站报表与列表的默认周期
quarterYYYY-Qn2026-Q4
yearYYYY2026

切换器只暴露月/季/年三档，服务端却接受五档——这不是矛盾，是分层：切换器是 shell 级控件，管的是「全站看哪个大周期」；日/周两档是明细视图的钻取粒度，由跳转链接携带（上一张卡点数据点跳明细，带的就是日编码）。两层共用同一个 period 字段和同一套编码规则，只是暴露面不同。

2. 1007 不回落：前端的契约义务

非法编码（2026-Q5、2026-13、26-10、空串）服务端的处理是：400 + 业务码 1007，不回落到任何默认档。注意「不回落」的分量：服务端不会帮你兜底成「本月」，而是让请求直接失败。这个设计把义务压给了前端——

前端必须自己保证：非法值根本发不出去。做法不是「发之前校验一遍」（校验逻辑和生成逻辑分开写就会漂移），而是让非法值无从产生：所有 period 一律由 encode 函数从日期对象算出来，任何地方不许手拼字符串、不许写死字面量。生成即合法，这才是「保证」。

片段 · 编码函数：period 的唯一出生地// period.js —— 全部五档各一个纯函数，输入 Date，输出合法编码
export const encodeDay     = (d) => fmt(d, 'YYYY-MM-DD')
export const encodeMonth   = (d) => fmt(d, 'YYYY-MM')
export const encodeYear    = (d) => String(d.getFullYear())
export const encodeWeek    = (d) => /* ISO 周号计算，略 */
export const encodeQuarter = (d) =>
  `${d.getFullYear()}-Q${Math.floor(d.getMonth() / 3) + 1}`
// getMonth() 是 0-11：0-2→Q1，3-5→Q2，6-8→Q3，9-11→Q4
// 写边界自测：1月、3月、4月、12月四个输入，四个输出必须全对

对照 React：等价于你把日期格式化收口到 date-fns 的 format 而不是各处手写字符串拼接——「解析/生成收口一处」是跨生态的老纪律。

3. 全站唯一一份：period 的数据通路

period 住在 useShellStore（F3 建好的三个 store 之一：auth 管会话、family 管家庭上下文、shell 管未读计数 + 时间窗）。全站唯一一份意味着：任何页面都不许持有自己的 period 副本，所有消费者都从 store 读。

片段 · store 与消费者的接法// stores/shell.js
export const useShellStore = defineStore('shell', () => {
  const period = ref(encodeMonth(new Date()))
  function setPeriod(p) { period.value = p }
  return { period, setPeriod }
})

// 消费组件（报表页、流水列表页……每个都一样）
const shell = useShellStore()
const { period } = storeToRefs(shell)   // 解构必须走 storeToRefs，否则丢响应性（F1 老坑）
watch(period, () => refresh())          // 切换 = 刷新：分页重置游标重读（F4 第 4 张卡）

于是「切换时间窗」的完整通路是一条单行道：

片段 · 数据通路切换器点击 → shell.setPeriod(encodeXxx(…)) → store.period 变
  → 各消费组件的 watch 触发 → 各自 refresh()（游标重置，带新 period 重新请求）
  → 图表 updateData / 列表重填 —— 全站一起翻页

两个细节：① 切换 period 属于换筛选条件，列表必须走「刷新」路径——清空、游标归零、重读第一页；带着旧游标续读新周期的数据是无意义请求。② 为什么唯一一份这么重要：如果报表页存一个 period、列表页存一个，用户在切换器切到「年」，就会出现「图表按年、列表按月」的精神分裂画面——定位题正是这个事故。

定位题（bug 在哪一层：切了「年」图表还是月）

现象：切换器切到「年」之后，报表图表还是按月显示。

三个嫌疑人：store 没更新、组件没监听、请求参数没带上。沿 §3 的通路从源头往下走，三步定论：

  1. store 更新了吗？Vue Devtools 的 Pinia 面板直接看 useShellStore.period 的实时值（或在切换器的点击处理里打日志）。还是旧的月编码 → 切换器的问题：没调 setPeriod、或者调的是某个页面私有副本（多份 period 的典型事故）——前端，且是切换器/状态归属层。
  2. store 对了，组件重发请求了吗？看 Network：切换那一刻有没有新的 reports/summary 请求发出。没有 → 组件没监听：watch 漏了、或者监听的是「拿 store 初始化的本地 ref」（本地副本分家，F1 第 3 张卡的老朋友）、或者解构 store 没走 storeToRefs 丢了响应性——前端，消费组件层。
  3. 请求发了，参数对吗？看这次请求的 Query String：period 没带、或还是旧值 → 组参代码读错了来源（又是副本嫌疑）——前端。参数正确（比如 2026）但响应里的趋势序列还是按月 12 个点 → 前端到此全部排除，服务端问题（年档的聚合粒度没生效），带着请求截图去查服务端报表实现。

三步分别对应通路的三个环节：源头（store）→ 监听（watch）→ 参数（请求），走完还没问题才轮到服务端。这条「沿数据通路逐环节验证」的排查法和 F4 第 5 张卡「拿 id 找重复的第一出现层」是同一个方法论。记进 notes/f4/。
