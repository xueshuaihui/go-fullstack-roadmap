F4 · 组件、样式与列表

前端辅线最长的一段：七张周日卡，对应服务端 S5（并发与工程化）+ S6（财务功能面 30 条接口）。走到这里，web/ 已经不是你第一次见它时的脚手架了——F2 建好了工程与请求层，F3 建好了 Pinia store 与路由守卫并完成了第一次真对接，服务端也开始吐出真实的财务数据。F4 的主题一句话：把 agent 写出来的这些页面，变成你能拆开、能改、能调的东西。教材全部是 web/ 里的真实页面：流水列表、报表图表、shell 切换器。

为什么 F4 的判据仍是「能讲清 / 能改」

前端线的分工没变：agent 写代码，你学到能改。F4 与 F1 的差别是教材从内嵌片段换成了真实页面，但判据口径一字不改：① 能读懂任意一页 ② 能改字段与样式 ③ 能独立定位一个 bug 在前端还是服务端。每张卡都有一个「动手改」（改真实文件，带小勾选）和一道「定位题」（分层排查，结论写进 notes/f4/）——完成检查里没有一条是「代码写出来了」。不许拿「页面能跑」当自己通过了。

本阶段不做什么（明确划掉，免得手滑）

  • 不改服务端：字段对不上时改前端，不改响应契约——服务端先定契约、前端服从，这是三条不变约定之首；发现服务端 bug 走定位题的结论去找对应的 S 段卡修
  • 不学壳基座专属内容：底栏五项、分包 subPackages、PIN 应用锁是 F5 的事
  • 不做系统化的调试方法论训练——那是 F6；F4 每张卡的定位题是分层的实战积累
  • 不引入新依赖：不上 Storybook（假数据单独渲染用一个临时调试页就够）、不上额外图表库（ucharts 一个管够）、不碰任何 React 代码（它只作概念对照出现）
  • 不动 pages.json 的结构性约定：三段式路由与「无 tabBar 字段」的纪律（F2 判据）在整个 F4 期间继续有效
