三段定位法与容器化后的前端连线

进入最后一段 F6：调试与定位。这一段不新增功能面，只干两件事：把 F1-F5 攒下的定位经验收拢成一套可复述的方法——三段定位法；以及把「服务跑进容器之后，前端怎么连上它」讲透。对应服务端 S8 阶段（收口与部署）。F6 的硬判据下一张卡验收：agent 故意留一个 bug（或真出现一个），你能不靠 agent 说出它在哪一层、为什么——今天先把武器磨好。

今日目标

判据提醒：三段定位法不是「看过了」而是「能默画」——给你任何一个症状，你要能先说出「我第一步看哪、看到什么就排除什么」，再动手。顺序本身就是判据。

1. 三段定位法：两个分界线，三个证据面

F1 立的四步法（Console → Network → 绑定 → 事件）是纯前端视角；现在服务端是你自己写的了，排查面延伸成三段：

段看什么能下的结论
① Console前端运行时错误、Vue 警告、渲染栈有红色报错 → 前端 JS 层，看堆栈第一行；栈是压缩产物时靠 sourcemap 映射回源码行号（dev 构建默认带；生产一般不对外发布，防源码泄露——排查生产问题时用带 sourcemap 的同版本产物在本地对照）
② Network请求发没发、URL 与参数对不对、HTTP 状态、响应体的 code/message、响应头里的 request_id请求没发 → 前端（校验拦截 / 事件没绑 / 按钮禁用逻辑）；发了且响应不对 → 进第 ③ 段；响应对但页面不对 → 前端渲染层（store 映射、绑定字段名）
③ 服务端日志拿 request_id grep：请求到没到、在哪一层被拒（中间件 → 权限判定 → handler 校验 → DB），每层的错误与耗时日志里没有这个 id → 请求根本没到服务（代理 / 网络 / 域名）；有 id 且有拒绝记录 → 看拒绝发生在哪一层，是你自己写的服务端逻辑，改不改由契约说了算

两条分界线要能背出来：第一条在 Network——请求发出去了没有，分掉「前端没发」与「发了以后」；第二条在响应体——code 是不是 0，分掉「服务端给了正确答复、前端没画对」与「服务端拒了 / 错了」。

两个老纪律在这一段仍然生效：HTTP 状态与业务码要一起看——本站约定 200 + code≠0 不存在于成功语义里，但 4xx/5xx 的响应体同样带 code，真正的分类依据是 §5.1 那张唯一错误码表；401（1005）先别慌——http 层会自动走 refresh → 重放一次（F3 建的链路），业务层最终看到 1005 意味着 refresh 也失败了，结论是「会话真的没了，回登录」，不是「这个接口坏了」。

2. request_id：一个 id 串起三段

request_id 是服务端中间件给每个请求生成的唯一标识：写进请求上下文、打进这条请求途经的每一行日志、并随响应头带回给客户端（响应头字段名以你仓里的实际实现为准，通行做法是 X-Request-Id）。它的价值是把第 ② 段和第 ③ 段焊死：

片段 · 一次报障的正确姿势用户视角：「点保存弹了参数错误」
前端界面：错误详情里显示 request_id: 9f3c…（今天的动手改就是给它加上这个能力）
服务端：cd <你的学习仓根目录> 后在日志里 grep 这个 id
   → 命中一行 handler 校验日志：「bind failed: field=amount_cents, err=…」
   → 结论：请求到了、在 handler 绑定层被拒、拒的是 amount_cents 字段
   → 再回 Network 看请求体里 amount_cents 传的是什么——三段闭环

没有 request_id 的报障是什么样？「我下午三点多点了一下保存失败了」——然后你去翻几百行日志按时间猜。能不能把 id 从界面一路带到日志行，是「可运维」与「靠运气」的分界线。

3. 错误码对照表怎么用（含一条故意的同形）

前端只认一张表（全站唯一错误码表，S1 起落成常量）。挑定位时最常撞见的几条：

codeHTTP前端该做什么
02xx取 data 渲染（http 层已拆包）
1001404资源不存在。越权读也返回本码——故意的同形，不泄露存在性。文案统一「不存在或无权访问」，不许靠它区分「没权限」和「真没有」写两个分支
1003403权限不足（角色矩阵拒绝 / 面未启用 / 越权写）。收起入口、给明确文案
1004400参数错误。先看自己发的请求体——多数 1004 是前端组装问题（单位、类型、漏字段）
1005401token 无效/过期。http 层已自动 refresh 重放一次，业务层再见到它 = 会话真没了，清会话回登录
1009409版本冲突（乐观锁）。重新拉数据给用户看新状态，不许吞掉冲突硬重试
5000500服务器内部错误。带上 request_id 直接查日志，这是唯一「肯定是服务端」的码

「1001 同形」值得再强调一遍，因为它是安全设计而非缺陷：如果「无权访问」返回 403、「不存在」返回 404，探测者就能靠响应差异枚举出「哪些资源存在」。前端把两者写成不同文案，等于替探测者把差异重新广播出去。

4. 容器化之后，前端怎么连服务端

S8 会把服务跑进容器（compose 里三个服务：postgres / server / web，容器网络内用服务名寻址）。前端侧的纪律只有一条：baseURL 永远是相对路径 '/api'，环境变化不改前端代码——变的是「谁把 /api 转发给服务端」：

场景连线方式为什么
H5 本地开发devServer 代理：开发服务器配置 /api → http://localhost:8080浏览器看到的是同源请求，CORS 根本不登场；服务端地址变了只改代理配置
生产（容器）nginx 反向代理：web 容器发静态资源，location /api 转发到 http://server:8080（服务名寻址）对外只有一个域名，同源；服务端容器不暴露公网端口
真机调试手机访问不了你电脑的 localhost：devServer 要监听局域网 IP，或走隧道工具「模拟器好的、真机连不上」九成是这一条
片段 · nginx 反代的最小形态（S8 的部署产物，这里只求看懂）server {
  listen 80;
  location / { root /usr/share/nginx/html; try_files $uri $uri/ /index.html; }
  location /api/ { proxy_pass http://server:8080; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; }
}

三个连带知识点：① 冒烟用 /healthz——它没有 /api 前缀、不走浏览器链路，部署完先 curl 服务端容器验活，再验 nginx 转发；② CORS_ORIGIN 是服务端 S7 引入的环境变量，只在「浏览器跨源直连服务端」的场景才需要——走了代理/反代的同源链路用不到它；③ 生产 nginx 若要正确记录来源 IP，服务端侧要配合可信代理设置（S8 服务端卡会讲，前端知道有这回事即可）。

5. uni-app 的跨端坑（定位时的「第四嫌疑」）

三段之外还有一类「哪段都没错，换个端就错」的问题，排查时当第四嫌疑处理：

差异典型症状处置
生命周期页面级 onLoad/onShow（uni-app 提供）与组件级 onMounted 时机不同；把请求放错钩子，小程序端时序就不对页面数据进 onLoad/onShow；组件内副作用才用 onMounted（F1 第 4 张的清理纪律照旧）
DOM 与平台 APIH5 里 window/document 随便用，小程序端没有条件编译 #ifdef H5 圈起来，或改用 uni API
样式部分选择器小程序不支持；fixed + 安全区表现不一样式走主题令牌与 rpx；壳组件在双端各验一次
真机 vs 模拟器路径大小写、https 与域名白名单、性能差异——模拟器全绿真机报错收口判据一律以真机为准；域名白名单是小程序平台的部署前置

动手改（今天的判据现场）

目标：给一处失败请求加上「把 request_id 显示出来」的能力，让报障能闭环。起点是 web/src/api/http.js 的拦截器错误分支（F3 建的那个：拆 body.code !== 0 → reject）：

片段 · 起点代码// 响应拦截器（现状：只带出业务码与文案）
if (body.code !== 0) {
  return Promise.reject({ code: body.code, message: body.message })
}

验收口径不是「界面上出现了一串字符」，而是你能讲清这串字符的完整旅程：中间件生成 → 上下文 → 每行日志 → 响应头 → 拦截器 → 界面 → 复制回日志 grep。七站，一站不能断。

定位题（完整症状：写出你的排查顺序）

现象：记一笔流水，点了「保存」，转圈很久，最后弹出「参数错误」。写出你会按什么顺序看哪三个地方、每一步看到什么就能排除哪一类原因。

要求先写排查表再动手（写进 notes/f6w1/），参考骨架：

  1. Network：找那条 POST /api/finance/transactions。(a) 找不到 → 请求没发出去，排除服务端与网络：前端问题——表单校验拦截了提交、按钮 handler 没调请求、或发到了错误的 URL（搜拼串）。(b) 找到了 → 记下三样：发出到响应的耗时、HTTP 状态、响应体 code。「转圈很久」在这里有了第一个分岔：耗时数秒说明请求真实地等了服务端（或前端超时设置过短提前放弃）；如果几乎立刻返回 1004，「转圈很久」是前端 loading 状态没被正确关闭的另一个小 bug——一个症状两个病，Network 一步分开。
  2. 请求 payload 逐字段核对（响应 400 + 1004 时）：金额是不是整数分（把「12.5 元」原样发出去、或发了浮点数，都会被拒——金额契约是 *_cents 整数，前端只负责元 ↔ 分的换算与显示，不做浮点累加）；日期与时间窗编码是否合法（非法编码 1007 且不回落）；必填字段缺没缺、类型对不对（字符串 "100" vs 数字 100）；写请求的幂等键 client_request_id 带没带（没带是前端错；带了但复用旧值会撞 1008）。payload 本身错 → 结论：前端组装问题，不用再看日志。
  3. payload 看着没错 → 拿 request_id 去服务端日志 grep：看拒绝发生在哪一层、错误详情指向哪个字段。两种收尾：日志显示的字段确实在 payload 里有问题（你看漏了）→ 前端；日志显示服务端按契约不该拒（比如校验写错了单位）→ 服务端——你是 owner，改服务端，契约（接口清单与错误码表）是仲裁标准。若日志里压根没有这个 id → 请求没到服务：查代理/反代链路（§4 的表）。

排除逻辑总表：请求没发 → 排除服务端；发了且 payload 错 → 排除服务端；payload 对且日志有拒绝行 → 排除前端组装；日志无此 id → 排除服务端逻辑、锁定链路。每一行都是「看到 X 就排除 Y」——这张表就是 F6 硬判据的答案形态。
