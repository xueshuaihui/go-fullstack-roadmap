前端线毕业自测与红线总核账

前端辅线的最后一张卡。没有新知识——今天全部是验收：三个硬能力逐条过、全站红线复测六条、F1-F6 全 22 张卡的判据总核账，最后产出一份你以后要长期使用的东西：「agent 改了前端，我怎么快速复核」检查单。对应服务端 S8 阶段的收口。毕业硬判据只有一句话：agent 故意留一个 bug（或真出现一个），你能不靠 agent 说出它在哪一层、为什么。

今日目标

今天最容易犯的错：翻着资料做自测。全部脱稿——判据的原话是「不看文档回答」「不靠 agent 说出」。翻资料答对 = 不会。答不上来的条目，回对应卡重做，不裁剪判据。

1. 硬能力 ①：随机打开一页，讲清三段数据链路

验收动作：在 web/src/pages/ 里随机挑三页（一个列表页、一个表单页、一个报表页），每页写出一条完整链路：

片段 · 三段链路的固定句式数据从哪个接口来：GET /api/finance/transactions（Network 里能指认，游标分页）
经过哪个 store：txStore.list / nextCursor / hasMore（唯一赋值来源是 api 层函数）
由哪个组件渲染：TxList.vue 的 v-for + 触底加载调 store.loadMore()

两条固定的查找路线，任选其一走通即可：正向——从页面文件出发，顺着 import 找到用到的 store，再从 store 的 action 找到 api 层函数，函数里的 URL 就是接口；反向——打开页面时在 Network 里看它发了哪些请求，拿 URL 路径字符串全局搜索，命中处就是 api 层，再向上追 store 与组件。讲不清的页 = 该页重读，讲到能脱稿。

2. 硬能力 ②：改一个字段与一处样式，说清影响面

验收动作（改完可还原，但要说得出来）：

改什么怎么改影响面怎么答
一个字段例如把流水列表某列从「分类名」换成「分类名 + 账户名」：改模板绑定，数据不够就改 store 的映射（接口字段本来就有，只是没往上带）全局搜这个字段/这个 store key 的所有读取点，列出还有哪些组件会跟着变；改的是 store 映射就影响所有消费方，改的是模板就只影响这一页
一处样式例如调整卡片圆角或强调色：只许改主题令牌或 scoped 样式，不许在组件里写死色值改令牌 = 全站引用该令牌的地方一起变（先搜引用面再动手）；改 scoped = 只影响本组件。深色主题下再看一眼（F4 的判据）

「说清影响面」的最低标准：动手之前就能列出受影响的页面/组件清单，动手之后逐条验证。先改后看 = 不合格。

3. 硬能力 ③：未知 bug 的层级判定

验收动作：让 agent（或未来的自己）在 web/ 或 server/ 里埋一个 bug，你只用三段定位法（Console → Network → 服务端日志 + request_id）判定它在哪一层，并用证据句式作答：

片段 · 证据句式（判定必须长这样）「我判定这是 {前端|服务端|链路} 问题，
  因为我在 {Network 的响应体 / 日志的哪一行 / Console 的哪条栈} 看到了 {证据}，
  排除了 {另一层}，依据是 {分界物两侧的事实}。」

「感觉是后端的问题」不是判定；没有分界物证据的结论一律重来。分界物清单你已经攒了六件：未读数字（响应 unread vs store）、faces[]（响应数组 vs 渲染格子数）、分包路径（注册表 vs 运行时报错）、PIN 存储键（本地有与没有）、请求发没发（Network 有无该条）、request_id（日志命中与否）。

4. 全站红线复测（六条，命令 + 人眼）

先 cd <你的学习仓根目录>。每条红线 = 一条命令（或一个动作）+ 一句「背后的病」。grep 命中只是线索，不是判决——逐条人眼确认：

红线复测方法背后的病
pages.json 无 tabBargrep -n "tabBar" web/src/pages.json → 必须零输出（CI 第一查）原生 + 自绘双份注册：双底栏、页面栈不可预期
faces[] 无客户端硬编码grep -rn "faces" web/src --include=*.js --include=*.vue → 检查面清单的赋值来源是否只有 home/summary 响应；搜不到任何本地面名常量表双份必漂；前端复刻权限判定与服务端漂移
无硬编码色值grep -rnE "#[0-9a-fA-F]{3,8}" web/src --include=*.vue --include=*.scss → 只允许命中主题令牌定义文件本身深色主题失效；改一处色全站追不上
游标分页不重不漏实操：流水列表下拉刷新后连续触底加载三页，把每页返回的 id 抄下来核对——无重复、无遗漏、has_more 为 false 后不再请求；下拉刷新必须重置游标重 = 刷新没重置游标；漏 = 续读用了旧游标或本地又拼错数组；禁止 offset/总页数的口径也在这里一并确认
金额不在前端做浮点累加grep -rn "reduce" web/src --include=*.js --include=*.vue → 检查命中的累加对象是不是金额；金额只允许「cents 整数 ÷ 100 显示」，报表的累计/环比必须来自 GET /api/finance/reports/summary 的返回字段浮点累加分位漂移；报表数字与服务端对不上账
PIN 无服务端接口grep -rni "pin" web/src/api → 必须零输出；再确认 PIN 模块只出现本地存储调用72 条清单外的假入口；PIN 出端就变第二密码

六条全过 ≠ 背下六条命令。抽问任何一条，你要能立刻说出「病是什么、判据卡在哪张卡」——说不出来就回那张卡重做。

5. F1-F6 全 22 张卡判据总核账

建 notes/f6w2/review.md，把下表手抄进去逐行填「能 / 不能」与卡壳点。这是整条前端线的毕业账本——任何一行「不能」，回那张卡原地重做：

段毕业判据（脱稿）能 / 不能
F1（4 张）「这个变量改了，为什么那个地方会重渲染」——读即依赖，没有依赖数组；SFC 三段、computed/watch、props/emit/slot、生命周期清理各一句
F2（2 张）pages.json 为什么不能有 tabBar（反例判据）；能把请求层指向本地 Go 服务并看到响应
F3（3 张）401 时前端该做什么（refresh → 重放一次）不该做什么（无限重试）；token 存在哪、为什么；登录 → 建家庭 → 拉分类全链路讲清
F4（7 张）游标分页前端侧不重复、不漏、触底续读；能改出一套深色主题变量；组件拆分与图表各讲一处
F5（4 张）面清单为什么不允许客户端二次裁剪；能配一个分包并说明何时被下载；壳的数据流与 PIN 边界（notes/f5w4/review.md 六条）
F6（2 张）三段定位法默画；硬判据：埋一个 bug，不靠 agent 说出在哪一层、为什么

22 张卡的定位题笔记（F1 四则、F2-F4 各则、F5 四则、F6 两则）合并成一份 notes/f6w2/定位案例集.md——按「分界物」归类，不按周归类。这份案例集就是你的定位能力本体。

6. 产出：快速复核检查单（以后长期用）

写进 notes/f6w2/recheck-checklist.md。目标：agent 每次交付前端改动，你 5 分钟内完成复核。骨架（可增删，但四步不能少）：

步动作耗时
1. 红线 grep§4 的六条命令跑一遍，零输出/白名单命中才继续1 分钟
2. 冒烟开首页：Network 里只有一个 home/summary 聚合请求；翻一页流水列表：游标续读正常；触发一次失败请求：request_id 可见2 分钟
3. 抽查一页讲链路从本次改动涉及的页面里随机挑一页，脱稿讲三段数据链路；讲不清 = 打回并记下这一页1 分钟
4. diff 扫一眼看 agent 的改动清单：有没有新增 store、有没有动 http 层、有没有新出现的绝对地址或色值——这三处是架构级变更，必须逐行读1 分钟

动手改（今天的判据现场）

目标：挑一处你觉得 agent 写得最绕的代码，重构它，且行为不变。「绕」的常见形态：一个函数干三件事、模板里的三层嵌套三元、该是 computed 的却写成 watch 再赋值、复制粘贴的五段相似代码。流程是判据本体：

React 对照：这就是你熟悉的「refactor without changing behavior + characterization test」流程，只是这里的 characterization test 是手工基线表。前端线毕业不要求你会写 Vue 工程，但要求你有这套安全改代码的流程感——因为以后 agent 交付的每一次改动，本质上都是别人替你做了「动手改」，你要做的是验收。

定位题（这次你自己出）

任务：自己出一道定位题——写清症状、正确结论、以及排除其他结论的依据。格式照下面的示范答案，成品记进 notes/f6w2/。

出题要求：症状必须是用户视角的一句话（不许直接写「store 里数组重复了」这种答案泄露式描述）；结论必须落在某一层（前端 / 服务端 / 链路 / 设计如此）；依据必须引用三段里的可观察证据，且至少排除两个错误结论。

示范答案（照这个标准出你的题）——症状：「流水列表下拉刷新之后，最上面几条重复出现了两次。」结论：前端——下拉刷新处理器没有重置游标与列表数组，把同一页又 append 了上去。依据：Network 里看到刷新后发出的两次 GET /api/finance/transactions 携带了相同的 cursor 参数，两次响应的 list 内容逐条相同——服务端对同一游标返回同一页，行为符合契约（游标不透明、无状态），排除服务端；Console 无报错、渲染出的条数与 store 里数组长度一致，排除渲染层；store 里数组本身就有重复项，问题锁定在「谁往数组里塞的第二遍」→ 刷新处理器。顺手验证：修复后同场景两次请求的 cursor 一次为空（重置）一次为新游标。

出完题的自检：把你写的症状念给别人听（或未来的自己），对方只凭三段定位法能不能走到你的结论？走不到 = 依据没写全，补。

常见坑

坑现象正确姿势
拿「页面能跑」当毕业自测全勾，一被抽问就卡壳判据全是「能讲清 / 能改」；全部脱稿
红线复测只跑 grep 不解含义命令会跑，问「为什么是红线」答不上每条红线配一句「背后的病」，抽问即答
grep 命中就当违规令牌定义文件里的色值、注释里的 pin 字样被误判命中是线索，人眼确认才算判决
重构顺手改行为「反正这看着也像 bug」——两个改动搅在一起，坏了不知道谁坏的重构与修 bug 永远分开提交；先基线后动手
自出定位题症状泄露答案「store 数组重复了，为什么」——这考不到定位症状只写用户视角可观察的现象
影响面「先改后看」改令牌改出全站连锁变化，回滚都找不全动手前先列受影响清单，动手后逐条验
核账表翻资料填填完全「能」，实为照抄脱稿；填「不能」不丢人，漏空洞才丢人

今日名词卡

术语一句话解释
三段数据链路接口 → store → 组件；读懂任意一页的固定讲述顺序
行为基线重构前记录的 3-5 种输入下的可观察行为；「行为不变」的唯一裁判
特征化验证用基线逐条重验重构结果的手法（手工版 characterization test）
红线复测六条全站纪律的命令化检查；grep 是线索、人眼是判决
证据句式「我判定 X 层，因为在 Y 看到 Z，排除了 W」——层级判定的合格作答格式
分界物两侧事实能切开两类结论的那个可观察对象（响应数组、存储键、注册表、日志行…）
冒烟检查最小功能验证集：首页单请求、列表续读、失败请求带 id
快速复核检查单agent 每次交付后的 5 分钟四步验收流程；本卡最终产出
影响面一处改动波及的页面/组件清单；动手前列出、动手后验证
脱稿自测不翻资料作答；前端线全部判据的验收口径
