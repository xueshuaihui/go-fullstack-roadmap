生命周期钩子与 composable

这是 F1 的最后一张卡，两件事：① 补齐心智模型的最后一块——组件什么时候出生、什么时候死、死之前要打扫什么；② F1 收口：四张卡的判据逐条自测，回答毕业题。生命周期这块恰好是 React 的 useEffect 拆成具名钩子的地方，也是前端「资源泄漏」这类 bug 的老家。

今日目标

F1 的毕业判据（阶段总览里那条）：不看文档，回答「这个变量改了，为什么那个地方会重渲染」。答案你已经见过两次了——今天收口时要能完整讲给别人听，包括「为什么没有依赖数组」。

1. React → Vue：这一周的映射行

ReactVue 3差异要点
useEffect(() => {…}, [])onMounted(() => {…})具名钩子，不靠空数组表达「只跑一次」
useEffect 的 return 清理函数onUnmounted(() => {…})清理逻辑从「同一个函数的返回值」变成「另一个具名钩子」
自定义 hook useXxx()composable useXxx()形态几乎一样；差别在 Vue 的 composable 靠自动依赖追踪，不返回「要手动 spread 的依赖数组」
StrictMode 下 effect 跑两次无对应行为Vue 开发模式不会故意双调钩子

常用钩子按时间轴排一遍（F1 只要求前两个，其余混个脸熟）：

钩子时机典型用途
setup（即 <script setup> 本身）组件实例创建时，早于挂载定义状态、computed、watch
onMountedDOM 挂好后发首屏请求、启动定时器、量元素尺寸
onUpdated响应式数据变更导致 DOM 更新后很少用；用了先自问是不是该用 watch
onUnmounted组件销毁时清定时器、解绑全局监听、中止请求

onMounted ≠ 「数据就绪」。挂载完成只代表 DOM 有了，首屏数据此时往往还没回来（请求刚发出去）。所以模板里凡读接口数据的地方，都要能扛住「数据还是初始值」的第一帧——这也是为什么状态初始值要给得有意义（空数组而不是 undefined）。

2. composable：把「一组状态 + 它的生老病死」打包

composable 就是一个普通函数，约定 use 开头，内部可以建 ref、注册钩子，返回一组响应式值：

片段 · 形态示意（完整实现见动手改）// useXxx.js
import { ref, onUnmounted } from 'vue'

export function useXxx() {
  const state = ref(0)
  const timer = setInterval(() => { state.value++ }, 1000)
  onUnmounted(() => clearInterval(timer))  // 谁生的谁养
  return { state }
}

三条纪律：

纪律原因
只能在 script setup 顶层同步调用钩子注册依赖「当前正在初始化哪个组件」的上下文；放进回调或 v-if 分支里，上下文就丢了
在 composable 里注册的 onUnmounted 会绑到调用它的组件所以清理逻辑跟着 composable 走，组件不用重复写——这正是它比裸 setInterval 强的地方
返回 ref 而不是 .value 后的裸值裸值解包一次就断了响应性；调用方拿到 ref 整对象，模板里自动解包

和 React hook 的心智差别只有一条：Vue 的 composable 不需要返回依赖数组、调用方也不需要传依赖——依赖追踪是自动的（读即依赖，第三次出现这句话了）。

结构 · 产出目标notes/f1w4/

定位题（四步法的第四次练习）

现象：离开页面之后，Network 里请求还在每隔几秒发一次。

这是前端生命周期泄漏的标准现场——和服务端「goroutine 泄漏」是同一类病：有东西生了没人杀。排查链：

  1. 确认「离开」的含义：是路由切换（组件销毁）还是切到别的浏览器标签页（组件还活着）？后者发请求是正常行为——先别冤枉代码。
  2. 路由切换还在发 → 找定时器/轮询：全局搜 setInterval / setTimeout / watch 里发起的请求，逐个问「注册它的人在 onUnmounted 里清理了吗」。
  3. 清理写了但没生效？两个高频死法：① 清理代码写在了 composable 外面，而定时器建在 composable 里面——注册和清理不在同一层；② 在异步回调里建的定时器，建的时候组件已经卸载，onUnmounted 早就跑完了，清理扑空。
  4. 验证：在 onUnmounted 里加一行日志，路由切走看它打没打；打了但请求还在 → 泄漏源不止一处，回到第 2 步继续搜。

把「生命周期泄漏排查链」补进 notes/。到这里四步法已经练了四轮：绑定层（w01）→ 依赖层（w02）→ 数据流层（w03）→ 生命周期层（w04），F6 的定位判据在 F1 打的地基就是这四层。

毕业题的参考答案骨架（先自己讲，讲不下去再看）：读即依赖——组件渲染函数执行期间，读过哪些 ref，Vue 就把这些 ref 记为它的依赖；任何一个依赖变化，就重新执行这个组件的渲染函数，DOM 随之更新。不需要依赖数组，因为「读了谁」是运行时自动收集的，不存在漏写。computed / watch / 模板三者共用同一套追踪机制。

四轮的定位题笔记（四步法 + computed 分层 + props 排查链 + 生命周期泄漏）合并检查一遍——这份东西就是 F6「独立定位一个前后端 bug」判据的原始积累。

常见坑

坑现象正确姿势
定时器不清理离开页面请求还在发；页面越用越卡onUnmounted 里 clearInterval；或封进 composable 让它自带清理
钩子写在回调 / 条件分支里钩子不触发或绑错组件，警告难懂onMounted 等只能在 script setup 顶层同步调用
以为 onMounted 时数据已就绪首帧渲染 undefined 报错状态给有意义的初始值；模板对「还没数据」可渲染
composable 返回 .value 裸值调用方拿到的数字不再更新返回 ref 整对象；解包交给模板
把 onUpdated 当 watch 用任何状态变化都触发，逻辑纠缠盯具体数据用 watch；onUpdated 只留给「每次 DOM 更新后必须做」的事
全局事件监听只加不解同一监听器叠 N 份，一次点击触发 N 次onMounted 加、onUnmounted 解，成对出现
