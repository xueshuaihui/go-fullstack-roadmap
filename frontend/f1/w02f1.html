组合式 API：computed 与 watch

上周你把 React 心智模型翻译成了 Vue 3。这周补上翻译表里最容易翻错的一行：派生状态与副作用。React 里这两件事都塞进 useMemo / useEffect，Vue 把它们拆成两个职责单一的工具——computed 负责「由别人算出来的值」，watch 负责「值变了之后要干的活」。今天的判据只有一个：不看资料，说清两者的缓存与触发时机差别。

今日目标

还是那条纪律：前端线的判据不是「代码写没写出来」，而是能讲清、能改、能定位。今天写的 SFC 依然存进 notes/，不进任何构建——跑起来是 F2 的事。

1. React → Vue：这一周的映射行

ReactVue 3差异要点
useMemo(() => f(x), [x])computed(() => f(x.value))Vue 不写依赖数组——回调里读了谁就自动依赖谁（读即依赖，上周的毕业判据）
useEffect(() => {…}, [x])watch(x, (newVal, oldVal) => {…})watch 只在源变化时跑；默认不在挂载时立即跑一次，这点和 useEffect 相反
useEffect(…, [])（只跑一次）onMounted(…)具名钩子，不靠空依赖数组表达（w04 展开）
setState 时顺手算派生值派生值一律 computed，不要用 watch 手动同步「watch 一个值再 set 另一个值」在 Vue 里多数是坏味道，见 §4

2. computed：惰性 + 缓存的派生值

片段 · script setup 里import { ref, computed } from 'vue'

const items = ref([
  { id: 1, name: '牛奶', cents: 1250 },
  { id: 2, name: '面包', cents: 800 },
])

// 回调里读了 items.value —— items 就是它的依赖，自动的
const totalYuan = computed(() =>
  items.value.reduce((sum, it) => sum + it.cents, 0) / 100
)

三条性质，逐条讲得出来才算过：

性质含义和 React 的差别
惰性没人读 totalYuan.value，回调就根本不执行useMemo 在每次渲染时都会评估要不要重算；computed 连评估都懒得做
缓存依赖没变，重复读一万次也只算一次同 useMemo，但依赖是自动收集的，不用手写数组、不会漏写
只读totalYuan.value = 5 会警告且不生效——它是算出来的，不是存起来的React 里没有直接对应物；硬要对应就是「你不会去 setState 一个 useMemo 的结果」

computed 里不许有副作用。发请求、改别的 ref、console.log 之外的任何「干事」，都不属于 computed——它的契约是「同样的依赖算出同样的值」。想「值变了之后干件事」，那是 watch 的活。

金额用 cents（整数分）存、显示时才 ÷100，这个习惯和服务端的 amount_cents 约定是同一件事的两端——前端不许自己发明「元」为单位的浮点存储。

3. watch：值变了之后干一件事

片段 · script setup 里import { ref, watch } from 'vue'

const keyword = ref('')

watch(keyword, (newVal, oldVal) => {
  // 副作用区：发请求、写 localStorage、打日志……
  console.log(`搜索词从「${oldVal}」变成「${newVal}」`)
})
行为默认值怎么改
挂载时立即跑一次？不跑（和 useEffect 相反）{ immediate: true }
盯对象内部字段变化？不盯，只盯引用替换{ deep: true }——大列表慎用，遍历有成本
盯多个源？—watch([a, b], ([newA, newB]) => …)
组件卸载后还触发？不会，script setup 里创建的 watch 自动停在异步回调里创建的 watch 要手动 stop()（w04 再碰）

还有个 watchEffect：不用声明源，回调里读了谁就盯谁，且立即跑一次。本项目约定：优先写明确源的 watch——「盯什么」写在明面上，读代码的人不用进回调里找。知道 watchEffect 存在即可，F1 不要求会用。

4. 选哪个：一句话判据

要一个值 → computed；要干一件事 → watch。最典型的坏味道是「用 watch 手动同步派生值」：

片段 · 反例// ❌ 坏味道：keyword 变了就手动重算 filtered
const filtered = ref([])
watch(keyword, () => { filtered.value = items.value.filter(…) })

// ✅ 正确：filtered 是「算出来的值」，交给 computed
const filtered = computed(() => items.value.filter(…))

反例多了一个可写 ref、多了一次同步时机的心智负担，还引入了「初始值没算」的 bug（watch 默认不立即跑）。凡是能写成 B = f(A) 的，都是 computed。

定位题（四步法的第二次练习）

现象：列表有数据，但「合计」一直显示 0 元。

接着上周的四步法走，这次重点练第 2、3 步的分层：

  1. Console：有红色报错吗？有 → 先看堆栈第一行，可能是 undefined.reduce 这类运行时错误。
  2. Network：如果列表数据来自接口——响应体里金额字段有值吗？字段名和前端读的一致吗（cents vs amount_cents）？值在但字段名对不上 → 前后端契约问题，去对接口文档。
  3. 前端绑定层：接口有值、字段也对，合计却是 0 → 三个高频死法逐一排：① 求和时读了 items 而不是 items.value（script 里漏 .value）；② 把接口数据赋给了 items 而不是 items.value（整个 ref 被替换成数组，响应性断掉）；③ 字段类型是字符串，'1250' + '800' 变成了拼接再被 NaN 掉。
  4. 验证：在 computed 回调里临时加一行 console.log——它到底跑没跑？跑了但结果是 0 → 输入数据的问题；根本没跑 → 依赖没被读到（多半是模板里读的不是这个 computed）。

把「computed 没触发」和「computed 算错了」这两种情况分开，是这道题真正要练的东西——前者查依赖链，后者查数据。补进 notes/ 里上周那份四步法。

常见坑

坑现象正确姿势
computed 回调里漏 .value依赖收集不到，值永远不更新且不报错回调里读 ref 必须 x.value；读漏一次，缓存就永久失效
给 computed 赋值控制台警告 Write operation failed它是只读派生值；想改就改它的依赖
用 watch 同步派生值初始不算、时机难控、多一个可写 ref能写成 B = f(A) 的一律 computed
watch 对象忘了 deep改 obj.a 不触发，只有整体替换才触发要么 { deep: true }，要么直接盯 () => obj.a（getter 形式）
以为 watch 挂载时会跑一次首屏数据「没加载」默认不跑；需要就 { immediate: true }，或把首次加载放 onMounted（w04）
在 computed 里发请求重渲染时重复请求、时序错乱请求是副作用，归 watch / onMounted 管

今日名词卡

术语一句话解释
computed惰性求值 + 自动缓存的只读派生值；依赖自动收集，读即依赖
watch盯住声明的源，变化时执行副作用回调；默认不立即跑、不深盯
watchEffect自动收集依赖的 watch 变体，立即执行一次；本项目约定少用
deep / immediatewatch 的两个选项：深盯对象内部 / 挂载时先跑一次
副作用（side effect）计算返回值之外的「干事」：请求、定时器、写存储、改别的状态
getter 形式的源watch(() => obj.a, …)——盯对象里的某个字段而不开 deep
派生值坏味道用 watch + 可写 ref 手动同步本可以 computed 的值
