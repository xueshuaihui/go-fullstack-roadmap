日志、请求 ID 与优雅关闭

接口能跑只是及格线；出问题时的可观测性和下线时的体面才区分玩具和工程。今天三件事：把 fmt.Printf 升级成结构化日志 slog；给每个请求盖一个 X-Request-ID 钢印方便 grep 全链路；用 http.Server.Shutdown 让 kill 信号到来时先把存量请求伺候完再走。

今天的验收带一点「表演性质」：晚上睡前把服务用 kill -TERM 停一次，看着它在途请求跑完才说 bye，你会对「生产就绪」这四个字有实感。

课前须知：给 JS 开发者的两句话

1. 后端日志的第一读者不是你，是 3 个月后的你和日志采集系统。winston/pino 教会你的「level + JSON 输出」在 Go 里的原生答案是 Go 1.21 进标准库的 log/slog——不用装包。

2. Node 里你可能写过 process.on('SIGTERM', ...)；Go 里对应 signal.NotifyContext。Gin 的 r.Run() 内部自己起了 http.Server 且拿不到引用，所以优雅关闭必须改用显式的 http.Server。

知识讲义

1. fmt.Printf vs slog：差别在哪

对比// fmt.Printf —— 一锅粥文本，机器没法聚合
fmt.Printf("登录失败 user=%s ip=%s err=%v\n", name, ip, err)

// slog —— 结构化：消息 + 键值对，输出为可解析 JSON
slog.Error("登录失败", "user", name, "ip", ip, "error", err)
// {"time":"2026-09-23T20:11:02+08:00","level":"ERROR","msg":"登录失败","user":"alice","ip":"127.0.0.1","error":"..."}
能力fmt.Printfslog
分级过滤（Debug 只在开发开）❌ 全靠注释✅ Debug/Info/Warn/Error 四级起步
按字段检索（user=alice 全捞出来）❌ 正则碰运气✅ JSON 直接被 ELK/Loki 采集
统一时间戳/格式❌ 手写 \n 忘了就串行✅ Handler 统一负责
并发安全部分场景交错输出✅ 内置锁

2. slog 上手：Handler、Logger、Level

internal/pkg/log/log.gopackage log

import (
    "log/slog"
    "os"
    "strings"
)

// New 按 gin_mode 顺带决定日志级别：debug 环境看 Info 以下，生产只看 Warn+
func New(mode string) *slog.Logger {
    level := slog.LevelInfo
    if strings.EqualFold(mode, "release") {
        level = slog.LevelWarn
    }
    h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level})
    return slog.New(h)
}
用法logger := log.New(cfg.GinMode)
logger.Info("服务启动", "port", cfg.Port)
logger.With("request_id", rid)   // With 派生"带着公共字段"的子 logger，业务层到处传它
logger.Error("写库失败", "table", "articles", "error", err)

API 记忆点：slog.New(slog.NewJSONHandler(w, opts)) 造实例；键值对成对传（写奇数个会把最后一个当属性名乱配）；生产别用 NewTextHandler，JSON 才谈得上检索。

3. 访问日志中间件（Logger 注入）

internal/middleware/access_log.gofunc AccessLog(logger *slog.Logger) gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        path := c.Request.URL.Path
        if c.Request.URL.RawQuery != "" {
            path += "?" + c.Request.URL.RawQuery
        }
        c.Next()                       // ← 先放行，回来时状态码已写好
        logger.Info("access",
            "method", c.Request.Method,
            "path", path,
            "status", c.Writer.Status(),  // c.Writer 实现了 Status()
            "latency_ms", time.Since(start).Milliseconds(),
            "ip", c.ClientIP(),
            "request_id", c.GetString("request_id"),
        )
    }
}

Gin 自带 gin.Logger() 可先用着，但它输出的是文本行；自己写 20 行的好处是每行都是 JSON、级别可控、字段随你加（比如下一节的 request_id）。中间件注册顺序：RequestID 在前，AccessLog 在后，日志才有 ID 可打。

关于 c.ClientIP() 的一个前置知识：它拿到的是「与服务器建 TCP 连接那台机器的 IP」。本机测试是 127.0.0.1 没问题；将来套上 Nginx 后所有人都会变成代理机的 IP。到第 7 周再处理（r.SetTrustedProxies + X-Forwarded-For），今天先挂个 TODO，别现在就去自行解析转发头——那会引入「IP 可被伪造」的新坑。

4. 请求 ID：生成、透传、回写

shell$ go get github.com/google/uuid
internal/middleware/request_id.goconst HeaderRequestID = "X-Request-ID"

func RequestID() gin.HandlerFunc {
    return func(c *gin.Context) {
        rid := c.GetHeader(HeaderRequestID)      // 网关/前端已带则沿用，串起跨服务链路
        if rid == "" {
            rid = uuid.NewString()
        }
        c.Set("request_id", rid)                // 业务层用 c.GetString("request_id") 取
        c.Writer.Header().Set(HeaderRequestID, rid) // 回写响应头：用户报障时甩这个 ID 给你
        c.Next()
    }
}

// 业务层带出的典型用法（service 收 *slog.Logger 参数）：
func (h *AuthHandler) Login(c *gin.Context) {
    logger := h.logger.With("request_id", c.GetString("request_id"))
    // ... 后续该请求的所有日志自动带同一个 request_id ...
    logger.Warn("登录失败", "user", req.Username, "error", err)
}

排查场景秒懂：用户说「我 20:11 登录报错」。你让他看响应头/前端日志里的 X-Request-ID，然后 grep 那个ID app.log | jq . —— 这次请求从进来到写库失败的每一行日志按时间排好躺在眼前。这就是「全链路追踪」的最小可用版。

5. 优雅关闭：Shutdown 全流程

粗暴关闭（Ctrl+C 直接退）的问题：正在处理到一半的请求被掐断，用户拿到连接重置。优雅关闭 = 停止接新活 → 等在途干完（有上限）→ 退出：

cmd/server/main.go    srv := &http.Server{
        Addr:    ":" + cfg.Port,
        Handler: r,                       // r 是 *gin.Engine，它实现了 http.Handler
        ReadTimeout:  5 * time.Second,   // 生产服务务必设超时，防慢连接拖垮
        WriteTimeout: 10 * time.Second,
    }

    // 1. 造一个"收到 SIGINT/SIGTERM 就自动 cancel"的 context
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    // 2. ListenAndServe 是阻塞的，放到 goroutine 里跑
    go func() {
        logger.Info("服务启动", "addr", srv.Addr)
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            logger.Error("监听失败", "error", err)
            os.Exit(1)
        }
    }()

    // 3. 主 goroutine 阻塞在这：等信号
    <-ctx.Done()
    logger.Info("收到退出信号，开始优雅关闭（最多等 10 秒）")

    // 4. Shutdown：关闭监听、等在途请求处理完；给了 10 秒上限，到点强退
    shutCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutCtx); err != nil {
        logger.Error("优雅关闭超时，强制退出", "error", err)
    }
    logger.Info("bye 👋 存量请求已处理完毕")
零件职责
signal.NotifyContextSIGTERM/SIGINT 一到就 cancel 掉 ctx——把信号翻译成 context 语言
<-ctx.Done()主函数挂起等待，否则 main 立刻跑完程序就退了
srv.Shutdown(ctx)关监听 + 等空闲；ctx 超时则不再等。K8s/Docker 停容器默认就是发 SIGTERM
http.ErrServerClosedShutdown 会让 ListenAndServe 返回这个「正常退休」错误，必须排除掉别当事故报

别忘了 main.go 顶部 import："context" "errors" "net/http" "os/signal" "syscall"。另外 gin.SetMode(cfg.GinMode) 要在 gin.Default() 之前调用，否则模式已按 debug 定了——release 模式会关掉调试色的控制台输出，为第 7 周部署做好准备。

6. Shutdown 时序图解与两个延伸点

时序t0   用户请求A ──────────▶ handler 处理中（5 秒 sleep）
t0+1 kill -TERM ─▶ ctx cancel ─▶ main 醒来 ─▶ srv.Shutdown()
                       │
                       ├─ 立即：关闭监听端口，新请求 TCP 层不再受理
                       └─ 等待：请求A 继续跑… t0+6 返回 200 ─▶ Shutdown 返回 ─▶ main 打印 bye 退出
（若请求A 要跑 30 秒：t0+11 到达 WithTimeout 上限，Shutdown 带 error 返回，进程照样退出——有界等待是底线）
延伸点说明
srv.Close() vs srv.Shutdown(ctx)Close 立即掐断全部连接，等于粗暴版；Shutdown 才优雅。生产只应出现 Shutdown
清理资源的挂载位Shutdown 返回后、进程退出前，是关数据库连接池/刷日志缓冲的位置：sqlDB, _ := db.DB(); sqlDB.Close()
Docker/K8s 的对应关系docker stop 默认发 SIGTERM、10 秒后补 SIGKILL；你的 10 秒 Shutdown 预算要与它对齐，否则永远是被 -9 带走

今日练习

练习 1：装上三件套并观察（60 分钟，主线）

接入 RequestID → AccessLog → Auth 中间件链（顺序有讲究），main 换成 http.Server + Shutdown 版本。验证：curl -i localhost:8080/articles 响应头有 X-Request-ID，stdout 出现对应 JSON 日志行。做完再验证一次失败路径：不带 token 的请求，日志里应出现 "status":401 且 request_id 与响应头一致——失败请求同样要被追踪。

参考答案（要点）

r.Use(middleware.RequestID(), middleware.AccessLog(logger)) 放在路由注册前；curl -i 看到 X-Request-ID: 5b8a...(uuid)，同时日志里 {"msg":"access","method":"GET","path":"/articles","status":200,"latency_ms":1,"ip":"127.0.0.1","request_id":"5b8a..."} 两边 ID 一致。

练习 2：kill -TERM 观察优雅关闭（25 分钟）

终端 A 启服务；终端 B 写个 /sleep 接口（handler 里 time.Sleep(5*time.Second) 后返回 ok）并发起请求，请求飞行途中执行 kill -TERM <pid>。

参考答案

现象：终端 A 立刻打印「收到退出信号…」，但进程没死；5 秒后 /sleep 请求正常拿到 200 响应，随后打印「bye 👋」。对照组：换成 kill -9 则请求直接 connection reset——-9 不可捕获，没有优雅可言。

/sleep 接口参考实现（仅本地测试用，别带进生产）：

main.go 临时路由    r.GET("/sleep", func(c *gin.Context) {

连续制造 3 次登录失败（带同一个用户名），从响应头里任取一个 request_id，用 grep 该ID + jq . 把这次请求的 access 行与业务 Warn 行一起捞出来按时间读一遍。

练习 4：级别开关验证（15 分钟）

GIN_MODE=release go run ./cmd/server 启动，确认 Info 级 access 日志消失、Error 仍输出（可临时制造一次 500 验证）。理解「代码不变、环境变、行为变」。

常见坑（新手 100% 会踩）

坑现象正确姿势
中间件里先 return 后打日志access 日志永远不输出，或状态码是 0记录型中间件先 c.Next()，放行后再取 Status()
RequestID 顺序放 Auth 后面401 的日志没有 request_id，白名单外的请求查不到RequestID 永远第一个 Use
忘排 http.ErrServerClosed每次正常关闭都打一条「监听失败」Error 还 os.Exit(1)!errors.Is(err, http.ErrServerClosed) 才算真故障
ListenAndServe 没放 goroutine主 goroutine 被阻塞，下面的信号等待永远执行不到，kill 无反应服务跑 go func，main 等 ctx.Done()
Shutdown 不给超时 ctx有个长轮询请求挂着，进程永远退不掉，部署卡到被 kill -9必须 context.WithTimeout 包一层上限
日志里打敏感字段access 日志把 password 明文、完整 token 打进 stdout，日志文件成了第二数据库只打 path 不打 body；需要认证上下文时只打 request_id/userID
用 print 混用两套输出一半 fmt.Println 一半 slog，级别格式互不相干，检索时漏一半服务启动后全项目只允许 logger，fmt 仅限 CLI 一次性脚本
slog 键值对写漏一个logger.Info("x", "user") 少配对值，输出里出现 "!BADKEY"键值必须成对；条件字段用 slog.Any/slog.Group 动态拼装
在循环里新建 logger/Handler每个请求 new 一个 JSONHandler，锁与缓冲区反复重建，性能白流main 里建一次 logger，经构造函数注入到 handler/service 全链路共享
