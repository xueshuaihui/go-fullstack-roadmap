日志、请求 ID 与优雅关闭

接口能跑只是及格线；出问题时的可观测性和下线时的体面才区分玩具和工程。今天三件事：把 fmt.Printf 升级成结构化日志 slog；给每个请求盖一个 X-Request-ID 钢印方便 grep 全链路；用 http.Server.Shutdown 让 kill 信号到来时先把存量请求伺候完再走。

今天的验收带一点「表演性质」：晚上睡前把服务用 kill -TERM 停一次，看着它在途请求跑完才说 bye，你会对「生产就绪」这四个字有实感。

课前须知：给 JS 开发者的两句话

1. 后端日志的第一读者不是你，是 3 个月后的你和日志采集系统。winston/pino 教会你的「level + JSON 输出」在 Go 里的原生答案是 Go 1.21 进标准库的 log/slog——不用装包。

2. Node 里你可能写过 process.on('SIGTERM', ...)；Go 里对应 signal.NotifyContext。Gin 的 r.Run() 内部自己起了 http.Server 且拿不到引用，所以优雅关闭必须改用显式的 http.Server。

知识讲义

1. fmt.Printf vs slog：差别在哪

对比// fmt.Printf —— 一锅粥文本，机器没法聚合
fmt.Printf("登录失败 user=%s ip=%s err=%v\n", name, ip, err)

// slog —— 结构化：消息 + 键值对，输出为可解析 JSON
slog.Error("登录失败", "user", name, "ip", ip, "error", err)
// {"time":"2026-09-23T20:11:02+08:00","level":"ERROR","msg":"登录失败","user":"alice","ip":"127.0.0.1","error":"..."}
能力fmt.Printfslog
分级过滤（Debug 只在开发开）❌ 全靠注释✅ Debug/Info/Warn/Error 四级起步
按字段检索（user=alice 全捞出来）❌ 正则碰运气✅ JSON 直接被 ELK/Loki 采集

2. slog 上手：Handler、Logger、Level

internal/pkg/applog/applog.go（新文件）package applog

import (
    "log/slog"
    "os"
    "strings"
)

// New 按 gin_mode 顺带决定日志级别：debug 环境看 Info 以下，生产只看 Warn+
func New(mode string) *slog.Logger {
    level := slog.LevelInfo
    if strings.EqualFold(mode, "release") {
        level = slog.LevelWarn
    }
    h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level})
    return slog.New(h)
}

为什么这个包叫 applog 而不是 log：Go 的包名就是调用前缀。如果你建 internal/pkg/log，main.go 里既要 log.Fatal("配置加载失败")（标准库）又要 log.New(cfg.GinMode)（自家的），两个 log 打架，编译直接报 log redeclared in this block。要么换个不撞名的包（我们的做法），要么起别名 applog "goblog/internal/pkg/log"——别名容易漏，初学者抄代码时最常见的报错就来自这里。对照 JS：ESM 里 import log from './log.js' 和全局 console 不会撞名，因为 JS 没有「包名即前缀」这回事。

用法（前两行与最后一行在 main.go 里，第 8 节给完整文件；中间那行 With 在 handler 里，见第 4 节）logger := applog.New(cfg.GinMode)          // *slog.Logger，全项目只建这一个
logger.Info("服务启动", "port", cfg.Port)
logger.With("request_id", rid)              // With 派生"带着公共字段"的子 logger，业务层到处传它
logger.Error("写库失败", "table", "articles", "error", err)

API 记忆点：slog.New(slog.NewJSONHandler(w, opts)) 造实例；键值对成对传（写奇数个会把最后一个当属性名乱配）；生产别用 NewTextHandler，JSON 才谈得上检索。applog.New 的入参就是昨天 cfg.GinMode 那个字符串——本周刻意不加 LOG_LEVEL 这个环境变量：配置项越少越不容易和 GIN_MODE 打架（两个都能控制级别时，谁赢？），第 7 周真要按文件分级时再单开一项。

3. 访问日志中间件（Logger 注入）

internal/middleware/access_log.gopackage middleware

import (
    "log/slog"
    "time"

    "github.com/gin-gonic/gin"
)

// AccessLog 收一个 *slog.Logger 参数：级别随配置走
// （第 3 天 cfg.GinMode 决定的就是它）——这就是「注入 logger 而不是裸用 slog 默认实例」的价值
func AccessLog(logger *slog.Logger) gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        path := c.Request.URL.Path
        if c.Request.URL.RawQuery != "" {
            path += "?" + c.Request.URL.RawQuery
        }

        c.Next()                       // ← 先放行，回来时状态码才写得好（第 2 天说过的「gin 中间件有回程」）

        logger.Info("access",
            "method", c.Request.Method,
            "path", path,
            "status", c.Writer.Status(),          // c.Writer 实现了 Status()
            "latency_ms", time.Since(start).Milliseconds(),
            "ip", c.ClientIP(),
            "request_id", c.GetString(CtxKeyRequestID),  // ← 第 4 节定义的常量，值就是 "request_id"
        )
    }
}

Gin 自带 gin.Logger() 可先用着，但它输出的是文本行；自己写 20 行的好处是每行都是 JSON、级别可控、字段随你加（比如下一节的 request_id）。中间件注册顺序：RequestID 在前，AccessLog 在后，日志才有 ID 可打。

JS 对照：这就是 pino/http 中间件里 const t0 = Date.now(); await next(); logger.info({status: res.statusCode, ms: Date.now()-t0}) 的 Go 版。c.Next() 相当于那个 await next()（Koa 的洋葱模型），Express 里则要靠 res.on('finish', ...) 才拿得到状态码——gin 在 c.Next() 之后直接读 c.Writer.Status() 就行。

关于 c.ClientIP() 的一个前置知识：它拿到的是「与服务器建 TCP 连接那台机器的 IP」。本机测试是 127.0.0.1 没问题；将来套上 Nginx 后所有人都会变成代理机的 IP。这一条第 7 周 D2 的 nginx 课兑现（那一节 4.2 就写着 r.SetTrustedProxies([]string{"172.16.0.0/12"})，并讲 X-Forwarded-For 的可信边界）。今天先挂在这里，不要现在就去自行解析转发头——那会引入「IP 可被客户端伪造」的新坑。

4. 请求 ID：生成、透传、回写

一个请求在服务里往往会留下两三行日志（access 一行、业务 Warn 一行、可能还有 GORM 一行）。想把它们按顺序串起来，就得在进门那一刻给请求盖个钢印。先装 uuid：

shell$ go get github.com/google/uuid
internal/middleware/request_id.go（新文件，和第 2 天的 auth.go 同属 middleware 包）package middleware

import (
    "github.com/gin-gonic/gin"
    "github.com/google/uuid"
)

// 两个常量都放这里：CtxKeyRequestID 是 context 里的键名（第 3 节 access_log.go 用的就是它），
// HeaderRequestID 是对外暴露的 HTTP 头名。同包内常量共享，不需要 import、也不要重复定义
const CtxKeyRequestID = "request_id"
const HeaderRequestID = "X-Request-ID"

func RequestID() gin.HandlerFunc {
    return func(c *gin.Context) {
        rid := c.GetHeader(HeaderRequestID)          // 网关/前端已经带了就沿用，链路能跨服务串起来
        if rid == "" {
            rid = uuid.NewString()                // 形如 2f8c1a63-9b04-4a71-8f2d-6e0c5b7a1d90
        }
        c.Set(CtxKeyRequestID, rid)                    // string 值 → 后面用 c.GetString(CtxKeyRequestID) 取
        c.Writer.Header().Set(HeaderRequestID, rid)  // 回写响应头：用户报障时让他甩这个 ID 给你
        c.Next()
    }
}

JS 对照：Express 里你大概写过 app.use((req,res,next)=>{ req.id = crypto.randomUUID(); res.set('X-Request-ID', req.id); next() })，或者直接用 pino-http 的 genReqId。区别在「怎么把 id 传给下游」：Node 靠 AsyncLocalStorage 隐式传递（同一个异步上下文自动可见），Go 没有这套运行时魔法——要么显式地把它塞进 c（gin 的 context）再由下游取，要么当参数一层层传。今天两条都用：中间件从 c 里取，handler 取出来塞进子 logger，再把子 logger 当参数交给 service。

业务层怎么用？把第 2 天的 Login 整段换成下面这版（只多了三行日志，判断逻辑一字未改）。顺带把今天唯一的构造函数变动一起改掉：AuthHandler 多一个 logger 字段，NewAuthHandler 多一个参数——这是本周最后一次改它的签名，第 5 天的测试就按四个参数传。

internal/handler/auth.go（今天动三处：struct 加字段、构造函数加参数、Login 加日志）package handler

import (
    "errors"
    "log/slog"
    "net/http"

    "github.com/gin-gonic/gin"

    "goblog/internal/middleware"   // ← 今天新增：要用 middleware.CtxKeyRequestID
    "goblog/internal/pkg/jwtutil"
    "goblog/pkg/response"
    "goblog/internal/repository"    // ← 昨天的 Me 在用 repository.ErrUserNotFound，加 logger 时别把它顺手删了（删了就报 undefined: repository）
    "goblog/internal/service"
)

type AuthHandler struct {
    svc           *service.AuthService
    accessSecret  string
    refreshSecret string
    logger        *slog.Logger      // ← 今天新增的第四个字段
}

func NewAuthHandler(svc *service.AuthService, accessSecret, refreshSecret string, logger *slog.Logger) *AuthHandler {
    return &AuthHandler{svc: svc, accessSecret: accessSecret, refreshSecret: refreshSecret, logger: logger}
}

func (h *AuthHandler) Login(c *gin.Context) {
    // ① 派生一个"自带本次请求 ID"的子 logger：这个函数里后面所有日志自动带同一个 request_id
    logger := h.logger.With("request_id", c.GetString(middleware.CtxKeyRequestID))

    // ② req / err 都是这里就地声明的（第 2 天的 Login 同款，抄过来即可）
    var req struct {
        Username string `json:"username" binding:"required"`
        Password string `json:"password" binding:"required"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数错误")
        return
    }

    user, err := h.svc.Login(req.Username, req.Password)
    if err != nil {
        if errors.Is(err, service.ErrBadCredential) {
            // ③ 三条纪律：不打 password、不打 token、不在日志里写"密码错了"这种结论（防枚举）
            logger.Warn("登录失败", "user", req.Username, "ip", c.ClientIP(), "error", err)
            response.Fail(c, http.StatusUnauthorized, response.CodeBadPassword, "用户名或密码错误")
            return
        }
        logger.Error("登录时仓储异常", "user", req.Username, "error", err)  // 真故障才用 Error
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务器开小差了")
        return
    }
    access, err := jwtutil.NewAccessToken(h.accessSecret, user.ID)
    refresh, err2 := jwtutil.NewRefreshToken(h.refreshSecret, user.ID)
    if err != nil || err2 != nil {
        logger.Error("签发 token 失败", "uid", user.ID, "error", err)
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "签发失败")
        return
    }
    logger.Info("登录成功", "uid", user.ID)                // 成功也要留一行：审计用
    response.OK(c, gin.H{"user": user, "access_token": access, "refresh_token": refresh})
}

Refresh 和 Me 的做法一样：函数第一行先 logger := h.logger.With("request_id", c.GetString(middleware.CtxKeyRequestID))，再在失败分支补一行 Warn/Error。留给你在练习 3 里补，这里不重复贴。handler 里的 logger 是局部变量（子 logger），h.logger 是共享的那个——别写 h.logger.With(...) 却不赋值给变量，那样等于白派生。

5. 统一错误码：把码表钉死

日志和响应是同一件事的两面：响应体里的 code 就是日志里可 grep 的字段。第 1 天补过三个常量，今天把整张表铺开——以后六周只用这些数字，不再新增（第 8 周权限课会复用 1003，不会另发明一个 4030）：

常量名codeHTTP含义第一次用到它的地方
CodeOK02xx成功（response.OK / Created 都发它）W2D3 起每次成功响应
CodeUserNotFound1001404资源不存在（通用；文章有专属的 2001）D1 Me · NoRoute（今天）
CodeBadPassword1002401用户名或密码错误D1 Login
CodeForbidden1003403已登录但没权限（改了别人的文章）D2「谁能改文章」埋线 · D5 第 5 节补全 Delete 与测试
CodeInvalidParam1004400参数校验没过（ShouldBindJSON 报错）D1 Register
CodeTokenInvalid1005401未认证 / token 无效或过期D2 Auth 中间件 · Refresh
CodeUsernameTaken1006409用户名已存在D1 Register
CodeArticleNotFound2001404文章不存在（含被软删的）D2 ArticleUpdate
CodeInternal5000500服务器内部错误（兜底 default 分支）D1 起每个 handler 的 default

三件禁止的事：① 别用 1000 当「通用失败」——它有 HTTP 那侧的 400/500 兜底，加个 1000 只会让人猜它到底等于谁；② 别用 5001，内部错误只有 5000；③ 别让 code 直接等于 HTTP 状态码（{"code":404} 是典型的新手写法）。HTTP 状态码管「传输层结论」，业务 code 管「哪一类错误」，两者各走各的：404 配 1001、401 配 1005、401 配 1002，都是合法组合。

还有一个今天必须挂上的兜底：路径写错时的 404。gin 默认对未匹配路径返回纯文本 404 page not found，前端拦截器拿到它会被 JSON.parse 噎住。补一句 r.NoRoute(...) 让它也吐统一 Body（第 8 节的 main.go 里已经带上）：

cmd/server/main.go（紧挨着 /health 放）    // 所有没匹配上的路径都走这里：404 + 1001，绝不返回裸文本
    r.NoRoute(func(c *gin.Context) {
        response.Fail(c, http.StatusNotFound, response.CodeUserNotFound, "资源不存在")
    })

输出对比：curl -i localhost:8080/api/v1/eerken 改前是 404 page not found（Content-Type: text/plain），改后是 {"code":1001,"message":"资源不存在","data":null}。

JS 对照：Express 里你多半写过 res.status(404).json({ error: 'not found' }) 加一个 err.code 字符串（'USER_EXISTS'）。Go 这边没有异常对象可挂，所以把「错误类别」做成数字常量 + 集中的 const 块，好处是前端只要认 code !== 0 一个分支就能覆盖全部失败路径——第 6 周 http.js 的拦截器就写这一句。

6. 优雅关闭：Shutdown 全流程

粗暴关闭（Ctrl+C 直接退）的问题：正在处理到一半的请求被掐断，用户拿到连接重置。优雅关闭 = 停止接新活 → 等在途干完（有上限）→ 退出。

本节会用到三样你还没正式学过的语法：go func(){…}()（goroutine）、<-ctx.Done()（channel 接收）、context.Context。这三个词你在第 1、2 周只见过面孔（「net/http 每个请求开一个 goroutine」），系统课在下一周——第 5 周并发周，goroutine / channel / context 三讲连发。今天的要求只有一条：照抄，不要自创、不要改顺序。今天的讲义只讲「这段代码在关闭流程里扮演什么角色」，够你把服务体面地停下来就行。defer 不在照抄名单里——它第 1 周 D3 就正式讲过（函数返回前执行，回收资源），今天还是那个用法。

cmd/server/main.go（main 函数后半段，替换昨天的 r.Run(...)）    srv := &http.Server{
        Addr:    ":" + cfg.Port,
        Handler: r,                       // r 是 *gin.Engine，它实现了 http.Handler
        ReadTimeout:  5 * time.Second,   // 生产服务务必设超时，防慢连接拖垮
        WriteTimeout: 10 * time.Second,
    }

    // 1. 造一个"收到 SIGINT/SIGTERM 就自动 cancel"的 context  ← 照抄（context 第 5 周正式讲）
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()                            // defer 是第 1 周 D3 的老朋友：main 返回前执行，把"监听信号"这件事注销掉

    // 2. ListenAndServe 是阻塞的，放到 goroutine 里跑  ← 照抄：go 开头 = 另开一条执行线，主流程继续往下走
    go func() {
        logger.Info("服务启动", "addr", srv.Addr)
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            logger.Error("监听失败", "error", err)
            os.Exit(1)
        }
    }()

    // 3. 主 goroutine 阻塞在这：等信号  ← 照抄：<- 是"从 channel 里取一个值"，取不到就一直等
    <-ctx.Done()
    logger.Info("收到退出信号，开始优雅关闭（最多等 10 秒）")

    // 4. Shutdown：关闭监听、等在途请求处理完；给了 10 秒上限，到点强退  ← 照抄
    shutCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()                        // ← 照抄：不 cancel 就漏一个计时器，第 5 周会专门数落它
    if err := srv.Shutdown(shutCtx); err != nil {
        logger.Error("优雅关闭超时，强制退出", "error", err)
    }
    logger.Info("bye 👋 存量请求已处理完毕")

四条 JS 对照，串起来就是整段流程：
① go func(){ … }() ≈ 你熟悉的 server.listen(port, cb)——Node 的事件循环天然异步，所以不需要显式 go；Go 的 main 一跑完就退进程，必须自己找一条「副线」把监听挂住。
② <-ctx.Done() ≈ await new Promise(r => process.once('SIGTERM', r))：都是「挂在这儿直到事件发生」，Go 用 channel 接收实现等待。
③ context.WithTimeout ≈ AbortSignal.timeout(10_000)：一个「到点自己取消」的传播式信号，Go 里它还得当参数一路传下去（srv.Shutdown(shutCtx)）。
④ defer stop() ≈ try/finally 里的 process.removeListener(…)，只是 Go 写在申请资源的下一行，不会忘在 finally。

零件职责今天需要掌握到什么程度
signal.NotifyContextSIGTERM/SIGINT 一到就 cancel 掉 ctx——把信号翻译成 context 语言照抄，认得出它的两个返回值 ctx / stop
<-ctx.Done()主函数挂起等待，否则 main 立刻跑完程序就退了照抄，知道「这行卡住 = 好事」
srv.Shutdown(ctx)关监听 + 等空闲；ctx 超时则不再等。K8s/Docker 停容器默认就是发 SIGTERM会调、会给超时 ctx
http.ErrServerClosedShutdown 会让 ListenAndServe 返回这个「正常退休」错误，必须排除掉别当事故报理解为什么要 !errors.Is(...)

唯一需要真懂的一点：为什么 ListenAndServe 必须塞进 go func——它是阻塞调用，如果不另开一条线，代码就永远停在那一行，下面的 <-ctx.Done() 根本没机会执行，于是 kill -TERM 完全没反应（这是本页坑表的常客）。errors.Is(err, http.ErrServerClosed) 用的还是第 1 天那张「哨兵错误 + errors.Is」的配方，这里只是把它反过来用：正常退休不算错。

别忘了 main.go 顶部 import：标准库要一次凑齐 "context"、"errors"、"net/http"、"os"、"os/signal"、"syscall"、"time"，再加 "goblog/internal/pkg/applog"。少一个就是 undefined: signal 这类报错——Go 的报错永远指向「这个标识符我没见过」，看它属于哪个包就补哪个 import。第 8 节给的是完整文件，直接对照它逐行补齐。

7. Shutdown 时序图解与两个延伸点

时序t0   用户请求A ──────────▶ handler 处理中（5 秒 sleep）
t0+1 kill -TERM ─▶ ctx cancel ─▶ main 醒来 ─▶ srv.Shutdown()
                       │
                       ├─ 立即：关闭监听端口，新请求 TCP 层不再受理
                       └─ 等待：请求A 继续跑… t0+6 返回 200 ─▶ Shutdown 返回 ─▶ main 打印 bye 退出
（若请求A 要跑 30 秒：t0+11 到达 WithTimeout 上限，Shutdown 带 error 返回，进程照样退出——有界等待是底线）
延伸点说明
srv.Close() vs srv.Shutdown(ctx)Close 立即掐断全部连接，等于粗暴版；Shutdown 才优雅。生产只应出现 Shutdown
清理资源的挂载位Shutdown 返回后、进程退出前，是关数据库连接池/刷日志缓冲的位置：sqlDB, _ := db.DB(); sqlDB.Close()
Docker/K8s 的对应关系docker stop 默认发 SIGTERM、10 秒后补 SIGKILL；你的 10 秒 Shutdown 预算要与它对齐，否则永远是被 -9 带走

8. 今日终态：cmd/server/main.go 完整文件

前面三节都是片段，第 2 节、第 5 节、第 6 节都说过「完整文件在这一节」——现在兑一次。整文件替换你自己的 main.go，逐行对照补齐；最先对照的是 import 块：Go 里少一个是 undefined: signal，多一个是 imported and not used，两边都编译不过，这一段没有「先跑起来再说」的空间。

cmd/server/main.go（第 4 天终态，整文件替换）package main

import (
    "context"
    "errors"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"

    "github.com/gin-gonic/gin"

    "goblog/internal/config"
    "goblog/internal/handler"
    "goblog/internal/middleware"
    "goblog/internal/model"
    "goblog/internal/pkg/applog"
    "goblog/pkg/response"
    "goblog/internal/repository"
    "goblog/internal/service"
)

func main() {
    cfg, err := config.Load()
    if err != nil {
        log.Fatal("配置加载失败: " + err.Error()) // logger 还没建，这一行只能用标准库 log
    }

    logger := applog.New(cfg.GinMode)        // *slog.Logger，全项目只建这一个（第 2 节）
    logger.Info("配置就绪", "port", cfg.Port, "gin_mode", cfg.GinMode)

    db, err := repository.New(cfg.DSN)         // 第 3 周的封装：gorm.Open + 连接池 + Ping
    if err != nil {
        logger.Error("数据库连接失败", "error", err)
        os.Exit(1)                       // 有 logger 之后就不再 log.Fatal：一套输出比两套干净
    }
    if err := db.AutoMigrate(&model.User{}, &model.Tag{}, &model.Article{}); err != nil {
        logger.Error("迁移失败", "error", err)
        os.Exit(1)
    }

    // 装配顺序：仓储 → service → handler。密钥和 logger 都从构造函数递进去，谁也读不到全局
    userRepo := repository.NewGormUserRepo(db)
    artRepo  := repository.NewGormArticleRepo(db)
    userSvc  := service.NewUserService(userRepo, artRepo)
    artSvc   := service.NewArticleService(artRepo, userRepo)
    authSvc  := service.NewAuthService(userRepo, cfg.JWTSecret, cfg.JWTRefreshSecret)

    h     := handler.New(userSvc, artSvc)
    authH := handler.NewAuthHandler(authSvc, cfg.JWTSecret, cfg.JWTRefreshSecret, logger) // ← 今天的第四个参数

    gin.SetMode(cfg.GinMode)
    r := gin.New()
    // 顺序就是正确性：RequestID 第一个挂，AccessLog 才打得出 ID；
    // gin.Recovery() 放最后（最内层），它兜住 panic 写出 500 之后，AccessLog 的回程还能把这一行记下来
    r.Use(middleware.RequestID(), middleware.AccessLog(logger), gin.Recovery())

    r.GET("/health", func(c *gin.Context) {
        response.OK(c, gin.H{"status": "ok"})  // 统一 Body：{"code":0,"message":"ok","data":{"status":"ok"}}
    })

    // 第 5 节那条兜底：路径写错也吐统一 Body，绝不返回裸文本 404 page not found
    r.NoRoute(func(c *gin.Context) {
        response.Fail(c, http.StatusNotFound, response.CodeUserNotFound, "资源不存在")
    })

    v1 := r.Group("/api/v1")
    {
        // 公开组：注册/登录/换发不需要登录态，文章读取游客也要能看
        pub := v1.Group("/auth")
        pub.POST("/register", authH.Register)
        pub.POST("/login", authH.Login)
        pub.POST("/refresh", authH.Refresh)
        v1.GET("/articles", h.ArticleList)
        v1.GET("/articles/:id", h.ArticleDetail)

        // 保护组：中间件在 Group 这一行就挂好，下面注册的路由才会过它
        priv := v1.Group("", middleware.Auth(cfg.JWTSecret))
        priv.GET("/users/me", authH.Me)
        priv.POST("/articles", h.ArticleCreate)
        priv.PUT("/articles/:id", h.ArticleUpdate)
        priv.DELETE("/articles/:id", h.ArticleDelete)
    }

    srv := &http.Server{
        Addr:         ":" + cfg.Port,
        Handler:      r,                  // r 是 *gin.Engine，它实现了 http.Handler
        ReadTimeout:  5 * time.Second, // 生产服务务必设超时，防慢连接拖垮
        WriteTimeout: 10 * time.Second,
    }

    // 下面这段就是第 6 节的四步流程（造 ctx → go 起服务 → 等信号 → Shutdown），一字未改。
    // context / channel / goroutine 三样第 5 周正式讲，今天照抄
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    go func() {
        logger.Info("服务启动", "addr", srv.Addr)
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            logger.Error("监听失败", "error", err)
            os.Exit(1)
        }
    }()

    <-ctx.Done()
    logger.Info("收到退出信号，开始优雅关闭（最多等 10 秒）")

    shutCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutCtx); err != nil {
        logger.Error("优雅关闭超时，强制退出", "error", err)
    }
    logger.Info("bye 👋 存量请求已处理完毕")
}

对照片刻自检三件事：① r.Use(...) 在所有路由注册之前，否则 RequestID/AccessLog 对已注册的路由不生效；② 保护组的中间件挂在 v1.Group("", middleware.Auth(cfg.JWTSecret)) 那一行，不是挂在某条路由上；③ 全文没有一处 r.Run(...)——它起的是 gin 自己的服务器，绕开 http.Server，Shutdown 就成了空话。

第 7 节提到的「关数据库连接池」在这份文件里故意没写：本周 repository.New 没有把 *sql.DB 交出来，main 里拿不到它。等第 7 周容器化真需要优雅退出连接池时，再给 repository 加一个 Close()，位置就插在 srv.Shutdown 成功返回之后、最后那行 bye 之前。

练习 1：装上三件套并观察（60 分钟，主线）

接入 RequestID → AccessLog → Auth 中间件链（顺序有讲究），main 换成 http.Server + Shutdown 版本。验证：curl -i localhost:8080/api/v1/articles 响应头有 X-Request-ID，stdout 出现对应 JSON 日志行。做完再验证一次失败路径：不带 token 的请求（curl -i localhost:8080/api/v1/users/me），日志里应出现 "status":401 且 request_id 与响应头一致——失败请求同样要被追踪。

参考答案（要点）

r.Use(middleware.RequestID(), middleware.AccessLog(logger)) 放在路由注册前；curl -i 看到 X-Request-ID: 5b8a...(uuid)，同时日志里 {"msg":"access","method":"GET","path":"/api/v1/articles","status":200,"latency_ms":1,"ip":"127.0.0.1","request_id":"5b8a..."} 两边 ID 一致。

练习 2：kill -TERM 观察优雅关闭（25 分钟）

常见坑（新手 100% 会踩）

坑现象正确姿势
中间件里先 return 后打日志access 日志永远不输出，或状态码是 0记录型中间件先 c.Next()，放行后再取 Status()
RequestID 顺序放 Auth 后面401 的日志没有 request_id，白名单外的请求查不到RequestID 永远第一个 Use
忘排 http.ErrServerClosed每次正常关闭都打一条「监听失败」Error 还 os.Exit(1)!errors.Is(err, http.ErrServerClosed) 才算真故障
ListenAndServe 没放 goroutine主 goroutine 被阻塞，下面的信号等待永远执行不到，kill 无反应服务跑 go func，main 等 ctx.Done()
Shutdown 不给超时 ctx有个长轮询请求挂着，进程永远退不掉，部署卡到被 kill -9必须 context.WithTimeout 包一层上限
日志里打敏感字段access 日志把 password 明文、完整 token 打进 stdout，日志文件成了第二数据库只打 path 不打 body；需要认证上下文时只打 request_id/userID
用 print 混用两套输出一半 fmt.Println 一半 slog，级别格式互不相干，检索时漏一半服务启动后全项目只允许 logger，fmt 仅限 CLI 一次性脚本
slog 键值对写漏一个logger.Info("x", "user") 少配对值，输出里出现 "!BADKEY"键值必须成对；条件字段用 slog.Any/slog.Group 动态拼装
在循环里新建 logger/Handler每个请求 new 一个 JSONHandler，锁与缓冲区反复重建，性能白流main 里建一次 logger，经构造函数注入到 handler/service 全链路共享
