配置管理与 .env

你的 main.go 里现在躺着数据库 DSN 和 JWT secret 的字面量——换环境要改代码、secret 跟着 Git 一起进了远程仓库。今天把它们全部收进 .env + config 包，这是「代码与配置分离」的第一课，也是第 7 周 Docker 部署的前提（容器不改代码，只改环境变量）。

课前须知：给 JS 开发者的两句话

1. 你早就会一半了。Node 的 process.env.DB_HOST + dotenv 包，Go 对应 os.Getenv("DB_HOST") + godotenv 包，概念一一对应，只是 Go 没有全局 process 对象。

2. Go 没有「导入即生效」的全局 config 单例传统。社区主流做法是：启动时加载一次成 Config 结构体，像普通参数一样 传 给需要它的函数——依赖关系全部显式，测试时随手替换假配置。

知识讲义

1. 12-factor 一句话与三个层级

12-factor 应用关于配置的原话浓缩成一句：「配置与代码严格分离，存放在环境（environment）里」——同一份编译产物，改环境不改代码就能跑在开发机、测试服、生产容器里。

层级例子进不进 Git
写死在代码里的常量AccessTTL=15min 这类几乎不变的业务常量✅ 进
环境变量 / .envPORT、DB DSN、JWT_SECRET、第三方 Key❌ .env 不进，.env.example 进
配置中心 / 密钥管理服务Consul、Vault、云厂商 KMS（生产环境）知道有这层即可，本课程不涉及

判断标准很简单：会随「部署到哪儿」而变化的值都是配置。数据库地址是配置，「密码最少 8 位」是代码逻辑。别把两者混在一个文件里。

2. godotenv：把 .env 装进环境变量

shell$ go get github.com/joho/godotenv

项目根目录建 .env（注意：仅本地开发用，生产容器由编排直接注入环境变量，不需要这个文件）：

.env# 服务
PORT=8080
GIN_MODE=debug

# 数据库（第 3 周 docker-compose 里的那套账密）
DB_USER=root
DB_PASS=devpass123
DB_HOST=127.0.0.1
DB_NAME=blog

# JWT：openssl rand -hex 32 生成，绝不提交
JWT_SECRET=9f2c74ab1e...此处省略52位随机字符...d3a80fc
internal/config/config.gopackage config

import (
    "fmt"
    "os"

    "github.com/joho/godotenv"
)

// Load 一次性读入全部配置：.env 文件只是"开发期便利"，
// 已存在的系统环境变量优先级更高时可用 godotenv.Overload 反转，默认 Load 不覆盖。
func Load() (Config, error) {
    // 文件不存在不报错：生产环境本来就靠真实环境变量注入
    _ = godotenv.Load()

    var c Config
    c.Port = getEnv("PORT", "8080")          // 可选项：给默认值
    c.GinMode = getEnv("GIN_MODE", "debug")
    c.JWTSecret = requireEnv("JWT_SECRET")    // 必填项：没有就启动失败
    if c.JWTSecret == "" {
        return c, fmt.Errorf("缺少环境变量 JWT_SECRET")
    }
    dbPass := requireEnv("DB_PASS")
    if dbPass == "" {
        return c, fmt.Errorf("缺少环境变量 DB_PASS")
    }
    c.DSN = fmt.Sprintf("%s:%s@tcp(%s:3306)/%s?charset=utf8mb4&parseTime=True&loc=Local",
        getEnv("DB_USER", "root"), dbPass, getEnv("DB_HOST", "127.0.0.1"), getEnv("DB_NAME", "blog"))
    return c, nil
}

func getEnv(key, fallback string) string {
    if v := os.Getenv(key); v != "" { return v }
    return fallback
}

func requireEnv(key string) string { return os.Getenv(key) }

「可选给默认值、必填直接报错」是配置加载的黄金分工：默认值让开箱即用，fail-fast（启动即挂，而不是运行到签发 token 时才 panic）让缺配置在第一秒暴露。

3. Config 结构体：一次加载，传参传递

internal/config/config.gotype Config struct {
    Port      string // ":8080" 监听用
    GinMode   string // debug / release
    DSN       string // MySQL 连接串
    JWTSecret string // HS256 密钥
}
cmd/server/main.gofunc main() {
    cfg, err := config.Load()
    if err != nil {
        log.Fatal("配置加载失败: " + err.Error()) // fail-fast
    }

    db, err := gorm.Open(mysql.Open(cfg.DSN), nil)
    if err != nil { log.Fatal("数据库连接失败: " + err.Error()) }
    _ = db.AutoMigrate(&model.User{}, &model.Article{})

    gin.SetMode(cfg.GinMode)
    r := gin.Default()

    authSvc := service.NewAuthService(db, cfg.JWTSecret)  // 依赖靠构造函数传进去
    authH := handler.NewAuthHandler(authSvc, cfg.JWTSecret)

    r.POST("/auth/register", authH.Register)
    r.POST("/auth/login", authH.Login)
    r.POST("/auth/refresh", authH.Refresh)
    r.Use(middleware.Auth(cfg.JWTSecret))               // 中间件也从 cfg 拿，不读全局
    // ... 受保护路由 ...

    r.Run(":" + cfg.Port)
}

反对的反模式：var JWTSecret string 放在 config 包里当全局变量，任何函数直接引用。它编译最方便、调试最痛苦——测试想换 secret 只能改全局，并发跑测试就互相踩。传参虽要多写几行签名，换来的是依赖清晰 + 天然可测（明天写测试马上受益）。

4. .env 进 .gitignore + .env.example 模式

.gitignore# 本地环境配置，绝不入库
.env
*.local

仓库里提交一份只有键没有值（或值是占位符）的模板，队友 clone 后照着复制：

.env.examplePORT=8080
GIN_MODE=debug
DB_USER=root
DB_PASS=<你的本地密码>
DB_HOST=127.0.0.1
DB_NAME=blog
JWT_SECRET=<openssl rand -hex 32>
shell$ cp .env.example .env # 新成员入场第一步，README 里写清楚

如果 .env 已经提交过：git rm --cached .env 移除跟踪并补 .gitignore，然后立刻轮换里面的所有密码和 JWT secret——已进历史提交的密钥视为永久泄露，光删文件不够（历史里还在），要重写历史或换密钥。

5. viper：什么时候才值得升级

github.com/spf13/viper 支持 yaml/toml 配置文件、命令行参数、远程配置、热加载（WatchConfig）。但代价是魔法多、初始化复杂。经验法则：

场景选择
十几个平铺的字符串配置，12-factor 风格部署godotenv + os.Getenv（今天这套）就够了
配置项几十上百、有嵌套结构（server.port、log.level...）、需要 yaml 多环境文件、运行期热更新上 viper：SetConfigFile + Unmarshal(&cfg) 一次映射进 Config 结构体，外层接口不变
viper 长什么样（了解即可，暂不用装）var cfg Config
v := viper.New()
v.SetConfigName("config")      // config.yaml / config.toml 多环境
v.AddConfigPath("./configs")
v.AutomaticEnv()               // yaml 缺的键仍可被环境变量覆盖：与 12-factor 合流
v.ReadInConfig()
v.Unmarshal(&cfg)              // 一次性映射进结构体——出口仍是 Config，与今天同构

正因为今天的 Config 结构体是「唯一出口」，以后从 godotenv 换到 viper 只需要重写 Load() 内部，其他代码一行不动——这就是先建模后选库的好处。

7. 值的优先级：真实环境变量 > .env 文件

godotenv.Load() 的语义是「不覆盖已存在的环境变量」（想反转用 Overload）。于是天然形成三级瀑布：

优先级  高 ──  shell/容器注入的环境变量   PORT=9999 go run ./cmd/server   # 临时试验、部署平台
       └──  .env 文件里的值            PORT=8080                        # 本地开发默认
  低 ──  代码里的 fallback 默认值     getEnv("PORT", "8080")           # 开箱兜底

这也是练习 1 里「PORT=9999 前缀启动能覆盖 .env」的原理——不需要为测试临时改 .env 文件。

今日练习

练习 1：把端口/DSN/JWTSecret 收进 config 包（60 分钟，主线）

重构项目：main.go 里不允许再出现任何字面量的地址、密码、secret；全部走 cfg。完成后连续验证两次：PORT=9999 go run ./cmd/server 应监听 9999；删掉 .env 里 JWT_SECRET 行应启动即报「配置加载失败」。

参考答案（要点）

internal/config 提供 Config + Load()；main 第一行调用并 fail-fast；service.NewAuthService(db, cfg.JWTSecret) 之类通过构造函数注入；DSN 在 Load 内用 Sprintf 拼装（占位符 %s:%s@tcp(%s:3306)/%s?charset=utf8mb4&parseTime=True&loc=Local）。环境变量临时覆盖 .env 之所以生效，是因为 godotenv.Load 不覆盖已存在的变量。

练习 2：密钥轮换演练（20 分钟）

openssl rand -hex 32 生成新 secret 替换 .env，重启服务，用旧 secret 签发的 access token 请求受保护接口。

参考答案

返回 401+1005——签名校验用的是新 secret，旧 token 全部作废。这就是「泄露即轮换」的底气：换密钥的成本只是让用户重新登录一次。

练习 3：补齐 .gitignore 与 .env.example（15 分钟）

执行 git status 确认 .env 未被跟踪；提交 .env.example 与 .gitignore；README 加「快速开始：cp .env.example .env → 填值 → go run」三行说明。

练习 4：给 docker-compose 的 MySQL 也换密码来源（20 分钟）

把 compose 文件里 MySQL 的 MYSQL_ROOT_PASSWORD 也改成从 shell 环境变量读（${DB_PASS}），与 .env 保持同一份密码。

参考答案 
docker-compose.ymlservices:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASS}   # compose 自己也会读项目根目录的 .env
      MYSQL_DATABASE: ${DB_NAME:-blog}

Docker Compose 原生读取同目录 .env，:- 语法是 compose 层的默认值。改完 docker compose up -d 重建容器验证 Go 服务仍可连库。

做完四条练习后自问：明天我要给日志级别也做成可配置的（LOG_LEVEL），要动的文件是不是只有 config.go 和 main？如果是，说明收口成功——配置系统的健康标准就是「加一个配置项只改一处」。

常见坑（新手 100% 会踩）

坑现象正确姿势
.env 提交进了 GitGitHub 推上 secret，扫描机器人几分钟内就把你的 key 用掉第一时间 .gitignore + 轮换所有泄露值，README 用 .env.example
godotenv 路径不对从别的目录 go run 时 Load 找不到 .env，全走默认值，排查半天约定 .env 放项目根并从根目录启动；或 Load 传绝对路径
全局变量满天飞config 包 var Secret string 人人直读，测试互相污染Config 结构体 + 构造函数传参（今天的模式）
secret 用弱值JWT_SECRET=123456，HS256 可被字典穷举伪造≥32 字节随机串，openssl rand -hex 32 生成
必填项没做 fail-fast启动正常，第一个登录请求 panic「secret is invalid key or message」requireEnv + 启动即返回 error，把事故消灭在部署阶段
.env 值带引号/空格踩解析DB_PASS="p 1" 或行尾多了空格，连库时密码怎么都不对godotenv 按字面取值：值不加多余引号，编辑器关掉「行尾保留空白」，出问题时先 print 配置长度
