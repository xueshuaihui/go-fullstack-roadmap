配置管理与 .env

你的 main.go 里现在躺着数据库 DSN 和 JWT secret 的字面量——换环境要改代码、secret 跟着 Git 一起进了远程仓库。今天把它们全部收进 .env + config 包，这是「代码与配置分离」的第一课，也是第 7 周 Docker 部署的前提（容器不改代码，只改环境变量）。

课前须知：给 JS 开发者的两句话

1. 你早就会一半了。Node 的 process.env.DB_HOST + dotenv 包，Go 对应 os.Getenv("DB_HOST") + godotenv 包，概念一一对应，只是 Go 没有全局 process 对象。

2. Go 没有「导入即生效」的全局 config 单例传统。社区主流做法是：启动时加载一次成 Config 结构体，像普通参数一样 传 给需要它的函数——依赖关系全部显式，测试时随手替换假配置。

知识讲义

1. 12-factor 一句话与三个层级

12-factor 应用关于配置的原话浓缩成一句：「配置与代码严格分离，存放在环境（environment）里」——同一份编译产物，改环境不改代码就能跑在开发机、测试服、生产容器里。

层级例子进不进 Git
写死在代码里的常量AccessTTL=15min 这类几乎不变的业务常量✅ 进
环境变量 / .envPORT、DB_HOST/DB_PORT/DB_USER/DB_PASS/DB_NAME、JWT_SECRET、JWT_REFRESH_SECRET、第三方 Key❌ .env 不进，.env.example 进
配置中心 / 密钥管理服务Consul、Vault、云厂商 KMS（生产环境）知道有这层即可，本课程不涉及

判断标准很简单：会随「部署到哪儿」而变化的值都是配置。数据库地址是配置，「密码最少 8 位」是代码逻辑。别把两者混在一个文件里。

项目根目录建 .env（注意：仅本地开发用，生产容器由编排直接注入环境变量，不需要这个文件）。九个键就是本项目全站统一的键名清单，第 7 周的 compose、第 8 周的上传目录都往这个清单上加：

# 数据库：第 3 周 goblog-mysql 容器那套账密
DB_HOST=localhost
DB_PORT=3306
DB_USER=goblog
DB_PASS=goblog123
DB_NAME=goblog

# JWT：两把不同的密钥，各用 openssl rand -hex 32 生成，绝不提交
JWT_SECRET=9f2c74ab1e...此处省略52位随机字符...d3a80fc
JWT_REFRESH_SECRET=41b8d05ce7...此处省略52位随机字符...9ac3f6

两把密钥必须真的不一样。用同一把，等于「拿 refresh 串去 NewAccessToken 也能验通过」——第 2 天讲的 typ 校验是第一道闸，密钥分离是第二道。生成时老老实实跑两遍 openssl rand -hex 32，别复制粘贴同一个值。（goblog123 是库的账号密码，和 JWT 密钥是两套凭证，轮换互不影响。）

对照 Node：这就是 .env + require('dotenv').config()。唯一要记住的差异是 Go 里 os.Getenv 拿到的一直是 string，没有 process.env 那个对象；数字要自己 strconv.Atoi，本项目端口直接当字符串拼 ":"+cfg.Port，省一次转换。

3. Config 结构体 + Load()：整个 config.go

internal/config/config.gopackage config

import (
    "fmt"
    "os"
    "strings"

    "github.com/joho/godotenv"
)

// Config 是本项目的配置唯一出口：九个键进来，最后只对外暴露五个值
// （DSN 由 DB_* 拼出来，调用方不需要知道有几段）
type Config struct {
    Port               string // "8080"，监听时拼成 ":8080"
    GinMode            string // debug / release
    DSN                string // MySQL 连接串，由 DB_* 拼装
    JWTSecret          string // access token 的 HS256 密钥（JWT_SECRET）
    JWTRefreshSecret   string // refresh token 的 HS256 密钥（JWT_REFRESH_SECRET）
}

// Load 一次性读入全部配置。
// .env 只是"开发期便利"：godotenv.Load 不覆盖已存在的环境变量，
// 所以真实环境（shell / 容器）注入的值优先级更高，想反转用 godotenv.Overload。
func Load() (Config, error) {
    var c Config

    // 文件不存在不报错：生产环境本来就靠真实环境变量注入
    _ = godotenv.Load()

    // 必填项：一次把缺的键全列出来，而不是一个一个试
    if miss := missingEnv("DB_USER", "DB_PASS", "DB_NAME", "JWT_SECRET", "JWT_REFRESH_SECRET"); len(miss) > 0 {
        return c, fmt.Errorf("缺少环境变量：%s", strings.Join(miss, "、"))
    }

    // 可选项：给默认值
    c.Port = getEnv("PORT", "8080")
    c.GinMode = getEnv("GIN_MODE", "debug")
    c.JWTSecret = os.Getenv("JWT_SECRET")
    c.JWTRefreshSecret = os.Getenv("JWT_REFRESH_SECRET")

    // DSN：端口一定用 DB_PORT，别写死 3306
    // 第 7 周把容器端口映射改成 3307 时，写死的 3306 会连到另一台 MySQL 上，报的错还很难看懂
    host := getEnv("DB_HOST", "localhost")
    port := getEnv("DB_PORT", "3306")
    c.DSN = fmt.Sprintf("%s:%s@tcp(%s:%s)/%s?charset=utf8mb4&parseTime=True&loc=Local",
        os.Getenv("DB_USER"), os.Getenv("DB_PASS"), host, port, os.Getenv("DB_NAME"))

    return c, nil
}

// getEnv 可选配置：没设就用默认值
func getEnv(key, fallback string) string {
    if v := os.Getenv(key); v != "" { return v }
    return fallback
}

// missingEnv 变长参数（keys ...string）：把没设置到的必填键名收集起来。
// JS 对照：const missing = (...keys) => keys.filter(k => !process.env[k])
func missingEnv(keys ...string) []string {
    var miss []string
    for _, k := range keys {
        if os.Getenv(k) == "" {
            miss = append(miss, k)
        }
    }
    return miss
}

「可选给默认值、必填一次报全」是配置加载的黄金分工：默认值让开箱即用，fail-fast（启动即挂，而不是运行到签发 token 时才 panic）让缺配置在第一秒暴露；missingEnv 把五个键一次列全，比「改一个报一个」省五轮重启。顺带一个 Go 细节：var miss []string 是 nil 切片，append 对 nil 切片照样工作（第一次 append 就地分配），所以不用写成 miss := []string{}。

Config 里只有 Port/GinMode/DSN/JWTSecret/JWTRefreshSecret 五个字段，而 .env 有九个键——DB_HOST/DB_PORT/DB_USER/DB_PASS/DB_NAME 五个键在 Load() 内部就被拼成 DSN 消化掉了。这是有意的收口：调用方不需要知道 DSN 有几段，第 7 周换 Postgres 也只改 config.go。

4. main.go：装配一次做完，中间件排在路由前面

下面是今天完整可编译的 cmd/server/main.go（第 2 天那段「这一步的样子」正式落地）。三个要求：字面量清零、service 收到的永远是仓储接口而不是 *gorm.DB、鉴权中间件在注册受保护路由之前挂好。

cmd/server/main.gopackage main

import (
    "log"

    "github.com/gin-gonic/gin"

    "goblog/internal/config"
    "goblog/internal/handler"
    "goblog/internal/middleware"
    "goblog/internal/model"
    "goblog/pkg/response"
    "goblog/internal/repository"
    "goblog/internal/service"
)

func main() {
    cfg, err := config.Load()
    if err != nil {
        log.Fatal("配置加载失败: " + err.Error())  // fail-fast：带着坏配置启动更糟
    }

    db, err := repository.New(cfg.DSN)              // 第 3 周的封装：gorm.Open + 连接池 + Ping
    if err != nil {
        log.Fatal("数据库连接失败: " + err.Error())
    }
    if err := db.AutoMigrate(&model.User{}, &model.Tag{}, &model.Article{}); err != nil {
        log.Fatal("迁移失败: " + err.Error())
    }

    // 装配顺序：仓储 → service → handler。两把密钥从 cfg 递进去，谁也读不到全局
    userRepo := repository.NewGormUserRepo(db)
    artRepo  := repository.NewGormArticleRepo(db)
    userSvc  := service.NewUserService(userRepo, artRepo)
    artSvc   := service.NewArticleService(artRepo, userRepo)
    authSvc  := service.NewAuthService(userRepo, cfg.JWTSecret, cfg.JWTRefreshSecret)

    h     := handler.New(userSvc, artSvc)
    authH := handler.NewAuthHandler(authSvc, cfg.JWTSecret, cfg.JWTRefreshSecret)

    gin.SetMode(cfg.GinMode)                       // release 模式会关掉调试日志，第 7 周部署时改这一个值
    r := gin.New()
    r.Use(gin.Logger(), gin.Recovery())

    r.GET("/health", func(c *gin.Context) {
        response.OK(c, gin.H{"status": "ok"})  // 统一 Body：{"code":0,"message":"ok","data":{"status":"ok"}}
    })

    v1 := r.Group("/api/v1")
    {
        // 公开组：注册/登录/换发不需要登录态，文章读取游客也要能看
        pub := v1.Group("/auth")
        pub.POST("/register", authH.Register)
        pub.POST("/login", authH.Login)
        pub.POST("/refresh", authH.Refresh)
        v1.GET("/articles", h.ArticleList)
        v1.GET("/articles/:id", h.ArticleDetail)

        // 保护组：中间件在 Group 这一行就挂好，下面注册的路由才会过它
        priv := v1.Group("", middleware.Auth(cfg.JWTSecret))
        priv.GET("/users/me", authH.Me)
        priv.POST("/articles", h.ArticleCreate)
        priv.PUT("/articles/:id", h.ArticleUpdate)
        priv.DELETE("/articles/:id", h.ArticleDelete)
    }

    if err := r.Run(":" + cfg.Port); err != nil {
        log.Fatal(err)
    }
}

为什么不是 r.Use(middleware.Auth(cfg.JWTSecret))？引擎级 Use 作用于「在它之后注册的所有路由」——写在装配前面，等于把 /health、/api/v1/auth/register、/login 一起拦了（登录接口要求先登录，是个经典死锁）；写在注册后面，前面那些路由又一条都不过鉴权。本周终态的写法就是上面的分组挂法：公开组不挂，保护组在 Group("", Auth(...)) 里一次挂到位。真要给某个路由单独特判，才在 handler 里自己判断（第 8 周管理员接口会用到）。

NewAuthHandler 今天是三个参数（service + 两把密钥）。明天 D4 会给它再加一个 *slog.Logger，变成四个参数——这是本周最后一次改构造函数签名，第 5 天的测试就按四参数版本传。

反对的反模式：var JWTSecret string 放在 config 包里当全局变量，任何函数直接引用。它编译最方便、调试最痛苦——测试想换 secret 只能改全局，并发跑测试就互相踩。对照 Node：很多人把 config.js export default { jwt: process.env.JWT_SECRET } 到处 import，测一个函数要连带 mock 整个模块；Go 的 cfg 当参数传，测试里 config.Config{JWTSecret: "test-key"} 直接构造一个假配置就完了，不用 mock。

6. viper：什么时候才值得升级

github.com/spf13/viper 支持 yaml/toml 配置文件、命令行参数、远程配置、热加载（WatchConfig）。但代价是魔法多、初始化复杂。经验法则：

场景选择
十几个平铺的字符串配置，12-factor 风格部署godotenv + os.Getenv（今天这套）就够了
配置项几十上百、有嵌套结构（server.port、log.level...）、需要 yaml 多环境文件、运行期热更新上 viper：SetConfigFile + Unmarshal(&cfg) 一次映射进 Config 结构体，外层接口不变
viper 长什么样（了解即可，暂不用装）var cfg Config
v := viper.New()
v.SetConfigName("config")      // config.yaml / config.toml 多环境
v.AddConfigPath("./configs")
v.AutomaticEnv()               // yaml 缺的键仍可被环境变量覆盖：与 12-factor 合流
v.ReadInConfig()
v.Unmarshal(&cfg)              // 一次性映射进结构体——出口仍是 Config，与今天同构

正因为今天的 Config 结构体是「唯一出口」，以后从 godotenv 换到 viper 只需要重写 Load() 内部，其他代码一行不动——这就是先建模后选库的好处。

8. 值的优先级：真实环境变量 > .env 文件

godotenv.Load() 的语义是「不覆盖已存在的环境变量」（想反转用 Overload）。于是天然形成三级瀑布：

优先级  高 ──  shell/容器注入的环境变量   PORT=9999 go run ./cmd/server   # 临时试验、部署平台
       └──  .env 文件里的值            PORT=8080                        # 本地开发默认
  低 ──  代码里的 fallback 默认值     getEnv("PORT", "8080")           # 开箱兜底

这也是练习 1 里「PORT=9999 前缀启动能覆盖 .env」的原理——不需要为测试临时改 .env 文件。

今日练习

练习 1：把端口/DSN/两把 JWT 密钥收进 config 包（60 分钟，主线）

重构项目：main.go 里不允许再出现任何字面量的地址、密码、secret；全部走 cfg。完成后连续验证两次：PORT=9999 go run ./cmd/server 应监听 9999；删掉 .env 里 JWT_SECRET 行应启动即报「配置加载失败」。

参考答案（要点）

internal/config 提供 Config + Load()；main 第一行调用并 fail-fast；装配全部走仓储接口——authSvc := service.NewAuthService(userRepo, cfg.JWTSecret, cfg.JWTRefreshSecret)、authH := handler.NewAuthHandler(authSvc, cfg.JWTSecret, cfg.JWTRefreshSecret)，main.go 里不许出现 gorm.Open（第 3 周的 repository.New(cfg.DSN) 就是干这个的）。DSN 在 Load 内用 Sprintf 拼装，端口位置用 %s 吃 DB_PORT：

DSN 模板%s:%s@tcp(%s:%s)/%s?charset=utf8mb4&parseTime=True&loc=Local
 ↑  ↑    ↑   ↑     ↑
DB_USER DB_PASS DB_HOST DB_PORT DB_NAME     ← 渲染后：goblog:goblog123@tcp(localhost:3306)/goblog?…

PORT=9999 前缀能覆盖 .env，是因为 godotenv.Load() 不覆盖已存在的变量（第 8 节的瀑布）。删掉 JWT_SECRET 时的报错应该是配置加载失败: 缺少环境变量：JWT_SECRET——一次报全，不是改一个报一个。

练习 2：密钥轮换演练（20 分钟）

openssl rand -hex 32 生成新值替换 .env 里的 JWT_SECRET（先只换这一把），重启服务，用旧密钥签发的 access token 请求受保护接口；再单独换 JWT_REFRESH_SECRET，用旧的 refresh 串调 /api/v1/auth/refresh。

参考答案

两次都是 401 + 1005：验签用的是新密钥，旧 token 全部作废。第二次还多证明了一件事——换 refresh 密钥不影响已签发的 access（两把密钥各管各的），这正是双密钥设计的隔离效果。这就是「泄露即轮换」的底气：换密钥的成本只是让用户重新登录一次。

练习 3：补齐 .gitignore 与 .env.example（15 分钟）

执行 git status 确认 .env 未被跟踪；提交 .env.example 与 .gitignore；README 加「快速开始：cp .env.example .env → 填值 → go run」三行说明。

练习 4：让 compose 与 .env 用同一份密码（30 分钟）

把第 3 周 compose 里 MySQL 的写死密码改成 ${...} 引用，与 Go 读的 .env 同源。注意：这一步不会改动数据库里已经存在的账号密码，先把这件事搞清楚的收益比改文件大。

参考答案 
docker-compose.yml（第 3 周的 goblog-mysql，今天只改密码来源）# ——— 第 1 段：MySQL 官方镜像认识的变量（只在「数据卷第一次初始化」时生效）———
services:
  mysql:
    image: mysql:8.0
    container_name: goblog-mysql
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_ROOT_PASS:-goblogroot}  # root 密码：compose 变量，不是后端用的账号
      MYSQL_DATABASE:      ${DB_NAME:-goblog}           # 首次启动自动建库
      MYSQL_USER:          ${DB_USER:-goblog}           # 首次启动自动建这个业务账号
      MYSQL_PASSWORD:      ${DB_PASS:-goblog123}         # ↑ 它和 .env 的 DB_PASS 必须是同一个值
    ports:
      - "3306:3306"
# ——— 第 2 段：本项目后端读的九个键（PORT / GIN_MODE / DB_* / JWT_*），由 Go 的 godotenv 读，
#      compose 自己不认它们，只是恰好和上面共用同一个 .env 文件 ———

Docker Compose 原生读取项目根目录的 .env 做变量插值，:- 是 compose 层的默认值语法。第 3 周 compose 里写死的 goblog123 今天改成了 ${DB_PASS:-goblog123}：值没变，所以现有容器和数据库账号一切照旧，重启即可。

这里有个大坑，别指望改文件就能改密码。MySQL 镜像只在数据目录为空（第一次 up）时读取 MYSQL_ROOT_PASSWORD / MYSQL_DATABASE / MYSQL_USER / MYSQL_PASSWORD 去建库建账号；卷已经存在时它直接跳过整个初始化流程（docker compose logs mysql 里看不到 Initializing database 那一段就是证据）。所以你把 MYSQL_PASSWORD 改成新值再 docker compose up -d，数据库里的密码还是老的，Go 服务立刻 Access denied for user 'goblog'@'%'。改 MYSQL_ROOT_PASSWORD 同理无效——它的语义是「初始化时把 root 密码设成这个」，不是「每次启动都把 root 密码改成这个」。

正确路线有两条，看这份库里有没有你要留的数据：

① 数据要留（推荐，日常就这么干）：直接改数据库里的账号，然后让 .env 跟上。

shell$ docker exec -it goblog-mysql mysql -uroot -p"goblogroot" \
    -e "ALTER USER 'goblog'@'%' IDENTIFIED BY '新密码'; FLUSH PRIVILEGES;"

$ # 改 .env 里的 DB_PASS=新密码，同步改 compose 的默认值（或直接靠 .env 覆盖）
$ go run ./cmd/server      # 立刻能连上，数据一行没丢

② 数据可以丢（学习期最省事）：连卷一起删掉重建，让镜像重新初始化。

shell$ docker compose down -v    # -v = 删除命名卷，MySQL 的数据目录一起没了！
$ docker compose up -d      # 空目录 → 镜像读新的 MYSQL_* → 账号密码按 compose 重建

后果写清楚：down -v 之后第 3、4 周练的那些用户和文章全部消失，要重新注册、重新 AutoMigrate；它只适合「学习期重来」或「确认无有效数据」。分不清哪种情况就用第 ① 条。

做完四条练习后自问一句：明天要把日志级别做成「跟环境走」，需要动 .env 吗？不需要——明天直接读今天已经收进 cfg.GinMode 的那个值（debug → Info、release → Warn），所以只新增 internal/pkg/applog 和 main.go 里的一行。这是刻意的设计：本周不加 LOG_LEVEL 这个变量，环境变量清单就停在讲义开头那 9 个——能由 GIN_MODE 推导出来的东西，就别再多开一项让人记。
