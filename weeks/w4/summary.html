主线项目：JWT 认证博客 API

在第 3 周 MySQL 版博客上扩展，要求全部满足：

  • 认证三接口：POST /auth/register（强度校验 + 唯一冲突 1006）、POST /auth/login（返回 access + refresh 双 token）、POST /auth/refresh（校验 refresh 串换发新的一对）。
  • 文章 CRUD：GET 列表/详情开放只读；POST/PUT/DELETE 全部过鉴权中间件。
  • 仅作者可改删：更新/删除时取 c.GetInt64("userID") 与文章的 UserID 比对，不等返回 403 + {"code":1003}。
  • 统一错误码：0 成功 / 1001 用户不存在 / 1002 密码错误 / 1003 无权限 / 1004 参数错误 / 1005 token 无效或过期 / 1006 用户名已存在，HTTP 状态码与 code 双层同步。
  • 工程化底座：配置全部来自 config 包；每个请求有 X-Request-ID 且日志可 grep；kill -TERM 优雅退出；go test ./... 全绿。
权限核心代码（PUT /articles/:id）uid := c.GetInt64("userID")
article, err := h.svc.Get(id)
if err != nil { resp.Fail(c, 404, 2001, "文章不存在"); return }
if article.UserID != uid {
    resp.Fail(c, 403, 1003, "无权限操作他人文章")  // ← 本周验收的灵魂一行
    return
}

验收 curl 清单（全部通过才算毕业）

shell# ① 未登录只读：GET 公开、POST 被拒
$ curl -s localhost:8080/articles                      # 200 + code:0
$ curl -s -X POST localhost:8080/articles -H "Content-Type: application/json" \
  -d '{"title":"noauth"}'                             # 401 + code:1005

# ② 登录可写：alice 建文成功
$ LOGIN=$(curl -s -X POST localhost:8080/auth/login -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"goodpass123"}')
$ ACCESS=$(echo "$LOGIN" | grep -o '"access_token":"[^"]*"' | cut -d'"' -f4)
$ curl -s -X POST localhost:8080/articles -H "Authorization: Bearer $ACCESS" \
  -H "Content-Type: application/json" -d '{"title":"jwt week"}'   # 201 + code:0

# ③ 非作者 403：bob 改 alice 的文章
$ BOB=$(curl -s -X POST localhost:8080/auth/login -H "Content-Type: application/json" \
  -d '{"username":"bob","password":"goodpass456"}' | grep -o '"access_token":"[^"]*"' | cut -d'"' -f4)
$ curl -s -X PUT localhost:8080/articles/1 -H "Authorization: Bearer $BOB" \
  -H "Content-Type: application/json" -d '{"title":"hijack"}'     # 403 + code:1003

# ④ 坏 token 401
$ curl -s localhost:8080/articles -H "Authorization: Bearer $ACCESSx"       # 篡改一位 → 401+1005
$ curl -s localhost:8080/articles -H "Authorization: $ACCESS"               # 缺 Bearer 前缀 → 401+1005

# ⑤ refresh 成功换发（并把新 access 再验证一次可用）
$ REFRESH=$(echo "$LOGIN" | grep -o '"refresh_token":"[^"]*"' | cut -d'"' -f4)
$ curl -s -X POST localhost:8080/auth/refresh -H "Content-Type: application/json" \
  -d "{\"refresh_token\":\"$REFRESH\"}"                                      # 200 + 新 token 对

# ⑥ 请求 ID：任一响应头都含 X-Request-ID，且能在日志里 grep 到同一值
$ curl -si localhost:8080/health | grep -i x-request-id

本周常见卡点答疑

Q1：登录成功、token 也带了，却处处 401。三查：① Bearer 后必须有且只有一个空格；② 签发和校验用的 JWT_SECRET 是不是两个进程各读了一份（比如服务起着起着改了 .env 没重启）；③ 解码 payload 看 exp 是不是早就过了（时钟漂了或 TTL 忘了改回 15 分钟）。

Q2：403 返回了，但文章还是被改了。Abort/写响应之后没 return，handler 继续往下执行。本周所有「拦截型」分支都过一遍：中间件、权限比对、参数校验，一个 return 都不能少。

Q3：注册第二次同名没报 1006，反而 500。唯一索引根本没建上（改 tag 后没 AutoMigrate，或表已存在时索引没补）——SHOW INDEX FROM users; 看有没有 username 的 UNIQUE 索引；再确认 service 里 1062 的翻译分支生效。

Q4：go test 一跑，开发库数据没了。测试连到了开发 DSN！立刻检查测试用的连接来源，改成内存 sqlite 或独立的 blog_test 库，并从开发库备份恢复数据。这是本周最贵的坑，中招的同学反而印象最深。

Q5：logout 到底做没做？按 D2 的诚实方案：客户端删 token + README 记录「access 有效期内技术上仍可用」的技术债。别为了「看起来完整」写一个只返回 ok 却什么都不作废的接口骗验收——那是伪功能。

Q6：/auth/refresh 用对了还是 401。四查：① 传的是 refresh 串而不是 access（解码看 "typ" 字段）；② 两个签发函数用的 secret 是否同一个来源；③ refresh 的 7 天 TTL 是否真给了（常量复制错很常见）；④ Parse 的 wantType 参数在该路由上传的是否为 "refresh"。

Q7：文章创建成功但 author 是空的。handler 里取了 c.GetInt64("userID") 却忘了赋给模型，或者中间件 Set 的 key 与 Get 的 key 拼写不一致（"userID" vs "userId"，Go 大小写敏感）。用常量 CtxKeyUserID 统一管理 key 可根治。

下周预告：第 5 周 并发 + 性能

Go 真正的杀手锏要登场了：goroutine、channel、context、sync.Mutex。主线项目「并发 URL 聚合 API」——5 个各需 1 秒的端点，串行 5 秒、你写的并发版要 ≈1 秒；某个 URL 卡死时 5 秒超时返回部分结果。本周学的 context.WithTimeout 会在 D4 重逢（只不过这次是你主动用它掐请求），今天的测试功底的用武之地是 go test -race。
