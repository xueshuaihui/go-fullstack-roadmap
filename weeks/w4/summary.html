主线项目：JWT 认证博客 API

在第 3 周 MySQL 版博客上扩展，要求全部满足：

  • 认证三接口 + 一个「我是谁」：POST /api/v1/auth/register（强度校验 + 唯一冲突 1006）、POST /api/v1/auth/login（data 里同时给出 user + access_token + refresh_token）、POST /api/v1/auth/refresh（只认 refresh 串，换发新的一对）、GET /api/v1/users/me（受保护，取自己的资料，前端刷新页面靠它）。
  • 文章 CRUD：GET /api/v1/articles 列表/详情开放只读；POST/PUT/DELETE 全部过 middleware.Auth(cfg.JWTSecret)。
  • 仅作者可改删：更新/删除时取 c.GetUint(middleware.CtxKeyUserID) 与文章的 UserID（同为 uint）比对，不等返回 403 + {"code":1003}；资源本身不存在返回 404 + {"code":2001}（含已被软删除的）。
  • 统一错误码：0 成功 / 1001 资源不存在（通用，NoRoute 也发它）/ 1002 密码错误 / 1003 权限不足 / 1004 参数错误 / 1005 未认证或 token 无效 / 1006 唯一冲突（用户名已存在、邮箱已被注册共用此码，靠 message 区分）/ 2001 文章不存在 / 5000 服务器内部错误。常量全部写在 pkg/response 里，HTTP 状态码与 code 双层同步。
  • 工程化底座：配置全部来自 config 包；每个请求有 X-Request-ID 且日志可 grep；kill -TERM 优雅退出；go test ./... 全绿；.github/workflows/ci.yml 推上 GitHub 后 Actions 是绿的。
权限核心（PUT / DELETE /api/v1/articles/:id 共用同一套形状）// 取当前用户：中间件 Set 进去的是 uint，这里就必须 GetUint；键名走常量，别裸写字符串
uid := c.GetUint(middleware.CtxKeyUserID)

a, err := h.arts.Update(uint(id), uid, req.Title, req.Content)   // 判断在 service：先 Get 再比 UserID
if err != nil {
    switch {
    case errors.Is(err, repository.ErrArticleNotFound):
        response.Fail(c, http.StatusNotFound, response.CodeArticleNotFound, "文章不存在")
    case errors.Is(err, service.ErrNotOwner):
        response.Fail(c, http.StatusForbidden, response.CodeForbidden, "只能修改自己的文章")  // ← 本周验收的灵魂一行
    default:
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务器开小差了")
    }
    return                                                       // ← 这个 return 也不能省
}
response.OK(c, gin.H{"article": a})

注意上面没有 resp 这个别名：response.OK(c, data) 两参、response.Created(c, data) 两参、response.Fail(c, httpStatus, code, msg) 四参（先 HTTP 状态码再业务码），全站只有这一套。「仅作者可改删」的完整正文分在两处：D2 第 8 节（Update + 那张 curl 矩阵）和 D5 第 5 节（补完 Delete + 表驱动权限矩阵测试）。验收要求 DELETE 也交出和 PUT 一样的四种结果。

常量名以 pkg/response 里那一个 const 块为准（D1 补齐、D4 第 5 节整表铺开，以后六周不再新增）：CodeOK 0、CodeUserNotFound 1001、CodeBadPassword 1002、CodeForbidden 1003、CodeInvalidParam 1004、CodeTokenInvalid 1005、CodeUsernameTaken 1006、CodeArticleNotFound 2001、CodeInternal 5000。三条禁令：不用 1000 当通用失败、不用 5001、不让 code 等于 HTTP 状态码。

记住双层约定的分工：HTTP 状态码给机器看（第 6 周 axios 拦截器只认 401/403 分支），code 给人和业务分支看（同样是 401，1002 该停在学习页、1005 该触发静默刷新）。两层同时出现、语义不冲突。

本周常见卡点答疑

Q1：登录成功、token 也带了，却处处 401。三查：① Bearer 后必须有且只有一个空格；② 保护组挂的是 middleware.Auth(cfg.JWTSecret) —— 拿 refresh 那把 JWT_REFRESH_SECRET 去验 access 必挂（这是双密钥设计的代价，不是 bug）；③ 服务起着起着改了 .env 没重启，两个进程各读了一份密钥；④ 解码 payload 看 exp 是不是早就过了（时钟漂了或 TTL 忘了改回 15 分钟）。

Q2：403 返回了，但文章还是被改了。Abort/写响应之后没 return，handler 继续往下执行。本周所有「拦截型」分支都过一遍：中间件、权限比对、参数校验，一个 return 都不能少。

Q3：注册第二次同名没报 1006，反而 500。两种可能：① 唯一索引根本没建上（改 tag 后没 AutoMigrate，或表已存在时索引没补）——SHOW INDEX FROM users; 看 username（和 email）有没有 UNIQUE 索引；② service 里那段翻译没生效：它得同时认 MySQL 的 1062 Duplicate entry … for key 'users.username' 和 sqlite 的 UNIQUE constraint failed: users.username（就是 D1 那个 isDuplicateOn(err, "username")）。只在测试里红、开发库里绿，多半是②。

Q4：go test 一跑，开发库数据没了。测试连到了开发 DSN！立刻检查测试用的连接来源，改成内存 sqlite（D5 第 4 节那种「库名带测试名」的写法）或独立的 goblog_test 库 + 单独的 TEST_DB_DSN，并从开发库备份恢复数据。这是本周最贵的坑，中招的同学反而印象最深。

Q5：logout 到底做没做？按 D2 的诚实方案：客户端删 token + README 记录「access 有效期内技术上仍可用」的技术债。别为了「看起来完整」写一个只返回 ok 却什么都不作废的接口骗验收——那是伪功能。（服务端撤销的黑名单方案在本课程范围外，第 8 周也不会引入它。）

Q6：/api/v1/auth/refresh 用对了还是 401。四查：① 传的是 refresh 串而不是 access（解码看 "typ" 字段）；② NewRefreshToken 和 Parse 用的是同一把 JWT_REFRESH_SECRET；③ refresh 的 7 天 TTL 是否真给了（常量复制错很常见）；④ Parse 的 wantType 参数在该路由上传的是否为 "refresh"。

Q7：文章创建成功但 author 是空的。handler 里取了 c.GetUint(middleware.CtxKeyUserID) 却忘了赋给 Article.UserID，或者中间件 Set 的键与 Get 的键拼写不一致（"userID" vs "userId"，Go 大小写敏感），又或者类型不匹配——存 uint 却用 GetInt64/GetInt 取，gin 断言失败不报错、只返回零值 0。用常量 CtxKeyUserID 统一键名、用 GetUint 统一类型，可根治这两类。

Q8：bob 删 alice 的文章返回了 200，权限判断像没生效。最典型的成因是两边同时为 0：创建文章时 handler 取错了值（Q7 那个 GetInt64，或键名拼成 "userId"，拿到零值 0），于是文章带着 UserID = 0 进库；改删时又用同一个错法取当前用户，照样是 0 —— a.UserID != userID 成了 0 != 0，对谁都不成立，判断被两个零值喂穿。反过来只有一侧为 0（文章是 0、请求者是正常的 2）时你会看到稳定的 403，那是另一种响法，别混。先跑 D5 第 5 节那张权限矩阵：它会在「偷改 bob 的」那条上直接红。另一类原因：写操作根本没挂进保护组，priv := v1.Group("", middleware.Auth(...)) 必须在注册路由之前建好（D2 第 6 节）。
