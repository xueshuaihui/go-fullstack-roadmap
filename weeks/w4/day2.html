课前须知：给 JS 开发者的两句话

1. 服务端 Session vs JWT。Session 是「服务器记账」：登录态存内存/Redis，cookie 里只放个编号；JWT 是「带公章的纸条」：服务器不记任何东西，每次请求验证纸条上的签名即可。水平扩容友好，代价是「签发出去就收不回来」——这也是第 7 节要诚实讨论 logout 的原因。

2. 你在 npm 里熟的 jwt/jsonwebtoken 库，Go 对应 github.com/golang-jwt/jwt/v5。概念完全一致：sign 签发、verify 校验，只是 v5 的 API 把校验拆成了 ParseWithClaims + 手动断言 Claims 类型。

知识讲义

1. JWT 三段结构：拆一个真 token

JWT 就是 header.payload.signature 三段 base64url 字符串用点连接。下面是一个真实的 HS256 token（签名密钥为 s3cr3t-key-change-me，仅供教学；它不是我们代码生成的，而是按 HS256 规则手工算出来的，你待会儿可以自己复算签名）：

tokeneyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1aWQiOjEsInR5cCI6ImFjY2VzcyIsImlhdCI6MTc1ODYwNDgwMCwiZXhwIjoxNzU4NjA1NzAwfQ.e0MV2PPHRpXA6xdl6sPG5Kknw603grjZ7tMl2VaNVHs

把前两段各做一次性 base64url 解码，原文立刻现形：

shell$ echo 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9' | base64 -D
{"alg":"HS256","typ":"JWT"}                    # header：算法与类型

$ echo 'eyJ1aWQiOjEsInR5cCI6ImFjY2VzcyIsImlhdCI6MTc1ODYwNDgwMCwiZXhwIjoxNzU4NjA1NzAwfQ==' | base64 -D
{"uid":1,"typ":"access","iat":1758604800,"exp":1758605700} # payload：claims 声明

上面那条命令里我偷偷加了两个 =，这不是笔误：base64url 为了塞进 URL 会做两件事——把 + / 换成 - _、把末尾的填充 = 全省掉。而 base64 解码器要求输入长度是 4 的倍数，所以解之前要把长度补满 4 的倍数。这段 payload 原文 78 个字符（78 % 4 = 2），补 2 个 = 正好。

直接拿未补填充的串去解，两个系统的表现不一样：

  • macOS/BSD：base64 -D 不报错，但结尾会静默少一个字符——你自己试一次，输出是没有右花括号 } 的残缺 JSON，比报错更难查。
  • Linux/GNU coreutils：base64 -d 直接报 invalid input，老老实实补 =。

顺手记住 base64 命令本身的大小写差异：macOS 用 -D/-E 解码/编码，Linux 用 -d/-e，两边都认长选项 --decode/--encode，写脚本时用长选项最省心。真要图省事，直接 python3 -c "import base64,sys;print(base64.urlsafe_b64decode(sys.argv[1]+'=='))" 'TOKEN段'。

段内容作用
header{"alg":"HS256","typ":"JWT"}声明签名算法
payload业务字段 + 标准字段（exp 过期时间戳、iat 签发时间戳、sub、iss 等）承载「谁、什么用途、何时过期」
signatureHMAC-SHA256(header + "." + payload, secret) 再 base64url公章：改一个字签名就对不上

常用标准 Claims 先记四个：exp（过期时间，服务器强制校验）、iat（签发时间，refresh 判断用）、sub（主体标识）、iss(签发者)。今天我们的自定义字段是 uid（用户 ID，类型 uint）和 typ（token 用途）。

自己验证一遍时间戳：exp - iat = 1758605700 - 1758604800 = 900 秒 = 15 分钟，正是下面 AccessTTL 的值。换算成人话：macOS 用 date -r 1758605700，Linux 用 date -d @1758605700，会打出 Sep 23 2025 ... 13:35 之类的本地时间。

2. 签名 ≠ 加密

上面你亲手解码了 payload——任何人都能。signature 只保证「不被篡改」（把 "uid":1 改成 "uid":2 冒充别人后，没有密钥就重算不出合法签名），不保证不被看见。铁律：payload 里只放 userID、token 用途这类不敏感标识，绝不放密码、手机号、身份证、支付信息。

推论：JWT 的 secret 只有一个作用——签名。泄露 secret 等于攻击者可以任意伪造 uid 为任何用户的 token，所以它和数据库密码同级对待（明天配置课把它收进 .env）。

3. 签发与解析：golang-jwt/jwt/v5

shell$ go get github.com/golang-jwt/jwt/v5
internal/pkg/jwtutil/jwt.gopackage jwtutil

import (
    "errors"
    "time"

    "github.com/golang-jwt/jwt/v5"
)

type Claims struct {
    UserID uint   `json:"uid"` // ← 和 gorm.Model 给的 user.ID 同一个类型，别写 int64
    Type   string `json:"typ"` // "access" 或 "refresh"，两种 token 靠它区分
    jwt.RegisteredClaims      // 内嵌标准字段：exp / iat / sub 全在这
}

const (
    AccessTTL  = 15 * time.Minute
    RefreshTTL = 7 * 24 * time.Hour
)

// Sign 通用签发：HS256 + 密钥字节
func Sign(secret string, c Claims) (string, error) {
    return jwt.NewWithClaims(jwt.SigningMethodHS256, c).SignedString([]byte(secret))
}

// 两把密钥：access 用 JWT_SECRET，refresh 用 JWT_REFRESH_SECRET。
// 一把泄露不等于两把全废，也顺手杜绝「拿 refresh 的密钥去签 access」这类混淆。
func NewAccessToken(accessSecret string, userID uint) (string, error) {
    now := time.Now()
    return Sign(accessSecret, Claims{UserID: userID, Type: "access",
        RegisteredClaims: jwt.RegisteredClaims{
            IssuedAt:  jwt.NewNumericDate(now),
            ExpiresAt: jwt.NewNumericDate(now.Add(AccessTTL)),
        }})
}

func NewRefreshToken(refreshSecret string, userID uint) (string, error) {
    now := time.Now()
    return Sign(refreshSecret, Claims{UserID: userID, Type: "refresh",
        RegisteredClaims: jwt.RegisteredClaims{
            IssuedAt:  jwt.NewNumericDate(now),
            ExpiresAt: jwt.NewNumericDate(now.Add(RefreshTTL)),
        }})
}

// ErrTokenType 自定义错误：token 本身合法但用途不对（拿 access 当 refresh 用）
var ErrTokenType = errors.New("token 类型不符")

// Parse 校验签名 + exp，并确认 typ 字段符合预期用途
func Parse(secret, tokenStr, wantType string) (Claims, error) {
    var empty Claims
    tok, err := jwt.ParseWithClaims(tokenStr, &empty, func(t *jwt.Token) (any, error) {
        if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok { // 防算法混淆攻击
            return nil, jwt.ErrTokenSignatureInvalid
        }
        return []byte(secret), nil
    }, jwt.WithValidMethods([]string{"HS256"}))
    if err != nil { // 过期: errors.Is(err, jwt.ErrTokenExpired)
        return empty, err
    }
    if !tok.Valid || empty.Type != wantType {
        return empty, ErrTokenType
    }
    return empty, nil
}

v5 与旧版（v3/v4）最大区别：keyfunc 返回 (any, error)、过期判断用 errors.Is(err, jwt.ErrTokenExpired) 而不是布尔比较。网上大量老教程贴的是 v4 写法，抄过来编译会挂，认准 v5。

为什么 Claims 里没有 role？因为 model.User 现在还没有 Role 字段（第 3 周的模型里没有，本周也不加，第 7 周的迁移 000002_add_role_to_users 才把它落库）。token 里签什么，取决于你能不能在库里兑现它——提前签一个恒为 0 的 role，等第 8 周真做后台时，老 token 会带着错误身份一直活到过期。本项目第 8 周才把 Role int8 `json:"role"` 加进 Claims，今天只有 uid + typ。

结构体内嵌（embedding）≠ 继承。Claims 里裸写一行 jwt.RegisteredClaims，Go 就把它的字段「提升」进来：claims.ExpiresAt 直接可用，JSON 序列化时 exp/iat 会和 uid/typ 平铺在同一个对象里（就是第 1 节你解码出来的那个形状）。对照 TS：interface Claims extends RegisteredClaims { uid: number } 的效果，但 Go 靠匿名字段组合，没有 is-a 关系。

4. 登录发双 token + /api/v1/auth/refresh 换发

今天要动昨天的两处：service 的 Login 返回值从 uint 升级成 *model.User（响应里要把 user 和两把 token 一起带出去，第 6 周前端登录后直接渲染昵称，省一次请求），handler 的 Login 整段替换。改完唯一裁判是 go build ./...。

            return nil, ErrBadCredential
        }
        return nil, err // 数据库真挂了，交给 handler 走 500
    }
    if bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(password)) != nil {
        return nil, ErrBadCredential // 与上面同一句提示，防枚举
    }
    return &user, nil // ByUsername 返的是值（第 3 周口径），这里取局部变量的地址交出去，编译器不拦
}

为什么返回指针而不是值？*model.User 是「要么给用户，要么没给」：nil 就是没给，配合 error 一起构成 Go 的标准返回形状。对照 JS：你习惯 throw 一个异常再 try/catch，Go 把「没拿到」写成普通的返回值，控制流一眼能看完。别和上面那句混起来：仓储层（第 3 周口径）返的是值，因为它没有「没这个人」这个状态——那件事由 ErrUserNotFound 表达；service 层面向 handler，指针 + nil 才是它需要的形状，所以最后一行是 return &user, nil。

internal/handler/auth.go（替换昨天的 Login，并新增 Refresh）package handler

import (
    "errors"
    "net/http"

    "github.com/gin-gonic/gin"

    "goblog/internal/pkg/jwtutil"     // ← 今天新增这个 import
    "goblog/pkg/response"
    "goblog/internal/repository"
    "goblog/internal/service"
)

// Login：校验密码 → 用两把密钥签两把 token → 一起返回
func (h *AuthHandler) Login(c *gin.Context) {
    var req struct {
        Username string `json:"username" binding:"required"`
        Password string `json:"password" binding:"required"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数错误")
        return
    }
    user, err := h.svc.Login(req.Username, req.Password)
    if err != nil {
        if errors.Is(err, service.ErrBadCredential) {
            response.Fail(c, http.StatusUnauthorized, response.CodeBadPassword, "用户名或密码错误")
            return
        }
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务器开小差了")
        return
    }
    access, err := jwtutil.NewAccessToken(h.accessSecret, user.ID)
    refresh, err2 := jwtutil.NewRefreshToken(h.refreshSecret, user.ID)
    if err != nil || err2 != nil {
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "签发失败")
        return
    }
    response.OK(c, gin.H{"user": user, "access_token": access, "refresh_token": refresh})
}

// Refresh：只接受 refresh token（用 JWT_REFRESH_SECRET 验签），通过则换发一对新 token
func (h *AuthHandler) Refresh(c *gin.Context) {
    var req struct {
        RefreshToken string `json:"refresh_token" binding:"required"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "缺少 refresh_token")
        return
    }
    claims, err := jwtutil.Parse(h.refreshSecret, req.RefreshToken, "refresh")
    if err != nil { // 过期 / 被篡改 / 类型不对，对外话术统一成一句
        response.Fail(c, http.StatusUnauthorized, response.CodeTokenInvalid, "token 无效或已过期，请重新登录")
        return
    }
    access, err := jwtutil.NewAccessToken(h.accessSecret, claims.UserID)
    refresh, err2 := jwtutil.NewRefreshToken(h.refreshSecret, claims.UserID)
    if err != nil || err2 != nil {
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "签发失败")
        return
    }
    response.OK(c, gin.H{"access_token": access, "refresh_token": refresh})
}

5. 鉴权中间件：把 uid 换成「当前登录用户」

中间件不是新概念——第 2 周 D3 你就写过 Logger 和 Recovery。今天这个 Auth 是同一件事：gin.HandlerFunc，进去拦一道，放行时把用户身份塞进 context。返回体继续用第 2 周的 response.Body，别自己拼 gin.H（键名手滑一次，前端的拦截器就静默失效）。

internal/middleware/auth.gopackage middleware

import (
    "net/http"
    "strings"

    "github.com/gin-gonic/gin"

    "goblog/internal/pkg/jwtutil"
    "goblog/pkg/response"
)

// CtxKeyUserID 全站统一的 context 键名。
// 用常量而不是到处裸写 "userID"：字符串写错（userId / userid）编译器不拦，
// 取出来是零值 0，于是「所有人都没登录」，这种 bug 能查半天
const CtxKeyUserID = "userID"

// Auth 只验 access token：签名对不对、exp 过没过期、typ 是不是 "access"
func Auth(secret string) gin.HandlerFunc {
    return func(c *gin.Context) {
        raw := c.GetHeader("Authorization")
        const prefix = "Bearer "
        if !strings.HasPrefix(raw, prefix) {       // 缺头 / 不是 Bearer 格式
            c.AbortWithStatusJSON(http.StatusUnauthorized, response.Body{
                Code: response.CodeTokenInvalid, Message: "未登录", Data: nil,
            })
            return                                // ← 这个 return 不能省！
        }
        claims, err := jwtutil.Parse(secret, strings.TrimPrefix(raw, prefix), "access")
        if err != nil {
            c.AbortWithStatusJSON(http.StatusUnauthorized, response.Body{
                Code: response.CodeTokenInvalid, Message: "token 无效或已过期", Data: nil,
            })
            return
        }
        c.Set(CtxKeyUserID, claims.UserID)         // 存的是 uint，后面必须用 GetUint 取
        c.Next()                                  // 放行：把控制权交给下一个 handler
    }
}
internal/handler/article.go（不属上面那个文件：今天第一次从 context 里取身份）func (h *Handler) ArticleCreate(c *gin.Context) {
    uid := c.GetUint(middleware.CtxKeyUserID)  // 中间件保证进来的必有值，且类型是 uint
    a := model.Article{UserID: uid}           // ← 作者字段今天就写上，第 8 节靠它判权限

类型要对齐：c.Set 存 uint，取就必须用 c.GetUint（第 1 天的 Me 用的就是这一对）。写成 c.GetInt64("userID")（或 GetInt）拿到的是 0——gin 的取值函数是先 Get 再断言具体类型，断言失败就返回零值，不 panic 也不报错。于是每篇文章的作者都是 0，第 8 节那个「仅作者可改删」永远返回 403，排查时你会以为是逻辑写错了。

和 Express 中间件对得上。Express 是 (req, res, next) => { req.userId = ...; next() }，gin 是 func(c *gin.Context) { c.Set(...); c.Next() }：都靠「往请求对象上挂字段」传递前置阶段的结论。区别只有一个——gin 的 c.Next() 之后还会回到你这里继续跑（所以「计时中间件」在 c.Next() 后面记耗时），Express 没有这个回程。

6. 挂载与路由注册：公开组与保护组

两个容易被忽略的点：① Group("", 中间件...) 是合法写法——第一个参数是路径前缀，空串表示「就挂在这个组上」，专门用来加中间件；② 中间件必须在注册路由之前挂好。gin 的分组只对它之后注册的路由生效，写成「先 priv.GET(...) 再 priv.Use(Auth)」，那条路由就永远不过鉴权（而且一声不吭）。用 Group(prefix, middlewares...) 一次传到位，是这个坑最省事的躲法。

对照 Express：这相当于 app.use('/api/v1/auth', publicRouter) 与 app.use('/api/v1', authMiddleware, privateRouter)。区别是 gin 的分组是「路径 + 中间件」一起绑定的对象，而不是挂载一棵子路由树。

7. logout：一个诚实的讨论

Session 时代登出 = 删服务器上的记录。JWT 无状态——服务器根本没记，想「让已签发的 token 立刻作废」就必须重新引入状态。三种务实选择：

方案做法代价
纯前端「登出」客户端删掉本地 token，服务端什么都不做token 在有效期内其实还活着；对 15 分钟的 access 通常可接受
黑名单（Redis/内存表）登出时把 access 的 jti、refresh 整串塞进黑名单，存活到原过期时间为止；中间件多查一次重新引入状态与一次存储查询，但粒度可控，生产常用
库内版本戳users 表加 token_version，改密码/全端登出时 +1，校验时比对每请求多一次查询；实现简单，适合中小项目

本项目今天采用第一档：不做服务端 logout，前端 logout 就是把 localStorage 里的两把 token 删掉（第 6 周会这么写），README 里写清「access 在剩余有效期内仍然可用，需要立刻失效请改密码」。顺带把「轮换」这个词说破：/auth/refresh 每次都签一把新 refresh（第 4 节那对 NewAccessToken + NewRefreshToken），可旧的那把并没有作废——它照样能活满 7 天。「用过的 refresh 立刻失效」这句话在没有服务端状态的前提下无处落地，这是无状态方案的固有代价，不是我们漏写了一段代码。Redis 黑名单这类服务端撤销方案在本课程范围之外，学有余力可以自行了解——本项目到第 8 周也不会引入它。诚实地记录技术债，比假装安全强。

// h 是第 3 周总结页那行 handler.New(userSvc, artSvc) 返回的 *Handler，文章 service 这里写作 h.arts
func (h *Handler) ArticleUpdate(c *gin.Context) {
    id, err := strconv.ParseUint(c.Param("id"), 10, 64)
    if err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "id 必须是数字")
        return
    }
    var req struct {
        Title   string `json:"title" binding:"required"`
        Content string `json:"content" binding:"required"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数错误")
        return
    }
    a, err := h.arts.Update(uint(id), c.GetUint(middleware.CtxKeyUserID), req.Title, req.Content)
    if err != nil {
        switch {
        case errors.Is(err, repository.ErrArticleNotFound):
            response.Fail(c, http.StatusNotFound, response.CodeArticleNotFound, "文章不存在")
        case errors.Is(err, service.ErrNotOwner):
            response.Fail(c, http.StatusForbidden, response.CodeForbidden, "只能修改自己的文章")
        default:
            response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务器开小差了")
        }
        return
    }
    response.OK(c, gin.H{"article": a})
}

403 还是 404？本项目用 404 + 2001 表示「文章不存在」、403 + 1003 表示「文章在、但不是你的」。这个组合会泄露「某个 ID 有文章」这一点点信息——对博客站可以接受（谁都能从列表页看到 ID）。如果做的是私密资源（网盘链接、发票），业内更常统一返回 404，用「不存在」把「没权限」盖住。记住这是一次权衡，不是教条。

对照 Express 生态里你可能用过的 ensureAuth + article.authorId === req.user.id：思路一模一样。差别只在于 JS 里 === 会帮你做类型转换（"1" == 1 为真），Go 里 a.UserID != userID 两侧必须同为 uint，所以第 5 节反复强调类型对齐——类型统一了，判断就是一行。

第 8 周加管理员角色时，只在这行判断上放宽：if a.UserID != userID && !isAdmin(c) { return nil, ErrNotOwner }。isAdmin 依赖还没进 token 的 role，所以今天不留坑位。
