密码哈希与注册登录

前三周你的用户接口是「裸奔」的：谁都能改任何人的资料。从今天起给项目装上锁。第一步不是 JWT，而是把密码安全地存进数据库——这一步做错，后面所有认证都是空中楼阁。今天结束时要能跑通 /auth/register 和 /auth/login 两个接口。

今日目标

↑ 这四条是「学习目标」，学的过程中随时回来勾；页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

课前须知：给 JS 开发者的两句话

1. 哈希不是加密。加密可以解密，哈希是单向的：bcrypt.Hash("123456") 永远还原不出 "123456"。所以登录校验不能「解密比对」，只能把用户输入的密码用同样算法再算一次去比对。

2. 数据库泄露是常态不是意外。设计存储方案时要假设「有一天拖库了」：只要库里没有明文、也没有可逆的密文，用户就是安全的。这就是只存哈希的理由。

知识讲义

1. 为什么明文不行、md5 也不行

方案死法真实案例
明文存储拖库 = 全站密码直接泄露，用户在其他网站同密码被连锅端（撞库）各类「账号密码裸奔」新闻，年年有
纯 md5 / sha1哈希速度快到 GPU 每秒可算数百亿次，可暴力穷举；常见密码的哈希早被算好收录成彩虹表，查表几秒还原2011 年 CSDN 600 万账号 md5 被撞开大半
md5 + 固定盐代码泄露后全体用户盐相同，仍可一次建表打全站不少早期 PHP 项目
bcrypt（自动逐用户加盐 + 可调慢哈希）✅ 当前推荐下限今天的主角

关键直觉：校验密码就应该慢。用户登录多等 100ms 毫无感知，攻击者穷举一亿次就要多等十几天。md5 的问题恰恰是「太快了」。

2. bcrypt 原理一句话 + API

bcrypt = 为密码设计的慢哈希：每个用户自动生成随机盐（同一密码两次注册哈希值不同，彩虹表失效），cost 参数控制计算轮数（2 的 cost 次方，可调到跟硬件一起变慢）。

shell$ go get golang.org/x/crypto/bcrypt
hash_demo.gopackage main

import (
    fmt
    log

    "golang.org/x/crypto/bcrypt"
)

func main() {
    // 注册时：明文 -> 哈希。cost 建议 10~12，bcrypt.DefaultCost 当前就是 10
    hashed, err := bcrypt.GenerateFromPassword([]byte("MyPassw0rd!"), bcrypt.DefaultCost)
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println(string(hashed))
    // $2a$10$N9qo8uLOickgx2ZMRZoMye...  前缀里就带着算法版本和 cost

    // 登录时：注意参数顺序是 (哈希, 明文)，返回 error 而不是 bool！
    err = bcrypt.ComparePassword(hashed, []byte("MyPassw0rd!"))
    fmt.Println("对了:", err == nil)       // true

    err = bcrypt.ComparePassword(hashed, []byte("wrong"))
    fmt.Println("错了:", err != nil)       // true，err 为 bcrypt.ErrMismatchedHashAndPassword
}

两处最容易翻车的细节：① ComparePassword(hashedPassword, password) 哈希在前、明文在后，写反了永远比不中且报错；② 它用 error 表达「不匹配」，判断要写 err == nil 表示密码正确，别 if err != nil { 登录成功 } 把逻辑整个反了。

3. 注册接口：强度校验 + 唯一索引冲突

模型上给 username 加唯一索引（第 3 周 GORM 的 uniqueIndex），密码列存 bcrypt 结果，注意长度至少 varchar(60)：

internal/model/user.gopackage model

import "gorm.io/gorm"

type User struct {
    gorm.Model
    Username   string gorm:"uniqueIndex;size:32" json:"username"
    Password   string gorm:"size:72;not null"    json:"-" // json:"-" 永远不把哈希序列化出去
    Nickname   string gorm:"size:32"             json:"nickname"
}
internal/service/auth.gopackage service

import (
    "errors"
    "regexp"
    "strings"

    "golang.org/x/crypto/bcrypt"
    "gorm.io/gorm"

    "studyblog/internal/model"
)

var ErrWeakPassword = errors.New("密码至少 8 位，且包含字母和数字")

// Register 校验 -> 哈希 -> 落库；用户名重复交给数据库唯一索引兜底
func (s *AuthService) Register(username, password string) error {
    if !passwordStrong(password) {
        return ErrWeakPassword
    }
    hashed, err := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
    if err != nil {
        return err
    }
    err = s.db.Create(&model.User{Username: username, Password: string(hashed)}).Error
    if err != nil && strings.Contains(err.Error(), "1062") {
        // MySQL: Error 1062 (23000): Duplicate entry 'xxx' for key 'users.username'
        return ErrUsernameTaken
    }
    return err
}

var (
    hasLetter = regexp.MustCompile(`[A-Za-z]`)
    hasDigit  = regexp.MustCompile(`[0-9]`)
)

func passwordStrong(p string) bool {
    return len(p) >= 8 && hasLetter.MatchString(p) && hasDigit.MatchString(p)
}

为什么靠数据库而不是先 SELECT 查一次再插入？「先查后插」在并发下两个请求可能同时通过检查。唯一索引是最后一道也最可靠的一道防线，应用层只需把 1062 翻译成 code:1006 用户名已存在 这样的业务码。

4. 登录接口：统一提示防枚举

internal/service/auth.govar ErrBadCredential = errors.New("用户名或密码错误")

// 一个固定的假哈希，仅用于"用户不存在"时空跑一次 bcrypt 拉齐耗时
var fakeHash = []byte("$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy")

// Login 校验通过返回用户（明天再发 token，今天先返回 nil error）
func (s *AuthService) Login(username, password string) (int64, error) {
    var user model.User
    err := s.db.Where("username = ?", username).First(&user).Error
    if err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            // 故意不暴露"用户不存在"——否则攻击者拿它当用户名探测仪
            bcrypt.ComparePassword(fakeHash, []byte(password)) // 空跑一次，耗时对齐
            return 0, ErrBadCredential
        }
        return 0, err // 数据库真挂了，走 500
    }
    if bcrypt.ComparePassword([]byte(user.Password), []byte(password)) != nil {
        return 0, ErrBadCredential // 同样的话术，同样的 error
    }
    return user.ID, nil
}

防枚举：「用户不存在」和「密码错误」如果返回不同提示（甚至不同响应时间），攻击者就能批量探测哪些用户名注册过。统一成一句「用户名或密码错误」，进阶做法如上——用户不存在时也拿一个假哈希空跑一次 bcrypt，把两条路径耗时拉齐。今天做到提示统一即可，耗时对齐了解原理就行。

5. handler 层接线

internal/handler/auth.gofunc (h *AuthHandler) Register(c *gin.Context) {
    var req struct {
        Username string json:"username" binding:"required,min=3,max=32"
        Password string json:"password" binding:"required"
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        resp.Fail(c, 400, 1004, "参数错误")
        return
    }
    if err := h.svc.Register(req.Username, req.Password); err != nil {
        switch {
        case errors.Is(err, service.ErrWeakPassword):
            resp.Fail(c, 400, 1004, err.Error())
        case errors.Is(err, service.ErrUsernameTaken):
            resp.Fail(c, 409, 1006, "用户名已存在")
        default:
            resp.Fail(c, 500, 5000, "服务器开小差了")
        }
        return
    }
    resp.OK(c, 201, gin.H{"username": req.Username})
}

路由注册（登录复用同样的 ShouldBindJSON 套路，成功今天先返回 {"user_id":1}，明天换成 token）：

6. 延伸两个必答小题

① 为什么 bcrypt 密码上限是 72 字节？算法内部把口令按 72 字节分块进 Expensive Key Setup，超出的部分被静默丢弃——意味着「前 72 字节相同、后段不同」的两个密码会被判为同一个。实践：注册校验限制最大长度（如 64），超长直接拒绝而不是截断。

② 为什么今天登录成功还只回 user_id、不发 token？凭证方案是明天的主角。今天把「密码对不对」这一步做扎实，明天只需在 Login 成功后追加两行签发调用——分层推进，每天只炸一个新变量。

顺手成本对比一下：bcrypt cost=10 单次哈希约 60–100ms。注册/登录是低频操作，用户无感；但如果你有「每秒几百次校验密码」的内部接口，就要换 argon2 或降低 cost 并重新评估威胁模型——慢是武器，也是负载，知道自己在权衡什么。

练习 2：肉眼验证「同密码不同哈希」（15 分钟）

写个小 main：对同一字符串调两次 GenerateFromPassword，打印结果。

参考答案

两个哈希串完全不同——因为每次自动生成了不同的随机盐。但 ComparePassword 对两者输入同一明文都返回 nil，因为盐就编码在哈希串内部（$2a$10$盐22字符+哈希31字符），比对时从串里取出盐重算。

常见坑（新手 100% 会踩）

坑现象正确姿势
ComparePassword 参数写反密码明明正确却返回 error，甚至 panic 日志里出现 illegal hash format顺序是 (hashedPassword, password)——库里存的在前，用户输入的在后
把哈希结果当 bool 用if bcrypt.ComparePassword(...) 编译不过或逻辑反它返回 error：err == nil 才是密码正确
password 列只给 varchar(20)插入 $2a$10$... 60 字符哈希时被截断，之后永远比对失败列长度 ≥ 60（推荐 72），bcrypt 输入上限也恰好是 72 字节
json 序列化带出密码字段接口返回里出现 "password":"$2a$10$..."模型 tag 写 json:"-"，或单独定义不含密码的 UserOut DTO
登录失败提示区分太细「该用户不存在」+「密码错误」两种话术统一「用户名或密码错误」，防枚举

今日名词卡

术语一句话解释
哈希（hash）单向摘要函数，只能正算不能反算，同输入必同输出
盐（salt）混入哈希的随机串，让相同密码产生不同结果，逐用户随机
彩虹表提前算好的「哈希 → 明文」巨表，专治不加盐的 md5/sha1
撞库拿 A 站泄露的账号密码去 B 站批量尝试，密码复用的最大风险
costbcrypt 的工作因子，实际轮数为 2^cost，越大越慢越安全
