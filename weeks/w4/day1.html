课前须知：给 JS 开发者的两句话

1. 哈希不是加密。加密可以解密，哈希是单向的：bcrypt.GenerateFromPassword([]byte("123456"), ...) 出来的那串永远还原不出 "123456"。所以登录校验不能「解密比对」，只能把用户输入的密码用同样算法再算一次去比对。

2. 数据库泄露是常态不是意外。设计存储方案时要假设「有一天拖库了」：只要库里没有明文、也没有可逆的密文，用户就是安全的。这就是只存哈希的理由。

知识讲义

1. 为什么明文不行、md5 也不行

方案死法真实案例
明文存储拖库 = 全站密码直接泄露，用户在其他网站同密码被连锅端（撞库）各类「账号密码裸奔」新闻，年年有
纯 md5 / sha1哈希速度快到 GPU 每秒可算数百亿次，可暴力穷举；常见密码的哈希早被算好收录成彩虹表，查表几秒还原2011 年 CSDN 600 万账号 md5 被撞开大半
md5 + 固定盐代码泄露后全体用户盐相同，仍可一次建表打全站不少早期 PHP 项目
bcrypt（自动逐用户加盐 + 可调慢哈希）✅ 当前推荐下限今天的主角

关键直觉：校验密码就应该慢。用户登录多等 100ms 毫无感知，攻击者穷举一亿次就要多等十几天。md5 的问题恰恰是「太快了」。

2. bcrypt 原理一句话 + API

bcrypt = 为密码设计的慢哈希：每个用户自动生成随机盐（同一密码两次注册哈希值不同，彩虹表失效），cost 参数控制计算轮数（2 的 cost 次方，可调到跟硬件一起变慢）。

shell$ go get golang.org/x/crypto/bcrypt
hash_demo.gopackage main

import (
    fmt
    log

    "golang.org/x/crypto/bcrypt"
)

func main() {
    // 注册时：明文 -> 哈希。cost 建议 10~12，bcrypt.DefaultCost 当前就是 10
    hashed, err := bcrypt.GenerateFromPassword([]byte("MyPassw0rd!"), bcrypt.DefaultCost)
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println(string(hashed))
    // $2a$10$N9qo8uLOickgx2ZMRZoMye...  前缀里就带着算法版本和 cost

    // 登录时：注意参数顺序是 (哈希, 明文)，返回 error 而不是 bool！
    err = bcrypt.CompareHashAndPassword(hashed, []byte("MyPassw0rd!"))
    fmt.Println("对了:", err == nil)       // true

    err = bcrypt.CompareHashAndPassword(hashed, []byte("wrong"))
    fmt.Println("错了:", err != nil)       // true，err 为 bcrypt.ErrMismatchedHashAndPassword
}

两处最容易翻车的细节：① CompareHashAndPassword(hashedPassword, password) 哈希在前、明文在后，写反了永远比不中且报错；② 它用 error 表达「不匹配」，判断要写 err == nil 表示密码正确，别 if err != nil { 登录成功 } 把逻辑整个反了。

3. 先把 User 模型补齐（顺便治一治 struct tag）

第 3 周建好的 users 表本周继续沿用，今天是「加字段语义」而不是「换表」。密码列存 bcrypt 结果，长度按算法上限 72 给；username 用 uniqueIndex（第 3 周 GORM 的老朋友）：

internal/model/user.gopackage model

import "gorm.io/gorm"

// gorm.Model = ID uint + CreatedAt + UpdatedAt + DeletedAt（自带软删除）
// 所以下面不用再手写 ID 字段，user.ID 的类型是 uint——这点第 6 节登录返回值会用到
type User struct {
    gorm.Model

    Username string `gorm:"type:varchar(32);uniqueIndex;not null" json:"username"`
    Nickname string `gorm:"type:varchar(32)" json:"nickname"`
    Email    string `gorm:"type:varchar(128);uniqueIndex" json:"email"`
    Password string `gorm:"type:varchar(72);not null" json:"-"` // json:"-" 永远不把哈希序列化出去

    Articles []Article `gorm:"foreignKey:UserID" json:"articles,omitempty"`
}

struct tag 前后必须是一对反引号（ ` ），不是双引号。写成 Username string gorm:"uniqueIndex" json:"username"（少了两个反引号）会当场编译失败：syntax error: unexpected name gorm in struct type; possibly missing semicolon or newline or }。Go 的反引号是「原始字符串」——里面的 " 不用转义，正好适合装 tag；JS 模板字符串也用反引号，但那是能插值的另一回事，别混。

shell$ go build ./...        # 没有任何输出 = 编译通过（Go 的"沉默即成功"）
$ # 若报 unexpected name gorm，就逐行检查上面四条 tag 的反引号

字段 tag 的作用≈装饰器：TS/JS 里你写 @Column({ length: 32 })（TypeORM）或给 zod 传 schema；Go 没有装饰器，语言把「给结构体字段挂元数据」做成了语法的一部分——两个紧跟类型之后的字符串字面量，GORM 读 gorm:、encoding/json 读 json:。同一份 tag，两个不同的库各自解析自己那一段。

两个刻意的取舍：① Role 字段本周没有，它是第 7 周迁移 000002_add_role_to_users 才加进来的列，第 8 周才正式讲 RBAC——提前加只会让今天的 token 里出现没人消费的字段。② 注册接口收 username + password（必填）外加选填的 email 与 nickname。不填 email 时 GORM 的 Create 会跳过零值字段，于是 email 列写进去是 NULL；MySQL 的唯一索引允许多行 NULL（但不允许多行空字符串 ''），所以现在多注册几个不带邮箱的用户不会撞 users.email 索引——第 6 周前端注册页开始收 email 之后，这条索引才真正开始起作用（真填了重复邮箱会撞它，第 5 节把这件事也翻译成了业务码）。

5. 注册接口：service 层完整定义

先把 AuthService 这个类型本身立起来——它依赖repository 接口而不是 *gorm.DB（第 3 周的分层纪律：service 层不出现 *gorm.DB，否则接口白设计了），另外收两把 JWT 密钥（明天签发 token 用，今天先占好位）：

internal/repository/user.go（W3 已有这个文件，今天动两处）// ① 接口：前六个方法是第 3 周那份契约，签名一个字节都不改，今天只加最后这一行
type UserRepository interface {
    List() ([]model.User, error)
    Get(id uint) (model.User, error)
    Create(u model.User) (model.User, error)
    Update(u model.User) error
    Delete(id uint) error
    ExistsUsername(username string) (bool, error)

    ByUsername(username string) (model.User, error) // ← ② 今天新加：登录按用户名找人
}

// 实现补十行，形状照抄第 3 周的 Get（返回 W3 就有的 ErrUserNotFound，handler 才分得清 404 与 500）
func (r *gormUserRepo) ByUsername(username string) (model.User, error) {
    var u model.User
    err := r.db.Where("username = ?", username).First(&u).Error
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return model.User{}, ErrUserNotFound
    }
    if err != nil {
        return model.User{}, err
    }
    return u, nil
}

为什么新方法跟着返回 model.User 而不是 *model.User：第 3 周整条契约用的都是值语义（Get(id uint) (model.User, error)、Create(u model.User) (model.User, error)），ByUsername 只要风格不一致，接口里就出现两套取对象的写法，第 5 天的假仓储还得跟着写两份。JS 里传对象天然是引用，没有值/指针这层区别；最接近的心智模型是 structuredClone()——Get 还你的是一份拷贝，改它不会碰到库里的数据；只有 Create 内部把 &u 交给 GORM，为的是让数据库把自增 ID 回填进这个对象，再由返回值带出来。

internal/service/auth.gopackage service

import (
    "errors"
    "regexp"
    "strings"

    "golang.org/x/crypto/bcrypt"

    "goblog/internal/model"
    "goblog/internal/repository"
)

// 四个哨兵错误：handler 用 errors.Is 把它们翻译成 400 / 409 / 409 / 401
// 变量名 Err + 名词，是 Go 社区给「业务错误」的固定命名法
var (
    ErrWeakPassword  = errors.New("密码至少 8 位，且包含字母和数字")
    ErrUsernameTaken = errors.New("用户名已存在")
    ErrEmailTaken    = errors.New("该邮箱已被注册") // email 是选填，但填了就要吃 users.email 唯一索引
    ErrBadCredential = errors.New("用户名或密码错误")
)

// AuthService 只依赖仓储接口 + 两把 JWT 密钥（第 2 天签发 token 用）
// 两把密钥：access 与 refresh 各用一把不同的，泄露一把不等于两把全废
type AuthService struct {
    users         repository.UserRepository
    accessSecret  string
    refreshSecret string
}

func NewAuthService(users repository.UserRepository, accessSecret, refreshSecret string) *AuthService {
    return &AuthService{users: users, accessSecret: accessSecret, refreshSecret: refreshSecret}
}

// Register 校验 -> 哈希 -> 落库；用户名/邮箱重复交给数据库唯一索引兜底
// email、nickname 是选填：handler 里不 binding:"required"，空串传进来照样能注册
func (s *AuthService) Register(username, password, email, nickname string) (*model.User, error) {
    if !passwordStrong(password) {
        return nil, ErrWeakPassword
    }
    hashed, err := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
    if err != nil {
        return nil, err
    }
    u := model.User{Username: username, Password: string(hashed), Email: email, Nickname: nickname}
    created, err := s.users.Create(u)      // 第 3 周的 Create 收值、返值：自增 ID 从这个返回值里出来，最后一行 &created 交出去
    if err != nil {
        switch {
        case isDuplicateOn(err, "username"):
            // MySQL: Error 1062 (23000): Duplicate entry 'xxx' for key 'users.username'
            return nil, ErrUsernameTaken
        case isDuplicateOn(err, "email"):
            return nil, ErrEmailTaken
        }
        return nil, err
    }
    return &created, nil // created.ID 已被 GORM 回填（uint），第 9 节的 /users/me 与明天的 token 都吃它
}

// isDuplicateOn：把「撞了哪个唯一索引」这件事从数据库方言里抽出来。
// MySQL 报 1062 时原文形如 Duplicate entry 'x' for key 'users.username'；
// 第 5 天测试用的 sqlite 报 UNIQUE constraint failed: users.username——两种文案都含 users.username，
// 所以一次 Contains 同时认下两种方言
func isDuplicateOn(err error, index string) bool {
    if err == nil {
        return false
    }
    msg := err.Error()
    if !strings.Contains(msg, "1062") && !strings.Contains(msg, "UNIQUE constraint failed") {
        return false
    }
    return strings.Contains(msg, "users."+index)
}

var (
    hasLetter = regexp.MustCompile(`[A-Za-z]`)
    hasDigit  = regexp.MustCompile(`[0-9]`)
)

func passwordStrong(p string) bool {
    return len(p) >= 8 && hasLetter.MatchString(p) && hasDigit.MatchString(p)
}

这条策略为什么长这样（全站唯一的密码口径）：只卡长度，12345678 会过；只卡「含字母」，password 会过。len(p) >= 8 + hasLetter + hasDigit 三个条件同时命中才算强，是「撞库脚本第一轮字典」的最低门槛。两个细节：① len() 数的是字节，一个中文字 3 字节，所以中文密码在长度上天然占便宜——本周不为此加复杂度；② 正则字面量 `[A-Za-z]` 用反引号包，和 struct tag 一样是原始字符串，不需要写 "[A-Za-z]" 再转义。

四个同为 string 的参数是个体力活：Register(username, password, email, nickname string) 里把后两个写反，编译器一声不吭，只有肉眼能查。今天靠「调用点只有 handler 一处 + 参数名与 JSON 键同名」压住风险；等第 6 周注册页再加字段（验证码、昵称必填），就把它收进 dto.RegisterReq 结构体——第 3 周的 dto 包就是为这种时刻准备的。

构造函数返回指针（*AuthService）是 Go 后端的常规姿势：结构体是「对象」，指针是「引用」，方法挂在指针接收者上才不会每次调用都拷贝一份。对照 JS：你 new AuthService(...) 拿到的一直是引用，Go 得把「引用」显式写成 *。

为什么靠数据库而不是先 SELECT 查一次再插入？「先查后插」在并发下两个请求可能同时通过检查。唯一索引是最后一道也最可靠的一道防线，应用层只需把 1062 翻译成 code:1006 用户名已存在 这样的业务码。

6. 登录接口：统一提示防枚举

internal/service/auth.go（接上一段，同一个文件）// 一个固定的假哈希，仅用于"用户不存在"时空跑一次 bcrypt 拉齐耗时
var fakeHash = []byte("$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy")

// Login 校验通过返回用户 ID（明天再发 token，今天先返回 nil error）
// 返回类型是 uint：和 model.User 的 ID（gorm.Model 给的 uint）严格一致，
// 写成 int64 会在明天签发 token 时被迫到处转换
func (s *AuthService) Login(username, password string) (uint, error) {
    user, err := s.users.ByUsername(username)
    if err != nil {
        if errors.Is(err, repository.ErrUserNotFound) {
            // 故意不暴露"用户不存在"——否则攻击者拿它当用户名探测仪
            bcrypt.CompareHashAndPassword(fakeHash, []byte(password)) // 空跑一次拉齐耗时，返回的 error 故意不用
            return 0, ErrBadCredential
        }
        return 0, err // 数据库真挂了，走 500
    }
    if bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(password)) != nil {
        return 0, ErrBadCredential // 同样的话术，同样的 error
    }
    return user.ID, nil // user.ID 类型 uint，与返回值一致
}

防枚举：「用户不存在」和「密码错误」如果返回不同提示（甚至不同响应时间），攻击者就能批量探测哪些用户名注册过。统一成一句「用户名或密码错误」，进阶做法如上——用户不存在时也拿一个假哈希空跑一次 bcrypt，把两条路径耗时拉齐。今天做到提示统一即可，耗时对齐了解原理就行。

为什么 service 里不出现 gorm.ErrRecordNotFound：数据库方言的「没查到」应该在 repository 层翻译成业务错误 ErrUserNotFound（第 3 周 D2 就是这个分工）。service 只认业务错误，第 5 天换成内存假仓储时这段逻辑一行都不用改。

7. handler 层接线

先把 AuthHandler 这个类型立起来。构造函数参数今天定型、后面几天不再改：service + 两把密钥（第 4 天再加 logger，第 5 天的测试就照这个签名传参）：

internal/handler/auth.gopackage handler

import (
    "errors"
    "net/http"

    "github.com/gin-gonic/gin"

    "goblog/pkg/response"
    "goblog/internal/repository"
    "goblog/internal/service"
)

// AuthHandler 收 service + 两把 JWT 密钥。
// 今天两把密钥还用不上（明天签发 token 才用），但签名先定下来，后面几天不用改调用方
type AuthHandler struct {
    svc           *service.AuthService
    accessSecret  string
    refreshSecret string
}

func NewAuthHandler(svc *service.AuthService, accessSecret, refreshSecret string) *AuthHandler {
    return &AuthHandler{svc: svc, accessSecret: accessSecret, refreshSecret: refreshSecret}
}

func (h *AuthHandler) Register(c *gin.Context) {
    var req struct {
        Username string `json:"username" binding:"required,min=3,max=32"`
        Password string `json:"password" binding:"required,max=64"`   // max=64 兜住 bcrypt 的 72 字节上限（第 10 节小题①）；强度规则留给 service
        Email    string `json:"email" binding:"omitempty,email,max=128"`  // 选填：不传也照样注册
        Nickname string `json:"nickname" binding:"omitempty,max=32"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数错误")
        return
    }
    u, err := h.svc.Register(req.Username, req.Password, req.Email, req.Nickname)
    if err != nil {
        switch {
        case errors.Is(err, service.ErrWeakPassword):
            response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, err.Error())
        case errors.Is(err, service.ErrUsernameTaken):
            response.Fail(c, http.StatusConflict, response.CodeUsernameTaken, "用户名已存在")
        case errors.Is(err, service.ErrEmailTaken):
            response.Fail(c, http.StatusConflict, response.CodeUsernameTaken, err.Error())
        default:
            response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务器开小差了")
        }
        return
    }
    response.Created(c, gin.H{"user": u}) // 201；data.user 里没有 password（json:"-"）
}

为什么 binding:"required" 之外还要在 service 里再校验一次密码强度？binding 管「字段在不在、格式粗不粗」（这里 max=64 就是粗筛），业务规则（长度 + 字母 + 数字的组合）写在 service。这样第 5 天直接调 svc.Register(...) 的单元测试不用起 HTTP 也能覆盖强度分支。选填字段的正确写法是 omitempty：只写 binding:"email" 的话，不传邮箱的请求会被判成格式错；加 omitempty, 才是「没填就跳过这条规则」。邮箱撞车与用户名撞车是两个不同的唯一索引，所以分开报：同一个 409 里 ErrUsernameTaken 给「用户名已存在」、ErrEmailTaken 给「该邮箱已被注册」——全站码表没有「邮箱重复」这一项，就复用 1006 这个「唯一冲突」码、只把 message 换成邮箱口径，前端按 message 展示即可（第 6 周 http.js 只判 code !== 0，不受影响）。

internal/handler/auth.go（接上，Login）func (h *AuthHandler) Login(c *gin.Context) {
    var req struct {
        Username string `json:"username" binding:"required"`
        Password string `json:"password" binding:"required"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数错误")
        return
    }
    userID, err := h.svc.Login(req.Username, req.Password)
    if err != nil {
        if errors.Is(err, service.ErrBadCredential) {
            response.Fail(c, http.StatusUnauthorized, response.CodeBadPassword, "用户名或密码错误")
            return
        }
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务器开小差了")
        return
    }
    // 今天只回 user_id；明天在这里换成 access_token + refresh_token
    response.OK(c, gin.H{"user_id": userID})
}

internal/service/auth.go（再接一段）// Me：拿 token 里解出来的 userID 去查当前用户（Get 是第 3 周的老方法，不用新写）
func (s *AuthService) Me(userID uint) (*model.User, error) {
    if userID == 0 {
        return nil, ErrBadCredential // 没有身份，交给 handler 统一走 401
    }
    u, err := s.users.Get(userID)     // Get 返值，所以这里要落到局部变量再取地址
    if err != nil {
        return nil, err           // ErrUserNotFound 原样上抛，handler 翻成 404 + 1001
    }
    return &u, nil
}
internal/handler/auth.go（再接一段）func (h *AuthHandler) Me(c *gin.Context) {
    userID := c.GetUint("userID")   // ← 明天 Auth 中间件里 c.Set("userID", claims.UserID) 之后才有值
    if userID == 0 {                // 没挂中间件 / 没登录：GetUint 返回零值 0，而不是 panic
        response.Fail(c, http.StatusUnauthorized, response.CodeTokenInvalid, "未登录")
        return
    }
    u, err := h.svc.Me(userID)
    if err != nil {
        if errors.Is(err, repository.ErrUserNotFound) {
            response.Fail(c, http.StatusNotFound, response.CodeUserNotFound, "用户不存在")
            return
        }
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务器开小差了")
        return
    }
    response.OK(c, gin.H{"user": u})  // 第 6 周前端 fetchMe() 就吃 data.user
}

10. 延伸两个必答小题

① 为什么 bcrypt 密码上限是 72 字节？算法内部把口令按 72 字节分块进 Expensive Key Setup，超出的部分被静默丢弃——意味着「前 72 字节相同、后段不同」的两个密码会被判为同一个。实践：注册校验限制最大长度（如 64），超长直接拒绝而不是截断——第 7 节 DTO 里那句 binding:"required,max=64" 就是它，超长请求会拿到 400 + {"code":1004,"message":"参数错误"}。

② 为什么今天登录成功还只回 user_id、不发 token？凭证方案是明天的主角。今天把「密码对不对」这一步做扎实，明天只需在 Login 成功后追加两行签发调用——分层推进，每天只炸一个新变量。

顺手成本对比一下：bcrypt cost=10 单次哈希约 60–100ms。注册/登录是低频操作，用户无感；但如果你有「每秒几百次校验密码」的内部接口，就要换 argon2 或降低 cost 并重新评估威胁模型——慢是武器，也是负载，知道自己在权衡什么。

常见坑（新手 100% 会踩）

坑现象正确姿势
struct tag 忘了反引号syntax error: unexpected name gorm in struct type，一行报错连带整包编译失败tag 是反引号包起来的原始字符串：`gorm:"..." json:"..."`；从讲义复制时别被编辑器把反引号替换成中文引号
CompareHashAndPassword 参数写反密码明明正确却返回 error，甚至 panic 日志里出现 illegal hash format顺序是 (hashedPassword, password)——库里存的在前，用户输入的在后
把哈希结果当 bool 用if bcrypt.CompareHashAndPassword(...) 编译不过或逻辑反它返回 error：err == nil 才是密码正确
password 列只给 varchar(20)插入 $2a$10$... 60 字符哈希时被截断，之后永远比对失败列长度 ≥ 60（本项目给 72），bcrypt 输入上限也恰好是 72 字节
Login 返回 int64、ID 是 uint明天签发 token 时 jwtutil.NewAccessToken(secret, user.ID) 报 cannot use user.ID (variable of type uint) as int64 value全站 ID 统一 uint：Login(username, password string) (uint, error)
json 序列化带出密码字段接口返回里出现 "password":"$2a$10$..."模型 tag 写 json:"-"，或单独定义不含密码的 UserOut DTO
登录失败提示区分太细「该用户不存在」+「密码错误」两种话术统一「用户名或密码错误」，防枚举
给 service 直接传 *gorm.DB编译能过、当天能跑，但第 5 天写测试时无法替换成假仓储，分层前功尽弃NewAuthService(users repository.UserRepository, accessSecret, refreshSecret string)——只收接口

今日名词卡

术语一句话解释
哈希（hash）单向摘要函数，只能正算不能反算，同输入必同输出
盐（salt）混入哈希的随机串，让相同密码产生不同结果，逐用户随机
彩虹表提前算好的「哈希 → 明文」巨表，专治不加盐的 md5/sha1
撞库拿 A 站泄露的账号密码去 B 站批量尝试，密码复用的最大风险
costbcrypt 的工作因子，实际轮数为 2^cost，越大越慢越安全
用户名枚举攻击者通过差异化报错探测某账号是否注册过，统一提示即可缓解
哨兵错误（sentinel error）service 包里 var ErrXxx = errors.New(...) 导出的固定错误值，handler 用 errors.Is 认它
值语义仓储第 3 周的 Get/Create 收的是值、返的也是值：「没这个人」由 ErrUserNotFound 表达，nil 不属于仓储层；*model.User 只出现在 service 层的返回值里，为的是失败时能同时交出 nil + error，handler 只判 err != nil 就够
