项目分层

前三天的代码全堆在 main.go 里，500 行时就会变成意大利面。今天把主线项目重构进 handler → service → repository 三层结构——这是 Go 后端团队的通用布局，第 3 周接数据库时只需要换掉 repository 一层，其余代码原封不动。这就是分层的复利。

今日目标

↑ 这五条是「学习目标」，学的过程中随时回来勾；页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

课前须知：你为什么已经会分层了

把 React 项目倒过来看。页面组件（收 props、渲染）≈ handler；自定义 hooks / store 里的业务动作（校验、组合调用）≈ service；src/api/request.js 封装（只管发请求、拿数据）≈ repository。你写过的「组件不直接 fetch，走 api 层」的直觉，在这里 1:1 平移：handler 不碰数据存取，repository 不认识 HTTP。

Go 编译器强制包之间不允许循环依赖——A 引 B、B 又引 A 直接编译失败。所以今天不是「学习最佳实践」，是「不了解规则就写不编译」。

知识讲义

1. 三层各干什么

层职责绝对不做前端类比
handler解析参数/DTO 绑定、调 service、把结果/错误写成统一响应不写业务规则、不碰存储路由级页面组件：收参、渲染
service业务规则：重名检查、默认值、跨仓库编排、返回 error不 import gin（没有 *gin.Context！）hooks / store action：纯业务
repository数据的增删改查（今天是 map，第 3 周换 GORM）不判断 HTTP 状态码、不打印响应src/api 请求封装层
model数据结构定义，被所有层引用不 import 任何其他内部包types/ + zod schema

数据旅行路线（一次请求来回）：

textHTTP 请求
  → handler   ShouldBindJSON 得到 DTO
  → service   业务检查，DTO 转 model
  → repositorymap 存取，返回 model 或 error
  ← service   原样上抛 error（或包装）
  ← handler   error → HTTP 状态码 + 业务 code；model → response.OK
HTTP 响应 {code, message, data}

2. 目录结构与依赖方向

treegin-api/
├── go.mod                       # module gin-api
├── cmd/server/main.go           # 唯一入口：组装依赖 + 启动（cmd/xxx = 可执行程序的惯例位置）
├── internal/                    # 私有代码：别的模块 import 不到，Go 编译器强制
│   ├── model/                   # User、Article、DTO
│   ├── repository/              # 内存仓库（map + RWMutex）
│   ├── service/                 # 业务规则
│   ├── handler/                 # gin handler + 路由注册
│   └── middleware/              # 昨天的 CORS/Timer/Auth 搬进来
└── pkg/response/                # 与前两天一致的统一响应

依赖只能从上往下单向指：handler → service → repository → model。箭头反了（比如 repository 想调 service）就是 import cycle。记住口诀：下层不知道上层存在——repository 根本不知道谁在用它，所以它才能同时被 HTTP、CLI、定时任务复用。

3. model 层

internal/model/user.gopackage model

import "time"

// User 是领域模型：对外输出时 Password 因 `json:"-"` 永远不会泄漏
type User struct {
    ID        int      `json:"id"`
    Username  string   `json:"username"`
    Email     string   `json:"email"`
    Password  string   `json:"-"` // 第 4 周换成 bcrypt 哈希后依然不输出
    Role      string   `json:"role"`
    CreatedAt time.Time `json:"created_at"`
}

// CreateUserDTO 入参形状与存储形状分离——两者不必互相迁就
type CreateUserDTO struct {
    Username string `json:"username" binding:"required,min=3,max=20"`
    Email    string `json:"email" binding:"required,email"`
    Password string `json:"password" binding:"required,min=8"`
    Role     string `json:"role" binding:"omitempty,oneof=user admin"`
}

4. repository 层：map + RWMutex

Gin 每个请求跑在独立 goroutine 里，map 并发读写会直接让进程崩溃（fatal error: concurrent map writes，连 Recovery 都拦不住）。必须加锁；读多写少用 RWMutex（读读并行，写独占）：

internal/repository/user_repo.gopackage repository

import (
    "errors"
    "sync"

    "gin-api/internal/model"
)

// ErrUserNotFound 哨兵错误：service/handler 用 errors.Is 识别，第 3 周换成 GORM 后语义不变
var ErrUserNotFound = errors.New("用户不存在")

type UserRepo struct {
    mu     sync.RWMutex
    nextID int
    users  map[int]model.User
}

func NewUserRepo() *UserRepo {
    return &UserRepo{nextID: 1, users: make(map[int]model.User)}
}

func (r *UserRepo) Create(u model.User) model.User {
    r.mu.Lock()
    defer r.mu.Unlock() // defer 保证任何 return 路径都解锁，比 JS 的 try/finally 更顺手
    u.ID = r.nextID
    r.nextID++
    r.users[u.ID] = u
    return u
}

func (r *UserRepo) List() []model.User {
    r.mu.RLock()
    defer r.mu.RUnlock()
    out := make([]model.User, 0, len(r.users))
    for _, u := range r.users { // map 遍历无序，第 3 周 ORDER BY id 解决
        out = append(out, u)
    }
    return out
}

func (r *UserRepo) Get(id int) (model.User, error) {
    r.mu.RLock()
    defer r.mu.RUnlock()
    u, ok := r.users[id]
    if !ok {
        return model.User{}, ErrUserNotFound
    }
    return u, nil
}

func (r *UserRepo) Update(u model.User) error {
    r.mu.Lock()
    defer r.mu.Unlock()
    if _, ok := r.users[u.ID]; !ok {
        return ErrUserNotFound
    }
    r.users[u.ID] = u
    return nil
}

func (r *UserRepo) Delete(id int) error {
    r.mu.Lock()
    defer r.mu.Unlock()
    if _, ok := r.users[id]; !ok {
        return ErrUserNotFound
    }
    delete(r.users, id)
    return nil
}

哨兵错误定义在 repository 包里、由上层 import 使用，方向仍是上层 → 下层，不产生循环。若哪天 service 想「不认识 repository」，就把错误再下沉到 model 包——依赖永远指向稳定的底层。

5. service 层：业务规则的家

internal/service/user_service.gopackage service

import (
    "errors"
    "fmt"
    "time"

    "gin-api/internal/model"
    "gin-api/internal/repository"
)

type UserService struct {
    repo *repository.UserRepo
}

func NewUserService(repo *repository.UserRepo) *UserService {
    return &UserService{repo: repo}
}

func (s *UserService) Create(dto model.CreateUserDTO) (model.User, error) {
    for _, u := range s.repo.List() { // 业务规则 1：用户名不许重复
        if u.Username == dto.Username {
            return model.User{}, fmt.Errorf("用户名 %q 已被占用", dto.Username)
        }
    }
    role := dto.Role          // 业务规则 2：角色缺省为 user
    if role == "" { role = "user" }
    return s.repo.Create(model.User{
        Username: dto.Username, Email: dto.Email,
        Password: dto.Password, Role: role, CreatedAt: time.Now(),
    }), nil
}

func (s *UserService) Get(id int) (model.User, error)   { return s.repo.Get(id) }
func (s *UserService) List() []model.User                 { return s.repo.List() }
func (s *UserService) Update(u model.User) error          { return s.repo.Update(u) }
func (s *UserService) Delete(id int) error                { return s.repo.Delete(id) }

// IsNotFound 给 handler 用的判断助手，handler 不必直接依赖 repository
func IsNotFound(err error) bool { return errors.Is(err, repository.ErrUserNotFound) }

6. handler 层与 main.go 组装

internal/handler/user_handler.gopackage handler

import (
    "net/http"
    "strconv"

    "github.com/gin-gonic/gin"

    "gin-api/internal/model"
    "gin-api/internal/service"
    "gin-api/pkg/response"
)

type UserHandler struct { svc *service.UserService }

func NewUserHandler(svc *service.UserService) *UserHandler { return &UserHandler{svc: svc} }

// Register 把该资源的全部路由收在 handler 自己身上，main.go 只调一行
func (h *UserHandler) Register(r *gin.RouterGroup) {
    r.GET("/users", h.List)
    r.POST("/users", h.Create)
    r.GET("/users/:id", h.Get)
    r.PUT("/users/:id", h.Update)
    r.DELETE("/users/:id", h.Delete)
}

func (h *UserHandler) List(c *gin.Context) { response.OK(c, h.svc.List()) }

func (h *UserHandler) Create(c *gin.Context) {
    var dto model.CreateUserDTO
    if err := c.ShouldBindJSON(&dto); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数不合法: "+err.Error())
        return
    }
    u, err := h.svc.Create(dto)
    if err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, err.Error())
        return
    }
    response.Created(c, u)
}

func (h *UserHandler) Get(c *gin.Context) {
    id, err := strconv.Atoi(c.Param("id"))
    if err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "id 必须是数字")
        return
    }
    u, err := h.svc.Get(id)
    if service.IsNotFound(err) { // ← 错误码 1001 接入点：HTTP 404 + 业务 1001 双层
        response.Fail(c, http.StatusNotFound, response.CodeUserNotFound, "用户不存在")
        return
    }
    if err != nil {
        response.Fail(c, http.StatusInternalServerError, 5000, "服务繁忙")
        return
    }
    response.OK(c, u)
}
cmd/server/main.gopackage main

import (
    "github.com/gin-gonic/gin"

    "gin-api/internal/handler"
    "gin-api/internal/repository"
    "gin-api/internal/service"
)

func main() {
    // 组装依赖：repo → service → handler，从下往上 new（手工依赖注入，Go 圈主流做法）
    userRepo := repository.NewUserRepo()
    userSvc := service.NewUserService(userRepo)
    userH := handler.NewUserHandler(userSvc)

    r := gin.New()
    r.Use(gin.Logger(), gin.Recovery()) // 昨天的 CORS/Timer 也挂这里
    api := r.Group("/api/v1")
    userH.Register(api)

    r.Run(":8080")
}

注意 main.go 在 cmd/server/ 下，启动命令变成 go run ./cmd/server（或编译 go build ./cmd/server）。忘了路径前缀报 no Go files 或在错误目录执行都算新手礼。

练习 1：把 day1–3 的代码重构进分层结构（90 分钟，今天的主菜）

练习 2：GET /users/:id 与 PUT/DELETE 全链路错误码（40 分钟）

要求：访问不存在的 id 返回 HTTP 404 + {"code":1001,"message":"用户不存在","data":null}；PUT 不存在的 id 同样 1001；DELETE 成功返回 {"code":0,...} 且再 GET 变 404。

参考答案：Get 见讲义第 6 节；Update/Delete 照抄其 err 分支模式——if service.IsNotFound(err) { response.Fail(c, http.StatusNotFound, response.CodeUserNotFound, "用户不存在"); return }。体会一下：三个接口共享同一套「错误 → 双层响应」翻译规则，这就是分层的收敛效果。

练习 3：ArticleRepo + ArticleService + ArticleHandler（45 分钟）

要求：为 GET /articles、POST /articles（title 必填 1–50 字、content 必填、author_id 必填且必须真实存在，否则 1001）复制今天的三层模式。

参考答案要点：Article{ID int; Title, Content string; AuthorID int; CreatedAt time.Time}；ArticleService 注入 *ArticleRepo 和 *UserService（跨资源校验靠依赖上层的 service，注意 service → service 单向，不许反向 import）；不存在用户时返回包了 repository.ErrUserNotFound 的错误：fmt.Errorf("作者不存在: %w", err)，handler 里 errors.Is 依旧命中 1001。

练习 4：并发压一压锁（15 分钟）

要求：注释掉 RWMutex 的 Lock/Unlock，用 for i in $(seq 1 50); do curl -s localhost:8080/api/v1/users -o /dev/null & done; wait 并发 GET + 循环 POST，观察 fatal error: concurrent map read and map write；把锁加回来确认消失。这就是第 5 周并发周的预告片。
