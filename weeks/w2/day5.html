知识讲义

1. curl 五件套

参数作用记忆点
-X POST指定 HTTP 方法eXplicit method；GET 可省略
-H "K: V"添加请求头Header，可重复多次
-d '{"a":1}'请求体Data；默认方法变 POST、默认头变 form——测 JSON 务必显式带 Content-Type
-i响应连同状态行和响应头一起打印验证状态码 200/201/400/404 全靠它
-s静默模式，不显示进度条配合 | jq 或 | grep 用
shell# 本周主线项目（/api/v1 前缀 + 统一响应）全套验收命令，逐条执行并截图归档：

# 1) 创建用户：期望 201 + code 0
$ curl -si -X POST localhost:8080/api/v1/users \
  -H "Content-Type: application/json" \
  -d '{"username":"ada","email":"ada@example.com","password":"passw0rd-123"}'

# 2) 用户列表：期望 200 + data 数组
$ curl -s localhost:8080/api/v1/users | jq ".code, (.data | length)"

# 3) 单个用户：期望 200
$ curl -s localhost:8080/api/v1/users/1 | jq

# 4) 更新 / 删除
$ curl -si -X PUT localhost:8080/api/v1/users/1 -H "Content-Type: application/json" -d '{"username":"ada2","email":"a2@example.com","password":"passw0rd-456"}'
$ curl -si -X DELETE localhost:8080/api/v1/users/1

# 5) 文章：查询参数 + 创建
$ curl -s "localhost:8080/api/v1/articles?page=1&size=10" | jq
$ curl -si -X POST localhost:8080/api/v1/articles -H "Content-Type: application/json" -d '{"title":"Go 真香","content":"...","author_id":1}'

没装 jq 就用 python3 -m json.tool 管道美化。URL 里带 & 必须整体加引号（day1 老坑，今天第三次提醒）。

2. 用 curl 验证 CORS 预检

curl 不带 Origin 头时浏览器行为不存在，所以要手动伪装预检：

shell$ curl -si -X OPTIONS localhost:8080/api/v1/users \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST"

# 期望输出：HTTP/1.1 204 No Content，且带：
#   Access-Control-Allow-Origin: http://localhost:5173
#   Access-Control-Allow-Methods: ...POST...
#   Access-Control-Allow-Headers: ...Authorization...

204 却没有 Allow 头 = 你的 CORS 中间件没挂上或注册在路由之后；返回 404 = OPTIONS 漏进了 NoRoute。预检失败时浏览器控制台报的是 CORS 错误，极具误导——先用上面的命令在服务端定位，再怪浏览器。

3. Postman / Apifox 使用要点

  • Collection 结构：一个项目一个集合，内建 Users、Articles 两个文件夹，请求命名「创建用户 201」「用户名过短 400」——名字即用例。
  • 环境变量：Variables 里加 base_url = http://localhost:8080/api/v1，请求写 {{base_url}}/users，换环境只改一处。
  • 断言脚本（Postman Tests / Apifox 后置操作）：放进「成功创建用户」的 Scripts → Post-response：
javascriptpm.test("HTTP 201", () => pm.response.to.have.status(201));
pm.test("业务码 0", () => {
    const j = pm.response.json();
    pm.expect(j.code).to.eql(0);
    pm.expect(j.data.id).to.be.a("number");
    pm.environment.set("user_id", j.data.id); // 存起来给 GET/PUT/DELETE 用 {{user_id}}
});
  • Apifox 加分项：国内网络更顺、支持 Markdown 文档导出与接口调试一体化；概念与 Postman 完全对应（集合→项目、环境→环境变量）。选一个用到底即可。
  • 导出 collection JSON 提交进仓库 docs/ 目录——这就是可交接的测试资产。

5. 三条错误路径的实证

shell# ① 参数错 → 400 + code 1004（username 只有 2 个字符）
$ curl -si -X POST localhost:8080/api/v1/users -H "Content-Type: application/json" \
  -d '{"username":"ab","email":"x","password":"1"}' | head -n 1
HTTP/1.1 400 Bad Request

# ② 资源不存在 → 404 + code 1001
$ curl -si localhost:8080/api/v1/users/99999 | head -n 1
HTTP/1.1 404 Not Found

# ③ panic → Recovery 兜底 500：临时加一条会炸的路由
cmd/server/main.go// 测试专用：模拟 handler 深处的运行时错误（比如空指针）
r.GET("/debug/boom", func(c *gin.Context) {
    var m map[string]int
    m["panic"] = 1 // 向 nil map 写入 → panic
})
shell$ curl -si localhost:8080/debug/boom | head -n 1
HTTP/1.1 500 Internal Server Error
# 关键：终端里 Recovery 打印了完整堆栈，但服务没死——继续 curl /users 仍然正常

500 的 body 默认是 500 Internal Server Error 文本。把它统一成 JSON 需要自定义 Recovery Handler 或 NoRoute 配合——今天的选做练习；第 4 周工程化时给正式版。

把这张五行表打印出来贴在显示器边上——以后每写一个接口，五列各测一次，你的 API 就拥有了和产品级一致的「错误人格」。第 4 周做自动化测试时，这五行会原样变成 httptest 的表驱动用例。

6. 用 echo 服务验证「服务器收到了什么」

怀疑自己的请求头/方法/body 没发对时，拿一个「回显一切」的服务当镜子。两种任选：

shell# 方案 A：公共 httpbin（等价回显服务）
$ curl -s -X POST https://httpbin.org/headers -H "Authorization: Bearer abc" | jq
# 方案 B：给本周项目加一条 /debug/echo，回显 method + headers + raw body
internal/handler/debug_handler.gofunc Echo(c *gin.Context) {
    raw, _ := c.GetRawData()
    response.OK(c, gin.H{
        "method":  c.Request.Method,
        "path":    c.Request.URL.Path,
        "query":   c.Request.URL.RawQuery,
        "headers": c.Request.Header,
        "body":    string(raw),
    })
}

用它反查：Postman 到底有没有替你发 Content-Type？curl -d 默认发了什么头？答案全在回显里。

7. 把 curl 连成脚本：一条命令走完回归测试

接口多了以后，逐条手敲 curl 太累。写一个 scripts/smoke.sh，用 -w "%{http_code}" 只要状态码、用 jq 抽字段串起完整业务流：

scripts/smoke.sh#!/usr/bin/env bash
# 回归冒烟：创建 → 查询 → 更新 → 删除 → 删后再查应 404
BASE="localhost:8080/api/v1"
pass=0; fail=0

# expect <期望状态码> <实际状态码> <用例名>
expect() {
  if [ "$1" = "$2" ]; then echo "✔ $3"; pass=$((pass+1))
  else echo "✘ $3 期望 $1 实得 $2"; fail=$((fail+1)); fi
}

code=$(curl -s -o /tmp/user.json -w "%{http_code}" -X POST "$BASE/users" \
  -H "Content-Type: application/json" \
  -d '{"username":"smoke","email":"s@e.com","password":"passw0rd-123"}')
expect 201 "$code" "创建用户"

uid=$(jq -r ".data.id" /tmp/user.json)          # 从创建响应里取 id，链式传递
code=$(curl -s -o /dev/null -w "%{http_code}" "$BASE/users/$uid")
expect 200 "$code" "查询用户 $uid"

code=$(curl -s -o /dev/null -w "%{http_code}" -X DELETE "$BASE/users/$uid")
expect 200 "$code" "删除用户"

code=$(curl -s -o /dev/null -w "%{http_code}" "$BASE/users/$uid")
expect 404 "$code" "删后再查应 404"

code=$(curl -s -o /dev/null -w "%{http_code}" -X POST "$BASE/users" \
  -H "Content-Type: application/json" -d '{"username":"ab","email":"x","password":"1"}')
expect 400 "$code" "非法参数应 400"

echo "结果: $pass 通过 / $fail 失败"; [ "$fail" = "0" ]
shell$ chmod +x scripts/smoke.sh && ./scripts/smoke.sh
✔ 创建用户
✔ 查询用户 7
✔ 删除用户
✔ 删后再查应 404
✔ 非法参数应 400
结果: 5 通过 / 0 失败

-w "%{http_code}" -o /dev/null 这对组合意思是「丢掉响应体、只吐状态码」——写脚本断言的标配。这个 40 行的 bash 就是第 4 周 httptest 自动化测试的手工前身：思想完全一样（准备请求 → 断言响应），只是换成了 Go 代码。

今日练习

练习 1：curl 全量验收 + 预检实测（45 分钟）

要求：讲义第 1 节的 7 条命令逐条执行，每条把状态行 + body 贴进笔记；再执行第 2 节预检命令，截图三个 Allow 头。

参考答案：无捷径，输出应与讲义注释里的期望一致。对不上的话按「方法 → Content-Type → 路径 → 中间件注册顺序」四步排查。

练习 2：搭建 Postman/Apifox collection（60 分钟）

要求：① 建变量 base_url；② 9 个请求（7 正常 + 2 异常用例「用户名过短 400」「不存在 404」）；③ 创建用户后自动把 data.id 写入变量 user_id，后续 GET/PUT/DELETE 全部使用 {{user_id}}；④ Collection Runner 一键跑全部，绿灯。

参考答案：断言脚本见讲义第 3 节——注意 pm.environment.set 是链条传递 id 的关键，没有它你的 GET /users/1 会在删完后永远 404。

练习 3：README 接口文档页（40 分钟）

要求：在项目 README.md 写：项目简介、启动方式（go run ./cmd/server + curl 预检验证）、讲义第 4 节的接口表格、错误码清单、目录结构树。导出 collection JSON 放进 docs/，git 提交。

参考答案：模板即讲义第 4 节；目录树抄 day4 第 2 节。验收标准：找一个没看过代码的朋友，让他只看 README 把「创建用户 → 查询用户」跑通。

练习 4：/debug/boom 与 500 的 JSON 化（30 分钟）

要求：复现 panic → 500 且服务存活；然后尝试把 500 的响应也变成统一 JSON（提示：用 gin.CustomRecovery(recoveryFunc) 替换默认 Recovery，recoveryFunc 的签名是 func(c *gin.Context, recovered any)，内部直接 c.AbortWithStatusJSON(500, response.Body{Code: 5000, Message: "内部错误", Data: nil})）。

参考答案：见提示，测试完记得删掉 /debug/boom 路由或加鉴权保护——「只有 panic 才长得像 500」也是错误处理设计的一部分。

常见坑（新手 100% 会踩）

坑现象正确姿势
-d 的头陷阱只用 -d 不发 Content-Type，ShouldBindJSON 报 unsupported media type，误以为代码错了测 JSON 永远显式 -H "Content-Type: application/json"，或用 echo 服务（讲义第 6 节）自证
怪浏览器 CORS控制台红字 CORS error，其实服务返回了 500/404预检请求先用 curl -X OPTIONS 在服务端验，Allow 头齐全再看前端
测试数据写死 id删库重启后 id 从 1 开始，旧集合全部 404用 Postman 变量链式传递创建结果，别用爱发电记 id
只看 body 不看状态码“返回 code:1001 了呀！”但 HTTP 是 200——第 6 周前端拦截器直接罢工验收永远 -i 双看：状态码 + 业务 code 同时符合双层约定
panic 测试忘了删/debug/boom 进了生产仓库，人人可炸你的服务日志调试路由用完即删，或放独立 build tag / 加鉴权
