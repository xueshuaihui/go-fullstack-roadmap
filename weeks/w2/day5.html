1. curl 五件套

参数作用记忆点
-X POST指定 HTTP 方法eXplicit method；GET 可省略
-H "K: V"添加请求头Header，可重复多次
-d '{"a":1}'请求体Data；默认方法变 POST、默认头变 application/x-www-form-urlencoded。但本周接口用 ShouldBindJSON，它无视 Content-Type 直接按 JSON 解，所以带不带这个头都能测通（换成 ShouldBind 就会按这个头退回表单解析，见 day2 练习 4）；带上 -H "Content-Type: application/json" 只是为了严谨、给别的绑定器/工具看
-i响应连同状态行和响应头一起打印验证状态码 200/201/400/404 全靠它
-s静默模式，不显示进度条配合 | jq 或 | grep 用
shell# 本周主线项目（/api/v1 前缀 + 统一响应 + day4 的读写分组）全套验收命令，逐条执行并截图归档。
# 口径与 day4 一致：GET 匿名可读，POST/PUT/DELETE 挂在鉴权组，必须带 Bearer token。
# 下面用 shell 变量存 token，避免每条重复敲：
$ AUTH="Authorization: Bearer go-fullstack-2026"

# 1) 创建用户：期望 201 + code 0
$ curl -si -X POST localhost:8080/api/v1/users \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"username":"ada","email":"ada@example.com","password":"passw0rd-123"}'

# 2) 用户列表：期望 200 + data 数组
$ curl -s localhost:8080/api/v1/users | jq ".code, (.data | length)"

# 3) 单个用户：期望 200
$ curl -s localhost:8080/api/v1/users/1 | jq

# 4) 更新 / 删除（本周删除返回 200 + JSON body，不是 W1 的 204，原因见 summary）
$ curl -si -X PUT localhost:8080/api/v1/users/1 -H "$AUTH" -H "Content-Type: application/json" -d '{"username":"ada2","email":"a2@example.com","password":"passw0rd-456"}'
$ curl -si -X DELETE localhost:8080/api/v1/users/1 -H "$AUTH"

# 5) 文章：查询参数 + 创建。注意本周 List 只回显 page/size 并返回全部，真分页第 3 周接 MySQL 时用 OFFSET/LIMIT 才生效
$ curl -s "localhost:8080/api/v1/articles?page=1&size=10" | jq
$ curl -si -X POST localhost:8080/api/v1/articles -H "$AUTH" -H "Content-Type: application/json" -d '{"title":"Go 真香","content":"...","author_id":1}'

# 6) 少带 token：期望 401 + code 1005（证明鉴权组真的生效了）
$ curl -si -X POST localhost:8080/api/v1/users -H "Content-Type: application/json" -d '{"username":"noauth","email":"n@e.com","password":"passw0rd-123"}' | grep -E '^(HTTP|\{)'
HTTP/1.1 401 Unauthorized
{"code":1005,"message":"token 缺失或无效","data":null}

命令里的 grep -E '^(HTTP|\{)' 是干什么的？-i 会把状态行、响应头、空行、body 全打出来，中间那几行头（Date / Content-Length…）看久了反而遮住重点；这条 grep 只留状态行和以 { 开头的 body 行，正好对上"状态码 + 业务码双确认"。不想要它就把 | grep ... 删掉，输出更全。

没装 jq 就用 python3 -m json.tool 管道美化：curl -s localhost:8080/api/v1/users | python3 -m json.tool。URL 里带 & 必须整体加引号（day1 老坑，今天第三次提醒）。写操作忘带 -H "$AUTH" 会先撞 401，而不是你预期的 201/200。

2. 用 curl 验证 CORS 预检

curl 不带 Origin 头时浏览器行为不存在，所以要手动伪装预检：

shell$ curl -si -X OPTIONS localhost:8080/api/v1/users \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST"

# 期望输出：HTTP/1.1 204 No Content，且带：
#   Access-Control-Allow-Origin: http://localhost:5173
#   Access-Control-Allow-Methods: ...POST...
#   Access-Control-Allow-Headers: ...Authorization...

204 却没有 Allow 头 = 你的 CORS 中间件没挂上或注册在路由之后；返回 404 = OPTIONS 漏进了 NoRoute。预检失败时浏览器控制台报的是 CORS 错误，极具误导——先用上面的命令在服务端定位，再怪浏览器。

3. Postman / Apifox 使用要点

  • Collection 结构：一个项目一个集合，内建 Users、Articles 两个文件夹，请求命名「创建用户 201」「用户名过短 400」——名字即用例。
  • 环境变量：Variables 里加 base_url = http://localhost:8080/api/v1，请求写 {{base_url}}/users，换环境只改一处。
  • 断言脚本（Postman Tests / Apifox 后置操作）：放进「成功创建用户」的 Scripts → Post-response：
javascriptpm.test("HTTP 201", () => pm.response.to.have.status(201));
pm.test("业务码 0", () => {
    const j = pm.response.json();
    pm.expect(j.code).to.eql(0);
    pm.expect(j.data.id).to.be.a("number");
    pm.environment.set("user_id", j.data.id); // 存起来给 GET/PUT/DELETE 用 {{user_id}}
});
  • Apifox 加分项：国内网络更顺、支持 Markdown 文档导出与接口调试一体化；概念与 Postman 完全对应（集合→项目、环境→环境变量）。选一个用到底即可。
  • 导出 collection JSON 提交进仓库 docs/ 目录——这就是可交接的测试资产。

500 的响应体默认是空的——官方 gin.Recovery() 兜住 panic 后只调 c.AbortWithStatus(500)，上面 curl -si /debug/boom 的响应头里就是 Content-Length: 0，一个字节都没有。这同样打破了统一响应约定（前端 JSON.parse('') 会抛错）。把它变成 JSON 的完整实现 day3 §3.6 已经给出（middleware.Recovery()，内部写 response.Body{Code: response.CodeInternal, Message: "服务繁忙"}），练习 4 就是把注册那行的 gin.Recovery() 换成它，得到 HTTP 500 + code 5000。第 4 周工程化时给整条中间件链换成 slog 结构化日志并加 request_id（Recovery 就用你换好的这份，不再回头改它）。

第 6 行（405）有两个前置条件，都是 day1 那节「开关型知识点」的延续：① r.HandleMethodNotAllowed = true（Gin 默认 false，不开就是 404 冒充 405）；② 注册了 r.NoMethod（不注册时 Gin 回退纯文本 405 method not allowed，body 里没有 code）。day4 的 cmd/server/main.go 装配里两行都带了。验证：

Allow: GET, PUT, DELETE
{"code":1003,"message":"方法不允许","data":null}
# PATCH 没在 /users/:id 注册过；Gin 会把该路径下其它已注册的方法塞进 Allow 头告诉你

顺带两点从 Gin 源码里能读出来的行为，记下来省得以后再猜：404/405 走的是 engine.combineHandlers(noRoute/noMethod)，里面只有全局中间件（r.Use 的 Logger/Recovery/CORS/Timer），不包含分组中间件——所以这两条请求不需要带 token（带了也照样 405，不会被 RequireAuth 拦成 401），但服务日志里能看到它们的 [timer] 行。

把这张六行表打印出来贴在显示器边上——以后每写一个接口，六列各测一次，你的 API 就拥有了和产品级一致的「错误人格」。第 4 周做自动化测试时，这六行会原样变成 httptest 的表驱动用例。

6. 用本地 echo 镜子验证「服务器到底收到了什么」

怀疑自己的请求头/方法/body 没发对时，拿一个「回显一切」的服务当镜子。本手册正文不依赖 httpbin 之类外部站点（断网、被墙、对方限流都会让你的验收步骤失效），直接给本周项目加一条 /debug/echo 即可。

放在哪里：新建文件 internal/handler/debug_handler.go。一个包一个 package 声明，所以文件头必须写 package handler 和 import，不能只贴一个函数体：

internal/handler/debug_handler.gopackage handler

import (
    "github.com/gin-gonic/gin"

    "gin-api/pkg/response"
)

// Echo 原样回显服务器收到的方法、路径、查询串、全部请求头与原始 body。
// 注册在 r 上（不带 /api/v1 前缀、不进鉴权组），因为它只用于本地排查。
func Echo(c *gin.Context) {
    raw, _ := c.GetRawData() // day1 讲过：(body, err) 两返回值，排查场景忽略 error
    response.OK(c, gin.H{
        "method":  c.Request.Method,
        "path":    c.Request.URL.Path,
        "query":   c.Request.URL.RawQuery,
        "headers": c.Request.Header,
        "body":    string(raw),
    })
}
cmd/server/main.go// 在 r.GET("/health", ...) 附近加一行（r.Any = 任意方法都收，方便照 POST/PUT）
r.Any("/debug/echo", handler.Echo)
shell# 只发 -d、故意不给 Content-Type：看 curl 到底替你发了什么头
$ curl -s -X POST localhost:8080/debug/echo -d '{"a":1}' | python3 -m json.tool
{
    "code": 0,
    "message": "ok",
    "data": {
        "body": "{\"a\":1}",
        "headers": {
            "Accept": ["*/*"],
            "Content-Length": ["7"],
            "Content-Type": ["application/x-www-form-urlencoded"],  // ← -d 的默认头，不是 JSON
            "User-Agent": ["curl/8.7.1"]
        },
        "method": "POST",
        "path": "/debug/echo",
        "query": ""
    }
}

两处"和你想的不一样"都是真的：① data 里的键是 body → headers → method → path → query（不是 handler 里的书写顺序），② 每个头的键名也排了序。原因同一个：gin.H 和 c.Request.Header 都是 map，Go 的 encoding/json 序列化 map 固定按键名字典序输出——所以这个顺序每次都稳定，可以放心当参照。版面说明：jq 与 python3 -m json.tool 会把数组元素竖着各占一行（还想看到单行原文就加 jq -c .），上面为省版面并成了一行，键名与值完全一致。没装 jq 就用管道给 Python 自带的 python3 -m json.tool（macOS/Linux 自带 python3；Windows 若命令叫 python 就写 python -m json.tool）。用它反查：Postman 到底有没有替你发 Content-Type？curl -d 默认发了什么头？答案全在回显里。

7. 把 curl 连成脚本：一条命令走完回归测试

接口多了以后，逐条手敲 curl 太累。写一个 scripts/smoke.sh，用 -w "%{http_code}" 只要状态码、用 jq 抽字段串起完整业务流：

scripts/smoke.sh#!/usr/bin/env bash
# 回归冒烟：创建 → 查询 → 更新 → 删除 → 删后再查应 404 → 少带 token 应 401
BASE="localhost:8080/api/v1"
AUTH="Authorization: Bearer go-fullstack-2026"   # day4 的鉴权组要它；写操作忘带就全是 401
pass=0; fail=0

# expect <期望状态码> <实际状态码> <用例名>
expect() {
  if [ "$1" = "$2" ]; then echo "✔ $3"; pass=$((pass+1))
  else echo "✘ $3 期望 $1 实得 $2"; fail=$((fail+1)); fi
}

code=$(curl -s -o /tmp/user.json -w "%{http_code}" -X POST "$BASE/users" \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"username":"smoke","email":"s@e.com","password":"passw0rd-123"}')
expect 201 "$code" "创建用户"

uid=$(jq -r ".data.id" /tmp/user.json)          # 从创建响应里取 id，链式传递
code=$(curl -s -o /dev/null -w "%{http_code}" "$BASE/users/$uid")
expect 200 "$code" "查询用户 $uid"

code=$(curl -s -o /dev/null -w "%{http_code}" -X PUT "$BASE/users/$uid" \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"username":"smoke2","email":"s2@e.com","password":"passw0rd-456"}')
expect 200 "$code" "更新用户"

code=$(curl -s -o /dev/null -w "%{http_code}" -X DELETE "$BASE/users/$uid" -H "$AUTH")
expect 200 "$code" "删除用户"

code=$(curl -s -o /dev/null -w "%{http_code}" "$BASE/users/$uid")
expect 404 "$code" "删后再查应 404"

code=$(curl -s -o /dev/null -w "%{http_code}" -X POST "$BASE/users" \
  -H "$AUTH" -H "Content-Type: application/json" -d '{"username":"ab","email":"x","password":"1"}')
expect 400 "$code" "非法参数应 400"

# 鉴权反例：同一个创建请求去掉 token，必须被中间件先拦下
code=$(curl -s -o /dev/null -w "%{http_code}" -X POST "$BASE/users" \
  -H "Content-Type: application/json" -d '{"username":"noauth","email":"n@e.com","password":"passw0rd-123"}')
expect 401 "$code" "无 token 写操作应 401"

echo "结果: $pass 通过 / $fail 失败"; [ "$fail" = "0" ]
shell$ chmod +x scripts/smoke.sh && ./scripts/smoke.sh
✔ 创建用户
✔ 查询用户 7
✔ 更新用户
✔ 删除用户
✔ 删后再查应 404
✔ 非法参数应 400
✔ 无 token 写操作应 401
结果: 7 通过 / 0 失败

-w "%{http_code}" -o /dev/null 这对组合意思是「丢掉响应体、只吐状态码」——写脚本断言的标配。这个不到 50 行的 bash 就是第 4 周 httptest 自动化测试的手工前身：思想完全一样（准备请求 → 断言响应），只是换成了 Go 代码。没有 jq 时把 uid 那行换成 uid=$(python3 -c 'import json,sys;print(json.load(open("/tmp/user.json"))["data"]["id"])')。

今日练习

练习 1：curl 全量验收 + 预检实测（45 分钟）

要求：讲义第 1 节的 6 组命令逐条执行，每条把状态行 + body 贴进笔记（特别注意：写操作带 token 得 201/200/404，去掉 token 得 401）；再执行第 2 节预检命令，截图三个 Allow 头。

练习 2：搭建 Postman/Apifox collection（60 分钟）

要求：① 建变量 base_url = http://localhost:8080/api/v1 与 auth = Bearer go-fullstack-2026（写操作请求的 Headers 里写 Authorization: {{auth}}，换 token 只改一处）；② 10 个请求（7 正常 + 3 异常用例「用户名过短 400」「不存在 404」「去掉 Authorization 头的创建 401」）；③ 创建用户后自动把 data.id 写入变量 user_id，后续 GET/PUT/DELETE 全部使用 {{user_id}}；④ Collection Runner 一键跑全部，绿灯。

参考答案：断言脚本见讲义第 3 节——注意 pm.environment.set 是链条传递 id 的关键，没有它你的 GET /users/1 会在删完后永远 404。401 那个用例只存在于「故意删掉 Authorization 头」的副本请求里，别把正常的创建请求改坏了。

练习 4：/debug/boom 与 500 的 JSON 化（30 分钟）

要求：复现 panic → 500 且服务存活；再把 500 的响应变成统一 JSON——直接搬 day3 §3.6 那份 middleware/recovery.go，把注册那行的 gin.Recovery() 换成 middleware.Recovery()（想自己写也行：用 gin.CustomRecovery(recoveryFunc) 替换默认 Recovery，recoveryFunc 的签名是 func(c *gin.Context, recovered any)，内部 c.AbortWithStatusJSON(http.StatusInternalServerError, response.Body{Code: response.CodeInternal, Message: "服务繁忙", Data: nil})）。

参考答案（实测两态对照）：换之前 curl -si localhost:8080/debug/boom 是 HTTP/1.1 500 + Content-Length: 0（空 body）；换之后同一命令给出 HTTP/1.1 500 + {"code":5000,"message":"服务繁忙","data":null}，服务依旧接得下下一个请求。测试完记得删掉 /debug/boom 路由或加鉴权保护——「只有 panic 才长得像 500」也是错误处理设计的一部分。

常见坑（新手 100% 会踩）

坑现象正确姿势
以为"Gin 会自动因为头不对而拒绝"只用 -d 时 curl 默认发 Content-Type: application/x-www-form-urlencoded，本周的 ShouldBindJSON 照样按 JSON 解、能通。换成 ShouldBind/Bind 也不会返回 415：Gin 按头分发绑定器，表单类型是兜底分支（binding.Default 的 default 就是 Form），于是同一份 JSON 体被当表单解析，字段全空 → 400 + {"code":1004,"message":"Username 不能为空；Email 不能为空；Password 不能为空","data":null}。想要 415 得自己在 handler 开头判 c.ContentType()（day2 练习 4 的加餐给了写法）测 JSON 永远显式 -H "Content-Type: application/json"（对 Bind/ShouldBind、对 Postman、对别的工具都安全）；拿不准自己发了什么头就用本地 echo 镜子（讲义第 6 节）自证
写操作忘带 Bearer token明明是 400 的用例，实测却返回 401 + code 1005，以为校验器坏了day4 起 POST/PUT/DELETE 都在鉴权组，脚本里统一 AUTH="Authorization: Bearer go-fullstack-2026"，每条写请求都挂 -H "$AUTH"
怪浏览器 CORS控制台红字 CORS error，其实服务返回了 500/404预检请求先用 curl -X OPTIONS 在服务端验，Allow 头齐全再看前端
测试数据写死 id删库重启后 id 从 1 开始，旧集合全部 404用 Postman 变量链式传递创建结果，别用爱发电记 id
只看 body 不看状态码“返回 code:1001 了呀！”但 HTTP 是 200——第 6 周前端拦截器直接罢工验收永远 -i 双看：状态码 + 业务 code 同时符合双层约定
panic 测试忘了删/debug/boom 进了生产仓库，人人可炸你的服务日志调试路由用完即删，或放独立 build tag / 加鉴权
