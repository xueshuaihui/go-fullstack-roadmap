请求绑定与验证

昨天用 GetRawData() 拿到的是裸字节，没法用。今天学 Gin 的杀手锏：一次声明结构体，自动完成「解析 JSON → 校验规则 → 填充字段」三步，并把校验失败翻译成人类可读的 400。同时落地手册「API 设计约定」的 {code, message, data} 统一响应——从今天起，你写的每个接口都长一个样。

课前须知：从 fetch 到 Bind

前端是怎么处理用户输入的？const body = await res.json() 之后要么手写一堆 if (!body.name)，要么上 zod/yup 定义 schema。Gin 的绑定 = 这两件事合体：结构体本身就是 schema，tag 就是校验规则，一次 ShouldBindJSON(&dto) 全做完。

反射的代价。绑定靠 Go 反射逐字段赋值，所以有两条铁律：① 字段必须导出（大写字母开头）；② 想匹配 JSON 里的 user_name 这种蛇形键，必须写 json:"user_name" tag。违反任何一条，绑定结果就是零值且不报错——今天最大的坑。

知识讲义

1. ShouldBindJSON 与 DTO 结构体

DTO（Data Transfer Object）= 专门描述「这个接口接收什么」的结构体，只出现在入参/出参上，不和数据库模型混用：

main.go// CreateUserDTO 描述 POST /users 的请求体
type CreateUserDTO struct {
    Username string `json:"username" binding:"required,min=3,max=20"`
    Email    string `json:"email" binding:"required,email"`
    Password string `json:"password" binding:"required,min=8"`
    Role     string `json:"role" binding:"omitempty,oneof=user admin"` // 可省略，省略则默认 user
}

func createUser(c *gin.Context) {
    var dto CreateUserDTO
    if err := c.ShouldBindJSON(&dto); err != nil {
        // 解析失败或校验失败都走这里，第 3 节把它变成人话
        c.JSON(http.StatusBadRequest, gin.H{"detail": err.Error()})
        return
    }
    // 走到这里 dto 每个字段都合法，放心使用
    c.JSON(http.StatusOK, gin.H{"dto": dto})
}
绑定方法数据来源典型场景
ShouldBindJSON请求体（要求 Content-Type: application/json）POST/PUT 传 JSON
ShouldBindQueryURL 查询参数分页 ?page=1&size=10
ShouldBindUri路径参数/users/:id 的 id 转 int
ShouldBind按 Content-Type 自动选同一 handler 兼容 JSON/表单

前缀 Should 的含义：解析失败只 return err 给你处理；不带 Should 的 c.BindJSON 失败时会直接写 400 响应并 Abort，你连错误消息格式都控制不了。团队项目一律用 Should 系列。

2. binding 校验 tag 速查

tag 由 go-playground/validator 提供，Gin 内置调用。多个规则用逗号串联，从上到下依次校验：

规则含义备注
required不能是零值陷阱：数字 0、bool false、字符串 "" 都算零值，"年龄必填且允许为 0" 不能用它
min=3 / max=20string 按长度、数字按数值、slice 按元素数密码 min=8、昵称 max=20
email基本邮箱格式只查格式，不代表邮箱真实存在
oneof=user admin值必须是列举之一空格分隔，等价前端的枚举白名单
omitempty字段缺省时跳过后续规则配合 oneof 实现「可选枚举」
gte=1 / lte=150大于等于 / 小于等于年龄用 gte=0,lte=150 替代 required
main.gotype ListQuery struct {
    Page int `json:"page" form:"page" binding:"omitempty,gte=1"`
    Size int `json:"size" form:"size" binding:"omitempty,gte=1,lte=100"`
}
// 用法：c.ShouldBindQuery(&q)，URL 传 ?page=2&size=20 即自动转成 int

查询参数的 tag 是 form:"page"（表单/查询键名），JSON body 才是 json:"page"。两个都写上，同一个结构体就能同时服务 query 与 body。

3. 自定义错误消息：把 validator 报错翻译成人话

err.Error() 的默认输出是 Key: 'CreateUserDTO.Email' Error:Field validation for 'Email' failed on the 'email' tag——机器看得懂，用户看不懂。用 errors.As 拿到结构化错误逐条翻译：

main.goimport (
    "errors"
    "strings"

    "github.com/go-playground/validator/v10"
)

// bindErrMsg 把校验错误转成一句中文提示
func bindErrMsg(err error) string {
    var ves validator.ValidationErrors
    if errors.As(err, &ves) {
        msgs := make([]string, 0, len(ves))
        for _, ve := range ves {
            switch ve.Tag() {
            case "required": msgs = append(msgs, ve.Field()+" 不能为空")
            case "min":      msgs = append(msgs, ve.Field()+" 长度不足 "+ve.Param())
            case "max":      msgs = append(msgs, ve.Field()+" 长度超限 "+ve.Param())
            case "email":    msgs = append(msgs, ve.Field()+" 不是合法邮箱")
            case "oneof":    msgs = append(msgs, ve.Field()+" 只能是: "+ve.Param())
            default:          msgs = append(msgs, ve.Field()+" 校验失败("+ve.Tag()+")")
            }
        }
        return strings.Join(msgs, "；")
    }
    return "请求体不是合法 JSON" // 非校验类错误（格式/Content-Type）
}

对比 JS：validator 之于 Go，≈ zod 的 safeParse：result.error.issues 是一条条结构化错误，你决定怎么展示。errors.As 则是 Go 版的 err instanceof ValidationError——上周学的 error 接口今天正式上岗。

4. 统一响应 pkg/response.go：本周约定落地

新建 pkg/response/response.go（目录 pkg/response，包名 response），这是手册「十三、API 设计约定」的代码化：

pkg/response/response.gopackage response

import (
    net/http

    "github.com/gin-gonic/gin"
)

// Body 是全部接口的统一响应结构：{code, message, data}
type Body struct {
    Code    int  `json:"code"`
    Message string `json:"message"`
    Data    any  `json:"data"`
}

// 业务错误码常量：与 HTTP 状态码分两层（见手册第十三节）
const (
    CodeOK           = 0    // 成功
    CodeUserNotFound = 1001 // 用户不存在
    CodeBadPassword  = 1002 // 密码错误
    CodeForbidden    = 1003 // 无权限
    CodeInvalidParam = 1004 // 参数错误
    CodeTokenInvalid = 1005 // token 无效或过期
)

// OK 成功：HTTP 200 + code 0
func OK(c *gin.Context, data any) {
    c.JSON(http.StatusOK, Body{Code: CodeOK, Message: "success", Data: data})
}

// Created 创建成功：HTTP 201 + code 0
func Created(c *gin.Context, data any) {
    c.JSON(http.StatusCreated, Body{Code: CodeOK, Message: "success", Data: data})
}

// Fail 失败：HTTP 状态码反映请求处理结果，code 反映业务错误细分
func Fail(c *gin.Context, httpStatus, code int, message string) {
    c.JSON(httpStatus, Body{Code: code, Message: message, Data: nil})
}

双层规则背下来：HTTP 状态码管「大类」——参数错 400、未认证 401、无权限 403、不存在 404、服务器错误 500；body 的 code 管「细分」——同样是 401 里，token 过期是 1005，未携带是 1005 但 message 不同；同样是 400 里能区分 1004 参数错。成功一律 200/201 + code 0。第 6 周前端拦截器就靠这套规则写。

5. 合体：POST /users 完整校验接口

main.goimport "gin-api/pkg/response" // 模块名 go mod init 时定的 gin-api

func createUser(c *gin.Context) {
    var dto CreateUserDTO
    if err := c.ShouldBindJSON(&dto); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, bindErrMsg(err))
        return // ← 写完错误响应必须 return，否则继续往下执行双写响应
    }
    if dto.Role == "" {
        dto.Role = "user" // required 管不了缺省值，业务默认值在代码里补
    }
    response.Created(c, gin.H{"id": 1, "username": dto.Username, "role": dto.Role})
}

加餐：一个 handler 同时绑三种来源

PUT /users/:id?page=2 这类「URI + Query + Body 混着要」的场景很常见，每个来源各绑各的结构体，互不干扰：

main.gotype IDUri struct {
    ID int `uri:"id" binding:"required,gt=0"`
}
type PageQuery struct {
    Page int `form:"page" binding:"omitempty,gte=1"`
}

func updateUser(c *gin.Context) {
    var uri IDUri
    if err := c.ShouldBindUri(&uri); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "id 必须是正整数")
        return
    }
    var q PageQuery
    if err := c.ShouldBindQuery(&q); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "page 必须是 ≥1 的整数")
        return
    }
    var dto UpdateUserDTO // 与 CreateUserDTO 类似，字段全部 omitempty + 各自规则（更新允许只传部分字段）
    if err := c.ShouldBindJSON(&dto); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, bindErrMsg(err))
        return
    }
    response.OK(c, gin.H{"id": uri.ID, "page": q.Page, "updated": dto.Username})
}
shell$ curl -s -X PUT "localhost:8080/users/5?page=2" -H "Content-Type: application/json" \
  -d '{"username":"ada","email":"ada@example.com","password":"passw0rd-123"}'
{"code":0,"message":"success","data":{"id":5,"page":2,"updated":"ada"}}

绑定顺序有讲究：ShouldBindJSON 会读取并消耗请求体流——先绑 URI/Query（它们不碰 body），最后再绑 JSON，且同一请求里别第二次读 body。今天先记结论，第 8 周文件上传会正面撞上这个问题。

练习 1：POST /users 校验用户名密码（45 分钟）

要求：用户名 3–20 位必填、密码至少 8 位必填、role 可选但只能是 user/admin；校验失败返回 400 + code 1004 + 中文消息；成功返回 201 + code 0 + 创建结果。

步骤：① 建 pkg/response/response.go（抄讲义第 4 节）；② 写 CreateUserDTO + bindErrMsg；③ 在 main 里注册 r.POST("/users", createUser)；④ 用讲义第 5 节的 curl 验证 400 与 201 两条路径。

参考答案：三段代码分别见讲义 1/3/4/5 节，拼装即可。自测清单：空 body、非法 JSON、username:"ab"、role:"superuser" 四种输入都要拿到 400 且 message 各不相同；合法输入拿到 {"code":0,...}。

练习 2：分页参数 ShouldBindQuery（30 分钟）

要求：GET /users 绑定 ListQuery{Page,Size}，size 上限 100，非法时同样返回统一 400；合法时回显解析后的 int 值。

参考答案：

main.gofunc listUsers(c *gin.Context) {
    var q ListQuery
    if err := c.ShouldBindQuery(&q); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, bindErrMsg(err))
        return
    }
    if q.Page == 0 { q.Page = 1 }  // required 不能用于允许 0 的场景，缺省值代码补
    if q.Size == 0 { q.Size = 10 }
    response.OK(c, gin.H{"page": q.Page, "size": q.Size})
}
练习 3：ShouldBindUri 处理路径参数（20 分钟）

要求：GET /users/:id 用结构体绑定 id 为 int，/users/abc 返回统一 400。

参考答案：type IDUri struct { ID int `uri:"id" binding:"required,gt=0"` }，handler 里 c.ShouldBindUri(&uri) 失败即 response.Fail(c, 400, response.CodeInvalidParam, "id 必须是正整数")。注意：required 对 int 意味着不能为 0，所以配 gt=0。

练习 4：Content-Type 事故复现（15 分钟）

要求：发送正确的 JSON 但不带 -H "Content-Type: application/json"，记录报错（提示：unsupported media type / json: cannot unmarshal 类）。再故意发一个残缺 JSON {"username": 观察错误类型差别——前者走不进校验，后者是语法错误，两者都归 400 + 1004。

常见坑（新手 100% 会踩）

坑现象正确姿势
字段小写开头绑定不报错，但字段永远是零值（反射看不见未导出字段）参与 JSON 的字段一律大写字母开头 + json:"xxx" tag
Content-Type 不对ShouldBindJSON 直接报 unsupported media type调用方带 application/json；Postman 选 raw + JSON
required 杀零值年龄 0、bool false、分页 page=0 全被拒用 omitempty,gte=0 组合，缺省值在代码里补
Fail 后忘 return继续执行到 response.OK，响应体双写、日志报 superfluous write每个 response.Fail 紧跟 return，形成肌肉记忆
tag 拼写错误bding:"required" 静默失效，校验没跑校验规则改完必测一条非法输入，确认 400 真的来了
min/max 语义混淆以为 min=8 对 int 字段也是「值≥8」？其实数字按数值、字符串按字节长度数字字段更推荐 gte/lte，语义无歧义
