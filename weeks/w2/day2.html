请求绑定与验证

昨天用 GetRawData() 拿到的是裸字节，没法用。今天学 Gin 的杀手锏：一次声明结构体，自动完成「解析 JSON → 校验规则 → 填充字段」三步，并把校验失败翻译成人类可读的 400。同时落地手册「API 设计约定」的 {code, message, data} 统一响应——从今天起，你写的每个接口都长一个样。

课前须知：从 fetch 到 Bind

前端是怎么处理用户输入的？const body = await res.json() 之后要么手写一堆 if (!body.name)，要么上 zod/yup 定义 schema。Gin 的绑定 = 这两件事合体：结构体本身就是 schema，tag 就是校验规则，一次 ShouldBindJSON(&dto) 全做完。

反射的代价。绑定靠 Go 反射逐字段赋值，所以有两条铁律：① 字段必须导出（大写字母开头）；② 想匹配 JSON 里的 user_name 这种蛇形键，必须写 json:"user_name" tag。违反任何一条，绑定结果就是零值且不报错——今天最大的坑。

知识讲义

1. ShouldBindJSON 与 DTO 结构体

DTO（Data Transfer Object）= 专门描述「这个接口接收什么」的结构体，只出现在入参/出参上，不和数据库模型混用：

main.go// CreateUserDTO 描述 POST /users 的请求体
type CreateUserDTO struct {
    Username string `json:"username" binding:"required,min=3,max=20"`
    Email    string `json:"email" binding:"required,email"`
    Password string `json:"password" binding:"required,min=8"`
    Role     string `json:"role" binding:"omitempty,oneof=user admin"` // 可省略，省略则默认 user
}

func createUser(c *gin.Context) {
    var dto CreateUserDTO
    if err := c.ShouldBindJSON(&dto); err != nil {
        // 解析失败或校验失败都走这里，第 3 节把它变成人话
        c.JSON(http.StatusBadRequest, gin.H{"detail": err.Error()})
        return
    }
    // 走到这里 dto 每个字段都合法，放心使用
    c.JSON(http.StatusOK, gin.H{"dto": dto})
}
绑定方法数据来源典型场景
ShouldBindJSON请求体，无视 Content-Type 一律按 JSON 解析（不看头、不校验头）POST/PUT 传 JSON；-d 不带 Content-Type 也能绑上
ShouldBindQueryURL 查询参数分页 ?page=1&size=10
ShouldBindUri路径参数/users/:id 的 id 转 int
ShouldBind / Bind先读 Content-Type 再分发绑定器：JSON 走 JSON、XML 走 XML、multipart 走 multipart，其余一律退回表单解析（binding.Default 的 default 分支就是 Form，Gin 自己不报 415）同一 handler 兼容 JSON/表单

记住这一组差异（否则会被"玄学 400"折磨）：ShouldBindJSON 是"专用绑定器"，它不看 Content-Type，直接把 body 当 JSON 解；ShouldBind/Bind 是"通用绑定器"，先读 Content-Type 决定用哪种解析方式，认不出的类型退回表单解析（源码里 binding.Default 的 default: 分支返回 Form），于是 JSON body 被当表单拆、字段全空，报错是一串 required 校验失败，不是 415 unsupported media type——那个 415 是别的框架或你自己手写头校验才会有的东西。所以"没带 Content-Type 也能绑上"是 ShouldBindJSON 的正常行为，不是 bug。练习 4 用四条 curl 把这个差别亲手跑出来。

前缀 Should 的含义：解析失败只 return err 给你处理；不带 Should 的 c.Bind/c.BindJSON 走的是 MustBindWith，失败时它自己写一个 400（AbortWithError → 纯文本 Bad Request）并 Abort，你的 response.Fail 根本轮不到，统一响应格式当场被绕过。团队项目一律用 Should 系列。

2. binding 校验 tag 速查

tag 由 go-playground/validator 提供，Gin 内置调用。多个规则用逗号串联，从上到下依次校验：

规则含义备注
required不能是零值陷阱：数字 0、bool false、字符串 "" 都算零值，"年龄必填且允许为 0" 不能用它
min=3 / max=20string 按长度、数字按数值、slice 按元素数密码 min=8、昵称 max=20
email基本邮箱格式只查格式，不代表邮箱真实存在
oneof=user admin值必须是列举之一空格分隔，等价前端的枚举白名单
omitempty字段缺省时跳过后续规则配合 oneof 实现「可选枚举」
gte=1 / lte=150大于等于 / 小于等于年龄用 gte=0,lte=150 替代 required
main.gotype ListQuery struct {
    Page int `json:"page" form:"page" binding:"omitempty,gte=1"`
    Size int `json:"size" form:"size" binding:"omitempty,gte=1,lte=100"`
}
// 用法：c.ShouldBindQuery(&q)，URL 传 ?page=2&size=20 即自动转成 int

查询参数的 tag 是 form:"page"（表单/查询键名），JSON body 才是 json:"page"。两个都写上，同一个结构体就能同时服务 query 与 body。

3. 自定义错误消息：把 validator 报错翻译成人话

err.Error() 的默认输出是 Key: 'CreateUserDTO.Email' Error:Field validation for 'Email' failed on the 'email' tag——机器看得懂，用户看不懂。用 errors.As 拿到结构化错误逐条翻译：

先装依赖。下面的 validator.ValidationErrors 是第三方包（Gin 内部用的就是它，但翻译错误要你自己 import）。在项目根目录执行一次即可：

shell$ go get github.com/go-playground/validator/v10   # ≈ npm i；写进 go.mod 的 require（导入路径带 /v10，别漏）
$ go mod tidy                                   # 幂等：补齐 go.sum、剔除没用的依赖
main.goimport (
    "errors"
    "strings"

    "github.com/go-playground/validator/v10"
)

// bindErrMsg 把校验错误转成一句中文提示
func bindErrMsg(err error) string {
    var ves validator.ValidationErrors
    if errors.As(err, &ves) {
        msgs := make([]string, 0, len(ves))
        for _, ve := range ves {
            switch ve.Tag() {
            case "required": msgs = append(msgs, ve.Field()+" 不能为空")
            case "min":      msgs = append(msgs, ve.Field()+" 长度不足 "+ve.Param())
            case "max":      msgs = append(msgs, ve.Field()+" 长度超限 "+ve.Param())
            case "email":    msgs = append(msgs, ve.Field()+" 不是合法邮箱")
            case "oneof":    msgs = append(msgs, ve.Field()+" 只能是: "+ve.Param())
            default:          msgs = append(msgs, ve.Field()+" 校验失败("+ve.Tag()+")")
            }
        }
        return strings.Join(msgs, "；")
    }
    return "请求体不是合法 JSON" // 非校验类错误（格式/Content-Type）
}

对比 JS：validator 之于 Go，≈ zod 的 safeParse：result.error.issues 是一条条结构化错误，你决定怎么展示。errors.As 则是 Go 版的 err instanceof ValidationError——上周学的 error 接口今天正式上岗。

4. 统一响应 pkg/response.go：本周约定落地

新建 pkg/response/response.go（目录 pkg/response，包名 response），这是手册「十三、API 设计约定」的代码化：

pkg/response/response.gopackage response

import (
    "net/http"

    "github.com/gin-gonic/gin"
)

// Body 是全部接口的统一响应结构：{code, message, data}
type Body struct {
    Code    int  `json:"code"`
    Message string `json:"message"`
    Data    any  `json:"data"`
}

// 业务错误码常量：与 HTTP 状态码分两层（见手册第十三节 / CANONICAL 码表）
const (
    CodeOK           = 0    // 成功
    CodeUserNotFound = 1001 // 资源不存在（通用；今天是用户）
    CodeBadPassword  = 1002 // 密码错误
    CodeForbidden    = 1003 // 权限不足/禁止
    CodeInvalidParam = 1004 // 参数错误
    CodeTokenInvalid = 1005 // 未认证/token 无效
    CodeUserExists   = 1006 // 用户名已存在（day4 service 重名检查用，HTTP 409）
    CodeArticleNotFound = 2001 // 文章不存在（HTTP 404；day4 练习 3 给 articles 补查删时用）
    CodeInternal     = 5000 // 服务器内部错误（HTTP 500；day4 兜底分支用）
)

// OK 成功：HTTP 200 + code 0
func OK(c *gin.Context, data any) {
    c.JSON(http.StatusOK, Body{Code: CodeOK, Message: "ok", Data: data})
}

// Created 创建成功：HTTP 201 + code 0
func Created(c *gin.Context, data any) {
    c.JSON(http.StatusCreated, Body{Code: CodeOK, Message: "ok", Data: data})
}

// Fail 失败：HTTP 状态码反映请求处理结果，code 反映业务错误细分
func Fail(c *gin.Context, httpStatus, code int, message string) {
    c.JSON(httpStatus, Body{Code: code, Message: message, Data: nil})
}

双层规则背下来：HTTP 状态码管「大类」——参数错 400、未认证 401、无权限 403、不存在 404、服务器错误 500；body 的 code 管「细分」——同样是 401 里，token 过期是 1005，未携带是 1005 但 message 不同；同样是 400 里能区分 1004 参数错。成功一律 200/201 + code 0。第 6 周前端拦截器就靠这套规则写。

5. 合体：POST /users 完整校验接口

main.goimport "gin-api/pkg/response" // 模块名 go mod init 时定的 gin-api

func createUser(c *gin.Context) {
    var dto CreateUserDTO
    if err := c.ShouldBindJSON(&dto); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, bindErrMsg(err))
        return // ← 写完错误响应必须 return，否则继续往下执行双写响应
    }
    if dto.Role == "" {
        dto.Role = "user" // required 管不了缺省值，业务默认值在代码里补
    }
    response.Created(c, gin.H{"id": 1, "username": dto.Username, "role": dto.Role})
}

加餐：一个 handler 同时绑三种来源

PUT /users/:id?page=2 这类「URI + Query + Body 混着要」的场景很常见，每个来源各绑各的结构体，互不干扰：

main.gotype IDUri struct {
    ID uint `uri:"id" binding:"required,gt=0"`
}
type PageQuery struct {
    Page int `form:"page" binding:"omitempty,gte=1"`
}
// UpdateUserDTO：PUT 更新时字段可选（允许只传要改的那几个），所以一律不带 required、只带各自的范围规则
type UpdateUserDTO struct {
    Username string `json:"username" binding:"omitempty,min=3,max=20"`
    Email    string `json:"email" binding:"omitempty,email"`
    Password string `json:"password" binding:"omitempty,min=8"`
    Role     string `json:"role" binding:"omitempty,oneof=user admin"`
}

func updateUser(c *gin.Context) {
    var uri IDUri
    if err := c.ShouldBindUri(&uri); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "id 必须是正整数")
        return
    }
    var q PageQuery
    if err := c.ShouldBindQuery(&q); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "page 必须是 ≥1 的整数")
        return
    }
    var dto UpdateUserDTO // 类型定义见本节上方；PUT 允许只传部分字段，规则都是 omitempty
    if err := c.ShouldBindJSON(&dto); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, bindErrMsg(err))
        return
    }
    response.OK(c, gin.H{"id": uri.ID, "page": q.Page, "updated": dto.Username})
}

{"code":0,"message":"ok","data":{"id":5,"page":2,"updated":"ada"}}

绑定顺序有讲究：ShouldBindJSON 会读取并消耗请求体流——先绑 URI/Query（它们不碰 body），最后再绑 JSON，且同一请求里别第二次读 body。今天先记结论；这个「body 只能被读一次」的坑，会在第 4 周 day5 与第 8 周 day4 的 httptest 自动化测试课里再次撞上（测试代码手动构造请求体时同理），届时正面讲。

练习 3：ShouldBindUri 处理路径参数（20 分钟）

要求：GET /users/:id 用结构体绑定 id 为 int，/users/abc 返回统一 400。

参考答案：type IDUri struct { ID uint `uri:"id" binding:"required,gt=0"` }，handler 里 c.ShouldBindUri(&uri) 失败即 response.Fail(c, 400, response.CodeInvalidParam, "id 必须是正整数")。注意：required 对数字类型意味着不能是零值，这里 uint 的零值就是 0，所以 required 已经够用，gt=0 是把它写成显式规则、换 int 时也能用。ID 用 uint 不是随手写的——day4 的 model/仓储/service 全线 uint（对齐 CANONICAL），这里提前一致。

练习 4：ShouldBindJSON vs ShouldBind 对比实验（20 分钟）

结论先给你：「没带 Content-Type: application/json 就报错」不是 ShouldBindJSON 的行为，它是专用绑定器、无视请求头；按头分发的是通用绑定器 ShouldBind/Bind。这个实验用同一段 DTO、两个 handler、同一个 body，亲手把差别跑出来。

加两条临时路由（api 分组里，POST /users 之外）：

main.go// A：专用绑定器，不看头
api.POST("/bind-json", func(c *gin.Context) {
    var dto CreateUserDTO
    if err := c.ShouldBindJSON(&dto); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, bindErrMsg(err)); return
    }
    response.OK(c, dto)
})
// B：通用绑定器，先读 Content-Type 再决定解析方式（用 Should 前缀，响应仍由我们自己写）
api.POST("/bind", func(c *gin.Context) {
    var dto CreateUserDTO
    if err := c.ShouldBind(&dto); err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, bindErrMsg(err)); return
    }
    response.OK(c, dto)
})

四次敲键，对照现象（每条都写清了为什么会这样）：

  • ① ShouldBindJSON + 正确 JSON、不带 Content-Type（curl -d 默认发 application/x-www-form-urlencoded）→ 200 正常绑定：它压根不看头。
  • ② ShouldBind + 完全相同的请求 → 400 + 一串 required 校验消息：头是表单类型 → 走 Form 绑定器 → ParseForm 把 {"username":"ada",...} 当成一堆不成对的键，字段全空 → required 全挂。报错来自校验器，不来自头。
  • ③ ShouldBind + 同一 body，只补 -H "Content-Type: application/json" → 200：换了头就换了解析方式，这才是"按头分发"的证据。
  • ④ 任一 handler + 残缺 JSON {"username": + 带 JSON 头 → 400 + 1004，报的是 unexpected EOF 一类语法错误（非 validator 错误，被 bindErrMsg 兜底成"请求体不是合法 JSON"）。

把这四段输出贴进笔记，并写一句：团队里为什么接口统一用 ShouldBindJSON（不受调用方请求头质量影响、错误消息格式自己控），而只在"同一 handler 要兼容表单/JSON"时才用 ShouldBind。

想拿 415 得自己写。Gin 的通用绑定器对认不出的媒体类型一律退回表单，不会替你说 415 Unsupported Media Type。真有这种契约要求（"本接口只收 JSON，其他一律拒"），就在 handler 开头自己判头：if c.ContentType() != "application/json" { response.Fail(c, http.StatusUnsupportedMediaType, response.CodeInvalidParam, "只接受 application/json"); return }——注意 Content-Type: application/json; charset=utf-8 会被 c.ContentType() 去掉参数后比较，判等写成 strings.EqualFold 更稳。

常见坑（新手 100% 会踩）

坑现象正确姿势
字段小写开头绑定不报错，但字段永远是零值（反射看不见未导出字段）参与 JSON 的字段一律大写字母开头 + json:"xxx" tag
把 Content-Type 当成 ShouldBindJSON 的门槛误以为"没带 application/json 就会 400"。其实 ShouldBindJSON 无视请求头照样解析；换成 ShouldBind/Bind 时，同一个请求报的也不是 415，而是一串 required 校验失败（认不出的头退回表单解析，字段全空）接口固定收 JSON 就用 ShouldBindJSON（练习 4 已用四条 curl 对比证明）；确实要按头分流才用 ShouldBind，想强制 415 就自己判 c.ContentType()
用不带 Should 的 Bind/BindJSON绑定失败时 Gin 已经自己写了 400（纯文本 Bad Request）并 Abort，你后面的 response.Fail 变成无效二次写，前端拿到的不是 {code,message,data}只在需要同一个 handler 兼容多种媒体类型时用 ShouldBind（它只返错、不写响应），错误消息永远由 response.Fail + bindErrMsg 出口
required 杀零值年龄 0、bool false、分页 page=0 全被拒用 omitempty,gte=0 组合，缺省值在代码里补
