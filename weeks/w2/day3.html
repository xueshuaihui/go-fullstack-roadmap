中间件

日志、计时、跨域、鉴权——这些「每个接口都需要、但和业务本身无关」的逻辑，不该复制粘贴 20 遍。今天学的中间件就是干这个的。核心心智模型只有一个：洋葱模型——请求从外层穿到内层，响应再从内层穿回外层，c.Next() 是进与出的分界线。

课前须知：你已经写过中间件了

前端axios 拦截器就是中间件思想。axios.interceptors.request.use(cfg => { cfg.headers.Authorization = token; return cfg })——在请求到达业务代码前统一插一段逻辑。Gin 中间件是同一定位在服务端：请求进 handler 前（Next 之前）做鉴权、打日志；handler 出来后（Next 之后）计时、改写响应。

gin.Default() 之所以「开箱即用」，就是因为它偷偷帮你 Use 了 Logger 和 Recovery 两个中间件。今天把这两个拆开看清，再自己写三个。

知识讲义

1. 中间件签名与注册

中间件就是一个普通的 func(c *gin.Context)，类型别名叫 gin.HandlerFunc。注册方式三种：

main.gofunc helloMw() gin.HandlerFunc {
    return func(c *gin.Context) {
        fmt.Println("[mw] 请求进来:", c.Request.Method, c.Request.URL.Path)
        c.Next() // ← 分界线：上面的代码在 handler 前跑，下面的在 handler 后跑
        fmt.Println("[mw] 响应离开:", c.Writer.Status())
    }
}

func main() {
    r := gin.New()            // 白纸引擎，中间件全部手动注册（生产推荐）
    r.Use(gin.Logger())       // 全局：每个请求都过
    r.Use(gin.Recovery())     // 全局：兜住 panic
    r.Use(helloMw())          // 全局：自定义

    // RequireAuth / CORS / Timer 都在 middleware 包里，引用必须带包名限定：
    //   import "gin-api/middleware"（今天中间件还在仓库根的 middleware/ 目录，day4 才搬进 internal/）
    admin := r.Group("/admin", middleware.RequireAuth())   // 分组级：只有 /admin/** 过这个中间件（RequireAuth 见第 6 节）
    admin.GET("/stats", func(c *gin.Context) { c.JSON(200, gin.H{"online": 1}) })

    r.PUT("/users/:id", middleware.RequireAuth(), updateUser) // 路由级：单条临时加；updateUser 是你已有的 handler
}

别把 middleware.RequireAuth() 写成裸 RequireAuth()。第 6 节把 RequireAuth 定义在 middleware 包里（package middleware），Go 没有"跨包自动可见"，调用处一定要 包名限定，并在文件头 import "gin-api/middleware"。IDE 不会帮你圆过去——裸写会直接 undefined: RequireAuth 编译失败。

注册顺序 = 洋葱从外到内的层序。Use(A); Use(B) 的执行顺序是 A进 → B进 → handler → B出 → A出。Recovery 必须尽早注册（越外层越能兜住内层中间件的 panic）；鉴权中间件要注册在你希望它拦住的那些路由之前。

2. 洋葱模型：c.Next() 与 c.Abort()

调用效果
c.Next()放行：继续执行内层中间件与 handler；handler 返回后回到 Next 之下的代码继续
c.Abort()熔断：内层中间件和 handler 统统不再执行，但本中间件 Next 之后的代码、外层中间件的「出」阶段仍会跑
c.AbortWithStatus(204)写状态码 + 熔断，一步到位
c.AbortWithStatusJSON(401, ...)写 JSON + 熔断，鉴权失败的标准收尾
shell# 三层洋葱的执行顺序（在每处 Println 亲测一遍，今天最重要的实验）
[A-before] → [B-before] → [handler] → [B-after] → [A-after]

# B 里先 c.Abort() 之后：
[A-before] → [B-before, handler 被跳过] → [A-after]

这个「先进后出」结构和浏览器的事件冒泡捕获、Redux middleware 的 next(action)、React Query 的 queryFn 包裹是同一个数学模型（onion / chain of responsibility）。c.Next() ≈ Redux 里的 next(action)：不调它，内层永远不执行。

3. 内置双雄：Logger 与 Recovery

main.gor := gin.New()
r.Use(gin.LoggerWithConfig(gin.LoggerConfig{
    Formatter: func(params gin.LogFormatterParams) string {
        return fmt.Sprintf("%s | %3d | %-7s %s | %s\n",
            params.TimeStamp.Format("15:04:05"),
            params.StatusCode, params.Method, params.Path, params.Latency,
        )
    },
    Output: os.Stdout,
}))
r.Use(gin.Recovery()) // handler 里 panic("boom") 不会打挂进程：日志堆栈 + 返回 500（注意 body 是空的，见 3.6）

Recovery 的原理下一节（3.5）就展开讲：Go 的 panic 默认让整个进程崩溃（不像 JS 的异常只死一个请求），Recovery 中间件用 defer + recover() 把 panic 拦在单请求范围内，转成 500 响应。没有它，一个接口的一行 bug 就能让全站下线。这就是 gin.Default() 自带它的原因。

3.5 panic / recover 最小认识（只需会读，day4/第 5 周还会反复用）

今天必须把上面那句"panic 会打挂整个进程"落到能写出来的程度，否则后面 MustGet、Recovery、向 nil map 写入全是它的坑。三句话：

  1. panic = 运行时的"炸锅"：Go 里 panic(v) 会立刻停止当前函数，一路往上炸（deferred 函数按 LIFO 执行），直到没人接住就把整个进程干掉、打印堆栈。
    对照 JS：≈ 一个没被 try/catch 接住的 throw，但 JS 通常只终止这个调用栈/这个请求，Go 终止的是进程——这是两者最要命的区别。
  2. recover() = 在 defer 里把 panic"接住"：recover() 只有在 defer 的函数里被调用才有效，它返回 panic 抛出的值并让当前函数正常返回，从而阻断 panic 继续上抛。
  3. 为什么中间件里要 recover：Gin 每个请求跑在独立 goroutine 里，一个请求 handler 里 panic，如果没人 recover，全站的其它请求会跟着一起下线。Recovery 中间件正是每个请求最外层那圈 defer recover()——接住 panic，写一个 500，进程继续接下一个请求。
panic-demo/main.go（最小可跑：亲手看 recover 怎么把 panic 拦下来）package main

import "fmt"

// safeCall 用 defer+recover 把 f 里的 panic 变成一句打印，而不是让程序崩
func safeCall(f func()) {
    defer func() {
        if r := recover(); r != nil { // recover 返回 panic 的值；返回非 nil 说明真接住了
            fmt.Println("接住了 panic:", r)
        }
    }()
    f() // f 里 panic 时，上面这个 defer 会执行
}

func main() {
    safeCall(func() { panic("boom") })
    fmt.Println("程序还活着") // 能打到这行，就说明 recover 生效了

    // 对比：不 recover，这一句就会让进程当场崩、打印堆栈，后面的代码不执行
    // var m map[string]int; m["x"] = 1 // panic: assignment to entry in nil map
}
shell$ go run ./demo/panic
接住了 panic: boom
程序还活着

这份代码放哪：它自带 package main + func main()，而你的 gin-api/ 根目录已经有一份 main.go（今天整页代码都往它那一个 func main() 里加）。Go 的规矩是同一目录只能有一个 func main()，抄进同一个目录会直接 main redeclared in this block。按第 1 周 day2 的老办法「一个子目录一份 main」：在 gin-api 里单独开 demo/panic/，把上面这份存成 demo/panic/main.go，然后 go run ./demo/panic（还在同一个模块里，不用重新 go mod init）。它只是理解用的沙盒，明天分层前可以删掉，也不要 import 到项目里——工程上真正兜 panic 的是 Recovery 中间件，不是自己到处写 recover。

把 defer recover() 想成 Express 里那个包在所有 handler 外面的错误中间件，或 React 的 ErrorBoundary：它不是"捕获每个异常"的日常工具（日常错误照旧用 if err != nil），而是最后一道防线。Go 的哲学是"错误是值，别乱 panic"；只有在"程序此刻根本没法继续"（比如启动失败 panic(err)、MustGet 取不到必需值）才 panic，然后靠最外层的 Recovery 兜住不让全站陪葬。

3.6 自定义 Recovery：让 500 也说统一的 JSON

3.5 讲的是原理，这一节把原理写成能跑的中间件。为什么要自己写？因为 gin.Recovery() 兜住 panic 后只调 c.AbortWithStatus(500)——状态码有，响应体是空的（curl -si localhost:8080/debug/boom 里能看到 Content-Length: 0，body 一行字节都没有）。day2 立的"所有响应都是 {code,message,data}"规矩，被它一个字面地打破了：前端 JSON.parse('') 直接抛错，连"服务器出错了"这句人话都收不到。下面这份就是 3.5 三句话的工业版：

middleware/recovery.gopackage middleware

import (
    "log"
    "net/http"
    "runtime/debug"

    "github.com/gin-gonic/gin"

    "gin-api/pkg/response"
)

// Recovery 替换 gin.Recovery()：三件事一件不落——
// ① 接住 panic（CustomRecovery 内部就是 defer + recover()）
// ② 把 panic 值和堆栈写进服务端日志（debug.Stack() 等价于终端里那一大坨）
// ③ 用统一响应结构返回 500：HTTP 500 + 业务码 5000
func Recovery() gin.HandlerFunc {
    return gin.CustomRecovery(func(c *gin.Context, recovered any) {
        log.Printf("[recovery] %s %s panic: %v\n%s",
            c.Request.Method, c.Request.URL.Path, recovered, debug.Stack())
        c.AbortWithStatusJSON(http.StatusInternalServerError, response.Body{
            Code: response.CodeInternal, Message: "服务繁忙", Data: nil,
        })
    })
}
main.go（注册处换掉一行）// 原来：r.Use(gin.Logger(), gin.Recovery(), middleware.CORS(), middleware.Timer())
r.Use(gin.Logger(), middleware.Recovery(), middleware.CORS(), middleware.Timer()) // Recovery 仍留在最外层（紧跟 gin.Logger() 之后），别挪到 CORS/鉴权后面，否则那几层里 panic 就没人兜了

签名要认得：gin.CustomRecovery(handle gin.RecoveryFunc) gin.HandlerFunc，其中 RecoveryFunc = func(c *gin.Context, recovered any)——recovered 就是 panic() 里传进去的那个值（老资料里写作 interface{}，和 any 是同一个类型）。你不用自己写 defer 和 recover()，CustomRecovery 已经把这套壳子套好了，你只负责"接住之后干什么"。

本周口径：day4 的装配讲义里仍写 gin.Recovery()（先把进程保住这一件事做对，分层和 Recovery 两件事不搅在一起）；day5 练习 4 会把注册那行换成上面这份，届时 /debug/boom 的响应从"500 + 空 body"变成"500 + {"code":5000,"message":"服务繁忙","data":null}"，服务照常接下一个请求。周末 summary 的装配按终态写，也就是直接挂 middleware.Recovery()。第 4 周正式给那一条链上的结构化日志与 request_id（AccessLog + RequestID 两个中间件），它并不替换 Recovery——所以这份 §3.6 的 JSON Recovery 就是你本周、也是后面各周的终态，别退回官方的空 body 版。

4. 自定义：请求计时中间件

middleware/timer.gopackage middleware

import (
    "log"
    "time"

    "github.com/gin-gonic/gin"
)

// Timer 把每个请求的方法、路径、最终状态码、耗时打进服务端日志。
// 注意：耗时只能在 c.Next() 之后才知道，而那时响应头已经发出去了——
// 所以这里只写日志，不去改响应头（想回写 X-Process-Time 见下方「坑」）。
func Timer() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        c.Next() // ← 把"业务"包在里面，出来时请求已处理完
        cost := time.Since(start)
        log.Printf("[timer] %s %s -> %d 耗时 %s",
            c.Request.Method, c.Request.URL.Path, c.Writer.Status(), cost)
    }
}
shell$ curl -s localhost:8080/api/v1/users -o /dev/null
# 终端 A（服务日志）里应出现一行：
2026/01/05 10:12:33 [timer] GET /api/v1/users -> 200 耗时 63.458µs

# 客户端侧想看到耗时，用 curl 自带的计时（不用服务端配合）：
$ curl -s -o /dev/null -w "状态=%{http_code} 总耗时=%{time_total}s\n" localhost:8080/api/v1/users
状态=200 总耗时=0.000412s

「Next 之后才有的信息」是中间件设计的关键：耗时、最终状态码（c.Writer.Status()）都必须在 c.Next() 之后读，写在 Next 之前拿到的是零值。

别在 Next 之后 c.Header(...) 回写响应头（很多博客里那句 c.Header("X-Process-Time", cost.String()) 是无效的）：handler 里的 c.JSON 已经把状态行和响应头发出去了，之后再改 header 映射表，客户端收不到，而且不报错——最坑的那种。想把耗时交给客户端，得在 c.Next() 之前就写头（比如 X-Request-Id 这种请求进入就能算的），或者包一层自定义 gin.ResponseWriter 在真正 flush 前插值——那是第 4 周 day4 结构化 access 日志（一行 JSON 记方法/路径/状态码/耗时/IP）才会碰的工程量，本周不碰。今天的口径：耗时进服务端日志，客户端想看就用 curl -w 自己量。本周项目按上面的日志版实现即可。

5. CORS：手写版理解预检

浏览器同源策略：前端 localhost:5173 调你的 localhost:8080 属于跨域。对于带 Content-Type: application/json 或自定义头的请求，浏览器会先发一次 OPTIONS 预检，服务端允许了才发真正的请求。手写版把全过程摊开：

middleware/cors.gopackage middleware

import (
    "net/http"

    "github.com/gin-gonic/gin"
)

// CORS 手写版：搞懂每一行，再切官方库
func CORS() gin.HandlerFunc {
    return func(c *gin.Context) {
        origin := c.GetHeader("Origin")
        if origin != "" {
            c.Header("Access-Control-Allow-Origin", origin)      // 回声来源；练习用 * 也可
            c.Header("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,OPTIONS")
            c.Header("Access-Control-Allow-Headers", "Content-Type,Authorization")
            c.Header("Access-Control-Max-Age", "86400")          // 预检结果缓存 1 天
            c.Header("Access-Control-Allow-Credentials", "true") // 需要带 cookie 时才加
        }
        if c.Request.Method == http.MethodOptions {
            c.AbortWithStatus(http.StatusNoContent) // 预检到此为止，绝不进业务 handler
            return
        }
        c.Next()
    }
}

6. 鉴权中间件雏形

第 4 周才学 JWT，今天先用「写死的 token」把骨架搭起来——流程一模一样，以后只是把比较逻辑换成验签：

middleware/auth.gopackage middleware

import (
    "net/http"
    "strings"

    "github.com/gin-gonic/gin"

    "gin-api/pkg/response"
)

const fixedToken = "go-fullstack-2026"

// RequireAuth 校验 Authorization: Bearer <token>，失败 401 + code 1005
func RequireAuth() gin.HandlerFunc {
    return func(c *gin.Context) {
        got := c.GetHeader("Authorization")
        if !strings.HasPrefix(got, "Bearer ") || strings.TrimPrefix(got, "Bearer ") != fixedToken {
            c.AbortWithStatusJSON(http.StatusUnauthorized, response.Body{
                Code: response.CodeTokenInvalid, Message: "token 缺失或无效", Data: nil,
            })
            return
        }
        c.Set("userID", uint(1)) // 把"当前用户"塞进上下文（CANONICAL 口径：userID 存 uint），下游 handler 用 c.GetUint 取
        c.Next()
    }
}
main.goapi := r.Group("/api/v1")   // 读：匿名组，只挂全局中间件
api.GET("/users", listUsers)
api.GET("/users/:id", getUser)

write := r.Group("/api/v1") // 全站 W2 起统一 /api/v1 前缀；全部写操作（POST/PUT/DELETE）挂鉴权
write.Use(middleware.RequireAuth())
write.POST("/users", createUser)
write.PUT("/users/:id", updateUser)
write.DELETE("/users/:id", deleteUser)

读写分离的做法见练习 2：读接口挂在匿名的 api := r.Group("/api/v1")，写接口（POST 创建 + PUT 更新 + DELETE 删除，一个都不例外）收进 write := r.Group("/api/v1") 再 write.Use(middleware.RequireAuth())。前缀必须是 /api/v1（不是空串 ""），否则和 day1 练习 3、day4 装配的路径口径不一致，curl 会一头雾水。两个 group 前缀相同、互不冲突，Gin 允许同一前缀注册多组——day4 的 Register(public, auth) 就是这套写法，只是同一个组换了个名字：今天的 write 在 day4/summary 里叫 auth（含义完全一样，搬代码时按新名字改引用即可）。今天的口径会一路用到第 4 周真 JWT。

7. 层间信箱：c.Set / c.Get 传递请求级数据

中间件解析出的东西（用户 ID、请求 ID、语言偏好）不该塞进全局变量，Gin 提供了请求级键值空间 c.Keys：

main.go// 写入（鉴权中间件里，见第 6 节）
c.Set("userID", uint(1))

// 读取（任意下游 handler / 中间件「出」阶段）
if v, exists := c.Get("userID"); exists {
    uid := v.(uint)             // 取出来是 any，需要断言回原类型（这里中间件塞的是 uint）
    fmt.Println("当前用户:", uid)
}
uid := c.GetUint("userID")     // 更推荐：带类型的便捷方法，取不到给零值（0 = 未登录）
name := c.MustGet("userID").(uint) // 断言失败会 panic——被 Recovery 兜成 500；只在「前面必挂鉴权」时敢用（原理见 3.5）

断言的类型要和中间件写入时的实际类型一致。CANONICAL 统一 c.Set("userID", uint)、读取用 c.GetUint("userID")，所以下游断言写 .(uint) 不是 .(int)——写成 .(int) 会 panic「interface conversion: interface {} is uint, not int」。day4 的 service 方法签名也用 uint（ID 一律 uint），从 c.GetUint 取出的值可以直接传进去。

方法取不到时使用建议
c.Get(k)返回 (nil, false)最安全，配 exists 分支
c.GetInt/GetString…返回零值业务默认值场景，配合「零值 = 未登录」判断
c.MustGet(k)panic（被 Recovery 兜 500，原理见 3.5）链路有强约束时用，失败要在日志可查

第 4 周学 JWT 后，auth 中间件验签得到 userID + role，依旧走 c.Set；handler 一行都不用改——中间件换芯、上层无感，这就是今天把接口写成「从 c.Get 拿用户」而不是「解析 Header」的原因。

常见坑（新手 100% 会踩）

坑现象正确姿势
Abort 后不 return你以为拦住了，其实本函数继续往下跑，重复写响应c.Abort() / AbortWithStatusJSON 之后立刻 return
Next 后写响应handler 已经写完 JSON，中间件又 c.JSON(...)，日志报 superfluous response.WriteHeader call中间件「出」阶段只读（Status/耗时），要改响应体请三思；重写响应用 c.Writer.Write(...) 前检查 c.Writer.Written()
注册顺序错鉴权中间件 Use 在业务路由之后，前面的路由裸奔Use 只影响之后注册的路由；启动时用 go run 打印的 Routes 列表自查
Abort 想取消已发出的响应handler 已经写了一半 body，Abort 拦不住字节流Abort 的语义是「阻止内层继续执行」，不是「回滚响应」；要在写响应之前判断
OPTIONS 漏进业务 handler预检返回 404/405，浏览器报 CORS 失败（报错极具误导性）CORS 中间件必须对 OPTIONS AbortWithStatus(204)，且注册在鉴权之前（预检不带 Authorization 头！）
在 goroutine 里用 c请求结束后 c 被回收，偶发 panic/数据错乱今天先记住：c 不能跨 goroutine 用；要异步须 c.Copy()（第 5 周细讲）
