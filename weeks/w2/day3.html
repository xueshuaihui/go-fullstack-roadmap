中间件

日志、计时、跨域、鉴权——这些「每个接口都需要、但和业务本身无关」的逻辑，不该复制粘贴 20 遍。今天学的中间件就是干这个的。核心心智模型只有一个：洋葱模型——请求从外层穿到内层，响应再从内层穿回外层，c.Next() 是进与出的分界线。

课前须知：你已经写过中间件了

前端axios 拦截器就是中间件思想。axios.interceptors.request.use(cfg => { cfg.headers.Authorization = token; return cfg })——在请求到达业务代码前统一插一段逻辑。Gin 中间件是同一定位在服务端：请求进 handler 前（Next 之前）做鉴权、打日志；handler 出来后（Next 之后）计时、改写响应。

gin.Default() 之所以「开箱即用」，就是因为它偷偷帮你 Use 了 Logger 和 Recovery 两个中间件。今天把这两个拆开看清，再自己写三个。

知识讲义

1. 中间件签名与注册

中间件就是一个普通的 func(c *gin.Context)，类型别名叫 gin.HandlerFunc。注册方式三种：

main.gofunc helloMw() gin.HandlerFunc {
    return func(c *gin.Context) {
        fmt.Println("[mw] 请求进来:", c.Request.Method, c.Request.URL.Path)
        c.Next() // ← 分界线：上面的代码在 handler 前跑，下面的在 handler 后跑
        fmt.Println("[mw] 响应离开:", c.Writer.Status())
    }
}

func main() {
    r := gin.New()            // 白纸引擎，中间件全部手动注册（生产推荐）
    r.Use(gin.Logger())       // 全局：每个请求都过
    r.Use(gin.Recovery())     // 全局：兜住 panic
    r.Use(helloMw())          // 全局：自定义

    admin := r.Group("/admin", RequireAuth())      // 分组级：只有 /admin/** 过这个中间件（RequireAuth 见第 6 节）
    admin.GET("/stats", func(c *gin.Context) { c.JSON(200, gin.H{"online": 1}) })

    r.PUT("/users/:id", RequireAuth(), updateUser)   // 路由级：单条临时加；updateUser 是你已有的 handler
}

注册顺序 = 洋葱从外到内的层序。Use(A); Use(B) 的执行顺序是 A进 → B进 → handler → B出 → A出。Recovery 必须尽早注册（越外层越能兜住内层中间件的 panic）；鉴权中间件要注册在你希望它拦住的那些路由之前。

2. 洋葱模型：c.Next() 与 c.Abort()

调用效果
c.Next()放行：继续执行内层中间件与 handler；handler 返回后回到 Next 之下的代码继续
c.Abort()熔断：内层中间件和 handler 统统不再执行，但本中间件 Next 之后的代码、外层中间件的「出」阶段仍会跑
c.AbortWithStatus(204)写状态码 + 熔断，一步到位
c.AbortWithStatusJSON(401, ...)写 JSON + 熔断，鉴权失败的标准收尾
shell# 三层洋葱的执行顺序（在每处 Println 亲测一遍，今天最重要的实验）
[A-before] → [B-before] → [handler] → [B-after] → [A-after]

# B 里先 c.Abort() 之后：
[A-before] → [B-before, handler 被跳过] → [A-after]

这个「先进后出」结构和浏览器的事件冒泡捕获、Redux middleware 的 next(action)、React Query 的 queryFn 包裹是同一个数学模型（onion / chain of responsibility）。c.Next() ≈ Redux 里的 next(action)：不调它，内层永远不执行。

3. 内置双雄：Logger 与 Recovery

main.gor := gin.New()
r.Use(gin.LoggerWithConfig(gin.LoggerConfig{
    Formatter: func(params gin.LogFormatterParams) string {
        return fmt.Sprintf("%s | %3d | %-7s %s | %s\n",
            params.TimeStamp.Format("15:04:05"),
            params.StatusCode, params.Method, params.Path, params.Latency,
        )
    },
    Output: os.Stdout,
}))
r.Use(gin.Recovery()) // handler 里 panic("boom") 不会打挂进程：日志堆栈 + 返回 500

Recovery 的原理明天讲分层后会用到：Go 的 panic 默认让整个进程崩溃（不像 JS 的异常只死一个请求），Recovery 中间件用 defer + recover() 把 panic 拦在单请求范围内，转成 500 响应。没有它，一个接口的一行 bug 就能让全站下线。这就是 gin.Default() 自带它的原因。

4. 自定义：请求计时中间件

middleware/timer.gopackage middleware

import (
    "log"
    "time"

    "github.com/gin-gonic/gin"
)

// Timer 记录每个请求耗时，并回写到响应头 X-Process-Time
func Timer() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        c.Next() // ← 把"业务"包在里面，出来时请求已处理完
        cost := time.Since(start)
        c.Header("X-Process-Time", cost.String())
        log.Printf("[timer] %s %s -> %d 耗时 %s",
            c.Request.Method, c.Request.URL.Path, c.Writer.Status(), cost)
    }
}

「Next 之后才有的信息」是中间件设计的关键：耗时、最终状态码（c.Writer.Status()）都必须在 c.Next() 之后读，写在 Next 之前拿到的是零值。

5. CORS：手写版理解预检

浏览器同源策略：前端 localhost:5173 调你的 localhost:8080 属于跨域。对于带 Content-Type: application/json 或自定义头的请求，浏览器会先发一次 OPTIONS 预检，服务端允许了才发真正的请求。手写版把全过程摊开：

middleware/cors.gopackage middleware

import (
    "net/http"

    "github.com/gin-gonic/gin"
)

// CORS 手写版：搞懂每一行，再切官方库
func CORS() gin.HandlerFunc {
    return func(c *gin.Context) {
        origin := c.GetHeader("Origin")
        if origin != "" {
            c.Header("Access-Control-Allow-Origin", origin)      // 回声来源；练习用 * 也可
            c.Header("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,OPTIONS")
            c.Header("Access-Control-Allow-Headers", "Content-Type,Authorization")
            c.Header("Access-Control-Max-Age", "86400")          // 预检结果缓存 1 天
            c.Header("Access-Control-Allow-Credentials", "true") // 需要带 cookie 时才加
        }
        if c.Request.Method == http.MethodOptions {
            c.AbortWithStatus(http.StatusNoContent) // 预检到此为止，绝不进业务 handler
            return
        }
        c.Next()
    }
}

生产上换官方库 go get github.com/gin-contrib/cors：

main.goimport "github.com/gin-contrib/cors"

r.Use(cors.New(cors.Config{
    AllowOrigins:     []string{"http://localhost:5173"}, // 生产列白名单，别 * 到底
    AllowMethods:     []string{"GET", "POST", "PUT", "DELETE", "OPTIONS"},
    AllowHeaders:     []string{"Content-Type", "Authorization"},
    AllowCredentials: true,
}))

验证 CORS 只靠 curl 不够（curl 没有同源策略，永远不会"被拦"）。终极验证是浏览器：明天起项目分层后，第 6 周会真的用前端页面来打这些接口。今天先用 curl -X OPTIONS 模拟预检，确认响应头齐全。

6. 鉴权中间件雏形

第 4 周才学 JWT，今天先用「写死的 token」把骨架搭起来——流程一模一样，以后只是把比较逻辑换成验签：

middleware/auth.gopackage middleware

import (
    "net/http"
    "strings"

    "github.com/gin-gonic/gin"

    "gin-api/pkg/response"
)

const fixedToken = "go-fullstack-2026"

// RequireAuth 校验 Authorization: Bearer <token>，失败 401 + code 1005
func RequireAuth() gin.HandlerFunc {
    return func(c *gin.Context) {
        got := c.GetHeader("Authorization")
        if !strings.HasPrefix(got, "Bearer ") || strings.TrimPrefix(got, "Bearer ") != fixedToken {
            c.AbortWithStatusJSON(http.StatusUnauthorized, response.Body{
                Code: response.CodeTokenInvalid, Message: "token 缺失或无效", Data: nil,
            })
            return
        }
        c.Set("userID", 1) // 把"当前用户"塞进上下文，下游 handler 用 c.Get/c.MustGet 取
        c.Next()
    }
}
main.gowrite := r.Group("") // 只给写操作挂鉴权，读接口保持公开
write.PUT("/users/:id", middleware.RequireAuth(), updateUser)
write.DELETE("/users/:id", middleware.RequireAuth(), deleteUser)

7. 层间信箱：c.Set / c.Get 传递请求级数据

中间件解析出的东西（用户 ID、请求 ID、语言偏好）不该塞进全局变量，Gin 提供了请求级键值空间 c.Keys：

main.go// 写入（鉴权中间件里，见第 6 节）
c.Set("userID", 1)

// 读取（任意下游 handler / 中间件「出」阶段）
if v, exists := c.Get("userID"); exists {
    uid := v.(int)              // 取出来是 any，需要断言回原类型
    fmt.Println("当前用户:", uid)
}
uid := c.GetInt("userID")       // 更推荐：带类型的便捷方法，取不到给零值
name := c.MustGet("userID").(int) // 断言失败会 panic——只在「前面必挂鉴权」时敢用
方法取不到时使用建议
c.Get(k)返回 (nil, false)最安全，配 exists 分支
c.GetInt/GetString…返回零值业务默认值场景，配合「零值 = 未登录」判断
c.MustGet(k)panic（被 Recovery 兜 500）链路有强约束时用，失败要在日志可查

第 4 周学 JWT 后，auth 中间件验签得到 userID + role，依旧走 c.Set；handler 一行都不用改——中间件换芯、上层无感，这就是今天把接口写成「从 c.Get 拿用户」而不是「解析 Header」的原因。

常见坑（新手 100% 会踩）

坑现象正确姿势
Abort 后不 return你以为拦住了，其实本函数继续往下跑，重复写响应c.Abort() / AbortWithStatusJSON 之后立刻 return
Next 后写响应handler 已经写完 JSON，中间件又 c.JSON(...)，日志报 superfluous response.WriteHeader call中间件「出」阶段只读（Status/耗时），要改响应体请三思；重写响应用 c.Writer.Write(...) 前检查 c.Writer.Written()
注册顺序错鉴权中间件 Use 在业务路由之后，前面的路由裸奔Use 只影响之后注册的路由；启动时用 go run 打印的 Routes 列表自查
Abort 想取消已发出的响应handler 已经写了一半 body，Abort 拦不住字节流Abort 的语义是「阻止内层继续执行」，不是「回滚响应」；要在写响应之前判断
OPTIONS 漏进业务 handler预检返回 404/405，浏览器报 CORS 失败（报错极具误导性）CORS 中间件必须对 OPTIONS AbortWithStatus(204)，且注册在鉴权之前（预检不带 Authorization 头！）
在 goroutine 里用 c请求结束后 c 被回收，偶发 panic/数据错乱今天先记住：c 不能跨 goroutine 用；要异步须 c.Copy()（第 5 周细讲）
