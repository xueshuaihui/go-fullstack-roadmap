context：取消与超时

前几天的遗留问题：select + time.After 超时了，可那个慢 goroutine 还在继续烧资源——超时只是"我不等了"，不是"你别干了"。今天要学的 context.Context 就是 Go 标准的"喊停机制"：一个信号从请求入口一路传到底，告诉所有下游 HTTP 调用、数据库查询、worker——这活儿不用干了，撤。它是 Go Web 后端每个函数的第一个参数，没有例外。

课前须知：给 JS 开发者的一句话

JS 世界其实有一模一样的东西：浏览器 fetch(url, { signal }) 里的 AbortController/AbortSignal。Go 的 context.Context 就是"官方 AbortSignal + 超时 + 每请求元数据"的三合一加强版，而且整个生态（net/http、database/sql、GORM、pgx、k8s client）都约定俗成地接受它。你在 JS 里"想起来才传 signal"，在 Go 里函数签名第一个参数就是 ctx，编译器替你逼所有调用方传。

知识讲义

1. context.Context 是什么

它就是一个接口，方法少得可怜：

接口定义（标准库 context）type Context interface {
    Done() <-chan struct{} // 取消信号：取消后此 channel 关闭并可读
    Err() error             // 为何取消：context.Canceled 或 context.DeadlineExceeded
    Deadline() (time.Time, bool) // 截止时间，没有则 ok==false
    Value(key any) any     // 请求级小数据：requestID、已解析的 user 等
}

根 context 有两个：context.Background()（程序根，偶尔在 main/初始化用）和 context.TODO()（"还没想好传什么"的占位符）。所有其它 context 都从它们逐层派生。记一条纪律：ctx 只用作参数往下传，绝不存进 struct 字段（除非实现 http.Request 这类标准结构）。

2. WithCancel：手动喊停

派生方法都返回"新 context + 停止函数 cancel"。取消的实现正是前两天学的 channel 关闭：cancel() 一调用，ctx.Done() 这条 channel 被关闭，所有阻塞在 <-ctx.Done() 上的 goroutine 同时醒来：

main.gopackage main

import (
    context
    fmt
    time
)

func worker(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Printf("worker%d 收到停工信号: %v\n", id, ctx.Err())
            return
        case <-time.After(300 * time.Millisecond):
            fmt.Printf("worker%d 干活中…\n", id)
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel() // 纪律：拿到 cancel 必 defer，防资源泄漏

    go worker(ctx, 1)
    go worker(ctx, 2)

    time.Sleep(1 * time.Second)
    fmt.Println("main: 宣布取消")
    cancel() // 一声令下，所有监听者同时收到
    time.Sleep(300 * time.Millisecond) // 等 worker 打最后一行日志
}

为什么 cancel() 之后所有阻塞在 <-ctx.Done() 的 goroutine 都能醒？因为从已关闭的 channel 接收会立即返回零值（day2 学过的特性）——关闭一条 channel 等于向全世界所有接收者广播。这就是 context"广播取消"的底层原理。

3. WithTimeout 与 WithDeadline：到点自动喊停

超时是取消的最常见特例。WithTimeout(parent, 2*time.Second) 等价于"2 秒后自动 cancel()"；WithDeadline 则是给定一个具体时刻（如 time.Now().Add(90*time.Second)）：

ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel() // 即使提前完成也要 cancel：释放内部定时器

select {
case <-doSlowTask():
    fmt.Println("任务完成")
case <-ctx.Done():
    fmt.Println("失败:", ctx.Err()) // context deadline exceeded
}
派生方法触发取消的时机ctx.Err() 的值
WithCancel(parent)你手动调 cancel()context.Canceled
WithTimeout(parent, d)d 之后context.DeadlineExceeded
WithDeadline(parent, t)时刻 t 到，或 parent 先取消（取更早者）对应上两者
WithValue(parent, k, v)不取消，只携带请求级值—

子 context 永远不晚于父 context 取消——父树任一节点断，整棵子树全断（传播性）。所以"给整个请求设 5 秒预算"只需在入口派生一次，深处的每次 DB 查询再派生更短的局部超时即可。另外：WithValue 只放"这个请求是谁/为了什么"（requestID、user），别把业务参数塞 context 当隐式传参通道。

4. HTTP 场景：ctx 的两端

入口端：每个进入 handler 的请求自带一个 context——客户端还在不在听？浏览器一关标签页/用户按取消，net/http（及 Gin 的 c.Request()）就把这个请求的 context cancel 掉，你借它省算力。出口端：你发起的下游请求要 http.NewRequestWithContext 才会继承超时预算，否则"上游已撤、下游还在烧钱"：

handler.go（Gin 版）func reportHandler(c *gin.Context) {
    ctx := c.Request.Context() // 请求级 ctx：客户端断连即 cancel

    // 出口：下游 HTTP 调用继承 ctx（再叠一层 2 秒局部超时）
    callCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    req, _ := http.NewRequestWithContext(callCtx, http.MethodGet, "http://localhost:8080/mock-slow?d=1s", nil)
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        // ctx 超时/取消时 err 里包装着 callCtx.Err()
        c.JSON(502, gin.H{"error": err.Error()})
        return
    }
    defer resp.Body.Close()

    // GORM 同理：所有方法都有 WithContext 变体
    var users []User
    if err := db.WithContext(callCtx).Find(&users).Error; err != nil {
        c.JSON(500, gin.H{"error": err.Error()})
        return
    }
    c.JSON(200, users)
}

长任务里还要主动"查岗"：每做一阵就 non-blocking 地探一眼 ctx，发现取消就提前 return：

func heavyLoop(ctx context.Context) error {
    for i := 0; i < 100; i++ {
        select {
        case <-ctx.Done():
            return ctx.Err() // 第 37 次迭代时遇到取消，立刻收摊
        default:
        }
        doChunk(i)
    }
    return nil
}

签名规范从第 1 周就该遵守：ctx 是函数第一个参数、命名就叫 ctx、不传 nil（没有就用 context.Background()）。库函数若收到 ctx == nil，按规范应视同已取消或直接返回错误。

5. 一张图记住传播链

context 树Background                    // 进程根
 └─ reqCtx（r.Context()，浏览器断连 → cancel）
     └─ ctx5s = WithTimeout(reqCtx, 5s)      // 整请求预算 5 秒
         ├─ ctxA = WithTimeout(ctx5s, 2s)    // 下游调用 A：2 秒
         ├─ ctxB = WithTimeout(ctx5s, 3s)    // 下游调用 B：3 秒
         └─ ctxDB = WithTimeout(ctx5s, 1s)   // GORM 查询：1 秒
// reqCtx 一取消，下面所有节点瞬间全部取消——父断子必断

明天周日项目里的 errgroup.WithContext 就是自动帮你造这棵树：组里任何一个任务失败，其余任务立刻收到取消。

今日练习

练习 1：WithTimeout 观察取消日志（必做，20 分钟）

写一个 slowJob(ctx, name, cost)：内部按 100ms 一格循环共 cost 时长，每格 select 探一次 ctx；main 里给 2 秒超时的 ctx 同时交给一个 1 秒任务和一个 5 秒任务。预期输出：1 秒任务正常完成，5 秒任务在约 2 秒时打印 被取消: context deadline exceeded 后 return。

参考答案 
package main

import (
    context
    fmt
    sync
    time
)

func slowJob(ctx context.Context, wg sync.WaitGroup, name string, cost time.Duration) {
    defer wg.Done()
    for elapsed := time.Duration(0); elapsed < cost; elapsed += 100 * time.Millisecond {
        select {
        case <-ctx.Done():
            fmt.Printf("%s 被取消: %v（已跑 %v）\n", name, ctx.Err(), elapsed)
            return
        case <-time.After(100 * time.Millisecond):
        }
    }
    fmt.Println(name, "正常完成")
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    var wg sync.WaitGroup
    go slowJob(ctx, wg, "快任务", 1*time.Second)
    go slowJob(ctx, wg, "慢任务", 5*time.Second)
    wg.Wait()
}
练习 2：3 秒超时的慢接口 + 客户端提前 abort（30 分钟）

用标准库起一个服务：GET /slow?d=10s handler 按 500ms 一格模拟 10 秒工作，每格检查 r.Context().Done()，被取消就打日志 "客户端已离开，提前收工" 并 return；正常完成则回 200。另开终端：curl localhost:8080/slow & 后立刻 pkill curl（或 curl --max-time 2），观察服务端日志在约 2 秒时出现取消行，且 ctx.Err() 是 context.Canceled。

参考答案核心片段 
func slow(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()
    for i := 0; i < 20; i++ { // 20 格 × 500ms = 10s
        select {
        case <-ctx.Done():
            log.Println("客户端已离开，提前收工", ctx.Err())
            return
        case <-time.After(500 * time.Millisecond):
        }
    }
    fmt.Fprintln(w, "10 秒到，结果如下…")
}

对照实验：把 select 的 ctx 分支删掉再 abort 一次，服务端日志显示它傻跑满 10 秒——这就是"ctx 不传到底，取消就是空话"。

练习 3：下游调用继承超时（20 分钟）

给练习 2 的服务加一个 GET /proxy-slow：handler 用 http.NewRequestWithContext 调本机 /slow?d=10s，并套 WithTimeout(r.Context(), 2s)。用 curl 访问 /proxy-slow，确认约 2 秒即返回错误（而非 10 秒），且服务端 /slow 一侧也几乎同时打出取消日志——证明超时沿 context 树传下去了。

参考答案要点 
ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", "http://localhost:8080/slow?d=10s", nil)
resp, err := http.DefaultClient.Do(req)
if err != nil {
    http.Error(w, "下游超时/取消: "+err.Error(), 504)
    return
}

关键点：/slow 也能感知取消，是因为 client 侧 ctx 取消会断开 TCP 连接，server 侧 r.Context() 随之 cancel。若忘了 NewRequestWithContext 而用了裸 http.Get，下游 /slow 会被傻等到 10 秒——这就是验收里"超时不生效"的经典成因。

常见坑（新手 100% 会踩）

坑现象正确姿势
ctx 不传到底超时/取消只在入口"看起来生效"，深处的 http.Get、db.Find 照跑不误，资源照烧凡是能接 ctx 的 API 一律接：NewRequestWithContext、db.WithContext、自定义函数第一参数 ctx
忘了 defer cancel()WithTimeout 的内部定时器与父子关联不释放，go vet 直接报 the cancel function is not used on all paths (possible context leak)派生后下一行永远写 defer cancel()，哪怕 ctx 会先到期
把取消信号"吞"在循环里长循环不 select ctx，cancel 了也跑完，接口超时后进程还在空转迭代式任务每轮查岗（讲义第 4 节模板）；阻塞式收发改成 select + ctx.Done() 分支
往 ctx 里塞业务参数 / 自己 new ctx 传下游取消链断裂：handler 里 context.Background() 重起炉灶，客户端断连没人知道WithValue 只放请求级元数据；下游派生永远以 r.Context() 为 parent
误以为 ctx 能强行杀死 goroutinecancel 后代码没监听 Done，照跑不误context 是协作式取消：信号已广播，接不接全看你写没写 select

今日名词卡

术语一句话解释
context.Context沿调用链传递的"取消信号 + 截止时间 + 请求级值"三合一载体
Done()返回只读 channel，取消那一刻被 close，所有接收者同时醒来
deadline / timeout截止时刻 / 相对时长，Err() 报 context.DeadlineExceeded
传播树子 ctx 随父取消、父不随子取消；父断子必断
协作式取消Go 不能强杀 goroutine，只能广播信号由任务自己体面收摊
