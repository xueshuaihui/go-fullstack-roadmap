Mutex 与竞态检测

昨天说"状态大家改时用锁"，今天正面迎战。你会先亲手让程序崩溃——多个 goroutine 同时写一个 map，Go 会毫不留情地当场判死刑；然后学会两样武器：sync.Mutex（互斥锁）保护共享状态，-race（竞态检测器）抓出你没锁漏的地方。「并发代码必须过 go test -race」是 Go 团队的工程底线，也是本手册第 5 周验收标准第三条。

课前须知：给 JS 开发者的一句话

你过去几乎不需要"锁"这个概念：JS 单线程，一个函数从第一行到最后一行不会被人插队，这就是天然的原子性。Go 里同样十行代码，可能被另一个核上的 goroutine 从中间劈开穿插执行。锁的本质，就是人为把你选中的几行代码变回"JS 那样不可打断的一整块"。

1. 案发现场：并发写 map 直接 fatal error

Go 的内置 map 不是并发安全的，它甚至自带"并发写报警器"。day2 练习 2 里"不加锁 append / 多个 goroutine 写 map"的遗留问题，今天正式引爆：

main.gopackage main

import (
    fmt
    sync
)

func main() {
    m := make(map[int]int)
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            m[n] = n // 多个 goroutine 同时改同一张 map 的内部结构
        }(i)
    }
    wg.Wait()
    fmt.Println(len(m))
}
运行结果（不是 error，是 fatal error）$ go run main.go
fatal error: concurrent map writes

goroutine 27 [running]:
runtime.mapassign_fast64(...)
main.main.func1(0x1a?)
        /Users/you/w5day3/main.go:14 +0x5c
created by main.main in goroutine 1
        /Users/you/w5day3/main.go:12 +0x88
exit status 2

注意用词：这是 fatal error，不可 recover、直接杀死进程。换个角度它是幸运的——map 帮你当场抓到现行。更可怕的是那些"不崩溃但结果错"的竞态（比如练习 2 里不加锁的 append，偶尔少几个元素，没人发现）。所以光靠 map 报警远远不够，引出今天的二号主角 -race。

2. sync.Mutex：把一段代码变成"独舞"

互斥锁只有两个动作：Lock()（拿到钥匙进屋，别人只能在门外等）和 Unlock()（出来还钥匙）。规范写法是拿到锁的下一行就 defer 解锁，保证任何 return/panic 路径都不会把锁忘在手里：

var mu sync.Mutex
var m = make(map[int]int)

func write(n int) {
    mu.Lock()
    defer mu.Unlock() // defer 让"锁住的范围"= 函数体，永不泄漏
    m[n] = n
}

把上面练习代码里的 m[n] = n 用锁包住，1000 个 goroutine 瞬间安分。两条纪律：

  • 临界区越小越好。只把真正碰共享变量的语句锁进去；在锁里做网络请求、sleep，等于抱着麦克风不让别人开会——并发度归零。
  • 同一个数据的每一处读写都要过同一把锁。99 处加锁 + 1 处裸奔 = 没加锁。读操作也一样（map 并发读+并发写同样是 fatal）。

JS 里 Mutex 没有对应物，硬要类比：Lock() 之后的代码块 ≈ 一个不可被事件循环打断的同步函数。但别忘了 Go 里门外真的站着一排等着的 goroutine，它们会被真正阻塞（且不吃 CPU，调度器直接让它们睡）。

3. sync.RWMutex：读多写少的优化

普通 Mutex 连"两个人同时只读"都要排队——其实读读之间不会冲突。RWMutex 把锁分成两种：RLock/RUnlock（读锁，可多人同时持有）与 Lock/Unlock（写锁，独占）。适合缓存、配置这类"天天有人查、偶尔有人改"的数据：

var rw sync.RWMutex
var cache = map[string]string{"k": "v"}

func get(k string) string {
    rw.RLock()      // 读锁：成百上千个读者可同时进入
    defer rw.RUnlock()
    return cache[k]
}

func set(k, v string) {
    rw.Lock()       // 写锁：独占，来得晚的读者全部排队
    defer rw.Unlock()
    cache[k] = v
}

别反射性地"读多就用 RWMutex"。读锁本身也有计数开销，读操作极短（一次 map 取值）时 RWMutex 常比普通 Mutex 更慢；而且写者长期抢不到独占权会饿死。默认用 Mutex，压测证明读锁是瓶颈再换。

4. 死锁四要素：知道才能避开

锁用过头的结局是死锁（deadlock）：所有人都在等所有人，谁也无法前进。学术上四个条件同时成立才会死锁，破坏任意一条即可预防：

条件含义常用破解
互斥资源（锁）同一时刻只能被一人持有改无锁结构（atomic）或 channel
持有并等待拿着一把锁的同时去等另一把一次把所有锁按固定顺序拿齐
不可剥夺锁不能被外力抢走，只能持有者自己放带超时的等待（Go 的锁本身不支持，要用 context/channel 模拟——context 明天 D4 正式讲，今天知道有这条路即可）
循环等待A 等 B 的锁、B 等 A 的锁，成环全局约定加锁顺序（最实用），杜绝交叉持锁

Go 运行时能检测到"所有 goroutine 都睡着"这种全局死锁并直接 fatal error: all goroutines are asleep - deadlock!；但两个 goroutine 互等、其余 goroutine 还在干活的那种局部死锁，运行时救不了你，只能靠 code review 和压测。

5. sync/atomic：单个数字的无锁计数

counter++ 看着一行，机器上是"读-改-写"三步，两个 goroutine 交错就丢更新。如果只是一个数字的增减比较，用 sync/atomic 让 CPU 直接保证这三步不可分，比锁轻得多：

package main

import (
    fmt
    sync
    sync/atomic
)

func main() {
    var counter int64
    var wg sync.WaitGroup
    for i := 0; i < 10000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            atomic.AddInt64(&counter, 1) // 原子自增，永丢不了
        }()
    }
    wg.Wait()
    fmt.Println(atomic.LoadInt64(&counter)) // 稳定输出 10000
}

选型速查：单数字加减 → atomic；复合结构（map/struct/多字段一致性）→ Mutex；数据需要在 goroutine 间移交所有权 → channel。拿不准就用 Mutex，它最不容易用错。

6. -race：让隐形竞态现形

把今天学到的串起来——下面这段只有一个共享 int、不崩溃、多数时候"看起来对"，只有竞态检测器能抓它：

main.gopackage main

import (
    fmt
    sync
)

func main() {
    var wg sync.WaitGroup
    count := 0
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            count++ // 第 13 行：读-改-写无保护
        }()
    }
    wg.Wait()
    fmt.Println(count) // 每次输出都不同：873、921、956……
}
shell$ go run -race main.go   # 测试时用 go test -race ./...
==================
WARNING: DATA RACE
Write at 0x00c0000b4028 by goroutine 9:
  main.main.func1()
      /Users/you/w5day3/main.go:13 +0x38

Previous write at 0x00c0000b4028 by goroutine 7:
  main.main.func1()
      /Users/you/w5day3/main.go:13 +0x4c

Goroutine 9 (running) created at:
  main.main()
      /Users/you/w5day3/main.go:11 +0x5c
==================
923
Found 2 data race(s)
exit status 66

逐行认脸：① WARNING: DATA RACE 开头即有竞态；② Write at 0x... 谁在何时访问了同一块内存（Write/Read）；③ Previous write ... by goroutine 7 上一次访问是谁——两次堆栈就是冲突的两名凶手，直接给出文件行号；④ Goroutine created at 涉案 goroutine 在哪被 go 出来的；⑤ 末尾 Found N data race(s) 且进程以非 0 退出码失败——CI 里 go test -race 正是靠退出码卡住合并的。

-race 有性能开销（约 2–10 倍），永远不要带进生产构建；它只能发现"实际发生过的"交错，没跑到的路径不代表没竞态。所以它必须常驻测试环节，而不是出事后才想起。

今日练习

练习 1：制造 → 定位 → 修复一条龙（必做，30 分钟）

用讲义第 6 节的 count++ 程序完成三步：① 不加任何保护 go run 三遍，记录三个不同的错误结果；② go run -race 抓到报告，指出报告里"两名凶手"分别是哪两个 goroutine、哪一行代码；③ 分别用 Mutex 和 atomic 两种方式修复，确认输出恒为 1000 且 -race 干净（无 WARNING）。

参考答案 
// 修复 A：Mutex
var mu sync.Mutex
mu.Lock()
count++
mu.Unlock()

// 修复 B：atomic（count 需改成 int64）
atomic.AddInt64(&count, 1)

报告中 Write at 0x00c... 与 Previous write ... by goroutine 7 都指向 main.go 第 13 行的 count++——两处写、无任何同步，属于最典型的写写竞态。

练习 2：并发安全计数器结构体（25 分钟）

把练习 1 封装成类型：定义 type Counter struct { mu sync.Mutex; n int }，提供方法 Inc() 与 Value() int，10 个 goroutine 各 Inc 100 次，最终 Value 恒为 1000。注意方法必须用指针接收者——想想为什么（提示：值接收者锁的是副本）。

参考答案 
type Counter struct {
    mu sync.Mutex
    n  int
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}

func (c *Counter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n
}

// 使用时：
c := &Counter{} // 注意是 &，Counter 不可拷贝

若写成值接收者 func (c Counter) Inc()，每次调用锁的、改的都是 c 的副本，原值纹丝不动，且 go vet 会报 passes lock by value。这个类型模板就是你以后所有"内存 session 表 / 内存统计面板"的标准底子。

练习 3：读多写少的 RWMutex 实测（20 分钟）

写一个 map[string]int 缓存，启动 100 个只读 goroutine + 5 个写 goroutine（各跑 1 万次）。先全程用 Mutex，再换成 RWMutex（读走 RLock），用 time.Since 比较两种实现总耗时。把结论写进笔记：你的机器上谁赢了？和讲义第 3 节的警告对得上吗？

参考答案要点

读操作只有一行 map 取值时，RWMutex 与 Mutex 差距通常在一成上下，甚至 Mutex 略快（读锁计数也有开销）；把读操作改重（循环拼接字符串）后 RWMutex 才明显赢。结论：换锁之前先压测，别凭教条。本练习两种写法都必须过 go run -race。

常见坑（新手 100% 会踩）

坑现象正确姿势
只锁写、不锁读map 并发读写照样 fatal error；struct 读到"半更新"状态同一数据的所有读写路径使用同一把锁
忘 Unlock / 提前 return第一轮正常，第二轮 Lock 永久阻塞——程序挂死Lock 的下一行永远写 defer Unlock()
锁的粒度过大锁里 sleep/发 HTTP，全部 goroutine 排长队，"并发了但没完全并发"临界区缩到几行以内；耗时操作放锁外，结果拿回来再加锁合并
把带锁结构体按值传参go vet 报 copylocks；锁副本导致两边各锁各的指针接收者 + 传 *T；WaitGroup/Mutex 同理不可拷贝
对 atomic 的错觉两个 atomic 各自安全，但 if n < limit { n++ } 两步合起来照样超卖跨多个值的复合判断要么用锁，要么用 atomic.CompareAndSwapInt64(&n, old, old+1) 这类接口（"值还是我刚才读到的那个才改"，把两步并成一步；今天不要求会写，认得即可）
