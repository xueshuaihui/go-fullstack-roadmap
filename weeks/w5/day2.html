channel 与 select

昨天你用 WaitGroup 解决了"等"，但没解决"拿结果"——goroutine 里算出来的东西还在它自己手里。今天的 channel（通道）就是 goroutine 之间递东西的传送带，也是 Go 并发哲学的正面表达：不要通过共享内存来通信，而要通过通信来共享内存。再配上 select，你还能同时盯着多条传送带、谁先来收谁。

承接上周：第 4 周 D4 你照抄的优雅关闭里有这么一行——<-ctx.Done()，main 挂在它上面等 SIGTERM，等来了才继续走 srv.Shutdown(shutCtx)。当时它被当作"模板里必须照抄的一行"，而它此刻的动作正是今天要讲的 channel 接收：<- 取不到值就一直挂住，值（或 close）一到就全部醒来。昨天（D1）讲了怎么起 goroutine，今天讲它们之间怎么递东西，第 4 天再把 signal.NotifyContext／Shutdown 那套 context 从原理上讲完——上周的欠账这周全还清。

课前须知：给 JS 开发者的一句话

JS 里在两个异步任务之间传数据，靠的是"把结果 return 出来给 await 方"或闭包共享变量——因为只有一个线程，共享变量永远不会"同一瞬间被两个人改"。Go 有多个真并行线程，直接共享变量天天都是事故现场（明天 -race 会让你大开眼界）。channel 相当于给你一条带锁的、只能单件传递的队列：数据从这边放进去，所有权就转移了，那边拿出来用——没有人再同时碰它。

1. 无缓冲 channel：一次同步握手

make(chan T) 创建的通道没有容量，发送方 ch <- v 会一直阻塞，直到某个接收方 <-ch 来取——两个 goroutine 像换手接力棒，必须同时到位才算完成一次传递。这也是它叫"同步握手"的原因：

main.gopackage main

import (
    fmt
    time
)

func main() {
    done := make(chan struct{}) // struct{} 不占空间，纯当信号弹用

    go func() {
        time.Sleep(2 * time.Second)
        fmt.Println("后台任务完成")
        done <- struct{}{} // 发送信号：没人接就一直卡在这
    }()

    fmt.Println("main 等待握手…")
    <-done // 接收信号：这一行等价于昨天的 wg.Wait()，且绝不会多等一秒
    fmt.Println("收到信号，安全退出")
}

对比昨天的 time.Sleep 假等待：<-done 是精确等待——任务 2 秒完成它就 2 秒醒，完成得更快/更慢都不影响正确性。昨天练习 1 里"Add 挪进 goroutine 偶发提前退出"的问题，用 channel 改写后天然不存在。

2. 有缓冲 channel：带容量的小仓库

make(chan T, n) 给通道加一个长度 n 的环形队列：队列没满，发送不阻塞；队列没空，接收不阻塞。缓冲只改变阻塞时机，不改变"谁取走算传递完成"的语义。

main.gopackage main

import fmt

func main() {
    ch := make(chan int, 3) // 容量 3

    ch <- 1 // 满之前发送不阻塞
    ch <- 2
    ch <- 3
    fmt.Println("len/cap:", len(ch), cap(ch)) // 3 3

    fmt.Println(<-ch) // 取走一个，腾出位置
    go func() { ch <- 4 }() // 否则这行会永久阻塞，写成 goroutine 演示非死锁
    fmt.Println(<-ch, <-ch, <-ch)
}

新手误区：给 channel 加缓冲"以提高性能"。缓冲满了照样阻塞，而且会把死锁从"立刻发生"变成"跑半小时才发生"，更难查。第一原则：先想清楚通信结构，默认用无缓冲；只有"生产突发的快、消费稳定的慢"这种削峰场景才加缓冲，且容量要有依据。

3. range 接收、close 与 ", ok"

接收方可以用 for v := range ch 持续收，直到通道被发送方 close。注意三铁律：① 只能由发送方关闭；② 向已关闭通道发送会 panic；③ 从已关闭通道接收不阻塞，返回零值，靠 ok 辨别"这是真数据还是关闭后的零值"：

main.gopackage main

import fmt

func main() {
    ch := make(chan int, 5)
    go func() {
        for i := 1; i <= 5; i++ {
            ch <- i
        }
        close(ch) // 忘写这行，下面的 for range 永远收不完 → 死锁
    }()

    for v := range ch { // 通道关闭且取空后自动退出循环
        fmt.Println("收到", v)
    }

    v, ok := <-ch // 关闭后再收：立即返回零值，ok == false
    fmt.Println(v, ok) // 0 false
}

4. 通过通信共享内存 vs 用锁保护共享内存

Go 官方格言出自 Rob Pike。落到工程上其实就一句话：当数据的"所有权"需要在 goroutine 之间流转（典型：任务进、结果出）时用 channel；当一份状态被多个 goroutine 高频读写、谁也带不走（典型：缓存 map、计数器）时用锁（明天讲 Mutex）。两种都是合法武器，别教条。下面两格是伪码示意，不用跑：compute() 代表任意函数，mu 是明天正式登场的 sync.Mutex，stats 是一张公共 map：

channel 风格（伪码示意）// 结果的所有权从 worker 转移到汇总方，worker 之后不再碰它
results := make(chan string)
go func() { results <- compute() }()
fmt.Println(<-results)
锁 风格（伪码示意）// stats 是公共账本，人人要改一行，不存在"交给谁"
mu.Lock()
stats[url]++
mu.Unlock()

JS 类比：channel 像把结果 postMessage 给 Worker 后移交副本（发出去的那份就不归你了）；锁像两个模块直接读写同一个全局对象——在 JS 里之所以没事，纯粹因为单线程不会"同时"发生。别把后者当理所当然，Go 里它就是竞态。

5. select：同时盯多条 channel

select 之于 channel，相当于 switch 之于值：列出多个收发分支，哪个先就绪执行哪个；多个同时就绪则随机挑一个（防止饿死）。加一个 default 分支就变成非阻塞探测；配 time.After 就是最常用的超时写法：

main.gopackage main

import (
    fmt
    time
)

func main() {
    slow := make(chan string)
    fast := make(chan string)
    go func() { time.Sleep(3 * time.Second); slow <- "慢服务回来了" }()
    go func() { time.Sleep(300 * time.Millisecond); fast <- "快服务回来了" }()

    select {
    case s := <-slow:
        fmt.Println(s)
    case s := <-fast:
        fmt.Println(s) // ← 300ms 后命中这里，慢服务被彻底放弃
    case <-time.After(2 * time.Second):
        fmt.Println("两秒内没人响应，超时") // 永不触发，仅作演示
    }

    // default 让 select 立即返回，不阻塞：
    select {
    case s := <-slow:
        fmt.Println(s)
    default:
        fmt.Println("现在没货，我先去干别的") // ← 命中
    }
}

time.After(d) 返回一条 channel，d 之后收到一个值——"给它 d 时间，到点没结果就走超时分支"。这正是后天 context 超时控制的简化前身，也是周日项目"某个 URL 超过 5 秒返回部分结果"的原型。

6. pipeline：生产者 → 处理 → 汇总

把 channel 首尾相接就构成流水线，每一级只管"从上游收、加工、发下游、close"。这是本周日项目"并发 URL 聚合"的骨架：

main.gopackage main

import fmt

// 生产者：发 1..5 后关闭
func produce() <-chan int {
    out := make(chan int)
    go func() {
        for i := 1; i <= 5; i++ { out <- i }
        close(out)
    }()
    return out // 返回只读 channel，编译期禁止 main 往里发
}

// 处理：平方后转发
func square(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        for v := range in { out <- v * v }
        close(out)
    }()
    return out
}

func main() {
    sum := 0
    for v := range square(produce()) { // 汇总：for range 到流水线尽头
        sum += v
    }
    fmt.Println("平方和:", sum) // 1+4+9+16+25 = 55
}

今日练习

练习 1：用 channel 重写昨天的任务收集（必做，25 分钟）

回看 day1 练习 1：10 个 goroutine 各睡不等时间后打印"完成"。现在改成：每个 goroutine 把 fmt.Sprintf("任务%d完成", id) 发进一条 channel，main 收满 10 条后打印汇总。关键问题：main 怎么知道收够了 10 条？试两种方案：① 数满 10 次（自己维护计数）；② 10 个 worker 共用一个 WaitGroup，main 里再开一个"看守 goroutine"：wg.Wait() 之后 close(ch)，main 用 for range 收。

参考答案（方案 ②，工业标准写法） 
package main

import (
    fmt
    sync
    time
)

func main() {
    results := make(chan string)
    var wg sync.WaitGroup

    for i := 1; i <= 10; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            time.Sleep(time.Duration(id%3) * 200 * time.Millisecond)
            results <- fmt.Sprintf("任务%d完成", id)
        }(i)
    }

    go func() { wg.Wait(); close(results) }() // 看守：最后一个 worker 收尾时关闸

    for s := range results { fmt.Println(s) } // 关闸后 for range 自然结束
    fmt.Println("共收到 10 条结果")
}
练习 2：channel vs WaitGroup+锁，收集结果的两种写法（25 分钟）

并发调用 5 个假 API（各 time.Sleep(1s) 后返回不同字符串），把结果收集进 []string。写法 A：结果 channel + for range；写法 B：WaitGroup + sync.Mutex 保护 append。跑通后回答：哪种写法结果的顺序是完成顺序？哪种你能自己控制存放位置（如 results[i] = ... 按下标写）？各适合什么场景？

参考答案要点

写法 A（channel）：for range 收到的顺序 = 完成顺序，天然适合"先到先处理"的流水线/进度上报。写法 B：预分配 results := make([]string, 5)，每个 goroutine 写 results[i]——不同下标互不重叠时甚至不需要锁；同一切片 append 才必须 mu.Lock()。B 适合"结果要按输入顺序回位"（如 URL 聚合保持入参顺序）。工业代码两种都常见，本周日项目会各用一次。fakeAPI 直接沿用 day1 练习 2 的定义，names 就是 []string{"a","b","c","d","e"}，写法 B 的 import 多一个 sync。

练习 3：select 竞速与超时（20 分钟）

起两个 goroutine：A 在 200ms 后发 "A胜"，B 在 400ms 后发 "B胜"，都发到各自的 channel。用 select 收第一个到达的值并打印；再给整个 select 加 case <-time.After(100*time.Millisecond) 超时分支，把超时缩短到 100ms 观察走超时分支。思考：这个"select 三件套（两个数据源 + 一个 time.After）"结构，离周日项目的"5 秒抓不到就返回部分结果"还差什么？

参考答案 
main.go（片段）a := make(chan string)
b := make(chan string)
go func() { time.Sleep(200 * time.Millisecond); a <- "A胜" }()
go func() { time.Sleep(400 * time.Millisecond); b <- "B胜" }()

// ① 不带超时：200ms 时 A 先到
select {
case s := <-a: fmt.Println(s) // ← 命中这里
case s := <-b: fmt.Println(s)
}

// ② 加超时分支：另起一对，别复用已经收过的 channel（A 早已空，会一直等）
c := make(chan string)
go func() { time.Sleep(200 * time.Millisecond); c <- "C胜" }()
select {
case s := <-c: fmt.Println(s)
case <-time.After(100 * time.Millisecond):
    fmt.Println("100ms 内无人响应") // ← C 要 200ms，命中这里
}
// 把 100ms 改成 300ms，同一个 select 就变成命中 C——两个数字来回调，体感最准

整段贴进 main（import fmt / time）。注意：100ms 超时分支只有把 A 的 200ms 也一起缩短才会命中，否则 select 一定先收到 A——亲手调两个数字各改一次，比背结论有用。

离周日项目还差：① 要等的是一批任务而不是取第一个；② 超时后没完成的 goroutine 需要被取消，不能让它们继续白烧资源——这正是后天 context 要解决的事。

常见坑（新手 100% 会踩）

坑现象正确姿势
忘 close 导致 range 永不结束数据全收到了，但 for range 不退出，最后报 fatal error: all goroutines are asleep - deadlock!发送方发完必须 close；多发送方时用一个 WaitGroup+看守 goroutine 统一关（见练习 1）
向已关闭 channel 发送panic: send on closed channel，整个进程崩溃只有发送方 close，且 close 之后不再发；多 worker 场景由"看守"在所有 worker 结束后统一关
重复 close / 接收方 closepanic: close of closed channel关闭永远是发送方（生产者）的责任，接收方只管收
无缓冲 channel 自己等自己main 里 <-ch，但没人发 → 死锁；或同一段代码里先收后发发送方必须在另一个 goroutine 里；单 goroutine 演示无缓冲收发必死锁，这是语义使然
拿 channel 当队列疯狂塞无缓冲时生产方卡死；有缓冲时内存涨到容量上限再卡死想清楚谁消费、消费多快；背压（producer 被堵住）是特性不是 bug，别用超大缓冲假装解决

术语一句话解释
channel带类型的 goroutine 间传送带，ch <- v 发送、<-ch 接收
