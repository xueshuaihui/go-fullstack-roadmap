课前须知：给 JS 开发者的一句话

在 JS 里你几乎不需要"等线程"，因为根本没有第二个线程：异步靠事件循环，await 之后代码还是一行行顺序执行。在 Go 里，go f() 之后 f 真的可能在另一个 CPU 核上和 main 同时跑。所以 JS 里"忘了 await"顶多是 lint 警告，Go 里"忘了等待"就是程序行为错误——今天的第一课就是这个坑。

知识讲义

1. 并发与并行：一句话版

并发（concurrency）是"同一时间段内处理多件事"的组织方式，并行（parallelism）是"同一时刻真的做多件事"的执行状态。JS 的单线程事件循环是并发但不并行（宏任务微观上仍是一件件做）；Go 程序默认跑在多个 CPU 核上，既并发又并行。Go 谚语的来源 Rob Pike 的说法：并发是处理多条任务线的设计问题，并行是利用不同算力资源执行多条任务线的运行时问题。

JS（浏览器/Node）Go
多任务手段事件循环 + Promise/asyncgoroutine + channel
是否多线程主逻辑单线程（Worker 除外）天生多线程
是否真并行否（IO 由系统底层并行）是（多核同时执行）
CPU 密集型任务卡死主线程丢给另一个 goroutine 即可吃满另一核

2. go func()：两个字母启动一个任务

本页文件怎么放：讲义与练习里有多个 func main，一个 package main 里只能有一个 main——按 W1D2 的老规矩，每节各建一个子目录（如 w5day1/sec2/main.go）分别 go run .，或直接覆盖同一个 main.go 逐节跑。标了"伪码/片段"的格子不用单独跑，旁边都给了可运行版本。

在任意函数调用前加 go，这个调用就进入一个新的 goroutine（Go 协程，由 Go 运行时调度的轻量线程）里执行，当前代码不等待它，立刻往下走：

main.gopackage main

import (
    fmt
    time
)

func say(s string) {
    for i := 0; i < 3; i++ {
        fmt.Println(s)
        time.Sleep(100 * time.Millisecond)
    }
}

func main() {
    go say("goroutine 里打的") // 启动后立即返回，不等
    say("main 里打的")          // 主 goroutine 自己干活
    time.Sleep(1 * time.Second)   // 先粗暴地等 1 秒，第 3 节会解释为什么这是权宜之计
}

goroutine 有多轻？初始栈只有几 KB（OS 线程通常 1–8 MB），起一万个毫无压力。JS 里开一万个 setTimeout 没问题，开一万个线程想都不敢想；Go 里一万个 goroutine 就是日常操作。

顺手转正一处旧代码：第 4 周 D4 优雅关闭里你照抄过的 go func() { srv.ListenAndServe() }() 就是今天这个语法——ListenAndServe 是阻塞调用，必须丢进 goroutine，main 才能继续走到下面的 <-ctx.Done() 等信号。当时"为什么加 go"的疑问，现在有了答案；那行 <-ctx.Done() 本身第 4 天（context）正式展开。

3. 主函数退出不等子 goroutine：一场翻车演示

Go 的规则简单粗暴：main 函数一返回，进程立刻结束，所有还没跑完的 goroutine 直接死亡，不会有任何提示。把等待的那行 Sleep 拿掉试试：

main.gofunc main() {
    for i := 1; i <= 5; i++ {
        go func() {
            fmt.Println("worker 干完活了")
        }()
    }
    fmt.Println("main 退出")
}
运行结果$ go run main.go
main 退出
// 五次 "worker 干完活了" 一行都没打印出来！

最"能骗人"的补救法是 time.Sleep(100 * time.Millisecond)（下面两行是伪码，doHeavyTask 换成练习 2 的 fakeAPI 就能直接跑）：

伪码go doHeavyTask()             // 假设要跑 200ms
time.Sleep(100 * time.Millisecond) // 只等 100ms：偶发丢结果

Sleep 等待是并发代码的头号假朋友。等短了结果丢失、机器忙时偶现、机器闲时正常——这种"今天复现明天复现不了"的 bug 比编译错误可怕一百倍。它的存在价值只有一个：让你亲手体验一次竞态，然后引出真正的解决方案。

4. sync.WaitGroup：三方法扳回一局

WaitGroup 内部就是一个计数器和一把锁：Add(n) 把计数器加 n，每个任务收尾时 Done() 减 1，Wait() 阻塞直到计数器归零。三个方法，永远成套出现：

main.gopackage main

import (
    fmt
    sync
    time
)

func main() {
    var wg sync.WaitGroup

    for i := 1; i <= 10; i++ {
        wg.Add(1) // 注意：Add 必须在 go 之前调用，见下方警告
        go func(id int) {
            defer wg.Done() // defer 保证就算 panic 也会减一
            time.Sleep(time.Duration(id%3) * 200 * time.Millisecond)
            fmt.Println("任务", id, "完成")
        }(i)
    }

    wg.Wait() // 阻塞，直到计数器归零
    fmt.Println("全部 10 个任务完成，main 收工")
}

为什么 wg.Add(1) 要写在 go 前面而不是 goroutine 内部？因为 go 是非阻塞的：main 可能先执行到 Wait()，此时计数器还是 0，Wait 直接放行，程序提前退出——竞态又回来了。规则背下来：Add 在 go 之前，Done 在任务结尾（推荐 defer）。

WaitGroup 是结构体且内部有锁，不能拷贝，要么用 var wg sync.WaitGroup 声明后原地使用，要么以 *WaitGroup 指针传参。别把它作为值参数传给函数。

5. Go 调度器 GMP：三分钟科普

你可能会问：一万个 goroutine，CPU 只有 8 核，怎么排得过来？答案是 Go 运行时自带一个调度器，把三样东西分层管理：G（Goroutine）——你的任务，带着自己的栈和状态；M（Machine）——真正干活的内核 OS 线程；P（Processor）——调度令牌，数量默认等于 CPU 核数（可用 GOMAXPROCS 改），M 必须持有 P 才能执行 G。每个 P 维护一个本地 G 队列，M 拿到 P 后从队列里取 G 跑；G 遇到阻塞系统调用（比如读文件）时，M 会整体让位，P 换一个空闲 M 继续跑别的 G——这就是"一个 IO 卡住不会拖垮全部"的秘密。你写代码时感觉像在单线程世界漫游，底层这套 GMP 机器一直在默默换人。日常开发不需要碰调度器，知道 G=任务、M=线程、P=通行证 这三层关系就够吹一年。

6. 对比 JS：Promise.all 与事件循环

用 JS 最熟的方式做同一件事——并发 5 个"API 调用"并等全部完成：

app.jsconst urls = ["/a", "/b", "/c", "/d", "/e"];
const results = await Promise.all(urls.map(u => fetch(u)));
// 5 个请求几乎同时发出，await 等所有 Promise 落定
main.go（伪码）var wg sync.WaitGroup
for _, u := range urls {
    wg.Add(1)
    go func(url string) {
        defer wg.Done()
        fetch(url)
    }(u)
}
wg.Wait() // ≈ await Promise.all

上面那格是伪码：urls 和 fetch 都没定义（JS 里一个是自己的数组、一个是浏览器内置函数，Go 都得自己给）。落成可跑的 Go 代码只要补上这两样——先假请求、真 sleep，保证离线能跑；D5 的项目里 fetch 才换成真的 http.NewRequestWithContext：

main.gopackage main

import (
    fmt
    sync
    time
)

// fetch 用 sleep 代表一次"API 调用"，与上面 JS 的 fetch(u) 同位
func fetch(url string) string {
    time.Sleep(300 * time.Millisecond)
    return url + " -> 200 OK"
}

func main() {
    urls := []string{"/a", "/b", "/c", "/d", "/e"}
    var wg sync.WaitGroup

    for _, u := range urls {
        wg.Add(1) // Add 在 go 之前（第 4 节的纪律）
        go func(url string) {
            defer wg.Done()
            fmt.Println(fetch(url))
        }(u)
    }
    wg.Wait() // ≈ await Promise.all
    fmt.Println("5 个请求全部返回")
}
运行结果$ go run .
/a -> 200 OK   // 5 行几乎同时冒出来
// ...
5 个请求全部返回
// 总耗时 ≈ 0.3s；改成顺序调用 fetch 就是 5×0.3s ≈ 1.5s

JS 单线程异步 vs Go 多线程真并行。Promise.all 的"同时"是假象：JS 主线程把 5 个 fetch 交给浏览器/系统 IO 层后自己继续跑事件循环，回调仍是排队串行执行的；如果任务里有 for 大循环算 CPU，整个页面卡死。Go 的 5 个 goroutine 则可能被 5 个不同的 M 拿去不同 CPU 核上真正同时执行，算满 CPU 也不影响别的 goroutine。所以：Promise.all ≈ WaitGroup（等待语义相似），但底下是两种完全不同的世界。

练习 1：10 个 goroutine + WaitGroup（必做，20 分钟）

新建目录 w5day1，go mod init w5day1。要求：

  • 启动 10 个 goroutine，每个 time.Sleep 一个随自己编号变化的时长（如 id%3 的 200ms 倍数）后打印 任务 N 完成
  • 先不加 wg.Wait() 跑一遍，观察输出少了什么；再用 WaitGroup 三件套修复，确认 10 行全部出现
  • 把 wg.Add(1) 挪进 goroutine 内部再跑几遍，观察是否偶发提前退出，体会上课时的警告
参考答案 
main.gopackage main

import (
    fmt
    sync
    time
)

func main() {
    var wg sync.WaitGroup
    for i := 1; i <= 10; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            time.Sleep(time.Duration(id%3) * 200 * time.Millisecond)
            fmt.Println("任务", id, "完成")
        }(i)
    }
    wg.Wait()
    fmt.Println("全部完成")
}

不加 Wait() 时通常只看到 全部完成（或零星几行）；Add 挪进 goroutine 后偶尔会在不足 10 行时就通过 Wait——两种现象都是竞态。

练习 2：串行 vs 并发计时（20 分钟）

写 5 个"假 API"函数，每个 time.Sleep(1 * time.Second) 后返回字符串。先顺序调用 5 次并打印总耗时，再用 WaitGroup 并发调用并打印总耗时。记录两个数字（预期约 5s vs 约 1s）——这就是本周日项目验收标准的雏形。

参考答案 
main.go（片段）func fakeAPI(name string) string {
    time.Sleep(1 * time.Second)
    return name + "-ok"
}

start := time.Now()
for _, n := range []string{"a", "b", "c", "d", "e"} {
    fmt.Println(fakeAPI(n))
}
fmt.Println("串行耗时:", time.Since(start)) // ≈ 5.00s

start = time.Now()

练习 3：亲眼见证"循环变量捕获"（15 分钟）

写 for i := 0; i < 5; i++ { go func(){ fmt.Println(i) }() } 加 WaitGroup，用 go run . 跑三遍看输出是否重复；再改写成把 i 作为参数传入 go func(id int){...}(i) 的版本对比。最后执行 go version 确认你的版本 ≥ 1.22，思考两者区别（完整解释在下方"常见坑"表格第一行）。

参考答案与原理 
main.gopackage main

import (
    fmt
    sync
)

func main() {
    var wg sync.WaitGroup

    for i := 0; i < 5; i++ {               // 闭包直接吃 i
        wg.Add(1)
        go func() { defer wg.Done(); fmt.Println("闭包版:", i) }()
    }
    for i := 0; i < 5; i++ {               // 把 i 当参数传进去
        wg.Add(1)
        go func(id int) { defer wg.Done(); fmt.Println("传参版:", id) }(i)
    }

    wg.Wait()
}

Go 1.22 起 for 循环每轮迭代新建变量，闭包捕获的是各自副本，所以两个版本在现代 Go 上都输出 0–4 的乱序但完整的五个数。在 Go 1.21 及更早版本里，旧写法会打印 5 个 5——所有 goroutine 共享同一个 i，等它们跑起来时循环早已结束、i 已经是 5。显式传参写法跨版本都正确，老项目里至今常见，务必认识。

练习 4：眼见为实——CPU 任务真并行（选做，20 分钟）

练习 2 的 sleep 是"假任务"。写一个纯计算的 burn(n int) int64（从 1 累加到 n，n 取 2 亿，实测单份约 0.4–0.8 秒）。先串行跑 4 份计时，再用 WaitGroup 并发跑 4 份计时；然后用 GOMAXPROCS=1 go run main.go 再跑一次并发版。三个数字对比，解释：为什么 GOMAXPROCS=1 时并发不再明显加速？（这题没有陷阱，只有体感。）

参考答案与解读 
main.go（片段）func burn(n int) int64 {
    var sum int64
    for i := 1; i <= n; i++ {
        sum += int64(i) % 7
    }
    return sum
}

// 并发 4 份：每个 burn 丢进一个 goroutine，wg.Wait 后计时
start := time.Now()
var wg sync.WaitGroup
for k := 0; k < 4; k++ {
    wg.Add(1)
    go func() { defer wg.Done(); burn(200_000_000) }()
}
wg.Wait()
fmt.Println("并发 4 份:", time.Since(start))

文件怎么放：burn 写在 main 外面，上面这段贴进 main；串行版把 goroutine 那三行换成直接调用 burn(200_000_000) 四次即可。import 同练习 1。跑并发版时顺手看一眼 top/活动监视器：并发 4 份真的占了 4 个核，GOMAXPROCS=1 时退回 1 个核。

典型结果：串行 4 份 ≈ 4×单份；并发 4 份 ≈ 1×单份多一点（4 核以上时，真并行吃满多核）；GOMAXPROCS=1 时并发退回 ≈ 4×单份——P 只剩 1 个，任意时刻只有一个 goroutine 在执行 Go 代码，退化成"调度器轮流切换"，和 JS 事件循环神似。这一组数字就是"GMP 里 P 的个数=并行度"的直接证据。

常见坑（新手 100% 会踩）

坑现象正确姿势
for 循环变量被 goroutine 共享（旧版本）Go 1.22 之前：for i:=0;i<10;i++ 里起 10 个 goroutine 打印 i，结果全部输出 10——goroutine 真正执行时循环早已跑完，大家共享同一个 iGo 1.22 起官方把每轮迭代改为新建变量，此坑已被语言修复；但传参写法 go func(id int){...}(i) 跨版本安全、意图更显式，老代码审查时仍要认得它
忘了 wg.Done()Wait() 永远不归零，程序死等，最后报 fatal error: all goroutines are asleep - deadlock! 或干脆挂着不退进 goroutine 第一行就写 defer wg.Done()，中途 panic/return 也不会漏减
Add 写在 goroutine 里偶发提前退出，输出缺行，重启又"正常"——典型竞态永远在 go 语句之前 Add
用 time.Sleep 等结果本地正常、线上偶发丢数据Sleep 只配当教学反例，等任务完成一律 WaitGroup/channel（明天学）
拷贝 WaitGroup把 sync.WaitGroup 按值传参，子函数 Done 的是副本，外面 Wait 的还是不归零原地声明使用，或传 *sync.WaitGroup；go vet 能抓出这个错误
