 ├─ sync.WaitGroup：Add（go 之前）/ Done（defer）/ Wait

 ├─ 取消信号 + 截止时间 + 请求级值，Done() 是被广播的 channel

 ├─ worker pool：固定工人 + 任务 channel，并发度是旋钮
 └─ errgroup：Go / Wait / SetLimit / WithContext，首错取消 vs 部分结果的选型

一句话收束全周：goroutine 负责"一起跑"，channel/锁负责"别打架"，context 负责"该停就停"，errgroup 负责"打包收工"。四件套齐了，Go 并发日常就够用了。

概念快问快答（合上讲义答，答不出的回炉）

Q1 · 并发和并行的区别？
答案

并发是"同一时间段处理多条任务线"的组织设计，并行是"同一时刻真的做多件事"的执行状态。JS 事件循环是并发不并行；Go 默认多核真并行。

Q2 · 无缓冲 channel 什么时候发送方不阻塞？
答案

永远阻塞，直到有接收方就位——这就是"同步握手"。想不阻塞只有两条路：加缓冲（make(chan T, n)），或 select+default。

Q3 · 向已关闭 channel 发送 / 重复 close，各是什么后果？
答案

都是 panic：send on closed channel 与 close of closed channel，进程直接崩溃。所以 close 只能由发送方、且只关一次；多 worker 用 WaitGroup+看守 goroutine 统一关。

Q4 · 何时 channel、何时锁、何时 atomic？
答案

数据所有权要在 goroutine 间移交（任务进、结果出）→ channel；一份状态人人读写（缓存、账本）→ Mutex/RWMutex；只动一个数字 → atomic。复合判断（先检查再动手，check-then-act）atomic 也救不了，要么上锁、要么用 D3 坑表里那种"比对再换"的 CAS 接口。

Q5 · context.WithTimeout 到点后，goroutine 一定停吗？
答案

不一定。Go 无法强杀 goroutine，context 是协作式取消：只有代码自己 select 了 ctx.Done()（或把 ctx 传给了支持它的 API）才会停。"ctx 不传到底，超时不生效"是本周验收头号杀手。

Q6 · errgroup 的 WithContext 在聚合场景为什么反而要"吞错误"？
答案

WithContext 派生的 ctx 在首个任务 return error 时立即取消全组——适合"一错全撤"的批处理。聚合 API 要"部分成功也算成功"，所以每个任务把错误写进自己的结果、永远 return nil，errgroup 只当带 SetLimit 的调度器用。

并发怎么测：本周"测试"半张脸

并发代码光靠 curl 手测是不够的——竞态平时不现身。Go 的答案：把压测场景写成单元测试，用 go test -race 当探针。给聚合器补一个针对 fetchOne+结果收集的最小并发测试：

aggregate_test.gopackage main

import (
    context
    net/http
    net/http/httptest
    sync
    testing
    time
)

// httptest 起一个固定延迟的假上游，模拟 5 个 1s 端点并发抓取
func TestFetchOneConcurrent(t *testing.T) {
    slow := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        select {
        case <-time.After(1 * time.Second): fmt.Fprint(w, "pong")
        case <-r.Context().Done():
        }
    }))
    defer slow.Close()

    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    const n = 5
    results := make([]urlResult, n)
    var wg sync.WaitGroup
    start := time.Now()
    for i := 0; i < n; i++ {
        wg.Add(1)
        go func(idx int) {
            defer wg.Done()
            results[idx] = fetchOne(ctx, slow.URL+"?d=1s")
        }(i)
    }
    wg.Wait()

    if cost := time.Since(start); cost > 2*time.Second {
        t.Fatalf("并发 5 个 1s 请求耗时 %v，预期应 ≈1s", cost)
    }
    for i, r := range results {
        if r.Status != 200 {
            t.Errorf("结果 %d 未成功: %+v", i, r)
        }
    }
}
shell$ go test -race -v ./...
=== RUN   TestFetchOneConcurrent
--- PASS: TestFetchOneConcurrent (1.02s)
PASS

三个要点：① 断言的是耗时上界（2 秒红线）——固定 sleep 让这条测试不会因网络波动误报；② -race 让每次 CI 都顺带扫一遍竞态；③ httptest.Server 是 Go 自带的轻量假服务，第 4 周 D5 引入后所有接口测试都靠它，本周把它加上 -race 用来测并发，两条线正式会师。

顺带把 httptest 的另一半补齐：D5 用的是 httptest.NewRecorder()（不起端口，把请求直接灌进 handler 再读 Recorder）；今天这条测试需要给被测代码一个真能访问的 URL，所以用 httptest.NewServer(handler) —— 它在随机端口上起一个临时服务，slow.URL 就是 http://127.0.0.1:59832 这种地址，defer slow.Close() 用完即散。照抄即可，本周不会深讲。

验收清单（全勾才算本周毕业）

为什么验收坚持用固定 sleep 端点？拿真实外网 URL 测"并发≈5 倍加速"，DNS、TLS、限流、网络抖动都会污染数字，今天在明天不过几乎必然发生。/mock-slow?d=1s 把变量锁死为"已知耗时"，1s/5s 就是硬指标——以后你给任何并发功能写验收，第一个念头都该是把不确定性赶出测试。

下周预告：第 6 周 · 全栈联调

从下周起，你熟悉的 React 回来了——但角色变了：不再是"页面里随便 fetch"，而是拿着第 4 周的 JWT 双 token 规范、第 5 周的超时取消意识，去对接一个真正的 Go 后端。五天走完：登录注册对接 → 文章列表/详情（分页搜索）→ 创建编辑删除的权限控制 → axios 拦截器静默刷新（401 时用 refresh token 换发重试）→ CORS/代理/构建。练手项目：React + Go 博客前端，验收要求浏览器里从注册到删帖全流程跑通、token 过期用户无感知。讲义照旧全中文、全部可运行代码、不需要你额外搜索任何资料。

最后三条维护习惯，从这周带到第 8 周：

  • 任何碰共享状态的 PR/提交前，先跑一遍 go vet ./... && go test -race ./...；

  • 并发方案拿不准时，回到选型三问：移交所有权？公共账本？单个数字？——分别对应 channel、Mutex、atomic。
