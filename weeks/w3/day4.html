分页、搜索、排序

课前须知：为什么排序不能「透传」

JS 里你习惯把前端传来的 sortField 直接丢给 db.order(field)（Sequelize 会帮你转义）。GORM 的 Order() 会把字符串原样拼进 SQL——因为它要支持 "created_at desc, id asc" 这种表达式。所以「哪里是占位符、哪里不是」是本周最重要的安全分界线：Where("...", ?) 的参数走占位符安全；Order()、Select()、表名/列名都是直接拼接，必须自己校验。

知识讲义

1. Offset / Limit：分页的两个旋钮

分页 SQL 原理// 第 page 页（page 从 1 开始）、每页 size 条：
//   offset = (page - 1) * size
SELECT * FROM articles ORDER BY created_at DESC LIMIT 10 OFFSET 20;  -- 第 3 页

GORM 写法（两种等价）db.Order("created_at desc").Limit(10).Offset(20).Find(&articles)
db.Limit(10).Offset(20).Find(&articles)   // 顺序无所谓，链式只是攒条件

参数一定要在入口处夹紧（clamp），否则 ?size=-1、?page=99999999 会直接打到数据库：

internal/dto/page.gopackage dto

const (
    DefaultPageSize = 10
    MaxPageSize     = 50   // 对外接口必须有上限，防被刷：size=100000 一次拖库
)

func NormalizePage(page, size int) (int, int) {
    if page < 1 {
        page = 1
    }
    switch {
    case size <= 0:
        size = DefaultPageSize
    case size > MaxPageSize:
        size = MaxPageSize
    }
    return page, size
}

func OffsetOf(page, size int) int { return (page - 1) * size }

2. Count 总数：必须单独跑一条，且不能带 Limit/Order

internal/repository/article.govar total int64

// ✅ 用 Model(&T{}) 才能统计「这个表」；Count 会生成 SELECT count(*)
db.Model(&model.Article{}).Where("user_id = ?", 1).Count(&total)

// ❌ 常见错误：把 Count 接在已有 Limit/Select 的链后面
db.Select("id", "title").Limit(10).Model(&model.Article{}).Count(&total) // 语义混乱，可能得 10

total 必须是「符合条件的所有行数」，与分页无关。所以正确顺序是：同一套 WHERE 条件 → ① Count(&total)，② 再 Order + Limit + Offset + Find。而 GORM 的链式对象是有状态的：Count 之后那条链的字段选择等会影响下一次。标准解法是把条件封装成一个「构造函数」，两处各调一次，见下一节。

3. 分页 DTO 与 PageResult

internal/dto/article.gopackage dto

// query 参数用 form tag 绑定（不是 json tag！）
type ArticleListQuery struct {
    Page int    `form:"page,default=1" binding:"omitempty,min=1"`
    Size int    `form:"size,default=10" binding:"omitempty,min=1,max=50"`

    Keyword string `form:"keyword"`                    // 标题模糊搜索
    UserID  uint   `form:"user_id"`                     // 只看某人
    Tag     string `form:"tag"`                         // 按标签名
    MinView int    `form:"min_views"`                   // 阅读量下限
    From    string `form:"from"`                        // 2026-09-01 起始日期
    To      string `form:"to"`                          // 结束日期
    Sort    string `form:"sort,default=-created_at"`    // -前缀 = desc
}

// Normalize 夹紧页码：非法值不报错，直接修正为安全默认（同包函数，见第 1 节 page.go）
func (q ArticleListQuery) Normalize() (int, int) {
    return NormalizePage(q.Page, q.Size)
}

func (q ArticleListQuery) Offset() int {
    page, size := q.Normalize()
    return (page - 1) * size
}
internal/dto/sort.go（排序白名单）// SortableColumns 白名单：URL 里的 sort 只能映射到这些真实列名
var SortableColumns = map[string]string{
    "created_at": "articles.created_at",
    "views":      "articles.views",
    "id":         "articles.id",
    "title":      "articles.title",
}

// OrderClause 把 "sort=-views" 翻译成安全的 ORDER BY 片段；非法值回落默认
func (q ArticleListQuery) OrderClause() string {
    col, dir := "articles.created_at", "desc"
    s := strings.TrimSpace(q.Sort)
    if s != "" {
        dir = "asc"
        if strings.HasPrefix(s, "-") {
            dir, s = "desc", strings.TrimPrefix(s, "-")
        }
        if ok, exists := SortableColumns[s]; exists {
            col = ok
        } else {
            dir = "desc" // 未知字段 → 整体回落默认排序，绝不拼进去
        }
    }
    return col + " " + dir + ", articles.id desc" // 追加唯一列，保证翻页不重不漏
}
internal/dto/common.gopackage dto

// 统一分页返回体：前端只需要认识这一个形状
type PageResult struct {
    List     any   `json:"list"`
    Total    int64 `json:"total"`
    Page     int   `json:"page"`
    Size     int   `json:"size"`
    TotalPage int64 `json:"total_page"`
}

func NewPageResult(list any, total int64, page, size int) PageResult {
    pages := total / int64(size)
    if total%int64(size) != 0 {
        pages++            // 向上取整：21 条 / 10 = 3 页
    }
    return PageResult{List: list, Total: total, Page: page, Size: size, TotalPage: pages}
}

4. LIKE 模糊搜索：必须参数化

repository 里的正确写法// ✅ 占位符 + 参数：驱动会把 kw 当字面量转义，里面的引号/分号都变普通字符
if kw != "" {
    tx = tx.Where("articles.title LIKE ?", "%"+escapeLike(kw)+"%")
}

// ❌ 危险到不能上生产：字符串拼接 SQL
tx = tx.Where(fmt.Sprintf("title LIKE '%%%s%%'", kw))

亲手验证一下差别（今天最重要的 15 分钟）：

cmd/inject/main.gofunc main() {
    db := mustConnect()
    kw := "' OR '1'='1'"              // 经典注入片段：本想闭合引号

    var safe []model.Article
    db.Where("title LIKE ?", "%"+kw+"%").Find(&safe)
    fmt.Println("参数化：返回", len(safe), "条（正常是 0 条）")

    var bad []model.Article
    db.Where(fmt.Sprintf("title LIKE '%%%s%%'", kw)).Find(&bad)
    fmt.Println("拼接版：返回", len(bad), "条 —— 表被全量泄露了")
}
运行结果$ go run ./cmd/inject
参数化：返回 0 条（正常是 0 条）        // LIKE "%' OR '1'='1%" 被当作要匹配的文本
拼接版：返回 5 条 —— 表被全量泄露了      // SQL 变成 WHERE title LIKE '%' OR '1'='1%' → 恒真

把 WHERE 换成 ; DROP TABLE articles; -- 就是删库事故的起点。规则只有一条：值永远走 ? 占位符，绝不进字符串。另外 % 和 _ 在 LIKE 里是通配符，用户输入 100% 会命中意外结果，要转义：

func escapeLike(s string) string {
    s = strings.ReplaceAll(s, "\\", "\\\\")
    s = strings.ReplaceAll(s, "%", "\%")
    s = strings.ReplaceAll(s, "_", "\_")
    return s
}
// 用：WHERE title LIKE ? （参数为 "%"+escapeLike(kw)+"%"），MySQL 默认 ESCAPE '\\' 即生效

大小写不敏感搜索：articles 表用 utf8mb4_unicode_ci（Day 1 的 command 已配），LIKE 本身就不区分大小写，所以 keyword=GO 能搜到 Go。真要区分再考虑 BINARY 或 LOWER()。

5. 组合筛选：把条件构造抽成一个函数

internal/repository/article.gopackage repository

import (
    "goblog/internal/dto"
    "goblog/internal/model"

    gorm.io/gorm
)

type ArticleRepo interface {
    List(q dto.ArticleListQuery) ([]model.Article, int64, error)
}

type articleRepo struct { db *gorm.DB }

func NewArticleRepo(db *gorm.DB) ArticleRepo { return &articleRepo{db: db} }

// base 每次返回一条全新的、只带了筛选条件的链 —— Count 和 Find 各用一份，互不污染
func (r *articleRepo) base(q dto.ArticleListQuery) *gorm.DB {
    tx := r.db.Model(&model.Article{}).
        Where("articles.deleted_at IS NULL")  // GORM 自动加，写出来便于理解（Day 5 讲）

    if q.Keyword != "" {
        tx = tx.Where("articles.title LIKE ?", "%"+escapeLike(q.Keyword)+"%")
    }
    if q.UserID > 0 {
        tx = tx.Where("articles.user_id = ?", q.UserID)
    }
    if q.MinView > 0 {
        tx = tx.Where("articles.views >= ?", q.MinView)
    }
    if q.From != "" {
        tx = tx.Where("articles.created_at >= ?", q.From+" 00:00:00")
    }
    if q.To != "" {
        tx = tx.Where("articles.created_at <= ?", q.To+" 23:59:59")
    }
    if q.Tag != "" {  // 多对多筛选：子查询比 join 更省事，也不会行放大
        tx = tx.Where("articles.id IN (SELECT at.article_id FROM article_tags at "+
            "JOIN tags t ON t.id = at.tag_id WHERE t.name = ?)", q.Tag)
    }
    return tx
}

func (r *articleRepo) List(q dto.ArticleListQuery) ([]model.Article, int64, error) {
    page, size := q.Normalize()
    var total int64
    if err := r.base(q).Count(&total).Error; err != nil {
        return nil, 0, err
    }

    list := []model.Article{}      // 空 slice 保证 JSON 是 []
    err := r.base(q).
        Preload("Tags").
        Order(q.OrderClause()).     // 白名单产物，安全
        Limit(size).
        Offset((page - 1) * size).
        Find(&list).Error
    return list, total, err
}
internal/handler/article.gofunc (h *ArticleHandler) List(c *gin.Context) {
    var q dto.ArticleListQuery
    if err := c.ShouldBindQuery(&q); err != nil {
        c.JSON(400, gin.H{"code": 1004, "message": "参数不合法: " + err.Error()})
        return
    }
    list, total, err := h.repo.List(q)
    if err != nil {
        c.JSON(500, gin.H{"code": 5000, "message": "查询失败"})
        return
    }
    c.JSON(200, gin.H{"code": 0, "message": "success", "data": dto.NewPageResult(list, total, q.Page, q.Size)})
}

Normalize() 就是第 1 节 NormalizePage 的接收者版本，加在 ArticleListQuery 上即可（返回夹紧后的 page/size）。注意 Gin 的 binding:"max=50" 会直接 400 拒掉超限请求，而 repository 的夹紧是静默修正——两处都留着：前者给明确的错误信息，后者兜住内部调用。

6. 性能边角：深翻页与索引

问题现象对策
OFFSET 100000 慢MySQL 要扫过并丢弃前 10 万行，越翻越慢游标分页：WHERE created_at < ? ORDER BY created_at DESC LIMIT 10（信息流/加载更多常用）

LIKE '%kw%' 前置通配无法走普通索引，百万行开始变慢先接受（学习项目数据量小）；真上线用全文索引 FULLTEXT 或 ES
翻页时数据在变同一条数据在第 2 页又出现一次排序里追加唯一种（, articles.id desc），已在 OrderClause 里做了

今日练习

练习 1：造 25 条数据并接通分页（40 分钟）

写一个 cmd/seed/main.go：3 个用户 × 若干文章（标题里混入 Go/Docker/MySQL 关键词，views 随机 0~500），共 25 篇。把第 3 节 DTO 的 Normalize/OrderClause 补全，接通 GET /articles。

参考答案：curl -s 'localhost:8080/articles?page=1&size=10' → data.list 长度 10、total: 25、total_page: 3；page=3 返回 5 条；page=9 返回 list: []（不是 null）且 total 仍是 25。

练习 2：keyword 搜索 + 注入实验（35 分钟）

依次请求：?keyword=go、?keyword=GO（大小写不敏感应命中同一批）、?keyword=100%（验证 % 转义）、再跑 cmd/inject 那段对比程序。

参考答案：前两个命中条数相同；不转义时 keyword=100% 会命中所有含 100 后接任意字符的标题（意外），转义后只命中字面 100%；注入对比里拼接版返回全表，参数化版返回 0 条。

练习 3：sort 白名单与非法输入（30 分钟）

测四种：?sort=views、?sort=-created_at、?sort=password（不在白名单）、?sort=id; DROP TABLE articles;。要求前两个正确排序，后两个回落默认且不产生 500。

参考答案：白名单查不到 → col 保持默认 articles.created_at，所以非法输入只是「按默认顺序返回」，SQL 里永远不会出现用户那段字符串。日志里搜一下 DROP 应该完全找不到，这就是白名单的价值。注意若把 password 放进白名单也是错的——可排序列不该包含敏感列。

练习 4：组合筛选（30 分钟）

实现并验收 GET /articles?page=1&size=10&keyword=go&sort=-views&user_id=1&tag=gorm&from=2026-09-01&min_views=50，要求 Count 与 Find 的 WHERE 完全一致（否则 total 和列表会自相矛盾）。

参考答案：日志应出现两条同条件的 SQL——SELECT count(*) FROM articles WHERE ... 与 SELECT * FROM articles WHERE ... ORDER BY articles.views desc, articles.id desc LIMIT 10。若 tag 用了 join 而非子查询，检查 count(distinct articles.id)，不然 total 会被中间表放大。
