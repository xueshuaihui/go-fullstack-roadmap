课前须知：为什么排序不能「透传」

JS 里你习惯把前端传来的 sortField 直接丢给 db.order(field)（Sequelize 会帮你转义）。GORM 的 Order() 会把字符串原样拼进 SQL——因为它要支持 "created_at desc, id asc" 这种表达式。所以「哪里是占位符、哪里不是」是本周最重要的安全分界线：Where("...", ?) 的参数走占位符安全；Order()、Select()、表名/列名都是直接拼接，必须自己校验。

今天全程只有三条线，记住就不会犯大错：值（用户输入的关键词、ID、日期）→ 一律走 ? 占位符；SQL 片段（列名、排序方向、表名）→ 一律走白名单，映射不到就用默认；普通文本（拼摘要、拼日志）→ 随便拼，但循环里请换 strings.Builder（第 5 节）。

知识讲义

1. Offset / Limit：分页的两个旋钮

分页 SQL 原理SELECT * FROM articles ORDER BY created_at DESC LIMIT 10 OFFSET 20;  -- 第 3 页

// 第 page 页（page 从 1 开始）、每页 size 条：
//   offset = (page - 1) * size
GORM 写法（两种等价）db.Order("created_at desc").Limit(10).Offset(20).Find(&articles)
db.Limit(10).Offset(20).Find(&articles)   // 顺序无所谓，链式只是攒条件

参数一定要在入口处夹紧（clamp），否则 ?size=-1、?page=99999999 会直接打到数据库。这件事 day3 练习 2 让你建的 internal/dto/page.go 已经做完了（defaultPage=1 / defaultSize=10 / maxSize=100 + Normalize() + Offset()），今天不重写一遍，只是把它的字段表扩宽。先确认你真理解它在防什么——把 cmd/demo/main.go 整段换成下面这段（day2 用它练 GORM，今天它不碰数据库）：

cmd/demo/main.go（整段替换，只验证夹紧逻辑）package main

import (
    fmt

    "goblog/internal/dto"
)

func main() {
    for _, q := range []dto.PageQuery{
        {Page: 0, Size: 0},            // 前端常见：压根没传

        q.Normalize()                   // ← 指针接收者，改的就是 q 自己

2. Count 总数：必须单独跑一条，且不能带 Limit/Order

计数写法对比（讲义片段，不是某个文件）var total int64

// ✅ 用 Model(&T{}) 才能统计「这个表」；Count 会生成 SELECT count(*)
db.Model(&model.Article{}).Where("user_id = ?", 1).Count(&total)

// ❌ 常见错误：把 Count 接在已有 Limit/Select 的链后面
db.Select("id", "title").Limit(10).Model(&model.Article{}).Count(&total) // 语义混乱，可能得 10

total 必须是「符合条件的所有行数」，与分页无关。所以正确顺序是：同一套 WHERE 条件 → ① Count(&total)，② 再 Order + Limit + Offset + Find。而 GORM 的链式对象是有状态的：Count 之后那条链的字段选择等会影响下一次。标准解法是把条件封装成一个「构造函数」，两处各调一次，见下一节。

// 嵌入 PageQuery —— page/size 两个字段、Normalize()、Offset() 全是现成的，零复制零重写
type ArticleQuery struct {
    PageQuery

    Keyword  string `form:"keyword"`    // 标题模糊搜索
    UserID   uint   `form:"user_id"`    // 只看某个人
    Tag      string `form:"tag"`        // 按标签名
    MinViews int    `form:"min_views"`  // 阅读量下限
    From     string `form:"from"`       // 2026-09-01，起始日期
    To       string `form:"to"`         // 结束日期
    Sort     string `form:"sort"`       // views / -views / created_at / ...
}

// 嵌入（embedding）带来的两个写法，第 7 节会真的用到：
//   q.Normalize()                          // 方法从 PageQuery 提升上来，作用于内嵌的那个 PageQuery
//   dto.NewPageResult(list, total, q.PageQuery)   // 要 PageQuery 本身时，用字段名取

Go 的嵌入不是继承，它做的是「组合 + 方法/字段提升」：ArticleQuery 里确实躺着一个名为 PageQuery 的字段，编译器顺便把它的方法和字段转发到外层。JS 里最像的写法是 const q = { ...basePage, ...filters }——但 Go 是按类型转发的，不是按属性名合并，两个同名字段（比如内外都有 Page）时你得写全路径 q.Inner.Page 来消歧。

三个坑先说明白：① query 参数用 form tag，json tag 是给请求体的，写错了绑定就是零值；② min_views=abc 这种绑不进 int 的输入，ShouldBindQuery 会返回 error → 我们给 400 + 1005（CodeInvalidParam），这是「无法解释的输入」，该拒；③ From/To 故意留 string（不是 time.Time）：它们直接进 WHERE created_at >= ? 的占位符，MySQL 自己会把 "2026-09-01 00:00:00" 转成时间。真要校验格式再换 time.Time + binding:"datetime=2006-01-02"，本周不展开。

4. 排序白名单：只允许已知安全值

internal/dto/sort.go（新文件）package dto

import strings

// SortableColumns 白名单：URL 里的 sort 只能映射到这些真实列名。
// 只放「排序有意义、且不泄露敏感数据」的列。
// 千万别把 password / email 放进来：能被排序的列，就能被二分猜出内容。
var SortableColumns = map[string]string{
    "created_at": "articles.created_at",
    "views":      "articles.views",
    "id":         "articles.id",
    "title":      "articles.title",
}

// OrderClause 把 "sort=-views" 翻译成安全的 ORDER BY 片段；非法值回落默认
func (q ArticleQuery) OrderClause() string {
    col, dir := "articles.created_at", "desc"
    s := strings.TrimSpace(q.Sort)
    if s != "" {
        dir = "asc"
        if strings.HasPrefix(s, "-") {
            dir, s = "desc", strings.TrimPrefix(s, "-")
        }
        if mapped, exists := SortableColumns[s]; exists {
            col = mapped
        } else {
            dir = "desc" // 未知字段 → 整体回落默认排序，绝不拼进去
        }
    }
    return col + " " + dir + ", articles.id desc" // 追加唯一列，保证翻页不重不漏
}

5. 字符串拼接与 strings.Builder（W1 day1 埋的坑，今天填）

W1 day1 那张「JS 语法对照表」里留过一句话：循环里 s += x 性能差，第 3 周 day4 正式讲 strings.Builder。今天兑现。为什么正好是今天？因为今天你要写不少拼接代码——"%" + kw + "%" 的 LIKE 模式、col + " " + dir + ", articles.id desc" 的 ORDER BY 片段——工具和边界一起讲最省时间。

① Go 的 string 是不可变的。所以 s += x 不是「往 s 尾巴上接一段」，而是：申请一块新内存 → 把 s 的整段旧字节抄过去 → 再把 x 抄在后面 → 让 s 指向新块。拼 n 次，抄的总字节数是 5 + 10 + 15 + …，量级是 O(n²)，而且中途那 n 个旧字符串全变成垃圾等 GC 收。

JS 里同样写 s += x 常常不慢，是因为 V8 内部有 cons-string（拼接树），把拼接做成惰性结构，真要用才展平。Go 没有这种魔法：+ 就是立刻生成一个新的字符串头 + 新的字节数组。Go 里承担「惰性累积」这个角色的就是 strings.Builder（对应 JS 的 arr.join('') 那种「先攒着，最后一次算」思路）。

② Builder 的写法：内部是一个 []byte，WriteString 只往后追加，容量不够时按 slice 规则扩容（均摊 O(1)），String() 最后一次性产出。

cmd/strcat/main.go（新建，这个练手程序不碰数据库）package main

import (
    fmt
    strings
    time
)

func main() {
    words := make([]string, 50000)
    for i := range words {
        words[i] = "word"
    }

    // ① += 版：每加一次，前面已经拼好的整段都要重抄一遍
    start := time.Now()
    var s string
    for _, w := range words {
        s += w + " "
    }
    plus := time.Since(start)

    // ② Builder 版：只追加，不重复拷贝
    start = time.Now()
    var b strings.Builder
    b.Grow(len(words) * 5)  // 可选：预估字节容量，少扩几次容
    for _, w := range words {
        b.WriteString(w)     // 签名是 (int, error)，但 error 恒为 nil，可以直接不接
        b.WriteByte(' ')
    }
    built := time.Since(start)

    fmt.Printf("%-10s %8s  长度 %d\n", "+= 版", plus.Round(time.Microsecond), len(s))
    fmt.Printf("%-10s %8s  长度 %d\n", "Builder 版", built.Round(time.Microsecond), b.Len())
    fmt.Println("两次结果完全一致：", s == b.String())
}
shell$ go run ./cmd/strcat
+= 版          2.9ms  长度 250000
Builder 版   310µs  长度 250000
两次结果完全一致： true

数字每台机器差好几倍都正常，要看的是量级差。另外说句实话：较新的 Go 编译器对「循环里 s += x」做了原地扩容优化（命中条件是 s 正好是最后一次分配的那块内存），所以现在没老帖子里写的「慢一千倍」那么夸张。但那是编译器的赠品，不是保证——中间一旦插了别的分配就退化回 O(n²)。Builder 是从写法上就不重复拷贝，这才是你可以依赖的东西。

③ 什么时候用哪个：

场景写法为什么
固定两三段a + b + c 或 fmt.Sprintf最清楚。今天 "%"+dto.EscapeLike(kw)+"%" 就属于这类，别为了用工具而用
一个切片用同一个分隔符拼起来strings.Join(parts, ", ")Join 内部就是 Builder，一行搞定
循环里拼，还要加判断/转义strings.Builder今天的主角：段数未知、每段内容有逻辑
要当 io.Writer 用（比如喂 json.NewEncoder、template.Execute）bytes.BufferBuilder 没实现 io.Writer……其实它有 Write 方法，但你要可写字节切片语义时用 Buffer 更直观
拼 SQL 的任何部分谁都不许拼值走 ?，片段走白名单。性能话题在这里毫无意义，看第 6 节

Builder 三个小脾气，现在知道比踩到强：① 不能复制使用（内置 copyCheck，复制后写会 panic），也别跨 goroutine 共享同一个 Builder；② 写完 String() 之后不要再往里写（结果不保证）；③ 没有「清空重来」的接口，要复用就 b = strings.Builder{} 重新声明一个。

6. LIKE 模糊搜索：值必须参数化

internal/dto/like.go（新文件）package dto

import strings

// EscapeLike 把用户输入里的 LIKE 通配符还原成普通字符。
// 反斜杠必须第一个替换，否则会把后面两步补出来的 \ 再转义一遍。
func EscapeLike(s string) string {
    s = strings.ReplaceAll(s, `\`, `\\`)
    s = strings.ReplaceAll(s, `%`, `\%`)
    s = strings.ReplaceAll(s, `_`, `\_`)
    return s
}

// 用法：Where("articles.title LIKE ?", "%"+EscapeLike(kw)+"%")
// MySQL 的 LIKE 默认转义符就是反斜杠，不用再写 ESCAPE 子句；
// 注意这只管「通配符」，跟防注入无关 —— 防注入靠的是那个 ?。
repository 里的两种写法对照// ✅ 占位符 + 参数：驱动把 kw 当字面量，里面的引号、分号都变普通字符
if q.Keyword != "" {
    tx = tx.Where("articles.title LIKE ?", "%"+dto.EscapeLike(q.Keyword)+"%")
}

// ❌ 危险到不能上生产：把 kw 拼进 SQL 源码
tx = tx.Where(fmt.Sprintf("articles.title LIKE '%%%s%%'", q.Keyword))

亲手验证差别——这是今天最重要的 15 分钟。新建 cmd/inject/main.go，四个用例一次跑完：

cmd/inject/main.gopackage main

import (
    fmt
    strings

    "goblog/internal/config"
    "goblog/internal/dto"
    "goblog/internal/model"
    "goblog/internal/repository"
)

func main() {
    db := repository.MustConnect(config.DSN) // 只有练手程序才直连，业务代码必须走 repository 层

    cases := []string{
        "的第",          // ① 正常关键词：两条路应当等价
        `' OR '1'='1`,       // ② 不带尾引号：恒真条件，注入成功
        `' OR '1'='1'`,      // ③ 网上帖子那种带尾引号：SQL 语法先崩，1064
        `x' OR 1=1 -- `,     // ④ 注释型：-- 后面必须跟空格，把模板尾巴整段注释掉
    }

    for i, kw := range cases {
        var safe []model.Article
        err := db.Where("articles.title LIKE ?", "%"+dto.EscapeLike(kw)+"%").Find(&safe).Error
        if err != nil {
            fmt.Printf("[%d] 参数化版本都报错，说明你 WHERE 写错了: %v\n", i+1, err)
            continue
        }

        sql := fmt.Sprintf("articles.title LIKE '%%%s%%'", kw) // 展开后是 title LIKE '%<kw>%'
        var bad []model.Article
        if err := db.Where(sql).Find(&bad).Error; err != nil {
            fmt.Printf("[%d] %-14q 参数化 %2d 条 / 拼接 → %s\n", i+1, kw, len(safe), firstLine(err))
            continue
        }
        fmt.Printf("[%d] %-14q 参数化 %2d 条 / 拼接 %2d 条\n", i+1, kw, len(safe), len(bad))
    }
}

func firstLine(err error) string { // MySQL 的错误有两行，取第一行就够了
    if i := strings.IndexByte(err.Error(), '\n'); i > 0 {
        return err.Error()[:i]
    }
    return err.Error()
}

为什么③会 1064 而②能成功？模板是 title LIKE '%%%s%%'，展开成 title LIKE '%<kw>%'，里面有一对引号。你的 kw 想「闭合」它，就得把吃掉的那个开引号补回来：写 ' OR '1'='1 时展开成 title LIKE '%' OR '1'='1%'，MySQL 按 (title LIKE '%') OR ('1'='1%') 解析，左半边恒真 → 全表泄露；再手贱多写一个尾引号 ' OR '1'='1' 就展开成 … = '1'%' '，引号数量对不上，语法先炸，于是你看到 1064。很多教程直接抄带尾引号的那串，跟着做的人以为注入失败了——其实是被语法错误挡住了。结论不是「这个 payload 没用」，而是「引号能不能配上完全取决于模板长什么样」，这正是拼接要禁止的原因。

把 WHERE 换成 ; DROP TABLE articles; -- 就是删库事故的起点（多数驱动默认不开 multiStatements，所以一句里塞两句会被拒；但读接口被拖走全表数据、被 UNION 猜密码哈希已经足够致命）。规则只有一条：值永远走 ? 占位符，绝不进字符串。

大小写不敏感搜索：articles 表用 utf8mb4_unicode_ci（Day 1 的 compose 已配），LIKE 本身就不区分大小写，所以 keyword=GO 能搜到 Go。真要区分再考虑 BINARY 或 LOWER()。

// base 每次返回一条全新的、只带筛选条件的链 —— Count 和 Find 各拿一份，互不污染
func (r *gormArticleRepo) base(q dto.ArticleQuery) *gorm.DB {
    tx := r.db.Model(&model.Article{})  // 软删除过滤 GORM 自己加（day5 细讲），这里别手写一遍

    if q.Keyword != "" {
        tx = tx.Where("articles.title LIKE ?", "%"+dto.EscapeLike(q.Keyword)+"%")
    }
    if q.UserID > 0 {
        tx = tx.Where("articles.user_id = ?", q.UserID)
    }
    if q.MinViews > 0 {
        tx = tx.Where("articles.views >= ?", q.MinViews)
    }
    if q.From != "" {
        tx = tx.Where("articles.created_at >= ?", q.From+" 00:00:00")
    }
    if q.To != "" {
        tx = tx.Where("articles.created_at <= ?", q.To+" 23:59:59")
    }
    if q.Tag != "" {  // 多对多筛选：子查询比 join 更省事，也不会行放大（day3 第 6 节踩过的那个坑）
        tx = tx.Where("articles.id IN (SELECT at.article_id FROM article_tags at "+
            "JOIN tags t ON t.id = at.tag_id WHERE t.name = ?)", q.Tag)
    }
    return tx
}

// ListPage 约定：传进来的 q 必须已经 Normalize 过（service 负责，见第 2 步），
// 所以这里直接用 q.Size / q.Offset()，不再自己算一遍
func (r *gormArticleRepo) ListPage(q dto.ArticleQuery) ([]model.Article, int64, error) {
    var total int64
    if err := r.base(q).Count(&total).Error; err != nil {
        return nil, 0, err                // total 是出参，失败时一律返零值
    }

    list := []model.Article{}      // 空 slice 保证 JSON 是 []，不是 null
    err := r.base(q).
        Preload("User").Preload("Tags").   // day3 的批量 IN，两条额外 SQL
        Order(q.OrderClause()).     // 白名单产物，安全
        Limit(q.Size).
        Offset(q.Offset()).
        Find(&list).Error
    return list, total, err
}

}

问题现象对策
