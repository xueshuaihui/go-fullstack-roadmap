关联查询：一对多与多对多

单表 CRUD 只是及格线，真实业务的力量在关系上：一篇文章属于某个作者（一对多）、可以贴多个标签（多对多）。今天你要搞定 GORM 的关联声明与 Preload，并且亲眼看一次 N+1 灾难——这是规划「常见坑」清单第 6 条，也是面试高频题。

↑ 这五条是「学习目标」，学的过程中随时回来勾；页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

课前须知：关系在数据库里到底是什么

没有「对象嵌套」这回事，只有外键。数据库里 articles.user_id = 1 就是一个数字。所谓「拿到用户和他的文章」，永远是两条 SQL：先查 users，再查 articles WHERE user_id IN (1)。GORM 的关联功能只是把这两条 SQL 的编排自动化了。理解这点，Preload 为什么有时变 N+1、为什么 Joins 只要一条 SQL，全都通了。

ORM 世界里的四种关系，对应 JS 里你熟悉的数据形状：BelongsTo（文章 → 一个作者）、HasOne（用户 → 一个头像）、HasMany（用户 → 多篇文章）、Many2Many（文章 ↔ 多个标签）。声明方向很重要：外键在哪张表，哪张表就写 belongs-to。

知识讲义

1. 关联声明：模型今天一行都不用改

day2 定稿的三个模型就是本周最终形态，关系字段当时就写好了：User.Articles（HasMany，外键 user_id 在对方表上）、Article.User（BelongsTo，外键在自己身上）、Article.Tags（Many2Many，中间表 article_tags）。今天只是开始用它们。

声明方向怎么记GORM 靠什么找到对方
Articles []Article `gorm:"foreignKey:UserID"`我有多个 → HasMany去 articles 表找 user_id = 我的 id
User User `gorm:"foreignKey:UserID"`我属于一个 → BelongsTo用我自己的 user_id 去 users.id
Tags []Tag `gorm:"many2many:article_tags"`互相多个 → Many2Many查中间表 article_tags 的两列 article_id / tag_id

迁移仍是 day2 那一行，三个模型一次传进去：

cmd/server/main.goif err := db.AutoMigrate(&model.User{}, &model.Article{}, &model.Tag{}); err != nil {
    log.Fatalf("迁移失败: %v", err)
}

先纠正一个流传很广的说法：有人告诉你「AutoMigrate 的顺序影响外键约束，必须先迁父表」——GORM 根本不会创建数据库级外键约束。翻遍它的日志你也找不到一句 FOREIGN KEY / ADD CONSTRAINT。它建的是普通索引（UserID uint `gorm:"index"` 那句就是）。所以 articles.user_id = 999（不存在的用户）照样插得进去——引用完整性由你的 service 层负责（练习 4 里 ErrAuthorNotFound 就是干这个的）。顺序真正影响的只有一件事：漏传某个模型 → 那张表压根不存在 → 后面 Preload 直接报 Table 'goblog.article_tags' doesn't exist。数据库级外键什么时候需要？第 7 周用版本化迁移手工加。

中间表就两列，两列组成联合主键：PRIMARY KEY (article_id, tag_id)。这条约束意味着「同一篇文章贴同一个标签两次」在数据库层面就被禁止（第 4 列 PRI 就是证据），但它不阻止「同一个标签被 100 篇文章用」——那正是多对多的语义。GORM 没给这张表加 id、created_at，因为它只是一张关系表。想看关系：SELECT * FROM article_tags;。

2. 最小 SQL 前置：四行看懂就够

今天第 6 节要手写 JOIN，day4 还要写子查询。你不需要会设计 SQL，只要能看懂 GORM 打在日志里的那几行。下面四条请在 MySQL 命令行里逐条真跑一遍（先做第 3 节的种子数据），这 10 分钟能省掉你后面两小时的对猜。

shell$ docker exec -it goblog-mysql mysql -ugoblog -pgoblog123 --database=goblog

-- ① 取行：只要这三列，按创建时间倒排，跳过前 10 行取 5 行（这就是「分页」的全部秘密）
mysql> SELECT id, title, views FROM articles WHERE user_id = 1
          ORDER BY created_at DESC LIMIT 5 OFFSET 10;

-- ② 连接：按 ON 的条件把两张表的行拼成一行；LEFT 保证「没有作者的文章也不丢」
mysql> SELECT a.id, a.title, u.username FROM articles AS a
          LEFT JOIN users AS u ON u.id = a.user_id;

-- ③ 分组聚合：按 user_id 分堆，每堆算一次；HAVING 过滤的是「堆」，WHERE 过滤的是「行」
mysql> SELECT user_id, COUNT(*) AS n, SUM(views) AS sum_views
          FROM articles GROUP BY user_id HAVING n > 1;

-- ④ 子查询：IN 后面套一条 SELECT
mysql> SELECT id, title FROM articles WHERE user_id IN
          (SELECT id FROM users WHERE role = 0);
SQL 片段GORM 写法要点
WHERE user_id = 1db.Where("user_id = ?", 1)值永远走 ? 占位符，不要字符串拼接（day4 亲手打断一次）
LIMIT 5 OFFSET 10db.Limit(5).Offset(10)分页 = 这两个数；OFFSET = (page-1)*size
LEFT JOIN users ON u.id = a.user_iddb.Joins("LEFT JOIN users ON users.id = articles.user_id")GORM 不替你写 ON 子句，引号里的字符串原样拼进 SQL，所以表名列名要写全
SELECT u.username AS usernamedb.Select("users.username AS username").Scan(&rows)结果列对不上 model 字段时用 Scan + 自定义 struct
GROUP BY user_id + COUNT(*) AS ndb.Group("user_id").Select("user_id, COUNT(*) AS n").Scan(&rows)聚合结果不在任何表里，只能用带 n 字段的 struct 接
HAVING n > 1db.Having("n > ?", 1)带聚合的条件才走 HAVING；Where 里是拿不到 n 的
IN (SELECT id FROM users ...)db.Where("user_id IN (?)", sub)，sub := db.Model(&model.User{}).Select("id").Where("role = ?", 0)把一个 *gorm.DB 当子查询传进去，它不会被执行
AS a（表别名）GORM 默认用全表名，不用别名所以手写 join 里请写 articles.id 而不是 a.id，除非你自己 Table("articles AS a")

三条最容易混的：INNER JOIN 丢掉拼不上的行（没作者的文章消失）；LEFT JOIN 保留左表全部行，右表列给 NULL；WHERE 在分组前筛行、HAVING 在分组后筛堆。对照 JS：rows.filter(r => r.user_id === 1) 是 WHERE，Object.entries(groupBy(rows)).filter(([,v]) => v.length > 1) 才是 HAVING。

3. 造点种子数据：一个能跑的 cmd/seed/main.go

关联查询得有数据才好观察。新建文件 cmd/seed/main.go（和 cmd/server 平级，各自一个 package main，互不干扰），整份抄进去就能跑：

cmd/seed/main.gopackage main

import (
    fmt
    log

    "gorm.io/gorm"

    "goblog/internal/config"
    "goblog/internal/model"
    "goblog/internal/repository"
)

func main() {
    db := repository.MustConnect(config.DSN)       // day1 建的那个函数，别自己再 gorm.Open 一次
    if err := db.AutoMigrate(&model.User{}, &model.Article{}, &model.Tag{}); err != nil {
        log.Fatalf("迁移失败: %v", err)
    }
    if err := seed(db); err != nil {
        log.Fatalf("种子失败: %v", err)
    }
}

func seed(db *gorm.DB) error {
    tagNames := []string{"go", "mysql", "gorm", "docker"}
    users := []model.User{
        {Username: "xiaoming", Nickname: "小明", Email: "xm@example.com", Password: "abcdef123456"},
        {Username: "ahua", Nickname: "阿花", Email: "ahua@example.com", Password: "abcdef123456"},
        {Username: "laozhang", Nickname: "老张", Email: "lz@example.com", Password: "abcdef123456"},
    }

    // 1) 标签：有则复用、无则插入 —— 多对多的标准起手式
    tags := make([]model.Tag, 0, len(tagNames))
    for _, name := range tagNames {
        var t model.Tag
        if err := db.Where(map[string]any{"name": name}).FirstOrCreate(&t).Error; err != nil {
            return fmt.Errorf("seed tag %q: %w", name, err)
        }
        tags = append(tags, t)
    }

    // 2) 用户 + 每人 2 篇文章 + 每篇 2 个标签（全部幂等，反复跑结果一致）
    for _, u := range users {
        if err := db.Where("username = ?", u.Username).FirstOrCreate(&u).Error; err != nil {
            return fmt.Errorf("seed user %s: %w", u.Username, err)
        }
        for n := 1; n <= 2; n++ {
            title := fmt.Sprintf("%s 的第 %d 篇", u.Nickname, n)
            a := model.Article{Title: title, Content: "正文若干……",
                Summary: title + "（摘要）", UserID: u.ID, Views: int64(n * 10)}
            if err := db.Where("title = ? AND user_id = ?", title, u.ID).FirstOrCreate(&a).Error; err != nil {
                return fmt.Errorf("seed article %q: %w", title, err)
            }
            // 关键：不在 Create 里塞 Tags，而是关系单独走 Association（下一节解释为什么）
            rel := []model.Tag{tags[n%len(tags)], tags[(n+1)%len(tags)]}
            if err := db.Model(&a).Association("Tags").Replace(rel); err != nil {
                return fmt.Errorf("seed rel %q: %w", title, err)
            }
        }
        fmt.Printf("user %-9s id=%d 文章 2 篇\n", u.Username, u.ID)
    }

    // 3) 汇报战果：Table("article_tags") 直接数中间表
    var nu, na, nt, nr int64
    db.Model(&model.User{}).Count(&nu)
    db.Model(&model.Article{}).Count(&na)
    db.Model(&model.Tag{}).Count(&nt)
    db.Table("article_tags").Count(&nr)
    fmt.Printf("完成：users=%d articles=%d tags=%d article_tags=%d\n", nu, na, nt, nr)
    return nil
}

级联保存的两个注意事项（也是上面这段为什么绕一圈用 Association 的原因）：① 如果在 db.Create(&a) 里直接塞 Tags: []model.Tag{{Name: "go"}}，那是零 ID 的新 struct，GORM 会连带 INSERT 一行新标签；因为 tags.name 上有唯一索引，第二篇也用 "go" 时就撞 Error 1062 Duplicate entry——而不是复用已有标签。正确做法永远是先按名字查/建拿到 ID，再把带 ID 的 tag 挂上去。② Save(&a) 会连带更新关联；想只改文章本身用 Updates，想整体替换关联用 Association("Tags").Replace。

4. 只维护关系，不创建记录：Association 模式

internal/repository/tag.go（今天新建，完整）package repository

import (
    "goblog/internal/model"

    "gorm.io/gorm"
)

// TagRepository 标签这一侧的能力。名字与 day2 的 UserRepository 同一套风格
type TagRepository interface {
    FindOrCreate(name string) (model.Tag, error)
    ReplaceFor(articleID uint, tagIDs []uint) error
    ListByArticle(articleID uint) ([]model.Tag, error)
}

type gormTagRepo struct { db *gorm.DB }

func NewTagRepo(db *gorm.DB) TagRepository { return &gormTagRepo{db: db} }

var _ TagRepository = (*gormTagRepo)(nil)

// FindOrCreate 有则复用、无则插入。返回的 tag 一定带 ID
func (r *gormTagRepo) FindOrCreate(name string) (model.Tag, error) {
    var tag model.Tag
    err := r.db.Where(map[string]any{"name": name}).FirstOrCreate(&tag).Error
    return tag, err
}

// ReplaceFor 整体替换这篇文章的标签：只动 article_tags，永远不碰 tags 表的行
func (r *gormTagRepo) ReplaceFor(articleID uint, tagIDs []uint) error {
    var tags []model.Tag
    if len(tagIDs) == 0 {
        return r.db.Model(&model.Article{ID: articleID}).Association("Tags").Clear()
    }
    if err := r.db.Find(&tags, tagIDs).Error; err != nil {
        return err
    }
    return r.db.Model(&model.Article{ID: articleID}).Association("Tags").Replace(tags)
}

func (r *gormTagRepo) ListByArticle(articleID uint) ([]model.Tag, error) {
    var tags []model.Tag
    err := r.db.Model(&model.Article{ID: articleID}).Association("Tags").Find(&tags)
    return tags, err
}

注意 Association 系列方法的返回值类型：它们返回的是裸 error，不是 *gorm.DB。所以 Association("Tags").Replace(tags).Error 编译不过（Replace 已经没有 .Error 可取了），写成 err := ...Replace(tags).Error 是初学高频错误。正确形态就是上面那样：if err := r.db.Model(...).Association("Tags").Replace(tags); err != nil { ... }。同理 Find(&tags)、Clear()、Delete(...) 都是 error，只有 Count() 是 (int64, error)。

Association 四件套（对照上面三个方法，看清语义差别）// 追加：只补没有的关系，已有的不删
if err := db.Model(&a).Association("Tags").Append([]model.Tag{goTag}); err != nil { /* … */ }

// 替换：先把这篇文章现有的关系全断掉，再写入这批 —— 幂等，seed 用的就是它
if err := db.Model(&a).Association("Tags").Replace([]model.Tag{goTag, mysqlTag}); err != nil { /* … */ }

// 断开指定关系（标签本身还在 tags 表里，别人的关系也不受影响）
if err := db.Model(&a).Association("Tags").Delete([]model.Tag{dockerTag}); err != nil { /* … */ }

// 清空这篇文章的全部关系
if err := db.Model(&a).Association("Tags").Clear(); err != nil { /* … */ }

// 读关系 / 数一下
var tags []model.Tag
if err := db.Model(&a).Association("Tags").Find(&tags); err != nil { /* … */ }
n, err := db.Model(&a).Association("Tags").Count()

类比 JS：这就像 Set.add（Append）、set = new Set(list)（Replace）、Set.delete（Delete）。Association 模式只动中间表，永远不会删除 tags 表的行，所以「删一篇文章」不会误删别人也在用的标签。反过来说：真要删一个标签，得自己 Delete(&model.Tag{}, id) 再清 article_tags 里它的行（GORM 不会替你级联清）。

5. Preload：一次把关联带出（以及 N+1 灾难）

默认情况下关联字段是空的——GORM 不查它，一条 SQL 都不多发：

N+1 对比// ❌ 手写循环查询：1 + N 条 SQL
var users []model.User
db.Find(&users)                                   // SQL 1：SELECT * FROM users
for i := range users {
    db.Where("user_id = ?", users[i].ID).Find(&users[i].Articles) // 每个用户一条 → N 条
}

// ✅ Preload：固定 2 条 SQL，不管多少用户
db.Preload("Articles").Find(&users)              // SQL 1: SELECT * FROM users
                                                  // SQL 2: SELECT * FROM articles WHERE user_id IN (1,2,3,...)

这就是你在 JS 里写过的坑：for (const u of users) { u.articles = await api.getArticles(u.id) }——串行 N 次请求。GORM 的 N+1 完全同构，只是把「await 网络」换成「round-trip 数据库」。修正思路也一样：把 N 次单查合并成一次批查（SQL 里就是 IN (...)），或者一次性 join 出来。区别在于：JS 里你还能 Promise.all 并发掩盖问题，数据库里 100 次 round-trip 就是实打实的 100 次网络往返。

Preload 的四种进阶形态：

Preload 进阶// ① 带条件（字符串 + 占位符）
db.Preload("Articles", "views > ?", 100).First(&user, 1)
var kw string = "gorm"                       // 真实来源是 ?kw=… 查询参数，day4 教绑定与转义
db.Preload("Articles", "title LIKE ?", "%"+kw+"%").First(&user, 1)

// ② 裁剪字段 + 排序 + 限量（回调里返回一个加了条件的 *gorm.DB）—— 列表页「最近 5 篇」
db.Preload("Articles", func(db *gorm.DB) *gorm.DB {
    return db.Select("id", "title", "user_id", "created_at").Order("created_at desc").Limit(5)
}).Find(&users)

// ③ 嵌套：用户 → 文章 → 文章标签（三条 SQL）
db.Preload("Articles.Tags").Find(&users)

// ④ 反向：文章带作者、带标签（多对多与 belongs-to 都能 Preload）
var article model.Article
db.Preload("Tags").Preload("User").First(&article, 1)

Preload 是「懒加载 + 显式批量」的组合，好处是主查询干净、支持 order/limit/条件；代价是每次关联多一条 SQL。列表接口里关联只需用于显示一两个字段时，考虑下面的 Joins。

6. Joins：一条 SQL 搞定

Joins 三种用法// ① 简写：belongsto / hasone 关联可以直接写名字（不支持 has-many / many2many）
var arts []model.Article
db.Joins("User").Where("users.username = ?", "xiaoming").Preload("Tags").Find(&arts)
// → LEFT JOIN users ON users.id = articles.user_id AND users.deleted_at IS NULL
//    WHERE users.username = 'xiaoming'   ← 注意：join 条件是 GORM 按外键自己推的

// ② 原生 JOIN + 自定义结果结构体：只要作者邮箱，不要整个 User 对象（第 2 节那条 SQL）
type ArticleRow struct {
    ID        uint   `gorm:"column:id" json:"id"`
    Title     string `gorm:"column:title" json:"title"`
    UserEmail string `gorm:"column:user_email" json:"user_email"`
}
// ↑ 结果形状和 model 不一样，就用这种「行结构体」接；Scan 只填字段、不管主键
var rows []ArticleRow
db.Table("articles").
    Select("articles.id, articles.title, users.email AS user_email").
    Joins("LEFT JOIN users ON users.id = articles.user_id").
    Where("articles.views > ?", 0).
    Scan(&rows)

// ③ 关联计数：某用户有多少篇文章（不 Preload 整份数据）
var cnt int64
db.Model(&model.Article{}).Where("user_id = ?", 1).Count(&cnt)

// ④ 分组聚合 + HAVING（第 2 节 ③ 那条 SQL 的 GORM 版）
type AuthorStat struct { UserID uint `gorm:"column:user_id"`; N int64 `gorm:"column:n"` }
var stats []AuthorStat
db.Table("articles").Select("user_id, COUNT(*) AS n").
    Group("user_id").Having("n > ?", 1).Scan(&stats)

② 里的 Table("articles") 会让 GORM 不再自动加软删除条件吗？不会——Table 只是换个 FROM 目标，它拿不到模型信息，所以 articles.deleted_at IS NULL 得你自己写（改成 Joins("LEFT JOIN users ON ...").Where("articles.deleted_at IS NULL")，或用 Model(&model.Article{}) 而不是 Table）。这是 Table + 软删除最经典的漏数据口子：回收站里的文章会出现在列表里。day5 会专门回头讲这件事。

手段SQL 条数能带出 has-many？能对关联表 where/order/limit？什么时候用
循环里查（N+1）1 + N能能永远不用
Preload1 + 每种关联 1 条能能（条件/裁剪/限量都行）详情接口、要返回嵌套 JSON
Joins1 条不能（会行放大）能，但要自己写 ON/WHERE只取关联的少量字段、需要按关联表条件过滤/排序

Count 和 Joins 混用要小心：一对多 JOIN 会让行数翻倍，db.Model(&a).Joins("User").Count(&n) 统计的是 join 后的行数。需要去重时写 Distinct("articles.id")，或干脆拆成两次查询。另外 GORM 的 Delete(&user, 1) 不会级联删除他的文章——第 1 节说过 GORM 不建数据库外键，所以数据库也不会帮你删。删除用户时要在事务里手工删/软删其文章（Day 5 会说）。

练习 1：跑种子 + 亲眼看 N+1（30 分钟）

跑第 3 节的 go run ./cmd/seed（它会造 3 用户 / 6 文章 / 4 标签 / 12 关系行）。然后写两版「列出所有用户及其文章」：循环版与 Preload("Articles") 版，把终端里 [rows:n] 的 SQL 条数分别记下来。

参考答案：循环版 1 + 3 = 4 条 SELECT（用户多了就是几十条）；Preload 版恒定 2 条，第二条是 WHERE user_id IN (1,2,3)。Preload("Articles.Tags") 是 3 条，第三条多一个 WHERE article_tags.article_id IN (...)。把 middleware.Timer() 打的 耗时 也抄下来，你会看到 4 条 SQL 和 2 条 SQL 在本地 Docker 上差 2~3 毫秒——生产上是几十毫秒级。

internal/dto/page.go（今天照抄，day4 正式讲）package dto

// PageQuery 列表接口的公共查询参数：GET …?page=2&size=10
// 注意 tag 是 form 不是 json —— 它从 URL 查询串绑定，不从请求体
type PageQuery struct {
    Page int `form:"page"`
    Size int `form:"size"`
}

const (
    defaultPage = 1
    defaultSize = 10
    maxSize     = 100  // 不设上限，别人一句 ?size=999999 就能拖死你
)

// Normalize 把乱七八糟的入参收进安全区间。必须在使用 page/size 之前调用
func (q *PageQuery) Normalize() {
    if q.Page < 1 { q.Page = defaultPage }
    if q.Size < 1 { q.Size = defaultSize }
    if q.Size > maxSize { q.Size = maxSize }
}

// Offset 页码 → 跳过多少行，就是第 2 节那条 SQL 里的 OFFSET
func (q PageQuery) Offset() int { return (q.Page - 1) * q.Size }

// PageResult 全站统一的列表形状：{list,total,page,size,total_page}
type PageResult struct {
    List      any   `json:"list"`
    Total     int64  `json:"total"`
    Page      int   `json:"page"`
    Size      int   `json:"size"`
    TotalPage int   `json:"total_page"`
}

// NewPageResult 传入的 q 必须是已经 Normalize 过的，否则 size=0 会除零
func NewPageResult(list any, total int64, q PageQuery) PageResult {
    pages := 0
    if q.Size > 0 {
        pages = (int(total) + q.Size - 1) / q.Size  // 整数向上取整，不用 math.Ceil
    }
    return PageResult{List: list, Total: total, Page: q.Page, Size: q.Size, TotalPage: pages}
}

// ArticleRepository 前 5 个方法来自第 2 周（gin-api 的内存版），签名不动；
// 后 2 个是今天为「关联查询」新增的 —— 改接口的代价见 day2 练习 2 的说明。
type ArticleRepository interface {
    List() ([]model.Article, error)
    Get(id uint) (model.Article, error)
    Create(a model.Article) (model.Article, error)
    Update(a model.Article) error
    Delete(id uint) error

    ListByUser(userID uint, limit, offset int) ([]model.Article, int64, error)
    DetailWithRels(id uint) (model.Article, error)
}

type gormArticleRepo struct { db *gorm.DB }

func NewArticleRepo(db *gorm.DB) ArticleRepository { return &gormArticleRepo{db: db} }

var _ ArticleRepository = (*gormArticleRepo)(nil)

func (r *gormArticleRepo) List() ([]model.Article, error) {
    arts := []model.Article{}
    err := r.db.Order("id asc").Find(&arts).Error
    return arts, err
}

func (r *gormArticleRepo) Get(id uint) (model.Article, error) {
    var a model.Article
    err := r.db.First(&a, id).Error
    if errors.Is(err, gorm.ErrRecordNotFound) { return model.Article{}, ErrArticleNotFound }
    return a, err
}

func (r *gormArticleRepo) Create(a model.Article) (model.Article, error) {
    if err := r.db.Create(&a).Error; err != nil { return model.Article{}, err }
    return a, nil
}

func (r *gormArticleRepo) Update(a model.Article) error {
    var n int64
    if err := r.db.Model(&model.Article{}).Where("id = ?", a.ID).Count(&n).Error; err != nil {
        return err
    }
    if n == 0 { return ErrArticleNotFound }
    return r.db.Omit("User", "Tags").Save(&a).Error   // 更新主表，别连带写关联
}

func (r *gormArticleRepo) Delete(id uint) error {
    res := r.db.Delete(&model.Article{}, id)
    if res.Error != nil { return res.Error }
    if res.RowsAffected == 0 { return ErrArticleNotFound }
    return nil
}

// ListByUser 4 条 SELECT：计数 1 + 主表 1 + 作者批量 1 + 标签批量 1。
// 如果不 Preload 而回到 for 循环里逐条查，会变成 2 + 2N。
func (r *gormArticleRepo) ListByUser(userID uint, limit, offset int) ([]model.Article, int64, error) {
    var total int64
    if err := r.db.Model(&model.Article{}).Where("user_id = ?", userID).Count(&total).Error; err != nil {
        return nil, 0, err
    }
    arts := []model.Article{}
    err := r.db.Where("user_id = ?", userID).
        Preload("User").Preload("Tags").
        Order("created_at desc").Limit(limit).Offset(offset).
        Find(&arts).Error
    return arts, total, err
}

// DetailWithRels：作者走 Joins（一条 SQL 顺手带出），标签走 Preload（多对多 Preload 才成）
func (r *gormArticleRepo) DetailWithRels(id uint) (model.Article, error) {
    var a model.Article
    err := r.db.Preload("Tags").
        Joins("User").
        Select("articles.*").  // join 后两张表都有 id/created_at，不写清楚就歧义
        First(&a, id).Error
    if errors.Is(err, gorm.ErrRecordNotFound) { return model.Article{}, ErrArticleNotFound }
    if err != nil { return model.Article{}, err }
    return a, nil
}

func (h *ArticleHandler) ListByUser(c *gin.Context) {

    if !ok { return }

    var q dto.PageQuery
    if err := c.ShouldBindQuery(&q); err != nil {

        return

    q.Normalize()                               // ← 归一化必须紧跟绑定，之后只用 q.Size/q.Page

    switch {
    case service.IsNotFound(err):
        response.Fail(c, http.StatusNotFound, response.CodeUserNotFound, "用户不存在")
    case err != nil:
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务繁忙")
    default:
        response.OK(c, res)                     // {list,total,page,size,total_page}
    }
}

        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务繁忙")
    default:
        response.OK(c, a)
    }
}

问题 1：跑起来一共几条 SQL？答：2 条——articles LEFT JOIN users ON … WHERE articles.id = 1 LIMIT 1 一条，tags WHERE article_tags.article_id IN (1) 一条。把 Joins("User") 换成 Preload("User") 就变 3 条，两种写法都要会。

入参带 tags: ["go","docker"]（字符串数组）。落库时先 FindOrCreate 拿标签 ID，再用 Association("Tags").Replace 建立关系。反复用同一批标签创建两篇文章，确认 tags 表里没有重复行。

internal/service/article.go（追加）// Create 三步：验作者 → 建文章 → 挂关系。今天故意「不加事务」，练习 4 末尾会踩出脏数据，day5 收拾
func (s *ArticleService) Create(userID uint, req dto.CreateArticleReq) (model.Article, error) {
    if _, err := s.users.Get(userID); err != nil {
        if IsNotFound(err) { return model.Article{}, ErrAuthorNotFound } // → 400 + 1004
        return model.Article{}, err
    }
    a, err := s.arts.Create(model.Article{
        Title: req.Title, Content: req.Content,
        Summary: req.Summary, CoverImage: req.CoverImage, UserID: userID,
    })
    if err != nil { return model.Article{}, err }

    ids := make([]uint, 0, len(req.Tags))
    for _, name := range req.Tags {
        t, err := s.tags.FindOrCreate(name)      // 有则复用，无则插入；返回的 t 一定带 ID
        if err != nil { return a, err }         // ← 注意这里返回的是 a：文章已经躺在库里了
        ids = append(ids, t.ID)
    }
    if err := s.tags.ReplaceFor(a.ID, ids); err != nil {
        return a, err                            // ← 同样：脏数据已经产生了
    }
    return s.arts.DetailWithRels(a.ID)             // 回读一次，把关联字段填好再返给前端
}

常见坑（新手 100% 会踩）

坑现象正确姿势
以为 Preload 自动生效a.User.Nickname 一直是零值，JSON 里没关联关联必须显式 Preload / Joins / Association().Find()，GORM 没有惰性加载
循环里逐条查列表页 50 条 SQL，日志刷屏，接口 800msPreload("X")，让它变成 WHERE ... IN (...)
Create 时直接塞新关联对象标签表出现重复行或 Error 1062先 FirstOrCreate 拿 ID，再用 Association().Append/Replace
foreignKey 方向搞反报 invalid field reference 或结果永远是空HasMany 写 foreignKey:UserID（对方表的外键），BelongsTo 外键在自己身上
many2many 表名带空格/写错中间表建了但查不到关系；或 Table "x doesn't exist"tag 写成 gorm:"many2many:article_tags;"（结尾分号是习惯），AutoMigrate 后 SHOW TABLES 确认
Join 后列名歧义Ambiguous column name 'id'、Preload 结果被 join 污染Select("articles.*") 或写表名前缀；Count 时加 Distinct
以为删父记录会级联用户删了，文章还在，指向不存在的 user_id事务里显式删关联数据，或建真正的数据库外键约束

今日名词卡

术语一句话解释
N+1 查询1 条主查询 + N 条子查询，ORM 最常见的性能事故，等价于 JS 的 await-in-loop
Preload主查询完成后，用一条 IN (...) 批量把关联数据填进 struct 字段
Joins把关联表拼进同一条 SQL，一条搞定，适合只取少数字段或按关联条件过滤
中间表（join table）多对多的落地形式，两个外键列组成联合主键，GORM 用 many2many: 自动管理
Association 模式db.Model(&x).Association("Tags")：只读写关系，不创建也不删除对方记录
级联保存Create/Save 主记录时连带写入非零 ID 的关联 struct 的行为
行放大（row multiplication）一对多 join 后父行按子行数重复出现，Count/分页都会失真
