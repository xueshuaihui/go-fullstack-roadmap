关联查询：一对多与多对多

单表 CRUD 只是及格线，真实业务的力量在关系上：一篇文章属于某个作者（一对多）、可以贴多个标签（多对多）。今天你要搞定 GORM 的关联声明与 Preload，并且亲眼看一次 N+1 灾难——这是规划「常见坑」清单第 6 条，也是面试高频题。

课前须知：关系在数据库里到底是什么

没有「对象嵌套」这回事，只有外键。数据库里 articles.user_id = 1 就是一个数字。所谓「拿到用户和他的文章」，永远是两条 SQL：先查 users，再查 articles WHERE user_id IN (1)。GORM 的关联功能只是把这两条 SQL 的编排自动化了。理解这点，Preload 为什么有时变 N+1、为什么 Joins 只要一条 SQL，全都通了。

ORM 世界里的四种关系，对应 JS 里你熟悉的数据形状：BelongsTo（文章 → 一个作者）、HasOne（用户 → 一个头像）、HasMany（用户 → 多篇文章）、Many2Many（文章 ↔ 多个标签）。声明方向很重要：外键在哪张表，哪张表就写 belongs-to。

2. 造点种子数据：关联的创建与级联保存

GORM 在 Create 时会自动保存关联对象——这既是便利也是陷阱：

cmd/seed/main.gofunc seed(db *gorm.DB) {
    u := model.User{Name: "小明", Email: "xm@example.com", Password: "h1"}
    db.Create(&u)   // 拿到 u.ID = 1

    // ⚠️ 一次 Create 带上 Tags：GORM 会连带 INSERT tags 与 article_tags，共 3 类写入
    a := model.Article{
        Title:   "Go 的 Preload 为什么快",
        Content: "……",
        UserID:  u.ID,
        Tags: []model.Tag{
            {Name: "go"},
            {Name: "gorm"},
        },
    }
    if err := db.Create(&a).Error; err != nil {
        log.Fatal(err)
    }
    fmt.Printf("article=%d tags=%d(id=%d,id=%d)\n", a.ID, len(a.Tags), a.Tags[0].ID, a.Tags[1].ID)
}

级联保存的两个注意事项：① 关联的 Tag 是新 struct 零 ID，所以每次 Create 文章都会新插入标签行；因为 Name 上有唯一索引，第二篇也用 "go" 时会报 Error 1062 Duplicate entry，而不是复用已有标签。正确做法：先按名字查/建标签拿到 ID，再把带 ID 的 tag 挂上去（见第 3 节与练习 4）。② Save(&a) 会连带更新关联：想只改文章本身，用 Updates；想整体替换关联，用 db.Session(&gorm.Session{FullSaveAssociations: true}).Save(&a)。

3. 只维护关系，不创建记录：Association 模式

关系维护// 拿或建标签（有则复用，无则插入）—— 多对多的标准起手式
func firstOrCreateTag(db *gorm.DB, name string) (model.Tag, error) {
    var tag model.Tag
    err := db.Where(map[string]any{"name": name}).FirstOrCreate(&tag).Error
    return tag, err
}

var a model.Article
db.First(&a, 1)
goTag, _ := firstOrCreateTag(db, "go")
dockerTag, _ := firstOrCreateTag(db, "docker")

db.Model(&a).Association("Tags").Append([]model.Tag{goTag, dockerTag}) // 追加，只写中间表
db.Model(&a).Association("Tags").Replace([]model.Tag{goTag})           // 整体替换成这组
db.Model(&a).Association("Tags").Delete([]model.Tag{dockerTag})        // 断开指定关系（标签本身还在）

var tags []model.Tag
db.Model(&a).Association("Tags").Find(&tags)       // 读关系
n, err := db.Model(&a).Association("Tags").Count() // 数一下

类比 JS：这就像 Object.assign（Append）、整份替换（Replace）、把外键设成 null（Disconnect / Erase）。Association 模式只动中间表，永远不会删除 tags 表的行，所以「删一篇文章」不会误删别人也在用的标签。

4. Preload：一次把关联带出（以及 N+1 灾难）

默认情况下关联字段是空的——GORM 不查它，一条 SQL 都不多发：

N+1 对比// ❌ 手写循环查询：1 + N 条 SQL
var users []model.User
db.Find(&users)                                   // SQL 1：SELECT * FROM users
for i := range users {
    db.Where("user_id = ?", users[i].ID).Find(&users[i].Articles) // 每个用户一条 → N 条
}

// ✅ Preload：固定 2 条 SQL，不管多少用户
db.Preload("Articles").Find(&users)              // SQL 1: SELECT * FROM users
                                                  // SQL 2: SELECT * FROM articles WHERE user_id IN (1,2,3,...)

这就是你在 JS 里写过的坑：for (const u of users) { u.articles = await api.getArticles(u.id) }——串行 N 次请求。GORM 的 N+1 完全同构，只是把「await 网络」换成「round-trip 数据库」。修正思路也一样：把 N 次单查合并成一次批查（SQL 里就是 IN (...)），或者一次性 join 出来。区别在于：JS 里你还能 Promise.all 并发掩盖问题，数据库里 100 次 round-trip 就是实打实的 100 次网络往返。

Preload 的四种进阶形态：

Preload 进阶// ① 带条件（字符串 + 占位符）
db.Preload("Articles", "views > ?", 100).First(&user, 1)
db.Preload("Articles", "title LIKE ?", "%"+kw+"%").First(&user, 1)

// ② 裁剪字段 + 排序 + 限量（回调里返回一个加了条件的 *gorm.DB）—— 列表页「最近 5 篇」
db.Preload("Articles", func(db *gorm.DB) *gorm.DB {
    return db.Select("id", "title", "user_id", "created_at").Order("created_at desc").Limit(5)
}).Find(&users)

// ③ 嵌套：用户 → 文章 → 文章标签（三条 SQL）
db.Preload("Articles.Tags").Find(&users)

// ④ 反向：文章带作者、带标签（多对多与 belongs-to 都能 Preload）
var article model.Article
db.Preload("Tags").Preload("User").First(&article, 1)

Preload 是「懒加载 + 显式批量」的组合，好处是主查询干净、支持 order/limit/条件；代价是每次关联多一条 SQL。列表接口里关联只需用于显示一两个字段时，考虑下面的 Joins。

5. Joins：一条 SQL 搞定

Joins// ① 简写：belongsto / hasone 关联可以直接写名字（不支持 has-many / many2many）
var arts []model.Article
db.Joins("User").Where("users.name = ?", "小明").Preload("Tags").Find(&arts)

// ② 原生 JOIN + 自定义结果结构体：只要作者名，不要整个 User 对象
type ArticleRow struct {
    ID        uint   `gorm:"column:id" json:"id"`
    Title     string `gorm:"column:title" json:"title"`
    UserEmail string `gorm:"column:user_email" json:"user_email"`
}
// ↑ 若结构体名恰好匹配表名，GORM 会做内嵌扫描；用独立 DTO 结构最稳
var rows []ArticleRow
db.Table("articles").
    Select("articles.id, articles.title, users.email AS user_email").
    Joins("LEFT JOIN users ON users.id = articles.user_id").
    Where("articles.views > ?", 0).
    Scan(&rows)

// ③ 关联计数：某用户有多少篇文章（不 Preload 整份数据）
var cnt int64
db.Model(&model.Article{}).Where("user_id = ?", 1).Count(&cnt)
手段SQL 条数能带出 has-many？能对关联表 where/order/limit？什么时候用
循环里查（N+1）1 + N能能永远不用
Preload1 + 每种关联 1 条能能（条件/裁剪/限量都行）详情接口、要返回嵌套 JSON
Joins1 条不能（会行放大）能，但要自己写 ON/WHERE只取关联的少量字段、需要按关联表条件过滤/排序

Count 和 Joins 混用要小心：一对多 JOIN 会让行数翻倍，db.Model(&a).Joins("User").Count(&n) 统计的是 join 后的行数。需要去重时写 Distinct("articles.id")，或干脆拆成两次查询。另外 GORM 的 Delete(&user, 1) 不会级联删除他的文章——删除用户时要在事务里手工删/软删其文章（Day 5 会说），或建表时加数据库级外键约束。

练习 1：种子数据 + 亲眼看 N+1（30 分钟）

跑第 2 节的 seed 程序，建 3 个用户、每人 2 篇带标签的文章。然后写两版「列出所有用户及其文章」：循环版与 Preload("Articles") 版，把终端里 [rows:n] 的 SQL 行数分别记下来。

参考答案：循环版 1 + 3 = 4 条 SELECT（用户多了就是几十条）；Preload 版恒定 2 条，第二条是 WHERE user_id IN (1,2,3)。标签版 Preload("Articles.Tags") 是 3 条，多一条 WHERE article_tags.article_id IN (...)。

练习 2：GET /users/:id/articles（40 分钟）

返回该用户的分页文章列表，每篇带作者信息（id、name、email，不含 password），并带出评论位（标签）。要求只发 2 条 SQL。

internal/handler/article.gofunc (h *ArticleHandler) ListByUser(c *gin.Context) {
    id, err := strconv.ParseUint(c.Param("id"), 10, 64)
    if err != nil || id == 0 {
        c.JSON(400, gin.H{"code": 1004, "message": "id 必须是正整数"})
        return
    }

    var user model.User
    if err := h.db.Select("id", "name", "email").First(&user, id).Error; err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            c.JSON(404, gin.H{"code": 1001, "message": "用户不存在"})
            return
        }
        c.JSON(500, gin.H{"code": 5000, "message": "服务异常"})
        return
    }

    var arts []model.Article
    if err := h.db.Preload("Tags").
        Where("user_id = ?", user.ID).
        Order("created_at desc").
        Find(&arts).Error; err != nil {
        c.JSON(500, gin.H{"code": 5000, "message": "服务异常"})
        return
    }

    c.JSON(200, gin.H{"code": 0, "message": "success", "data": gin.H{
        "user":    user,   // password 因 json:"-" 不会出现
        "list":    arts,
        "total":   len(arts),
    }})
}

验收：curl -s localhost:8080/users/1/articles 的 data.list[0].tags 非空，响应里搜不到 password。

练习 3：GET /articles/:id 带 tags 与作者（30 分钟）

一次请求返回 { id, title, content, views, user:{id,name}, tags:[{id,name}] }。

repository/article.gofunc (r *gormArticleRepo) DetailWithRels(id uint) (*model.Article, error) {
    var a model.Article
    err := r.db.Preload("Tags").
        Joins("User").          // belongs-to 用 Joins 一条 SQL 带出作者，省一条
        Select("articles.*").   // 避免 join 后列名歧义，显式只要主表列
        First(&a, id).Error
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, ErrArticleNotFound
    }
    return &a, err
}

参考答案：跑起来共 2 条 SQL（articles LEFT JOIN users 一条 + tags WHERE article_tags.article_id IN (id) 一条）。若嫌 Select("articles.*") 麻烦，把 Joins("User") 换成 Preload("User") 也可以，只是变成 3 条 SQL。

练习 4：让标签可复用（25 分钟）

把 POST /articles 的入参改成带 tags: ["go","docker"]（字符串数组），落库时先 FirstOrCreate 拿标签 ID，再用 Association("Tags").Replace 建立关系。反复用同一篇相同标签创建两篇文章，确认 tags 表里没有重复行。

参考答案要点：db.Where(map[string]any{"name": n}).FirstOrCreate(&tag) 是幂等的；关系写入用 Association 而不是把 tag 塞进 Article.Tags 再 Create，后者在标签已存在时仍会尝试插入而撞唯一索引。若标签不存在又希望并发安全，第 4 周会补 ON DUPLICATE KEY UPDATE id = id（clause.OnConflict）写法。

今日名词卡

术语一句话解释
N+1 查询1 条主查询 + N 条子查询，ORM 最常见的性能事故，等价于 JS 的 await-in-loop
Preload主查询完成后，用一条 IN (...) 批量把关联数据填进 struct 字段
Joins把关联表拼进同一条 SQL，一条搞定，适合只取少数字段或按关联条件过滤
中间表（join table）多对多的落地形式，两个外键列组成联合主键，GORM 用 many2many: 自动管理
Association 模式db.Model(&x).Association("Tags")：只读写关系，不创建也不删除对方记录
级联保存Create/Save 主记录时连带写入非零 ID 的关联 struct 的行为
