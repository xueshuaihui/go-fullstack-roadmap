事务、连接池、软删除

本周最后一天，把三件「上线前必须懂」的事补上：事务保证多步写入要么全成要么全废；连接池决定你的服务在并发下是稳还是崩；软删除让数据可以「消失但不丢」。今天的练习会要求你故意制造一次失败，亲眼看数据库回滚。

课前须知：为什么这三件事放在一起讲

它们都关于「连接」这个稀缺资源。事务会把一条连接独占到你 return nil 为止；连接池决定同时能有几条连接；软删除则让「删数据」变成一次普通的 UPDATE——不需要级联删除大量行，也就不会长事务占着连接。把它们一起理解，你就从「会写 CRUD」升级到「会写服务端」。

知识讲义

1. 事务是什么：全成或全废

没有事务时，一个「创建文章 + 关联 3 个标签」的接口由 2 条以上 SQL 组成。如果第 2 步挂了（标签唯一索引冲突、连接断了、进程被 kill），你会看到文章存在但没有标签的脏数据——这类残留数据是最难查的线上问题之一。

无事务 vs 有事务// ❌ 裸写：第二步失败，第一步不会撤销
db.Create(&article)                        // 成功 → id=42 落库
db.Model(&article).Association("Tags").Replace(badTags) // 失败

// ✅ 事务：两步要么都留痕，要么都不留
err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(&article).Error; err != nil {
        return err            // ← 返回 error：自动 ROLLBACK，文章也不会留下
    }
    if err := tx.Model(&article).Association("Tags").Replace(tags); err != nil {
        return err
    }
    return nil                // ← 返回 nil：自动 COMMIT
})

类比你在 JS 里写过多步副作用的补偿逻辑：try { await stepA(); await stepB(); } catch (e) { await undoA(); throw e }。事务就是数据库帮你写好了那个 catch——你只管把「失败就 return err」写清楚，ROLLBACK 由数据库执行，不存在「补偿失败」或忘记补偿。而且它比手写补偿更强：undoA 只能撤销 A 的可回退部分，事务能撤销任意多条写入。

闭包结局GORM 行为Transaction 的返回值
return nilCOMMITnil
return errROLLBACK就是你返回的那个 err（会原样传给你）
闭包内 panic先 ROLLBACK，再把 panic 重抛出去不会返回，panic 继续向上传（Gin 的 Recovery 中间件会兜住）

三条铁律：① 闭包里只能用 tx，写成 db.Create(...) 就跳出事务了（这是本周最容易犯且最难发现的 bug）；② 事务里不要有网络调用、不要 time.Sleep，连接被独占期间别人拿不到；③ 嵌套调用 tx.Transaction(...) GORM 会用 savepoint，内层回滚不影响外层，但别把逻辑绕复杂。

2. 事务跨层：把 tx 当参数传下去

真实项目里「创建文章」不止建一行：挂标签、给作者的文章数 +1（ArticleCount 是 day2 在 internal/model/user.go 里就定好的冗余列，类型 int64、tag 是 gorm:"column:article_count;type:bigint;not null;default:0"），这些写入分属不同 repository。标准做法是让仓储方法多收一个事务句柄 tx *gorm.DB——谁开事务谁把 tx 传下去，方法内部只用传进来的 tx，绝不碰自己那份 r.db。下面是形状（完整可跑版在练习 1）：

片段：仓储方法接 tx + 新文件 stats.go（完整实现见练习 1）// internal/repository/article.go：在 day3 那份 gormArticleRepo 上补一个 tx 版 Create
func (r *gormArticleRepo) CreateWith(ctx context.Context, tx *gorm.DB, a model.Article) (model.Article, error) {
    if err := tx.WithContext(ctx).Create(&a).Error; err != nil {
        return model.Article{}, err
    }
    return a, nil
}

// internal/repository/stats.go：day5 新文件，专门维护上面那个 ArticleCount 冗余列
type StatsRepository interface {
    IncArticleCount(ctx context.Context, tx *gorm.DB, userID uint) error
}

type gormStatsRepo struct { db *gorm.DB }

func NewStatsRepo(db *gorm.DB) StatsRepository { return &gormStatsRepo{db: db} }

var _ StatsRepository = (*gormStatsRepo)(nil)

// DB 端自增（gorm.Expr）避免「读出来 +1 再写回去」的并发丢更新；UpdateColumn 不顺手改 updated_at
func (r *gormStatsRepo) IncArticleCount(ctx context.Context, tx *gorm.DB, userID uint) error {
    return tx.WithContext(ctx).Model(&model.User{}).Where("id = ?", userID).
        UpdateColumn("article_count", gorm.Expr("article_count + ?", 1)).Error
}

service 层的业务边界就是事务边界：day3 定型的 ArticleService 有三个依赖（arts/users/tags），day5 为「开事务 + 更新计数」再加 db（只用来 Transaction）和 stats（上面那个仓储），构造函数从 3 参扩到 5 参——这正是 day3 练习里预告的「day5 会给它加 db 和 stats」那次签名变化：

片段：service 开事务，把 tx 往下传// internal/service/article.go（struct 与构造函数的完整改造见练习 1）
func (s *ArticleService) publishInTx(ctx context.Context, userID uint, req dto.CreateArticleReq) (model.Article, error) {
    var created model.Article
    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        a, err := s.arts.CreateWith(ctx, tx, model.Article{
            Title: req.Title, Content: req.Content,
            Summary: req.Summary, CoverImage: req.CoverImage, UserID: userID, // 作者来自登录态，不在 DTO 里
        })
        if err != nil { return err }
        // 标签：先用 tx 版 FindOrCreateWith 拿带 ID 的 tag，再 ReplaceForWith 挂关系（练习 1 给全）
        if err := s.attachTags(ctx, tx, a.ID, req.Tags); err != nil { return err }
        if err := s.stats.IncArticleCount(ctx, tx, userID); err != nil { return err }
        created = a
        return nil                        // 返回 nil → COMMIT；中途 return err → ROLLBACK
    })
    if err != nil { return model.Article{}, err }
    return s.arts.DetailWithRels(created.ID)   // 事务外回读一次，把 user/tags 填好
}

context.Context 第一次进本项目（第 5 周正式讲，今天照抄）：它是 Go 沿调用链往下传「取消信号 / 超时 / trace-id」的固定约定，凡是能阻塞的 I/O 都接一个 ctx。对照你在 JS 里熟悉的 AbortSignal——前端断开连接时 signal.aborted 变 true；Go 里对应 ctx.Done() 这个 channel 被关闭，tx.WithContext(ctx) 让 MySQL 驱动看到取消就中断当前查询。区别是 Go 把它做成了贯穿标准库的显式参数，而 JS 各库各自决定接不接。今天的用法记两条就够：ctx 从 handler 的 c.Request.Context() 取、一路往下传；脚本里没有请求就传 context.Background()，别传 nil。

顺带一个 GORM 冷知识：Create 单条记录（含关联）默认就已经包在一个事务里，日志里会看到 BEGIN;...COMMIT;。如果你的写入路径单一、不需要这些额外 BEGIN/COMMIT，可以在配置里 SkipDefaultTransaction: true 关掉；但学习阶段建议保持默认 false（即不跳过），多一层保护。

3. 手工事务：Begin / Commit / Rollback

等价写法tx := db.Begin()
if tx.Error != nil {
    return tx.Error
}

// 用一个内联函数把多步收成一个 error，出口只剩两条路径
err := func() error {
    if err := tx.Create(&article).Error; err != nil {
        return err
    }
    // Association(...).Replace(...) 返回的是裸 error，没有 .Error 可取（day3 第 4 节强调过）
    if err := tx.Model(&article).Association("Tags").Replace(tags); err != nil {
        return err
    }
    return nil
}()

if err != nil {
    tx.Rollback()      // ← 每条失败路径都必须显式回滚，这就是闭包版存在的理由
    return err
}
return tx.Commit().Error

能用 db.Transaction 就用它——闭包版本不会忘记 Rollback（每个 return 路径都自动处理）。手工 Begin 只在你需要「事务生命周期比一个函数更长」的少见场景使用，且必须保证每条出口都 Commit 或 Rollback，否则连接泄漏，池子被耗尽。

4. 连接池：三个参数的调法

gorm.Open 返回的 db 内部持有一个 *sql.DB（不是连接，是连接池），Go 标准库 database/sql 自带池化。day1 的 internal/repository/db.go 里那个 New(dsn) 已经取出了 sqlDB 做 Ping，今天就在它旁边补几行池参数（MustConnect 不动，它内部调的还是这个 New）：

internal/repository/db.go（在 day1 的 New 里补池参数）package repository

import (
    fmt
    time

    "gorm.io/driver/mysql"
    "gorm.io/gorm"
    "gorm.io/gorm/logger"
)

func New(dsn string) (*gorm.DB, error) {
    db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{
        Logger:            logger.Default.LogMode(logger.Info), // day1 原样：开发期把 SQL 打到终端
        BlockGlobalUpdate: true,                              // day1 原样
    })
    if err != nil {
        return nil, fmt.Errorf("open mysql: %w", err)
    }

    sqlDB, err := db.DB()          // 拿到标准库的连接池（day1 这里只做了 Ping）
    if err != nil {
        return nil, err
    }
    sqlDB.SetMaxOpenConns(25)      // 池内同时最多 25 条连接（含在用+空闲）；0 = 不限
    sqlDB.SetMaxIdleConns(10)      // 空闲时保留 10 条，避免高峰期反复握手
    sqlDB.SetConnMaxLifetime(10 * time.Minute) // 活够 10 分钟就换新，防被中间设备悄悄断
    sqlDB.SetConnMaxIdleTime(3 * time.Minute)  // 闲 3 分钟就关，夜里不占 MySQL 名额

    if err := sqlDB.Ping(); err != nil {   // 启动即探活，别等第一个请求才发现连不上
        return nil, err
    }
    return db, nil
}
参数调太小调太大怎么定
SetMaxOpenConns并发请求排队等连接，接口 P99 飙升（但不会崩）MySQL 侧 max_connections（默认 151）被打满，报 Error 1040: Too many connections，别人也连不上单个 Go 进程取 10~25 起步；算法：实例数 × MaxOpen ≤ max_connections × 0.8
SetMaxIdleConns波峰时反复建连（TCP + MySQL 认证握手，几毫秒到几十毫秒）白占 MySQL 内存（每连接约几百 KB~几 MB）约为 MaxOpen 的 1/3~1/2；流量平稳时可与 MaxOpen 相等
SetConnMaxLifetime频繁重建连接，浪费握手比 MySQL wait_timeout（默认 28800s）或云 LB 空闲超时（常为 60~3600s）还长时，会拿到已被对端关掉的连接 → invalid connection / driver: bad connection取「所有中间层超时里最小的那个」再除以 2，本地/学习项目 10 * time.Minute 很稳

对照 Node：mysql2 的 connectionLimit: 10 就是 SetMaxOpenConns。区别在于 Go 的 db 变量本身就是池，全进程共用一个 *gorm.DB 就对了——不要每次请求 gorm.Open 一次，那等于每次握手新建连接，性能立刻塌方。

5. 软删除：gorm.DeletedAt 与 Unscoped

判断「删一行到底是 UPDATE 还是 DELETE」只看一件事：模型有没有 DeletedAt 字段。day2 定的 User 与 Article 都内嵌了 gorm.Model，而 gorm.Model 里就躺着 DeletedAt gorm.DeletedAt `gorm:"index"`——所以对它俩调 Delete 发的是 UPDATE：

谁软删、谁硬删（对照 day2 的三个模型，不重定义）// User / Article：内嵌 gorm.Model → 有 DeletedAt → Delete 打时间戳（软删除）
// Tag（day2）：只写 ID/Name/CreatedAt，没有 gorm.Model 也没有 DeletedAt →
//   db.Delete(&tag, id) 发的是真 DELETE，行直接从 tags 表消失

// gorm.Model 展开出来那行就是开关（day2 第 1 节已给）：
DeletedAt gorm.DeletedAt `gorm:"index"`  // ← 有它 = 软删除；json 没打标，所以序列化时会露 deleted_at，
                                       //   要藏就在 DTO 里处理（day1 第 6 节那个 note 讲过大写键问题）
shell / Go 对照// ① 删除：不是 DELETE，而是打上时间戳
db.Delete(&model.Article{}, 1)
// UPDATE articles SET deleted_at='2026-09-23 10:00:00' WHERE articles.id = 1

// ② 所有普通查询自动加 WHERE deleted_at IS NULL（First/Find/Count/Preload 全都加）
db.Find(&list)                 // SELECT * FROM articles WHERE articles.deleted_at IS NULL
db.Model(&model.Article{}).Count(&total)  // total 不含已软删的行 ✅ 统计口径天然正确

// ③ Unscoped：绕过软删除过滤
db.Unscoped().First(&a, 1)     // 能读到刚「删掉」的那篇（含 deleted_at 值）
db.Unscoped().Find(&all)       // 管理后台「回收站」列全部
db.Unscoped().Delete(&model.Article{}, 1) // 真·DELETE FROM articles WHERE id = 1

// ④ 只列已删除的
db.Unscoped().Where("deleted_at IS NOT NULL").Find(&trash)

软删除的四个代价要知道：① 唯一索引仍占位——软删了 a@x.com 的用户后，注册同名邮箱会撞 Error 1062；解法是把唯一索引改成 (email, deleted_at) 联合，或删除时把邮箱改名（deleted_1_a@x.com），或用 is_deleted 标记列而非 NULL。
② Preload 的关联也会被过滤，作者被软删后文章的 User 字段是零值，展示要留 user_name 冗余字段。
③ AutoMigrate 不会因为删掉 DeletedAt 字段就恢复硬删除——列还在表里，得手工 DROP。
④ day3 说的「删除用户不会级联删文章」在软删除下同样成立，业务上要么在事务里一起软删，要么允许「孤儿文章」并在 UI 显示「已注销用户」。

internal/repository/article.go + tag.go（补 tx 版方法；两个文件的 import 各加一行 "context"）// —— article.go：接口加一行 CreateWith，实现接收 tx 而不是 r.db ——

func (r *gormArticleRepo) CreateWith(ctx context.Context, tx *gorm.DB, a model.Article) (model.Article, error) {

        return model.Article{}, err
    }
    return a, nil

// —— tag.go：接口加两行，实现把 day3 那份从 r.db 换成传入的 tx ——
//   FindOrCreateWith(ctx context.Context, tx *gorm.DB, name string) (model.Tag, error)
//   ReplaceForWith(ctx context.Context, tx *gorm.DB, articleID uint, tagIDs []uint) error
func (r *gormTagRepo) FindOrCreateWith(ctx context.Context, tx *gorm.DB, name string) (model.Tag, error) {
    var tag model.Tag
    err := tx.WithContext(ctx).Where(map[string]any{"name": name}).FirstOrCreate(&tag).Error
    return tag, err
}

func (r *gormTagRepo) ReplaceForWith(ctx context.Context, tx *gorm.DB, articleID uint, tagIDs []uint) error {
    a := model.Article{ID: articleID}
    if len(tagIDs) == 0 {
        return tx.Model(&a).Association("Tags").Clear()   // 裸 error，别写 .Error（day3 第 4 节）
    }
    var tags []model.Tag
    if err := tx.WithContext(ctx).Find(&tags, tagIDs).Error; err != nil {
        return err
    }
    return tx.Model(&a).Association("Tags").Replace(tags) // 裸 error，别写 .Error
}

import (
    context
    errors

type ArticleService struct {
    arts  repository.ArticleRepository
    users repository.UserRepository
    tags  repository.TagRepository
    stats repository.StatsRepository // ← day5 新增（section 2 的 stats.go）
    db    *gorm.DB                   // ← day5 新增：只为开事务，不拿来直接 Where/Find
}

// 构造函数从 day3 的 3 参加到 5 参 —— 就是 day3 练习里预告的那次签名变化
func NewArticleService(arts repository.ArticleRepository, users repository.UserRepository,
    tags repository.TagRepository, stats repository.StatsRepository, db *gorm.DB) *ArticleService {
    return &ArticleService{arts: arts, users: users, tags: tags, stats: stats, db: db}
}

// attachTags：事务内把标签名换成带 ID 的 tag，再整体替换关系（只动 article_tags）
func (s *ArticleService) attachTags(ctx context.Context, tx *gorm.DB, articleID uint, names []string) error {
    ids := make([]uint, 0, len(names))
    for _, name := range names {
        t, err := s.tags.FindOrCreateWith(ctx, tx, name) // 有则复用、无则插入
        if err != nil { return err }
        ids = append(ids, t.ID)
    }
    return s.tags.ReplaceForWith(ctx, tx, articleID, ids)
}

// Create 取代 day3 的无事务版：建文章 + 挂标签 + 计数 +1，要么全成要么全废。
// forceFail 只是本练习的「故意炸」开关，验收完从签名里删掉，Create 回到 (ctx, userID, req)。
func (s *ArticleService) Create(ctx context.Context, userID uint, req dto.CreateArticleReq, forceFail bool) (model.Article, error) {
    if _, err := s.users.Get(userID); err != nil {
        if IsNotFound(err) { return model.Article{}, ErrAuthorNotFound } // → 400 + 1004
        return model.Article{}, err
    }
    var created model.Article
    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        a, err := s.arts.CreateWith(ctx, tx, model.Article{
            Title: req.Title, Content: req.Content,
            Summary: req.Summary, CoverImage: req.CoverImage, UserID: userID,
        })
        if err != nil { return err }
        if err := s.attachTags(ctx, tx, a.ID, req.Tags); err != nil { return err }
        if err := s.stats.IncArticleCount(ctx, tx, userID); err != nil { return err }
        if forceFail { return errors.New("故意失败：观察回滚") } // ← 触发 ROLLBACK
        created = a
        return nil                                    // ← 返回 nil 才 COMMIT
    })
    if err != nil { return model.Article{}, err }
    return s.arts.DetailWithRels(created.ID)         // 事务外回读，把 user/tags 填好
}

练习 3：软删除三件套（35 分钟）

先纠正一件事：day2 的 gormArticleRepo.Delete 其实早就是软删除了（Article 内嵌 gorm.Model 带 DeletedAt），所以这里不用再写一个 SoftDelete。今天真正要补的是「读回收站」和「真删除」两个能力，走满三层（handler 里不许出现 *gorm.DB，也不许 c.JSON），路由全部挂 /api/v1。

internal/repository/article.go（接口加两行，实现接在文件末尾）//   Trash(q dto.PageQuery) ([]model.Article, int64, error)   // 回收站：分页 + 总数
//   HardDelete(id uint) error                                // 真·DELETE

// Trash：Unscoped 关掉软删除过滤，再手动只挑 deleted_at 非空的行；base 每次返新链，Count/Find 不互污（day4 的规矩）
func (r *gormArticleRepo) Trash(q dto.PageQuery) ([]model.Article, int64, error) {
    base := func() *gorm.DB {
        return r.db.Unscoped().Model(&model.Article{}).Where("articles.deleted_at IS NOT NULL")
    }
    var total int64
    if err := base().Count(&total).Error; err != nil {
        return nil, 0, err
    }
    list := []model.Article{}
    err := base().Order("articles.deleted_at desc").Limit(q.Size).Offset(q.Offset()).Find(&list).Error
    return list, total, err
}

// HardDelete：Unscoped().Delete 才发 DELETE FROM，而不是再打一次时间戳
func (r *gormArticleRepo) HardDelete(id uint) error {
    res := r.db.Unscoped().Delete(&model.Article{}, id)
    if res.Error != nil { return res.Error }
    if res.RowsAffected == 0 { return ErrArticleNotFound }
    return nil
}

func (h *ArticleHandler) Delete(c *gin.Context) {
    id, ok := parseID(c)
    if !ok { return }
    if err := h.svc.Delete(id); err != nil {
        if service.IsArticleNotFound(err) {
            response.Fail(c, http.StatusNotFound, response.CodeArticleNotFound, "文章不存在") // 404 + 2001
            return
        }
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务繁忙")
        return
    }
    response.OK(c, gin.H{"soft_deleted": id})
}

func (h *ArticleHandler) Trash(c *gin.Context) {
    var q dto.PageQuery
    if err := c.ShouldBindQuery(&q); err != nil {

        return
    }
    res, err := h.svc.Trash(q)
    if err != nil {
        response.Fail(c, http.StatusInternalServerError, response.CodeInternal, "服务繁忙")
        return
    }
    response.OK(c, res)
}

        }

        return
    }

参考答案：① 联合唯一索引 uniqueIndex:idx_email_del 同时挂在 Email 和 DeletedAt 上——NULL 在 MySQL 唯一索引里不参与去重，所以软删行不冲突；缺点：两条同邮箱的已软删记录仍会冲突（MySQL 8 可用函数索引绕）。② 删除时改写业务键（email = fmt.Sprintf("%s#%d.deleted", email, id)）——实现最简单，缺点：真实邮箱被污染，导出统计要小心。③ 不用 deleted_at，改用 status 字段（active/disabled）+ 部分索引思路——最贴近业务（「注销」本来就不是「删除」），但要自己在 base 查询里加条件。学习项目选 ①，生产项目多数选 ③。

常见坑（新手 100% 会踩）

坑现象正确姿势
事务闭包里用 db 而不是 tx回滚了，但那一步的数据还在——因为它在事务外闭包内所有写操作只用 tx；把 repository 方法设计成接收 tx 参数
忘了 return err出错却照常 COMMIT，脏数据入库每步 if err != nil { return err }，最后一行 return nil
事务里放外部 HTTP 调用接口一慢连接就被长期占用，池子耗尽把外部调用挪到事务外，事务只包数据库写入
手工 Begin 某条出口没 Rollback连接泄漏，一段时间后全线卡死优先 db.Transaction
每次请求都 gorm.Open连接数暴涨，MySQL 1040 Too many connections进程启动时建一个 *gorm.DB 全生命周期复用
ConnMaxLifetime 比网络层超时还长偶发 invalid connection / bad connection，重试即好设为最小超时的 1/2；重启容器也能复现该现象
以为软删是硬删表越来越大、唯一索引被占、磁盘不降需要真删时定时任务 Unscoped().Delete；或明确这就是「归档」
Unscoped().Find 后按 deleted_at IS NULL 手动过滤忘写回收站数据混进正常列表Unscoped 只在管理员/恢复场景用，且条件写清楚
