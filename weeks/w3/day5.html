事务、连接池、软删除

本周最后一天，把三件「上线前必须懂」的事补上：事务保证多步写入要么全成要么全废；连接池决定你的服务在并发下是稳还是崩；软删除让数据可以「消失但不丢」。今天的练习会要求你故意制造一次失败，亲眼看数据库回滚。

课前须知：为什么这三件事放在一起讲

它们都关于「连接」这个稀缺资源。事务会把一条连接独占到你 return nil 为止；连接池决定同时能有几条连接；软删除则让「删数据」变成一次普通的 UPDATE——不需要级联删除大量行，也就不会长事务占着连接。把它们一起理解，你就从「会写 CRUD」升级到「会写服务端」。

知识讲义

1. 事务是什么：全成或全废

没有事务时，一个「创建文章 + 关联 3 个标签」的接口由 2 条以上 SQL 组成。如果第 2 步挂了（标签唯一索引冲突、连接断了、进程被 kill），你会看到文章存在但没有标签的脏数据——这类残留数据是最难查的线上问题之一。

无事务 vs 有事务// ❌ 裸写：第二步失败，第一步不会撤销
db.Create(&article)                        // 成功 → id=42 落库
db.Model(&article).Association("Tags").Replace(badTags) // 失败

// ✅ 事务：两步要么都留痕，要么都不留
err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(&article).Error; err != nil {
        return err            // ← 返回 error：自动 ROLLBACK，文章也不会留下
    }
    if err := tx.Model(&article).Association("Tags").Replace(tags); err != nil {
        return err
    }
    return nil                // ← 返回 nil：自动 COMMIT
})

类比你在 JS 里写过多步副作用的补偿逻辑：try { await stepA(); await stepB(); } catch (e) { await undoA(); throw e }。事务就是数据库帮你写好了那个 catch——你只管把「失败就 return err」写清楚，ROLLBACK 由数据库执行，不存在「补偿失败」或忘记补偿。而且它比手写补偿更强：undoA 只能撤销 A 的可回退部分，事务能撤销任意多条写入。

闭包结局GORM 行为Transaction 的返回值
return nilCOMMITnil
return errROLLBACK就是你返回的那个 err（会原样传给你）
闭包内 panic先 ROLLBACK，再把 panic 重抛出去不会返回，panic 继续向上传（Gin 的 Recovery 中间件会兜住）

三条铁律：① 闭包里只能用 tx，写成 db.Create(...) 就跳出事务了（这是本周最容易犯且最难发现的 bug）；② 事务里不要有网络调用、不要 time.Sleep，连接被独占期间别人拿不到；③ 嵌套调用 tx.Transaction(...) GORM 会用 savepoint，内层回滚不影响外层，但别把逻辑绕复杂。

2. 事务跨层：把 tx 当参数传下去

真实项目里「创建文章」还要写「操作日志」「更新用户文章数」，它们分布在多个 repository。标准做法是让 repository 方法接收一个 *gorm.DB，谁开事务谁负责：

repository / service 协作// repository：不自己开事务，用传进来的 handle
func (r *articleRepo) CreateWith(ctx context.Context, tx *gorm.DB, a *model.Article) error {
    return tx.WithContext(ctx).Create(a).Error       // WithContext 让请求取消能传导到 SQL
}

func (r *statRepo) IncArticleCount(tx *gorm.DB, userID uint) error {
    // 前提：User 模型上有一个冗余计数字段 ArticleCount int（gorm:"not null;default:0"）
    return tx.Model(&model.User{}).Where("id = ?", userID).
        UpdateColumn("article_count", gorm.Expr("article_count + ?", 1)).Error // DB 端自增，避免读改写丢数
}

// service：业务边界 = 事务边界
func (s *articleService) Publish(ctx context.Context, in dto.CreateArticleReq) error {
    a := &model.Article{Title: in.Title, Content: in.Content, UserID: in.UserID}
    return s.db.Transaction(func(tx *gorm.DB) error {
        if err := s.articles.CreateWith(ctx, tx, a); err != nil {
            return err
        }
        tags := s.tags.FindOrCreateMany(tx, in.Tags)
        if err := tx.Model(a).Association("Tags").Replace(tags); err != nil {
            return err
        }
        return s.stats.IncArticleCount(tx, in.UserID)
    })
}

顺带一个 GORM 冷知识：Create 单条记录（含关联）默认就已经包在一个事务里，日志里会看到 BEGIN;...COMMIT;。如果你的写入路径单一、不需要这些额外 BEGIN/COMMIT，可以在配置里 SkipDefaultTransaction: true 关掉；但学习阶段建议保持默认 false（即不跳过），多一层保护。

3. 手工事务：Begin / Commit / Rollback

等价写法tx := db.Begin()
if tx.Error != nil {
    return tx.Error
}

// 用一个内联函数把多步收成一个 error，出口只剩两条路径
err := func() error {
    if err := tx.Create(&article).Error; err != nil {
        return err
    }
    if err := tx.Model(&article).Association("Tags").Replace(tags).Error; err != nil {
        return err
    }
    return nil
}()

if err != nil {
    tx.Rollback()      // ← 每条失败路径都必须显式回滚，这就是闭包版存在的理由
    return err
}
return tx.Commit().Error

能用 db.Transaction 就用它——闭包版本不会忘记 Rollback（每个 return 路径都自动处理）。手工 Begin 只在你需要「事务生命周期比一个函数更长」的少见场景使用，且必须保证每条出口都 Commit 或 Rollback，否则连接泄漏，池子被耗尽。

4. 连接池：三个参数的调法

gorm.Open 返回的 db 内部持有一个 *sql.DB（不是连接，是连接池），Go 标准库 database/sql 自带池化。想调参数就取出来：

internal/repository/db.gopackage repository

import (
    fmt
    time

    gorm.io/driver/mysql
    gorm.io/gorm
    gorm.io/gorm/logger
)

func New(dsn string) (*gorm.DB, error) {
    db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{
        Logger:            logger.Default.LogMode(logger.Warn),
        BlockGlobalUpdate: true,
    })
    if err != nil {
        return nil, fmt.Errorf("open mysql: %w", err)
    }

    sqlDB, err := db.DB()          // 拿到标准库的连接池
    if err != nil {
        return nil, err
    }
    sqlDB.SetMaxOpenConns(25)      // 池内同时最多 25 条连接（含在用+空闲）；0 = 不限
    sqlDB.SetMaxIdleConns(10)      // 空闲时保留 10 条，避免高峰期反复握手
    sqlDB.SetConnMaxLifetime(10 * time.Minute) // 活够 10 分钟就换新，防被中间设备悄悄断
    sqlDB.SetConnMaxIdleTime(3 * time.Minute)  // 闲 3 分钟就关，夜里不占 MySQL 名额

    if err := sqlDB.Ping(); err != nil {   // 启动即探活，别等第一个请求才发现连不上
        return nil, err
    }
    return db, nil
}
参数调太小调太大怎么定
SetMaxOpenConns并发请求排队等连接，接口 P99 飙升（但不会崩）MySQL 侧 max_connections（默认 151）被打满，报 Error 1040: Too many connections，别人也连不上单个 Go 进程取 10~25 起步；算法：实例数 × MaxOpen ≤ max_connections × 0.8
SetMaxIdleConns波峰时反复建连（TCP + MySQL 认证握手，几毫秒到几十毫秒）白占 MySQL 内存（每连接约几百 KB~几 MB）约为 MaxOpen 的 1/3~1/2；流量平稳时可与 MaxOpen 相等
SetConnMaxLifetime频繁重建连接，浪费握手比 MySQL wait_timeout（默认 28800s）或云 LB 空闲超时（常为 60~3600s）还长时，会拿到已被对端关掉的连接 → invalid connection / driver: bad connection取「所有中间层超时里最小的那个」再除以 2，本地/学习项目 10 * time.Minute 很稳

对照 Node：mysql2 的 connectionLimit: 10 就是 SetMaxOpenConns。区别在于 Go 的 db 变量本身就是池，全进程共用一个 *gorm.DB 就对了——不要每次请求 gorm.Open 一次，那等于每次握手新建连接，性能立刻塌方。

5. 软删除：gorm.DeletedAt 与 Unscoped

只要模型里有 DeletedAt gorm.DeletedAt 字段（内嵌 gorm.Model 已含），Delete 就自动变成 UPDATE：

模型与行为type Article struct {
    ID        uint           `gorm:"primaryKey" json:"id"`
    Title     string         `gorm:"type:varchar(128);not null;index" json:"title"`
    UserID    uint           `gorm:"not null;index" json:"user_id"`
    CreatedAt time.Time      `json:"created_at"`
    UpdatedAt time.Time      `json:"updated_at"`
    DeletedAt gorm.DeletedAt `gorm:"index" json:"-"`   // ← 软删除开关
}
shell / Go 对照// ① 删除：不是 DELETE，而是打上时间戳
db.Delete(&model.Article{}, 1)
// UPDATE articles SET deleted_at='2026-09-23 10:00:00' WHERE articles.id = 1

// ② 所有普通查询自动加 WHERE deleted_at IS NULL（First/Find/Count/Preload 全都加）
db.Find(&list)                 // SELECT * FROM articles WHERE articles.deleted_at IS NULL
db.Model(&model.Article{}).Count(&total)  // total 不含已软删的行 ✅ 统计口径天然正确

// ③ Unscoped：绕过软删除过滤
db.Unscoped().First(&a, 1)     // 能读到刚「删掉」的那篇（含 deleted_at 值）
db.Unscoped().Find(&all)       // 管理后台「回收站」列全部
db.Unscoped().Delete(&model.Article{}, 1) // 真·DELETE FROM articles WHERE id = 1

// ④ 只列已删除的
db.Unscoped().Where("deleted_at IS NOT NULL").Find(&trash)

软删除的四个代价要知道：① 唯一索引仍占位——软删了 a@x.com 的用户后，注册同名邮箱会撞 Error 1062；解法是把唯一索引改成 (email, deleted_at) 联合，或删除时把邮箱改名（deleted_1_a@x.com），或用 is_deleted 标记列而非 NULL。
② Preload 的关联也会被过滤，作者被软删后文章的 User 字段是零值，展示要留 user_name 冗余字段。
③ AutoMigrate 不会因为删掉 DeletedAt 字段就恢复硬删除——列还在表里，得手工 DROP。
④ 第 3 周说的「删除用户不会级联删文章」在软删除下同样成立，业务上要么在事务里一起软删，要么允许「孤儿文章」并在 UI 显示「已注销用户」。

练习 1：事务 + 故意失败，观察回滚（45 分钟 · 本周最重要的练习）

实现 POST /articles（带 tags: ["go","docker"]），把「建文章 + 挂标签」放进同一事务；再加一个开关 ?fail=1，让事务在第二步之后返回一个错误。

internal/handler/article.gofunc (h *ArticleHandler) Create(c *gin.Context) {
    var req dto.CreateArticleReq
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(400, gin.H{"code": 1004, "message": "参数错误: " + err.Error()})
        return
    }

    var a model.Article
    var relTags []model.Tag
    err := h.db.Transaction(func(tx *gorm.DB) error {
        a = model.Article{Title: req.Title, Content: req.Content, UserID: req.UserID}
        if err := tx.Create(&a).Error; err != nil {
            return err
        }
        for _, name := range req.Tags {
            var tag model.Tag
            if err := tx.Where(map[string]any{"name": name}).FirstOrCreate(&tag).Error; err != nil {
                return fmt.Errorf("创建标签 %s 失败: %w", name, err)
            }
            relTags = append(relTags, tag)
        }
        if err := tx.Model(&a).Association("Tags").Replace(relTags); err != nil {
            return err
        }
        if c.Query("fail") == "1" {
            return errors.New("故意失败：观察回滚")   // ← 触发 ROLLBACK
        }
        return nil
    })
    if err != nil {
        c.JSON(500, gin.H{"code": 5001, "message": "创建失败: " + err.Error()})
        return
    }
    c.JSON(201, gin.H{"code": 0, "message": "success", "data": a})
}

练习 2：连接池参数实验（30 分钟）

把 SetMaxOpenConns(1) 打开，用 for i in $(seq 1 10); do curl -s "localhost:8080/articles?size=20" -o /dev/null -w "%{time_total}\n" &; done; wait 并发打 10 个请求；然后改回 25 再打一次，比较总耗时。再打印 sqlDB.Stats()。

观察池状态st := sqlDB.Stats()
fmt.Printf("open=%d inuse=%d idle=%d 等待中=%d 累计等待时长=%v\n",
    st.OpenConnections, st.InUse, st.Idle, st.WaitCount, st.WaitDuration)

参考答案：maxOpen=1 时 10 个请求变成串行，总耗时 ≈ 单请求 × 10，WaitCount 明显 > 0；maxOpen=25 时总耗时接近单请求。这告诉你：池子大小就是吞吐上限之一，也和第 5 周的并发直接相关。

练习 3：软删除三件套（35 分钟）

实现 ① DELETE /articles/:id（软删）；② GET /articles/:id 删后返回 404；③ GET /admin/articles/trash 用 Unscoped().Where("deleted_at IS NOT NULL") 列出回收站；④ 再补一个永久删除（Unscoped().Delete）。

internal/repository/article.gofunc (r *articleRepo) SoftDelete(id uint) error {
    res := r.db.Delete(&model.Article{}, id)   // 有 DeletedAt → UPDATE deleted_at
    if res.Error != nil { return res.Error }
    if res.RowsAffected == 0 { return ErrArticleNotFound }
    return nil
}

func (r *articleRepo) Trash() ([]model.Article, error) {
    var list []model.Article
    err := r.db.Unscoped().Where("deleted_at IS NOT NULL").Order("deleted_at desc").Find(&list).Error
    return list, err
}

参考答案：软删后 SELECT COUNT(*) FROM articles 行数不变（这就是证据），但 GET /articles 少了一条、total 也少 1；回收站里能看到它，且 deleted_at 有值。

练习 4：设计题（20 分钟，写进笔记）

用户软删后，为什么再用同一邮箱注册会失败？给出三种解法并说明取舍。

参考答案：① 联合唯一索引 uniqueIndex:idx_email_del 同时挂在 Email 和 DeletedAt 上——NULL 在 MySQL 唯一索引里不参与去重，所以软删行不冲突；缺点：两条同邮箱的已软删记录仍会冲突（MySQL 8 可用函数索引绕）。② 删除时改写业务键（email = fmt.Sprintf("%s#%d.deleted", email, id)）——实现最简单，缺点：真实邮箱被污染，导出统计要小心。③ 不用 deleted_at，改用 status 字段（active/disabled）+ 部分索引思路——最贴近业务（「注销」本来就不是「删除」），但要自己在 base 查询里加条件。学习项目选 ①，生产项目多数选 ③。

常见坑（新手 100% 会踩）

坑现象正确姿势
事务闭包里用 db 而不是 tx回滚了，但那一步的数据还在——因为它在事务外闭包内所有写操作只用 tx；把 repository 方法设计成接收 tx 参数
忘了 return err出错却照常 COMMIT，脏数据入库每步 if err != nil { return err }，最后一行 return nil
事务里放外部 HTTP 调用接口一慢连接就被长期占用，池子耗尽把外部调用挪到事务外，事务只包数据库写入
手工 Begin 某条出口没 Rollback连接泄漏，一段时间后全线卡死优先 db.Transaction
每次请求都 gorm.Open连接数暴涨，MySQL 1040 Too many connections进程启动时建一个 *gorm.DB 全生命周期复用
ConnMaxLifetime 比网络层超时还长偶发 invalid connection / bad connection，重试即好设为最小超时的 1/2；重启容器也能复现该现象
以为软删是硬删表越来越大、唯一索引被占、磁盘不降需要真删时定时任务 Unscoped().Delete；或明确这就是「归档」
Unscoped().Find 后按 deleted_at IS NULL 手动过滤忘写回收站数据混进正常列表Unscoped 只在管理员/恢复场景用，且条件写清楚
