1. 发布前测试清单：六大类逐格验证法

别漫无目的地乱点。把功能切成六个格子，每格写清「操作 → 预期」，手动过一遍（浏览器 + curl 各半），这就是小团队最低成本的发布回归。第 8 周新增的 RBAC 与上传务必占格。

类别验证项（操作 → 预期）常用工具
① 接口每个端点正常调用 → 200/201 + code:0；必填缺失 → 400 + code:1004；不存在资源 → 404 + code:1001curl + jq
② 权限未登录写操作 → 401；非作者改文 → 403；普通用户进 admin → 403；管理员全通 → 200curl（三种 token 各备一份）
③ 上传真图 → 成功且重启后仍可访问；伪 PNG → 400；0 字节 → 400；6MB → 400；前端无 Content-Type 手设 → 正常curl -F + 手工改名的文本文件
④ 登录错误密码 → code:1002；access 过期 → 前端静默 refresh 无感；refresh 过期 → 跳登录；退出后 localStorage 清空浏览器 DevTools（把 JWT_SECRET 改了重启可人造过期）
⑤ 分页page 超界 → 空 list 不报错；size=0/负数/999 → 兜底为默认值；总数 total 恒正确curl 拼参数
⑥ 搜索关键词命中 → 只出匹配项；特殊字符 % _ ' → 不报 500；空串 → 返回全量列表浏览器搜索框 + curl

把这张表原样贴进项目 TESTING.md，每格后面加「通过 ✅ / bug 编号」。上线前任何人（包括下个月的你）都能按表回归，这就是「可展示的工程素养」。

2. 把第 4 周的测试债补上（一）：纯逻辑单测

第 4 周学了 testing，但只给老接口写了零星测试。本周新增的两块逻辑恰好都不依赖数据库，是绝佳的可测代码——RBAC 判定抽成纯函数、上传校验只吃 FileHeader。表驱动（第 4 周口径）：

internal/service/rbac_test.gopackage service

import (
    "testing"
    "blog/internal/model"
)

// CanModerate 是 RBAC+所有权判定的纯函数版本（从 handler 里抽出来的）：
// 管理员可处置任何文章；否则只有作者本人可改删自己的。
func CanModerate(role model.Role, uid, articleAuthorID uint) bool {
    if role == model.RoleAdmin { return true }
    return uid == articleAuthorID
}

func TestCanModerate(t *testing.T) {
    cases := []struct {
        name       string
        role       model.Role
        uid, owner uint
        want       bool
    }{
        {"管理员处置他人文章", model.RoleAdmin, 9, 1, true},
        {"作者处置自己文章", model.RoleUser, 1, 1, true},
        {"普通用户碰他人文章", model.RoleUser, 2, 1, false},
        {"零值用户碰零值文章", model.RoleUser, 0, 0, false}, // ← 特意测 uid=0：真实用户 ID 从 1 起，0 必须拒绝
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            if got := CanModerate(tc.role, tc.uid, tc.owner); got != tc.want {
                t.Errorf("CanModerate(%v, %d, %d) = %v, want %v", tc.role, tc.uid, tc.owner, got, tc.want)
            }
        })
    }
}

上面第 4 个用例暴露了一个真实 bug 候选：若 Auth 中间件异常导致 uid=0 透传下来，而某篇文章的 author_id 恰好为 0（脏数据），判定会误放行。修法：CanModerate 开头加 if uid == 0 { return false }——今天的 3 个 bug 名额，这可能就是第一个。

上传校验单测：先把 D2 的 ValidateImage 内核抽成纯函数 Check(ext string, size int64, head []byte) error（ValidateImage 只负责从 FileHeader 里取这三样再调它）——「为了可测而重构」的日常，测试从此不需要构造 FileHeader：

internal/pkg/upload/validate_test.gofunc TestCheck(t *testing.T) {
    // 最小合法 PNG 头：8 字节签名，够 DetectContentType 认出 image/png
    png := append([]byte{0x89, 'P', 'N', 'G', '\r', '\n', 0x1a, '\n'}, make([]byte, 512)...)

    cases := []struct {
        name             string
        ext              string
        size             int64
        head             []byte
        wantErr          bool
    }{
        {"真 PNG", ".png", int64(len(png)), png[:512], false},
        {"0 字节", ".png", 0, nil, true},
        {"文本改名 .png", ".png", 9, []byte("just text"), true},
        {"脚本改名 .png", ".png", 19, []byte("#!/bin/sh\nexit 1"), true},
        {"合法内容坏后缀 .svg", ".svg", int64(len(png)), png[:512], true},
        {"超 5MB", ".png", 6 << 20, png[:512], true},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            err := Check(tc.ext, tc.size, tc.head)
            if (err != nil) != tc.wantErr {
                t.Fatalf("Check(%q, %d) err = %v, wantErr = %v", tc.ext, tc.size, err, tc.wantErr)
            }
        })
    }
}

3. 把第 4 周的测试债补上（二）：httptest 测 admin 403

第 4 周用 httptest 测过「非作者改文 403」，今天加上「非管理员进 admin 403」——这是全站最重要的安全断言，值得一个常驻测试保护：

internal/handler/admin_test.gopackage handler

import (
    "net/http"
    "net/http/httptest"
    "strings"
    "testing"

    "github.com/gin-gonic/gin"
    "blog/internal/middleware"
    "blog/internal/model"
)

func init() { gin.SetMode(gin.TestMode) }

// fakeAuth 模拟 Auth 中间件：塞入指定角色，跳过真 token 解析，专测 RBAC 段
func fakeAuth(role model.Role) gin.HandlerFunc {
    return func(c *gin.Context) {
        c.Set("uid", uint(2))
        c.Set("role", role)
        c.Next()
    }
}

func TestAdminUsers_RequiresAdmin(t *testing.T) {
    setup := func(role model.Role) *gin.Engine {
        r := gin.New()
        g := r.Group("/api/v1/admin", fakeAuth(role), middleware.RequireRole(model.RoleAdmin))
        g.GET("/users", func(c *gin.Context) { c.JSON(200, gin.H{"code": 0}) })
        return r
    }

    // 场景一：普通用户 → 403 且业务码 1003
    w := httptest.NewRecorder()
    req := httptest.NewRequest(http.MethodGet, "/api/v1/admin/users", nil)
    setup(model.RoleUser).ServeHTTP(w, req)
    if w.Code != http.StatusForbidden {
        t.Fatalf("status = %d, want 403", w.Code)
    }
    if !strings.Contains(w.Body.String(), `"code":1003`) {
        t.Errorf("body = %s, want code 1003", w.Body.String())
    }

    // 场景二：管理员 → 200
    w2 := httptest.NewRecorder()
    setup(model.RoleAdmin).ServeHTTP(w2, httptest.NewRequest(http.MethodGet, "/api/v1/admin/users", nil))
    if w2.Code != http.StatusOK {
        t.Fatalf("admin status = %d, want 200", w2.Code)
    }
}

httptest 的思维方式与 JS 里的 supertest 一致：不起端口，直接把请求"灌"进路由函数，拿 Recorder 断响应。快（毫秒级）、稳（不占端口不依赖 DB）、适合 CI。

4. -race 全量跑一遍

第 5 周学的竞态检测今天做全站体检。重点怀疑对象：上传写盘、登录计数、以及任何你用了包级变量/map 的地方。

shell$ go vet ./...                      # 先静态检查，白捡的低级错误
$ go test -race ./... -count=1      # 所有测试带竞态检测跑一遍
ok      blog/internal/service   1.4s
ok      blog/internal/handler   2.1s
$ go build -race -o /tmp/blog-race . # 再编一个带 race 的调试二进制
$ /tmp/blog-race &
$ ab -n 200 -c 20 http://localhost:8080/api/v1/articles   # 或手写并发 curl 脚本轰炸
# 无 WARNING: DATA RACE 输出 = 通过；有则把栈贴进 bug 表

没有 ab 也可以用一段纯 curl 的并发轰炸脚本，顺便当作回归入口：

scripts/hammer.sh#!/usr/bin/env bash
# 用法：TOKEN=xxx ./scripts/hammer.sh  # 对登录/发文/上传三连轰 20 并发
set -euo pipefail
BASE="http://localhost:8080/api/v1"

for i in $(seq 1 20); do
  curl -s -o /dev/null -w "login %{http_code}\n" -X POST "$BASE/auth/login" \
    -H "Content-Type: application/json" \
    -d '{"username":"xiaoming","password":"123456"}' &
  curl -s -o /dev/null -w "create %{http_code}\n" -X POST "$BASE/articles" \
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
    -d "{\"title\":\"并发文章 $i\",\"content\":\"x\"}" &
done
wait
# 预期：全部 200/201，race 二进制日志无 DATA RACE；
# 出现 500 = 有共享状态没上锁，或 DB 连接池配置过小

用 JS 思维类比：这相当于给你的 API 跑一次 Promise.allSettled 并发压测——只不过 Go 这边还要额外开 race detector，才能抓到「单请求永远撞不出来」的共享变量竞态。

5. 边界清单：六连轰炸（各给预期与复现）

攻击项curl 复现预期结果（不是这样就是 bug）
超长标题curl -X POST .../articles -H "Authorization: Bearer $T" -d '{"title":"'$(python3 -c "print('a'*5000)")'","content":"x"}'400 + code:1004（binding:"max=200" 挡住）；绝不是 500（MySQL Data too long 冒到响应里）
空内容文章-d '{"title":"t","content":""}'400 + code:1004；若允许空文则必须显式产品决策
0 字节文件: > empty.png; curl -F "file=@empty.png" .../uploads/avatar400 +「文件为空」；不能落一个 0 字节文件进 uploads
伪 PNG（文本改名）echo hi > fake.png; curl -F "file=@fake.png" ...400 +「真实类型不是图片」（D2 的 DetectContentType 生效）
SQL 注入尝试curl ".../articles?keyword=%27%20OR%201%3D1%20--%20"（即 ' OR 1=1 -- ）当普通字符串处理：返回空列表 200；出现全量数据/报错 500 说明有人手写了字符串拼 SQL
并发同名上传for i in {1..10}; do curl -F "file=@me.png" .../uploads/avatar & done; wait10 个请求全部成功、落 10 个互不相同的文件名（随机名机制）；出现覆盖或 500 即失败

注意每一项的「预期」都写的是用户可理解的行为而不是「不报错」：0 字节文件要拒、注入串要当字符串——这列清单本身就能钓出 3 个以上真 bug。

今日练习

练习 1：清单过格（60 分钟）

按第 1 节六大类清单逐项手动过一遍，任何一格与预期不符就记 BUGLOG 并当场修。今天结束时表格里应该躺着 ≥3 行。

参考答案：常见钓出的鱼——① page=999 返回 500（Offset 负数/乘溢出）；② 搜索输入 % 返回 500（LIKE 通配符没转义，GORM 里用 Like("%"+escape(kw)+"%") 前处理 \ % _）；③ 上传字段名拼错（form 里写成 files）返回 500 而非 400。三个都符合「现象/根因/修复/commit」模板。

练习 2：三个测试文件落地（45 分钟）

把讲义的 RBAC 表驱动测试、httptest admin 403 测试抄进项目并跑通；再给 ListUsers 的分页兜底（size>50 回落 10）补一个 httptest 断言。

参考答案：go test ./... -v 应看到 --- PASS: TestCanModerate/管理员处置他人文章 等子测试逐条打印；若 fakeAuth 版 RequireRole 测试编译失败说 role 类型不匹配，说明 D1 的中间件里存的类型和断言不一致——正好按坑表修正。

练习 3：边界六连 + race（45 分钟）

逐行执行第 5 节表格里的 6 条 curl，把实际返回写成「预期 vs 实际」两列；然后 go test -race ./... 与并发上传轰炸，确保无 DATA RACE。

参考答案：6 条里最容易翻车的是并发同名上传——若你 D2 用了「时间戳+rand」但 rand 源没初始化好出现重名互相覆盖，换 crypto/rand 或 UUID 并记 BUGLOG；race 若命中在 gin 之外的自建 map（比如你缓存了验证码），立刻上 sync.RWMutex。
