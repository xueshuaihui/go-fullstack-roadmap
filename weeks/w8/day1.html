角色与权限 RBAC

第 4 周你写过「仅作者可改删自己的文章」，那是资源级所有权；今天补上另一根支柱——角色级权限（RBAC）：管理员可以看所有用户、可以强制下架任何文章。改动全部落在你第 7 周已经上线的那个 goblog 后端上。先说清一件事：今天要动的 role 列，第 7 周做迁移练习时你已经用 000002_add_role_to_users 建好了（TINYINT），管理员也是 000004_seed_admin 回填的——所以今天的代码是把地基接线：Go 侧给字段、JWT 侧带角色、路由侧加一道鉴权中间件。

今日目标

↑ 这四条是「学习目标」，学的过程中随时回来勾；页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

课前须知：RBAC 只有三句话

1. Role-Based Access Control：不直接判断「这个人能不能干这件事」，而是判断「这个人属于哪个角色、这个角色有没有这项权限」。你的项目只有两级——user 与 admin，所以一个 int 字段就够了，不需要引入角色表、权限表三件套。

2. 前端藏按钮不是权限控制。第 3 天你会在 React 里隐藏管理员入口，但那只是体验优化；真正的门永远在后端中间件。任何人手敲 curl 或 URL，挡他的必须是 Gin。

3. 权限判定发生在两处：认证中间件（第 4 周的 Auth）回答「你是谁」，鉴权中间件（今天的 RequireRole）回答「你配吗」。二者串联，职责分离。

知识讲义

1. role 字段设计：int8 + iota，第 1 周枚举知识闭环

第 1 周 Day 1 你用 iota 写过 RoleGuest/RoleUser/RoleAdmin 的练习题——今天它进生产代码。选型理由：字符串 "admin" 容易打错、布尔 is_admin 无法扩展到第三种角色；小整数常量 + 自定义类型是 Go 项目的通行做法。

但注意顺序：数据库里 role TINYINT 已经存在（第 7 周 000002），所以 Go 侧的类型必须如实描述那一列——TINYINT（未写 UNSIGNED）就是有符号的 1 字节，对应 int8。gorm tag 里的 type:tinyint;not null;default:0;index 四个片段和 000002 建的列一模一样，读起来才不会对不上号。

internal/model/user.go（整份替换：字段与全站基准一致）package model

import gorm.io/gorm

// Role 用户角色。底层 int8 正好对上迁移 000002 的 TINYINT 列。
type Role int8

const (
    RoleUser  Role = iota // 0 普通用户（零值即最普通角色，这是刻意设计）
    RoleAdmin              // 1 管理员
)

// 让角色能翻译成人类语言，日志和接口返回都用它
func (r Role) Name() string {
    switch r {
    case RoleAdmin:
        return "admin"
    default:
        return "user"
    }
}

type User struct {
    gorm.Model // ID uint / CreatedAt / UpdatedAt / DeletedAt（软删除）
    Username string `gorm:"type:varchar(32);uniqueIndex;not null" json:"username"`
    Nickname string `gorm:"type:varchar(32)" json:"nickname"`
    Email    string `gorm:"type:varchar(128);uniqueIndex" json:"email"`
    Password string `gorm:"type:varchar(72);not null" json:"-"`   // json:"-" 永不输出到响应
    Role     Role   `gorm:"column:role;type:tinyint;not null;default:0;index" json:"role"` // ← 列来自 W7 的 000002
    Avatar   string `gorm:"type:varchar(255)" json:"avatar"`                  // ← 列还没生：D2 的 000006 建它
    Articles []Article `gorm:"foreignKey:UserID" json:"articles,omitempty"`
}

今天唯一会让接口 500 的地方就是 Avatar 这一行。第 7 周生产已关掉 AUTO_MIGRATE，改 model 不会动表结构：一旦某个 SELECT 带上 avatar 列，MySQL 就回 Unknown column 'avatar' in 'field list'。两条规矩：① 今天要么先不写这行、要么立刻按 D2 的 000006_add_avatar_to_users 建列；② 今后「model 加字段」和「对应的 up/down 迁移」必须同一个 PR 合入——这正是 D5 发布六步把 migrate up 排在 up -d --build 之前的原因。

零值即普通用户是安全设计：任何遗漏（老数据、忘记赋值的注册流程）落到的默认角色都是权限最小的 user，而不是 admin。Go 的零值哲学在这里刚好和最小权限原则对上了。

3. role 放不放 JWT Claims？先想清楚这个 trade-off

鉴权中间件已经解析了 token，如果 role 就在 Claims 里，RequireRole 一行搞定不用查库；但 JWT 签发即不可变——你在数据库把一个用户提为 admin，他手里的旧 token 依然写着 role:0，直到过期。反过来，每次查库则即时生效：

方案优点缺点
A. role 写进 Claims鉴权零额外查询；中间件简单改角色/封号要等 access token 过期（你设的 15 分钟，影响可接受）；refresh token 有效期内若续签会带出新角色，注意签发时机
B. 每个请求按 uid 查库取 role改库即时生效；封号立刻拦每个请求多一次 DB 查询；高并发时数据库压力大
C.（推荐）Claims 带 role + admin 接口再查库复核普通接口享受零查询；高危接口以库为准代码多一处，但只加在 /admin 组，代价极小
internal/pkg/jwtutil/jwt.go（第 4 周版 + 今天新增的 Role）// Claims 保留第 4 周的 Type（access / refresh 靠它区分），只加一个 Role
type Claims struct {
    UserID uint   `json:"uid"`
    Role   int8   `json:"role"`      // ← 今天加：int8 与 model.Role 底层类型一致
    Type   string `json:"typ"`       // 第 4 周就有：Parse 强制比对 wantType
    jwt.RegisteredClaims        // exp / iat / sub 这些标准字段
}

// 两个签名函数各多一个 role 参数（jwtutil 不认识 model，所以传 int8 而不是 model.Role）
func NewAccessToken(accessSecret string, userID uint, role int8) (string, error) { ... }
func NewRefreshToken(refreshSecret string, userID uint, role int8) (string, error) { ... }
// 内部就是把 Role 填进 Claims：Sign(accessSecret, Claims{UserID: userID, Role: role, Type: "access", ...})

// 三处调用点各改一行（都在 internal/handler/auth.go，diff 形式）：
// ① Login 成功后签发双 token
- access, err1 := jwtutil.NewAccessToken(h.accessSecret, user.ID)
- refresh, err2 := jwtutil.NewRefreshToken(h.refreshSecret, user.ID)
+ access, err1 := jwtutil.NewAccessToken(h.accessSecret, user.ID, int8(user.Role))
+ refresh, err2 := jwtutil.NewRefreshToken(h.refreshSecret, user.ID, int8(user.Role))

// ② Refresh 换发：把旧 Claims 里的 role 原样带过去
- access, _ := jwtutil.NewAccessToken(h.accessSecret, claims.UserID)
+ access, _ := jwtutil.NewAccessToken(h.accessSecret, claims.UserID, claims.Role)

// 返回体字段不变（第 4 周基准）：data:{user, access_token, refresh_token}，前端 W6 已按蛇形适配

refresh 换发时要不要查库取新 role？上面这行 claims.Role 是「快照续期」：提权后要等 access 与 refresh 都换一轮才生效。要立刻生效就把换发处改成按 claims.UserID 查库拿当前 role（方案 C 的落点）——两者都行，但必须在 README 里写清你选了哪个，不然半年后的你就是 bug 现场里的受害者。

对比前端经验：这就像把 role 存进 localStorage 的 user 对象——方便，但「本地快照」和「服务端真值」会漂移。方案 C 的本质就是：展示用快照，放行查真值。

4. 同步修改 Auth 中间件：role 从 Claims 落到 context

Claims 多了一个字段，中间件不同步改就是白加：解析出来的 role 要用 model.Role 塞进 context，下一节的 RequireRole 才有东西可断言。整份覆盖第 4 周那个版本（密钥由 main.go 以参数传进来，不在包里读全局配置）：

internal/middleware/auth.go（整份替换第 4 周版）package middleware

import (
    net/http
    strings

    "github.com/gin-gonic/gin"

    "goblog/internal/model"
    "goblog/internal/pkg/jwtutil"
)

// Auth 校验 Authorization: Bearer <access>，通过后把 userID 与 role 塞进 context。
// 参数是 access 密钥（cfg.JWT_SECRET）：refresh 密钥只在 /auth/refresh 里用，别传错。
// 注意第二个返回值是 int8 —— model.Role 只是它的别名，jwtutil 里不 import model。
func Auth(accessSecret string) gin.HandlerFunc {
    return func(c *gin.Context) {
        header := c.GetHeader("Authorization")
        if !strings.HasPrefix(header, "Bearer ") {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{
                "code": 1005, "message": "未认证：缺少 Bearer token", "data": nil,
            })
            return
        }
        claims, err := jwtutil.Parse(accessSecret, strings.TrimPrefix(header, "Bearer "), "access")
        if err != nil {   // 签名错、过期、拿 refresh 当 access 用，全落这里
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{
                "code": 1005, "message": "token 无效或已过期", "data": nil,
            })
            return
        }
        c.Set("userID", claims.UserID)         // uint：handler 里用 c.GetUint("userID") 取
        c.Set("role", model.Role(claims.Role)) // ← 关键：塞 model.Role，别塞 int8
        c.Next()
    }
}

两个键名全站统一："userID"（读用 c.GetUint("userID")）与 "role"（读用 c.Get("role").(model.Role)）。第 4 周讲义里的裸键 "uid" 是 JWT 里的 JSON 字段名，不是 context 键——两者混用是本周最隐蔽的一类 bug（GetUint 取不到就是 0，等于「谁都没登录」，偏偏 0 还是合法零值）。

5. RequireRole 中间件：完整可粘贴实现

约定：上面的 Auth 已经把 userID 与 role 塞进 c.Set。RequireRole 站在它后面，只做一件事——比对角色等级，不够就 403 + 业务码 1003（第 2 周定死的双层约定）。

internal/middleware/rbac.gopackage middleware

import (
    net/http

    "github.com/gin-gonic/gin"

    "goblog/internal/model"
)

// RequireRole 返回一个鉴权中间件：角色等级 < min 的一律 403。
// 用「等级」而不是「等于」，将来加 RoleSuperAdmin 时不用改这里。
func RequireRole(min model.Role) gin.HandlerFunc {
    return func(c *gin.Context) {
        raw, exists := c.Get("role") // Auth 中间件写入
        if !exists {                  // 忘了挂 Auth？属于部署事故，按未认证处理
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{
                "code": 1005, "message": "未认证", "data": nil,
            })
            return
        }
        role, ok := raw.(model.Role)
        if !ok || role < min {
            c.AbortWithStatusJSON(http.StatusForbidden, gin.H{
                "code": 1003, "message": "权限不足", "data": nil,
            })
            return
        }
        c.Next()
    }
}

注意 raw.(model.Role) 是带 ok 的类型断言。若 Auth 当年塞的是 int8，断言失败 ok=false 会直接 403——这是好事：类型对不上宁可拒绝，绝不能让 role 落到零值再被「碰巧放行」。

        mine.DELETE("/articles/:id", articleHandler.Delete)
    }

    admin := api.Group("/admin",                              // ← 今天新增的管理员组

    {
        admin.GET("/users", adminHandler.ListUsers)              // 用户列表（分页）
        admin.DELETE("/articles/:id", adminHandler.ForceDelete) // 强制下架任意文章
        admin.GET("/stats", adminHandler.Stats)                 // 简单统计
    }
}

middleware.Auth 的签名从第 4 周起就是 Auth(accessSecret string)——它要参数，写成 middleware.Auth() 编译不过。另外两个中间件的顺序就是执行顺序：把 RequireRole 写在前面的话，它从 c.Get("role") 永远取不到值，所有请求都在 !exists 分支被 401 挡掉，你只会以为是「权限没配好」。顺序永远 Auth → RequireRole →（可选 Audit）→ handler。

上面用 api.Group("/admin", 中间件...) 的写法把守卫直接压在组上——组内以后新增任何端点都自动受保护，比逐条路由挂中间件可靠（挂在路由上迟早漏一条）。cfg 来自 W4 的 internal/config，读的就是 §env 那套键：这里用到 JWT_SECRET（access）与 JWT_REFRESH_SECRET（refresh）。

internal/handler/admin.go（完整可粘贴）package handler

import (
    strconv

    "github.com/gin-gonic/gin"
    "gorm.io/gorm"

    "goblog/internal/model"
    "goblog/pkg/response"
)

// AdminHandler 三个管理端点共用一个 handler。本课从简：直接持 *gorm.DB。
// 生产写法是把 Count / 分页 Find 下沉到 repository 接口（第 2、3 周那条线），
// 让 handler 不认识 *gorm.DB——接口形状不变，将来换缓存、拆服务都不用动这里。
type AdminHandler struct {
    db *gorm.DB
}

func NewAdminHandler(db *gorm.DB) *AdminHandler {
    return &AdminHandler{db: db}
}

// ListUsers GET /api/v1/admin/users?page=1&size=10
// 必须分页！管理员接口一旦裸奔 SELECT 全表，就是给自己留了个拖库后门。
func (h *AdminHandler) ListUsers(c *gin.Context) {
    page, _ := strconv.Atoi(c.DefaultQuery("page", "1"))
    size, _ := strconv.Atoi(c.DefaultQuery("size", "10"))
    if page < 1 { page = 1 }
    if size < 1 || size > 50 { size = 10 }   // 兜底 + 上限，防一次拖全表

    var total int64
    if err := h.db.Model(&model.User{}).Count(&total).Error; err != nil {
        response.Fail(c, 500, 5000, "查询失败")
        return
    }
    var users []model.User
    if err := h.db.Omit("Password").Order("role DESC, id ASC").
        Offset((page - 1) * size).Limit(size).Find(&users).Error; err != nil {
        response.Fail(c, 500, 5000, "查询失败")
        return
    }
    response.OK(c, gin.H{"list": users, "total": total, "page": page, "size": size})
}

// ForceDelete DELETE /api/v1/admin/articles/:id —— 不校验所有权，admin 直接下架
func (h *AdminHandler) ForceDelete(c *gin.Context) {
    id, err := strconv.ParseUint(c.Param("id"), 10, 32)
    if err != nil || id == 0 {
        response.Fail(c, 400, 1004, "id 必须是正整数")
        return
    }
    if err := h.db.Delete(&model.Article{}, uint(id)).Error; err != nil {
        response.Fail(c, 500, 5000, "删除失败")
        return
    }
    response.OK(c, gin.H{"deleted": id})
}

// Stats GET /api/v1/admin/stats —— 三条 Count 足够作品集使用
// （model.Comment 是 D3 才建的结构体，今天先把这一行注释掉，D3 回来放开）
func (h *AdminHandler) Stats(c *gin.Context) {
    var users, articles, comments int64
    if err := h.db.Model(&model.User{}).Count(&users).Error; err != nil {
        response.Fail(c, 500, 5000, "统计失败")
        return
    }
    if err := h.db.Model(&model.Article{}).Count(&articles).Error; err != nil {
        response.Fail(c, 500, 5000, "统计失败")
        return
    }
    h.db.Model(&model.Comment{}).Count(&comments) // D3：评论表建好前这行先注释
    response.OK(c, gin.H{"users": users, "articles": articles, "comments": comments})
}

三个接口都走 response 包（第 2 周定的统一 Body），业务码按码表来：查询/删除这种服务器侧失败是 500 + 5000，参数不合法是 400 + 1004，权限不够是 403 + 1003，没登录是 401 + 1005。ListUsers 里那句 Omit("Password") 也值得说：Password 的 tag 是 json:"-"，永远不会被序列化出去，但 Omit 连查都不查——把「不泄露哈希」做成两层防线。

软删除（第 3 周）在这里正好发光：Delete 只是给 deleted_at 打时间戳，误下架还能进数据库把 NULL 改回来——对「强制下架」这种高危操作，可恢复是刚需。

7. 审计日志：一句话方案

管理员的每一次删改都该留痕：最简单做法是给 /admin 组再加一个中间件，在 c.Next() 之后把 c.GetUint("userID") + 方法 + 路径 + 状态码 用 slog 打一行结构化日志（够作品集用）；进阶再落一张 operation_logs 表。顺序别搞反——Auth → RequireRole → Audit → handler，被 403 拒掉的请求也值得记录（可能有人在试探）。

练习 3：亲自撞一次「JWT 快照不一致」（20 分钟）

用练习 2 的过程写一段笔记：提权后拿旧 token 访问 → 仍然 403（旧 Claims 里 role=0）；等 15 分钟过期或重新登录 → 200。这正是讲义第 3 节表格「方案 A 的缺点」的实景体验；若走方案 C（admin 接口查库复核），403 会立刻变 200——两种行为你能各演示一遍，这个知识点就真正是你的了。

常见坑

坑现象正确姿势
admin 列表接口忘分页用户多了以后 GET /admin/users 一次拖回全表，内存和带宽爆炸，等于自带拖库入口所有列表接口一律 page/size + size 上限（如 50）
role 写进 JWT 后又即时改库提权/降权后旧 token 仍带旧角色，状态不一致让人怀疑人生接受 15 分钟延迟（方案 A）或高危接口查库复核（方案 C），二选一并写进 README
000004 的 seed 没跑（库里没有 role=1）没有 admin，功能「上线即不可用」，还以为是中间件写错先 migrate version 确认已到 4 且 dirty: false，再用验收 SQL 查出一个 role=1；生产要提权就新开一对迁移，不许手敲 UPDATE
RequireRole 挂在组外面只保护了 /users，后来加的 /articles/:id 忘了挂，admin 组漏权限权限挂在 Group 上：admin.Use(...) 一夫当关
Auth 塞 role 用 int8、中间件断言 model.Role类型断言永远失败，管理员也 403两处类型统一用 model.Role；调试时先打印 c.Get("role") 的真实类型
