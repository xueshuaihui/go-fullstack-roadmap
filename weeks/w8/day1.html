角色与权限 RBAC

第 4 周你写过「仅作者可改删自己的文章」，那是资源级所有权；今天补上另一根支柱——角色级权限（RBAC）：管理员可以看所有用户、可以强制下架任何文章。全部改动落在你已经上线的第 6/7 周博客后端上：加一列、加一个中间件、加一个路由组。

今日目标

↑ 这四条是「学习目标」，学的过程中随时回来勾；页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

课前须知：RBAC 只有三句话

1. Role-Based Access Control：不直接判断「这个人能不能干这件事」，而是判断「这个人属于哪个角色、这个角色有没有这项权限」。你的项目只有两级——user 与 admin，所以一个 int 字段就够了，不需要引入角色表、权限表三件套。

2. 前端藏按钮不是权限控制。第 3 天你会在 React 里隐藏管理员入口，但那只是体验优化；真正的门永远在后端中间件。任何人手敲 curl 或 URL，挡他的必须是 Gin。

3. 权限判定发生在两处：认证中间件（第 4 周的 Auth）回答「你是谁」，鉴权中间件（今天的 RequireRole）回答「你配吗」。二者串联，职责分离。

知识讲义

1. role 字段设计：int + iota，第 1 周枚举知识闭环

第 1 周 Day 1 你用 iota 写过 RoleGuest/RoleUser/RoleAdmin 的练习题——今天它进生产代码。选型理由：字符串 "admin" 容易打错且难加索引意义，布尔 is_admin 无法扩展到第三种角色；int 常量 + 小枚举是 Go 项目的通行做法。

internal/model/user.gopackage model

import gorm.io/gorm

// Role 用户角色。用 int8 而不是 string：占空间小、可比较、可加索引。
type Role int8

const (
    RoleUser  Role = iota // 0 普通用户（零值即最普通角色，这是刻意设计）
    RoleAdmin              // 1 管理员
)

// 让角色能翻译成人类语言，日志和接口返回都用它
func (r Role) Name() string {
    switch r {
    case RoleAdmin:
        return "admin"
    default:
        return "user"
    }
}

type User struct {
    gorm.Model
    Username string `gorm:"size:32;uniqueIndex;notNull" json:"username"`
    Password string `gorm:"size:60;notNull" json:"-"`
    Avatar   string `gorm:"size:255" json:"avatar"`
    Role     Role   `gorm:"column:role;type:tinyint;notNull;default:0;index" json:"role"`
}

零值即普通用户是安全设计：任何遗漏（老数据、忘记赋值的注册流程）落到的默认角色都是权限最小的 user，而不是 admin。Go 的零值哲学在这里刚好和最小权限原则对上了。

2. 迁移加列 + 回填：复用第 7 周 golang-migrate

生产库已经跑着第 7 周的 golang-migrate，不要指望 AutoMigrate 在生产偷偷改表——写迁移文件，一上一下成对出现：

migrations/000003_add_user_role.up.sql-- 1) 加列：默认 0，存量用户自动变成普通用户，不会炸
ALTER TABLE users
  ADD COLUMN role TINYINT NOT NULL DEFAULT 0 COMMENT '0=user 1=admin';

-- 2) 建索引：admin 列表页会按角色筛选
CREATE INDEX idx_users_role ON users(role);

-- 3) 回填：把管理员账号提为 role=1（先用真实账号登录注册好，再执行）
UPDATE users SET role = 1 WHERE username = 'admin';
migrations/000003_add_user_role.down.sqlDROP INDEX idx_users_role ON users;
ALTER TABLE users DROP COLUMN role;
shell$ migrate -path migrations -database "mysql://$DSN" up 1   # 只前进一个版本
$ mysql -u root -p blog -e "SELECT id, username, role FROM users ORDER BY role DESC LIMIT 5;"
+----+----------+------+
| id | username | role |
+----+----------+------+
|  3 | admin    |    1 |
|  1 | xiaoming |    0 |
+----+----------+------+

本地开发若用 AutoMigrate，GORM 也会给 users 补上 role 列，但 回填那条 UPDATE 它永远不会替你写。所以流程固定：改 model → 写迁移文件 → 测试库 migrate up 验证 → 生产执行。

3. role 放不放 JWT Claims？先想清楚这个 trade-off

鉴权中间件已经解析了 token，如果 role 就在 Claims 里，RequireRole 一行搞定不用查库；但 JWT 签发即不可变——你在数据库把一个用户提为 admin，他手里的旧 token 依然写着 role:0，直到过期。反过来，每次查库则即时生效：

方案优点缺点
A. role 写进 Claims鉴权零额外查询；中间件简单改角色/封号要等 access token 过期（你设的 15 分钟，影响可接受）；refresh token 有效期内若续签会带出新角色，注意签发时机
B. 每个请求按 uid 查库取 role改库即时生效；封号立刻拦每个请求多一次 DB 查询；高并发时数据库压力大
C.（推荐）Claims 带 role + admin 接口再查库复核普通接口享受零查询；高危接口以库为准代码多一处，但只加在 /admin 组，代价极小
internal/pkg/jwtutil/jwt.go// Claims 在原有 UserID 基础上加 Role 字段（方案 A/C 的地基）
type Claims struct {
    UserID uint `json:"uid"`
    Role   int8 `json:"role"`
    jwt.RegisteredClaims
}

// 登录成功签发时（service/auth.go 里改一行）：
claims := &Claims{
    UserID: u.ID,
    Role:   int8(u.Role),   // ← 新增：把角色装进 token
    RegisteredClaims: jwt.RegisteredClaims{
        Subject:  u.Username,
        ExpiresAt: jwt.NewNumericDate(time.Now().Add(15 * time.Minute)),
    },
}

对比前端经验：这就像把 role 存进 localStorage 的 user 对象——方便，但「本地快照」和「服务端真值」会漂移。方案 C 的本质就是：展示用快照，放行查真值。

4. RequireRole 中间件：完整可粘贴实现

约定：第 4 周的 Auth 中间件解析 token 后已把 uid 与 role 塞进 c.Set。RequireRole 站在它后面，只做一件事——比对角色等级，不够就 403 + 业务码 1003（第 2 周定死的双层约定）。

internal/middleware/rbac.gopackage middleware

import (
    net/http
    "github.com/gin-gonic/gin"
    "blog/internal/model"
)

// RequireRole 返回一个鉴权中间件：角色等级 < min 的一律 403。
// 用「等级」而不是「等于」，将来加 RoleSuperAdmin 时不用改这里。
func RequireRole(min model.Role) gin.HandlerFunc {
    return func(c *gin.Context) {
        raw, exists := c.Get("role") // Auth 中间件写入
        if !exists {                  // 忘了挂 Auth？属于部署事故，按未认证处理
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{
                "code": 1005, "message": "未认证", "data": nil,
            })
            return
        }
        role, ok := raw.(model.Role)
        if !ok || role < min {
            c.AbortWithStatusJSON(http.StatusForbidden, gin.H{
                "code": 1003, "message": "权限不足", "data": nil,
            })
            return
        }
        c.Next()
    }
}

注意 raw.(model.Role) 是带 ok 的类型断言。若 Auth 当年塞的是 int8，断言失败 ok=false 会直接 403——这是好事：类型对不上宁可拒绝，绝不能让 role 落到零值再被「碰巧放行」。

5. /api/v1/admin 路由组：三个管理接口

cmd/server/main.go（路由部分）api := r.Group("/api/v1")
{
    auth := api.Group("/auth")      // 原有注册/登录/refresh，不动
    {
        auth.POST("/register", authHandler.Register)
        auth.POST("/login", authHandler.Login)
        auth.POST("/refresh", authHandler.Refresh)
    }

    admin := api.Group("/admin")     // ← 今天新增的管理员组
    admin.Use(middleware.Auth(), middleware.RequireRole(model.RoleAdmin))
    {
        admin.GET("/users", userHandler.ListUsers)              // 用户列表（分页）
        admin.DELETE("/articles/:id", articleHandler.ForceDelete) // 强制下架任意文章
        admin.GET("/stats", statsHandler.Overview)               // 简单统计
    }
}
internal/handler/admin.gopackage handler

import (
    "strconv"
    "github.com/gin-gonic/gin"
    "blog/internal/model"
    "blog/internal/pkg/response"
)

// ListUsers GET /api/v1/admin/users?page=1&size=10
// 必须分页！管理员接口一旦裸奔 SELECT 全表，就是给自己留了个拖库后门。
func (h *UserHandler) ListUsers(c *gin.Context) {
    page, _ := strconv.Atoi(c.DefaultQuery("page", "1"))
    size, _ := strconv.Atoi(c.DefaultQuery("size", "10"))
    if page < 1 { page = 1 }
    if size < 1 || size > 50 { size = 10 }

    var total int64
    h.db.Model(&model.User{}).Count(&total)
    var users []model.User
    if err := h.db.Order("role DESC, id ASC").
        Offset((page - 1) * size).Limit(size).Find(&users).Error; err != nil {
        response.Fail(c, 500, 1000, "查询失败")
        return
    }
    response.OK(c, gin.H{"list": users, "total": total, "page": page})
}

// ForceDelete DELETE /api/v1/admin/articles/:id —— 不校验所有权，admin 直接下架
func (h *ArticleHandler) ForceDelete(c *gin.Context) {
    id := c.Param("id")
    if err := h.db.Delete(&model.Article{}, id).Error; err != nil {
        response.Fail(c, 500, 1000, "删除失败")
        return
    }
    response.OK(c, gin.H{"deleted": id})
}

// Overview GET /api/v1/admin/stats —— 三条 Count 足够作品集使用
func (h *StatsHandler) Overview(c *gin.Context) {
    var users, articles, comments int64
    h.db.Model(&model.User{}).Count(&users)
    h.db.Model(&model.Article{}).Count(&articles)
    h.db.Model(&model.Comment{}).Count(&comments)
    response.OK(c, gin.H{"users": users, "articles": articles, "comments": comments})
}

软删除（第 3 周）在这里正好发光：Delete 只是给 deleted_at 打时间戳，误下架还能进数据库把 NULL 改回来——对「强制下架」这种高危操作，可恢复是刚需。

6. 审计日志：一句话方案

管理员的每一次删改都该留痕：最简单做法是给 /admin 组再加一个中间件，在 c.Next() 之后把 操作者uid + 方法 + 路径 + 状态码 用 slog 打一行结构化日志（够作品集用）；进阶再落一张 operation_logs 表。顺序别搞反——Auth → RequireRole → Audit → handler，被 403 拒掉的请求也值得记录（可能有人在试探）。

练习 1：迁移上库（30 分钟）

照讲义写好 000003_add_user_role 上下两个迁移文件，注册一个名为 admin 的账号，执行 migrate up 并用 SQL 确认 role 值。

分别拿普通用户 token 与 admin token 调 /api/v1/admin/users，验证双层约定：HTTP 状态码 + body 里的 code。

练习 3：亲自撞一次「JWT 快照不一致」（20 分钟）

用练习 2 的过程写一段笔记：提权后拿旧 token 访问 → 仍然 403（旧 Claims 里 role=0）；等 15 分钟过期或重新登录 → 200。这正是讲义第 3 节表格「方案 A 的缺点」的实景体验；若走方案 C（admin 接口查库复核），403 会立刻变 200——两种行为你能各演示一遍，这个知识点就真正是你的了。

练习 4：强制下架 + 统计接口（30 分钟）

用 admin token 删除别人的文章：curl -X DELETE -H "Authorization: Bearer $ADMIN" localhost:8080/api/v1/admin/articles/2，预期 code:0；再验证普通列表接口已查不到该文章（软删除生效）。然后调 /admin/stats，数字应比删除前少 1。

常见坑

坑现象正确姿势
admin 列表接口忘分页用户多了以后 GET /admin/users 一次拖回全表，内存和带宽爆炸，等于自带拖库入口所有列表接口一律 page/size + size 上限（如 50）
role 写进 JWT 后又即时改库提权/降权后旧 token 仍带旧角色，状态不一致让人怀疑人生接受 15 分钟延迟（方案 A）或高危接口查库复核（方案 C），二选一并写进 README
迁移只加列没回填没有 admin，功能「上线即不可用」，还以为是中间件写错up 脚本里带回填 UPDATE；验收 SQL 必须能查出一个 role=1
RequireRole 挂在组外面只保护了 /users，后来加的 /articles/:id 忘了挂，admin 组漏权限权限挂在 Group 上：admin.Use(...) 一夫当关
Auth 塞 role 用 int8、中间件断言 model.Role类型断言永远失败，管理员也 403两处类型统一用 model.Role；调试时先打印 c.Get("role") 的真实类型

今日名词卡

术语一句话解释
RBAC基于角色的访问控制：权限跟着角色走，角色跟着用户走
认证 vs 鉴权Authentication 回答「你是谁」（Auth 中间件），Authorization 回答「你能不能」（RequireRole）
回填（backfill）给新列的存量数据补值，如把 admin 账号的 role 手动置 1
Claims 快照JWT 签发瞬间固化的数据，签发后改库不会影响已签出的 token
审计日志记录「谁在什么时候用管理员身份干了什么」，用于追责与回放
