知识讲义

1. 更新发布流程：migrate 先跑，健康检查再切流

这周改了表结构（role 列、comments 表）又加了上传。新代码依赖新列，老库没有列——所以顺序不能错：先备份、先迁移、再起新版本、健康检查过了才算完。把第 7 周的「一把梭 up -d」升级成下面这条流水线（服务器上执行，或写进 deploy.sh）：

shell（发布六步）$ cd /opt/blog && git pull                     # 1) 拉新代码
$ docker compose ps -q mysql > /dev/null \
  && mysqldump -h127.0.0.1 -uroot -p"$DB_PASS" blog > backup_$(date +%F).sql
                                                # 2) 迁移前备份，30 秒保命
$ docker compose run --rm migrate up            # 3) 迁移先跑（role 列 + comments 表）
$ docker compose build backend frontend         # 4) 构建新镜像
$ docker compose up -d backend                  # 5) 只重启 backend，老容器还在服务
$ for i in $(seq 1 10); do
    curl -fsS http://127.0.0.1:8080/healthz && break || sleep 2
  done                                          # 6) 健康检查通过才收工；
                                                #    多实例架构时这一步通过后才把流量切新机

compose 里给 backend 补上健康检查（第 7 周只给 MySQL 配了，应用自己也要有）：

docker-compose.yml（backend 节选）  backend:
    build: ./backend
    volumes:
      - ./uploads:/app/uploads
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/healthz"]
      interval: 15s
      timeout: 3s
      retries: 3
      start_period: 5s

配套的 Go 端点三行搞定（查一次 DB 才算真健康）：

cmd/server/main.gor.GET("/healthz", func(c *gin.Context) {
    sqlDB, err := db.DB()
    if err != nil || sqlDB.Ping() != nil {
        c.JSON(http.StatusServiceUnavailable, gin.H{"status": "db down"})
        return
    }
    c.JSON(http.StatusOK, gin.H{"status": "ok", "version": "w8"})
})

本周加了 /uploads 与 /swagger 两个新入口，Nginx 的 server 块最终形态一次配齐（第 4 节结尾会用到）：

nginx/conf.d/blog.conf（最终版）server {
    listen 80;
    server_name blog.yourname.dev;

    location /api/ {
        proxy_pass http://backend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        client_max_body_size 8m;      # ← 上传必经：默认 1m 会把 5MB 图挡在 Nginx 层
    }

    location /uploads/ {
        alias /data/blog/uploads/;    # 与 backend 挂的宿主目录一致
        expires 30d;
    }

    location /swagger/ {
        proxy_pass http://backend:8080;   # 上线记得加 Basic Auth 或仅内网
    }

    location / {
        root /usr/share/nginx/html;       # React 构建产物
        try_files $uri $uri/ /index.html; # SPA 路由回退，第 7 周已配
    }
}

回滚预案也要一句话写死：新版本 500 飙升时 git checkout 上一tag && docker compose up -d --build backend；但数据库不自动回滚（down 迁移会丢 comments 数据），所以第 2 步的备份不是仪式，是救命的。

2. README 完整模板：直接改名套用

README 的 KPI 只有一个：让一个没见过的程序员在 10 分钟内把项目跑起来，并在 60 秒内看懂它是什么。以下模板把本周全部内容装进去了：

README.md# GoBlog · Go 全栈博客（Gin + GORM + React + Docker）

面向学习者的完整全栈博客：JWT 双 token 认证、RBAC 管理员、图片上传、评论、分页搜索，
一键 Docker 部署，已通过 HTTPS 公网访问：**https://blog.yourname.dev**

## 功能清单
- 认证：注册 / 登录 / access(15m)+refresh(7d) 双 token 静默续期
- 文章：CRUD、分页、标题搜索、封面图上传；作者可管理自己的文章
- 评论：登录可评；作者本人或管理员可删
- 权限：users.role（0 用户 / 1 管理员）；/api/v1/admin 组 RequireRole 保护；
  管理员可查用户列表、强制下架任意文章、查看统计
- 上传：扩展名白名单 + 魔数 MIME 嗅探 + 5MB 限制；随机文件名防覆盖防穿越
- 部署：多阶段 Dockerfile、Compose 编排 backend/nginx/mysql/migrate、数据卷持久化

3. API 文档两种做法（一）：手写 markdown 表

全量 20 多个端点，先用最笨但最清楚的方式留一份速查表 docs/api.md——它同时是给面试官看的「接口设计能力」证明：

docs/api.md（节选）统一响应：`{ "code": 0, "message": "success", "data": {} }`
错误码：1001 用户不存在 · 1002 密码错误 · 1003 无权限 · 1004 参数错误 · 1005 token 无效/过期
鉴权：除标注「公开」外均需 `Authorization: Bearer <access>`

| 方法 | 路径 | 鉴权 | 说明 | 关键参数 |
|---|---|---|---|---|
| POST | /api/v1/auth/register | 公开 | 注册 | username, password |
| POST | /api/v1/auth/login | 公开 | 登录，返回双 token + user(含 role) | username, password |
| POST | /api/v1/auth/refresh | refreshToken | 换发新 access | refreshToken |
| GET | /api/v1/articles | 公开 | 分页列表 | page, size, keyword |
| POST | /api/v1/articles | 登录 | 发文（≤200 字标题，含 cover_image） | title, content, cover_image |
| PUT | /api/v1/articles/:id | 作者 | 编辑 | title, content |
| DELETE | /api/v1/articles/:id | 作者 | 删除（软删） | — |
| POST | /api/v1/uploads/avatar | 登录 | 头像（multipart 字段 file） | file |
| POST | /api/v1/uploads/cover | 登录 | 文章封面 | file, article_id? |
| GET | /api/v1/articles/:id/comments | 公开 | 评论列表（带作者） | — |
| POST | /api/v1/articles/:id/comments | 登录 | 发评论 | content ≤500 字 |
| DELETE | /api/v1/comments/:id | 作者或管理员 | 删评论 | — |
| GET | /api/v1/admin/users | 管理员 | 用户分页列表 | page, size(≤50) |
| DELETE | /api/v1/admin/articles/:id | 管理员 | 强制下架 | — |
| GET | /api/v1/admin/stats | 管理员 | 用户/文章/评论计数 | — |

4. API 文档两种做法（二）：swaggo 注解生成 Swagger

手写表清楚但不能交互。用 swaggo/swag：在 handler 上写注释注解，命令行扫代码生成 OpenAPI 文档，再挂一个 /swagger 路由得到可以「Try it out」的网页。五分钟上手：

shell$ go install github.com/swaggo/swag/cmd/swag@latest
$ swag init -g cmd/server/main.go -o docs/swagger   # 扫注释生成 docs/swagger/{docs.go,swagger.json}
internal/handler/admin.go（注解示例）// ListUsers 管理员用户列表
//
//	@Summary		[admin] 用户分页列表
//	@Tags			admin
//	@Security		BearerAuth
//	@Produce		json
//	@Param			page	query		int	false	"页码，默认 1"
//	@Param			size	query		int	false	"每页条数，默认 10，上限 50"
//	@Success		200		{object}	response.Body{data=[]model.User}
//	@Failure		403		{object}	response.Body
//	@Router			/api/v1/admin/users [get]
func (h *UserHandler) ListUsers(c *gin.Context) { /* ...原实现不动... */ }
cmd/server/main.go（挂载 + 全局注解）import (
    swaggerfiles "github.com/swaggo/files"
    ginswagger   "github.com/swaggo/gin-swagger"
    _            "blog/docs/swagger" // swag init 生成的包，只需 _ 导入
)

// @title			GoBlog API
// @version		1.0
// @description	Gin + GORM + React 全栈博客（含 RBAC 与文件上传）
// @securityDefinitions.apikey	BearerAuth
// @in							header
// @name						Authorization
func main() {
    ...
    r.GET("/swagger/*any", ginswagger.WrapHandler(swaggerfiles.Handler))
    ...
}

访问：http://localhost:8080/swagger/index.html 是交互页（Try it out 会真的调你的接口），http://localhost:8080/swagger/doc.json 是 OpenAPI/Swagger 的 JSON 源文件（可导入 Postman）。上线时给 Nginx 加一句 location /swagger { proxy_pass http://backend:8080; } 即可公网可访。

两个安全提醒：① swag init 要在每次改注解后重跑并把生成物提交进仓库，否则别人 clone 下来编译不过；② 生产环境要么给 Swagger 加 Basic Auth，要么只在 README 里放 doc.json 链接——公开可交互的 API 控制台等于给攻击者发了张地图。

作品集一句话简历项目栏：「独立完成 Go+React 全栈博客：JWT 双 token 无感续期、RBAC 管理端、带魔数校验与路径穿越防护的文件上传、多阶段 Docker 部署至公网，含测试与 Swagger 文档」——每个短语背后都有今天之前你写的真实代码兜底，面试随便深挖

今日练习

练习 1：按六步流水线重新发布（60 分钟）

把第 1 节流程在云服务器完整执行一次（这周代码还没上线的话，现在正是时候）。要求逐步截图：migrate up 输出、healthz 200、公网打开管理后台。

参考答案：高频翻车点依次为——① 服务器 .env 忘了加新变量（UPLOAD_DIR/CORS_ORIGIN），backend 起了又 crash，docker compose logs backend 一眼看到「missing env」；② migrate 容器没配 role/comments 两个迁移就 up -d，接口报 Unknown column 'role'；③ uploads 卷在服务器路径与本地不同，挂到了空目录——现象是「本地有图线上没图」，按 D2 练习 2 的对照法排查。

练习 2：README + api.md 成稿（60 分钟）

按模板写完整 README.md 与 docs/api.md，截图四张（首页/详情评论/管理后台/Swagger 页），并把「本地一键启动」在全新目录 git clone 后验证一遍。

参考答案：自检三问：新人能在 3 条命令内跑起来吗？mermaid 图在 GitHub 上渲染出来了吗？环境变量表里每个变量都能在后端 config 里找到对应读取点吗？三问有一个「否」就回炉。

练习 3：swaggo 上线（45 分钟）

给 admin 三个接口 + 上传两个接口 + 登录补注解，swag init 生成、挂载路由、打开 /swagger/index.html，用 Authorize 填 admin token 后 Try it out 调通 GET /admin/stats。

练习 4：真人验收（30 分钟 + 等待）

把 https://你的域名 + README 链接发给一位朋友（最好是同行），话术就一句：「我做的博客，帮我 5 分钟随便点点，挑一个 bug 或一个不爽」。把反馈原话记进 README 下方「Known issues / Feedback」小节——这一条真实反馈就是你面试时「用户视角」的证据。

参考答案：非技术朋友最常见的三条反馈：图片上传没有进度条（其实网络很快，但没转圈就是「感觉坏了」）、评论区没有排版、移动端表格溢出。修其中成本最低的一条并回复对方——完成一次真实的用户反馈闭环。

常见坑

坑现象正确姿势
