文件上传：从 Multipart 到持久化

知识讲义

1. Multipart 请求原理：文件到底怎么发上来

JSON 请求体是纯文本，塞二进制文件要么 base64 膨胀 33%，要么根本塞不下。multipart/form-data 的解法是：用一个随机 boundary 字符串把请求体切成多段，每段一个表单字段，文件段的 Content 就是原始字节。JS 里 new FormData() 就是帮你生成这个结构的 API——你以前从没关心过它发出的字节长什么样，今天看一次：

一个真实的 multipart 请求体POST /api/v1/uploads/avatar HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="file"; filename="me.png"
Content-Type: image/png

‹这里开始是 PNG 的原始二进制字节，一直到下一个 boundary 为止›
------WebKitFormBoundary7MA4YWxkTrZu0gW--
Content-Type谁在用适合
application/jsonaxios.post(url, obj) 默认普通接口
application/x-www-form-urlencoded老式 <form>、登录接口少量纯文本字段
multipart/form-dataFormData、文件上传带文件的任何提交

后端是否真的收到，用 curl 一行验收（这是今天所有上传接口的测试标准姿势）：

shell$ curl -s -X POST http://localhost:8080/api/v1/uploads/avatar \
    -H "Authorization: Bearer $TOKEN" \
    -F "file=@./test.png" | jq .
{
  "code": 0,
  "message": "success",
  "data": { "url": "/uploads/avatar/1727100000_ab12cd34.png" }
}

-F 会自动设置 multipart 头和 boundary；如果你手动 -H "Content-Type: multipart/form-data" 反而会因为没有 boundary 而失败。记住：multipart 的边界是生成出来的，不是手写的。

2. Gin 三种接收姿势：FormFile / SaveUploadedFile / maxMemory

Gin 对 multipart 的封装就三个关键概念：

  • c.FormFile("file")：按表单字段名取出 *multipart.FileHeader（含 Filename、Size、以及打开文件内容的方法），它不是文件内容本身。
  • c.SaveUploadedFile(file, dst)：把上传内容写到你指定好的完整路径 dst（目录必须已存在）。
  • maxMemory：Gin 引擎默认 MaxMultipartMemory = 32<<20（32MB）。请求体在限额内先驻内存、超出部分溢写到系统临时文件——所以「大文件=先吃满内存」是误解，但你也应该按业务把 32MB 收紧到 5MB。
internal/handler/upload.gopackage handler

import (
    "net/http"

    "github.com/gin-gonic/gin"
    "gorm.io/gorm"
    "blog/internal/model"
    "blog/internal/pkg/response"
    "blog/internal/pkg/upload"
)

type UploadHandler struct {
    dir string        // dir = "./uploads"
    db  *gorm.DB
}

// Avatar POST /api/v1/uploads/avatar
func (h *UploadHandler) Avatar(c *gin.Context) {
    file, err := c.FormFile("file")       // 1) 取出文件头
    if err != nil {
        response.Fail(c, http.StatusBadRequest, 1004, "缺少文件字段 file")
        return
    }
    if err := upload.ValidateImage(file); err != nil { // 2) 三件套校验，见下节
        response.Fail(c, http.StatusBadRequest, 1004, err.Error())
        return
    }

    url, err := h.save(c, file, "avatar") // 3) 随机名落盘，见第 4 节
    if err != nil {
        response.Fail(c, http.StatusInternalServerError, 1000, "存储失败")
        return
    }
    uid := c.GetUint("uid")               // 4) 把 url 写回 users.avatar
    h.db.Model(&model.User{}).Where("id = ?", uid).Update("avatar", url)
    response.OK(c, gin.H{"url": url})
}

在 main.go 里把引擎限额收紧（放在 gin.Default() 之后）：

cmd/server/main.gor := gin.Default()

3. 校验三件套：扩展名白名单 + 真 MIME + 大小限制

扩展名可以随便骗人：把木马改名 shell.png 就过了后缀检查。http.DetectContentType 读文件前 512 字节的魔数（PNG 以 \x89PNG 开头），骗不了。两者都查，再加大小限制，才叫三件套：

internal/pkg/upload/validate.gopackage upload

import (
    "errors"
    "io"
    "mime"
    "net/http"
    "path/filepath"
    "strings"

    "mime/multipart"
)

var allowedExt = map[string]bool{
    ".jpg": true, ".jpeg": true, ".png": true, ".gif": true, ".webp": true,
}

// DetectContentType 返回值可能带参数（如 image/gif; charset...），先剥离再比对
var allowedMIME = map[string]bool{
    "image/jpeg": true, "image/png": true, "image/gif": true, "image/webp": true,
}

const maxSize = 5 << 20 // 5MB

func ValidateImage(file *multipart.FileHeader) error {
    if file.Size == 0 {
        return errors.New("文件为空")
    }
    if file.Size > maxSize {
        return errors.New("文件超过 5MB 限制")
    }
    ext := strings.ToLower(filepath.Ext(file.Filename))
    if !allowedExt[ext] {
        return errors.New("仅支持 jpg/png/gif/webp")
    }
    src, err := file.Open()
    if err != nil {
        return errors.New("读取文件失败")
    }
    defer src.Close()

    buf := make([]byte, 512)
    n, err := src.Read(buf)
    if err != nil && err != io.EOF {
        return errors.New("读取文件头失败")
    }
    base, _, _ := mime.ParseMediaType(http.DetectContentType(buf[:n]))
    if !allowedMIME[base] {
        return errors.New("文件真实类型不是图片")
    }
    return nil
}

前端 input accept=".png,.jpg" 和 file.type 检查只做体验（少传错文件），任何一道服务端防线都不能省——攻击者根本不会经过你的表单。

4. 随机文件名：防覆盖，更是防路径穿越（安全重点）

file.Filename 来自客户端，是纯外部输入。如果有人上传名为 ../../../../etc/cron.d/evil 的「文件」，而你写了 filepath.Join(dir, file.Filename) 的变体拼接……不细说了，那就是任意文件写入。铁律两条：① 永远用服务端生成的随机名；② 从原始名里只允许借一个扩展名（且过白名单）。

internal/pkg/upload/save.gofunc (h *UploadHandler) save(c *gin.Context, file *multipart.FileHeader, sub string) (string, error) {
    // 只取扩展名：filepath.Ext("a/../../etc/x.png") 得到 ".png"，穿越部分自然丢弃
    ext := strings.ToLower(filepath.Ext(file.Filename))
    if len(ext) > 6 { ext = ".png" } // 兜底，白名单已在上一步保证合法

    // 服务端说了算的名字：纳秒时间戳 + 随机串，防覆盖、防猜测枚举
    name := fmt.Sprintf("%d_%x%s", time.Now().UnixNano(), randBits(4), ext)

    dir := filepath.Join(h.dir, sub)         // sub 是自己写死的 "avatar"/"cover"，不含外部输入
    if err := os.MkdirAll(dir, 0755); err != nil {
        return "", err
    }
    dst := filepath.Join(dir, name)
    if err := c.SaveUploadedFile(file, dst); err != nil {
        return "", err
    }
    return "/uploads/" + sub + "/" + name, nil // 返回相对 URL 存库，换域名不返工
}

额外保险：落盘前可以再验一句 strings.HasPrefix(dst, filepath.Clean(h.dir)+string(os.PathSeparator))——确保最终路径仍在 uploads 目录内。本项目 sub 目录写死其实已无穿越面，但这行断言值得养成习惯。

5. 两种暴露方式：Gin 静态路由 与 Nginx location

文件落了盘，还得让浏览器用 URL 拿到它。两条路，你的架构（第 7 周：Nginx → Go）两条都会遇到：

方式 A：Go 进程直接伺服（本地开发用）// main.go，Auth 中间件之前注册，图片不需要带 token
r.Static("/uploads", "./uploads") // /uploads/avatar/x.png → ./uploads/avatar/x.png
方式 B：Nginx 直接读盘（生产推荐）# /etc/nginx/conf.d/blog.conf，在 server 块内、/api 反代之前加：
location /uploads/ {
    alias /data/blog/uploads/;   # 与 backend 容器挂载的宿主目录同一个
    expires 30d;                 # 文件名带时间戳，天然可长缓存
    add_header Cache-Control "public, immutable";
}
A. Gin StaticB. Nginx location
性能每个图片请求穿一遍 Go 进程Nginx sendfile，不碰应用
适用开发环境、单机 demo生产、需要缓存策略
前提无Nginx 与 backend 共享 uploads 目录（同机 bind mount）

6. Docker 卷持久化：不挂卷，重建镜像图片全丢

第 7 周教训在 uploads 上会重演一遍：容器可写层里的东西，容器一删就没了。MySQL 你挂了卷，图片同样要挂。注意第二个坑——如果 ./uploads 被 COPY 进了镜像，改代码重建镜像时里面还是老图，不挂卷就会「复活一堆被删掉的图」：

docker-compose.yml（backend 服务节选）services:
  backend:
    build: ./backend
    environment:
      - UPLOAD_DIR=./uploads
    volumes:
      - ./uploads:/app/uploads     # ← 关键：宿主目录挂进来，盖住镜像里的旧内容
    depends_on:
      mysql:
        condition: service_healthy
  nginx:
    image: nginx:alpine
    volumes:
      - ./uploads:/data/blog/uploads:ro   # 只读给 Nginx 伺服，权限最小化
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
.dockerignore（backend 目录下，加一行）uploads/   # 本地开发攒的测试图永远不要进镜像

7. 两个接口 + 前端上传组件

路由注册（复用 Avatar 的写法，封面只是换个 sub 目录和落库字段）：

src/components/ImageUpload.jsximport { useRef, useState } from "react"
import api from "../api"

export default function ImageUpload({ kind = "avatar", onDone }) {
  const inputRef = useRef(null)
  const [preview, setPreview] = useState("")
  const [busy, setBusy] = useState(false)

  async function pick() {
    const file = inputRef.current.files[0]
    if (!file) return
    if (file.size > 5 * 1024 * 1024) return alert("图片不能超过 5MB") // 体验层拦截

    const fd = new FormData()
    fd.append("file", file)            // 字段名必须与 c.FormFile("file") 一致
    setBusy(true)
    try {
      const { data } = await api.post(`/api/v1/uploads/${kind}`, fd)
      // ⚠️ 不要手动设 Content-Type：axios 检测到 FormData 会自动带上正确的
      //    multipart/form-data + boundary；手设 json 或 multipart 都会坏
      setPreview(data.data.url)
      onDone?.(data.data.url)          // 头像：刷新 userInfo；封面：写进表单字段
    } finally { setBusy(false) }
  }

  return (
    <div className="upload">
      <input ref={inputRef} type="file" accept=".png,.jpg,.jpeg,.gif,.webp" hidden onChange={pick} />
      <button disabled={busy} onClick={() => inputRef.current.click()}>
        {busy ? "上传中…" : "选择图片"}
      </button>
      {preview && <img src={preview} alt="预览" width={120} />}
    </div>
  )
}

今日练习

练习 1：curl 打通头像接口（30 分钟）

用 curl -F 上传一张真 PNG，再传一个改名为 fake.png 的文本文件。预期：第一次 code:0 返回 url 且浏览器能打开；第二次 400 +「文件真实类型不是图片」。

参考答案：echo hacker > fake.png; curl -s -X POST -H "Authorization: Bearer $TOKEN" -F "file=@fake.png" localhost:8080/api/v1/uploads/avatar | jq .code → 1004。若 fake.png 竟然过了，检查你是不是只查了扩展名没跑 DetectContentType（文本会被识别成 text/plain; charset=utf-8）。

练习 2：核心验收——重启容器图片仍在（40 分钟）

compose 配好卷后：上传头像 → 记下 url → docker compose restart backend → 再 docker compose up -d --force-recreate backend（模拟更狠的「重建」）→ 刷新图片 URL。

参考答案：两次之后图片必须仍然 200。若第一次就 404：十有八九是 volumes 少挂或路径对不上——docker compose exec backend ls -la ./uploads/avatar 看文件到底落在容器哪里，再对照 compose 里宿主侧 ls ./uploads，两边一比对立刻破案。

练习 3：路径穿越攻击自测（20 分钟）

printf 'x' > "evil.png"; curl -F "file=@./evil.png;filename=../../../../tmp/evil.png" ... 上传。预期：文件既没落进 /tmp，也正常保存在 uploads/avatar/ 下的随机名里。

参考答案：ls /tmp/evil.png 应不存在（Linux/macOS 的 curl 对 ../ 有截断行为时，用 Go 单测构造带 ../ 的 FileHeader 更严谨）；你的实现里原始名只贡献了 filepath.Ext() 的 .png，穿越段天然无效——能亲口讲出「为什么无效」就是本题真正答案。

练习 4：文章封面端到端（40 分钟）

写 Cover 接口（存 uploads/cover/），发布文章时若填了 cover_image 则列表页卡片左侧显示缩略图；前端发文章页嵌 <ImageUpload kind="cover" onDone={url => form.cover = url}/>。验收：发文带图 → 列表页看图 → 重启容器图还在。
