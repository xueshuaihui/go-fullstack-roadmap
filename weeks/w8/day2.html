知识讲义

1. Multipart 请求原理：文件到底怎么发上来

JSON 请求体是纯文本，塞二进制文件要么 base64 膨胀 33%，要么根本塞不下。multipart/form-data 的解法是：用一个随机 boundary 字符串把请求体切成多段，每段一个表单字段，文件段的 Content 就是原始字节。JS 里 new FormData() 就是帮你生成这个结构的 API——你以前从没关心过它发出的字节长什么样，今天看一次：

一个真实的 multipart 请求体POST /api/v1/uploads/avatar HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="file"; filename="me.png"
Content-Type: image/png

‹这里开始是 PNG 的原始二进制字节，一直到下一个 boundary 为止›
------WebKitFormBoundary7MA4YWxkTrZu0gW--
Content-Type谁在用适合
application/jsonaxios.post(url, obj) 默认普通接口
application/x-www-form-urlencoded老式 <form>、登录接口少量纯文本字段
multipart/form-dataFormData、文件上传带文件的任何提交

后端是否真的收到，用 curl 一行验收（这是今天所有上传接口的测试标准姿势）：

shell$ curl -s -X POST http://localhost:8080/api/v1/uploads/avatar \
    -H "Authorization: Bearer $TOKEN" \
    -F "file=@./test.png" | jq .
{
  "code": 0,
  "message": "success",
  "data": { "url": "/uploads/avatar/1727100000_ab12cd34.png" }
}

-F 会自动设置 multipart 头和 boundary；如果你手动 -H "Content-Type: multipart/form-data" 反而会因为没有 boundary 而失败。记住：multipart 的边界是生成出来的，不是手写的。

3. Gin 接收 multipart 的三个概念

  • c.FormFile("file")：按表单字段名取出 *multipart.FileHeader（含 Filename、Size，以及 Open() 方法）。它不是文件内容本身，Filename 更是纯外部输入。
  • c.SaveUploadedFile(file, dst)：把上传内容写到你给的完整路径 dst（父目录必须已存在，所以代码里先 os.MkdirAll）。
  • MaxMultipartMemory：Gin 引擎默认 32<<20（32MB）。限额内先驻内存、超出部分溢写到系统临时文件——所以「大文件一定先吃满内存」是误解，但博客用不到 32MB，收紧到 5MB。
cmd/server/main.go（紧接 gin.Default() 之后）r := gin.Default()
r.MaxMultipartMemory = 5 << 20  // 5MB：与下面 upload.MaxSize 同值，别留 32MB 默认

4. 校验三件套：pkg/upload/validate.go（完整文件）

扩展名可以随便骗人：把木马改名 shell.png 就过了后缀检查。http.DetectContentType 读文件前 512 字节的魔数（PNG 以 \x89PNG 开头），骗不了。两者都查，再加大小与 0 字节检查，才叫三件套。

注意下面的分层：真正做判断的是 Check，它只吃三个纯值，不碰 HTTP、不开文件；ValidateImage 只是把 multipart.FileHeader 拆成这三个值再调它。Check 是纯函数，第 4 天就能在测试里逐条构造用例——这就是「可测试性」在上传功能上的具体形状。

internal/pkg/upload/validate.go（整份复制即可编译）package upload

import (
    errors
    io
    mime
    mime/multipart
    net/http
    path/filepath
    strings
)

// MaxSize 单文件上限，与 main.go 的 MaxMultipartMemory 同值。
// 导出是为了让 handler 的错误文案和第 4 天的测试用同一个数，不再各处写 5MB。
const MaxSize = 5 << 20

var allowedExt = map[string]bool{
    ".jpg": true, ".jpeg": true, ".png": true, ".gif": true, ".webp": true,
}

// allowedMIME 比对的是 DetectContentType 返回的第一段。
// 它的返回值可能带参数（image/gif; charset=...），所以比对前用 ParseMediaType 剥掉参数。
var allowedMIME = map[string]bool{
    "image/jpeg": true, "image/png": true, "image/gif": true, "image/webp": true,
}

// Check 纯函数：只认扩展名、字节数、文件头前 512 字节。
// 不打开文件、不读请求，因此可以脱离 HTTP 单独测试（第 4 天）。
// 便宜的检查放前面：0 字节和超限只看整数，魔数要嗅探，放最后。
func Check(ext string, size int64, head []byte) error {
    if size == 0 {
        return errors.New("文件为空")
    }
    if size > MaxSize {
        return errors.New("文件超过 5MB 限制")
    }
    if !allowedExt[strings.ToLower(ext)] {
        return errors.New("仅支持 jpg/png/gif/webp")
    }
    base, _, _ := mime.ParseMediaType(http.DetectContentType(head))
    if !allowedMIME[base] {
        return errors.New("文件真实类型不是图片")
    }
    return nil
}

// ValidateImage 是给 handler 用的壳：从 FileHeader 里凑齐 Check 的三个入参。
func ValidateImage(file *multipart.FileHeader) error {
    ext := filepath.Ext(file.Filename)

    src, err := file.Open()
    if err != nil {
        return errors.New("读取文件失败")
    }
    defer src.Close()

    head := make([]byte, 512)
    n, err := src.Read(head)
    if err != nil && !errors.Is(err, io.EOF) {
        return errors.New("读取文件头失败")
    }
    return Check(ext, file.Size, head[:n])  // ← 判定全部交给纯函数
}

前端 input accept=".png,.jpg" 和 file.type 检查只做体验（少传错文件），任何一道服务端防线都不能省——攻击者根本不会经过你的表单。

webp 要多留一句：标准库现在认得 image/webp（RIFF/WEBP 魔数），但老版本 Go 只会回 application/octet-stream，某些浏览器也会把 webp 的 file.type 报成 image/png。真遇到「明明是 webp 却被 400 拒」，先看错误文案出自 Check 的哪个分支：走到最后一个分支就是魔数不匹配（第 4 天有用例覆盖它），别一上来就怀疑整条上传链路。

5. 随机文件名与路径穿越：pkg/upload/save.go（完整文件）

file.Filename 是纯外部输入。铁律两条：① 落盘名由服务端生成；② 从原始名里只允许借扩展名，且必须再过一遍白名单。随机名同时解决三件事：防覆盖、防猜测枚举、把原始名的穿越面清零。

internal/pkg/upload/save.go（整份复制即可编译）package upload

import (
    crypto/rand
    encoding/hex
    fmt
    path/filepath
    strings
    time
)

// RandomName 生成落盘名：纳秒时间戳 + 8 位十六进制随机串 + 安全化后的扩展名。
// 例：1727100000123456789_ab12cd34.png
func RandomName(origName string) string {
    return fmt.Sprintf("%d_%s%s", time.Now().UnixNano(), randHex(4), SafeExt(origName))
}

// randHex 返回 n 字节随机数据的十六进制串（4 字节 → 8 个字符）。
// 为什么用 crypto/rand，而不是第 1 周用过的 math/rand？
// ① math/rand 的种子可固定，同一台机器上序列能重复，文件名就成了可预测值；
// ② 这里的用途是「不可猜测」——属于安全语义，安全语义只用密码学随机源；
// ③ crypto/rand 读失败必须当回事：这里退回时间戳派生串，宁可偶发重名也不 panic 带走整个进程。
func randHex(n int) string {
    b := make([]byte, n)
    if _, err := rand.Read(b); err != nil {
        return fmt.Sprintf("%08x", time.Now().UnixNano())
    }
    return hex.EncodeToString(b)
}

// SafeExt 只从客户端文件名里借扩展名：先 filepath.Base 去掉任何目录成分，
// 再转小写比对白名单；对不上或异常长一律退回 .png（魔数那一关已保证内容真是图片）。
func SafeExt(origName string) string {
    ext := strings.ToLower(filepath.Ext(filepath.Base(origName)))
    if !allowedExt[ext] || len(ext) > 6 {
        return ".png"
    }
    return ext
}

再说路径穿越。很多人以为「我用了 filepath.Join 就安全了」——恰恰相反，下面三段可以在本机 15 行复现，值得亲手跑一遍：

反例与正解（可以先塞进一个 package main 的小程序里验证，再回到项目）// 反例一：手工拼字符串，把外部输入塞进路径
dst := h.dir + "/" + sub + "/" + nameFromClient   // nameFromClient = "../../../tmp/evil"
os.WriteFile(dst, data, 0o644)                     // → /tmp/evil：写到 uploads 之外

// 反例二：换成 filepath.Join 就没事了吗？并没有——Join 会 Clean，穿越照样成立
fmt.Println(filepath.Join("/app/uploads", "../../../tmp/evil"))
// 输出：/tmp/evil   ← Join 把 a/../../ 折叠掉了，折叠的结果正是跳出根目录

// 正解一（本课做法）：目录成分一个都不接受外部输入，sub 是写死的常量，名字是随机生成的
dst := filepath.Join(h.dir, sub, upload.RandomName(file.Filename))

// 正解二：将来若 sub 也要从请求里取，落盘前必须补一句前缀断言（第 6 节 save 里就留着这行）
if !strings.HasPrefix(dst, filepath.Clean(h.dir)+string(os.PathSeparator)) {
    return errors.New("非法存储路径")
}

还有一件容易讲错的事：Go 标准库的 multipart 读取器已经把 Filename 取过基名——curl -F "file=@a.png;filename=../../../../tmp/evil.png" 到达 handler 时 file.Filename 就是 evil.png。所以你在本机「演示穿越攻击」会演不成功，那是标准库先替你挡了一道，不能当成自己代码安全的证据：它保护不了 c.PostForm("dir") 这类你自己拼进路径的字段，换一层解析（手撸 multipart.NewReader、换别的框架）也没有这层清洗。真正可复现的反例是上面两段 Go 代码。

internal/handler/upload.go（整份复制即可编译）package handler

import (
    errors
    mime/multipart
    net/http
    os
    path/filepath
    strconv
    strings

    "github.com/gin-gonic/gin"
    "gorm.io/gorm"

    "goblog/internal/model"
    "goblog/internal/pkg/upload"
    "goblog/pkg/response"
)

// UploadHandler 持有落盘根目录（cfg.UploadDir）和库句柄。
// 本课从简：只回写 users.avatar 与 articles.cover_image 两列，直接拿 *gorm.DB；
// 生产写法是把 Update 下沉到 repository 接口（第 2 周那条线），handler 不认识 gorm。
type UploadHandler struct {
    dir string
    db  *gorm.DB
}

func NewUploadHandler(dir string, db *gorm.DB) *UploadHandler {
    return &UploadHandler{dir: dir, db: db}
}

// Avatar POST /api/v1/uploads/avatar —— 表单字段 file，落盘后把相对 URL 写回 users.avatar
func (h *UploadHandler) Avatar(c *gin.Context) {
    file, err := c.FormFile("file")
    if err != nil {
        response.Fail(c, http.StatusBadRequest, 1004, "缺少文件字段 file")
        return
    }
    if err := upload.ValidateImage(file); err != nil {
        response.Fail(c, http.StatusBadRequest, 1004, err.Error())  // 校验文案直接透给前端
        return
    }
    url, err := h.save(c, file, "avatar")
    if err != nil {
        response.Fail(c, http.StatusInternalServerError, 5000, "存储失败")
        return
    }

    uid := c.GetUint("userID")   // ← 第 1 天 Auth 中间件塞的 context 键，全站统一
    if err := h.db.Model(&model.User{}).Where("id = ?", uid).Update("avatar", url).Error; err != nil {
        response.Fail(c, http.StatusInternalServerError, 5000, "更新头像失败")
        return
    }
    response.OK(c, gin.H{"url": url})
}

// Cover POST /api/v1/uploads/cover —— 可选表单字段 article_id：带上就顺手把 cover_image 写进那篇自己的文章
func (h *UploadHandler) Cover(c *gin.Context) {
    file, err := c.FormFile("file")
    if err != nil {
        response.Fail(c, http.StatusBadRequest, 1004, "缺少文件字段 file")
        return
    }
    if err := upload.ValidateImage(file); err != nil {
        response.Fail(c, http.StatusBadRequest, 1004, err.Error())
        return
    }
    url, err := h.save(c, file, "cover")
    if err != nil {
        response.Fail(c, http.StatusInternalServerError, 5000, "存储失败")
        return
    }

    if idStr := c.PostForm("article_id"); idStr != "" {   // multipart 里的普通字段用 PostForm 取
        id, err := strconv.ParseUint(idStr, 10, 32)
        if err != nil || id == 0 {
            response.Fail(c, http.StatusBadRequest, 1004, "article_id 必须是正整数")
            return
        }
        res := h.db.Model(&model.Article{}).
            Where("id = ? AND user_id = ?", uint(id), c.GetUint("userID")).
            Update("cover_image", url)
        if res.Error != nil {
            response.Fail(c, http.StatusInternalServerError, 5000, "更新封面失败")
            return
        }
        if res.RowsAffected == 0 {   // 不是你的文章也回 404：不给外人探测文章是否存在
            response.Fail(c, http.StatusNotFound, 2001, "文章不存在")
            return
        }
    }
    response.OK(c, gin.H{"url": url})
}

// save 落盘：目录 = h.dir/sub（sub 写死），文件名完全由服务端生成，返回可公开的相对 URL。
func (h *UploadHandler) save(c *gin.Context, file *multipart.FileHeader, sub string) (string, error) {
    name := upload.RandomName(file.Filename)
    dir := filepath.Join(h.dir, sub)
    if err := os.MkdirAll(dir, 0o755); err != nil {   // SaveUploadedFile 不建目录，必须先 MkdirAll
        return "", err
    }
    dst := filepath.Join(dir, name)
    // 兜底断言：最终路径必须仍在 h.dir 里。今天恒为真，但将来 sub 改成从请求里取时，
    // 这行就是拦住任意文件写入的最后一道门（filepath.Join 自己不会拦，见第 5 节反例二）。
    if !strings.HasPrefix(dst, filepath.Clean(h.dir)+string(os.PathSeparator)) {
        return "", errors.New("非法存储路径")
    }
    if err := c.SaveUploadedFile(file, dst); err != nil {
        return "", err
    }
    return "/uploads/" + sub + "/" + name, nil  // 相对 URL 入库：换域名/上 CDN 都不改数据
}

7. 两种暴露方式：Gin 静态路由 与 frontend 容器里的 nginx

文件落了盘，还得让浏览器用 URL 拿到它。你的生产链路是 Caddy → frontend（镜像内置 nginx）→ backend：nginx 配置就是第 7 周那份 frontend/nginx.conf，构建时被 COPY nginx.conf /etc/nginx/conf.d/default.conf 烧进镜像——没有独立的 nginx 服务，也没有 blog.conf 这个文件，所以「加一段 location」= 改 frontend/nginx.conf + 重建前端镜像。

方式 A：Go 进程直接伺服（本地开发，main.go 里已经写好）r.Static("/uploads", cfg.UploadDir)   // /uploads/avatar/x.png → ./uploads/avatar/x.png
方式 B：frontend 容器里的 nginx 读盘（生产推荐，diff 形式） server {
     listen 80;
     server_name _;
     root /usr/share/nginx/html;
     index index.html;

+    client_max_body_size 12m;      # 第 7 周没写这行，nginx 默认 1m：5MB 的图会在这一层就被 413 挡掉，
+                                  # 后端连日志都不打。12m 给 multipart 边界开销留了余量

+    location /uploads/ {           # 第 7 周的 nginx.conf 里只有 /api/、/assets/、/，今天补一条
+        alias /var/www/uploads/;    # 与 backend 容器共享的 uploads 卷挂载点（见第 8 节）
+        expires 30d;               # 文件名带纳秒戳，内容变了名字就变，可以放心长缓存
+        add_header Cache-Control "public, immutable";
+    }

     location /api/ { proxy_pass http://backend:8080; ... }
     location /     { try_files $uri $uri/ /index.html; }

为什么 location /uploads/ 必须写在 location / 之前？其实和顺序无关——nginx 的前缀 location 取最长匹配，/uploads/ 比 / 长，永远优先命中。写在一起只是为了读配置的人一眼看见。真正会被顺序坑的是精确匹配（location = /index.html）和 try_files 兜底：漏了这条 location，/uploads/x.png 会掉进 location / 被兜底成 index.html——于是浏览器报「图片损坏」，Network 里状态码却是 200，Content-Type 是 text/html。这个「200 但内容不是图」的现象，是本章最值得记住的一条排查线索。

谁读盘Go 进程，每个图片请求穿一遍应用nginx sendfile，完全不碰应用
适用本地开发（docker compose up -d 就能看图）生产；需要缓存头、Range 请求
前提无两个容器挂同一个 uploads 卷，且容器内路径与 alias 对得上
省事变体—location /uploads/ { proxy_pass http://backend:8080; }：只有 backend 挂卷，图片交给 Gin。先用它跑通，再换 alias

顺带记住两个「不是后端的错」：413 且响应体是 nginx 的 HTML → client_max_body_size 没配（默认 1m）或被别人改小了，请求根本没到 Go——去 docker compose logs backend 看一眼，字段校验的日志一行都不会有；200 但图片裂开 → location /uploads/ 缺失，请求被 try_files 兜底成了 index.html。判据是同一条：拿到 HTML 就说明请求没进后端，先查中间层（frontend 的 nginx / Caddy）。Caddy 默认不限请求体，也不做兜底页面，所以嫌疑只在 nginx 这一段。

9. 前端上传组件：src/components/ImageUpload.jsx

第 6 周立的两条规矩在这里全用得上：一律 import { http } from '../api/http'（named export），URL 写相对路径交给 baseURL: '/api/v1'，响应已被拦截器拆过包——拿到的就是 data 本身，没有第二层 .data。

src/components/ImageUpload.jsx（新文件）import { useRef, useState } from 'react'
import { http } from '../api/http'        // ← named export，不是 import api from '../api'

export function ImageUpload({ kind = 'avatar', onDone }) {
  const inputRef = useRef(null)
  const [preview, setPreview] = useState('')
  const [busy, setBusy] = useState(false)
  const [err, setErr] = useState('')

  async function pick() {
    const file = inputRef.current.files[0]
    if (!file) return
    if (file.size > 5 * 1024 * 1024) { setErr('图片不能超过 5MB'); return }  // 体验层拦截

    const fd = new FormData()
    fd.append('file', file)            // 字段名必须与 c.FormFile("file") 一致
    setBusy(true); setErr('')
    try {
      // ⚠️ 不要手动设 Content-Type：axios 见到 FormData 会自己生成 multipart + boundary
      // 拦截器已经拆过包：res 就是后端的 data —— 所以是 res.url，不是 res.data.data.url
      const res = await http.post(`/uploads/${kind}`, fd)
      setPreview(res.url)
      onDone?.(res.url)              // 头像：交给父组件刷新展示；封面：写进表单字段
    } catch (e) {
      setErr(e.message || '上传失败')  // code≠0 时拦截器 reject，带的是后端 message
    } finally { setBusy(false) }
  }

  return (
    <div className="upload">
      <input ref={inputRef} type="file" accept=".png,.jpg,.jpeg,.gif,.webp" hidden onChange={pick} />
      <button disabled={busy} onClick={() => inputRef.current.click()}>
        {busy ? "上传中…" : "选择图片"}
      </button>
      {preview && <img src={preview} alt="预览" width={120} />}
      {err && <p className="err">{err}</p>}
    </div>
  )
}

练习 2：核心验收——重建容器图片仍在（40 分钟）

参考答案：三次之后图片必须仍然 200。第一次就 404 的话，九成是卷少挂或路径对不上：docker compose exec backend ls -la /app/uploads/avatar 看文件真正落在容器哪儿，再 docker volume inspect goblog_uploads 看卷挂到了哪个宿主路径，两边一比对立刻破案。如果 404 的是生产域名而容器里有文件，那是 frontend/nginx.conf 的 alias 路径没对上，或忘了 docker compose build frontend。

练习 3：亲手复现一次「穿越」，再把它堵住（25 分钟）
