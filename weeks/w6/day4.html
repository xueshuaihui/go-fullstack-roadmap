路由守卫与 axios 拦截器

本周的重头戏。前三天的应用有个假象：好像永远登录着。今天补上两块真·工程能力——①路由守卫：没登录的人根本进不了 /post/new；②401 静默续期：accessToken（15 分钟）过期时，用户毫无感知地被 refresh token 换发新 token 并重试原请求，只有 refreshToken（7 天）也过期才跳登录。这正是第 4 周后端留的钩子，今天前端把它接完。

课前须知：先把时序图刻进脑子

1. 正常链路：业务请求 → 拦截器带 accessToken → 后端 200 → 拆包返回。99% 的请求走这条路，静默刷新只在剩下 1% 出现。

2. 续期链路：业务请求 → 401（后端码 1005）→ 拿 refreshToken 调 POST /api/v1/auth/refresh，请求体 { refresh_token }、返回 data: { access_token, refresh_token }（两端都是 snake_case，和第 4 周后端一致）→ 成功：把新双 token 写回 localStorage 并广播 auth:change → 用新 token 重试原请求 → 用户看到的仍是一个成功的 Promise，全程无感。

3. 兜底链路：refresh 接口也失败（refreshToken 过期/被撤销）→ 清三个 localStorage 键 → 跳 /login?redirect=当前页。三张图对应拦截器的三个分支，今天的代码就是把它们写出来。

知识讲义

1. 为什么守卫要在「首次 render」就知道登录态

SPA 刷新即失忆：内存里的 user 没了，只剩 localStorage。如果登录态靠 useEffect 异步恢复，守卫在恢复完成前会认为「未登录」，用户会看到闪一下登录页再弹回来。所以昨天的 useAuth 特意用了「useState 同步初始化」——今天兑现它的价值：守卫读的是同步就能拿到的 localStorage.getItem('accessToken')。

2. ProtectedRoute 组件

jsx// src/components/ProtectedRoute.jsx
import { Navigate, useLocation } from 'react-router-dom'

export function ProtectedRoute({ children }) {
  // 同步读，绝不用 useEffect 异步判断——那就会闪烁
  const token = localStorage.getItem('accessToken')
  const location = useLocation()

  if (!token) {
    // 把被拦下的目标路径编码进 redirect 参数，登录成功后回跳
    const redirect = encodeURIComponent(location.pathname + location.search)
    return <Navigate to={`/login?redirect=${redirect}`} replace />
  }
  return children
}

守卫只判断「有没有 token」，不判断「token 有没有过期」——这是刻意的。要在守卫里验有效期，就得在前端解析 JWT（base64 拆 exp），既多一层代码又不可信（客户端时间能被改）。过期那份由第 4 节的链路兜：请求发出 → 401 → 静默刷新 → 重试成功，用户全程没感觉；只有 refreshToken 也废了才真的送你回登录页。所以这里的判定标准是「本地有没有会话」，而不是「服务端认不认」。

jsx// src/App.jsx —— 用守卫包住需要登录的路由
<Route path="/post/new"
  element={<ProtectedRoute><Editor /></ProtectedRoute>} />
<Route path="/post/:id/edit"
  element={<ProtectedRoute><Editor /></ProtectedRoute>} />
<Route path="/me"
  element={<ProtectedRoute><Profile /></ProtectedRoute>} />
// 列表 / 详情 / 登录 / 注册不包：游客可读

另一种写法是 v6.4+ 的 React.lazy + loader 路由守卫或布局路由 <Route element={<ProtectedLayout/>}> 包一批子路由。本质相同（同步检查 + Navigate），先掌握上面这种，迁移到布局路由只是换个位置放组件。

4. 响应拦截器完整代码：401 → 刷新 → 重试

把 day1 的骨架升级成完整版。整份替换 src/api/http.js（named export 的名字、baseURL 都不变，业务代码一行不用改）。先看不含并发控制的主干，下一节再加锁：

js// src/api/http.js —— 全周唯一一份完整实现（day5 只改 baseURL 的来源，结构不动）
import axios from 'axios'

export const http = axios.create({ baseURL: '/api/v1', timeout: 10000 })

http.interceptors.request.use((config) => {
  const token = localStorage.getItem('accessToken')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

const KEYS = ['accessToken', 'refreshToken', 'user']
const AUTH_EVENT = 'auth:change' // 和 day1 useAuth 里同名同值
// 这里手写常量而不是 import 那个文件：useAuth → api/auth → http 会形成循环依赖
const broadcast = () => window.dispatchEvent(new Event(AUTH_EVENT))

const clearTokens = () => {
  KEYS.forEach((k) => localStorage.removeItem(k))
  broadcast() // 清完必须广播，否则 NavBar 还挂着昵称，用户以为还登录着
}

const goLogin = () => {
  clearTokens()
  const redirect = encodeURIComponent(
    window.location.pathname + window.location.search
  )
  window.location.href = `/login?redirect=${redirect}` // 为什么用 location？见第 6 节
}

// 用裸 axios 调刷新接口：它绝不能走本实例的拦截器，
// 否则 refresh 自己 401 会再触发 refresh —— 死循环
const requestRefresh = async () => {
  const refreshToken = localStorage.getItem('refreshToken')
  if (!refreshToken) throw new Error('没有 refreshToken')

  const { data: body } = await axios.post('/api/v1/auth/refresh', {
    refresh_token: refreshToken, // ← 后端要 snake_case，别写 refreshToken（会被当空值 → 401）
  }, { timeout: 10000 })

  if (body.code !== 0) throw new Error(body.message || 'refresh 失败')

  // 刷新成功返回的 data 和登录同形：{ access_token, refresh_token }（snake_case）
  // 有的实现会顺带回 user，这里不依赖它：user 键保持登录时写进去的那份
  localStorage.setItem('accessToken', body.data.access_token)
  localStorage.setItem('refreshToken', body.data.refresh_token) // 滑动续期，双 token 都换
  broadcast()  // 换完也广播：订阅 useAuth 的组件重读 localStorage
  return body.data.access_token
}

http.interceptors.response.use(
  (response) => {
    const body = response.data
    if (body.code !== 0) { // HTTP 2xx 但业务码非 0（本项目少见，但要防）
      const e = new Error(body.message || '请求失败')
      e.status = response.status; e.code = body.code; e.response = response
      return Promise.reject(e)
    }
    return body.data // 业务代码拿到的就是 data：列表是 { list, total, page, size, total_page }
  },
  async (error) => {
    const original = error.config
    const status = error.response?.status

    // —— 分支一：401（后端码 1005，token 无效或过期）且有 refreshToken，且这枪没搭过便车 ——
    if (status === 401 && localStorage.getItem('refreshToken') && !original?._retried) {
      original._retried = true // 每个请求只允许搭一次「刷新重试」的便车
      try {
        const newToken = await requestRefresh() // 主干版：每 401 各刷各的（下一节改进）
        original.headers.Authorization = `Bearer ${newToken}` // 与请求拦截器同一种写法，别混展开语法
        return http(original) // 关键：把重试的 Promise 交出去，调用方 await 到的就是最终结果
      } catch (e) {
        goLogin() // —— 分支二：refresh 也失败（401/1005）→ 清 token 跳登录 ——
        const done = new Error('登录已过期，请重新登录')
        done.status = 401
        return Promise.reject(done)
      }
    }
    // —— 分支三：其它错误（403/404/500 或重试后仍 401）照常抛，但把状态码一起带上 ——
    const res = error.response
    const e = new Error(res?.data?.message || error.message || '网络错误')
    e.status = res?.status       // day2 详情页的空态判断靠它（e.status === 404）
    e.code = res?.data?.code     // 后端业务码：1003 无权限 / 2001 文章不存在 / 1005 token 失效
    e.response = res             // 有人就是喜欢 error.response.status，也留一条通路
    return Promise.reject(e)
  }
)

四个细节定生死：①original._retried 标志防「重试请求又 401 → 再刷」的无限循环；②refresh 用裸 axios 绕开本实例，并且请求体写 refresh_token、响应读 data.access_token（snake_case，后端 JSON tag 就是这么定的）；③return http(original) 返回的是 Promise，页面里 await listArticles() 会一直等到重试结果——这就是「用户无感知」的实现原理；④抛出的 Error 一定带上 status/code，否则 day2 的「404 走空态」和今天的「401 走刷新」都无从判断。

5. 并发 401 只刷新一次：pending Promise 单例

真实场景：一个页面同时发两枪都要带 token 的请求（比如个人页的 Profile 拉 GET /users/me，同屏另一个「我的文章数」小组件也拉 GET /users/me），accessToken 恰好过期，两个 401 同时到达。主干版会发两次 refresh——后端 refresh 若是一次性轮换（旧 refreshToken 用完即废），第二次刷新拿废弃 token 必挂，好好的会话被踢。两种解法：

做这个实验，第二枪必须是受保护接口。本项目里 GET /articles 是游客可读的，accessToken 废掉它照样 200，Network 里 refresh 只会出现 1 条——你会误以为「锁生效了」，其实压根没有第二个 401。第二枪用 GET /users/me（Auth 中间件保护，见第 4 周）。

jsx// src/pages/Profile.jsx —— 临时把取数改成并发两枪，制造可复现的并发 401
import { fetchMe } from '../api/auth' // day1 第 5 节那个函数

useEffect(() => {
  Promise.all([fetchMe(), fetchMe()]) // 同一毫秒发出、同一毫秒各自 401
    .then(([a, b]) => console.log('两枪都回来了', a.user.id, b.user.id))
    .catch((e) => console.log('失败', e.status, e.code, e.message))
}, [])
// 拦截器里临时加一行计数，验完删掉：
//   console.log('[refresh] 发出')  放在 requestRefresh 的第一行
方案思路评价
等待队列第一个 401 开始刷新，后续 401 把自己的「重试函数」push 进数组；刷新成功后遍历执行经典教学模型，代码长、要自己管队列；理解概念够用
pending Promise 单例全局存一个 refreshPromise：有在途刷新就 await 同一个 Promise，没有才发起今天采用：几行代码，语义等价「并发合流」
js// 队列方案长这样（读懂即可，不必采用）——注意 refreshPromise 其实就是它的压缩版：
let pendingQueue = []      // 等刷新的请求都把"重试函数"存这
let refreshing = false

async function on401(retryFn) {
  pendingQueue.push(retryFn)
  if (refreshing) return        // 已经有人在刷了，排队等叫号
  refreshing = true
  try {
    await requestRefresh()
    pendingQueue.forEach((fn) => fn()) // 刷新成功，全体重试
  } finally {
    pendingQueue = []; refreshing = false
  }
}
// 对比可见：Promise 天生自带"等待队列"（then 链），手动数组+布尔锁是重复造轮子
js// 在上一节代码基础上：把 requestRefresh 原样保留，改动两处 ——

let refreshPromise = null // 模块级单例：同一时刻最多一次刷新在途

const refreshOnce = () => {
  if (!refreshPromise) {
    refreshPromise = requestRefresh().finally(() => {
      refreshPromise = null // 成败都要复位，否则下次过期永远 await 一个旧 Promise
    })
  }
  return refreshPromise // 第 2、3、N 个 401 拿到的是同一个 Promise（合流点）
}

// 拦截器分支一里只改一行：
const newToken = await refreshOnce() // 原来是 requestRefresh()

时间线：401-A 到达 → refreshPromise 为空 → 创建并发出 refresh；401-B 到达 → 不为空 → 直接 await 同一个 Promise；refresh 返回 → A、B 同时醒来各拿新 token 重试自己的请求 → finally 复位。一次刷新，N 个请求复用的效果就这四行。

做法说明结论

练习 3：双请求并发 401，验证只刷一次（40 分钟）

练习 4：refresh 也失效的兜底（30 分钟）

把 accessToken 和 refreshToken 同时改成废值，访问 /me。预期：业务请求 401 → refresh 发出 → 后端回 401 + code 1005 → 清空三个键并广播 → 整页跳到 /login?redirect=%2Fme；重新登录后回到 /me。全程不应出现页面反复横跳（死循环）。控制台顺手确认 localStorage.getItem('user') 是 null。

常见坑

坑现象正确姿势
refresh 的字段名按前端习惯写请求体写成 refreshToken、响应读 data.accessToken → 后端读不到 → refresh 401，会话每次过期都被踢后端契约是 snake_case：发 refresh_token，读 data.access_token / data.refresh_token；本地 localStorage 键才是小驼峰
并发实验拿公开接口凑数第二枪用了 GET /articles，Network 里只有一条 refresh，误判「锁生效」两枪都要带 token（本项目就用两次 GET /users/me），先确认两个 401 都出现了再数 refresh
拦截器里异步不返回 Promise刷新逻辑明明执行了，页面却拿到 undefined / 报错被吞错误分支必须 return Promise.reject(...)；重试必须 return http(original)，让 Promise 链不断
refresh 走了 http 实例自己refresh 401 → 触发刷新 → 又调 refresh…… Network 刷屏refresh 用裸 axios.post，或给 config 打 _skipAuthFlow 标记跳过
没有 _retried 标志重试请求再次 401 时又刷一次，无限循环每个 original 请求只许搭一次便车：重试前置 _retried = true，条件里排除
守卫异步恢复登录态刷新页面瞬间闪一下登录页/空数据守卫同步读 localStorage；useAuth 初始值同步 parse（day1 埋的伏笔）
refreshPromise 忘了 finally 复位第一次续期正常，第二次过期永远卡住不动finally(() => refreshPromise = null)，成败都要清
闭包拿到旧 state拦截器里用 React state 判断登录，永远读到挂载时的旧值拦截器与组件解耦：真相源只有一个——localStorage；React state 只是它的展示副本

今日名词卡

术语一句话解释
路由守卫渲染目标页前检查准入条件的组件/函数，不合格就 Navigate 改道
静默刷新（silent refresh）用户无感知地用 refreshToken 换回新 accessToken 并重试原请求
重试（retry）把失败请求的 config 原样再发一次，仅把 Authorization 换成新 token
并发合流多个 401 共享同一个在途 refresh Promise，只发一次刷新；pending 单例是其最小实现
滑动续期每次 refresh 同时发新 refreshToken，活跃用户 7 天期限不断向后滚
