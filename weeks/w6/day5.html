课前须知：同源策略只约束浏览器

1. curl / Postman 永远不会有 CORS 问题。跨域是浏览器对「网页里的 JS 发起跨源请求」的管制，服务器之间、命令行之间不存在。所以「curl 通、前端不通」几乎必然是 CORS，而不是接口坏了。

2. 拦截发生在响应之后。多数请求其实已经打到后端执行了，只是响应被浏览器拦下不给 JS。所以你在 Gin 日志里看到请求进来了、数据也查了，前端却报 CORS——不是没通，是「回程被扣」。

3. 端口不同即不同源。localhost:5173 的页面请求 localhost:8080，协议/域名/端口三者有一不同就是跨域——端口不同就够了。

知识讲义

1. CORS 报错三连：认清每张案发现场的照片

text① Response to preflight request doesn't pass access control check:
   No 'Access-Control-Allow-Origin' header is present on the requested resource.
   Access to script at 'http://localhost:8080/api/v1/articles' from origin
   'http://localhost:5173' has been blocked by CORS policy

② OPTIONS /api/v1/articles 404   ← Network 里红色的小 OPTIONS 请求
   （预检请求本身没被后端处理，浏览器直接判死刑）

③ The value of the 'Access-Control-Allow-Origin' header in the response
   must not be the wildcard '*' when the request's credentials mode is 'include'.
报错成因解法
①缺 Allow-Origin响应头没允许该来源；任何简单请求也要带此头浏览器才放行后端 CORS 中间件加 Access-Control-Allow-Origin: http://localhost:5173
②预检 OPTIONS 挂掉带 Authorization、Content-Type: application/json 的请求不是「简单请求」，浏览器先替 JS 发一个 OPTIONS 探路；后端没回应探路 = 正请求根本不发中间件对 OPTIONS 返回 204，并带 Access-Control-Allow-Methods / Allow-Headers
③credentials 与 * 冲突请求开了 withCredentials（带 cookie）时，Allow-Origin 不允许通配 *，必须写明白名单本手册用 localStorage 存 token，不需要 withCredentials；若要用 cookie 会话则必须精确 origin

记忆锚点：简单请求看「响应头」，非简单请求先「预检」再响应头。你的 API 全用 JSON + Bearer 头，所以每一个写请求都带预检——Network 面板里成对出现的 OPTIONS+POST 不是重复发送。

你的请求是否简单请求原因
GET /articles?page=1（不带自定义头）是GET + 无 Authorization，直接发，响应缺 Allow-Origin 才被拦
POST /auth/login（JSON）否Content-Type: application/json 不在简单白名单（仅 form 三种）
任何带 Authorization 的请求否自定义头必触发预检，预检会问 Access-Control-Request-Headers: authorization

2. Go 侧 CORS 中间件（第 2 周写过，今天温故升级版）

go// internal/middleware/cors.go —— 开发期够用的最小实现（函数名全站统一叫 CORS，第 2 周就是它）
package middleware

func CORS() gin.HandlerFunc {
    return func (c *gin.Context) {
        // 学习期直接 * 图方便；上生产换白名单精确匹配 Origin
        c.Header("Access-Control-Allow-Origin", "*")
        c.Header("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,OPTIONS")
        c.Header("Access-Control-Allow-Headers", "Content-Type,Authorization")
        if c.Request.Method == "OPTIONS" { // 预检到此为止，不必进业务逻辑
            c.AbortWithStatus(204)
            return
        }
        c.Next()
    }
}

注册顺序：CORS 必须在 Auth 之前。Gin 的 Use 是队列，写在哪就跑在哪。预检请求 OPTIONS 不会带 Authorization 头（浏览器规范如此），要是 Auth 中间件先跑，它一看没 token 直接 401 截断——浏览器于是报「CORS 失败」，你在前端看到的现象是「跨域」，在后端日志里看到的却是 401，两头都像是自己的锅。正确写法是把 CORS 放在全局中间件那一行里，排在分组挂载的 middleware.Auth(...) 前面。

第 3/4 周的 goblog 装配里没有挂 CORS（那几天都用 curl 和 Postman，跨域轮不到它出场）。今天做练习 1 之前先把这一行补上，改的就是第 4 周 Day 2 那段 cmd/server/main.go：

cmd/server/main.go// -  r := gin.New()
// -  r.Use(gin.Logger(), gin.Recovery())            // 全局中间件
// +  r := gin.New()
// +  r.Use(gin.Logger(), gin.Recovery(), middleware.CORS())  // ← CORS 在 Auth 之前，位置就是语义
//    （import 里补一行 "goblog/internal/middleware"，第 4 周挂 Auth 时已经有了）

生产上更常见的做法是根本不在 Go 里配 CORS，让第 7 周的 Nginx 同源反代把这个话题消灭掉（见第 4 节）。这个中间件是「前端独立域名部署」或「本地故意拆掉 proxy 做实验」时才需要。Allow-Origin: * 只能用于不需要 cookie 的接口——本手册用 localStorage 存 token，正好用得上；第 8 周若要 cookie 会话，得同时改成精确白名单 + Access-Control-Allow-Credentials: true（就是报错③）。

3. 开发环境 Vite proxy：今天正式把它拆开看

js// vite.config.js —— 与 day1 第 2 节那份一致，key 就用 /api/v1
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      // 所有以 /api/v1 开头的请求，由 Vite 开发服务器"代转"给 Go
      '/api/v1': {
        target: 'http://localhost:8080',
        changeOrigin: true, // 把请求头里的 Host 改写成 target，模拟同源服务
        // 故意不写 rewrite：后端的路由组就叫 /api/v1，路径原样递过去才对
      },
    },
  },
})

为什么 proxy 能绕开 CORS？因为跨域是浏览器的规矩，Vite 的 Node 进程不是浏览器，它转发请求不受任何同源限制：

text不用 proxy：  浏览器(5173) ──跨域请求──✗ 被拦 ✗──  Go(8080)
用 proxy：    浏览器(5173) ──同源请求 /api/v1──▶  Vite(5173) ──Node 转发──▶  Go(8080)
              浏览器以为一直在跟自己说话，压根没有跨域这回事

这也解释了 baseURL 为什么写 /api/v1 而不是 http://localhost:8080/api/v1：写绝对地址会绕开 proxy 直接跨域（练习 1 就故意这么炸一次）。路径叠错（请求变成 /api/v1/api/v1/articles）的成因不是 proxy key，而是baseURL 已经带了 /api/v1，api 函数里又把全路径写了一遍——约定：http.get('/articles') 只写资源路径，前缀归 baseURL。

proxy 配了不生效？按这张最小排查表走：

检查点怎么看修复
Vite 重启了吗改 vite.config.js 后终端会自己重启，但改 .env 系列不会都触发Ctrl+C 后重新 npm run dev，别信热更新

转发路径对不对默认不改路径：/api/v1/auth/login → http://localhost:8080/api/v1/auth/login，与 Gin 的 v1 := r.Group("/api/v1") 一致即可后端若没挂 /api/v1 前缀才需要 rewrite，本项目不需要（写了反而 404）

4. 生产环境：同源部署，CORS 直接消失

线上没有 Vite 给你转发。正解是让前端静态文件和 API 看起来同源——Nginx 一个入口分流：

text                 ┌─ /            → 返回 dist/ 里的 index.html 及静态资源
用户 ──▶ Nginx:80 ┤
                 └─ /api/*       → 反向代理 → Go 服务 :8080
同一域名同一端口，浏览器眼里根本没有第二个"源"，CORS 配置甚至可以全关。

具体 Nginx 配置、Docker 化部署是第 7 周主线（Day 2 就是「前端构建 + Nginx」），今天只需在 App.jsx 里先处理 SPA 路由的一个前奏问题：直接访问 /post/3 刷新时，Nginx 找不到这个「文件」。答案都是 try_files $uri /index.html 兜底，Vite preview 已内置同样行为。第 7 周你会亲手写的配置，提前混个脸熟：

text# nginx.conf —— 第 7 周正式逐行讲，今天只求认出结构
server {
    listen 80;
    location / {
        root  /usr/share/nginx/html;   # dist/ 拷进这里
        try_files $uri $uri/ /index.html;   # SPA 刷新兜底
    }
    location /api/ {
        proxy_pass http://backend:8080;     # /api/* 转给 Go 服务
    }
}

现象第一动作依次排查

字段对齐的根因常在后端这几行，Go 导出字段但没 tag 时，JSON 键就是字段原名；本手册后端一律 snake_case：

go// ❌ 无 tag：返回 {"ID":1,"CoverImage":""} → 前端 article.id / article.cover_image 全 undefined
type Article struct {
    ID         uint
    CoverImage string
}

// ✅ 补 tag：键名与前端用的完全一致（全周统一 snake_case）
type Article struct {
    ID         uint   `json:"id"`
    CoverImage string `json:"cover_image"` // ← 不是 coverImage，day2/day3 的页面都按这个键取
}

读响应头的习惯今天养成：DevTools → Network → 点开请求 → Headers 标签看请求/响应头，Preview 标签看拆包前的原始 JSON。「看请求头确认带没带 token，看 Preview 确认字段名」——排错清单的前两行全靠它。

1. 挪目录（四条命令）

shell$ cd ~/code                                  # 换成你放这两个项目的父目录
$ ls -d goblog blog-web                      # 两个都在才继续；名字不同就换成你的实际名字
$ mkdir goblog.tmp                           # 先建临时壳，避免 mv 时目标名和源名同名打架
$ mv goblog goblog.tmp/backend               # 后端整体变成 backend/（go.mod、cmd、internal、.env 全跟着走）
$ mv blog-web goblog.tmp/frontend            # 前端整体变成 frontend/（node_modules 也一起搬，不用重装）
$ mv goblog.tmp/backend/docker-compose.yml goblog.tmp/   # compose 提到仓库根
$ mv goblog.tmp goblog                       # 改名回正式位置，归置完成

$ cd goblog && ls                            # 期望看到：backend  frontend  docker-compose.yml

为什么要绕一个 goblog.tmp：mv goblog goblog/backend 会把目录往自己里面塞，直接报错或套娃。先建临时壳再改名，是唯一不用动脑子的安全走法。Go 模块名仍是 goblog，import 路径一行都不用改——搬目录改的是文件系统位置，不是包路径。

常见坑

坑现象正确姿势
baseURL 与函数路径各带一次前缀请求变 /api/v1/api/v1/articles，proxy 照转不误，后端 404前缀只在 baseURL 出现一次：api 函数写 http.get('/articles')；proxy key 与 baseURL 都写 /api/v1 是正常搭配
env 变量没加 VITE_ 前缀import.meta.env.XXX 是 undefined，baseURL 变 "undefined/auth/login"必须 VITE_ 前缀；改完重启 dev server
.env.local 提交了 git本机专属地址/密钥泄漏给协作者.gitignore 里必须有 .env.local、.env.*.local
以为 curl 通前端也该通对着「接口没问题」四个大字怀疑人生curl 无 CORS 约束；「curl 通、浏览器挂」先查 CORS
把预检 OPTIONS 当重复请求Network 两枪同 URL，误以为代码发了两次非简单请求浏览器自动先发 OPTIONS 探路，属正常
Go 字段缺 json tag前端字段 undefined，Preview 里全是大写键结构体每个对外字段都写 `json:"camelCase"`
以为 preview 一定跨域 / 改了 preview.proxy 没反应在 preview 里请求照样 200，就下结论「Vite 偷偷反代了」；或配了 preview.proxy 却发现两个 target 都像是生效了事实是 preview.proxy 未配置时默认继承 server.proxy，显式写了就整份替换（不是逐键合并）。改 vite.config 后重新跑 npm run preview 再看
改了 vite.config 没重启proxy「配了没反应」config 与 .env 变更都以重启为准，终端日志里看 re-start 提示
挪目录时 mv goblog goblog/backend报 cannot move a directory to its own subdirectory，或者真的套娃进去先 mkdir goblog.tmp 当临时壳，搬完再 mv goblog.tmp goblog 改名
归置后 .env 没跟着进 backend/启动即 配置加载失败（第 4 周的 config 读不到 JWT_SECRET）.env 按当前工作目录读取：它必须和 go run ./cmd/server 同在 backend/；.env.example 也一起放那边
归置后首次提交前没看 git statusbackend/.env 或 frontend/node_modules 进了仓库，仓库体积爆掉、密钥上公网git add . 之前先 git status --short | head；已进的用 git rm --cached <路径> 撤下再提交（W1D5 讲过），并立刻换掉那把密钥

今日名词卡

术语一句话解释
同源策略浏览器规定：协议+域名+端口三者全同才算同源，跨源的 JS 请求默认被拦
CORS跨源资源共享：服务端用一组响应头「发通行证」，浏览器验过才把响应交给 JS
预检请求（preflight）非简单请求前浏览器自动发的 OPTIONS 探路枪，问「待会用这方法这头允许吗」
反向代理Nginx/Vite 在服务端代收请求转给后端，对浏览器伪装成同一个源；绕 CORS 的正统姿势
内容 hash 文件名构建产物名里的 -a1b2c3：内容变名字变，让 CDN/浏览器缓存自动失效更新
monorepo（单仓多包）前后端放同一个 Git 仓库的两个子目录（goblog/{backend,frontend}）：一次 clone 就能跑全套，Docker/Nginx 的路径也只需写一份
构建上下文（build context）docker build 交给守护进程的那个目录；上下文圈多大，镜像就背多大——这就是第 7 周要求后端单独成目录的原因
