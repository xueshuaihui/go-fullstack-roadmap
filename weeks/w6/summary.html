卡点复盘：这周最容易翻车的四件事

1. token 到底存哪：localStorage vs cookie 的权衡

本周选择 localStorage：简单、天然免 CORS 携带问题、与「Authorization 头」的后端契约一致。代价是 XSS（页面注入脚本）可以直接读走它；cookie + HttpOnly 能防这一手，但要配 CSRF 防御、且和纯 JSON API 的气质不合。学习项目用 localStorage 是合理妥协，但要能说出这笔账：任何面试问「为什么不用 HttpOnly cookie」，答案就是这两段的对照。无论存哪，代码里真相源只能有一个——本项目是 localStorage，React state 只是它的展示副本。

2. 闭包陷阱：拦截器与 useEffect 拿到旧 state

两个案发现场：①有人把「当前是否登录」写成拦截器里引用的 React state——模块顶层代码永远读到挂载那一刻的旧值；②useEffect 里 setPage(1) 后又用闭包里的旧 page 发请求。共同解法：需要「最新值」的逻辑要么走同步真相源（localStorage / ref），要么把它放进依赖数组让 effect 重建。day4 拦截器只用 localStorage、day2 列表把防抖值进依赖，都是在还这笔债。

3. 跨域：报错三连各查各的

复盘口径（day5 排查表的浓缩）：缺 Access-Control-Allow-Origin → 后端中间件没挂或 origin 白名单不匹配；红色 OPTIONS → 预检没被应答，检查 Allow-Methods/Allow-Headers 是否含 Authorization；credentials 与 * 冲突 → 要么关 withCredentials（我们用 Bearer 头本来就不需要），要么精确写 origin 并加 Allow-Credentials。开发期终极答案永远是「走 proxy 让它不跨域」，生产期答案永远是「Nginx 同源」。

4. StrictMode 双请求：先辨真假再动手

React 18 开发模式下 StrictMode 故意挂载→卸载→再挂载，用来暴露不可清理的副作用，副作用就是每个 useEffect 请求在 Network 里出现两次。判别：只在 5173/开发模式出现、build 后消失 → 是 StrictMode，不用管；两种模式下都翻倍 → 是你的依赖数组或事件绑定真漏了。最忌讳的应对是给取数 hook 加全局防重锁——把体检仪的 beep 声当成火灾警报处理。

本周沉淀的三条工程直觉

1. 契约先行。一切联调问题的尽头都是「{code,message,data}、错误码、camelCase 字段、双 token」这份契约。先 curl 后前端，先对齐再 debug。

2. 异步三件套常挂嘴边：竞态、三态、重试。ignore 守卫、loading/error/empty、401 静默刷新——这三样写熟了，你的前端才算「接得住真实网络」。

3. 前端做的权限都是体验，后端做的才是安全。守卫、按钮隐藏、redirect 校验，每一样都以「后端还会再拦一次」为前提。这句话带到第 8 周做 RBAC 依然成立。
