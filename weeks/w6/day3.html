课前须知：三个写接口的契约

1. 全部需要登录。请求头带 Authorization: Bearer <accessToken>（昨天的拦截器已自动做）。不带或过期返回 401——今天先手动保证 localStorage 里有有效 token，静默刷新明天补。

2. 创建与编辑的请求体一致。{ title, summary, content, coverImage }；authorId 由后端从 token 里取，前端不传也不能传——这是权限的第一道设计。

3. 权限后端说了算。非作者 PUT/DELETE 会收到 403 + code:1003（无权限）。前端做作者判断只是「不让用户点了挨揍」，真正的守门员永远是后端。

知识讲义

路由顺序有讲究：/post/new 必须排在 /post/:id 前面。否则 /post/new 会被 :id 匹配走，详情页拿着 id="new" 去请求。react-router v6 按「特异性」排序能兜底一部分，但请显式保持这个书写顺序，别赌。

2. 编辑器：textarea + Markdown 原文，不引重库

市面上 TipTap / Slate / wangEditor 都很好，但学习项目引它们等于给自己加两天的未知数。本周先「textarea 写 Markdown 原文，详情页用 pre 展示原文」，把精力留给联调本身；想要所见即所得，第 8 周再加。

js// src/api/article.js 追加三个写函数
export const createArticle = (data) => http.post('/articles', data)
export const updateArticle = (id, data) => http.put(`/articles/${id}`, data)
export const deleteArticle = (id) => http.delete(`/articles/${id}`)

3. Editor.jsx：模式判断 + 回填 + 提交（核心 90 行）

jsx// src/pages/Editor.jsx
import { useEffect, useRef, useState } from 'react'
import { useNavigate, useParams } from 'react-router-dom'
import { getArticle, createArticle, updateArticle } from '../api/article'

const EMPTY = { title: '', summary: '', content: '', coverImage: '' }

export default function Editor() {
  const { id } = useParams()          // /post/new 时 id 是 undefined
  const isEdit = Boolean(id)
  const [form, setForm] = useState(EMPTY)
  const [loading, setLoading] = useState(isEdit)
  const [busy, setBusy] = useState(false)
  const [err, setErr] = useState('')
  const navigate = useNavigate()
  const dirtyRef = useRef(false)     // 用户开始打字后置 true，防回填覆盖（见坑表）

  // —— 编辑模式：拉详情回填表单 ——
  useEffect(() => {
    if (!isEdit) return
    let ignore = false
    getArticle(id)
      .then((a) => {
        if (ignore || dirtyRef.current) return // 回填要认用户已输入的吗？不认，但 ignore 防卸载后 setState
        setForm({ title: a.title, summary: a.summary, content: a.content, coverImage: a.coverImage })
        setLoading(false)
      })
      .catch((e) => { if (!ignore) { setErr(e.message); setLoading(false) } })
    return () => { ignore = true }
  }, [id, isEdit])

  const onChange = (e) => {
    dirtyRef.current = true
    setForm({ ...form, [e.target.name]: e.target.value })
  }

  const onSubmit = async (e) => {
    e.preventDefault()
    setErr('')
    if (!form.title.trim() || !form.content.trim()) return setErr('标题和内容不能为空')
    setBusy(true)
    try {
      const data = isEdit ? await updateArticle(id, form) : await createArticle(form)
      navigate(`/post/${data.id || id}`) // 成功后跳详情，跳转策略见第 6 节
    } catch (e2) {
      setErr(e2.message) // 「标题长度超限」等后端校验原样展示
    } finally {
      setBusy(false)
    }
  }

  if (loading) return <p>回填中…</p>

  return (
    <form onSubmit={onSubmit} style={{ maxWidth: 640, margin: '24px auto', display: 'grid', gap: 10 }}>
      <h2>{isEdit ? '编辑文章' : '写新文章'}</h2>
      <input name="title" placeholder="标题" value={form.title} onChange={onChange} />
      <input name="summary" placeholder="一句话摘要" value={form.summary} onChange={onChange} />
      <input name="coverImage" placeholder="封面图 URL（可空）" value={form.coverImage} onChange={onChange} />
      <textarea name="content" rows={15} placeholder="支持 Markdown 原文" value={form.content} onChange={onChange} />
      {err && <p style={{ color: '#f87171' }}>{err}</p>}
      <button disabled={busy}>{busy ? '提交中…' : isEdit ? '保存修改' : '发布'}</button>
    </form>
  )
}

新建模式连请求都不用发，初始态就是 EMPTY；编辑模式多一个 loading 门闩，回填没完成前渲染「回填中…」而不是空表单——否则用户对着空表单先打了两字，回填一到又被覆盖，这就是本节最大的坑。

4. 删除：二次确认从 window.confirm 起步

jsx// src/pages/ArticleDetail.jsx 里加一个处理函数
const onDelete = async () => {
  const ok = window.confirm(`确定删除《${article.title}》？此操作不可撤销`)
  if (!ok) return              // 取消：什么都不发生
  try {
    await deleteArticle(article.id)
    navigate('/')             // 删除后详情页已不存在，回列表
  } catch (e) {
    alert('删除失败：' + e.message) // 比如 token 过期、并发被作者本人先删了
  }
}

window.confirm 丑但零成本，学习项目完全够用。想要样式可控、可测试，就自己写一个受控弹窗组件——下面第 4.5 节给你一个最小可用版，列进本周选做。

4.5 选做：自研 ConfirmDialog（受控组件一次写对）

jsx// src/components/ConfirmDialog.jsx —— 一个 state 控制显隐 + 两个回调
import { useState } from 'react'

export function ConfirmDialog({ title, danger = true, onOk }) {
  const [open, setOpen] = useState(false)
  const run = async () => {
    setOpen(false)
    try { await onOk() } catch (e) { alert(e.message) }
  }
  return (
    <>
      <button onClick={() => setOpen(true)}
        style={{ color: danger ? '#f87171' : 'inherit' }}>删除</button>
      {open && (
        <div style={{ position: 'fixed', inset: 0, background: 'rgba(0,0,0,.5)',
          display: 'grid', placeItems: 'center' }}>
          <div style={{ background: '#fff', padding: 24, borderRadius: 12, maxWidth: 360 }}>
            <h3>{title}</h3>
            <button onClick={() => setOpen(false)}>取消</button>
            <button onClick={run} style={{ marginLeft: 8, color: '#fff', background: '#dc2626' }}>
              确定删除
            </button>
          </div>
        </div>
      )}
    </>
  )
}
// 用法：<ConfirmDialog title={`确定删除《${article.title}》？`} onOk={() => deleteArticle(article.id)} />

前端隐藏 ≠ 权限控制。懂 DevTools 的人手敲 /post/123/edit 照样能进编辑页、照样能发 PUT 请求——但后端会回 403。所以两层都要：前端判断给正常用户顺畅体验，后端判断给恶意请求兜底。今天的验收之一就是替别人验证他 403。

6. 成功之后：跳转与「列表为什么要刷新」

提交/删除成功后跳回哪里？跳回去列表还是旧数据怎么办？三个方案摆平了选：

方案写法优点代价 / 适用
A. 回上一页navigate(-1)一行代码，从哪来到哪去用户直接打开编辑器 URL 时 -1 会退出网站；且回到列表后是缓存前的旧数据（组件没重新挂载，useEffect 不会再跑）
B. 跳固定路由 + 列表自己重新拉navigate('/?t=' + Date.now())，列表把 searchParams 里的 t 加进 useEffect 依赖数据必新，URL 可分享多一个时间戳参数，略脏；本周推荐，简单可靠
C. 状态提升 / 全局 store列表数据提到 App 或引 Zustand / React Query，写操作直接改缓存（乐观更新）体验最好，业界正解学习成本最高；第 8 周或以后换 React Query 再做
jsx// 方案 B 的列表端配套改动（ArticleList.jsx 加两行）
const [searchParams] = useSearchParams()
const stamp = searchParams.get('t') // 编辑器成功后 navigate('/?t=...') 带来的

useEffect(() => { /* …原来的取数… */ }, [page, debouncedKeyword, stamp])
// stamp 一变 = 强制重新拉取，新发的文章立刻出现在第一页
jsx// 方案 A 现场复现「为什么不够用」（花 2 分钟体验一次胜过读十遍）：
// 1) 从列表第 2 页点进文章 → 编辑 → 保存 → navigate(-1) 回列表：
//    组件复用未重新挂载，useEffect 不跑，你改的标题在列表里还是旧的；
// 2) 直接从地址栏打开 /post/new → 提交后 navigate(-1)：
//    历史栈里你没有上一页，浏览器干脆退出了你的网站。

结论：新建成功跳「该文章的详情页」（navigate(`/post/${data.id}`)，因为后端返回了创建好的 article，id 拿到即用）；删除成功跳列表并带 ?t=；编辑成功跳详情页。别在 navigate(-1) 上省这一步，省了就会在「为什么我发的文章不在列表里」上花一小时。

练习 4：删前检查未保存修改（20 分钟）

利用第 3 节的 dirtyRef：在编辑页点浏览器返回或站内离开前，如果 dirtyRef.current 为 true 弹 confirm('有未保存修改，确定离开？')。做不动就先只在删除按钮旁加「重置草稿」二次确认，效果等价。

常见坑

坑现象正确姿势
回填竞态覆盖用户输入编辑页打开瞬间开始打字，详情响应回来后打的字没了回填完成前渲染「回填中…」不显示表单；或 dirtyRef 拦截晚到的回填
authorId 类型不对齐自己是作者却看不到按钮useParams/部分接口返回字符串，比较统一 Number()；或 String(a) === String(b)
PUT 忘拼路径 idhttp.put('/articles', ...) → 404 或打到创建接口update 必须 put(`/articles/${id}`)，Network 里先看 URL 再看 body
confirm 的返回值当布尔强校验if (confirm(...) === true) 在某些 polyfill 环境行为怪异confirm 返回布尔，直接 if (!ok) return 即可
成功后 navigate(-1) 数据是旧的回列表看不到刚发的文章，怀疑后端没存列表挂载时 useEffect 才跑；用方案 B 的 ?t= 强制刷新，或跳详情页
新建时把 user.id 塞进请求体后端忽略还好，若后端「信任前端 authorId」就是越权漏洞身份永远从 token 解，前端不传 authorId

今日名词卡

术语一句话解释
回填（hydrate form）编辑场景先把详情接口的数据灌进受控表单初始值
模式复用同一组件按路由参数决定新建/编辑，差异只体现在标题、按钮文案和提交函数
二次确认破坏性操作前拦一道（confirm 或自研弹窗），取消即完全不发请求
乐观更新不等后端确认先改本地 UI，失败再回滚；需要全局状态管理配合，本周不做只了解
受控弹窗显隐由组件 state 决定的自研确认框，替代 window.confirm，可样式化可测试
草稿保护（dirtyRef）用 ref 记录「用户是否已输入」，晚到的回填/离开动作据此让路，防覆盖打字内容
越权（IDOR）改别人的资源：前端藏按钮是体验，后端校验 token 身份才是安全
