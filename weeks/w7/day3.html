完整 Compose 编排

昨天你用 docker network create 手工串了三个容器，敲了十几行参数——今天把它们收敛成一个文件、一条命令。第 3 周你只会"用 compose 起一个 MySQL"，今天你要能读懂并默写一份生产可用的三服务编排：依赖顺序、健康检查、密钥注入、网络 DNS，一个都不少。

课前须知

先用你熟的东西类比：docker-compose.yml 干的活相当于 package.json 的 scripts 再叠一份 pm2.json——"起几个进程、各读哪些环境变量、谁要等谁、崩了要不要自动拉起"全部写进一个受版本控制的文件，一条命令起全栈。差别只有一条：compose 管的单位是容器，每个容器有自己的 localhost 和自己的网卡，所以"我此刻在哪台机器上"这件事必须想清楚（第 2 节）。

The container name "/goblog-mysql" is already in use by container …。具体命令与输出示例在练习 1 的第 0 步，先跑它再写 yml。

今天的三服务文件不是终点：D4 会加一个 migrate（profiles: [tools]，平时不起、只在迁移时手动起），D5 上云再加一个 caddy（自动 HTTPS）。编排文件是会长大的，所以它才值得进 Git。

1. docker-compose.yml 全文（可直接抄用）

name: goblog                             # 项目名：决定网络名 goblog_default、卷名 goblog_mysql-data

services:
  # ==================== ① 数据库：这一段键名由 mysql 镜像规定 ====================

      TZ: Asia/Shanghai                   # 容器内时区；字符集参数在下面的 command 里
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
    volumes:
      - mysql-data:/var/lib/mysql         # named volume：删容器不删数据
    healthcheck:
      # ${...} 由 compose 在宿主机渲染期替换成真实值（第 3 节讲透这一步）
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-u", "root", "-p${MYSQL_ROOT_PASSWORD}", "--silent"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s                   # MySQL 首次初始化很慢，前 30 秒失败不计数

    build:
      context: ./backend                  # 本地构建；image 给构建产物打 tag
    image: goblog-backend:local
    container_name: goblog-backend
    restart: unless-stopped
    environment:
      PORT: ${PORT:-8080}
      GIN_MODE: release                   # 生产形态；开发在 override 里覆盖成 debug
      AUTO_MIGRATE: ${AUTO_MIGRATE:-true} # 今天这份代码还不读它，D4 把它变成开关

      DB_PORT: "3306"                    # 注意要加引号：不加也能跑，但见第 4 节末尾的坑
      DB_USER: ${DB_USER:-goblog}
      DB_PASS: ${DB_PASS:?请在 .env 里设置 DB_PASS}
      DB_NAME: ${DB_NAME:-goblog}
      JWT_SECRET: ${JWT_SECRET:?请在 .env 里设置 JWT_SECRET}
      JWT_REFRESH_SECRET: ${JWT_REFRESH_SECRET:?请在 .env 里设置 JWT_REFRESH_SECRET}

      mysql:
        condition: service_healthy        # 等 mysql 的 healthcheck 通过才启动我

      interval: 15s
      timeout: 5s
      retries: 5

字段要点
build vs image只有 image = 从仓库拉现成镜像（mysql）；build = 从本地 Dockerfile 构建。两者可同写：build 的产物打上 image 这个 tag。D1/D2 里你用 docker build -t goblog-api:0.1 … 手动打 tag（goblog-api / goblog-web 这两个名字只活在练习里，今天起不再出现），现在交给 compose 打：全周唯一口径是 goblog-backend:local 与 goblog-frontend:local，D4 迁移、D5 上线与备份脚本都按这一对写，不要再混用 :0.1 / :0.2。W7D5 服务器上就是直接 up -d --build 现场构建，不需要镜像仓库账号
${VAR} / ${VAR:-默认} / ${VAR:?文案}compose 自动读取同目录 .env 做变量替换（第 4 节会精确讲"什么时候替换"）。密钥进 .env（不进 Git），编排进 yml（进 Git），从此密码不出现在任何提交里
两段时间的键名不能串MYSQL_* 是 mysql 镜像自己读的（首启建库建用户用），DB_* 是 你的 Go 程序读的。本项目只有一份事实：MYSQL_DATABASE/USER/PASSWORD 直接引用 DB_NAME/DB_USER/DB_PASS，额外只有 MYSQL_ROOT_PASSWORD 是 root 专用。别名 MYSQL_DSN / SERVER_PORT / DB_PASSWORD 一律不用
ports 只给 frontendbackend:8080、mysql:3306 故意不映射：内网服务名互访根本不需要发布端口。少暴露一个端口少一分被扫描爆破的风险——这是今天最重要的安全观
container_name写死名字后，docker logs goblog-backend、D4 的 docker compose exec mysql …、D5 的备份脚本都有稳定的靶子。代价是同名容器全局唯一（所以课前须知里要先清场）

2. 经典坑正解：服务间网络 DNS，DSN 主机名为什么是 mysql

compose 默认把同一文件里的所有服务挂进一个 bridge 网络（goblog_default），并内置 DNS 服务器：服务名 = 容器名别名 = 可直接解析的主机名。于是 backend 里写 tcp(mysql:3306)，Docker DNS 把 mysql 解析成数据库容器的内网 IP。

localhost 三连击（本周报错率第一名）：① 在 backend 容器里，localhost:3306 指向 backend 自己——那里没有 mysqld，日志刷 dial tcp 127.0.0.1:3306: connect: connection refused；② 在宿主机 curl 容器内端口也没用（没映射就不存在）；③ 图形化工具从宿主机连库，则要反过来用 127.0.0.1:3306 且先在 override 里映射端口。判断口径只有一句话：我此刻在哪个网络命名空间里？

动手验证 DNS 机制（三条命令看穿黑盒，都在容器起好之后跑）：

shell# ① 钻进 backend 容器里问一句：mysql 是谁？（busybox 自带 nslookup，alpine 镜像里一定能用）
$ docker compose exec backend nslookup mysql
Server:		127.0.0.11
Address:	127.0.0.11:53

Name:		mysql
Address: 172.18.0.2                       # ← 127.0.0.11 是 Docker 内置 DNS，它把服务名换成了容器 IP ✔

# ② 从容器外核对：这个 IP 确实是那个数据库容器
$ docker inspect goblog-mysql --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
172.18.0.2                                # ← 与上面对得上 ✔（注意是 goblog-mysql，中划线，compose 起的容器名以 container_name 为准）

# ③ 谁和谁在同一张网上
$ docker network inspect goblog_default --format '{{range .Containers}}{{.Name}} {{end}}'
goblog-mysql goblog-backend goblog-frontend  # ← 三兄弟同网 ✔

如果你的 ③ 少了一个名字，多半是那个容器没起来或者 yml 里给它写了 network_mode / networks 覆盖了默认网络。服务名解析不了的典型报错：dial tcp: lookup mysql on 127.0.0.11:53: no such host——先回去看 mysql 那个 service 的名字拼写。

3. 启动顺序：裸 depends_on 与 service_healthy 的差别

裸 depends_on（数组式）只保证"MySQL 容器被创建并启动"再启动我。而 MySQL 容器起来 ≠ mysqld 可用——首次初始化要 20~40 秒，这期间 TCP 能连上但认证/查询全失败，backend 连库报错直接退出。这就是第 3 周你见过"backend 崩一次、第二次才活"的原因。

正解是健康检查驱动的依赖：depends_on.mysql.condition: service_healthy，它会轮询 mysql 自己的 healthcheck，真的能 ping 通了才放行 backend。frontend 对 backend 用数组式即可（nginx 起不来无非 502，不需要强等）。

healthcheck 五件套含义
test容器内执行的探测命令，退出码 0 即健康。两种写法：CMD（数组＝直接 exec 那个二进制，没有 shell 参与，所以命令里不能出现 $VAR、&&、重定向）、CMD-SHELL（整条字符串丢给容器内的 /bin/sh -c 跑，能用 shell 的一切语法）。裸数组等价于 CMD。要点见下面 3.1
interval / timeout每 10s 探测一次 / 单次超 5s 算失败
retries连续失败 N 次才判 unhealthy
start_period启动宽限期，此期间失败不计数（MySQL 必需，否则初始化就被判死刑）

3.1 healthcheck 里的 ${VAR} 到底是谁替换的

这是本课第 4 个"变量在哪台机器上展开"的坑，说清楚只有一句话：compose 文件里所有 ${...}，无论写在 environment: 还是 healthcheck.test 里，都是 docker compose 命令在宿主机上解析 YAML 时替换掉的；等容器真正跑起来，命令里已经看不到 $ 了。

所以 test: ["CMD", "mysqladmin", "ping", "-u", "root", "-p${MYSQL_ROOT_PASSWORD}", "--silent"] 不需要 shell 也能拿到密码——compose 早就把它换成了 -p你的真实密码。验证给你看：

shell（都是实测输出，容器起来后自己跑一遍）# ① 容器配置里存的是"替换完"的命令：-p 后面已经是一串字面量密码，$ 没了
$ docker inspect goblog-mysql --format '{{json .Config.Healthcheck.Test}}'
["CMD","mysqladmin","ping","-h","127.0.0.1","-u","root","-pf0b8c2d94ae71365d8c4f2a90b7e5d11","--silent"]

# ② 最近几次探测的原始记录（Docker 只留最后 5 条，顺序是老的在前）
$ docker inspect goblog-mysql --format '{{json .State.Health}}' | head -c 300
{"Status":"healthy","FailingStreak":0,"Log":[{"Start":"2026-09-30T07:58:18.586…Z","End":"2026-09-30T07:58:18.655…Z","ExitCode":0,"Output":"mysqladmin: [Warning] Using a password …\nmysqld is alive\n"

这段输出里藏着三个实测出来的事实，比"healthcheck 会探测"这种话有用得多：

  • --silent 并没有真的安静：Output 里照旧有 mysqld is alive 和一句"命令行里带密码不安全"的警告。Docker 判定健康只看 ExitCode，Output 只是给你看的，所以别把 --silent 当"隐身"。
  • 密码写错时 mysqladmin ping 打印 Access denied，但 ExitCode 仍然是 0（我把密码换成 WRONG 实测过）——它只证明"mysqld 在监听"。
  • 只有连不上时才退 1：初始化那 20 多秒里日志能看到一串 ExitCode:1，这正是 start_period 存在的意义。

那 CMD-SHELL 什么时候必须用？① 命令里要写 &&、管道、重定向；② 你想让容器内的环境变量来展开（而不是宿主机 .env 的那份）。想让健康状态连认证一起验，正好两个都用上：

docker-compose.yml（healthcheck 的 YAML 块式写法：想换掉第 ① 段的 ping 就用这份）    healthcheck:
      test:
        - CMD-SHELL
        - mysql -u"$$MYSQL_USER" -p"$$MYSQL_PASSWORD" -e "SELECT 1" "$$MYSQL_DATABASE" >/dev/null   # ← 两个 $ 才留到容器里展开
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s
shell（同一条命令在容器里手动跑，看退出码）$ docker compose exec mysql sh -c 'mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" -e "SELECT 1" "$MYSQL_DATABASE" >/dev/null; echo exit=$?'
mysql: [Warning] Using a password on the command line interface can be insecure.
exit=0                                     # 密码对 ✔
$ docker compose exec mysql sh -c 'mysql -u"$MYSQL_USER" -p"WRONG" -e "SELECT 1" "$MYSQL_DATABASE" >/dev/null; echo exit=$?'
mysql: [Warning] Using a password on the command line interface can be insecure.
exit=1                                     # 密码错 ✔ → 换成探针命令后，.env 里改错密码会立刻 unhealthy

口诀：单 ${VAR} = 宿主机渲染期由 compose 替换；双 $$VAR = 原样下发，由容器里的 shell 替换。写错成一对的后果很具体：$$ 用在 environment: 段里，容器会拿到字面量 $MYSQL_ROOT_PASSWORD 当密码；单 $ 用在你以为"容器会展开"的地方，宿主机 .env 里没这个键时就被替换成空串，探测命令变成 -p --silent。今天本课的编排用第一段的 ping 版本就够（它只负责"别在 mysqld 监听前放 backend 进去"），密码对不对由 backend 自己证明——它连不上就退出、状态变 Restarting，练习 3 会亲眼看到。

各服务的探测命令选择：MySQL 用 mysqladmin ping（或上面那条认证版）；有 shell 的发行版镜像（alpine/debian）用 wget -qO-；scratch 镜像连 wget 都没有，只能把探测放到编排层（depends_on 用 service_started），或者在 Dockerfile 里 COPY 一个自己写的小探针二进制进镜像——这也是 W7D1 推荐 alpine 的原因之一。

4. .env 与变量注入

.env 里只有两类键：后端读的 9 个（第 4 周 internal/config 就那几个，全周口径一致）和 mysql 镜像读的 1 个（root 密码）。其余 MYSQL_* 在 yml 里已经指向第 1 段的 DB_* 了，不要在这里重复写一遍——一处事实只写一次。

shell（在 goblog/ 根目录整块抄；此文件绝不进 Git）$ ROOTPW=$(openssl rand -hex 24)     # ① 先在宿主机把 4 个随机串生成到 shell 变量
$ DBPASS=$(openssl rand -hex 24)
$ JWTACC=$(openssl rand -base64 32)
$ JWTRTF=$(openssl rand -base64 32)
$ cat > .env <<EOF                   # ② 定界符不带引号 → 这十几行里的 $DBPASS 等在宿主机就展开完
# ========== 第 1 段：Go 后端读的键（与 internal/config 一一对应） ==========
PORT=8080
GIN_MODE=release
AUTO_MIGRATE=true
DB_HOST=mysql
DB_PORT=3306
DB_USER=goblog
DB_PASS=$DBPASS
DB_NAME=goblog
JWT_SECRET=$JWTACC
JWT_REFRESH_SECRET=$JWTRTF

# ========== 第 2 段：mysql 镜像自己的键（只有 root 这一个） ==========
MYSQL_ROOT_PASSWORD=$ROOTPW
EOF
$ grep -v '^#' .env | grep -c '='   # ③ 数一下非注释行数 = 键的个数
11                                 # PORT/GIN_MODE/AUTO_MIGRATE + DB_×5 + JWT_×2 + MYSQL_ROOT_PASSWORD ✔
$ grep '^DB_PASS=' .env           # ④ 抽查那个来自 shell 变量的键：应该是 48 位十六进制，而不是字面量 "$DBPASS"
DB_PASS=a3f19c7b8d2e4451c0b7e9f215ad6c338be0f47a2d19c6e5

为什么 .env 内容里一个行尾注释都没有？因为 # 说明 跟在值后面（前面有空格）会被 compose 当行注释截掉后半句（本段末尾有实测表）。上一课 docker run --env-file 用 heredoc 时我们特意把注释写满，是因为那份文件由 Docker 逐行读成环境变量、规则不同；今天这份是 compose 插值用的，规则是"一行就是一个 KEY=value，多余的字一个都别写"。要解释，写在 .env.example 里。

再手写一份进 Git 的模板：键名、分段注释全保留，值的位置留空并写清怎么生成。队友 cp .env.example .env 后照提示填值就能起项目——解释写在 example 里、值只活在 .env 里。注意注释一律独占一行写在键的上面（这个文件会被复制成 .env，行尾注释不合规）：

.env.example（进 Git）# ========== 第 1 段：Go 后端读的键（与 internal/config 一一对应，别改名） ==========
# PORT：后端监听端口，compose 与 frontend/nginx.conf 都引用它
PORT=8080
# GIN_MODE：release（生产形态）/ debug（本地看日志）
GIN_MODE=release
# AUTO_MIGRATE：D4 起才生效，true 只给本地开发，生产必须 false
AUTO_MIGRATE=true
# DB_HOST：在 compose 网络里是服务名 mysql；本机裸跑后端才写 127.0.0.1
DB_HOST=mysql
DB_PORT=3306
# DB_USER：mysql 镜像首启会自动建这个普通用户（第 2 段引用同一个值）
DB_USER=goblog
# DB_PASS：自己生成 → openssl rand -hex 24（只用字母数字，零转义）
DB_PASS=
DB_NAME=goblog
# JWT_SECRET / JWT_REFRESH_SECRET：各跑一次 openssl rand -base64 32，两把必须不同
JWT_SECRET=
JWT_REFRESH_SECRET=

# ========== 第 2 段：mysql 镜像自己的键（另外三个 MYSQL_* 在 yml 里复用第 1 段） ==========
# MYSQL_ROOT_PASSWORD：openssl rand -hex 24，只用于建库、D4 迁移、D5 备份
MYSQL_ROOT_PASSWORD=
shell$ echo '.env' >> .gitignore          # 没有 .gitignore 就先 touch 一个
$ git status --short
?? .env.example
?? docker-compose.override.yml
?? docker-compose.yml                # 三个新文件都该被 Git 看见；唯独没有 .env ✔

两条规则分清（本课第 5 次强调"变量在哪台机器上展开"）：yml 里的 ${VAR} 是 compose 在渲染阶段、在你的终端进程里做的文本替换（读的是 yml 同目录的 .env，也接受你在命令最前面临时写 DB_PASS=xxx docker compose up 那种进程环境变量，进程变量优先于 .env）；替换完成后，容器里的进程才通过 os.Getenv 读到最终值。所以"改了 .env 但 up 了个没变化的容器"这事是有解的：compose 只在执行 up 的那一刻读 .env，改完必须重新 up -d（改了 yml 还要 --build）。

变量没定义会怎样？两种写法两种命运，都给你实测输出：

shell# 写法一：${MYSQL_ROOT_PASSWORD}  —— 缺键时只是警告一声，塞个空串继续（最阴）
$ docker compose config
time="2026-09-30T15:52:37+08:00" level=warning msg="The \"MYSQL_ROOT_PASSWORD\" variable is not set. Defaulting to a blank string."
$ docker compose up -d mysql && sleep 3 && docker compose logs mysql --tail 5
2026-09-30 07:56:30+00:00 [ERROR] [Entrypoint]: Database is uninitialized and password option is not specified
    You need to specify one of the following as an environment variable:
        - MYSQL_ROOT_PASSWORD
        - MYSQL_ALLOW_EMPTY_PASSWORD
        - MYSQL_RANDOM_PASSWORD
# 空串密码 → mysql 直接退出 → healthcheck 永远不过 → backend 卡在 dependency failed to start

# 写法二：${MYSQL_ROOT_PASSWORD:?请在 .env 里设置 MYSQL_ROOT_PASSWORD} —— 当场拒绝，省掉上面这一整轮排查
$ docker compose config
error while interpolating services.mysql.environment.MYSQL_ROOT_PASSWORD: required variable MYSQL_ROOT_PASSWORD is missing a value: 请在 .env 里设置 MYSQL_ROOT_PASSWORD
$ echo $?
1                                     # ← 非 0 退出码，脚本里也拦得住

空串只是开始，另一半是这个：mysql 镜像只在数据目录为空时执行"建库建用户设密码"。所以等你 named volume 已经初始化过、再回头改 .env 里的 DB_PASS，库里那个用户的密码不会跟着变，backend 于是 Access denied for user 'goblog'@'…'——"我明明改了密码"就是不改。开发期最省事的解法是连卷一起清（数据全没，想清楚再按回车）：

shell$ docker compose down -v              # 带 -v：连 named volume 一起删，下次 up 才是"首启"
$ docker compose up -d --build
# 不想删数据就得手动改密：先进容器、让容器里的 sh 展开它自己的环境变量（引号位置是关键，别照抄错）
$ docker compose exec mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'
mysql> ALTER USER 'goblog'@'%' IDENTIFIED BY '新的 DB_PASS 值';
mysql> EXIT
$ docker compose restart backend       # 后端拿着新密码重连一次

这条命令的引号值得说一句：外层单引号让宿主机 shell 原样把 $MYSQL_ROOT_PASSWORD 送进容器，容器里的 sh 再用它自己那份环境变量展开——和 3.1 里 $$VAR 是同一个原理。D4 迁移、D5 备份全靠这个姿势，今天先练熟。

把 ${VAR:?文案} 用成肌肉记忆：密钥类一律 :?，可选项一律 :-默认值。报错文案写中文、写清"去哪儿改"，比英文 required variable 友好十倍——这是你写给三个月后的自己的注释。

.env 的解析规则也实测一遍（这些行为和昨天的 docker run --env-file 不完全一样，别凭感觉推）：

.env 里写compose 渲染出的值结论
A="quoted"quoted首尾引号被剥掉；而 docker run --env-file 会连引号一起当值（D1 实测）。所以别指望加引号能躲转义
B=mid#hashmid#hash# 紧跟值、前面没空格 → 不算注释，安全
C=pre # afterpre空格 + # → 后半句被当行注释吃掉。密码里带这个组合就等着连不上库
D=val$dollarval（外加一条 warning）值里的 $ 会被再做一次变量展开，等于给自己埋二次替换的雷

结论照旧省事务实：数据库与 root 密码只用 openssl rand -hex 24（纯 0-9a-f，上面四个雷一个都踩不到）；JWT 用 -base64 32 没问题（可能含 + / =，它们不在雷区里），但别把 base64 串拿去当 MySQL 密码。

4.1 一处真实的历史包袱：DB_PORT 现在没人读

第 4 周写 config.Load() 时端口是硬编码在格式串里的，所以今天 .env 里那行 DB_PORT=3306 其实没人消费。改一行把它接上（顺手，也保证以后换端口不会"改了没生效"）：

backend/internal/config/config.go（改 DSN 那一行）// 第 4 周原样：3306 写死在格式串里
c.DSN = fmt.Sprintf("%s:%s@tcp(%s:3306)/%s?charset=utf8mb4&parseTime=True&loc=Local",
    getEnv("DB_USER", "root"), dbPass, getEnv("DB_HOST", "127.0.0.1"), getEnv("DB_NAME", "blog"))

// 第 7 周改成：端口也走 DB_PORT，默认值仍是 3306
c.DSN = fmt.Sprintf("%s:%s@tcp(%s:%s)/%s?charset=utf8mb4&parseTime=True&loc=Local",
    getEnv("DB_USER", "root"), dbPass,
    getEnv("DB_HOST", "127.0.0.1"), getEnv("DB_PORT", "3306"),
    getEnv("DB_NAME", "blog"))

参数个数从 4 变 5，格式串里的 3306 变成 %s——顺序千万别排错，Go 的 Sprintf 不会替你检查语义，DSN 拼歪了就是 unknown host 或者更诡异的 Access denied。改完在本地跑一遍确认没编译错、没参数漏：

shell$ cd backend
$ go vet ./...                           # 参数与 %s 不匹配时 vet 直接报：fmt.Sprintf format %s has arg 4 of wrong type
$ go build ./... && echo "编译通过 ✔"
编译通过 ✔
$ cd ..                                  # 回到 goblog/ 根目录：compose 的 build context、.env 都是按这个目录算的
$ docker compose build backend           # 改了 Go 代码就要重新构建镜像，up -d 不会替你热更新（第 6 节练习 1 见）

5. 开发 vs 生产：override 文件思路

base 文件保持"生产形态"，环境差异用叠加文件解决。compose 的合并规则：docker compose up 会自动加载 docker-compose.yml + docker-compose.override.yml；生产则显式指定，不走默认：

docker-compose.override.yml（开发专用，仓库里也提交它——里面没有密钥）services:
  mysql:
    ports:
      - "127.0.0.1:3306:3306"   # 只绑回环：本机能连库调试，公网扫不到（动手前先看 5.1）
  backend:
    environment:
      GIN_MODE: debug            # 覆盖 base 的 release：本地要看得懂启动日志
      AUTO_MIGRATE: "true"       # 开发期让 GORM 顺手补列；生产要置成 false（D4 讲为什么）
docker-compose.prod.yml（服务器上只放"差异"，绝不复制整份文件）services:
  backend:
    restart: always              # 机器重启必须自动拉起
    environment:
      AUTO_MIGRATE: "false"      # 生产只认迁移文件，不认 GORM 的"顺手补列"（D4）
    logging:
      driver: json-file
      options:
        max-size: "10m"          # 日志限量，防止刷爆系统盘
        max-file: "3"
  # 注意这里没有 mysql.ports：base 里本来就没映射，生产不加载 override，3306 天然不对外。
  # 想在 prod 里"清掉"某个字段必须写 ports: !reset []，写 ports: [] 是无效的（5.2 实测）。

两份文件怎么被合到一起——这条命令值得记住，它是一切"我明明改了 prod 文件"疑问的答案：

shell# 开发（本机）：自动合并 base + override，所以不用写 -f
$ docker compose up -d --build

# 生产（服务器）：显式两文件，顺序有意义——后出现的文件覆盖先出现的；不写 override 就等于没有
$ docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env up -d --build

# 合并结果不靠脑子想、只看渲染出来的最终配置（这里应该只看见 80 那一条）
$ docker compose -f docker-compose.yml -f docker-compose.prod.yml config | grep -B 2 -A 5 'ports:'
  frontend:
    image: goblog-frontend:local
    ports:
      - mode: ingress
        target: 80
        published: "80"
        protocol: tcp
# ← 全文只有 frontend 这一处命中：mysql 的 3306 在生产口径下根本不存在 ✔

原则：能合并、不复制。绝不维护两份完整的 compose 文件——那是一切"改了这边忘了那边"事故的温床。

5.1 把 3306 发布到本机之前，先看一眼这个端口现在归谁

第 3 周你已经跑过一个 MySQL 容器，不少同学宿主机上还常驻着 Homebrew MySQL 或 MySQL.app——端口只有一个 3306，撞上就是这句报错：

Bind for 127.0.0.1:3306 failed: port is already allocated

先查再动手（macOS / Linux 通用，输出示例都给你）：

shell$ lsof -nP -iTCP:3306 -sTCP:LISTEN        # macOS 自带；Linux 上若没装 lsof，用 ss -ltnp | grep 3306

mysqld   812  mysql  21u  IPv6  0x…        0t0        TCP    127.0.0.1:3306 (LISTEN)   # ← 宿主机自己的 mysqld

NAMES             PORTS
goblog-mysql      0.0.0.0:3306->3306/tcp            # ← 第 3 周起的 MySQL（那页的名字也可能是 golearn-mysql），今天就叫它 goblog-mysql，重名又占端口

本课口径写死，不留悬念：① 占端口的是旧容器（第 3 周或昨天 docker run 的）→ 按练习 1 第 0 步清掉，继续用 127.0.0.1:3306:3306；② 占端口的是宿主机常驻 MySQL（Homebrew / MySQL.app，你不想停它）→ 只改 override 那一行为 "127.0.0.1:3307:3306"，此后图形化工具连 3307，而 docker compose exec mysql … 那类命令完全不受影响（那是容器内网，永远 3306）。别发明第三种方案：改 base 文件、给 mysql 换 container_name、把 3306 发到 0.0.0.0，都是给未来的自己挖坑。

5.2 一个很容易想当然的合并规则：ports: [] 清不掉 base 的端口

很多人以为在 prod 文件里写 ports: [] 就能把 base/override 的映射清空。实测：不行——列表字段是追加合并，ports: [] 只等于"再追加零条"：

shell（base.yml 给 web 服务映射了 127.0.0.1:3306:3306，empty.yml 里写 ports: []）$ docker compose -f base.yml -f empty.yml config | grep -A 5 'ports:'
    ports:
      - mode: ingress
        host_ip: 127.0.0.1
        target: 3306                      # ← 还活着！ports: [] 白写
        published: "3306"

$ docker compose -f base.yml -f reset.yml config | grep -A 5 'ports:'
                                          # ← 一行都没有：reset.yml 里写的是 ports: !reset []

正解两个，按你的 Compose 版本选：

  • 要显式清空就用 !reset：ports: !reset []（Compose v2.24 起支持；先跑 docker compose version 确认，D5 的 prod 文件会再强调一次）。注意它是 YAML 自定义标签，所以 ! 前面不能加引号。
  • 更稳的工程做法：base 里根本不写端口映射（今天这份文件就是这样，mysql 没有 ports），只在 override 里加。生产用 -f docker-compose.yml -f docker-compose.prod.yml 时压根不加载 override，"生产不暴露 3306"于是天然成立，不需要任何 reset。把"发布端口"当成开发环境的特权，你就永远不会踩这条。

常见坑（新手 100% 会踩）

坑现象正确姿势
DSN 主机写 localhostbackend Restarting 循环，日志 dial tcp 127.0.0.1:3306: connection refused同网络一律用服务名；理解"容器里的 localhost 是它自己"（练习 3）
沿用别名键 MYSQL_DSN / SERVER_PORTcompose 起得一切正常，后端却连 127.0.0.1:3306（它没读到那串 DSN，用了默认值）只认第 4 周 config 读的那 9 个键；docker compose exec backend sh -c 'env | sort' 自查一遍
裸 depends_on 就完事首次冷启 backend 连不上还没初始化完的 MySQL依赖方 depends_on.condition: service_healthy + 被依赖方 healthcheck，二者缺一不可
.env 变量没定义只有一行 warning，接着 mysql 因空 root 密码直接退出、backend 永远起不来密钥类一律 ${VAR:?中文提示}；改完先 docker compose config --quiet
改了 .env 里的 DB_PASS 就当是改了密码Access denied for user 'goblog'@'…'，怎么重启都没用数据卷非空时镜像不再建用户：开发期 down -v 重来，或按第 4 节末尾 ALTER USER 改密
没清第 3 周的老容器和老卷port is already allocated，或者"健康地"连上一个装着 study_plan 的老库练习 1 第 0 步逐条走完：容器、网络、卷各确认一次
拿 mysqladmin ping 当"密码对不对"的探针密码写错照样 (healthy)，问题一路拖到 backend 才炸ping 只证明"在监听"；认证用 mysql -e "SELECT 1"（3.1 实测），或者交给 backend 自己崩给你看
密码里出现 空格 # 或 $行为诡异：配置"明明写了"却不生效数据库/root 密码只用 openssl rand -hex 24；别指望加引号，compose 会剥引号（第 4 节实测表）
给所有服务映射端口8080/3306 公网裸奔，等着被爆破只有需要外部访问的才 ports，而且绑 127.0.0.1；内网走服务名
用 ports: [] 想清掉 base 的映射prod 配置里端口还在，服务器 3306 对外裸奔列表是追加合并；要清用 !reset []（Compose v2.24+），或者按本课做法：base 里根本不写（5.2）
改了代码 up 了个"没变化"的站部署后跑的还是旧逻辑up -d --build；或先 docker compose build backend 再 up。周末总结页的卡点复盘专题
把 down 敲成 down -v整库数据没了down 只删容器和网络；-v 才删卷。D5 里 -v 是"彻底重置"级别的动作，敲之前先想三秒
