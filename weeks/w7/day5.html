知识讲义

1. 云服务器选购与开工准备

维度口径为什么
配置1 核 2G 起步够用，系统盘 ≥ 40GB，Debian 12 或 Ubuntu 22.04/24.04 镜像内存大头是 MySQL（约 500MB），backend 才 20–50MB，nginx/caddy 几十 MB
带宽按固定带宽 3–5Mbps 或按量计费均可本项目静态资源才 2MB，流量极小
地域就近选；一句话差异：中国大陆地域绑定域名对外提供 Web 服务需先完成 ICP 备案，海外/港澳台地域免备案但延迟略高未备案域名解析到大陆机器，80/443 会被运营商拦截
安全组放行 22（SSH）、80、443 三个入方向端口即可；3306、8080 不放行数据库和后端由 Nginx/Caddy 统一从 80/443 转发，直接暴露 = 被全网爆破

1G/2G 内存必做：加 swap。MySQL 冷启动和 docker build 编译 Go 都可能在瞬时打满内存，OOM 会直接杀掉 mysqld（表现：容器离奇 Restarting）。登录后先执行：

shell（root 执行，一次性）$ fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
$ echo '/swapfile none swap sw 0 0' >> /etc/fstab     # 开机自动启用
$ free -h                                               # 确认 Swap 行出现 2.0Gi

SSH 免密（macOS/Linux 本机执行；Windows 用 PowerShell 或后续全走网页终端）：

shell$ ssh-copy-id root@<你的服务器IP>     # 输一次密码，以后直接 ssh root@<IP>
$ ssh root@<你的服务器IP> 'hostname && date'   # 连通性验证

SSH 本身也是公网端口：买机时若选了"密码登录"，尽快改为本机公钥 + 关闭密码认证（/etc/ssh/sshd_config 里 PasswordAuthentication no 后 systemctl restart sshd）；22 端口同样有全网爆破。更稳妥的发行版自带的 fail2ban 或云控制台"仅允许我的 IP 段访问 22"都可以，学生项目至少做到密钥登录。

2. 安装 Docker 与 Compose 插件

官方一键脚本自动识别发行版、配好 apt 源与 systemd 服务（比"文档十一步"省事且不易错）：

shell（服务器上执行）$ curl -fsSL https://get.docker.com | sh
$ systemctl enable --now docker
$ docker --version          # Docker version 27.x
$ docker compose version    # Docker Compose version v2.x —— 官方脚本自带 compose 插件，注意是 docker compose 两个词，带空格

# 非 root 用户免 sudo（可选；用 root 部署可跳过）
$ usermod -aG docker $USER   # 重新登录生效

和第 3 周本机的区别：服务器上的 docker compose 是 v2 插件形态，命令与你熟悉的完全一致。旧文档里的 docker-compose（带横杠的 v1，Python 写的）已停止维护，见到就换掉。

3. 拉代码 + 生产 .env：弱口令是重灾区

shell$ mkdir -p /opt && cd /opt
$ git clone git@github.com:<你的用户名>/goblog.git   # HTTPS 仓库则用 https:// 地址 + Personal Access Token
$ cd goblog
$ cp .env.example .env && chmod 600 .env              # .env 权限收紧到只有 root 可读
$ openssl rand -base64 32                             # 现生成一个强随机串，下面多处要用
.env 项必改动作不改的下场
MYSQL_ROOT_PASSWORD / MYSQL_PASSWORD换成 openssl rand -hex 24 级别的随机串（纯十六进制，避开 YAML 特殊字符）公网 MySQL 弱口令几分钟内就会被扫描器爆破，轻则肉鸡、重则删库勒索——这不是吓唬，是全网常态
JWT_SECRET / JWT_REFRESH_SECRET各自 openssl rand -base64 32 现生成，两值必须不同沿用示例值 = 任何人可伪造任意用户的 token 直接登录
GIN_MODEreleasedebug 模式泄露堆栈路由信息、性能差
AUTO_MIGRATE删除或置 false（昨天加的开关）生产结构被代码"顺手"改动
DOMAIN（第 5 节 Caddyfile 会引用思想）你的真实域名HTTPS 签发对象错误

验证密钥没进 Git 的土办法但有效：git log -p | grep -i password 应该无输出（前提是你从第 4 周起就没提交过 .env；提交过的话历史里就有，需要换密钥而不仅是删文件）。

4. 首次上线与日常运维

shell（在 /opt/goblog）# 首次部署：按昨天的三步曲（migrate 建表），再全量起
$ docker compose --env-file .env up -d mysql
$ docker compose --env-file .env --profile tools run --rm migrate up
$ docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml up -d --build
$ docker compose ps                                  # 三服务 + healthy
$ curl -s -o /dev/null -w "%{http_code}\n" http://<服务器IP>/   # 先确认 200（还没有 HTTPS）

# ———— 日常四板斧 ————
$ docker compose logs -f backend --tail=50          # 追日志（Ctrl+C 退出，不影响容器）
$ docker compose ps                                  # 看状态：Up / Restarting / unhealthy
$ docker compose exec backend sh                     # 进容器：alpine 有 sh，scratch 进不去
$ docker compose restart backend                     # 只重启某个服务

# ———— 更新发布流程（以后每次改代码上线就这五行）————
$ cd /opt/goblog
$ git pull
$ docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env up -d --build
# ↑ 只重建 Dockerfile 上下文有变化的镜像（层缓存也在），mysql 完全不动
$ docker compose logs backend --tail 20              # 确认新进程正常
$ docker image prune -f                              # 清掉被替换下来的旧镜像，防磁盘堆积

发布前记得跑数据库迁移（如果这次更新带了新迁移文件）：docker compose --profile tools run --rm migrate up，在 up -d --build 之前执行。

5. 域名解析 + Caddy 自动 HTTPS

① 域名 A 记录：在域名控制台加一条解析——主机记录 blog（或 @），记录类型 A，记录值 = 服务器公网 IP。大陆地域须先完成备案。验证：

shell（本机执行）$ dig +short blog.example.com
47.98.xx.xx                 # 返回你的服务器 IP 即生效（DNS 全球生效一般几分钟到半小时）

② Caddy 是什么、为什么是它：Caddy 是自带 HTTPS 的 Web 服务器：你只需写一行"域名 → 反代到哪个上游"，它自动向 Let's Encrypt 申请证书、验证、90 天自动续期、HTTP 自动 308 跳 HTTPS。Nginx + certbot 也能做到，但要多维护一个续期定时器。作为代价，前面加一层 Caddy 后，frontend 的 80:80 映射要取消（否则 Let's Encrypt 校验会被 nginx 抢答，而且对外多了明文入口）——这正是第 3 天 override 思路的实战：

docker-compose.prod.yml（增补 caddy 服务）services:
  frontend:
    ports: []                      # 抹掉 base 里的 80:80，只让 Caddy 对外
  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data           # 证书与 ACME 账户存这里，named volume 重启不丢
      - caddy-config:/config
    depends_on:
      - frontend

volumes:
  caddy-data:
  caddy-config:
Caddyfile（项目根目录，完整可用）# 全局块：可留空；blog.example.com 换成你的域名（A 记录已指向本机）
blog.example.com {
    # 自动申请/续期 Let's Encrypt 证书，自动 http→https，无需任何额外配置
    encode gzip zstd

    # 全站反代到前端容器：静态文件与 /api 转发由容器里的 nginx 完成（W7D2 配置）
    reverse_proxy frontend:80
}
shell$ docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env up -d
$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://blog.example.com/
308 https://blog.example.com/          # ← HTTP 自动跳转生效

签发失败三查：① 安全组 443/80 是否放行；② dig +short 域名 是否已指向本机 IP（没生效就等会再 docker compose restart caddy 重试）；③ 大陆服务器域名未备案（80/443 被拦，永远签不下来）。证书申请有频率限制，调试期反复失败可临时加全局 email you@example.com + 本地测试用 tls internal（自签，浏览器告警但流程通）。macOS 本地想演练 Caddy：直接跑 docker run -p 8080:80 caddy:2-alpine caddy reverse-proxy --from localhost:8080 --to goblog-frontend:80 之类不如明天上线时一次配好，本地阶段用 http 即可。

6. macOS 本地预演路线（服务器没买/备案没下来的间隙别闲着）

整条流水线除"公网 HTTPS 签发"外都能在 Mac 本地 1:1 走通（Docker Desktop 或 OrbStack 任一，装好后 docker compose version 可用即可）：

shell（macOS 本地，在项目根目录）# ① 与服务器同样的三步曲
$ docker compose --env-file .env up -d mysql
$ docker compose --env-file .env --profile tools run --rm migrate up
$ docker compose --env-file .env up -d --build

# ② 本地演练 Caddy：把 Caddyfile 的站点地址临时改成 http://blog.localhost
#    （localhost 结尾的地址 Caddy 不申请公网证书，直接服务 HTTP，反代链路一模一样）
$ docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d caddy
$ curl -s -o /dev/null -w "%{http_code}\n" http://blog.localhost/    # 200

# ③ 本地 hosts 指个假域名，体验"改代码→重建→强刷"的完整发布循环
$ echo "127.0.0.1 blog.localhost" | sudo tee -a /etc/hosts

只有两件事必须等真服务器：公网可达（拿手机 4G 验证）与 真证书（Let's Encrypt 不会给 localhost/内网 IP 签发）。预演把其余 90% 的坑都提前踩掉，上线当天只做"搬运工"。

备案是"并行任务"：域名下单、备案材料提交和今天的本地预演同一周做，等备案短信到来时你早已万事俱备。海外机器则跳过备案直接解析上线。

7. 交付方式选型：拉代码 vs 推镜像

方式流程优点代价
git pull + 服务器现构（本篇）服务器装 Docker + git，up -d --build 一条龙零镜像仓库账号；构建上下文在服务器本地，无 arm/x86 平台坑；上手最快编译吃服务器 CPU/内存（1h2G 靠 swap 顶住）；git 凭证要放服务器
推镜像（GHCR/Docker Hub/阿里云 ACR）CI 或本地 buildx --platform linux/amd64 push，服务器只 pull + up服务器超轻；发布可秒级回滚（退一个 tag）；第 8 周之后值得升级要配仓库凭证与 CI；M 芯片 Mac 忘记 --platform 就 exec format error

本周用左列，把心智留给部署本身；两条路线的 compose 文件与环境变量完全一致，将来切镜像制只换"获取制品"一步。

8. 上线验证清单 + down 与 down -v 的天壤之别

验证项动作预期
浏览器域名访问开 https://blog.example.com首页秒开、小绿锁、无证书告警
子路由直访地址栏直接敲 https://域名/articles/1 回车200（D2 的 try_files 经受住了公网考验）
完整业务注册新号 → 发帖 → 编辑 → 退出重登全通；DevTools Network 里 /api 全走同域 https，无 CORS 报错
数据韧性docker compose restart 后再登录刚注册的账号登录成功 = named volume 在守护数据
备份习惯docker compose exec -T mysql mysqldump -ugoblog -p"$MYSQL_PASSWORD" --single-transaction goblog > backup_$(date +%F).sql拿到 SQL 文件，今天顺手下载回本机存一份
shell（两个命令，一个可悔一个不可悔）$ docker compose down        # 停并删【容器+网络】；named volume 原地不动 → 再 up 数据全在
$ docker compose down -v     # 连 named volume 一起删 —— MySQL 数据文件当场火化，不可恢复！

本周最重的一条警告：down -v 里的 -v 删卷不可撤销，没有回收站。生产机器上请形成肌肉记忆：先 down，确认不需要了再考虑一切带 -v 的命令；做实验删卷前看一眼卷名（docker volume ls）是不是练手项目。总结页的卡点复盘还会考这个。

9. 每日巡检：一次 SSH 会话的健康检查卡（30 秒跑完）

shell（存成 /opt/goblog/healthcheck.sh，养成习惯）#!/bin/sh
cd /opt/goblog
docker compose ps                                   # 全部 Up (healthy)？有无 Restarting？
df -h /                                             # 磁盘 >85% 就要 image prune + 清日志
free -h                                             # available 低于 100Mi？查谁在吃内存
docker compose exec -T mysql mysqladmin ping -h127.0.0.1 -uroot -p"$MYSQL_ROOT_PASSWORD" --silent
# mysqld is alive ← 数据库活着
curl -s -o /dev/null -w "https status: %{http_code}\n" https://blog.example.com/health

再配一条每周动作：备份定时化（crontab 每周日凌晨跑一次，保留 4 份滚动）：

shell（crontab -e 追加一行，路径按你机器改）0 4 * * 0 cd /opt/goblog && docker compose exec -T mysql mysqldump -ugoblog -p"$MYSQL_PASSWORD" --single-transaction goblog | gzip > /root/backup_$(date +\%F).sql.gz && find /root -name 'backup_*.sql.gz' -mtime +28 -delete
# 每周日 04:00 备份并 gzip，超过 4 周的自动清理；记得每月 scp 回本机一份——异地副本才算备份

小站没有监控告警，纪律就是监控。

10. 上线后 24 小时内值得做的三件小事

  1. 把首页链接发给三个朋友用手机网络打开——不同运营商、不同设备，是最便宜的兼容性测试；
  2. 看一次真实访问日志：docker compose logs caddy --tail 30，确认有真实访客的 GET、状态码正常，顺便感受"自己的服务在公网被访问"的奇妙；
  3. 演练一次完整回滚：git checkout HEAD~1 → 重新发布 → 确认旧版本可用 → git checkout main 再发布回来。敢回滚的人才敢上线，这话什么时候都对。

今日练习

练习 1：完整上线（必做，90 分钟）

按讲义 1→5 节顺序执行：买机/加 swap/安全组 → 装 Docker → clone + .env 五件套 → 三步曲部署 → Caddy 上 HTTPS。验收：手机用 4G 网络（排除本机缓存干扰）打开 https://你的域名，完成一次注册 + 发帖。截图存档——第 8 周 README 直接用。

练习 2：超时 vs 拒绝，学会定位卡在哪一层（15 分钟）

把服务器上的 caddy 停掉 docker compose stop caddy，curl 观察 Connection refused（端口没监听）；恢复后在云控制台临时移除安全组 80 放行，从手机 4G 访问感受一直转圈直到 timeout（包被防火墙丢弃）。记住这个判据：refused 查服务，timeout 查防火墙/安全组。练完把安全组恢复。

补充：Linux 服务器内部若还开着 ufw/firewalld，也要同步放行（ufw allow 80,443/tcp），两层防火墙任何一层没开都是 timeout。

练习 3：演练一次更新发布（20 分钟）

在本地把前端首页标题改成"Hello from Production"，commit + push → 服务器第 4 节的五行发布流程 → curl -s https://域名/ | grep -o "Hello from Production" 确认新产物。顺手观察：docker compose build 输出里 nginx 镜像那些 CACHED 层——D1 缓存课的知识在服务器上回来找你。

练习 4：备份与恢复推演（20 分钟，纸上 + 实操各一遍）

执行第 8 节的 mysqldump 备份；然后在预发库（新建一个一次性 mysql 容器，绝不碰生产卷！）restore 验证文件可用：docker exec -i restore-mysql mysql -uroot -p"$P" goblog < backup.sql。最后回答一题并写进笔记：docker compose down -v 之后，你刚才那份 backup 能救回什么、救不回什么？（答：数据全可回灌；但没备份过的那一刻起的新写入没了——所以备份要成例行。）
