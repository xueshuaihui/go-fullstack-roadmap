数据库迁移

前三天把"程序"容器化了，今天动"数据"。第 3 周起你就在靠 GORM 的 AutoMigrate 建表——开发期它是好人，但把它带进生产库，等于让每个版本的代码"自由发挥"改表结构。今天要学的 golang-migrate 把表结构变成和代码一样版本化、可回滚、可审查的 SQL 文件，并且把昨天 compose 里那行 AUTO_MIGRATE 从"占位"变成"真的读"。

课前须知

先用你熟的东西类比：AutoMigrate 相当于"启动时让 AI 随手改 package.json，改完直接 npm install"——它只保证"能装上"，不保证"装的是哪一版"。版本化迁移就是把这套换成 lockfile + CI 里的 npm ci：变更是一条条按序号写死的记录（迁移文件），环境状态是一个可查询的版本号（schema_migrations.version），要退回去就明确地退一步。差别只在规模：JS 锁的是依赖树，这里锁的是表结构。

仓库形状（D1~D3 的产物各就各位，今天只在根目录新增 migrations/，在 backend/ 下新增 scripts/hashpw/）：

migrations/ 必须在仓库根，不能在 backend/ 下。理由很硬：migrate 容器是用 ./migrations:/migrations:ro 挂载它的，./ 相对的是 compose 文件所在的根目录；而且迁移管的是库，不是后端的某个包——将来加 worker、加工具脚本，它们共用同一份结构定义。写进 backend/ 的话，挂载路径变成 ./backend/migrations，而 Go 的 .dockerignore 与构建上下文又在旁边虎视眈眈，纯属给自己加戏。

三份 env 文件今天开始要分清楚，别再问"改哪个才生效"：① backend/.env——在 backend/ 里裸跑 go run ./cmd/server 时 godotenv 读的那份；② backend/.env.docker——D1 用 docker run --env-file 单跑镜像时那份；③ 根目录 .env——compose 在渲染期读的那份，也是本周唯一的密钥事实源。今天新加的 AUTO_MIGRATE 这个键已经在第 ③ 份里了（D3 就写了，只是没人读它），你要做的是把它补进 ① 和 ②，别让本地裸跑变成"漏配"。

开工前确认昨天的全栈还在跑、并且是健康的：docker compose ps 三个 (healthy)。另外先跑一次 D3 练习 1 的第 0 步清场口径（docker rm -f 那些学习期旧容器、核对卷名）——今天所有"清卷重来"的操作都建立在"卷名我认得"这个前提上。

知识讲义

1. AutoMigrate 在生产库为什么危险

先肯定它：本地开发改个 model 结构体，重启就建表加列，零心智负担。但看它的实现哲学——"对比 struct 和当前表结构，缺什么补什么"。这个"只增不减、默默对齐"的行为放到有真实数据的表上，每一类变更都有雷：

你改了 modelAutoMigrate 实际干了什么生产后果
删掉一个字段什么都不做——旧列原样留在表里若旧列是 NOT NULL 且无默认值，代码已不再赋值 → INSERT 直接报错；若带唯一索引 → 幽灵冲突
字段改名（Nickname → DisplayName）当作"删旧 + 加新"：新建 display_name 列旧数据全在 nickname 列里睡死，新列一片 NULL，没人报错——静默的数据分裂
改类型（varchar → text / 加长）部分变更触发 ALGORITHM=COPY 的表重建百万行的表重建数分钟，期间锁写，接口超时雪崩；MySQL 8 的 instant DDL 只救少数场景
加 NOT NULL 无默认值字段对已有行的表执行 ALTER 失败或回填混乱启动即报错，或列被隐式填上 ""/0 这类脏值
任何变更没有版本号、没有执行记录、无法回滚线上结构"现在是哪个版本？"无人能答；多副本滚动发布时两个版本同时 AutoMigrate，互相踩踏

今天的处置方案不是"删掉 AutoMigrate"一刀切，而是分环境：本地/CI 可以用它快速起库（启动时读配置里的开关）；生产路径里默认关闭，结构变更只允许走迁移文件。这也正是 D3 的 compose 里那行 AUTO_MIGRATE: ${AUTO_MIGRATE:-true} 存在的意义——昨天它没人读，今天让它生效。

2. 把 AUTO_MIGRATE 变成真开关（三处改动）

第 4 周定的规矩是"main.go 里不许出现字面量、配置一律从 config.Load() 走"，所以开关不能写成 os.Getenv("AUTO_MIGRATE") == "true" 塞在 main 中间——那等于绕过 fail-fast、也没法在测试里注入。三步：

backend/internal/config/config.go（新增字段 + 读一行）type Config struct {
    Port             string
    GinMode          string
    DSN              string
    JWTSecret        string
    JWTRefreshSecret string
    AutoMigrate      bool   // ★ W7D4：false = 表结构只认 migrations/ 里的文件
}

func Load() (Config, error) {
    // ……必填项 missingEnv("DB_USER","DB_PASS","DB_NAME","JWT_SECRET","JWT_REFRESH_SECRET") 不动……

    // 可选项：给默认值。注意默认是 false——"没配"就等于"不动结构"，这是安全的一侧
    c.Port = getEnv("PORT", "8080")
    c.GinMode = getEnv("GIN_MODE", "debug")
    c.AutoMigrate = getEnv("AUTO_MIGRATE", "false") == "true"
    // ……DSN 拼装（D3 已把 DB_PORT 接上）不动……
}
backend/cmd/server/main.go（把 W4 那三行包起来）// 原来（W3~W6 一直这样）：
if err := db.AutoMigrate(&model.User{}, &model.Tag{}, &model.Article{}); err != nil {
    log.Fatal("迁移失败: " + err.Error())
}

// 今天改成：开关决定它跑不跑
if cfg.AutoMigrate {
    if err := db.AutoMigrate(&model.User{}, &model.Tag{}, &model.Article{}); err != nil {
        log.Fatal("迁移失败: " + err.Error())
    }
    log.Println("AutoMigrate 已执行（AUTO_MIGRATE=true，只允许在本地/CI）")
} else {
    log.Println("跳过 AutoMigrate：表结构由 migrations/ 管理")
}

用 getEnv(...) == "true" 而不是 strconv.ParseBool，是为了不多引一个包、也不多解释一种错误分支；代价是 AUTO_MIGRATE=1、True 这类写法会被当成 false。那就把值统一成 true/false 小写，这条口径写进 .env.example 的注释里（D3 那份已经写了 true 只给本地开发，生产必须 false）。

验证开关确实跟着环境走（两次都要看到日志原文，别猜）：

shell（在 goblog/ 根目录）$ docker compose build backend                     # 改了 Go 代码，必须先重建镜像

# ① 开发口径：base + 自动加载的 override
$ docker compose config | grep AUTO_MIGRATE
      AUTO_MIGRATE: "true"                         # ← override 里那个字面量说了算
$ docker compose up -d backend && docker compose logs backend --tail 3
AutoMigrate 已执行（AUTO_MIGRATE=true，只允许在本地/CI）

# ② 生产口径：显式两个 -f，override 不参与合并
$ docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env config | grep AUTO_MIGRATE
      AUTO_MIGRATE: "false"
$ docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env up -d backend
$ docker compose logs backend --tail 3
跳过 AutoMigrate：表结构由 migrations/ 管理        # ← 明天服务器上跑的就是这一行

今天最容易搞错的一件事：改 .env 里的 AUTO_MIGRATE 在开发机上不会生效。因为 D3 的 docker-compose.override.yml 把它写成了字面量 AUTO_MIGRATE: "true"，而 base 里的 ${AUTO_MIGRATE:-true} 只在渲染期被读一次——合并时后者被字面量覆盖。想看 false 的行为，就用上面第 ② 组 prod 口径的命令，别去和 override 较劲。（这就是 D3 §4 那句"compose 只在执行的那一刻读 .env、后出现的文件覆盖先出现的"的活用法。）

顺序纪律，记住这一段能省一小时：决定用迁移管结构之后，先把 AUTO_MIGRATE 关掉，再跑 migrate up。反过来的话，AutoMigrate 会抢先把 role、article_count 这些列补齐，你的 000002 再执行就撞上 Error 1060 (42S21): Duplicate column name 'role'——迁移器当场进 dirty 状态（第 7 节）。双轨并存不是"两个都跑一遍更保险"，是互相踩。

3. golang-migrate 安装与四个核心命令

两条路，选一条就行：本机装 CLI（图交互式顺手）或只用容器（服务器上零安装，本课主用这条）。

shell（可选：macOS 本机装 CLI）$ brew install golang-migrate
$ migrate -version
4.18.1
shell（可选：Debian/Ubuntu 云服务器装 CLI）$ curl -L https://github.com/golang-migrate/migrate/releases/download/v4.18.1/migrate.linux-amd64.tar.gz | tar xvz
$ sudo mv migrate /usr/local/bin/ && migrate -version

四个命令认识一遍（下面是本机 CLI 的写法；今天实际执行时用容器形态，即第 8 节的 docker compose --profile tools run --rm migrate <子命令>——子命令一模一样，只有前缀不同）：

shell（四个日常命令）# ① 生成一对带序号的空迁移文件（-seq 从 1 开始自增，两位作者同时创建必撞号，合并时后拉的改号）
$ migrate create -ext sql -dir migrations -seq init_users
migrations/000001_init_users.up.sql      # 做
migrations/000001_init_users.down.sql     # 撤（成对出现，两个都要手写内容！）

# ② 应用全部未执行的迁移（不带数字 = 升到最新版；带 N = 只升 N 步）
$ migrate -path ./migrations -database "mysql://goblog:<密码>@tcp(127.0.0.1:3306)/goblog?multiStatements=true" up

# ③ 看当前版本：输出两行——版本号 + dirty 标志
$ migrate -path ./migrations -database "mysql://..." version
2
dirty: false

# ④ 回滚最近 1 步（不带数字 = 一路 down 到 0，线上绝对别这么手滑）
$ migrate -path ./migrations -database "mysql://..." down 1

CLI 的数据库参数是 URL：mysql://用户:密码@tcp(主机:端口)/库名，和 GORM 的 DSN 不是一回事（GORM 那份没有 mysql:// 前缀、用户密码在 @ 左边但整体是 user:pass@tcp(...)/db?params）。两处格式不同，别互抄。要在一个 up 文件里执行多条语句（我们每条迁移几乎都是多语句），必须带 ?multiStatements=true。

迁移号起名要"读名字就知道线上发生了什么"：000002_add_role_to_users、000003_init_articles、000004_seed_admin。序号 + 蛇形动宾，review 时不用打开文件。

5. 容器内执行 mysql：一条姿势，今天用一整天

先看你昨天写的命令为什么会挂：

shell（错误示范：宿主机 shell 先把变量吃掉了）$ docker compose exec mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SELECT 1"
mysql: [Warning] Using a password on the command line interface can be insecure.
ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: NO)
#                                        ↑ 这个 NO 就是铁证：到达 mysql 的命令行里根本没有密码

机理 D3 讲过一遍，今天必须变成肌肉记忆：docker compose exec 后面的那串参数是宿主机 shell 先解析的，而 MYSQL_ROOT_PASSWORD 只存在于 .env 文件和容器环境里，你的终端进程里没有它 → 双引号展开成空串 → 命令变成 -p 空值。修法只有一条：让容器里的 sh 去展开它自己的环境变量。

shell（正确姿势：外层单引号 + 容器内 sh -c）$ docker compose exec mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW DATABASES;"'
Database
goblog
information_schema
performance_schema

# 普通用户版（D3 练习 4 用的就是这条）：连库名都不用写第二遍
$ docker compose exec mysql sh -c 'exec mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE" -e "SHOW TABLES;"'
Tables_in_goblog
schema_migrations
users

# 脚本/定时任务里加 -T：不分配伪终端，否则 mysqldump 输出里会混进 \r
$ docker compose exec -T mysql sh -c 'exec mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE" -e "SELECT VERSION();"'
写法谁来展开 $MYSQL_ROOT_PASSWORD结果
exec mysql mysql -p"$VAR"宿主机 shell（没有这个变量）空串 → using password: NO → 1045
exec mysql sh -c 'exec mysql -p"$VAR"'容器里的 sh（compose 注进去的那份）真密码 ✔ 本课唯一口径，D5 的备份脚本与巡检脚本用的也是它
exec mysql mysql -p$MYSQL_ROOT_PASSWORD（不带引号）还是宿主机 shell同样空串；密码里出现特殊字符时还会被再次分词

判据一句话：这串命令最终在谁的 shell 里跑，变量就得在谁的环境里存在。顺手记两个配套细节：① exec 后面第一个 - 开头的参数会被当成 docker 的旗，所以 sh -c 'exec mysql …' 里的 exec 不是装饰——它让 mysql 顶替 sh 成为容器里的当前进程，退出码原样传回来（第 8 节的一次性容器和明天的巡检脚本都靠退出码判断成败）；② 想让命令带上库名，把 "$MYSQL_DATABASE" 放最前面而不是靠 -D。

6. 四对迁移文件：列名对得上 model，索引名对得上 GORM

6.1 000001_init_users：用户表

口径来自两个硬事实：第 3 周 D1 里 AutoMigrate 打出来的那份 DDL，以及第 3 周 D2 定稿的 model.User。列名一律 GORM 蛇形，索引名照抄 GORM 的 uni_表_列 / idx_表_列——名字不对，将来 down 里的 DROP INDEX 就删不掉，第 3 周那条提示说的就是这件事。

migrations/000001_init_users.up.sqlCREATE TABLE users (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    username      VARCHAR(32)  NOT NULL,                 # model: uniqueIndex;not null
    nickname      VARCHAR(32)  NULL,                     # 显示名，可空（和 AutoMigrate 产物一致）
    email         VARCHAR(128) NULL,                     # uniqueIndex，可空但实际必填由 DTO 校验
    password      VARCHAR(72)  NOT NULL,                 # ★ 列名就是 password，不是 password_hash；72 = bcrypt 输入上限
    article_count BIGINT NOT NULL DEFAULT 0,             # ★ W3D2 的冗余计数列，漏了它生产必报 1054
    created_at    DATETIME(3) NULL,
    updated_at    DATETIME(3) NULL,
    deleted_at    DATETIME(3) NULL,                      # GORM 软删除
    PRIMARY KEY (id),
    UNIQUE KEY uni_users_username (username),
    UNIQUE KEY uni_users_email (email),
    KEY idx_users_deleted_at (deleted_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci;
# role 列不在这里——它是 000002 的主题（"一个迁移只做一件事"）
migrations/000001_init_users.down.sqlDROP TABLE IF EXISTS users;

password 这一列名是踩过的雷区。第 4 周的 model.User.Password 由 GORM 映射成列 password（json:"-" 让它永不进响应），不少教程把它写成 password_hash。写错的后果很具体：迁移"执行成功"，注册接口一跑 Error 1054 (42S22): Unknown column 'users.password' in 'field list'。本周基线就是 password。至于"库里存的是哈希不是明文"这件事，靠 DDL 注释和第 4 周就写好的 service 层 bcrypt 逻辑说明，不靠列名。

article_count 为什么今天就要建。它是第 3 周 D2 为"一篇文章 + 一个计数同生同死"的事务演示加的冗余列，AutoMigrate 会顺手补出来，所以本地一直没出过事。可一旦生产库只由迁移文件建出来（明天 D5 就是这个场景），漏了这列的后果是登录、列表、发帖全在 Error 1054 Unknown column 'article_count' 上翻车。第 8 周 D1 会给出同一课的第二次考试——那时漏的是 avatar，措辞一模一样：凡 model 里存在的列，迁移里必须存在。

6.2 000002_add_role_to_users：把 role 列就位（第 8 周才用它）

第 8 周 RBAC 要用 role，但那一周讲义里明确写着"这条迁移你在第 7 周已经写好了"，所以今天必须把它做成与第 8 周逐字一致的一对（TINYINT 对齐 Role int8，不是 VARCHAR(16) DEFAULT 'user'）：

migrations/000002_add_role_to_users.up.sqlALTER TABLE users
    ADD COLUMN role TINYINT NOT NULL DEFAULT 0 COMMENT '0=user 1=admin';
CREATE INDEX idx_users_role ON users(role);
migrations/000002_add_role_to_users.down.sql# 索引名和列名要分别删——只 DROP COLUMN 在某些 MySQL 版本会把索引留着占坑
ALTER TABLE users DROP INDEX idx_users_role;
ALTER TABLE users DROP COLUMN role;

三条口径钉死在这里：① 类型是 TINYINT NOT NULL DEFAULT 0，零值 0 就是 RoleUser，代码里不需要"空则补 user"的兜底（那是第 3 周 D2 改造 gin-api 时专门删掉的三行）；② 索引名 idx_users_role 与 AutoMigrate 产物一致；③ 这两条语句写在同一个 up 文件里，靠 URL 上的 multiStatements=true 才跑得动（第 3 节的注）。

6.3 000003_init_articles：文章 / 标签 / 中间表

对照 model.Article、model.Tag 和第 3 周 D3 里 DESCRIBE article_tags 的输出（两列、联合主键、没有 id 也没有时间戳）：

migrations/000003_init_articles.up.sqlCREATE TABLE tags (
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    name       VARCHAR(32) NOT NULL,
    created_at DATETIME(3) NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uni_tags_name (name)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci;

CREATE TABLE articles (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    title       VARCHAR(120) NOT NULL,

    views       BIGINT NOT NULL DEFAULT 0,

CREATE TABLE article_tags (
    article_id BIGINT UNSIGNED NOT NULL,
    tag_id     BIGINT UNSIGNED NOT NULL,
    PRIMARY KEY (article_id, tag_id),                   # 同一篇贴同一标签两次 → 数据库层直接拒

migrations/000003_init_articles.down.sql# 顺序与 up 相反：先拆中间表，再删 articles，最后删被引用的 tags
DROP TABLE IF EXISTS article_tags;
DROP TABLE IF EXISTS articles;
DROP TABLE IF EXISTS tags;

三处值得停一下的判断：① 建表顺序 articles 在 tags 之后、但在引用 users 之后——外键指向的表必须先存在，down 反着来；② 只给 articles→users 建一条物理外键，命名照 GORM 的 fk_表_关系字段 规矩（fk_articles_user），级别用默认的 RESTRICT：删用户时如果他还写着文章，让数据库拦住你，比级联删光全站文章体面得多；③ idx_article_tags_tag_id 是手写迁移主动加的一条——联合主键只覆盖 article_id 前缀，反查走 tag_id 时 AutoMigrate 版本会在 MySQL 里全表扫。跑完用 SHOW CREATE TABLE articles\G 对账，两边差在哪一两行，你心里要有数：从今天起权威定义是迁移文件，不是 AutoMigrate。

序号名字只做的那一件事跑完后的 version
000001init_users建 users（不含 role）1
000002add_role_to_users加 role 列 + 索引（第 8 周用）2
000003init_articles建 tags / articles / article_tags3
000004seed_admin确保存在 role=1 的 admin4
第 8 周接续000005_…（评论）、000006_add_avatar_to_users5 → 6

编号一旦定下来就是全周契约：本周结构迁移止于 000003，种子固定 000004。第 8 周不会、也不允许再凭空造一个 000003_add_role…——它要的 role 列就在你今天的 000002 里，它要登录的 admin 就在 000004 里，新东西一律从 000005 往后排。

7. schema_migrations：库结构状态的唯一答案

migrate 第一次连上库时自动建一张 schema_migrations 表，全库只有一行：

shell（进容器查，姿势见第 5 节）$ docker compose exec mysql sh -c 'exec mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE" -e "SELECT * FROM schema_migrations;"'
+---------+-------+
| version | dirty |
+---------+-------+
|       2 |     0 |
+---------+-------+

version = 已应用到第几号迁移；dirty = 上一次迁移执行到一半失败的坏标记。dirty=1 时所有后续 up/down 都拒绝执行（防止在结构不明的库上继续动刀）。修复三步，一步都不能省：

  1. 看报错，手动把半途而废的 SQL 补完（建了一半的表要么手工建完、要么 DROP 掉重来）；
  2. … migrate force <目标版本号> 清除 dirty 标记；
  3. 再 up 续跑。force 只改标记，不执行任何 SQL——它不是"忽略错误继续"的橡皮擦。

给前端同学的对位理解：schema_migrations.version ≈ lock 文件里的完整性哈希——它回答的唯一问题是"眼前这个库处于第几号结构"。Git 里 commit 有 SHA，库里结构有 version，两边一挂钩，"部署的代码配不配得上库的结构"就从玄学变成一次 migrate version 查询。明天 D5 的巡检脚本第一条就是它。

8. 接入 Compose：profiles 一次性 migrate 服务

服务器上不想装 CLI 也能跑迁移——用官方镜像 migrate/migrate 配成一次性任务服务。profiles: ["tools"] 让它平时完全不参与 up，只在显式点名时运行。整段贴进 docker-compose.yml 的 services: 下（缩进和 mysql/backend 平级）：

docker-compose.yml（services 下追加）  migrate:
    image: migrate/migrate:v4.18.1
    profiles: ["tools"]                # 默认不启动：docker compose up 会跳过它
    container_name: goblog-migrate      # ★ 一次性任务故意【不写】container_name：见下面第 ② 条
    volumes:
      - ./migrations:/migrations:ro     # 迁移文件不进镜像，跑时挂载 → 改迁移无需 rebuild
    entrypoint:                         # ★ 固定参数放 entrypoint，命令放 run 的追加参数（原因见 8.1）
      - /migrate
      - "-path=/migrations"
      - "-database=mysql://${DB_USER}:${DB_PASS}@tcp(mysql:3306)/${DB_NAME}?multiStatements=true"
    depends_on:
      mysql:
        condition: service_healthy      # 和 backend 一样：等库真的能用了再动结构
    restart: "no"                      # 跑完即退出，不留尸

      - /migrate

8.1 为什么固定参数写 entrypoint 而不是 command

这是今天最"工程"的一处决定。compose 的 run 语义是：你在命令行尾部追加的参数，会替换掉服务的 command，并追加到 entrypoint 后面。而我们的用法恰恰是"把子命令追加在最后"：

shell# 固定参数放在 command: 里（错误写法）
$ docker compose --profile tools run --rm migrate up
#   ↑ 这里的 up 把整条 command 顶掉了：-path / -database 一个字都没带上
#   结果 migrate 报"没有指定 -path/-database"当场退出（不同小版本措辞略有差别，反正跑不起来）

# 固定参数放在 entrypoint: 里（本课写法）
$ docker compose --profile tools run --rm migrate up
#   实际执行：/migrate -path=/migrations -database=mysql://… up   ✔

官方镜像 migrate/migrate 的 /migrate 就是二进制路径，把它写进 entrypoint 的第一项等于自己声明了一次 ENTRYPOINT（覆盖镜像默认的 ["-help"]），后三项是每次都不变的连接参数。于是四条日常命令变成同一前缀 + 不同尾巴，和第 3 节的 CLI 形态一一对上：

shell（四条日常命令的容器形态）$ docker compose --profile tools run --rm migrate up          # 升到最新
$ docker compose --profile tools run --rm migrate version     # 看版本 + dirty
$ docker compose --profile tools run --rm migrate down 1      # 回滚一步
$ docker compose --profile tools run --rm migrate force 4     # 清 dirty（先按第 7 节把结构补完）

两个细节顺手记牢：① run 是前台执行，日志直接打在你的终端，退出码 0 才算迁移成功（写进发布脚本时判 $? 就行）；--rm 让它退出即删容器。② 一次性容器不该占用固定名字——写了 container_name 后，第二次 run 会撞 Conflict. The container name "/goblog-migrate" is already in use（上一个还没退出干净、或者你忘了 --rm）。所以 mysql/backend/frontend 三个常驻服务写 container_name（D3 说过的"给 exec 和 logs 一个稳定靶子"），migrate 这类一次性服务不写，compose 会给它们临时名字。

8.2 三步曲：顺序不可拆

shell（标准发布序列——本地演练版）$ docker compose up -d mysql                                       # 1) 先起库，等 healthy
$ docker compose --profile tools run --rm migrate up               # 2) 点名跑迁移，退出码 0 即成功
$ docker compose up -d --build                                     # 3) 结构就绪，再起应用
shell（同一个三步曲的生产口径——明天 D5 原样复用）$ docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env up -d mysql
$ docker compose --profile tools run --rm migrate up
$ docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env up -d --build

第 3 步里 backend 必须已经读到 AUTO_MIGRATE=false（生产口径下 prod 文件给了字面量），否则它会在新迁移出来的库上再"顺手对齐"一次，把双轨并存的事故提前带到线上。第 2 节那两条 config | grep AUTO_MIGRATE 就是为这一步准备的。

为什么不能省掉第 2 步、让应用自己建表？因为"表还不存在"这件事的表现形式很不体面：backend 连库是成功的（Ping 只验连接），要到第一个真实请求才会炸出 Error 1146 (42S02): Table 'goblog.users' doesn't exist——接口 500、日志里一片 code:5000，而 docker compose ps 看着一切正常。结构问题必须在发布阶段就炸，这就是"显式、单独、一次性"执行迁移的全部价值。

9. 种子数据：000004_seed_admin 与哈希生成工具

初始管理员这类"上线必备数据"同样版本化。bcrypt 哈希不要手写、不要去网上搜一串贴进来，用一个 20 行的小工具现场生成（它放进仓库长期有用，所以住在 backend/scripts/——Go 模块根在 backend/，go run ./scripts/hashpw 只认这个相对路径）：

backend/scripts/hashpw/main.go（完整可抄，依赖 x/crypto 已在 go.mod 里）package main

import (
    "fmt"
    "os"

    "golang.org/x/crypto/bcrypt"
)

// 用法（在 backend/ 目录里）：go run ./scripts/hashpw '你的密码'
// 输出一行 bcrypt 串，贴进 migrations/000004_seed_admin.up.sql 的 password 位置。
func main() {
    if len(os.Args) < 2 {
        fmt.Fprintln(os.Stderr, "用法: go run ./scripts/hashpw <密码>")
        os.Exit(1)
    }
    pw := []byte(os.Args[1])
    if len(pw) > 72 {
        // bcrypt 会静默截断超过 72 字节的输入：不报错的坑，宁可在这里拦住
        fmt.Fprintln(os.Stderr, "密码超过 72 字节，先缩短再说")
        os.Exit(1)
    }
    h, err := bcrypt.GenerateFromPassword(pw, bcrypt.DefaultCost)
    if err != nil {
        fmt.Fprintln(os.Stderr, "生成失败:", err)
        os.Exit(1)
    }
    fmt.Println(string(h))
}
shell（跑一次，60 字符的串就是要贴进 SQL 的东西）$ cd backend
$ go run ./scripts/hashpw 'Adm1nGo2026'
$2a$10$kQ9k3F7mZq0Xw2nY1v7bUeS1jP9oQ4sN7tLxhKz2mRfT8cXq1dGeA    # ← 你生成的和这个不一样，那是正常的（盐随机）
$ cd ..

同一个密码每次生成的串都不同：bcrypt 把随机盐编进了输出。反过来说，验证靠的是 bcrypt.CompareHashAndPassword（第 4 周 D2 登录里那句 if bcrypt.CompareHashAndPassword([]byte(u.Password), []byte(req.Password)) != nil），不需要两边字符串相等。顺带解释了为什么列是 VARCHAR(72) 而不是 60：$2a$10$ 前缀占 7 个字符、哈希部分 31 个、盐 22 个，一共 60，多出的 12 个字符留给"将来换 cost 或前缀版本"。

migrations/000004_seed_admin.up.sql（两条语句，各司其职）-- ① 没有 admin 就插一个：INSERT IGNORE 让"已经通过注册接口建过 admin"这件事不算错误
INSERT IGNORE INTO users (username, nickname, email, password, article_count, created_at, updated_at)
VALUES ('admin', '站长', 'admin@yourdomain.com',
        '$2a$10$这里必须换成你刚生成的那一串', 0, NOW(3), NOW(3));

-- ② 不管它是 INSERT 新建的还是早就存在的，role 一律置成 1（000002 给的默认值是 0）
UPDATE users SET role = 1 WHERE username = 'admin';
migrations/000004_seed_admin.down.sqlDELETE FROM users WHERE username = 'admin';
-- 如果 admin 已经发过文章，这条会撞外键 RESTRICT（第 6.3 节那条 fk_articles_user）：
-- 这是数据库在保护你——先删/改它的文章，再考虑回滚种子。

三处判断说清楚，别当"抄来的写法"：① 为什么不是裸 INSERT——你在 D3 的浏览器里注册过 admin 的话，裸 INSERT 会撞 Error 1062，整条迁移失败 → 库进 dirty 状态，这是新手最常见的"我明明只多跑了一次"事故；② INSERT IGNORE 的代价——它不只忽略重复键，还会把别的数据错误一起降级成 warning（比如超长值被截断），所以只用在种子这种"一条数据、可人工核对"的场景，业务写入永远不许用它；嫌它太宽可以用严格变体 INSERT … ON DUPLICATE KEY UPDATE role = 1, updated_at = NOW(3);（一条语句同时负责插入与纠正，代价是 SQL 更绕）；③ 为什么还要接一条 UPDATE——因为 role 的默认值是 0（000002 定的），只 INSERT 不 UPDATE 会留下一个 role=0 的"假管理员"，第 8 周 RBAC 中间件会把他当普通用户，那种 bug 极难查。

迁移文件里的哈希是占位示例。合入 Git 前必须换成你自己用 hashpw 现场生成的串，而且那个密码要满足第 4 周定的强度（≥8 位、含字母与数字）；真实生产密码一旦泄露在这份仓库历史里，换文件没用、要重写历史。更稳的做法：seed 只建非管理员的占位数据，管理员账号在上线后用注册接口建、再用一条一次性的 UPDATE users SET role = 1 提权——那样 Git 里永远没有一个能登录你站点的账号。两种路线都合法，本课为了演示"种子也是迁移"用前者，你上线后建议按后者重来一次。

测试数据（造 100 篇文章跑分页那种）不要做成迁移：写个 backend/scripts/seed_demo/main.go 或一份 scripts/seed.sql 手动灌，和"线上必备种子"分开管理，否则你在第 8 周的生产库上一个 up 就多出一堆"第 1 篇测试文章"。

10. 工具选型与迁移纪律

Go 生态里做迁移的不止一家，先给结论再给理由：

方案形态适合
golang-migrate（本篇）独立 CLI + 纯 SQL 文件学习期首选：SQL 手写可见，每个变更都过你的眼；CI/服务器上执行方式统一
GORM 自带 db.Migrator()Go 代码里调方法想保留 AutoMigrate 语法糖又想要版本管理时用；但"迁移逻辑写在 Go 里"意味着改结构要重编程序，回滚支持弱
Atlas / goose 等声明式 / 命令式各有拥趸团队项目常见，思想与本篇完全互通，学会一个全能上手

不管用哪家，五条纪律通用：

  1. 迁移文件一经合入 Git 永不修改——写错了就加一个新迁移纠正，改旧文件会让"已在别处执行过 000002"的环境版本错乱；
  2. 序号只增不改：两个人同时占 000005 是协作第一课，合并时后拉的 renumber；
  3. 一个迁移只做一件事，文件名说清是什么事；大表变更拆小步（加带默认值的列、回填数据、建索引、删旧列各一对）；
  4. 不可逆的数据变更要故意让 down 失败——比如"删掉明文密码列"这种迁移，回滚等于恢复明文，必须在 down.sql 里写一条必然报错的语句拦路：SELECT '此迁移禁止回滚，见迁移说明'; 后面接 DROP TABLE guard_against_rollback;（不存在的表 → 迁移器报错终止）。结构可以回滚，数据覆水难收；
  5. 先在预发库全量跑一遍 up：生产永远执行"别人已经执行过一遍"的迁移。

常见坑（新手 100% 会踩）

今日名词卡

术语一句话解释
版本化迁移每次结构变更 = 一对编号 SQL 文件，库结构状态用整数版本号表达
预发库结构与生产一致、数据是副本的验证库，迁移先在那里跑一遍
schema_migrationsmigrate 自动建的版本表，单行记录当前 version 与 dirty
dirty 状态迁移执行到一半失败的"带病"标记，必须人工善后后 force 清除
force只把版本号强行设为 N 并清 dirty，不执行任何 SQL
不可逆迁移数据覆水难收的变更（删列、覆写密码），down 要故意写坏以拦截回滚
种子数据（seed）上线即需的基础数据（admin 账号），同样编入迁移版本号管理
multiStatements=true允许一个 up 文件里跑多条语句的开关，golang-migrate 的 MySQL URL 必填
profiles（compose）给服务打标签，默认 up 跳过，--profile tools run 时才被点名的一次性任务
entrypoint vs commandrun 追加的参数替换 command、接在 entrypoint 后面 → 固定参数写 entrypoint
