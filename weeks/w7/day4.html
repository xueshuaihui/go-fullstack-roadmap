数据库迁移

前三天把"程序"容器化了，今天动"数据"。第 3 周起你就在靠 GORM 的 AutoMigrate 建表——开发期它是好人，但把它带进生产库，等于让每个版本的代码"自由发挥"改表结构。今天要学的 golang-migrate 把表结构变成和代码一样版本化、可回滚、可审查的 SQL 文件。

知识讲义

1. AutoMigrate 在生产库为什么危险

先肯定它：本地开发改个 model 结构体，重启就建表加列，零心智负担。但看它的实现哲学——"对比 struct 和当前表结构，缺什么补什么"。这个"只增不减、默默对齐"的行为放到有真实数据的表上，每一类变更都有雷：

你改了 modelAutoMigrate 实际干了什么生产后果
删掉一个字段什么都不做——旧列原样留在表里若旧列是 NOT NULL 且无默认值，代码已不再赋值 → INSERT 直接报错；若带唯一索引 → 幽灵冲突
字段改名（Nickname → DisplayName）当作"删旧 + 加新"：新建 display_name 列旧数据全在 nickname 列里睡死，新列一片 NULL，没人报错——静默的数据分裂
改类型（varchar → text / 加长）部分变更触发 ALGORITHM=COPY 的表重建百万行的表重建数分钟，期间锁写，接口超时雪崩；MySQL 8 的 instant DDL 只救少数场景
加 NOT NULL 无默认值字段对已有行的表执行 ALTER 失败或回填混乱启动即报错，或列被隐式填上 ""/0 这类脏值
任何变更没有版本号、没有执行记录、无法回滚线上结构"现在是哪个版本？"无人能答；多副本滚动发布时两个版本同时 AutoMigrate，互相踩踏

今天的处置方案不是"删掉 AutoMigrate"一刀切，而是分环境：本地/CI 可以用它快速起库（启动时读环境变量开关）；生产镜像启动路径里彻底移除，结构变更只允许走迁移文件。

backend/cmd/server/main.go（节选改造）// 只保留给本地开发；.env 里 AUTO_MIGRATE=true 才执行
if os.Getenv("AUTO_MIGRATE") == "true" {
    if err := db.AutoMigrate(&model.User{}, &model.Article{}); err != nil {
        slog.Error("auto migrate failed", "err", err)
        os.Exit(1)
    }
} else {
    slog.Info("skip AutoMigrate: schema is managed by golang-migrate")
}

2. golang-migrate 安装与四个核心命令

shell（macOS 本地）$ brew install golang-migrate
$ migrate -version
4.18.1
shell（Debian/Ubuntu 云服务器）$ curl -L https://github.com/golang-migrate/migrate/releases/download/v4.18.1/migrate.linux-amd64.tar.gz | tar xvz
$ sudo mv migrate /usr/local/bin/
$ migrate -version
shell（四个日常命令）# ① 生成一对带序号的空迁移文件（-seq 从 1 开始自增）
$ migrate create -ext sql -dir migrations -seq init_users
migrations/000001_init_users.up.sql      # 做
migrations/000001_init_users.down.sql     # 撤（成对出现，必须手写！）

# ② 应用全部未执行的迁移（up 不带数字 = 升到最新版；带 N = 只升 N 步）
$ migrate -path ./migrations -database "mysql://goblog:<密码>@tcp(127.0.0.1:3306)/goblog" up

# ③ 看当前版本：输出两行——版本号 + dirty 标志
$ migrate -path ./migrations -database "mysql://..." version
2
dirty: false

# ④ 回滚最近 1 步（down 同样支持不带数字=全部回滚，慎用！）
$ migrate -path ./migrations -database "mysql://..." down 1

迁移号建议与功能同名可读（000002_add_role_to_users），review 时不用打开文件就知道线上发生了什么。

注意 CLI 的数据库 URL 是 mysql://用户:密码@tcp(主机:端口)/库名 格式，和 GORM 的 DSN 不是一回事（GORM 没有 mysql:// 前缀）。要在 URL 里执行多条语句需追加 ?multiStatements=true。

3. 成对迁移文件实战：建 users 表 + 加 role 列

第一对，migrations/000001_init_users.up.sql（列设计对齐第 4 周的 GORM model：GORM 默认蛇形列名、软删字段 deleted_at 可空）：

migrations/000001_init_users.up.sqlCREATE TABLE users (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    username    VARCHAR(32)  NOT NULL,
    email       VARCHAR(128) NOT NULL,
    password_hash VARCHAR(72) NOT NULL,          # bcrypt 串固定 60 字符，72 留余量
    bio         VARCHAR(200) NOT NULL DEFAULT '',
    created_at  DATETIME(3) NULL,
    updated_at  DATETIME(3) NULL,
    deleted_at  DATETIME(3) NULL,               # GORM 软删除
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_username (username),
    UNIQUE KEY uk_users_email (email),
    KEY idx_users_deleted_at (deleted_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci;
migrations/000001_init_users.down.sqlDROP TABLE IF EXISTS users;

第二对，模拟第 8 周要做的 RBAC——给 users 加 role 列：

migrations/000002_add_role_to_users.up.sqlALTER TABLE users
    ADD COLUMN role VARCHAR(16) NOT NULL DEFAULT 'user' AFTER email;
migrations/000002_add_role_to_users.down.sqlALTER TABLE users
    DROP COLUMN role;

down 文件的两条纪律：① 不许留空——空 down 会让"回滚"变成假动作；② 不可逆的数据变更要故意让 down 失败。比如"把明文密码列删掉"这种迁移，回滚等于恢复明文，必须在 down.sql 里写一条必然报错的语句拦路：SELECT '此迁移禁止回滚，见迁移说明'; 后面接 DROP TABLE guard_against_rollback;（不存在的表 → 迁移器报错终止）。结构可以回滚，数据覆水难收。

articles / tags / article_tags 三张表照此各写一对（练习 3 的素材），编号顺延 000003_init_articles……写迁移的口径：一个迁移只做一件事，文件名说清是什么事。

4. schema_migrations：库结构状态的唯一答案

migrate 第一次连上库时自动建一张 schema_migrations 表，全库只有一行：

shell（在 backend 容器里连库查看）$ docker compose exec mysql mysql -ugoblog -p"$MYSQL_PASSWORD" goblog -e "SELECT * FROM schema_migrations;"
+---------+-------+
| version | dirty |
+---------+-------+
|       2 |     0 |
+---------+-------+

version = 已应用到第几号迁移；dirty = 上一次迁移执行到一半失败的坏标记。dirty=1 时所有后续 up/down 都会拒绝执行（防止在结构不明的库上继续动刀）。修复流程：

  1. 看报错，手动把半途而废的 SQL 补完（比如表建了一半就手工建完，或 DROP 掉半成品重来）；
  2. migrate ... force <目标版本号> 清除 dirty 标记；
  3. 再 up 续跑。force 只是改标记，不动结构——它不是"忽略错误继续"的橡皮擦。

给前端同学的对位理解：schema_migrations.version ≈ lock 文件里的完整性哈希——它回答的唯一问题是"眼前这个库处于第几号结构"。Git 里 commit 有 SHA，库里结构有 version，两边一挂钩，"部署的版本配不配得上库的结构"就从玄学变成一次 migrate version 查询。

5. 接入 Compose：profiles 一次性 migrate 服务

服务器上不想装 CLI 也能跑迁移——用官方镜像 migrate/migrate，配成一次性任务服务。profiles: ["tools"] 让它平时完全不参与 up，只在显式点名时运行：

docker-compose.yml（在 services: 下追加）  migrate:
    image: migrate/migrate:v4.18.1
    profiles: ["tools"]                # 默认不启动：docker compose up 会跳过它
    volumes:
      - ./migrations:/migrations:ro     # 迁移文件不进镜像，跑时挂载，改迁移无需 rebuild
    command:
      - "-path"
      - "/migrations"
      - "-database"
      - "mysql://${MYSQL_USER:-goblog}:${MYSQL_PASSWORD}@tcp(mysql:3306)/${MYSQL_DB:-goblog}?multiStatements=true"
      - "up"
    depends_on:
      mysql:
        condition: service_healthy
    restart: "no"                      # 跑完即退出，不留尸
shell（标准发布序列——今天先演练）$ docker compose up -d mysql                    # 1) 先起库，等 healthy
$ docker compose --profile tools run --rm migrate up    # 2) 点名跑迁移，退出码 0 即成功
$ docker compose up -d backend frontend          # 3) 结构就绪，再起应用

进阶玩法（第 8 周之后了解即可）：把 migrate 放进 backend 的启动 ENTRYPOINT 前置脚本，"up 即自动迁移"。代价是迁移和应用权限耦合、多副本并发启动会抢跑同一迁移，所以教科书方案永远是显式、单独、一次性地执行迁移。

6. 种子数据：也做成迁移

初始管理员这类"上线必备数据"同样版本化，编号 000003（若结构迁移已占则顺延）。bcrypt 哈希不要手写，用第 4 周的工具函数现生成：

scripts/hashpw/main.go（放仓库里长期有用）package main

import (
    fmt
    os

    golang.org/x/crypto/bcrypt
)

func main() {
    h, err := bcrypt.GenerateFromPassword([]byte(os.Args[1]), bcrypt.DefaultCost)
    if err != nil {
        panic(err)
    }
    fmt.Println(string(h))
}
shell$ go run ./scripts/hashpw '<你的强密码>'
$2a$10$N9abcDEfGhIjKlMnOpQrStUvWxYz1234567890AbCdEfGhIjK   # ← 贴进下面的 SQL
migrations/000004_seed_admin.up.sqlINSERT INTO users (username, email, password_hash, role, created_at, updated_at)
VALUES ('admin', 'admin@yourdomain.com',
        '$2a$10$N9abcDEfGhIjKlMnOpQrStUvWxYz1234567890AbCdEfGhIjK',
        'admin', NOW(3), NOW(3));
migrations/000004_seed_admin.down.sqlDELETE FROM users WHERE username = 'admin';

SQL 文件里出现的 bcrypt 串是占位示例——上线前必须用你自己的强密码重新生成替换；种子迁移会进 Git，永远不要把真实密码/密钥写进迁移文件。测试数据（造 100 篇文章跑分页）建议用单独的 scripts/seed.sql 手动灌，和"线上必备种子"分开管理。

7. 工具选型与迁移纪律

Go 生态里做迁移的不止一家，先给结论再给理由：

方案形态适合
golang-migrate（本篇）独立 CLI + 纯 SQL 文件学习期首选：SQL 手写可见，每个变更都过你的眼；CI/服务器上执行方式统一
GORM 自带 Migrate（db.Migrator()）Go 代码里调方法想保留 AutoMigrate 语法糖又想要版本管理时用；但"迁移逻辑写在 Go 里"意味着改结构要重编程序，且回滚支持弱
Atlas / goose 等声明式 / 命令式各有拥趸团队项目常见，思想与本篇完全互通，学会一个全能上手

不管用哪家，四条纪律通用：

  1. 迁移文件一经合入 Git 永不修改——写错了就加一个新迁移纠正，改旧文件会让"已在别处执行过 000002"的环境版本错乱；
  2. 序号只增不改：两个人同时占 000005 是协作第一课，合并时后拉的 renumber 即可；
  3. 大表变更拆小步：加带默认值的列、回填数据、建索引、删旧列各一个迁移——MySQL 8 很多 DDL 已是 online 的，但一步一迁移让你在中间任何一点都能停下来；
  4. 先在预发库全量跑一遍 up：生产永远执行"别人已经执行过一遍"的迁移。

常见坑（新手 100% 会踩）

坑现象正确姿势
up/down 只写了单边no migration found 或回滚时炸出没定义的行为migrate create 每次生成一对，up 与 down 都要手写内容
迁移进了 dirty 状态之后任何命令都报 Dirty database version N. Fix and force version.先手动补齐/撤销半途 SQL，再 force N（它只清标记不动结构）
把 migrate CLI URL 写成 GORM DSNunknown scheme 或连不上库CLI 用 mysql://user:pass@tcp(host:3306)/db，两处格式不同别互抄
一个 up 文件塞多条语句没开 multiStatementsdriver: bad connection 或语法错CLI URL 加 ?multiStatements=true（第 5 节镜像服务已带）
列名与 GORM 蛇形约定不一致迁移跑"成功"了，接口却报 Unknown column 'displayName'以 GORM 默认蛇形为准（password_hash、user_id）；跑一次 SHOW CREATE TABLE 对账
AutoMigrate 和 migrate 双轨并存迁移刚建好表，AutoMigrate 又"顺手补列"，结构漂移谁都不认生产只留一条路：今天第 1 节的 AUTO_MIGRATE 开关就是隔离手段
改了已执行过的迁移文件本地库版本领先/落后文件号，别人环境行为对不上迁移号一旦执行过多处，只许新增纠正迁移，不许改旧文件
把含真实密码的种子提交进 Git仓库一公开，admin 直接被登录种子只放占位哈希 + 文档要求上线替换；真密钥永远走 .env
