课前须知

今天在 frontend/（第 6 周那个 React + Vite 项目，仓库归置已在 W6D5 完成，它就住在 goblog/frontend/）下工作。路由口径与既有代码逐字对齐：后端业务路由挂在 /api/v1 组下（/api/v1/articles、/api/v1/auth/login），健康检查是不带前缀的 GET /health；前端 src/api/http.js 的 baseURL 和 W6D5 的 VITE_API_BASE 都是 /api/v1；前端自己的页面路由是 /、/post/:id、/post/new、/me、/login。今天的 nginx 只负责两件事：把 /api/ 开头的请求转给后端（/api/v1/… 自然命中，规则见第 4 节），其余全部交给 try_files 兜回 index.html。

和上周的对接点：开发期你靠 vite.config.js 的 server.proxy['/api'] 把请求转给 localhost:8080。今天做的事一模一样，只是把"谁来转发"从 Vite 换成了 Nginx——key 只要 /api、baseURL 从 /api/v1 起写这条规矩在 nginx 这里同样成立（W6D5 排错表里那条"请求变成 /api/api/v1"的坑，nginx 也会踩）。

知识讲义

1. 先看产物：Vite build 之后的 dist 长什么样

shell（在 frontend/ 目录）$ npm run build

$ du -sh node_modules dist        # 感受一下"源码态 vs 产物态"的差距
412MB    node_modules
1.9MB    dist

$ find dist -type f
dist/index.html
dist/favicon.svg
dist/assets/index-4f2a9c1e.js     # JS 全部打包 + 压缩，文件名带内容 hash
dist/assets/index-7b3d81fa.css
dist/assets/vendor-a10c8f22.js

三个观察：

  • dist 只有 2MB 左右，而 node_modules 四百多 MB——部署只需要前者。昨天的道理在这里重演：构建环境（node_modules + 源码）不该进最终镜像。
  • 文件名带 hash（index-4f2a9c1e.js）：内容变、名字变；内容不变、名字不变。所以这些文件可以理直气壮地让浏览器缓存一年（immutable），发版用户自动拿新文件，这就是第 5 节缓存指令的依据。
  • index.html 的名字不带 hash，它是每次访问都要拿最新的"入口清单"。

2. 最小 nginx 容器：托管静态文件

Nginx 官方镜像开箱即用，把 dist 塞进它的默认根目录 /usr/share/nginx/html 就能当一个静态服务器：

shell$ docker run -d --name web -p 3000:80 \
    -v "$(pwd)"/dist:/usr/share/nginx/html:ro \
    nginx:1.27-alpine

$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/
200                                            # 首页正常
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/post/1
404                                            # ← 灾难现场：刷新文章详情页（W6 的真实路由 /post/:id）404 了

先别修，把这个 404 记住——下一节解释原理，然后一行配置根治它。

3. 重点：SPA history 路由为什么刷新 404，try_files 怎么救

history 模式原理（React Router 7 / history router）：你在站内从首页点进文章详情页时，Router 调用浏览器原生的 history.pushState()——它只改写地址栏并压入一条历史栈，不发任何网络请求，然后 React 在内存里换掉渲染的组件。所以"点进去"永远正常。

但当你刷新页面（或直接粘贴 URL 访问、别人转发给你的 /post/1 链接被点开）时，浏览器就真的向服务器发出 GET /post/1。Nginx 在 dist 目录里找一个叫 post/1 的文件——不存在，404。"路由"这个概念只活在 JS 里，服务器根本不知道。

解法：try_files——按顺序找文件，全都找不到就把 index.html 兜底返回。HTML 一加载，React Router 接管，根据地址栏 URL 渲染对应页面：

nginx.conf 节选location / {
    # $uri 原始路径 → $uri/ 目录 → 都没有就内部改写为 /index.html（返回 200）
    try_files $uri $uri/ /index.html;
}

副作用要知道：配了兜底之后，访问一个真不存在的静态资源（如 /logo-typo.png）也会返回 index.html + 200，排查图片 404 时容易被骗。更阴的一件事：后端那个 /health 探针在 nginx 里没有对应 location，浏览器直访 http://域名/health 会命中兜底的 location / → 返回 200 的 HTML，看代码的人以为后端健康，其实一行 Go 都没碰到——这就是"假绿探针"。两个应对：① /assets/（带 hash 的产物）单独设 location，不让它落进兜底（见第 5 节）；② D5 里要么加一条 location = /health 精确代理到后端，要么巡检脚本直接打后端容器的 8080，两边都讲。

hash 路由模式 #/post/1 不会有这个问题——# 后面的内容从不发给服务器。但 URL 丑、分享性差，本项目坚持 history 模式 + try_files 是标准答案。

4. proxy_pass：把 /api/v1 转给 Go 后端

同源部署后 CORS 都不需要了——浏览器眼里所有请求都来自同一个域名，Nginx 在内网替你转发：

nginx.conf 节选location /api/ {
    # backend 是容器/服务名，在共享网络里由 Docker DNS 解析（明天 compose 正式用）
    proxy_pass http://backend:8080;        # 结尾不写斜杠：路径原样透传

    # 三个标准透传头，否则后端日志里全是一个 IP、Host 也失真
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}

4.1 location 到底怎么匹配：为什么写 /api/ 而不是 /api/v1/

不带正则的 location 是"前缀匹配"：请求 URI 只要以这段字符串开头就算命中，所以 location /api/ 同时兜住 /api/v1/articles 和将来可能出现的 /api/v2/…；写成 location /api/v1/ 也完全能用，只是以后加版本要在 nginx 里再补一行。nginx 挑的是最长的那条命中规则（与书写顺序无关），全都匹配不上才落到 location /；location = /index.html 这种精确匹配优先级最高。两条纪律：

  • location 结尾的 / 要写：location /api（无斜杠）会连 /apifoo 都命中，属于意外通过。
  • 前端 baseURL 决定请求长什么样：W6 的 VITE_API_BASE=/api/v1 意味着产物里所有接口都是 /api/v1/… 开头 → location /api/ 稳命中。
浏览器请求的 URI命中的 location转发给后端的路径结果
/api/v1/articles?page=1&size=10/api//api/v1/articles?page=1&size=10（原样）200，Gin 的 r.Group("/api/v1") 命中
/api/v1/articles/1/api//api/v1/articles/1200
/api/v1/auth/login/api//api/v1/auth/login200 / 401（业务码，不是 nginx 的事）
/post/1/（try_files）不转发200 + index.html，前端路由接管
/health/（try_files）不转发200 + HTML ← 假绿探针，见第 3 节警告
/api/v1/articles/1，但 proxy_pass 结尾多写了 //api//v1/articles/1（前缀被剥掉）404 —— 经典事故
写法行为本项目
proxy_pass http://backend:8080;（不带结尾斜杠/路径）请求路径原样转发：/api/v1/articles → 后端收到 /api/v1/articles✔ 用这个（后端路由组本身带 /api/v1 前缀）
proxy_pass http://backend:8080/;（带结尾斜杠）把 location 前缀剥掉：/api/v1/articles → 后端收到 /v1/articles → 404✘ 经典"莫名其妙 404"来源

记一句就够：nginx 的 location 只管"哪些请求归我转发"，路径改不改由 proxy_pass 结尾有没有 URI 决定。本项目两端都保留 /api/v1，所以 proxy_pass 不带 URI。

4.2 兑现第 4 周的伏笔：后端必须 SetTrustedProxies

第 4 周 Day 4 讲访问日志时挂过一条 TODO："c.ClientIP() 拿的是与服务器建 TCP 连接那台机器的 IP，将来套上 Nginx 后所有人都会变成代理机的 IP，第 7 周用 SetTrustedProxies + X-Forwarded-For 处理"。今天就是第 7 周，两个动作配对：nginx 负责把真实来源写进请求头（上面那三行 proxy_set_header），后端负责决定信不信这些头。

现象（练习 4 组网后一定会看到）：所有请求在 backend 日志里的来源 IP 都是 nginx 容器的内网地址（172.18.0.x），W4 的访问日志、按 IP 限流、"最近登录地点"全部失效——因为 TCP 连接确实是从 nginx 来的。

backend/cmd/server/main.go（节选：改两行）r := gin.Default()                       // W4 就是这个，不动

// 紧跟其后、注册任何路由与中间件之前：声明"我只信 compose 内网网段送来的 X-Forwarded-For"
// Docker 给容器网络的地址通常落在 172.16.0.0/12（172.16–172.31 段），明天 D3 你会亲眼看到 172.18.0.2
r.SetTrustedProxies([]string{"172.16.0.0/12"})

r.GET("/health", func(c *gin.Context) { response.OK(c, gin.H{"status": "ok"}) })
// ... 后面的 /api/v1 路由组照 W4 原样 ...

三点必须讲清：

  • 放在哪里：r := gin.Default() 之后第一行。 Gin 的 Logger/AccessLog 中间件在请求到来时才读这张信任表，但你在中间件之后、甚至在某个 handler 里才设置，就等于前面的日志行已经用错值写出去了；放到路由注册之后虽然也能工作，但顺序读起来最容易被自己骗。
  • 为什么是 172.16.0.0/12：这是 Docker 容器网段所在的私有地址块。SetTrustedProxies 的语义是"当直连我的那台机器落在这个网段里，我才去解析 X-Forwarded-For 并把它当作 ClientIP"；否则一律用 TCP 直连地址。
  • 为什么不能写 0.0.0.0/0 / nil（全信任）：那等于任何客户端只要在请求头里塞 X-Forwarded-For: 1.2.3.4，你的日志和风控就照单全收——IP 可伪造。W4D4 那句"别现在就自行解析转发头"防的正是这个。
shell（验证信任表生效：故意打一个假 XFF）$ curl -s -H "X-Forwarded-For: 8.8.8.8, 1.1.1.1" http://localhost:3000/api/v1/articles > /dev/null

$ docker logs backend --tail 1
[GIN] 2026/09/28 - 21:02:11 | 200 |   1.234ms | 8.8.8.8       | GET      "/api/v1/articles"
# ↑ 设了信任表：nginx 在 172.16.0.0/12 内 → GIN 采纳 XFF 的第一个地址 8.8.8.8
# 没设那一行时这里会是 nginx 容器自己的 IP（172.18.0.2），真实访客全被抹成同一个人

顺带一条链路认知：nginx 容器里的 $remote_addr 是"连它的那个人"。你从宿主机 curl 时它是宿主机在该网段里的地址；到第 5 天套上 Caddy，它就变成真实访客 IP（Caddy 会把 XFF 续上）。信任网段这条线要从最外层一路通到后端，中间任何一层没转发或后端没信任，ClientIP 就断在那一格。

容器里的 localhost 陷阱（今天预习、明天主考）：在 nginx 容器内，proxy_pass http://localhost:8080 指向的是 nginx 容器自己，不是你的宿主机，更不是后端容器。本地想用 docker run 临时联调可以写 host.docker.internal:8080（宿主机地址），而正式方案永远是明天的容器网络服务名 backend。

5. GZIP 与缓存策略

nginx.conf 节选server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    # GZIP：JS/CSS 文本压缩率极高，1.9MB 产物传输时通常只剩 40–60%
    gzip on;
    gzip_comp_level 5;
    gzip_min_length 1024;          # 小于 1KB 压缩反而更亏（首部开销）
    gzip_types text/css application/javascript application/json image/svg+xml;

    # 带 hash 的构建产物：缓存一年没问题，内容变了名字自然变（见第 1 节）
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 入口 HTML 绝不缓存，否则发版后用户拿旧清单找不到新 JS
    location = /index.html {
        add_header Cache-Control "no-cache";
    }
}

验证 GZIP 生效：响应头要有 Content-Encoding: gzip。curl 默认不发 Accept-Encoding，要加 --compressed：curl -s -H "Accept-Encoding: gzip" -o /dev/null -w "%{size_download}\n" --compressed http://localhost:3000/assets/index-4f2a9c1e.js，对比文件原始大小。

今日名词卡

术语一句话解释
反向代理Nginx 代收浏览器请求、转发给内网服务再把响应原路送回，对外只暴露一个端口
history 模式用 pushState 改写地址栏的前端路由方案，URL 干净但要求服务器兜底返回 index.html
try_filesnginx 按序探测文件是否存在，最后一项通常写成内部跳转 /index.html
immutable 缓存配合内容 hash 文件名，让 /assets/ 下的产物被浏览器缓存一年
npm ci严格按 lock 文件安装、跳过交互式解析的干净安装命令，构建环境专用
前缀 location 匹配location /api/ = "URI 以 /api/ 开头的都归我"，最长的那条胜出，所以它同时兜住 /api/v1/*
X-Forwarded-For / X-Real-IP代理把"原始客户端 IP"逐跳写进请求头带下去；nginx 转发只是第一步
SetTrustedProxiesGin 侧的信任名单：只有直连来源在名单网段内，才采信 XFF 作为 ClientIP（W4D4 伏笔，4.2 兑现）
假绿探针不存在的路径被 try_files 兜成 index.html + 200，看状态码会误判服务健康
