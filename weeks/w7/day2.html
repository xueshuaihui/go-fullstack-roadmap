前端构建 + Nginx

课前须知

今天在 frontend/（第 6 周的 React + Vite 项目）下工作。约定沿用第 2 周起的口径：后端业务路由都挂在 /api 前缀下（/api/articles、/api/auth/login），健康检查在 /health；前端 axios 的请求基址是相对路径 /api（第 6 周 Day 5 的 VITE_API_BASE=/api）。这个约定是今天 proxy 配置成立的前提。

知识讲义

1. 先看产物：Vite build 之后的 dist 长什么样

shell（在 frontend/ 目录）$ npm run build

$ du -sh node_modules dist        # 感受一下"源码态 vs 产物态"的差距
412MB    node_modules
1.9MB    dist

$ find dist -type f
dist/index.html
dist/favicon.svg
dist/assets/index-4f2a9c1e.js     # JS 全部打包 + 压缩，文件名带内容 hash
dist/assets/index-7b3d81fa.css
dist/assets/vendor-a10c8f22.js

三个观察：

  • dist 只有 2MB 左右，而 node_modules 四百多 MB——部署只需要前者。昨天的道理在这里重演：构建环境（node_modules + 源码）不该进最终镜像。
  • 文件名带 hash（index-4f2a9c1e.js）：内容变、名字变；内容不变、名字不变。所以这些文件可以理直气壮地让浏览器缓存一年（immutable），发版用户自动拿新文件，这就是第 5 节缓存指令的依据。
  • index.html 的名字不带 hash，它是每次访问都要拿最新的"入口清单"。

2. 最小 nginx 容器：托管静态文件

Nginx 官方镜像开箱即用，把 dist 塞进它的默认根目录 /usr/share/nginx/html 就能当一个静态服务器：

shell$ docker run -d --name web -p 3000:80 \
    -v "$(pwd)"/dist:/usr/share/nginx/html:ro \
    nginx:1.27-alpine

$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/
200                                            # 首页正常
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/articles/1
404                                            # ← 灾难现场：刷新文章详情页 404 了

先别修，把这个 404 记住——下一节解释原理，然后一行配置根治它。

3. 重点：SPA history 路由为什么刷新 404，try_files 怎么救

history 模式原理（React Router 7 / history router）：你在站内从首页点进文章详情页时，Router 调用浏览器原生的 history.pushState()——它只改写地址栏并压入一条历史栈，不发任何网络请求，然后 React 在内存里换掉渲染的组件。所以"点进去"永远正常。

但当你刷新页面（或直接粘贴 URL 访问、别人转发给你的 /articles/1 链接被点开）时，浏览器就真的向服务器发出 GET /articles/1。Nginx 在 dist 目录里找一个叫 articles/1 的文件——不存在，404。"路由"这个概念只活在 JS 里，服务器根本不知道。

解法：try_files——按顺序找文件，全都找不到就把 index.html 兜底返回。HTML 一加载，React Router 接管，根据地址栏 URL 渲染对应页面：

nginx.conf 节选location / {
    # $uri 原始路径 → $uri/ 目录 → 都没有就内部改写为 /index.html（返回 200）
    try_files $uri $uri/ /index.html;
}

副作用要知道：配了兜底之后，访问一个真不存在的静态资源（如 /logo-typo.png）也会返回 index.html + 200，排查图片 404 时容易被骗。所以上面把 /assets/（带 hash 的产物）单独设了 location（见第 5 节），真实生产还会再为图片等加精确匹配。

hash 路由模式 #/articles/1 不会有这个问题——# 后面的内容从不发给服务器。但 URL 丑、分享性差，本项目坚持 history 模式 + try_files 是标准答案。

4. proxy_pass：把 /api 转给 Go 后端

同源部署后 CORS 都不需要了——浏览器眼里所有请求都来自同一个域名，Nginx 在内网替你转发：

nginx.conf 节选location /api/ {
    # backend 是容器/服务名，在共享网络里由 Docker DNS 解析（明天 compose 正式用）
    proxy_pass http://backend:8080;

    # 三个标准透传头，否则后端日志里全是一个 IP、Host 也失真
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
写法行为本项目
proxy_pass http://backend:8080;（不带结尾斜杠/路径）请求路径原样转发：/api/articles → 后端收到 /api/articles✔ 用这个（后端路由本身带 /api 前缀）
proxy_pass http://backend:8080/;（带结尾斜杠）把 location 前缀剥掉：/api/articles → 后端收到 /articles → 404✘ 经典"莫名其妙 404"来源

容器里的 localhost 陷阱（今天预习、明天主考）：在 nginx 容器内，proxy_pass http://localhost:8080 指向的是 nginx 容器自己，不是你的宿主机，更不是后端容器。本地想用 docker run 临时联调可以写 host.docker.internal:8080（宿主机地址），而正式方案永远是明天的容器网络服务名 backend。

5. GZIP 与缓存策略

nginx.conf 节选server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    # GZIP：JS/CSS 文本压缩率极高，1.9MB 产物传输时通常只剩 40–60%
    gzip on;
    gzip_comp_level 5;
    gzip_min_length 1024;          # 小于 1KB 压缩反而更亏（首部开销）
    gzip_types text/css application/javascript application/json image/svg+xml;

    # 带 hash 的构建产物：缓存一年没问题，内容变了名字自然变（见第 1 节）
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 入口 HTML 绝不缓存，否则发版后用户拿旧清单找不到新 JS
    location = /index.html {
        add_header Cache-Control "no-cache";
    }
}

验证 GZIP 生效：响应头要有 Content-Encoding: gzip。curl 默认不发 Accept-Encoding，要加 --compressed：curl -s -H "Accept-Encoding: gzip" -o /dev/null -w "%{size_download}\n" --compressed http://localhost:3000/assets/index-4f2a9c1e.js，对比文件原始大小。

6. 完整文件：前端多阶段 Dockerfile + nginx.conf

结构照抄第 6 周前端项目根目录，新增两个文件即可。

frontend/Dockerfile# ---------- 阶段一：构建（需要完整 node_modules，这层大但不要了）----------
FROM node:22-alpine AS build

WORKDIR /app

# 与 go mod download 同理：清单不变则 npm 安装层命中缓存
COPY package.json package-lock.json ./
RUN npm ci                       # ci 严格按 lock 安装、更快更可复现，CI/镜像首选

COPY . .
# 生产环境变量在构建时烧进产物（Vite 是构建期替换，不是运行期读取！）
ENV VITE_API_BASE=/api
RUN npm run build

# ---------- 阶段二：运行（只有 nginx + 2MB 静态文件）----------
FROM nginx:1.27-alpine

COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf   # 覆盖默认站点配置

EXPOSE 80
# nginx 镜像自带 CMD ["nginx","-g","daemon off;"]，无需再写；写 ENTRYPOINT 反而多此一举
frontend/nginx.conf（完整可抄）server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    gzip on;
    gzip_comp_level 5;
    gzip_min_length 1024;
    gzip_types text/css application/javascript application/json image/svg+xml;

    location /api/ {
        proxy_pass http://backend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}

今日练习

练习 1：产物观察（15 分钟）

本地 npm run build，执行 du -sh node_modules dist 与 find dist -type f；打开 dist/index.html 看它如何引用 assets 的 hash 文件名。把两个 du 数字记进笔记（这是"为什么镜像只要 50MB"的第一手证据）。

练习 2：亲手复现并修复刷新 404（25 分钟）

用第 2 节的 docker run -v .../dist nginx:alpine 挂载法：① 裸配置下 curl /articles/1 确认 404；② 在本地写一份只加 try_files 的最小 conf，追加挂载 -v $(pwd)/nginx.conf:/etc/nginx/conf.d/default.conf:ro 重启容器，再 curl 确认 200 且返回 index.html 内容。

要点：挂载配置文件改完后不用重建镜像，docker exec web nginx -s reload 或重跑容器即可——先习惯"配置即文件，文件可挂载"。

练习 3：产出前端镜像（必做，30 分钟）

抄录第 6 节三个文件（frontend/Dockerfile、frontend/nginx.conf、frontend/.dockerignore），构建 goblog-web:0.1。验收：docker images ≤ 60MB；curl / 与 curl /articles/1 均 200；curl -H "Accept-Encoding: gzip" --compressed -sI 大 JS 文件响应头含 Content-Encoding: gzip。

练习 4：一个容器内前端 + 代理全通（40 分钟）

不写 compose，用 docker network 手工把昨天的后端、一个 MySQL、今天的前端连成网，端到端打通 浏览器 → nginx → /api → Gin → MySQL：

shell$ docker network create goblog
$ docker run -d --name mysql --network goblog \
    -e MYSQL_ROOT_PASSWORD="<强占位符>" -e MYSQL_DATABASE=goblog \
    -e MYSQL_USER=goblog -e MYSQL_PASSWORD="<强占位符>" \
    -v mysql-demo:/var/lib/mysql mysql:8.0 --default-time-zone="+08:00"
$ docker run -d --name backend --network goblog -p 8080:8080 \
    -e MYSQL_DSN="goblog:<强占位符>@tcp(mysql:3306)/goblog?charset=utf8mb4&parseTime=True&loc=Local" \
    -e JWT_SECRET="$(openssl rand -base64 32)" -e GIN_MODE=release goblog-api:0.1
$ docker run -d --name frontend --network goblog -p 3000:80 goblog-web:0.1

# MySQL 首次初始化约 30 秒，等 backend 的 healthcheck 变 healthy 再测
$ curl -s http://localhost:3000/api/articles?page=1
{"code":0,"message":"success","data":{...}}   # ← 经 nginx 代理的完整链路！

参考答案排错：502 看 docker logs frontend——backend could not be resolved 说明两容器不在同一网络（docker network inspect goblog 检查 Containers）；500/连接库失败看 docker logs backend——DSN 主机必须是 mysql 而非 localhost（本练习已按此配好）。玩完 docker rm -f mysql backend frontend; docker network rm goblog 清理，明天交给 compose。
