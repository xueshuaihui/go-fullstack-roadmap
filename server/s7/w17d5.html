契约测试：客户端不得二次裁剪

红线原文你已经在 S7·D3 见过：面清单只能来自服务端下发，客户端不得二次裁剪、不得硬编码。今天回答一个工程问题：这是一条关于「客户端不做什么」的约定，服务端侧怎么把它变成能跑、能红的测试？答案：把它翻译成等价的服务端不变量——下发集合 == 应渲染集合，且渲染判定只依赖响应里的标记。

今日目标

知识讲义

1. 为什么「客户端不裁剪」需要服务端测试

如果服务端下发的清单本身就不是可渲染集合（少算了角色层、把没启用的面也当可用发出去），客户端就被迫拿本地信息补刀——硬编码一份「ward 不能看 finance」的名单，或者把 born 判断写死在打包配置里。红线就是这么被违反的：不是客户端想裁剪，是服务端没算完。

所以服务端侧的契约是：响应必须自足。翻译成两条不变量：

  1. 集合相等：对任意 (家庭, 角色)，把响应里满足渲染谓词（born ∧ enabled ∧ visible）的项挑出来，这个集合必须恰好等于从数据库状态 + registry + 角色矩阵独立推导出的「应渲染集合」。不多发（越权面泄露）、不少发（入口丢失）。
  2. 判定自足：渲染谓词的三个输入全部来自响应字段，客户端不需要任何本地知识（角色、硬编码名单、构建配置）就能算对。测试的表达方式：谓词函数只接受 Item，签名上没有第二个参数。

前端侧还有另一半契约测试（渲染出来的入口集合 == faces[] 里谓词为真的集合），归前端线的壳基座卡片管。服务端这半今天钉死：你下发的那份，就是该渲染的那份。

2. 期望集合怎么「独立推导」

契约测试最忌讳「用被测代码算期望值」——那叫同义反复，永远绿。正确做法是换一条路推导：

响应走的推导路径测试走的推导路径
handler → Compose → authz.ModuleVisible → JSON测试直接读 seed 时自己记下的配置（哪些 code 开了）+ registry 常量 + 手写的角色规则表

两条路径共享的只有原始事实（库里的行、registry 常量），不共享计算逻辑。这样 Compose 改错一个与号，测试立刻红。

3. 集合级断言，不是逐项顺序断言

比对用「code 集合」而不是「第 i 项」：目录顺序是实现细节，不该进契约；集合差（多了谁、少了谁）才是契约内容。断言失败信息要打印两个差集——出问题时你第一眼要知道的是「多发了 finance 给 ward」还是「少发了 homeos」。

步骤 1 · 契约测试

完整 · server/internal/homeos/faces/contract_test.gopackage faces

import (
    "context"
    "sort"
    "testing"

    "homecube/internal/homeos/model"
    "homecube/internal/platform/testdb"
)

// expectedRender 是测试侧的独立推导：不复用 Compose，不复用 authz。
// enabledCodes 由 seed 时记录；角色规则手写一份（与 registry 声明同源事实、不同代码路径）。
func expectedRender(role model.Role, enabledCodes map[string]bool) []string {
    hidden := map[model.Role][]string{
        model.RoleWard: {"finance"}, // 与 D1 registry 声明同源：ward 不可见财务（guest 可见）
    }
    var out []string
    for _, m := range All() {
        if !m.Born || !enabledCodes[m.Code] {
            continue
        }
        if role != model.RoleOwner {
            blocked := false
            for _, code := range hidden[role] {
                if code == m.Code {
                    blocked = true
                }
            }
            if blocked {
                continue
            }
        }
        out = append(out, m.Code)
    }
    sort.Strings(out)
    return out
}

// renderSet 模拟客户端唯一被允许的动作：按响应标记 filter。输入只有 Item 切片。
func renderSet(items []Item) []string {
    var out []string
    for _, it := range items {
        if it.ShouldRender() {
            out = append(out, it.Code)
        }
    }
    sort.Strings(out)
    return out
}

func TestContractNoClientSideTrimming(t *testing.T) {
    db := testdb.Open(t)
    // seed：homeos + finance 启用（S7·D2 的 seedFamily 口径），记录事实
    famID, _ := seedFamily(t, db)
    enabled := map[string]bool{"homeos": true, "finance": true}
    ctx := context.Background()

    for _, role := range []model.Role{model.RoleOwner, model.RoleMember, model.RoleWard} {
        items, err := Compose(ctx, db, famID, role)
        if err != nil {
            t.Fatal(err)
        }

        // 不变量一：下发集合（按标记 filter 后）== 独立推导的应渲染集合
        got, want := renderSet(items), expectedRender(role, enabled)
        if len(got) != len(want) {
            t.Fatalf("role=%d 下发=%v 应渲染=%v", role, got, want)
        }
        for i := range got {
            if got[i] != want[i] {
                t.Fatalf("role=%d 下发=%v 应渲染=%v", role, got, want)
            }
        }

        // 不变量二：判定自足——每个渲染结论都能由响应字段复算
        for _, it := range items {
            if it.ShouldRender() != (it.Born && it.Enabled && it.Visible) {
                t.Fatalf("%s 的谓词与标记不自洽", it.Code)
            }
            if role == model.RoleOwner && !it.Visible {
                t.Fatalf("owner 视角 %s visible 应恒真", it.Code)
            }
        }
    }
}

expectedRender 里那份手写的 hidden 表必须与 registry 的 VisibleRoles 声明保持同源事实。它故意不复用 registry 字段——复用就变成了「拿被测数据算期望」。代价是 D1 改可见集时这里要同步改一行，测试红了会提醒你；这份冗余正是契约测试的防呆机制。

常见坑（新手 100% 会踩）

坑现象正确姿势
用 Compose 的输出算期望值同义反复，Compose 改坏了测试照样绿期望值走独立推导路径，只共享原始事实
逐项按顺序断言目录调个顺序测试就红，契约被噪音淹没集合级比对（排序后比 / 差集），顺序不进契约
只测 ownerowner visible 恒真，四层里最容易的一层，测了等于没测至少 owner/member/ward 三角色；差异出现在角色层
断言失败只打 want/got 长度红是红了，不知道多了谁少了谁失败信息带两个完整集合（今天直接打切片）
从没弄红过测试可能因为 seed 不对根本没跑到断言故意破坏一次实现，确认能红，再改回来
把「客户端 filter 标记」当成二次裁剪吓得客户端硬编码全量渲染或不敢 filter按服务端标记 filter 是契约内动作；二次裁剪指动用本地知识再砍一刀

今日名词卡

术语一句话解释
契约测试把跨端约定翻译成两侧各自可执行的断言；今天钉服务端这半
二次裁剪客户端拿本地信息（角色、硬编码名单）对服务端清单再砍一刀——被禁止
判定自足渲染结论只依赖响应字段，不需要任何客户端本地知识
独立推导期望值不复用被测逻辑，只共享原始事实（库行、常量）
集合级断言比「谁多了谁少了」，不比顺序；顺序是实现细节
同源事实、不同路径hidden 表与 VisibleRoles 说的是同一件事，故意写两遍互为防呆
弄红再改回验证测试有效性的标准动作：破坏实现 → 确认红 → 还原 → 确认绿
不变量（invariant）任何输入下都必须成立的性质；测试是它的可执行形式
