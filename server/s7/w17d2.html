面启用配置：乐观锁 epoch 与变更审计

昨天把「目录」钉进代码，今天把「选择」落进数据库：每个家庭开了哪些面，存 homeos_family_module 表；改配置的接口 PUT /api/homeos/family/modules 走 version 乐观锁（这一行的 version 就是这份配置的 epoch），每次成功变更同时做三件事：写审计、全家 pver+1、版本 +1。审计表只落库、不提供任何查询接口——这是范围里明确砍掉的口子，今天要讲清为什么。

今日目标

知识讲义

1. 表存「选择」：每家庭每面一行

homeos_family_module 的行粒度是 (family_id, code)：7 个 code 每家庭 7 行，enabled 一个布尔。UNIQUE (family_id, code) 由数据库兜底，应用层不用防重。通用列（id/created_at/updated_at/deleted_at/deleted_by/version）照 S3 立的规矩一次建对。

两个口径今天定死：① homeos 基座行 enabled 恒真，且 PUT 对 code=homeos 一律拒绝（409 + 1010）——基座被关掉壳就没了；② 未出生面允许 enabled=true，语义是「预约开通」：面一出生自动生效，但渲染必须叠加 born，所以它现在不会出现在任何人的首页上。

2. 乐观锁 epoch：version 就是这份配置的纪元号

两个管理员同时改面配置怎么办？不加悲观锁，用你从 S6 就熟的乐观锁三拍：

  1. GET 时服务端把每行的 version 一并下发（明天面清单接口里它就是响应字段之一）；
  2. PUT 带上你看到的 version：{"code":"finance","enabled":false,"version":3}；
  3. 写库前比对：version 不等于库里当前值 → 说明有人先改了，返回 409 + 1009，响应体带双版本（你的 version 与库里当前 version），客户端拉新配置重来。

每次成功写 version+1——这个单调递增的行级版本号，就是这份面配置的 epoch（纪元号）：客户端手里的 epoch 落后了，写必然被拒。同一套机制 S6 在流水、账户、分类上已经用过三次，今天是第四次，写法完全一致。

1009 是全站唯一带 data 的失败响应（双版本 payload）。response.Fail 不带 data 参数，这一处直接用 response.Body 组装——例外只有这一个，别处不许模仿。

3. 审计只落库，不提供查询接口

「谁在什么时候把哪个面关了」要留痕：homeos_module_audit 追加一行（code、旧值、新值、操作者 member_id）。但注意范围口径：审计只落库，不做任何查询接口。为什么这么定：

  • 审计的消费者是「出问题之后翻记录的你」，不是界面上的用户。开一个查询接口 = 多一个要鉴权、要分页、要防越权的攻击面，而产品上没有一屏需要它。
  • 落库保证了可追溯（SQL 直查即可），不开接口保证了不膨胀。日后真有管理台需求，再登记进接口清单——先有需求再有接口，永远反过来。

这和「注册了但没实现/没用了的假入口」是同一纪律的两面：接口清单上的每一条都要有真实消费者；没有消费者的数据只落库。

4. 为什么改面配置要 pver+1

S4 立的规矩：token 里带 pver（权限版本）快照，库里成员行的 pver 一旦变大，旧 access token 校验不过（401 + 1005），客户端走 refresh 静默换新。角色变更要 pver+1，面配置变更同样要：面的开关直接决定「哪些路由域对你开放」（S7·D11 的路由门禁就查这个），配置变了，旧 token 里的权限视图就过期了。事务里一句 UPDATE homeos_member SET pver = pver + 1 WHERE family_id = ?，全家生效。

完整 · server/internal/homeos/faces/service.gopackage faces

import (
    "context"
    "errors"
    "fmt"

    "gorm.io/gorm"
    "gorm.io/gorm/clause"

    "homecube/internal/homeos/model"
    "homecube/pkg/response"
)

// ErrModuleNotConfigurable：homeos 基座面不可改（409 + 1010）。
var ErrModuleNotConfigurable = errors.New("基座面不可配置")

// UpdateResult 是 PUT 的成功返回：新状态 + 新 epoch。
type UpdateResult struct {
    Code    string `json:"code"`
    Enabled bool   `json:"enabled"`
    Version int    `json:"version"`
}

// ConflictError 携带双版本，供 handler 组 1009 的 data payload。
type ConflictError struct {
    CurrentVersion int `json:"current_version"`
    YourVersion    int `json:"your_version"`
}

func (e *ConflictError) Error() string {
    return fmt.Sprintf("版本冲突：当前 %d，你带的 %d", e.CurrentVersion, e.YourVersion)
}

// UpdateEnabled 是面启停的唯一写入口。一个事务四件事：
// 校验 epoch → 写配置（version+1）→ 落审计 → 全家 pver+1。
func UpdateEnabled(ctx context.Context, db *gorm.DB, familyID, memberID int64,
    code string, enabled bool, yourVersion int) (*UpdateResult, error) {

    if _, ok := Get(code); !ok {
        return nil, response.ErrNotFound // 目录外的 code 与「不存在」同形：404 + 1001
    }
    if code == "homeos" {
        return nil, ErrModuleNotConfigurable
    }

    var out UpdateResult
    err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        var row model.FamilyModule
        if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
            Where("family_id = ? AND code = ?", familyID, code).
            First(&row).Error; err != nil {
            return err // gorm.ErrRecordNotFound → 由 FailErr 映射 1001
        }
        if row.Version != yourVersion {
            return &ConflictError{CurrentVersion: row.Version, YourVersion: yourVersion}
        }
        if row.Enabled == enabled {
            out = UpdateResult{Code: code, Enabled: enabled, Version: row.Version}
            return nil // 状态未变：不写审计、不动 epoch，幂等返回
        }
        if err := tx.Model(&row).Updates(map[string]any{
            "enabled": enabled, "version": row.Version + 1,
        }).Error; err != nil {
            return err
        }
        audit := model.ModuleAudit{
            FamilyID: familyID, Code: code,
            OldEnabled: row.Enabled, NewEnabled: enabled,
            OperatorMemberID: memberID,
        }
        if err := tx.Create(&audit).Error; err != nil {
            return err
        }
        if err := tx.Exec("UPDATE homeos_member SET pver = pver + 1 WHERE family_id = ?", familyID).Error; err != nil {
            return err
        }
        out = UpdateResult{Code: code, Enabled: enabled, Version: row.Version + 1}
        return nil
    })
    if err != nil {
        return nil, err
    }
    return &out, nil
}

两个依赖说明：response.ErrNotFound 是 S1·D4 的哨兵（若你的命名不同，以 pkg/response 现有为准）；ConflictError 在 handler 里单独识别，不走哨兵映射，因为它要带 data。

步骤 3 · handler 与路由

完整 · server/internal/homeos/faces/handler.gopackage faces

import (
    "errors"
    "net/http"

    "github.com/gin-gonic/gin"
    "gorm.io/gorm"

    "homecube/internal/homeos/model"
    "homecube/internal/platform/authz"
    "homecube/pkg/response"
)

type updateReq struct {
    Code    string `json:"code" binding:"required"`
    Enabled *bool  `json:"enabled" binding:"required"`
    Version int    `json:"version" binding:"required"`
}

// PutModule PUT /api/homeos/family/modules —— 仅 owner（矩阵动作 module.update）。
func PutModule(db *gorm.DB) gin.HandlerFunc {
    return func(c *gin.Context) {
        role := c.MustGet("role").(model.Role)
        if !authz.Allow(role, authz.ActionModuleUpdate) { // S4 矩阵加一个动作，handler 不写角色分支
            response.Fail(c, http.StatusForbidden, response.CodeForbidden, "权限不足")
            return
        }
        var req updateReq
        if err := c.ShouldBindJSON(&req); err != nil {
            response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数错误")
            return
        }
        res, err := UpdateEnabled(c.Request.Context(), db,
            c.GetInt64("familyID"), c.GetInt64("memberID"),
            req.Code, *req.Enabled, req.Version)

        var conflict *ConflictError
        switch {
        case errors.As(err, &conflict): // 1009：全站唯一带 data 的失败响应
            c.JSON(http.StatusConflict, response.Body{
                Code: response.CodeVersionConflict, Message: "版本冲突", Data: conflict,
            })
        case errors.Is(err, ErrModuleNotConfigurable):
            response.Fail(c, http.StatusConflict, response.CodeStateNotAllowed, err.Error())
        case err != nil:
            response.FailErr(c, err)
        default:
            response.OK(c, res)
        }
    }
}

func TestUpdateEnabled(t *testing.T) {
    db := testdb.Open(t)
    famID, memID := seedFamily(t, db)
    ctx := context.Background()

    // ① happy path：停用 finance，epoch 3→ 假设为 1→2
    res, err := UpdateEnabled(ctx, db, famID, memID, "finance", false, 1)
    if err != nil || res.Version != 2 {
        t.Fatalf("happy path: res=%+v err=%v", res, err)
    }

    // ② 旧 epoch 再写 → ConflictError（1009 的双版本来源）
    _, err = UpdateEnabled(ctx, db, famID, memID, "finance", true, 1)
    var conflict *ConflictError
    if !errors.As(err, &conflict) || conflict.CurrentVersion != 2 {
        t.Fatalf("旧 version 应冲突: err=%v", err)
    }

    // ③ 基座面不可配置 → 1010 哨兵
    _, err = UpdateEnabled(ctx, db, famID, memID, "homeos", false, 1)
    if !errors.Is(err, ErrModuleNotConfigurable) {
        t.Fatalf("homeos 应拒绝: err=%v", err)
    }

    // ④ 审计恰落一行，且只落库——包里没有也不许有查询审计的 handler
    var n int64
    db.Model(&model.ModuleAudit{}).Where("family_id = ?", famID).Count(&n)
    if n != 1 {
        t.Fatalf("审计行数 = %d, want 1（②③均失败，不该有审计）", n)
    }

    // ⑤ 全家 pver +1
    var pver int
    db.Model(&model.Member{}).Where("id = ?", memID).Pluck("pver", &pver)
    if pver != 1 { // 初始 0，成功后 1（初始值以你的 S4 迁移为准）
        t.Fatalf("pver = %d, want 1", pver)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
先 SELECT 再 UPDATE，不在一个事务里并发下两个请求都拿到 version=1，都写成功，审计出现两条矛盾的变更记录事务 + FOR UPDATE 锁行（今天用的 clause.Locking），比对与写在同一事务
1009 响应不带双版本客户端只知道冲突，不知道该拿哪个版本重来data:{"current_version":…,"your_version":…}，全站唯一带 data 的失败响应
审计开了查询接口多一个要鉴权分页的口子，产品上没有消费者只落库；要翻记录 SQL 直查
忘了 pver+1管理员关了面，其他成员旧 token 还能打该面的接口（到 S7·D11 之前毫无拦截）配置变更与 pver+1 同事务，原子生效
状态没变也 version+1、也写审计客户端重试一次 PUT，epoch 白白跳号，审计全是噪音幂等返回：状态相同则不写审计、不动 epoch
down.sql 只 drop 一张表回滚后残留孤儿表，迁移序列脏了up 建几张 down 就 drop 几张，逆序

今日名词卡

术语一句话解释
epoch（纪元号）单调递增的配置版本号；这里就是 homeos_family_module.version，写一次 +1
乐观锁不锁资源，写时比对 version；不匹配 → 409 + 1009 + 双版本 payload
FOR UPDATE事务内锁住读到的行，防止「比对完、写入前」被人插队
审计（audit）变更留痕：谁、何时、把哪个面从什么改成什么。只落库，无查询接口
pvertoken 里的权限版本快照；库里的值变大 → 旧 access token 401 + 1005
幂等返回目标状态与当前一致时不写任何东西，直接返回现状
预约开通未出生面 enabled=true：配置先生效，渲染等 born
errors.As把 error 链里的目标类型取出来（S1·D4 讲过 errors.Is，As 是取指针版）
回填（backfill）迁移里给存量数据补新表的行，让老家庭无缝进入新口径
testdb.Open(t)本阶段约定的集成测试入口：读 DB_* 环境变量，未设则 skip

卡壳时查什么

  • 乐观锁的完整三拍想复习：S6 的流水编辑（PUT 带 version）与账户编辑，同一机制用过三次。
  • 迁移 up/down 与编号规矩：S3 整段（两个 code 独立计数、down 必须真能回滚）。
  • pver 与 token 失效链路：S4 的 Claims 与权限版本那课。
  • GORM 事务写法：S3 换真库那几天的 db.Transaction。
