到期中心三对象与注册表

S7 前半把「面」装好了：哪些面出生、哪些面启用、首屏一个请求拿全。从今天起进入到期中心——全家里所有「到点该发生的事」都归它管：提醒、待办、日历事件，外加财务面注册过来的预算周期与周期记账日。今天不写接口，只打数据地基：三张表的迁移 + 三个 model，以及贯穿整周的主角——幂等键 (source_system, source_id, kind)。

知识讲义

1. 到期中心是什么：一个 scheduler，不是七个

家里的「时间事务」来自四面八方：吃药提醒、交房租的待办、结婚纪念日、预算周期快结束、周期记账明天要执行。最糟的做法是每个业务面自建一个定时器——财务面一个 goroutine、提醒一个 goroutine，各扫各的表，重复通知没人管，关掉一个面还得记得停它的定时器。

到期中心把这件事收成一个：全进程只有一个调度器（本周 S7·D16 落地），业务面不建任何定时器，只做一件事——把「什么东西、什么时候到期」注册进来。注册走进程内接口（明天 S7·D14 建 DueRegistry），日历、提醒、通知全部从注册表投影出来。这正是 S7 阶段判据之一：「到期中心的提醒不由各业务模块自建定时器」。

2. 三对象一注册表

对象是什么落在哪
Reminder（提醒）到点通知某人；可周期重复、可设提前量、可暂停独立表 homeos_reminder
Todo（待办）分配给人、有完成态；勾选即完成独立表 homeos_todo
CalendarEvent（日历事件）日历三视图（日/周/月）上的一格没有独立表——它是注册表的投影

CalendarEvent 为什么没表？两个原因：① 日历自己不产生内容，它只聚合各面注册进来的到期项——「本周有什么」= 注册表里 due_at 落在本周的行；② 手工补录日历事件的接口在范围裁剪时已被砍掉，如果建一张没人写的表，就是「注册了但没用的假入口」那类死代码。所以：Reminder 和 Todo 是内容，CalendarEvent 是视图。视图的数据源就是注册表。

注册表 homeos_due_registry 每行代表「一个到期项」：不管它来自 homeos 自己的提醒/待办，还是 finance 注册的预算周期、周期记账，一律一行。首页 summary 的 due_today（S7 前半已接的占位）从本周起有了真数据源。

3. 幂等键：(source_system, source_id, kind)

注册可能发生很多次：创建规则时注册一次，编辑时间后再注册一次，暂停又撤销一次，恢复再来一次。如果每次都 INSERT，同一件事会在注册表里长出好几行——到期时用户收到三条一样的通知。防重复的办法不是「先 SELECT 看看有没有再 INSERT」（并发下照样穿），而是把唯一性交给数据库：

片段 · 幂等键三字段UNIQUE (source_system, source_id, kind)
-- source_system：哪个面注册的（'homeos' / 'finance'，即面目录里的 code）
-- source_id：源对象自己的 id（reminder 的 id、周期记账规则的 id……）
-- kind：到期种类（'reminder' / 'todo' / 'budget_cycle' / 'recurring_entry'……）

逐字段问「少了它会怎样」：

  • 少 source_system：homeos 的 reminder#7 和 finance 的规则#7 撞键，互相覆盖。
  • 少 source_id：同一面的两个到期项撞键，第二个注册不进去。
  • 少 kind：同一个源对象可能有两种到期语义——一条周期记账规则既有「执行日」也有「提前一天的提醒」，两行注册合法，撞键就只剩一行。

有了唯一索引，注册就写成 upsert：冲突则更新 due_at / title / status。改时间不用「先撤销再注册」，同一个键再 Register 一次即可（明天细讲）。

4. status 三态

status含义谁写
registered在册，等着到期Register（注册/重新注册）
revoked已撤销（暂停、删除源对象）——标记，不删行Revoke
fired已触发（通知已发出 / 已完成回写）调度器或 Complete

撤销为什么标记不删行？留痕才能对账：「上个月为什么没提醒我」这种问题，只有留着 revoked 行才答得上来。S7·D15 展开。

// Reminder 提醒：到点通知，可周期、可提前、可暂停。
type Reminder struct {
    ID             int64          `gorm:"primaryKey" json:"id"`

常见坑（新手 100% 会踩）

坑现象正确姿势
不建唯一索引，靠代码「先查再插」单测全绿，并发一跑就出重复行、重复通知幂等靠数据库唯一约束兜底，代码层用 upsert
把 due_at 塞进唯一键改一次到期时间就多一行注册，旧行永远在册时间不是身份的一部分；改时间 = 同键 upsert 更新
撤销时 DELETE 注册行「为什么没提醒我」无从查起，恢复暂停还得重建status 改 revoked，行留着
给 CalendarEvent 建表没有任何接口往里写，成了死表日历是注册表的投影；没有写路径的表不建
kind 用裸字符串到处散写拼错一个字母（remider）编译不报错，运行时静默不触发常量收口：今天先在 model，D14 升格进 platform 契约包
down 迁移只写一半回滚失败，up→down→up 重放断链三张表一个不少地 DROP，重放一遍验证

今日名词卡

术语一句话解释
到期中心全进程唯一的到期调度与注册台账；业务面只注册，不自建定时器
注册表（registry）homeos_due_registry：每个到期项一行，日历/首页 due_today 的数据源
幂等键(source_system, source_id, kind) 唯一索引；重复注册收敛为同一行的更新
upsert有则更新、无则插入；由数据库的唯一约束 + ON CONFLICT 实现，不靠先查后插
投影 / 读模型CalendarEvent 不存数据，只是注册表按时间窗过滤后的另一种读法
source_system到期项来自哪个面（面目录里的 code），跨模块注册的「户口」
registered / revoked / fired注册表 status 三态：在册 / 已撤销（留痕不删）/ 已触发
提前量（advance）提醒在 due_at 之前多少分钟触发，reminder 自己的字段，注册表存换算后的 due_at
深链（deep link）payload 里存的「前往源对象」跳转信息，S7·D18 的详情接口返回

卡壳时查什么

正文自足。只有三种情况往回翻：

  • 迁移 up/down 重放的手感忘了：回 S3 的 golang-migrate 卡，判据同为「up→down→up 不断链」。
  • 通用列（family_id / 软删 / version）为什么长这样：回 S3 建表卡与 S6 乐观锁卡。
  • 「不自建定时器」到底防什么：回看本阶段总览的阶段判据，S7·D16 调度器落地时会再讲一遍。

SQL 报错先读第一行：唯一约束冲突会明说 uq_due_idem——约束名起得好，报错自带导航。
