到期触发与完成回写

注册表躺在库里三天了，今天让它动起来：全进程唯一的调度器落地——定时扫描 registered 且到点的行，触发（写通知、置 fired）；周期项的改排周六随 PUT reminders 一起落。同时接两条待办接口：POST /api/homeos/todos 与 PUT /api/homeos/todos/{id}，勾选完成时走 Complete 回写注册表。回写失败怎么办？进对账清单留痕——死信队列那套属于消息中间件的能力，本课程范围外，不承诺周次。

知识讲义

1. 一个调度器，扫一张表

调度器就是「一个 goroutine + 一个 Ticker + 一次扫描」（goroutine 与优雅关闭是 S5 的手艺，今天照用）：

片段 · 循环形态每 30s：SELECT * FROM homeos_due_registry
        WHERE status = 'registered' AND due_at <= now()
对每一行：触发（写通知 + status→fired）
        周期项则改排下一轮 due_at、status 留 registered（周六 S7·D18 落地，今天先只做一次性触发）
  • 唯一性：Ticker 只在 duecenter 出现一次。财务面、以后的任何面都不许自建定时器——它们只有注册权。这就是阶段判据「到期中心的提醒不由各业务模块自建定时器」的落点。
  • 扫描是幂等的：就算一个 tick 里崩了、下个 tick 重扫，fired 的行不会再命中（status 已不是 registered）。
  • 测试友好：循环体抽成 RunOnce(ctx)，测试不起 Ticker 直接调它——S5 起的老手艺：把「时间」从逻辑里剥出去。

2. 触发时通知谁：payload 里的 member_id

注册行的 payload（JSONB）里存着 member_id——注册时就知道该通知谁（提醒的创建者、待办的负责人），触发时不用再回查源表。调度器读 payload 写 homeos_notification 行（S3 建的表，kind 今天先写字符串 "reminder"，S7·D19 分型常量化时当场还债）。

JSONB 反序列化的坑：payload 读回 map[string]any 后，数字一律是 float64（Go 的 JSON 惯例），直接当 int64 用会编译不过或静默丢精度。正确姿势见今日增量的 recipientOf。

3. 完成回写：先业务、后台账

勾选待办的顺序有讲究：

步骤动作失败了怎么办
①事务内更新待办行：status=done、done_at、done_by、version+1（带 version 条件，冲突 409 + 1009）整体失败，返回错误——业务动作没发生，什么也不用补
②提交后调 Complete 回写注册表（status→fired）不回滚①：待办确实完成了；写一行对账清单留痕

为什么②失败不回滚①？因为②是台账动作，不是业务动作——用户的待办完成了是事实，注册表没跟上只是「日历可能多显示一条已完成的事」，属于可补的差异。把台账失败升级成业务失败，用户会莫名其妙「勾选不成功」。

4. 对账清单，不是死信队列

正规军做法是消息队列 + 死信队列：失败消息进死信，可重放。本课程范围明确放弃消息中间件，替代物是一张只追加的表 homeos_due_reconcile：谁、哪一步、什么错、什么时候。它不自动重放——留痕 + 可人工补就是它的全部职责。范围外的东西只留一句前瞻：日后若真上队列，这张表降级为审计日志，调用点不用改。

注意它的列故意「不合常规」：没有 version、没有软删列。对账行只追加、不修改、不删除（处理完写 resolved_at），不是业务对象，全站通用列纪律在它身上裁剪掉这两件——这是本阶段第一个明账裁剪，记进 notes。

步骤 2 · 调度器

完整 · server/internal/homeos/duecenter/scheduler.gopackage duecenter

import (
    "context"
    "time"

    "gorm.io/gorm"

    "homecube/internal/homeos/model"
)

// Scheduler 全进程唯一的到期调度器。业务面只有注册权，没有定时权。
type Scheduler struct {
    db       *gorm.DB
    interval time.Duration
}

func NewScheduler(db *gorm.DB) *Scheduler {
    return &Scheduler{db: db, interval: 30 * time.Second}
}

// Run 阻塞循环，交给 main.go 起 goroutine；ctx 取消即优雅退出（S5）。
func (s *Scheduler) Run(ctx context.Context) {
    t := time.NewTicker(s.interval)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-t.C:
            _ = s.RunOnce(ctx) // 单轮失败只留痕不中断循环；错误细节进日志（S5）
        }
    }
}

// RunOnce 扫一轮到期行。测试直接调它，不起 Ticker。
func (s *Scheduler) RunOnce(ctx context.Context) error {
    var due []model.DueRegistry
    if err := s.db.WithContext(ctx).
        Where("status = ? AND due_at <= ?", model.DueStatusRegistered, time.Now()).
        Find(&due).Error; err != nil {
        return err
    }
    for i := range due {
        if err := s.fire(ctx, &due[i]); err != nil {
            Reconcile(ctx, s.db, &due[i], "fire", err) // 失败留痕，继续下一行
        }
    }
    return nil
}

// fire 触发一行：写通知 + 置 fired（一条事务）。
func (s *Scheduler) fire(ctx context.Context, row *model.DueRegistry) error {
    return s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        n := model.Notification{
            FamilyID: row.FamilyID, MemberID: recipientOf(row),
            Kind: "reminder", // 先硬编码；S7·D19 分型常量化时替换（当场还债）
            Title: row.Title, Body: "到期：" + row.Title,
        }
        if err := tx.Create(&n).Error; err != nil {
            return err
        }
        return tx.Model(&model.DueRegistry{}).
            Where("id = ? AND status = ?", row.ID, model.DueStatusRegistered).
            Updates(map[string]any{"status": model.DueStatusFired, "updated_at": gorm.Expr("now()")}).Error
    })
}

// recipientOf 从 payload 取「通知谁」。JSONB 数字读回是 float64——本站名坑。
func recipientOf(row *model.DueRegistry) int64 {
    if v, ok := row.Payload["member_id"].(float64); ok {
        return int64(v)
    }
    return 0 // 没有收件人的注册行不该存在；真出现则通知落 member_id=0，对账时一眼可见
}

// Reconcile 写对账清单：只追加，不重试，不阻塞。
func Reconcile(ctx context.Context, db *gorm.DB, row *model.DueRegistry, stage string, cause error) {
    rec := model.DueReconcile{
        FamilyID: row.FamilyID, SourceSystem: row.SourceSystem,
        SourceID: row.SourceID, Kind: row.Kind, Stage: stage, ErrText: cause.Error(),
    }
    if err := db.WithContext(ctx).Create(&rec).Error; err != nil {
        // 对账行都写不进去时只剩日志一条路；别让兜底的兜底再 panic
        _ = err
    }
}

步骤 3 · 两条待办接口

完整 · server/internal/homeos/service/todo.gopackage service

import (
    "context"
    "errors"
    "fmt"
    "time"

    "gorm.io/gorm"

    "homecube/internal/homeos/duecenter"
    "homecube/internal/homeos/model"
    "homecube/internal/platform/dueregistry"
    "homecube/pkg/response"
)

type TodoService struct {
    db  *gorm.DB
    due *duecenter.Inproc
}

func NewTodoService(db *gorm.DB, due *duecenter.Inproc) *TodoService {
    return &TodoService{db: db, due: due}
}

// Create 待办：有截止日才注册进到期中心（没截止的事不占日历）。
func (s *TodoService) Create(ctx context.Context, familyID, memberID int64, title string, dueAt *time.Time, assignee *int64) (*model.Todo, error) {
    td := &model.Todo{FamilyID: familyID, CreatedBy: memberID, Title: title, DueAt: dueAt, AssigneeMemberID: assignee, Status: "open", Version: 1}
    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(td).Error; err != nil {
            return err
        }
        if td.DueAt == nil {
            return nil
        }
        who := td.CreatedBy
        if td.AssigneeMemberID != nil { who = *td.AssigneeMemberID }
        return s.due.WithTx(tx).Register(ctx, dueregistry.Entry{
            FamilyID: familyID, SourceSystem: "homeos", SourceID: td.ID,
            Kind: dueregistry.KindTodo, Title: td.Title, DueAt: *td.DueAt,
            Payload: map[string]any{"member_id": who},
        })
    })
    return td, err
}

// Complete 勾选完成：①事务内更新业务行（version 乐观锁）②提交后回写注册表，失败进对账。
func (s *TodoService) Complete(ctx context.Context, familyID, memberID, todoID int64, ver int) (*model.Todo, error) {
    var td model.Todo
    if err := s.db.WithContext(ctx).
        Where("id = ? AND family_id = ?", todoID, familyID).First(&td).Error; err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) { return nil, response.ErrNotFound } // 越权读同形：404+1001
        return nil, err
    }
    if td.Version != ver {
        return nil, fmt.Errorf("%w: 提交 version=%d, 当前 version=%d", response.ErrConflict, ver, td.Version)
    }
    now := time.Now()
    res := s.db.WithContext(ctx).Model(&model.Todo{}).
        Where("id = ? AND family_id = ? AND version = ?", todoID, familyID, ver).
        Updates(map[string]any{"status": "done", "done_at": now, "done_by": memberID,
            "version": gorm.Expr("version + 1"), "updated_at": now})
    if res.Error != nil { return nil, res.Error }
    if res.RowsAffected == 0 { return nil, response.ErrConflict } // 并发抢先：409+1009 由 FailErr 映射

    // ② 台账回写：业务已提交，失败不回滚，进对账清单
    if err := s.due.Complete(ctx, "homeos", todoID, dueregistry.KindTodo); err != nil {
        row := &model.DueRegistry{FamilyID: familyID, SourceSystem: "homeos", SourceID: todoID, Kind: string(dueregistry.KindTodo)}
        duecenter.Reconcile(ctx, s.db, row, "writeback", err)
    }
    td.Status, td.DoneAt, td.DoneBy, td.Version = "done", &now, &memberID, ver+1
    return &td, nil
}

response.ErrConflict 到 1009 的映射若在你本地是独立哨兵（比如 ErrVersionConflict），以本地 S1 错误码卡落的名字为准——判据不变：version 不匹配返回 409 + 1009，且响应能看出两个版本号。路由装配照 S7·D15 的样子加两行：homeos.POST("/todos", ...)、homeos.PUT("/todos/:id", ...)，main.go 里起调度器：go sched.Run(ctx)（ctx 接 S5 的优雅关闭）。

import (
    "context"
    "testing"
    "time"

    "homecube/internal/homeos/model"
)

func TestRunOnceFiresOverdue(t *testing.T) {
    db := openTestDB(t)
    s := NewScheduler(db)
    ctx := context.Background()

    row := model.DueRegistry{FamilyID: 1, SourceSystem: "homeos", SourceID: 7,
        Kind: "reminder", Title: "交房租", DueAt: time.Now().Add(-time.Minute),
        Status: model.DueStatusRegistered, Payload: map[string]any{"member_id": float64(3)}, Version: 1}
    if err := db.Create(&row).Error; err != nil { t.Fatal(err) }

    if err := s.RunOnce(ctx); err != nil { t.Fatal(err) }

    db.First(&row, row.ID)
    if row.Status != model.DueStatusFired { t.Fatalf("status = %q, want fired", row.Status) }
    var n int64
    db.Model(&model.Notification{}).Where("family_id = 1 AND member_id = 3").Count(&n)
    if n != 1 { t.Fatalf("通知行数 = %d, want 1", n) }

    // 再跑一轮：fired 行不重复触发（扫描幂等）
    if err := s.RunOnce(ctx); err != nil { t.Fatal(err) }
    db.Model(&model.Notification{}).Where("family_id = 1 AND member_id = 3").Count(&n)
    if n != 1 { t.Fatalf("二轮后通知行数 = %d, want 仍为 1", n) }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
payload 数字直接断言 int64断言失败，通知发给 member_id=0JSONB 读回是 float64，int64(v) 显式转换
回写失败就回滚业务用户「勾选不成功」，其实台账差异可补先业务后台账；台账失败进对账清单
把对账清单做成自动重试队列悄悄重试、悄悄丢，最后没人知道失败过只追加留痕；重放是范围外的消息队列的事
fire 里忘了带 status 条件两个 tick 重叠时同一行触发两次、两条通知UPDATE 带 status='registered' 条件，天然互斥
在业务 service 里再起一个 Ticker「就扫我自己的表」定时器越繁殖越多，关掉一个面漏停一个grep 验收：全进程 Ticker 只许 duecenter 一处
PUT 不带 version 直接 UPDATE并发勾选互相覆盖，done_by 张冠李戴S6 的乐观锁手艺原样搬：version 条件 + 冲突 409 + 1009

今日名词卡

术语一句话解释
调度器（scheduler）Ticker + 扫描循环；全进程唯一，业务面只注册不定时
RunOnce把循环体抽成单次函数：测试不起 Ticker，逻辑与时间解耦
fired已触发：通知已写、行已置 fired；扫描幂等的关键
完成回写业务对象完成后同步注册表状态；先业务后台账，失败不反噬业务
对账清单homeos_due_reconcile：失败留痕、可人工补；死信队列的范围外替代
死信队列消息中间件里存放反复失败消息的队列，可重放——本课程范围外，只作前瞻
乐观锁UPDATE 带 version 条件，RowsAffected=0 即冲突：409 + 1009（S6 建的手艺）
float64 陷阱JSON 反序列化进 map[string]any 后数字一律 float64

卡壳时查什么

正文自足。往回翻的三种情况：

  • goroutine / Ticker / ctx 取消的手感：回 S5 并发段——调度器就是那套手艺的原样应用。
  • 乐观锁与 1009 的响应形态：回 S6 的 PUT 流水卡，双版本 payload 的口径从那里沿用。
  • 哨兵错误与 FailErr 映射：回 S1·D4 与 S2 的响应写出卡。
