未读口径唯一：三个出口同值的第一个出口

底栏角标那个小红点，是全站最容易被做出三个不同数字的地方。未读数会有三个出口：首页 summary 的 unread、通知列表接口的响应、标记已读接口的响应（后两个属本阶段后半的通知域）。今天把「唯一口径」立死：read_at IS NULL，按 member_id 聚合，只有一份函数实现——并把第一个出口（summary.unread）接上真数据。通知表与分型枚举也今天落库：表先行、接口后半，读的一侧从今天起就是真的。

今日目标

知识讲义

1. 一个口径，三个出口

结构                        ┌─ 出口①  GET /api/homeos/home/summary → unread.count   （今天接真）
UnreadCount(family, member) ─┼─ 出口②  通知列表接口 → 响应带 unread                （本阶段后半）
                        └─ 出口③  标记已读接口 → 响应带同一份 unread          （本阶段后半）

「三个出口同值」不是巧合要求，是实现要求：三个 handler 都只准调 notify.UnreadCount 这一个函数。谁在自己包里再写一遍 COUNT(*) … read_at IS NULL，谁就是未来的不一致源头——比如某处手滑加了 AND type != 'system'，于是角标和列表页永远差一个数，用户以为 app 有鬼。

为什么标已读的响应也要带 unread？因为客户端标完已读要立刻刷新角标。响应自带新值 = 少一个请求，且这个数字与刚完成的写操作在同一连接、同一时刻算出，不存在「标完已读角标还亮着」的时序缝隙。这是聚合思维在写接口上的应用。

2. 为什么按 member_id 聚合

  • 一个账号可以属于多个家庭（切换家庭 = 换 token，S4 口径）。未读是「这个家庭里给我看的」，跟着会话家庭走：token 里的 familyID + memberID 就是聚合键。
  • 无账号成员没有未读：ward 可以没有账号，通知发给了「成员」，但没有登录态就没有角标——这是产品事实，不是缺陷。
  • 按 user_id 聚合会把两个家庭的未读加在一起，切换家庭后角标数字对不上眼前这个家，直接违反「当前会话家庭」的世界观。

3. 表设计与分型

homeos_notification 每行是「发给某个成员的一条通知」。分型三个，落成 Go 常量（写死枚举，不用自由字符串）：

type来源举例备注
budget_alert预算告警（财务面的阈值触发，经 platform 接口写入）跨面写入照跨模块纪律走接口，不直查表
system成员变更、邀请结果、面配置变更提示
reminder到期中心的提醒到点生产者是本阶段后半的到期中心

未读查询的索引按查询长：部分索引 WHERE read_at IS NULL，只索引未读行——已读行再多，索引不膨胀。这是「索引跟着谓词走」的第一次实战。

今天只建表 + 枚举 + 读侧（UnreadCount）。通知的列表接口、标已读接口、推送设备注册都属本阶段后半的通知域，今天一个都不写。写入侧同样后置：测试用直接插行造数。

import "time"

// 通知分型：写死枚举，入库前校验，不接受自由字符串。
const (
    TypeBudgetAlert = "budget_alert"
    TypeSystem      = "system"
    TypeReminder    = "reminder"
)

func ValidType(t string) bool {
    switch t {
    case TypeBudgetAlert, TypeSystem, TypeReminder:
        return true
    }
    return false
}

type Notification struct {
    ID        int64      `gorm:"primaryKey"`
    FamilyID  int64      `gorm:"not null"`
    MemberID  int64      `gorm:"not null"`
    Type      string     `gorm:"not null"`
    Title     string     `gorm:"not null"`
    Body      string     `gorm:"not null;default:''"`
    ReadAt    *time.Time // NULL = 未读
    CreatedAt time.Time
    UpdatedAt time.Time
    DeletedAt *time.Time
    DeletedBy *int64
    Version   int        `gorm:"not null;default:1"`
}

func (Notification) TableName() string { return "homeos_notification" }
完整 · server/internal/homeos/notify/unread.gopackage notify

import (
    "context"

    "gorm.io/gorm"
)

// UnreadCount 是全站未读数的唯一实现。
// 口径：read_at IS NULL，按 (family_id, member_id) 聚合。
// 三个出口（summary.unread、通知列表、标记已读响应）都只准调本函数，
// 任何地方不得复制这段查询——复制即口径分叉的开始。
func UnreadCount(ctx context.Context, db *gorm.DB, familyID, memberID int64) (int64, error) {
    var n int64
    err := db.WithContext(ctx).
        Model(&Notification{}).
        Where("family_id = ? AND member_id = ? AND read_at IS NULL", familyID, memberID).
        Count(&n).Error
    return n, err
}

import (
    "context"
    "testing"
    "time"

    "homecube/internal/platform/testdb"
)

func TestUnreadCountScope(t *testing.T) {
    db := testdb.Open(t)
    ctx := context.Background()
    const fam, me, other = int64(9001), int64(11), int64(12)
    now := time.Now()

    // 固定 id 造数 → 必须清场，否则重跑测试计数会翻倍
    t.Cleanup(func() {
        db.Unscoped().Where("family_id IN ?", []int64{fam, fam + 1}).Delete(&Notification{})
    })

    seed := []Notification{
        {FamilyID: fam, MemberID: me, Type: TypeSystem, Title: "未读1"},
        {FamilyID: fam, MemberID: me, Type: TypeReminder, Title: "未读2"},
        {FamilyID: fam, MemberID: me, Type: TypeBudgetAlert, Title: "已读", ReadAt: &now}, // 已读：不算
        {FamilyID: fam, MemberID: other, Type: TypeSystem, Title: "别人的"},              // 别人的：不算
        {FamilyID: fam + 1, MemberID: me, Type: TypeSystem, Title: "别家庭的"},           // 别家庭：不算
    }
    for i := range seed {
        if err := db.Create(&seed[i]).Error; err != nil {
            t.Fatal(err)
        }
    }

    n, err := UnreadCount(ctx, db, fam, me)
    if err != nil || n != 2 {
        t.Fatalf("UnreadCount = %d, err = %v, want 2", n, err)
    }
}

func TestValidType(t *testing.T) {
    for _, ok := range []string{TypeBudgetAlert, TypeSystem, TypeReminder} {
        if !ValidType(ok) {
            t.Fatalf("%s 应合法", ok)
        }
    }
    if ValidType("promo") {
        t.Fatal("枚举外的分型应拒绝")
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
在 summary 里手写第二份 COUNT今天一样，改一处忘另一处，角标与列表差数只调 notify.UnreadCount；grep 全仓 read_at IS NULL 只许出现一次
按 user_id 聚合多家庭账号切换家庭后角标串数聚合键 (family_id, member_id)，跟会话走
用 is_read 布尔列丢了「何时读的」，且布尔默认值与 NULL 语义纠缠read_at NULL 一列两用：判未读 + 留时间
type 用自由字符串写侧手滑 "budget-alert"（连字符），读侧过滤全漏枚举常量 + ValidType 入库把关
全表索引 (family_id, member_id, read_at)已读行占索引大头，越用越肥部分索引 WHERE read_at IS NULL，与查询谓词同形
标已读的响应不带新 unread客户端标完还得再拉一次 summary 刷角标，首屏一个请求的纪律被写路径破掉出口③响应带同一份 unread（后半实现时照此契约）

今日名词卡

术语一句话解释
唯一口径一个业务数字只有一份计算实现，所有出口调它
三个出口summary.unread、通知列表响应、标已读响应；同函数故同值
read_at IS NULL未读的唯一判据；一列两用（状态 + 时间）
member_id 聚合未读跟「当前会话家庭的成员」走，不跟账号走
通知分型budget_alert / system / reminder 三个枚举值，入库校验
部分索引带 WHERE 的索引，只索引满足谓词的行；索引跟着查询长
表先行、接口后置读侧今天真实现，写侧与其余接口按排期后半落——假数据不留到收口
写响应带读数据标已读的响应自带新 unread，省一个请求、消一个时序缝隙
