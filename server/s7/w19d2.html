DueRegistry：跨模块调用收在 platform 接口后面

S4 建 FamilyDirectory（第一个跨模块接口）时留过一句话：跨模块调用点一律收在 internal/platform 的接口后面，日后要拆服务，只换接口实现。今天是这句伏笔的兑现日——第二个跨模块接口 DueRegistry：finance 要把预算周期、周期记账注册进到期中心，但 finance 不许 import homeos，更不许 select homeos_* 表。今天只落契约包（接口 + Entry + Kind 常量），实现明天接。

知识讲义

1. 为什么不能直接调、直接查

最直觉的做法：finance 的 service 里 import homeos 的 repo，直接往 homeos_due_registry 插行。三个理由否掉它：

  • 依赖方向失控。homeos 迟早也要知道 finance 的事（比如日历详情要展示规则金额），你 import 我、我 import 你，Go 直接报 import cycle，编译不过。接口放在两边都够得着的 platform，环就断了。
  • 表结构变成公共契约。直查表意味着 homeos 改一列，finance 跟着崩。收在接口后面，契约只剩方法签名——签名比表结构稳定一个数量级。
  • 换实现的成本。原设计里「注册/撤销」是走事件总线的三个事件（{code}.due.registered、{code}.due.revoked、homeos.todo.completed）。本课程范围明确放弃事件总线，用进程内接口调用替代——但接口方法名照事件语义起，将来真要拆服务、上总线，写一个「把方法调用变成发事件」的实现塞进 main.go 就完事，所有调用点一行不动。这就是 S4 那句伏笔的完整含义。

事件总线、消息队列属于本课程范围外，这里只作前瞻，不承诺任何周次。进程内版本必须保住原设计的两条性质：① 幂等键（昨天建的唯一索引）、② 注册与回写不阻塞请求链路（同事务内写自己的表不算 fan-out；真正的触发与通知在后台调度器里做，S7·D16 落地）。

2. 接口形状：三个方法 = 三个事件

片段 · 方法与事件的对照（完整版见今日增量）Register(ctx, entry)  ←→  {code}.due.registered   注册/重新注册（upsert）
Revoke(ctx, ...)      ←→  {code}.due.revoked      撤销（暂停、删源对象）
Complete(ctx, ...)    ←→  homeos.todo.completed   完成回写（勾选待办）

参数里反复出现的三元组 (sourceSystem, sourceID, kind) 就是昨天的幂等键——接口签名直接暴露它，等于把「你必须想清楚自己是谁、注册的是哪一件事」写进了契约。

3. 契约包放哪、实现放哪、谁装配

东西位置为什么
接口 + Entry + Kind 常量internal/platform/dueregistryplatform 只放契约，不放业务；与 S4 的 FamilyDirectory、authz 同住
真实现（写注册表）internal/homeos/duecenter（明天建）到期中心是 homeos 的功能，注册表是 homeos_* 表，只有 homeos 有权写
装配（注入）cmd/homecube/main.gomain 是全进程唯一「知道所有模块」的地方；S7·D17 finance 接入时见真章

依赖方向图，背下来：

片段 · import 方向internal/finance  ──→  internal/platform/dueregistry  ←──  internal/homeos/duecenter
      （只认接口）                （契约，谁都不 import）           （实现接口，写 homeos 的表）
main.go：new(duecenter.Inproc) 注入 finance 的 service —— 两个业务模块互相不 import

4. 编译级断言：接口的「测试」可以先于实现

Go 的接口是隐式实现（S1·D5），没有一个地方「声明」了实现关系——所以要用一行赋值把关系钉死，方法集不齐直接编译失败：

片段 · 惯用法，S7·D15 的实现靠它把关var _ dueregistry.DueRegistry = (*duecenter.Inproc)(nil)

今天实现还没出生，断言先在测试文件里用一个 stub 演示（测试里允许放假实现——假数据只能活在测试里，这条纪律没破）。

步骤 1 · 契约包

完整 · server/internal/platform/dueregistry/registry.gopackage dueregistry

import (
    "context"
    "time"
)

// Kind 到期种类。跨模块共享，所以常量必须放 platform，
// 不能留在 homeos 的 model 里（finance 够不着）。
type Kind string

const (
    KindReminder      Kind = "reminder"
    KindTodo          Kind = "todo"
    KindBudgetCycle   Kind = "budget_cycle"
    KindRecurringEntry Kind = "recurring_entry"
)

// Entry 一次注册的完整描述。幂等键 = SourceSystem + SourceID + Kind。
type Entry struct {
    FamilyID     int64
    SourceSystem string         // 面目录里的 code："homeos" / "finance"
    SourceID     int64
    Kind         Kind
    Title        string
    DueAt        time.Time
    Payload      map[string]any // 深链等附加信息，可空
}

// DueRegistry 跨模块到期注册契约（S4 FamilyDirectory 之后第二个）。
// 进程内实现；日后若换事件总线，只换实现，调用点不动。
type DueRegistry interface {
    // Register 注册或重新注册：按幂等键 upsert，status 置回 registered。
    Register(ctx context.Context, e Entry) error
    // Revoke 撤销：status 置 revoked，留痕不删行。撤销不存在的键不算错。
    Revoke(ctx context.Context, sourceSystem string, sourceID int64, kind Kind) error
    // Complete 完成回写：源对象已完成（如待办勾选），注册行置 fired。
    Complete(ctx context.Context, sourceSystem string, sourceID int64, kind Kind) error
}

Revoke 一个不存在的键返回 nil 而不是 ErrNotFound——这是故意的：撤销是「确保不在册」，本来就不在册也算达成目标（幂等）。把它设计成报错，调用方就得写「先查再撤」的丑陋分支。

步骤 2 · 编译级断言测试（用 stub）

完整 · server/internal/platform/dueregistry/registry_test.gopackage dueregistry

import (
    "context"
    "testing"
)

// stub 只为验证接口可实现、方法集齐全；真实现明天在 homeos/duecenter 出生。
type stub struct{ registered []Entry }

func (s *stub) Register(ctx context.Context, e Entry) error {
    s.registered = append(s.registered, e)
    return nil
}
func (s *stub) Revoke(ctx context.Context, sys string, id int64, k Kind) error { return nil }
func (s *stub) Complete(ctx context.Context, sys string, id int64, k Kind) error { return nil }

// 编译级断言：stub 的方法集若与接口不齐，这一行直接编译失败。
var _ DueRegistry = (*stub)(nil)

func TestStubSatisfiesInterface(t *testing.T) {
    var r DueRegistry = &stub{}
    if err := r.Register(context.Background(), Entry{SourceSystem: "homeos", SourceID: 1, Kind: KindReminder}); err != nil {
        t.Fatalf("Register: %v", err)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
接口放 homeos，让 finance 来 import今天能跑；哪天 homeos 反过来要 import finance 就死循环契约永远放 platform，两个业务模块都只依赖契约
接口方法照 SQL 起名叫 InsertRow换事件总线时语义对不上，调用点全得改照领域事件起名：Register / Revoke / Complete
Entry 里塞 *model.Reminderplatform 被迫 import homeos 的 model，契约包被污染Entry 只用基础类型与 map，任何模块都够得着
Kind 常量留在 homeos/modelfinance 注册时只好写裸字符串 "budget_cycle"跨模块共享的枚举升格进契约包（昨天留的伏笔今天收）
Revoke 找不到行就返回错误调用方写出「先查再撤」的并发漏洞撤销是幂等的：不在册 = 目标已达成，返回 nil
忘了编译级断言实现少一个方法，直到调用处才报错，报错点离病灶十万八千里var _ Iface = (*Impl)(nil) 一行钉死

今日名词卡

术语一句话解释
跨模块接口定义在 platform、由一个业务模块实现、供另一个业务模块调用的契约；S4 的 FamilyDirectory 是第一个，今天的是第二个
进程内调用同进程直接方法调用替代事件总线；保住幂等键与不阻塞请求链路两条性质
依赖倒置业务模块依赖抽象（接口）而不是彼此；main.go 装配时决定塞哪个实现
import cycleGo 编译器直接拒绝的循环依赖；接口放 platform 就是断环手段
编译级断言var _ Iface = (*Impl)(nil)：方法集不齐则编译失败，最早的失败点
stub测试里的最小假实现，只为满足接口；假数据只许活在测试里
幂等的撤销Revoke 不存在的键返回 nil——「确保不在册」本来就已达成
事件语义命名方法名照领域事件起（registered/revoked/completed），换总线时语义无缝
