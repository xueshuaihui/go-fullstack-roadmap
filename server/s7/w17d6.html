周六 · 停用面的三条语义与最后一面保护

本周把 D1-D5 串成一条完整能力：面目录（D1）→ 家庭启用配置与乐观锁（D2）→ 四层合成清单（D3）→ 分包清单（D4）→ 契约测试（D5）。今天补上「停用」这个动作的完整语义——它比想象中讲究：入口消失、数据保留、仍参与统计，三条缺一不可；再加一道保护：停用最后一个面会被拒绝（409 + 1010）。最后整链验收，本周能力收口。

今日目标

知识讲义

1. 停用不是删除：三条语义

语义内容防的事故
① 入口消失面清单里该项 enabled=false，首页矩阵不再渲染这个面；分包不再被请求（下周 S7·D11 再给服务端路由层加一道 403 门禁）用户还能点进一个家庭已决定不用的面
② 数据保留停用不写任何 DELETE、不碰软删列：finance 的账户、流水、预算一行不动；重新启用后历史数据原样都在「只是想清净一下」被实现成「数据没了」——不可逆事故
③ 仍参与统计跨面聚合口径只按 family_id 过滤，不看面的启用状态：家庭的年度回顾、动态流里 finance 来源的条目、到期项，停用后照常计入统计数字随开关跳变，同一家庭两份「历史」

三条合起来一句话：停用是收纳，不是销毁。它改变的只有「壳怎么表达这个面」，不改变「这个面曾经发生过什么」。

③ 的实现纪律：统计与聚合查询里永远不出现 homeos_family_module 这个表名。一旦某个报表「贴心地」按启用状态过滤，重新启用后历史曲线就会断一段——而且这种 bug 只在「停用又启用」之后出现，测试极难抓。今天的测试直接钉住：停用前后，聚合结果一个数都不许变。

2. 最后一面保护：1010

家庭创建时就强制选面，不允许存在 0 面家庭——这个不变量要靠「停用」这条唯一的写路径守住：当目标面是最后一个已启用的业务面时，停用被拒，409 + 1010（业务状态不允许）。

  • 计数口径：除 homeos 基座外的已启用面。基座恒启用、不可配置（D2 已拒绝），把 homeos 算进计数的话「最后一个面」永远轮不到，保护形同虚设。
  • 未出生但被「预约开通」的面计入：它代表家庭的选择，不能让用户掉进「只剩一个没出生的面」的空壳状态。
  • 当下的直接推论：家里只开了 finance 时，停用 finance 必被拒。想停 finance，先开通任何一个别的面——这正是今天 curl 整链的剧本。

错误码回顾（S1·D4 的码表）：1010 一族都是「业务状态不允许」——余额非 0 归档、删除有流水的分类、唯一 owner 未转让即移除，今天加上停用最后一个面。它们共同点：请求本身合法、权限也够，是世界状态说不行。

步骤 1 · UpdateEnabled 补最后一面保护

片段 · 加在 server/internal/homeos/faces/service.go 的事务内、epoch 比对之前// ErrLastEnabledModule：停用最后一个已启用业务面（409 + 1010）。
var ErrLastEnabledModule = errors.New("至少保留一个已启用的面")

// 事务内：仅当动作是「停用」时检查
if row.Enabled && !enabled {
    var n int64
    if err := tx.Model(&model.FamilyModule{}).
        Where("family_id = ? AND enabled = true AND code <> 'homeos'", familyID).
        Count(&n).Error; err != nil {
        return err
    }
    if n <= 1 { // 只剩目标自己
        return ErrLastEnabledModule
    }
}

handler 的错误分支表（D2 的 switch）加一行：errors.Is(err, ErrLastEnabledModule) → response.Fail(c, http.StatusConflict, response.CodeStateNotAllowed, err.Error())。

保护检查必须在同一个事务、FOR UPDATE 锁行之后做：两个管理员同时停用最后两个面，锁外计数会让两个请求都以为「还剩两个」，双双通过，家庭归零。

步骤 2 · 三条语义的测试

完整 · server/internal/homeos/faces/disable_test.gopackage faces

import (
    "context"
    "errors"
    "testing"

    "gorm.io/gorm"

    "homecube/internal/homeos/model"
    "homecube/internal/platform/testdb"
)

func TestDisableSemantics(t *testing.T) {
    db := testdb.Open(t)
    famID, memID := seedFamily(t, db)
    ctx := context.Background()

    // 前置：只开了 finance 时，停用被拒（最后一面保护）
    _, err := UpdateEnabled(ctx, db, famID, memID, "finance", false, 1)
    if !errors.Is(err, ErrLastEnabledModule) {
        t.Fatalf("停用最后一个面应 1010: err=%v", err)
    }

    // 预约开通 purchase（未出生面 enabled=true），凑出第二个已启用业务面
    if _, err := UpdateEnabled(ctx, db, famID, memID, "purchase", true, 1); err != nil {
        t.Fatal(err)
    }

    // 语义②③的前置事实：给 finance 塞两行流水（测试专用直插，生产代码禁止跨 schema）
    db.Exec("INSERT INTO finance_transaction (family_id, amount_cents, created_at, updated_at, version) VALUES (?, 1200, now(), now(), 1), (?, 3400, now(), now(), 1)",
        famID, famID)
    sumBefore := sumTxnCents(t, db, famID)

    // 停用 finance：现在应该成功。注意 epoch：前面两次尝试一次被 1010 拒、
    // 一次动的是 purchase 行，finance 行仍是 seed 时的 version=1（失败不跳号，D2 的幂等口径）
    if _, err := UpdateEnabled(ctx, db, famID, memID, "finance", false, 1); err != nil {
        t.Fatal(err)
    }

    // 语义①入口消失：owner 视角清单里 finance.enabled=false，渲染谓词为假
    items, err := Compose(ctx, db, famID, model.RoleOwner)
    if err != nil {
        t.Fatal(err)
    }
    for _, it := range items {
        if it.Code == "finance" && (it.Enabled || it.ShouldRender()) {
            t.Fatalf("停用后 finance 仍在渲染集合: %+v", it)
        }
    }

    // 语义②数据保留：流水一行没少、没被软删
    var n int64
    db.Table("finance_transaction").
        Where("family_id = ? AND deleted_at IS NULL", famID).Count(&n)
    if n != 2 {
        t.Fatalf("停用后流水 = %d 行, want 2", n)
    }

    // 语义③仍参与统计：聚合只按 family_id，停用前后一个数不许变
    if after := sumTxnCents(t, db, famID); after != sumBefore {
        t.Fatalf("统计口径变了: before=%d after=%d", sumBefore, after)
    }
}

// sumTxnCents 是「仍参与统计」的最小口径：聚合查询里没有 enabled 这个词。
// 正式项目里这里调 finance 模块的统计入口（进程内函数调用）；口径等价。
func sumTxnCents(t *testing.T, db *gorm.DB, familyID int64) int64 {
    t.Helper()
    var sum int64
    db.Table("finance_transaction").
        Where("family_id = ? AND deleted_at IS NULL", familyID).
        Select("COALESCE(SUM(amount_cents), 0)").Scan(&sum)
    return sum
}

两处诚实声明：① 测试直插 finance 表、直查 finance 表，是测试专用——生产代码的跨模块纪律（finance 不查 homeos_*，反之亦然，跨模块走 platform 接口）不因测试松动；② sumTxnCents 的列名以你 S6 落盘的 finance_transaction 为准，测试要表达的本质只有一句：聚合 SQL 里不出现启用状态。测试里的 version 数字假设 seed 出来的配置行都是初始值 1（被拒的写不跳号）——以你的 seedFamily 实际写入为准，对不上时看 1009 响应的双版本 payload 对账。

常见坑（新手 100% 会踩）

坑现象正确姿势
把停用实现成软删配置行重新启用要「复活」行，epoch 断链，审计对不上停用只翻 enabled 布尔；行的生命周期与家庭相同
停用时顺手清了面的业务数据用户重新启用，历史全没了——不可逆停用不写任何 DELETE、不碰 deleted_at
统计查询按 enabled 过滤停用又启用后，历史曲线断一段，极难复现聚合只按 family_id；今天的 sum 测试钉死
最后一面计数把 homeos 算进去基座恒启用，保护永远不触发，形同虚设计数口径 = 除 homeos 外的已启用面（含预约开通的未出生面）
保护检查在事务外计数并发停用最后两个面双双通过，家庭归零同事务、锁行后再计数
curl 链里 version 用了旧值第 ③⑤ 步收到 409 + 1009，误以为保护逻辑坏了每次 PUT 成功都用响应里的新 version；1009 的双版本 payload 就是给你对账用的
