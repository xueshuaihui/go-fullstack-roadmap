通知列表与未读红点

三个未读出口，第一个（首页 summary 的 unread）在 S7 前半就上岗了。今天第二个出口落地：GET /api/homeos/notifications——游标分页的通知列表，响应体自带 unread。前端壳的未读红点从此有两个数据源，而我们的判据是：它们永远同值。今天不只写接口，还要写一条同值契约测试，把判据变成 CI 里跑的代码。

↑ 这四条是「学习目标」。页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

知识讲义

1. 列表口径

  • 过滤：family_id = ?（scope helper 注入）+ member_id = ?（当前会话成员）——你只看得到发给你的通知。
  • 排序与分页：created_at DESC, id DESC 键集分页，游标 = base64 的 (created_at, id)，不透明、不可自造（S3 定的老规矩）。通知是无限增长的流，正是游标分页的主场；offset 分页在这里会在深翻页时把库拖垮。
  • 可选过滤：?kind=reminder 按分型筛（前端「只看提醒」的 tab）；非法 kind → 400 + 1004。?unread_only=true 只列未读。
  • 响应形状：分页三件套 list / next_cursor / has_more 之外多一个 unread——它是整份响应里唯一不分页的字段，数的是全量未读，不是本页的。

2. 为什么 unread 搭列表的车，而不是单开接口

红点要的是「一个数」，看起来 GET /notifications/unread 很合理——不。每多一个端点，前端进通知页就多一次请求、多一种时序（列表到了、数还没到，红点闪一下）。把 unread 塞进列表响应，一次请求，数据与计数天然同一时刻，还省了接口分母里的一条。这与首页 summary 的哲学同源：首屏只此一个业务请求。

3. 同值契约测试：判据要长成代码

「三个出口同值」如果只写在文档里，它会在某次重构后悄悄破掉。契约测试的写法：

片段 · 思路① httptest 造同一个 member 的会话（S4 的测试 token 手艺）
② GET /api/homeos/home/summary      → 解出 data.unread
③ GET /api/homeos/notifications     → 解出 data.unread
④ assert 两个数相等（且等于种下的未读行数）
⑤ 后天（S7·D21）POST read 之后，把第三个出口也拉进来断言

两个请求走同一个装配好的 router，中间没有任何写操作——如果这都能不相等，说明两个出口没共用 UnreadCount，测试当场抓获。

步骤 1 · service：列表 + 游标

完整 · server/internal/homeos/service/notification.gopackage service

import (
    "context"
    "encoding/base64"
    "fmt"
    "strconv"
    "strings"
    "time"

    "gorm.io/gorm"

    "homecube/internal/homeos/model"
    "homecube/internal/homeos/repo"
    "homecube/pkg/response"
)

type NotificationService struct {
    db   *gorm.DB
    repo *repo.NotificationRepo
}

func NewNotificationService(db *gorm.DB, r *repo.NotificationRepo) *NotificationService {
    return &NotificationService{db: db, repo: r}
}

// Unread 只是转发：全仓唯一实现仍在 repo.UnreadCount（昨天的纪律）。
func (s *NotificationService) Unread(ctx context.Context, familyID, memberID int64) (int64, error) {
    return s.repo.UnreadCount(ctx, familyID, memberID)
}

// List 键集分页：游标 = base64("RFC3339|id")，与 S3 的分页 helper 同构。
func (s *NotificationService) List(ctx context.Context, familyID, memberID int64, cursor, kind string, unreadOnly bool, limit int) ([]model.Notification, string, bool, error) {
    q := s.db.WithContext(ctx).Model(&model.Notification{}).
        Where("family_id = ? AND member_id = ?", familyID, memberID)
    if kind != "" {
        if kind != model.NotificationKindBudgetAlert && kind != model.NotificationKindSystem && kind != model.NotificationKindReminder {
            return nil, "", false, response.ErrInvalidParam
        }
        q = q.Where("kind = ?", kind)
    }
    if unreadOnly {
        q = q.Where("read_at IS NULL")
    }
    if cursor != "" {
        ts, id, err := decodeNotificationCursor(cursor)
        if err != nil { return nil, "", false, response.ErrInvalidParam }
        q = q.Where("(created_at, id) < (?, ?)", ts, id) // DESC 键集：比游标更旧
    }
    var list []model.Notification
    if err := q.Order("created_at DESC, id DESC").Limit(limit + 1).Find(&list).Error; err != nil {
        return nil, "", false, err
    }
    hasMore := len(list) > limit
    if hasMore { list = list[:limit] }
    next := ""
    if hasMore && len(list) > 0 {
        last := list[len(list)-1]
        next = encodeNotificationCursor(last.CreatedAt, last.ID)
    }
    return list, next, hasMore, nil
}

func encodeNotificationCursor(ts time.Time, id int64) string {
    raw := fmt.Sprintf("%s|%d", ts.UTC().Format(time.RFC3339Nano), id)
    return base64.RawURLEncoding.EncodeToString([]byte(raw))
}

func decodeNotificationCursor(cursor string) (time.Time, int64, error) {
    raw, err := base64.RawURLEncoding.DecodeString(cursor)
    if err != nil { return time.Time{}, 0, err }
    parts := strings.SplitN(string(raw), "|", 2)
    if len(parts) != 2 { return time.Time{}, 0, fmt.Errorf("bad cursor") }
    ts, err := time.Parse(time.RFC3339Nano, parts[0])
    if err != nil { return time.Time{}, 0, err }
    id, err := strconv.ParseInt(parts[1], 10, 64)
    return ts, id, err
}

如果你 S3 落地的分页 helper 已经是公共包（当时游标分页就是这么教的），把 encode/decode 两个函数换成公共版——判据不变：游标不透明、键集条件、多取一条判 has_more。本页给的是自足最小版。

步骤 2 · handler 与路由

完整 · server/internal/homeos/handler/notification.gopackage handler

import (
    "net/http"

    "github.com/gin-gonic/gin"

    "homecube/internal/homeos/service"
    "homecube/pkg/response"
)

type NotificationHandler struct{ svc *service.NotificationService }

func NewNotificationHandler(svc *service.NotificationService) *NotificationHandler {
    return &NotificationHandler{svc: svc}
}

// List GET /api/homeos/notifications —— 三个未读出口的第二出口。
func (h *NotificationHandler) List(c *gin.Context) {
    familyID := c.GetInt64("familyID")
    memberID := c.GetInt64("memberID")

    list, next, hasMore, err := h.svc.List(c.Request.Context(), familyID, memberID,
        c.Query("cursor"), c.Query("kind"), c.Query("unread_only") == "true", 20)
    if err != nil { response.FailErr(c, err); return }

    unread, err := h.svc.Unread(c.Request.Context(), familyID, memberID)
    if err != nil { response.FailErr(c, err); return }

    response.OK(c, gin.H{"list": list, "next_cursor": next, "has_more": hasMore, "unread": unread})
}

// 路由装配（Auth 之后）：homeos.GET("/notifications", nh.List)

注意 unread 的分量：它是响应契约的一部分，不是锦上添花——前端红点直接消费它，契约测试直接断言它。

步骤 3 · 同值契约测试

完整 · server/internal/homeos/handler/notification_unread_test.go（骨架）package handler

import (
    "encoding/json"
    "net/http/httptest"
    "testing"
)

func TestUnreadSameAcrossExits(t *testing.T) {
    r, db := newTestRouter(t)              // S4 起的全装配测试 router + 测试库
    token := seedMemberWithToken(t, r, db) // 一个 member 会话；顺手种 3 条未读通知

    read := func(path string) int64 {
        w := httptest.NewRecorder()
        req := httptest.NewRequest("GET", path, nil)
        req.Header.Set("Authorization", "Bearer "+token)
        r.ServeHTTP(w, req)
        if w.Code != 200 { t.Fatalf("%s → %d, body=%s", path, w.Code, w.Body.String()) }
        var body struct{ Data struct{ Unread int64 `json:"unread"` } `json:"data"` }
        if err := json.Unmarshal(w.Body.Bytes(), &body); err != nil { t.Fatal(err) }
        return body.Data.Unread
    }

    fromSummary := read("/api/homeos/home/summary?period=2026-11") // 出口一（S7 前半建）
    fromList := read("/api/homeos/notifications")                  // 出口二（今天建）

    if fromSummary != 3 || fromList != 3 {
        t.Fatalf("summary=%d list=%d, want 都是 3", fromSummary, fromList)
    }
    if fromSummary != fromList {
        t.Fatalf("两个出口不同值: %d vs %d", fromSummary, fromList)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
unread 数的是本页未读翻一页红点数变一次unread 永远是全量口径，与分页参数无关
handler 里现写一份 COUNT三出口同值判据从第二天开始腐烂只调 repo.UnreadCount；grep 全仓 COUNT 只此一处
游标里塞页码客户端开始「算页」，插入新行后重复/漏读游标 = (排序键, id) 的 base64，键集条件续读
排序只按 created_at同一时刻两条通知，翻页时反复出现/消失排序键补 id 兜底：created_at DESC, id DESC
kind 过滤不校验取值?kind=promoo 静默返回空列表，前端以为没通知非三分型之一 → 400 + 1004，错误要响
忘了 family 过滤只按 membermember_id 是全局序列时看似没事，撞号就串家庭family_id 与 member_id 两个条件一个都不能少

今日名词卡

术语一句话解释
未读出口把 unread 吐给客户端的位置；共三个，今天上线第二个
同值契约测试一次测试打多个出口断言相等——判据长成的代码形态

红点（badge）前端壳消费的未读数；服务端只保证数对，渲染归 F5
