注册与撤销：registered / revoked 语义

昨天契约包只有形状，今天给它一颗跳动的心脏：duecenter.Inproc——DueRegistry 的进程内真实现，Register 按幂等键 upsert、Revoke 标记不删行。然后接第一条 HTTP 入口：POST /api/homeos/reminders，创建提醒时在同一条事务里写提醒行与注册行。今天也是「注册与撤销不在请求链路做同步跨模块 fan-out」这条红线落地的日子。

今日目标

↑ 这四条是「学习目标」。页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

知识讲义

1. Register = upsert，不是 insert

注册会发生很多次：创建时一次、改时间一次、暂停后恢复又一次。upsert 的语义是「确保在册，且以本次参数为准」：键不存在则插入；键已存在则更新 due_at / title / payload，并把 status 置回 registered——最后这半句很关键，它让「恢复暂停」不需要第四个方法：撤销过的行再 Register 一次就活了。

GORM 侧靠 clause.OnConflict 把 upsert 翻译成 SQL 的 ON CONFLICT ... DO UPDATE（S3 讲过这个子句的话今天照用；没讲过就照抄，语义以上面这句为准）：

片段 · 冲突目标 = 幂等键三列（完整写法见今日增量）Clauses(clause.OnConflict{
    Columns:   []clause.Column{{Name: "source_system"}, {Name: "source_id"}, {Name: "kind"}},
    DoUpdates: /* title、due_at、status=registered、updated_at、version+1 */,
})

2. Revoke = 标记，留痕

撤销把 status 改成 revoked，行留着。三个收益：① 对账——「为什么没提醒」有据可查；② 恢复——再 Register 即复活，不用重建；③ 审计一致——全站软删纪律（deleted_at 留痕）在注册表上的同款思路。Revoke 不存在的键返回 nil（昨天讲过：撤销幂等，不在册 = 已达成）。

3. 红线：不在请求链路做同步跨模块 fan-out

原设计（事件总线版）的红线是：「注册与回写均不在请求链路上做同步跨服务调用」。进程内版本怎么守？先分清两件事：

动作发生时机算不算 fan-out
写提醒行 + 写注册行（同库同事务）请求链路内不算——同模块同库，一条事务两次写，没有网络、没有等待别的模块
到期触发：发通知、连环告知各面后台调度器（S7·D16）这才是要挪出请求链路的部分：一个请求绝不「顺手」触发一串下游动作

记忆口诀：「登记当场办，鸣锣另择时」。请求内只做登记（一次事务写），所有「到点之后发生的事」都归后台。

4. 两种幂等别混

S2 起写接口带的 client_request_id 防的是「客户端网络重试导致重复提交」，冲突时返回 409 + 1008；今天的注册表幂等键防的是「系统内同一到期项重复登记」，靠唯一索引 + upsert 消化，调用方无感。一个在 HTTP 层，一个在数据层，各管各的。

步骤 1 · duecenter.Inproc：真实现

完整 · server/internal/homeos/duecenter/registry.gopackage duecenter

import (
    "context"

    "gorm.io/gorm"
    "gorm.io/gorm/clause"

    "homecube/internal/homeos/model"
    "homecube/internal/platform/dueregistry"
)

// Inproc 是 DueRegistry 的进程内实现：直接写 homeos_due_registry。
// 只有 homeos 有权碰这张表——这正是「实现放 homeos、契约放 platform」的原因。
type Inproc struct {
    db *gorm.DB
}

func NewInproc(db *gorm.DB) *Inproc { return &Inproc{db: db} }

// 编译级断言（昨天的惯用法）：方法集不齐这里直接编译失败。
var _ dueregistry.DueRegistry = (*Inproc)(nil)

// Register 按幂等键 upsert；冲突则更新并把 status 置回 registered（恢复暂停即再注册）。
func (r *Inproc) Register(ctx context.Context, e dueregistry.Entry) error {
    row := model.DueRegistry{
        FamilyID: e.FamilyID, SourceSystem: e.SourceSystem, SourceID: e.SourceID,
        Kind: string(e.Kind), Title: e.Title, DueAt: e.DueAt,
        Status: model.DueStatusRegistered, Payload: e.Payload, Version: 1,
    }
    return r.db.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns: []clause.Column{{Name: "source_system"}, {Name: "source_id"}, {Name: "kind"}},
            DoUpdates: clause.Assignments(map[string]any{
                "title": e.Title, "due_at": e.DueAt,
                "status": model.DueStatusRegistered,
                "updated_at": gorm.Expr("now()"), "version": gorm.Expr("version + 1"),
            }),
        }).
        Create(&row).Error
}

// Revoke 标记撤销，不删行；键不存在返回 nil（撤销幂等）。
func (r *Inproc) Revoke(ctx context.Context, sys string, id int64, kind dueregistry.Kind) error {
    return r.db.WithContext(ctx).
        Model(&model.DueRegistry{}).
        Where("source_system = ? AND source_id = ? AND kind = ?", sys, id, string(kind)).
        Updates(map[string]any{"status": model.DueStatusRevoked, "updated_at": gorm.Expr("now()")}).Error
}

// Complete 完成回写：置 fired。S7·D16 的待办勾选会调用它。
func (r *Inproc) Complete(ctx context.Context, sys string, id int64, kind dueregistry.Kind) error {
    return r.db.WithContext(ctx).
        Model(&model.DueRegistry{}).
        Where("source_system = ? AND source_id = ? AND kind = ? AND status = ?", sys, id, string(kind), model.DueStatusRegistered).
        Updates(map[string]any{"status": model.DueStatusFired, "updated_at": gorm.Expr("now()")}).Error
}

// WithTx 返回一个绑定事务句柄的副本：homeos 自己的 service 用它把
// 「业务行 + 注册行」收进同一条事务。跨模块调用方（finance）不用它——
// 它们只认 platform 接口，注册放在自己事务提交之后，失败进对账清单（S7·D16）。
func (r *Inproc) WithTx(tx *gorm.DB) *Inproc { return &Inproc{db: tx} }

payload 是 JSONB 列（S7·D18 的日历详情接口才消费它），今天的 upsert 故意不更新 payload——注册时写入一次即可，改深链属于低频路径，留到需要时再加。

步骤 2 · POST /api/homeos/reminders（同事务两写）

完整 · server/internal/homeos/service/reminder.gopackage service

import (
    "context"
    "time"

    "gorm.io/gorm"

    "homecube/internal/homeos/duecenter"
    "homecube/internal/homeos/model"
    "homecube/internal/platform/dueregistry"
)

type ReminderService struct {
    db  *gorm.DB
    due *duecenter.Inproc // homeos 自家模块可直用实现（为了 WithTx 进事务）；
                          // 「只认接口」的纪律是约束跨模块调用方（finance）的
}

func NewReminderService(db *gorm.DB, due *duecenter.Inproc) *ReminderService {
    return &ReminderService{db: db, due: due}
}

// Create 一条事务：提醒行 + 注册行。任何一步失败整体回滚，绝不出「有提醒没注册」的半截状态。
func (s *ReminderService) Create(ctx context.Context, familyID, memberID int64, title string, dueAt time.Time, advanceMin int) (*model.Reminder, error) {
    r := &model.Reminder{
        FamilyID: familyID, CreatedBy: memberID, Title: title,
        DueAt: dueAt, AdvanceMinutes: advanceMin, Channel: "inapp", Version: 1,
    }
    err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(r).Error; err != nil {
            return err
        }
        // 注册：到期时刻 = due_at 减去提前量，调度器只看注册表，不做减法
        fireAt := r.DueAt.Add(-time.Duration(r.AdvanceMinutes) * time.Minute)
        return s.due.WithTx(tx).Register(ctx, dueregistry.Entry{
            FamilyID: familyID, SourceSystem: "homeos", SourceID: r.ID,
            Kind: dueregistry.KindReminder, Title: r.Title, DueAt: fireAt,
            Payload: map[string]any{"member_id": memberID}, // 触发时通知谁（S7·D16 的调度器读它）
        })
    })
    if err != nil {
        return nil, err
    }
    return r, nil
}

为什么 homeos 能直用实现、finance 不能？纪律「调用点收在 platform 接口后面」防的是模块间的编译依赖与表越权。homeos 调自家的 duecenter 是模块内调用，import 方向合法，还能借 WithTx 把两写收进一条事务。finance 明天（S7·D17）接入时只认 dueregistry.DueRegistry 接口：它的注册放在自己事务提交之后，失败靠对账清单兜底——两套姿势，一条纪律。

handler 是熟面孔（S2 三层），路由挂进 homeos 分组：

片段 · 路由装配（Auth 中间件之后）homeos := r.Group("/api/homeos", middleware.Auth(cfg.JWTSecret))
homeos.POST("/reminders", dueHandler.CreateReminder)

步骤 3 · 测试：幂等与撤销

完整 · server/internal/homeos/duecenter/registry_test.go（骨架，DB 用 S3 起的测试库）package duecenter

import (
    "context"
    "testing"
    "time"

    "homecube/internal/homeos/model"
    "homecube/internal/platform/dueregistry"
)

func TestRegisterIdempotent(t *testing.T) {
    db := openTestDB(t) // S3 起的测试库 helper，照你本地的用
    r := NewInproc(db)
    ctx := context.Background()
    e := dueregistry.Entry{FamilyID: 1, SourceSystem: "homeos", SourceID: 42,
        Kind: dueregistry.KindReminder, Title: "吃药", DueAt: time.Now().Add(time.Hour)}

    if err := r.Register(ctx, e); err != nil { t.Fatal(err) }
    e.DueAt = e.DueAt.Add(2 * time.Hour)
    e.Title = "吃药（改时间）"
    if err := r.Register(ctx, e); err != nil { t.Fatal(err) }

    var n int64
    db.Model(&model.DueRegistry{}).Where("source_system = ? AND source_id = ? AND kind = ?",
        "homeos", 42, "reminder").Count(&n)
    if n != 1 { t.Fatalf("重复注册后行数 = %d, want 1", n) }

    var row model.DueRegistry
    db.Where("source_id = ?", 42).First(&row)
    if row.Title != "吃药（改时间）" { t.Fatalf("title = %q, want 更新后的值", row.Title) }

    if err := r.Revoke(ctx, "homeos", 42, dueregistry.KindReminder); err != nil { t.Fatal(err) }
    db.Where("source_id = ?", 42).First(&row)
    if row.Status != model.DueStatusRevoked { t.Fatalf("status = %q, want revoked", row.Status) }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
先写提醒行、注册失败不回滚库里有提醒但日历上永远看不见两写进同一条事务，同生共死
注册时直接把 due_at 原样存设了提前量却到点才响注册行存换算后的触发时刻（due_at − advance），调度器不做减法
「恢复暂停」写了个 Resume 方法接口越长越难换实现再 Register 一次即可：upsert 会把 status 置回 registered
Revoke 用 deleted_at 软删唯一索引看不见软删行？不——行还在，键还占着，再注册撞键后行为诡异撤销走 status 列，不碰软删列；两套留痕机制各管各的
在创建提醒的请求里顺手发通知、刷首页缓存请求越挂越重，一处失败全链路 500登记当场办，鸣锣另择时——触发归后台调度器
拿 client_request_id 当注册幂等键客户端没带幂等键的调用路径全部裸奔两种幂等各管各：HTTP 层防重试，数据层防重复登记

今日名词卡

术语一句话解释
ON CONFLICT DO UPDATEPostgres 的 upsert 语法；GORM 里对应 clause.OnConflict
registered 语义「确保在册，以本次参数为准」；重复注册收敛为同一行的更新
revoked 语义标记撤销、行留着；对账与恢复都靠它
触发时刻due_at 减提前量后的真实响铃时间；换算在注册时做完，调度器只比较大小
fan-out一个请求内同步调用一串下游；到期触发绝不允许出现在请求链路
同事务两写业务行 + 注册行一条事务；杜绝「有对象没注册」的半截状态
gorm.Expr把 now()、version + 1 交给数据库算，避免 Go 与 DB 时钟打架

卡壳时查什么

正文自足。往回翻的三种情况：

  • 事务的写法手感没了：回 S3 事务与软删卡；Transaction(func(tx)) 的闭包形态从那里一直用到现在。
  • handler 三层（DTO → service → repo）怎么摆：回 S2 分层卡；今天只加了 service 一层的新文件。
  • 1008 与今天的幂等键有何区别：本页讲义第 4 节；再不清楚回 S4 建幂等表的卡。
