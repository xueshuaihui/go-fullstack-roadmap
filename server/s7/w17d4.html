分包清单接口：bundles 与校验回退

壳按面下发前端分包（uni-app 的 subPackages，产物是 .wgt 资源包）。今天写清单接口 GET /api/homeos/app/bundles：客户端报上「我要哪些面、我装了什么版本」，服务端回「每个面的包版本、下载地址、校验和、大小、最低兼容壳版本」。先划清边界：真实的远程包托管与下发链路不在本课程范围——今天做的是清单契约与本地语义，url 指向占位路径即可。契约对了，日后接对象存储只是换 url。

今日目标

知识讲义

1. 哪些面有分包：born 面域 − homeos

七处命名同源里有一条 pages/{code} 分包目录。但不是每个 code 都有分包：

  • homeos 没有分包——首页、登录、设置这些壳页面必须在主包里，冷启动第一帧就要用，不能等下载。
  • 未出生面没有分包——没有代码就没有产物，清单里回 not_born 条目（不带 url），客户端据此知道「不是我没装，是它还没出生」。
  • 所以今天的 bundle 目录只有一项：finance。这恰恰是重点——目录的结构比目录的内容重要，日后 purchase 出生，往代码里加一个条目、发一次版，清单接口自动多一行。

2. 五元组各管一件事

字段客户端拿它做什么
version与本地 installed 比对，决定要不要下载
url下载地址（今天是占位路径，真实托管不在范围）
sha256下载完整性校验：算出来不一致 → 这个包不许应用
size下载前提示用户/判断网络策略（蜂窝网要不要自动下）
min_compat这个包要求的最低壳版本：旧壳拿到新包也不许应用

3. 校验回退三级语义

「下发清单」的另一半是回答：客户端拿到包之后出了岔子怎么办。契约如下，服务端的设计要为它兜底：

  1. sha256 不符：下载损坏或被篡改 → 丢弃该包，保留本地旧版本，下次启动重新拉清单重试。绝不「将就用」。
  2. min_compat 高于当前壳版本：包太新、壳太旧 → 不应用新包，继续用旧包，提示用户升级 app。
  3. 无旧包可退（首装即失败）：该面入口置灰并显示「资源获取失败」，其余面照常——一个面的分包失败不许拖垮整个壳，这就是壳要能表达降级的第三处（前两处：面没出生、面没启用）。

服务端在这套语义里的责任只有一条：清单必须诚实。sha256 与 version 永远来自同一个构建产物（代码即配置，构建时写死），不许出现「清单说 1.1.0、url 指向 1.0.0 的包」这种漂移。客户端的所有回退判断都建立在清单诚实的前提上。

4. 请求参数口径

  • codes：逗号分隔的面 code 列表；缺省时下发全部可分发的面。出现 registry 之外的未知 code → 400 + 1004（参数错误），已知但未出生 → 正常回 not_born 条目（这不是错误，是事实）。
  • installed：逗号分隔的 code@version 对，可空。服务端据此在条目里回 update_available，省掉客户端逐个比对的逻辑。

步骤 1 · bundle 目录（代码即配置，与 registry 同理）

完整 · server/internal/homeos/faces/bundles.gopackage faces

// Bundle 是一个面的分包产物元数据。与 registry 同一思想：
// 只有发版才能改变的东西不建表。sha256/size 在构建分包时生成并写死到这里。
type Bundle struct {
    Code      string `json:"code"`
    Version   string `json:"version"`
    URL       string `json:"url"`
    SHA256    string `json:"sha256"`
    Size      int64  `json:"size"`
    MinCompat string `json:"min_compat"` // 要求的最低壳版本
}

// 只有「已出生且非 homeos」的面才有分包条目。
// url 是占位路径：真实远程下发链路不在课程范围，今天只做清单契约。
var bundleCatalog = map[string]Bundle{
    "finance": {
        Code: "finance", Version: "1.0.0",
        URL:    "/bundles/finance-1.0.0.wgt",
        SHA256: "9f2c1e6a4b8d7053e1f0a9c8b7d6e5f4031221344556677889900aabbccddeeff",
        Size:   204800, MinCompat: "1.0.0",
    },
}

// BundleOf 查一个面的分包。born=false 或 homeos → 第二返回值为 false。
func BundleOf(code string) (Bundle, bool) {
    b, ok := bundleCatalog[code]
    return b, ok
}

示例 sha256 是占位串。纪律在于流程：真做的时候由构建脚本算出真实校验和、连同 size 一起写进目录再发版——手写与产物脱节的校验和，等于把三级回退的第一级直接废掉。

步骤 2 · handler

完整 · server/internal/homeos/faces/handler_bundles.gopackage faces

import (
    "net/http"
    "strings"

    "github.com/gin-gonic/gin"

    "homecube/pkg/response"
)

// BundleItem 是清单响应的一项。not_born 条目只带 code 与 availability。
type BundleItem struct {
    Code            string `json:"code"`
    Availability    string `json:"availability"` // available | not_born
    Version         string `json:"version,omitempty"`
    URL             string `json:"url,omitempty"`
    SHA256          string `json:"sha256,omitempty"`
    Size            int64  `json:"size,omitempty"`
    MinCompat       string `json:"min_compat,omitempty"`
    UpdateAvailable bool   `json:"update_available"`
}

// GetBundles GET /api/homeos/app/bundles?codes=finance,purchase&installed=finance@0.9.0
func GetBundles() gin.HandlerFunc {
    return func(c *gin.Context) {
        codes := parseCodes(c.Query("codes"))
        if len(codes) == 0 { // 缺省 = 全目录
            for _, m := range All() {
                codes = append(codes, m.Code)
            }
        }
        installed := parseInstalled(c.Query("installed"))

        list := make([]BundleItem, 0, len(codes))
        for _, code := range codes {
            meta, known := Get(code)
            if !known {
                response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam,
                    "未知的面 code: "+code) // 目录外 → 参数错误 1004
                return
            }
            b, has := BundleOf(code)
            if !meta.Born || !has { // 未出生（含 homeos 不分包）→ 事实条目，不是错误
                list = append(list, BundleItem{Code: code, Availability: "not_born"})
                continue
            }
            list = append(list, BundleItem{
                Code: code, Availability:    "available",
                Version: b.Version, URL:     b.URL,
                SHA256: b.SHA256, Size:      b.Size, MinCompat: b.MinCompat,
                UpdateAvailable: installed[code] != b.Version,
            })
        }
        response.OK(c, gin.H{"list": list})
    }
}

func parseCodes(q string) []string {
    if q == "" {
        return nil
    }
    var out []string
    for _, s := range strings.Split(q, ",") {
        if s = strings.TrimSpace(s); s != "" {
            out = append(out, s)
        }
    }
    return out
}

// parseInstalled 解析 "finance@0.9.0,kin@1.2.0" → map[code]version。
func parseInstalled(q string) map[string]string {
    out := map[string]string{}
    for _, pair := range parseCodes(q) {
        code, ver, ok := strings.Cut(pair, "@")
        if ok && code != "" && ver != "" {
            out[code] = ver
        }
    }
    return out
}

homeos 在 bundle 目录里没有条目，走 not_born 分支会误导——细节修正：BundleOf("homeos") 返回 false，但 homeos 是 born 的。给 not_born 条目一个更准确的口径：「无分包可下发」统一回 availability=not_born 吗？不。homeos 应该回一个独立事实。最干净的写法是把判断改成品目录驱动：has == false 时回 BundleItem{Code: code, Availability: "no_bundle"}？——又多一个枚举值。本课程定口径：清单只接受 born 且非 homeos 的 code；请求 homeos → 400 + 1004（基座不分包，属参数用错）。在循环开头补：

片段 · 加在 known 判断之后if code == "homeos" {
    response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "基座页面在主包，无分包")
    return
}

于是 not_born 条目的语义纯粹了：面没出生，所以没有包。

步骤 3 · 测试

完整 · server/internal/homeos/faces/bundles_test.gopackage faces

import (
    "encoding/json"
    "net/http/httptest"
    "testing"

    "github.com/gin-gonic/gin"
)

func doGet(t *testing.T, target string) *httptest.ResponseRecorder {
    t.Helper()
    gin.SetMode(gin.TestMode)
    r := gin.New()
    r.GET("/api/homeos/app/bundles", GetBundles())
    w := httptest.NewRecorder()
    r.ServeHTTP(w, httptest.NewRequest("GET", target, nil))
    return w
}

func TestBundles(t *testing.T) {
    // ① born 面下发五元组，installed 旧版本 → update_available
    w := doGet(t, "/api/homeos/app/bundles?codes=finance,purchase&installed=finance@0.9.0")
    var body struct {
        Code int `json:"code"`
        Data struct {
            List []BundleItem `json:"list"`
        } `json:"data"`
    }
    if err := json.Unmarshal(w.Body.Bytes(), &body); err != nil {
        t.Fatal(err)
    }
    if body.Code != 0 || len(body.Data.List) != 2 {
        t.Fatalf("body = %s", w.Body.String())
    }
    fin, pur := body.Data.List[0], body.Data.List[1]
    if fin.Availability != "available" || fin.SHA256 == "" || !fin.UpdateAvailable {
        t.Fatalf("finance 条目 = %+v", fin)
    }
    // ② 未出生面：not_born 且不带 url
    if pur.Availability != "not_born" || pur.URL != "" {
        t.Fatalf("purchase 条目 = %+v", pur)
    }

    // ③ 未知 code → 400 + 1004；homeos → 400 + 1004
    if w := doGet(t, "/api/homeos/app/bundles?codes=nope"); w.Code != 400 {
        t.Fatalf("未知 code 状态 = %d, want 400", w.Code)
    }
    if w := doGet(t, "/api/homeos/app/bundles?codes=homeos"); w.Code != 400 {
        t.Fatalf("homeos 状态 = %d, want 400", w.Code)
    }

    // ④ installed 版本相同 → 不需要更新
    w = doGet(t, "/api/homeos/app/bundles?codes=finance&installed=finance@1.0.0")
    json.Unmarshal(w.Body.Bytes(), &body)
    if body.Data.List[0].UpdateAvailable {
        t.Fatal("同版本不应 update_available")
    }
}

这个 handler 不查库、不碰家庭数据（bundle 目录是全局常量），所以测试不需要 DB，NewRecorder 直调即可—— Auth 中间件在 main 装配时才有，单测 handler 本体不挂它。

常见坑（新手 100% 会踩）

坑现象正确姿势
给未出生面回 400/404客户端分不清「参数写错了」和「面还没出生」，重试逻辑全乱未知 code 才是 1004；已知未出生回 not_born 事实条目
sha256 手写、与产物脱节客户端永远校验失败，永远在回退校验和由构建脚本生成并写进目录，与 version 同一次发版
homeos 也进分包清单壳页面被拆进分包，冷启动白屏等下载基座页面在主包；请求 homeos 是参数用错（1004）
清单接口查库拼 enabled把「这家人开没开面」混进「包存不存在」，两个口径缠死bundles 只管产物事实；开没开由面清单接口（S7·D3）表达，客户端对已启用的 born 面才请求包
version 比对用字符串大于号"1.10.0" < "1.9.0" 字典序翻车今天只需「相等/不相等」；真要比大小用语义化版本解析
一个面包下载失败拖垮全壳启动流程串行等所有分包，一个超时全 app 不可用按面独立回退：失败的面入口置灰，其余照常（三级回退第 3 级）

术语一句话解释
分包（subpackage）按面拆分的前端资源包，进入该面时才下载；壳页面在主包
