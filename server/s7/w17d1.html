registry 面目录：代码即配置

S1-S6 你把一个完整的财务面从三层写到报表。从今天起的这个阶段做壳基座的服务端：首页、面（功能模块）的目录与开关、分包清单、到期、通知、设置。壳的世界观只有一句话——面是插件，壳负责表达「哪些面存在、哪些面出生了、这个家庭开了哪些面、你这个角色能看见哪些面」。今天落第一块基石：面目录 registry，7 个 code 全部登记，但只有 2 个已出生。

知识讲义

1. 七个面 code，一个 code 决定七处命名

整个 app 由「壳 + 若干功能面」组成。面的全集是 7 个，每个面有一个全小写的 code，它同时决定七处命名：

结构svc-{code}        服务名（拆服务时用，现在是模块化单体，只有一个进程）
schema {code}     数据库 schema（homeos / finance 两个已建）
/api/{code}/*     路由域（没有版本号段）
{code}_ 表前缀    表名（homeos_member、finance_transaction…）
pages/{code}      前端分包目录
{code}_{seq}_…    迁移文件名（两个 code 各自独立计数）
{code}. 前缀      进程内调用的来源标识（到期中心那几天会用到）
code名称born（已出生）说明
homeos家庭基座是家庭、成员、首页、通知、设置的宿主；它的页面在前端主包，不分包
finance家庭财务是S6 全阶段写完的那个面
purchase采购否规划中的面。code 必须现在就登记，但服务端没有任何它们的业务代码——壳要能表达「面没出生」，而不是假装它们不存在
diet饮食否
kin家人否
growth成长否
trip出行否

2. born 与 enabled 是两个正交的开关

维度谁决定存哪变的频率
born 出生发版：这个面的服务端代码写完并上线了代码（今天的 registry）随版本，一年几次
enabled 启用每个家庭自己：这家人开不开这个面数据库表（明天建 homeos_family_module）随用户操作，随时

两个开关加上后天的「角色可见」，一个面要出现在某个用户的首页上，需要同时通过多层过滤——这就是本阶段反复出现的四层合成：registry ∩ 家庭启用 ∩ 已出生 ∩ 角色可见集。今天先把第一层（registry）钉死。

没出生的面也可以被家庭「预约开通」（enabled=true），但它不渲染、不下发分包——渲染必须叠加 born。这个口径明天写配置表时会用到，今天先记住：born 是硬边界，enabled 是软配置。

3. 为什么面目录是代码，不是数据库表

直觉上「目录」像数据，该进表。但想清楚三件事就不会这么做：

  • 目录随发版变，不随运行时变。一个新面出生 = 它的 schema、迁移、路由、handler 全部随二进制上线。目录条目只有在这个时候才有意义——它天然和代码同一个生命周期，就该和代码住在一起。
  • 进表会制造假入口。如果 purchase 在表里有一行，管理台就能「启用」它、客户端就能请求它，但服务端一行 purchase 的业务代码都没有——注册了但没实现的假入口，是本课程从 S1 就点名的反模式。代码级 registry 让「目录里有」和「二进制里有」永远同源：编译不过 = 登记不上。
  • 表要存的其实是「选择」，不是「目录」。每个家庭开了哪些面，这是运行时数据，明天进 homeos_family_module 表。目录本身（7 个 code、名字、图标、born）是常量。常量进代码、选择进数据库，两边各归各位。

这和「分包清单也是代码即配置」（S7·D4）是同一个思想：凡是只有发版才能改变的东西，都不要给它建表。

步骤 1 · registry 本体

完整 · server/internal/homeos/faces/registry.gopackage faces

import "homecube/internal/homeos/model"

// Meta 是面目录里的一项。目录是代码即配置：增删面随二进制发版，不进数据库表。
type Meta struct {
    Code         string        // 七处命名同源的那个 code，全小写
    Name         string        // 展示名
    Icon         string        // 图标标识符（前端主题令牌体系里的名字，不是色值）
    Born         bool          // 服务端代码是否已实现并随本版上线
    VisibleRoles []model.Role  // 角色可见集；owner 恒真、不查此列表（S7·D3 经 authz 收口）
}

var registry = []Meta{
    {Code: "homeos", Name: "家庭基座", Icon: "home", Born: true,
        VisibleRoles: []model.Role{model.RoleOwner, model.RoleMember, model.RoleWard, model.RoleGuest}},
    {Code: "finance", Name: "家庭财务", Icon: "wallet", Born: true,
        VisibleRoles: []model.Role{model.RoleOwner, model.RoleMember, model.RoleGuest}}, // ward 不可见
    {Code: "purchase", Name: "采购", Icon: "cart", Born: false, VisibleRoles: allRoles()},
    {Code: "diet", Name: "饮食", Icon: "dish", Born: false, VisibleRoles: allRoles()},
    {Code: "kin", Name: "家人", Icon: "people", Born: false, VisibleRoles: allRoles()},
    {Code: "growth", Name: "成长", Icon: "sprout", Born: false, VisibleRoles: allRoles()},
    {Code: "trip", Name: "出行", Icon: "compass", Born: false, VisibleRoles: allRoles()},
}

func allRoles() []model.Role {
    return []model.Role{model.RoleOwner, model.RoleMember, model.RoleWard, model.RoleGuest}
}

// All 返回目录副本。直接暴露包级 slice，调用方一个 append 就能改花你的常量。
func All() []Meta {
    out := make([]Meta, len(registry))
    copy(out, registry)
    return out
}

// Get 按 code 查目录。
func Get(code string) (Meta, bool) {
    for _, m := range registry {
        if m.Code == code {
            return m, true
        }
    }
    return Meta{}, false
}

model.Role 与四个角色常量是 S4 建好的（RoleOwner/RoleMember/RoleWard/RoleGuest），今天直接引用。

步骤 2 · 目录不变量测试

完整 · server/internal/homeos/faces/registry_test.gopackage faces

import "testing"

func TestRegistryInvariants(t *testing.T) {
    all := All()

    // 不变量一：7 个 code 全登记，一个不少
    if len(all) != 7 {
        t.Fatalf("registry 条数 = %d, want 7", len(all))
    }

    // 不变量二：code 不重复
    seen := map[string]bool{}
    for _, m := range all {
        if seen[m.Code] {
            t.Fatalf("code 重复: %s", m.Code)
        }
        seen[m.Code] = true
    }

    // 不变量三：恰有两个 born，且是 homeos 与 finance
    born := []string{}
    for _, m := range all {
        if m.Born {
            born = append(born, m.Code)
        }
    }
    if len(born) != 2 || born[0] != "homeos" || born[1] != "finance" {
        t.Fatalf("born 集合 = %v, want [homeos finance]", born)
    }
}

func TestAllReturnsCopy(t *testing.T) {
    a := All()
    a[0].Name = "被改花了"
    if b := All(); b[0].Name == "被改花了" {
        t.Fatal("All() 返回了内部 slice 的引用，目录被外部改花")
    }
}

第二条测试看着小题大做，其实是在保护「代码即配置」的根基：包级变量一旦被调用方改花，「目录与二进制同源」这句话就作废了。返回副本是 registry 这类包级常量的标配。

坑现象正确姿势
把目录建进数据库表管理台能「启用」一个服务端根本没实现的面，请求过去全是 404目录进代码；表只存每个家庭的启用选择（S7·D2）

今日名词卡

术语一句话解释
面（face / module）一个可插拔的功能域（财务、采购…），有自己的 schema、路由域、表前缀、分包
registry 面目录面的全集常量：7 个 code 的 Meta 列表，代码即配置
born 已出生该面的服务端代码已实现并随本版二进制上线；发版才能改变
enabled 已启用某个家庭打开了这个面；存 homeos_family_module 表，随时可变
availability接口下发字段：available / not_born，壳对「面没出生」的降级表达
四层合成registry ∩ 家庭启用 ∩ 已出生 ∩ 角色可见集，服务端一处算完（S7·D3 落地）
七处命名同源一个 code 同时决定服务名、schema、路由域、表前缀、分包目录、迁移名、来源标识
代码即配置只有发版才能改变的东西放代码里，与二进制能力永远同源
包级变量副本返回All() 返回 copy，防止调用方改花常量
假入口注册了但没实现/没用了的入口；目录进数据库表就会批量制造它
