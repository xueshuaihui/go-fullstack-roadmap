越权测试先红后绿：404+1001 不是 403

今天写一组你期望它一开始就红的测试。功能测试证明「该能用的能用」，越权测试证明「不该能用的真的不能用」——前者红了你当天就知道，后者红了你可能永远不知道，直到用户 A 在群里贴出用户 B 的账单截图。今天的判据一句话：A 家庭的 token 读 B 家庭的资源，得到 404 + 1001，与「这行不存在」完全同形；只有同家庭内看得见却没权限的写操作，才允许 403 + 1003。

今日目标

知识讲义

1. 「先红后绿」不是仪式，是取证

普通做法是写完实现补测试，测出来永远是绿的——因为你只测了自己想到的路径。今天的顺序反过来：

  1. 把断言写成你认为正确的行为（跨家庭读 → 404 + 1001），不看实现；
  2. 跑一遍。凡是红的，都是现有代码真实的越权口子；
  3. 逐条修，修完再跑，直到全绿；
  4. 把「红的时候是什么码」记进 notes/——那是你这次学到的东西，比绿更值钱。

如果第 2 步一条都没红，只有两种可能：你的实现真的干净（少见但可能，昨天刚做过 scope 收口），或者你的断言写得不够狠（常见）。后者怎么判断：把断言里的期望值临时改成 200，如果测试还是绿的，说明你的断言根本没在检查状态码——这种测试叫安慰剂。

2. 三种红的形态，各自暴露什么

实际返回说明代码是这么写的怎么修
200 + 数据查询完全没有家庭边界（按主键 First(&x, id)）回昨天的 scope.InFamily，把边界塞进 where
403 + 1003先判角色/归属再定界：捞到了行，才发现不是你的把 scope 提到最前；捞不到就是 1001，不给 403 的机会
404 + 3001把「家庭无权访问」码用在了业务行上3001 只用于家庭入口（switch / 当前家庭）；业务行一律 1001
500 + 5000边界查空后没处理 ErrRecordNotFound，直接抛给兜底repo 里 errors.Is(err, gorm.ErrRecordNotFound) → response.ErrNotFound

注意第二行是今天最容易踩的：403 是一种信息泄露。探测者拿一串 id 扫你的接口，404 与 403 的分布就等于给他一张「哪些 id 真实存在」的地图。所以规则是「不属于你的家庭 → 它对你不存在」，而不是「属于别人 → 禁止你访问」。

3. 判定顺序：先定界，再判权

一个请求进来，依次过三道门，顺序不能换：

  1. 认证（中间件，D5）：你是谁？票不对 → 401 + 1005。
  2. 定界（scope，D10）：这东西在你的家庭里吗？不在 → 404 + 1001。
  3. 判权（authz，D14 起）：在你家里，你这个角色能做吗？不能 → 403 + 1003。

第 3 道门下周才建，但今天必须把顺序钉死，否则 D14 一写 authz，很多人会顺手把角色判断加在 handler 最前面（「先拦掉 member 再说」），于是第 2 道门被跳过，跨家庭请求又变回 403 了。今天这组测试就是给 D14 上的锁：将来谁把判权提到定界前面，这八条断言立刻红给他看。

本站基准的原话：越权读返 404 + 1001（与不存在同形），不是 403；越权写才返 403 + 1003。这里的「读 / 写」指的是同一个家庭内的可见性差异——跨家庭时，无论读写都是「不存在」，都是 404 + 1001。别把两句话读反了。

4. fixture 怎么摆

越权测试的 fixture 有一个铁律：两个家庭的资源必须都真实存在于同一个库里，且主键相邻。如果 B 家庭的行压根没建，你的测试就只是在验证「查不到不存在的行」，那当然是 404，绿得毫无意义。

  • 用户 A：注册 → 建家庭 1（A 是 owner）→ 建一个 ward 成员（id 相邻）→ 发一条邀请（invite id 相邻）。
  • 用户 B：注册 → 建家庭 2（B 是 owner）→ 同样建成员与邀请。
  • 拿 A 在家庭 1 的 token，去打 B 家庭那几个 id；再拿 A 家庭里 ward 成员的 token，去打 owner-only 的写接口。

全部走内存 repo + httptest.NewRecorder，不连库（S1·D5 立的约定，make test 不需要 Postgres）。真库那一遍在验收命令里用 curl 手工补。

今日增量（在学习仓里落盘）

今天属增量类型 ③+⑤：补一组越权测试用例 + 把红的那几处从「先判权」换成「先定界」的真实现。仓库根 = 你 clone 出来的学习仓根目录，命令一律 cd <你的学习仓根目录> 后执行。

步骤 1 · 先把断言写完，再跑（这一步不许提前修代码）

可跑 · 完整 <repo>/server/internal/homeos/handler/boundary_test.go（前置：同包的 newTestRouter / newTestAuthService，见 D4、D5）package handler_test

import (
    "encoding/json"
    "net/http"
    "net/http/httptest"
    "strings"
    "testing"
)

// envelope 响应信封：断言业务码只认这里，不去猜 message 文案。
type envelope struct {
    Code    int             `json:"code"`
    Message string          `json:"message"`
    Data    json.RawMessage `json:"data"`
}

// twoFamilies 越权 fixture：A 在家庭 1 当 owner，B 在家庭 2 当 owner，
// 两边的成员与邀请都真实建出来（主键相邻），否则「查不到」毫无意义。
func twoFamilies(t *testing.T) *boundaryFixture {
    t.Helper()
    f := newBoundaryFixture(t) // 同包 helper：装配内存 repo + service + router
    f.seedFamily(t, "13800000001", "A 家") // 建家庭、一个 ward 成员、一条邀请
    f.seedFamily(t, "13800000002", "B 家")
    return f
}

// TestCrossFamilyBoundary 八条断言，先跑一遍看哪几条红。
func TestCrossFamilyBoundary(t *testing.T) {
    f := twoFamilies(t)

    tests := []struct {
        name       string
        token      string
        method     string
        path       string
        body       string
        wantStatus int
        wantCode   int
    }{
        {"A 读 B 家的成员：不存在", f.TokenA, http.MethodGet, "/api/homeos/members/" + f.MemberB, "", 404, 1001},
        {"A 撤销 B 家的邀请：跨家庭写也是不存在，不是 403", f.TokenA, http.MethodDelete, "/api/homeos/family/invites/" + f.InviteB, "", 404, 1001},
        {"A 的成员列表里没有 B 家的人", f.TokenA, http.MethodGet, "/api/homeos/members", "", 200, 0},
        {"A 看当前家庭：只可能是 A 家", f.TokenA, http.MethodGet, "/api/homeos/family", "", 200, 0},
        {"A 切到 B 家：家庭入口用 3001，仍是 404", f.TokenA, http.MethodPost, "/api/homeos/families/switch", `{"family_id":` + f.FamilyB + `}`, 404, 3001},
        {"A 家的 ward 发起邀请：同家庭无权写，才是 403+1003", f.TokenAWard, http.MethodPost, "/api/homeos/members/invite", `{"role":2}`, 403, 1003},
        {"B 家的 ward 发起邀请：同上，两边口径一致", f.TokenBWard, http.MethodPost, "/api/homeos/members/invite", `{"role":2}`, 403, 1003},
        {"没有票：一律 401+1005，不许先泄露资源存在性", "", http.MethodGet, "/api/homeos/members/" + f.MemberB, "", 401, 1005},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            var body *strings.Reader
            if tt.body != "" {
                body = strings.NewReader(tt.body)
            } else {
                body = strings.NewReader("")
            }
            req := httptest.NewRequest(tt.method, tt.path, body)
            req.Header.Set("Content-Type", "application/json")
            if tt.token != "" {
                req.Header.Set("Authorization", "Bearer "+tt.token)
            }
            w := httptest.NewRecorder()
            f.Router.ServeHTTP(w, req)

            var env envelope
            if err := json.Unmarshal(w.Body.Bytes(), &env); err != nil {
                t.Fatalf("响应不是信封格式：%s", w.Body.String())
            }
            if w.Code != tt.wantStatus || env.Code != tt.wantCode {
                t.Fatalf("want %d+%d, got %d+%d（message=%q body=%s）",
                    tt.wantStatus, tt.wantCode, w.Code, env.Code, env.Message, w.Body.String())
            }
        })
    }

    // 列表隔离单独断言：A 家列表里绝不能出现 B 家的名字
    if strings.Contains(f.get(t, "/api/homeos/members", f.TokenA), "B 家") {
        t.Fatal("A 家成员列表混进了 B 家的人")
    }
}

// TestSameIDDifferentFamily 同主键、不同家庭上下文：结果必须不同。
// 这条是 scope 的对照实验——如果两边都 404，说明 B 家的行没建出来，测试无效。
func TestSameIDDifferentFamily(t *testing.T) {
    f := twoFamilies(t)
    path := "/api/homeos/members/" + f.MemberB
    if code := f.status(t, path, f.TokenB); code != 200 {
        t.Fatalf("B 读自己家的成员应 200，got %d（fixture 没建对，测试无效）", code)
    }
    if code := f.status(t, path, f.TokenA); code != 404 {
        t.Fatalf("A 读 B 家的成员应 404，got %d", code)
    }
}

fixture 的 seedFamily / get / status 是三个十行以内的小 helper：注册一个用户、建家庭、建一个 ward 成员、发一条邀请，然后把 token 与三个 id 存进结构体。TokenAWard 要用「A 家 ward 成员的账号」签一张票——ward 也可以有账号（user_id 非空），这条正好顺手验证。

先跑一遍，把红的抄下来。期望看到的典型红：撤销 B 家邀请返回 403+1003（D8 里 RevokeInvite 先判了 owner 角色，才轮到 scope），读 B 家成员返回 500+5000（ErrRecordNotFound 没映射成 ErrNotFound）。这两种红都不是测试写错了，是代码的顺序错了。

步骤 2 · 把红的修绿：调整判定顺序

片段 · <repo>/server/internal/homeos/service/invite.go 修正（前置：D8 的 RevokeInvite）// RevokeInvite 顺序：先定界（这邀请在不在这个家庭里），再判权（你是不是 owner）。
// 反过来写就会用 403 泄露「这条邀请存在」。
func (s *InviteService) RevokeInvite(ctx context.Context, familyID, inviteID, byMemberID int64, role model.Role) error {
    inv, err := s.invites.FindByID(ctx, familyID, inviteID) // ① 定界：别家的邀请在这里就捞不到
    if err != nil {
        return err // ErrNotFound → 404 + 1001
    }
    if inv == nil {
        return response.ErrNotFound
    }
    if role != model.RoleOwner { // ② 判权：看得见，但你不能动 → 403 + 1003
        return response.ErrForbidden // TODO(S4·D14)：收进 platform/authz 唯一实现
    }
    return s.invites.SoftDeleteInFamily(ctx, familyID, inviteID, byMemberID)
}

同一条顺序规则套到所有「先查后判」的地方：成员编辑、成员移除、角色变更（D17）、家庭转让（D12）。凡是 handler 或 service 里出现「先判角色再查行」的，今天一并翻过来。

步骤 3 · 真库上手工复核一遍

内存 repo 绿了不等于 GORM 侧绿了（两套实现）。真库那一遍只跑两条，用 -w 打状态码，不用管道截断：

  http://localhost:8080/api/homeos/members/<B 家成员 id> -H "Authorization: Bearer <A 的 token>"

# 2) B 自己的 token 读同一行 → 期望 200（证明行真的存在，上面的 404 是边界拦的）

  http://localhost:8080/api/homeos/members/<B 家成员 id> -H "Authorization: Bearer <B 的 token>"

# 3) 对照实验：把 id 换成一个真不存在的号，两条响应必须一模一样

第 1 条与第 3 条的输出逐字节相同才算过关——这就是「与不存在同形」的可操作定义。差一个字符（比如 message 里带了「无权访问」）都算泄露。

常见坑（新手 100% 会踩）

坑现象正确姿势
fixture 只建了一个家庭「查不到」永远绿，测试等于没写两个家庭的行都真实建出来，再拿 A 的票打 B 的 id；配一条 B 自己读得到 200 的对照

卡壳时查什么

正文自足，只有三种情况出去查：

  • 错误码全表与哨兵名：回 S1·D4（pkg/response 的常量与哨兵就是从那天落盘的）。
  • scope 的写法与 fail-closed：回 S4·D10，一分钟的事。
  • httptest 里怎么造带 header 的请求：httptest.NewRequest 文档（可选）；本站的用法在 S2·D4 已经立过。

如果某条断言红了但你确认代码顺序没问题，按这个顺序查：① fixture 是不是真建出了 B 家的行（先跑对照实验那条）；② token 里的 fam 是不是你以為的那个家庭（把 claims 解出来看）；③ 路由是不是压根没注册（404 来自 Gin 而不是你的 repo，此时响应体不是信封格式，json.Unmarshal 会直接报错——这也是为什么断言里要先解信封）。
