角色默认矩阵落地

昨天 authz 包出生，收的是存量的账——把散在六处的角色分支搬进一张表。今天补增量：把「治理 / 面配置 / 时间与协作」三类动作里还没落定的三行写进同一张 matrix，并给整张表配一组表驱动测试。收工时你要能对着那张四角色 × 动作类别的表，一格一格讲出「✓ 还是 ✗、✗ 发什么码」——讲不出哪一格，就说明那一格既没进矩阵也没进测试。

今日目标

知识讲义

1. 矩阵是一张表，不是一堆 if——先把它读出来

「角色默认矩阵」这个词听起来抽象，落地形态就是你昨天建的那张 map[Action]rule。今天把它排成可读的样子（✓ 放行；✗ 拒绝 → 写动作 403 + 1003；「仅本人」是 cond 行，要调用方递「是不是本人」这个事实）：

类别 · 动作契约串owner成人成员儿童/老人 ward访客 guest
治理 · 改家庭资料（今天新行）family:update✓✗✗✗
治理 · 邀请 / 移除 / 转让 / 解散（D14 存量）invite:create 等✓✗✗✗
治理 · 本人退出（D14 存量）member:leave✗（状态门 1010）✓✗✗
面配置 · 启用/停用面（今天新行，接口 S7 出生）face:enable✓✗✗✗
时间与协作 · 到期提醒订阅（今天新行）due:remind仅本人仅本人仅本人✗

三行新动作各有各的教学点：family:update 补全治理类（家庭资料只有主人能改，其余三个角色在矩阵里就没有这条边）；face:enable 是本阶段「矩阵先行、接口后生」的样板——面配置接口属 S7，但这一行今天定死，接口出生那天 service 第一行就是 Allow，矩阵一行都不用改；due:remind 是「仅本人」的 cond 行第一次给全部三个可写角色用：提醒订阅是个人设置，连 owner 也只能改自己的，所以这一行 full 是空的，owner 也站在 cond 里等事实。

读表口径先立好：矩阵只管写动作的资格。读方向不在这张表里——跨家庭的读被 scope 定界拦成 404 + 1001，同家庭内「看得见却没资格看的那部分」是明天 S4·D16 字段级与行级可见性的正课。所以 guest 在这张表里一个 ✓ 都没有，却仍然读得到成员列表——只读不代表读要过矩阵。

2. 判定顺序只有三层，两层明确不做

本站基准把权限判定钉成一条三层的流水线，顺序不许换、层数不许加：

层答什么问题今天谁在管拒绝的形态
① 显式拒绝这个人/这行还作数吗？不在档（D13 的 status 与软删，走 scope.OnFile）；访客的「限时」也在这层——过期就是不在档按各层既有口径：请求带死票 → 401 + 1005；捞不到行 → 404 + 1001
② 角色默认矩阵这个角色对这个动作有没有边？今天的主角：authz.Allow + 这张 matrix写动作资格不成立 → 403 + 1003
③ 字段级可见性这条边通过了，但哪些字段/哪些行不给看？明天 S4·D16（字段白名单收口 + 私密流水行级过滤）过滤掉或 1001 同形，不发 403

基准里另外两层——「家庭级覆盖」与「对象级 ACL」——明确不做。不是「以后再说」，是这一期压根不给它们留位置：不留 family_role_override 表，不在业务行上留 acl 列。理由一句话就能讲清：一旦允许「这张默认矩阵之上还有一张覆盖表、这一行对象上还有第三张授权表」，就没有人能一眼回答「这个人对这件事到底能不能」——而可回答性正是今天把判定收成一份的全部意义。代价也摆明：将来真需要覆盖时是加一层重设计，不是往今天的表里插一列——今天留了钩子反而会让那天的重设计偷偷长歪。

3. 拒绝的码分两侧：写 403 + 1003，读永远是 1001

这是今天必须能脱稿的一对孪生问题：「member 想改家庭资料」和「member 想读别家成员」都叫越权，码却不同。分工从 D11 就定了，今天按层的口径收口：

  • 矩阵拒绝 = 写动作资格不成立：人在你家里、行也捞得到，只是这个角色没有这条边。Allow 返回 false → service 发 response.ErrForbidden → 403 + 1003。「敢动手」才谈得上拒绝，403 说的正是「东西在这，你不许动」。
  • 越权读 = 不存在：跨家庭时 scope.InFamily 先捞空 → 404 + 1001（读写都算，D11 的八条断言今天仍然全体锁死这条顺序——谁把 Allow 提到定界前面，403 就把资源存在性送出去了）；同家庭内不该看见的读，交给明天的字段级/行级可见性过滤，出口也是过滤或 1001 同形，永远不给读发 403。

所以今天的表驱动测试里，每一行的「拒绝」断言测的都是 Allow(...) == false 这个布尔——它离码还有一层：发 1003 是写路径上的调用点的职责，不是 authz 包的事。Allow 永远只答能不能，不答该发什么码（它连 error 都不返回），这条边界昨天划下，今天一行都不许模糊。

别把 guest 当 ward，也别把 ward 当 guest。同姓、都排在这张表的右半边，语义却相反：ward 是有限写（本人的小名、头像、提醒订阅都改得动，治理与面配置一格都没有）；guest 是零写（全部写格都是 ✗，连改自己都不行），外加「限时」与「不可导出」——限时是不在档层的数据（①层），不可导出是 S6 导出闸要引用的矩阵事实（今天所有写格对 guest 都是 ✗，导出那条边出生时照此办理）。把两个角色并进同一个 ✗ 集合，第一周就会把 ward 本人的提醒订阅一起拒掉。

4. 表驱动测试是矩阵的影子，不许自己发光

昨天 TestAllowMatrix 已经演示了红利：规则在数据里，一组表就扫完四级角色 × 全部动作。今天的三行沿用同一形状，加两条防漂移的纪律：

  1. 每行至少一个允许 + 一个拒绝。全是 ✗ 的行（面配置那行对三个角色都拒）也必须配一个 ✓ 样本（owner），否则你分不清这是「只给 owner 的边」还是「整行写错了的废行」。
  2. 期望值表是矩阵的投影，不是第二份规格。改矩阵必在同一张 diff 里改测试；昨天那条 TestOfSortedAndComplete 的断言（Of 导出与 Allow 一致）今天会自动把三行新动作也纳入——导出与判定分叉会当场红。这条断言就是「表与测试各写一份导致漂移」的解药：它不许你在测试里手抄一份动作清单，只许你从矩阵推导。

cond 行还要多测一个维度：事实递 true、递 false、干脆没递，三种都得有样本——due:remind 这行连 owner 都在 cond 里，「没递事实一律拒」这条 fail-closed 今天第一次挡在 owner 面前，正好当教材。

今天属增量类型 ①+③：给 authz 加三行动作常量与矩阵行 + 补一组表驱动测试。今天不落任何新路由——面配置与提醒的接口各属后面的阶段，矩阵先行是本阶段的明账（见总览「本阶段不做什么」）。仓库根 = 你 clone 出来的学习仓根目录，命令一律 cd <你的学习仓根目录> 后执行。

步骤 2 · 表驱动测试：每行一个允许 + 一个拒绝

完整 · <repo>/server/internal/platform/authz/matrix_s4_test.gopackage authz

import (
    "testing"

    "homecube/internal/homeos/model"
)

// TestNewMatrixRows 今天三行 × 四级角色。want 依次对应 owner/member/ward/guest，
// 均按「事实 = true」判定；cond 行的三种事实另开一测（见 TestDueRemindFacts）。
// 每行至少一个 true 一个 false：全 false 的行说不清是「只给谁」还是整行写歪。
func TestNewMatrixRows(t *testing.T) {
    roles := []model.Role{model.RoleOwner, model.RoleMember, model.RoleWard, model.RoleGuest}
    cases := []struct {
        act  Action
        want []bool
    }{
        {ActionFamilyUpdate, []bool{true, false, false, false}}, // 治理：主人一格
        {ActionFaceEnable, []bool{true, false, false, false}},   // 面配置：同上，接口后生
        {ActionDueRemind, []bool{true, true, true, false}},      // 时间与协作：三个可写角色，guest 零写
    }
    for _, tc := range cases {
        for i, role := range roles {
            if got := Allow(role, tc.act, true); got != tc.want[i] {
                t.Errorf("Allow(%d, %q, true) = %v, want %v", role, tc.act, got, tc.want[i])
            }
        }
    }
}

// TestDueRemindFacts cond 行的三个事实维度：递 true、递 false、没递。
// 这一行连 owner 都在 cond 里，「没递事实一律拒」第一次要挡在主人面前——正适合当教材。
func TestDueRemindFacts(t *testing.T) {
    if !Allow(model.RoleWard, ActionDueRemind, true) {
        t.Fatal("ward 订本人的到期提醒被拒：仅本人该行写歪了")
    }
    if Allow(model.RoleWard, ActionDueRemind, false) {
        t.Fatal("ward 替别人改订阅却放行：事实没生效")
    }
    if Allow(model.RoleOwner, ActionDueRemind) {
        t.Fatal("owner 没递事实竟改得动提醒：fail-closed 破了")
    }
    if Allow(model.RoleGuest, ActionDueRemind, true) {
        t.Fatal("guest 零写：递了事实也不该有这格")
    }
    // guest 对今天全部三行都是 ✗，哪怕硬递事实——「把 ward 当 guest」的反向验证也在这一组：
    for _, a := range []Action{ActionFamilyUpdate, ActionFaceEnable, ActionDueRemind} {
        if Allow(model.RoleGuest, a, true) {
            t.Errorf("guest 在 %q 上有边：只读角色被写进了写行", a)
        }
    }
    if !Allow(model.RoleWard, ActionDueRemind, true) {
        t.Error("ward 在 due:remind 上被拒：把 ward 当 guest 处理了")
    }
}

// TestNewRowsExported 新行必须自动出现在 GET /permissions 的导出里——
// 断言从 Of 推导，不手抄动作清单（清单是第二份实现，昨天的坑今天照样钉）。
func TestNewRowsExported(t *testing.T) {
    o := Of(model.RoleOwner)
    for _, want := range []Action{ActionFamilyUpdate, ActionFaceEnable} {
        if !containsAction(o.Actions, want) {
            t.Errorf("owner 导出缺 %q：矩阵加了行，Of 却没跟上", want)
        }
    }
    if !containsAction(Of(model.RoleWard).Conditional, ActionDueRemind) {
        t.Error("ward 的 conditional 栏缺 due:remind")
    }
    g := Of(model.RoleGuest)
    if len(g.Actions)+len(g.Conditional) != 0 {
        t.Errorf("guest 导出非空（actions=%v conditional=%v）：只读角色混进了写行", g.Actions, g.Conditional)
    }
}

func containsAction(xs []Action, a Action) bool {
    for _, x := range xs {
        if x == a {
            return true
        }
    }
    return false
}

今日名词卡

术语一句话解释
角色默认矩阵「哪个角色对哪个动作有什么边」的唯一一张表；落地形态是 map[Action]rule，读出来是四角色 × 动作类别的格子
三层判定序显式拒绝 > 角色默认矩阵 > 字段级可见性；层数定死，多一层都不许加
显式拒绝（①层）不在档（status/软删/访客过期）与死票；本阶段没有独立的拒绝表，这两个来源就是它的全部家当
治理类动作家庭公共事务：family:update/invite:*/member:remove/family:transfer/family:disband——几乎整列都是 owner 一格
面配置行（矩阵先行）face:enable：接口属 S7，矩阵行今天定死；接口出生那天只接调用、不改表
时间与协作类动作due:remind：个人时间的事务——提醒订阅人人仅本人，owner 的特权在这行帮不上忙
预登记动作路由还没出生就先住进矩阵的动作名；fail-closed 保证它在接线前谁也调不到
写拒 1003 / 读拒 1001矩阵拒绝只在写路径发 403 + 1003；越权读永远 404 + 1001（跨家庭）或过滤（同家庭，D16）
不做的两层家庭级覆盖、对象级 ACL：不留表不留列不留钩子——可回答性（一眼说出能不能）比灵活性值钱
投影式测试期望值从矩阵推导、与 Of/Allow 一致性断言配套的表驱动写法；防「表与测试各一份」的漂移

卡壳时查什么

正文自足，四种情况出去查：

  • Allow 的签名、conds 的 AND 语义、三条 fail-closed 的原始出处：回 S4·D14 讲义 3——今天的三行完全沿用那个形状，没动过一行地基。
