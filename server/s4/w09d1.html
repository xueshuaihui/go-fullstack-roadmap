四级角色与成员 status：退出不是删除

昨天做了移除（owner 清除别人的身份，软删留痕），今天做它的孪生动作退出（本人放弃这个身份，只翻 status）。两个动作长得像，语义正交：移除动的是「这行还在不在」，退出动的是「这人还在不在档」。今天还要把一件从建表那天就欠着的事清掉：status 列的 CHECK 里只有两个取值，昨天写入的 removed 在真库上会被拒——一条迁移补上它，顺手把「已退出不是第五个角色」这句话从口号变成你能脱稿讲清的东西。

今日目标

知识讲义

1. 角色是四级封闭的，不多不少

常量值职责一句话今天已知的判定口径
RoleOwner1管理员：唯一可转让、可解散唯一来源是建家庭与转让；不能移除自己（D12）
RoleMember2成人成员：默认角色可写业务数据，不能管成员与邀请
RoleWard3儿童/老人：可无账号有账号时仅有限写权限，guardian_id 指向监护人
RoleGuest4访客：限时只读连自己都不改（D12 的编辑表），不可导出（S6 的导出闸用它）

这四级的值域在 S3·D5 就写进了库：role SMALLINT NOT NULL DEFAULT 2 CHECK (role IN (1,2,3,4))。「封闭」是有牙齿的——想加第五个角色，必须先改 CHECK、再改权限矩阵、再改所有前端入口，三处一起动才可能自洽。而「已退出」不需要这些，因为它根本不是角色。

2. 两根正交的轴：role 答「能做什么」，status 答「还在不在档」

把「已退出」建成第五个角色，会立刻撞上两个说不清的问题：一个退出的 owner 算什么（owner 的定义里就含着「在」）？退出的成员还能不能被历史流水署名（数据留家庭，作者标记必须还读得到）？改成 status 取值，两个问题都自动消失：角色不变，状态翻面。

status谁写、怎么触发在档查询可见手里的票历史数据
active建档与接受邀请时写（D7/D8）✓有效（到 TTL 或 pver 作废）照写
left今天：POST family/leave，本人意愿，行不软删✗下一次请求就 401 + 1005留着，作者标记不变
removedD12：DELETE members/{id}，owner 意愿，deleted_at + deleted_by 成对留痕✗下一次请求就 401 + 1005留着，同 left

常量名只有一个标准：本阶段各卡用的是 model.StatusActive 这一族。S7 的卡片里偶尔出现 model.MemberStatusActive 这种写法，那是同一个东西的另一个名字——你仓里只允许存在一个，以你 D5/D7 已经跑起来的调用点为准，别同时定义两套。

还有个小账：S1 设计阶段这份状态画的是整数枚举，建表时定成了 TEXT 取值。库里存文本、Go 里存同名字符串常量，判定只看常量；两套表示法混着用（有人写 status = 1）就是漏网之鱼的产地。

3. 昨天欠的那条迁移

S3·D5 建表时 CHECK 只认 'active' 和 'left'。昨天 D12 的移除写的是 status = 'removed'——内存 repo 的测试照样绿（内存实现不看 CHECK），真库那一步会被拒：

片段 · 真库上的报错原文（psql 里跑一次移除就会看到）ERROR:  new row for relation "homeos_member" violates check constraint "homeos_member_status_check"
DETAIL:  Failing row contains (... status = removed ...).
-- SQLSTATE 23514。这不是代码错，是库的约束还没跟上代码的语义。

两件事要一起记住：① Go 常量与库 CHECK 是同一份口径的两个副本，改一个必须改另一个，否则测试绿、生产红；② 放宽约束的迁移也是迁移，down 必须真能回滚（S3·D4 立的规矩）——把 removed 从 CHECK 里收回去时，库里已经存在 removed 的行，ADD CONSTRAINT 会直接失败，所以 down 里要先把这些行折回一个仍然合法的值，并在注释里写明「回滚即丢这段痕迹」。

4. 退出的三道门：谁能让这件事发生

情形响应为什么是这个码
member 本人 POST family/leave200，status=left矩阵里唯一给「本人对自己」开的退出边
owner 本人退出409 + 1010家庭不能没有主人。想走先转让（D12），转让完就是 member，再退出合法
ward/guest 本人退出403 + 1003他们的身份由 owner（或监护人）管理，「自己走」这条边压根不存在
已经 left 的人再点一次409 + 1010行还在（没软删），只是状态不对——用 1010 而不是 200，也不伪装成不存在
已被移除的人再点一次404 + 1001软删行不在一切在档查询里，退出与否轮不到它
拿 A 家的票退 B 家404 + 1001body 里没有 family_id：会话家庭只从 context 的 fam 取，跨家庭一律「不存在」

注意第一列与第四行的搭配：昨天 assertRemovable 给「owner 删自己」定的也是 409 + 1010。同一个状态门复用同一个码，这是「业务状态不允许」的标准用法（1010 从 S2 起就是这条门专用）。而「member 删自己」是 403、「member 退出自己」是 200——差别不在状态，在矩阵里有没有这条边。

退出只改 status，不改 role、不改 user_id、不软删行、不签新票。不要顺手在这里调 RevokeAllByUser（那是「重置密码 = 全设备下线」的动作，按账号撤销，会把他在别家的身份一起干掉）；也不要顺手把 role 降成 0 当作「没了」——角色的值域是 1..4，写 0 会在下一次读时撞上 CHECK，或者静默漂出一个矩阵里查不到的角色。票的失效靠在档校验，不靠删数据。

5. 「在档」要有一个名字

现在「查得到这个人」有了两个否定条件：deleted_at IS NULL 且 status = 'active'。前者 GORM 默认帮你加，后者没人帮你加。如果每个 repo 方法各写各的，就会有一处忘写——忘的那处就是「已退出的人还在成员列表里」或者「已退出的人还能过中间件」。解法和昨天定界的做法同构：把这个谓词做成一个具名 scope，调用点只能用它。

片段 · 为什么要具名（左是散落写法，右是收口写法）// 散落：三条查询抄了三遍，第四条漏了 status → 已退出的人又出现在列表里
db.Where("family_id = ? AND status = ?", fam, "active")
db.Where("status = 'active'")                     // 字面量第四处，谁也不知道
db.Where("family_id = ?", fam)                     // ← 漏了，这就是漏洞

// 收口：口径只有一份，漏不掉了；要读历史行必须显式绕开，绕开就是「我有意识」
db.Scopes(scope.InFamily(fam), scope.OnFile(model.StatusActive))

读历史署名（比如流水列表要把已退出的作者名字显示成「历史作者」）的地方，用 S3·D1 的 Unscoped 显式读——默认挡、显式放，方向不能反。platform/scope 里不 import 业务 model：地基不认识住户，状态值由调用方作为参数递进来。

今日增量（在学习仓里落盘）

今天属增量类型 ①+④+②：落 status 常量与在档判定 + 一条放宽 CHECK 的迁移（up/down 成对）+ 新增 POST /api/homeos/family/leave 一条路由。仓库根 = 你 clone 出来的学习仓根目录，命令一律 cd <你的学习仓根目录> 后执行。

步骤 1 · status 常量与在档判定

完整 · <repo>/server/internal/homeos/model/member_status.go（本文件零 import）package model

// 成员在档状态的三个取值，与 homeos_member.status 的 CHECK 一一对应。
// 「已退出」住在这里，不住在 Role 里：Role 答「能做什么」（四级封闭，1..4），
// Status 答「还在不在档」。历史流水的作者标记靠这个决定继续可读。
const (
    StatusActive  = "active"  // 在档：所有查询与判定的默认口径
    StatusLeft    = "left"    // 已退出：本人意愿（POST family/leave），行不软删
    StatusRemoved = "removed" // 被移除：owner 意愿（D12 的 DELETE），软删留痕
)

// ValidStatus 给建档与迁移校验用；值域封闭，第四个取值就是脏数据。
func ValidStatus(s string) bool {
    return s == StatusActive || s == StatusLeft || s == StatusRemoved
}

// OnFile 结构体侧的在档判定：Go 内存里的行与 SQL 里的 scope 同一个口径。
func (m *Member) OnFile() bool {
    return m != nil && m.Status == StatusActive && !m.DeletedAt.Valid
}

昨天 SoftDeleteInFamily 里那个字面量 "removed" 现在换成 model.StatusRemoved；顺手把 grep -rn '"active"\|"left"\|"removed"' server/internal/ 跑一遍——除常量定义那一行，其余必须零命中（字符串散在业务代码里，就等于口径没收到一处）。

编号接 server/migrations/homeos/ 里现有最大号 +1（前面几天可能已经补过 pver 那条，别硬抄我这里的占位号），up/down 成对：

完整 · <repo>/server/migrations/homeos/homeos_00NN_member_status_removed.up.sql-- 放宽 homeos_member.status 的值域：加入 removed（D12 的移除要写它）。

ALTER TABLE homeos.homeos_member
    DROP CONSTRAINT homeos_member_status_check;

ALTER TABLE homeos.homeos_member

    CHECK (status IN ('active', 'left', 'removed'));
完整 · <repo>/server/migrations/homeos/homeos_00NN_member_status_removed.down.sql-- down 三条：① 与 up 逆序 ② 先折叠数据再收紧约束（否则 ADD CONSTRAINT 当场失败）
-- ③ 折叠即丢痕迹：removed 折回 left 之后，「谁移除的」这条信息只剩 deleted_by。
ALTER TABLE homeos.homeos_member
    DROP CONSTRAINT homeos_member_status_check;

UPDATE homeos.homeos_member
    SET status = 'left', version = version + 1
    WHERE status = 'removed';

ALTER TABLE homeos.homeos_member
    ADD CONSTRAINT homeos_member_status_check
    CHECK (status IN ('active', 'left'));

重放判据照 S3 那三句：up 到顶记基线 → down 到底 → 再 up 逐项对回基线。\d homeos.homeos_member 里 Check constraint 那一行必须出现 'removed'。

步骤 3 · scope：在档口径收进一处

片段 · <repo>/server/internal/platform/scope/scope.go 追加（前置：D10 的 InFamily 与 InFamilyAs）// OnFile 在档口径的唯一定义：状态在档。软删由 GORM 默认代劳，不在此重复。
// platform 不 import 业务 model：值由调用方递进来（scope.OnFile(model.StatusActive)），
// 地基不认识住户，方向不能反——与 InFamily 同一套位置关系。
func OnFile(activeStatus string) func(*gorm.DB) *gorm.DB {
    return func(db *gorm.DB) *gorm.DB {
        return db.Where("status = ?", activeStatus)
    }
}
片段 · <repo>/server/internal/homeos/repo/member.go 追加与修正// MarkLeftInFamily 退出：只动 status 与 version，不软删、不动 role。
// RowsAffected == 0 当不存在处理（跨家庭 / 已软删），口径同 D12 的 SoftDeleteInFamily。
func (r *memberRepo) MarkLeftInFamily(ctx context.Context, familyID, id int64) error {
    res := r.db.WithContext(ctx).
        Scopes(scope.InFamily(familyID), scope.OnFile(model.StatusActive)).
        Model(&model.Member{}).
        Where("id = ?", id).
        Updates(map[string]any{
            "status":  model.StatusLeft,
            "version": gorm.Expr("version + 1"),
        })
    if res.Error != nil {
        return fmt.Errorf("mark member left: %w", res.Error)
    }
    if res.RowsAffected == 0 {
        return response.ErrNotFound
    }
    return nil
}

// FindActiveByID 中间件每个带 mid 的请求都要走它（D5）。当时库里只有 active 一个取值，
// 软删由 GORM 代劳，所以条件里没写 status——今天有了 left，这条不补就是
// 「退出的人手里那张票还活着」，D5 注释里那句「非在档返回 ErrNotFound」就成了空话。
func (r *memberRepo) FindActiveByID(id int64) (*model.Member, error) {
    var m model.Member
    err := r.db.Scopes(scope.OnFile(model.StatusActive)).Where("id = ?", id).First(&m).Error
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, response.ErrNotFound // → 中间件那一个出口：401 + 1005
    }
    if err != nil {
        return nil, fmt.Errorf("find active member: %w", err)
    }
    return &m, nil
}

同口径补两处：ListInFamily（成员列表）与 FindActiveByUserAndFamily（切换家庭的身份查询）都挂上 scope.OnFile；内存 repo（repo/memory_*.go）两个方法同步——两套实现共用一张测试表是 D10 立的规矩。历史署名那条（Unscoped 读法）留在后面的流水课，今天不动它。

步骤 4 · service 与 handler：leave 一条路由

片段 · <repo>/server/internal/homeos/service/member_edit.go 追加（前置：D12 的 MemberService）// canLeave 退出的判权——临时形态，明天 D14 建 platform/authz 后整体搬走。
// 只回答「这个角色有没有『自己退出』这条边」，不看状态。
func canLeave(self *model.Member) error {
    switch self.Role {
    case model.RoleOwner:
        return response.ErrStateNotAllowed // 409 + 1010：家庭不能没主人，先转让（D12）
    case model.RoleWard, model.RoleGuest:
        return response.ErrForbidden       // 403 + 1003：这条边不存在，由 owner 移除
    }
    return nil // RoleMember：本人意愿，允许
}

// LeaveFamily 三道门：定界（repo 的 scope）→ 判权（canLeave）→ 状态（在档）。
// familyID 只来自 token，绝不信 body；memberID 同样来自 context。
func (s *MemberService) LeaveFamily(ctx context.Context, familyID, memberID int64) error {
    self, err := s.members.FindByID(ctx, familyID, memberID) // ① 定界：别家/已软删 → 404 + 1001
    if err != nil {
        return err
    }
    if err := canLeave(self); err != nil { // ② 判权
        return err
    }
    if !self.OnFile() { // ③ 状态门：已 left 的人再退一次
        return response.ErrStateNotAllowed // 409 + 1010，不伪装成不存在，也不幂等返 200
    }
    return s.members.MarkLeftInFamily(ctx, familyID, memberID)
}
片段 · <repo>/server/internal/homeos/handler/member.go 追加 + 路由装配// Leave 处理 POST /api/homeos/family/leave。没有入参：退出哪个家庭由 token 决定。
func (h *MemberHandler) Leave(c *gin.Context) {
    err := h.members.LeaveFamily(c.Request().Context(),
        c.GetInt64("familyID"), c.GetInt64("memberID"))
    if err != nil {
        response.FailErr(c, err) // 1010 / 1003 / 1001 全在这一句里按哨兵分流
        return
    }
    response.OK(c, gin.H{"family_id": c.GetInt64("familyID"), "status": model.StatusLeft})
}

// 路由：挂在受保护组里，与 D7-D12 那几条同组（顺序无所谓，路径不冲突）。
g.POST("/family/leave", mh.Leave)

响应里为什么不返回新 token：退出是「失去这个上下文」，不是「换一个上下文」。切换家庭才要重签（D9 的 IssueForSession），退出之后此人手里的票下一次请求就 401 + 1005，前端拿这个码跳「选择家庭」页。给一个已经不属于这个家庭的人签一张新票，是把「票死了」这件事又救活，语义反了。

步骤 5 · 测试：六条断言一次写完

完整 · <repo>/server/internal/homeos/handler/leave_test.go（前置：D11 的 boundaryFixture / envelope，同包）package handler_test

import (
    "encoding/json"
    "net/http"
    "net/http/httptest"
    "strings"
    "testing"
)

// TestLeave 退出的六道门。断言只看状态码 + 信封里的业务码，不比 message 文案。
func TestLeave(t *testing.T) {
    f := twoFamilies(t) // A 家：owner(A) + member(AM) + ward(AW)；B 家：owner(B)
    cases := []struct {
        name           string
        token          string
        wantStatus     int
        wantCode       int
    }{
        {"member 本人退出", f.TokenAM, 200, 0},
        {"owner 退出：先转让", f.TokenA, 409, 1010},
        {"ward 退出：这条边不存在", f.TokenAW, 403, 1003},
        {"没票", "", 401, 1005},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            w := httptest.NewRecorder()
            req := httptest.NewRequest(http.MethodPost, "/api/homeos/family/leave", nil)
            if tc.token != "" {
                req.Header.Set("Authorization", "Bearer "+tc.token)
            }
            f.Router.ServeHTTP(w, req)
            var env envelope
            if err := json.Unmarshal(w.Body.Bytes(), &env); err != nil {
                t.Fatalf("响应不是信封：%s", w.Body.String())
            }
            if w.Code != tc.wantStatus || env.Code != tc.wantCode {
                t.Fatalf("want %d+%d, got %d+%d", tc.wantStatus, tc.wantCode, w.Code, env.Code)
            }
        })
    }

    // 后两条是状态推进后的复查，必须放在上面那轮之后跑：
    // ⑤ 已退出的人再退一次 → 409 + 1010（行还在，只是状态不对）
    if code, biz := f.post(t, "/api/homeos/family/leave", f.TokenAM); code != 409 || biz != 1010 {
        t.Fatalf("重复退出 want 409+1010, got %d+%d", code, biz)
    }
    // ⑥ 退出者手里的票在下一步就死了；成员列表里也不该再有他
    if code := f.status(t, "/api/homeos/members", f.TokenAM); code != 401 {
        t.Fatalf("退出后用旧票读列表 want 401, got %d（FindActiveByID 没补 status）", code)
    }
    if strings.Contains(f.get(t, "/api/homeos/members", f.TokenA), f.NameAM) {
        t.Fatal("已退出的人还在成员列表里：ListInFamily 没挂 scope.OnFile")
    }
}

twoFamilies 是 D11 那个 fixture，今天往上加一步：A 家再种一个 member 角色的账号（走 D8 接受邀请那条路最省事，直接把 access token 存进 f.TokenAM、成员名存进 f.NameAM），D11 只有 owner 与 ward 两把票，判不出「member 能退、ward 不能」这条差异。f.post 是第三个十行内的小 helper：POST 一把、返回状态码与信封里的业务码——断言业务码的地方只认它，别去比 message 文案。

最后那两条是今天的靶心：它们同时验在档的两处出口（中间件的 FindActiveByID 与列表的 ListInFamily）。把 scope.OnFile 那两行注释掉单独跑红一次，你就明白「只加常量、不加 scope」是什么后果。

常见坑（新手 100% 会踩）

坑现象正确姿势
加个 RoleLeft = 5 图省事矩阵多一行说不清的规则；库里 CHECK 当场拒 5；历史作者判定全崩四级封闭，退出走 status；role 值域恒 1..4
只改 Go 常量，不改库的 CHECK内存测试全绿，真库一移除就 23514常量与约束是同一口径的两个副本，一起改；\d 复核
down 里只 DROP 不折叠数据回滚时报 violations，down 成了空壳先 UPDATE 把 removed 折回合法值，再收紧约束，注释写明丢什么
退出时顺手把 role 写成 0下一次读出一个矩阵里查不到的角色，判定结果看运气退出不碰 role；「不在档」由 status 表达，状态与身份各归各的列
忘了给 FindActiveByID 补 status人退了，票还能用到 TTL——列表里也还查得到他在档口径只有一处定义（scope.OnFile），中间件与列表都走它

重复退出返 200 假装幂等前端分不清「刚退的」和「早退了的」，状态门形同虚设409 + 1010：行在、状态不对；已软删的行才轮到 404 + 1001

今日名词卡

术语一句话解释
四级封闭角色RoleOwner/RoleMember/RoleWard/RoleGuest（1..4），值域由库的 CHECK 钉住，没有第五级
status（在档状态）active / left / removed 三取值；「已退出成员」住在这里，历史作者的署名靠它继续可读
正交两根轴role 答「能做什么」，status 答「还在不在档」；两者互不解释，组合才是一个人的完整处境
退出 vs 移除退出是本人意愿、只改 status、行不软删；移除是 owner 意愿、软删 + status + deleted_by 留痕
在档口径（OnFile）「状态在档且未软删」这组谓词的唯一定义；默认挡、显式放，读历史行要写明
匿名 CHECK 约束名建表时不命名的约束，Postgres 按 表名_列名_check 自动命名；改值域时要 DROP 的就是它
状态门（1010）行在、状态不允许：ErrStateNotAllowed → 409 + 1010；与「不存在（1001）」「无权（1003）」三分
两侧实现同一张表GORM repo 与内存 repo 共用一套断言；只改一侧 = 内存测试绿、真库红
票当场死退出/移除后，中间件下一次请求的在档校验就查不到人 → 401 + 1005，不需要额外撤销动作

卡壳时查什么

正文自足，四种情况出去查：

  • 角色与状态的建模原委：回 S1·D3（四级枚举与「已退出为什么不是角色」第一次出现），建表落地在 S3·D5。
  • down 怎么写才真能回滚：回 S3·D4 的 down 三规则；今天的折叠 + 收紧就是那条规则用在 ALTER 上。
  • scope 的写法与 fail-closed：回 S4·D10；FindActiveByID 在中间件里怎么被用：回 S4·D5。
  • 1010 / 1003 / 1001 的分工与哨兵名：回 S1·D4 的码表落盘课，顺序判据在 S4·D11。

红了先分诊：⑤ 变 200 → 状态门被写在了判权前面（顺序倒了）；⑥ 变 200 或 403 而不是 401 → FindActiveByID 没挂 scope.OnFile；真库报 23514 → 迁移没 up 或者约束名猜错（用 \d 看真实名字，别硬拼）；内存测试绿真库红 → 两侧实现又分家了，回 D10 那条规矩。
