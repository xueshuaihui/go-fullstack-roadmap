家庭上下文注入：scope helper 强制 family_id

今天不加接口。今天把已经写好的九个接口全部拉回同一条起跑线：家庭域的任何一次查询，都必须过同一个 scope.InFamily(familyID)。这件事看着无聊，却是整个项目「A 家庭读不到 B 家庭」这条判据唯一的物理保障——靠每个 handler 自己记得写 where family_id = ?，两百处里必漏一处，漏的那处就是数据泄露。不写代码的一天不叫休息日，叫还债日。

今日目标

知识讲义

1. 为什么边界不能靠自觉

把「越权」拆开看，只有两种成因：身份没验（上周的中间件管这个）和边界没画（今天管这个）。边界没画的典型写法是先按主键捞行、再比对家庭：

片段 · 反面写法（今天要把仓里这种全清掉）var m model.Member
if err := db.First(&m, id).Error; err != nil { /* 只按主键查：任何家庭的行都能捞到 */ }
if m.FamilyID != familyID {
    return nil, response.ErrForbidden // 更糟：403 泄露了「这行存在」
}

两个毛病叠在一起：查询本身没有边界（捞得到才谈得上比对），比对失败还回了 403（探测者据此可以扫出全站主键的存在性）。正确姿势是把边界塞进查询本身——捞不到的行才叫不存在，返回 1001 / 404，与真不存在完全同形。

本站基准把这两条钉死：越权读返 404 + 1001（不是 403），越权写才返 403 + 1003。区别在语义：读一个不属于你的东西，它对你「不存在」；写一个你看得见但没权限动的东西（同家庭里 member 想改别人的角色），才是「禁止」。明天一整天就在拿测试把这条分界线钉进代码。

2. GORM 的 Scopes 是什么（首次出现，最小讲解）

db.Scopes(fns ...func(*gorm.DB) *gorm.DB) 接受一串「查询加工函数」，按顺序套在查询构造器上，返回加工后的 *gorm.DB。你可以把它读成可复用的 where 片段：

片段 · Scopes 的心智模型db.Scopes(scope.InFamily(7)).Where("id = ?", 3).First(&m)
// 等价于 db.Where("family_id = ?", 7).Where("id = ?", 3).First(&m)
// 生成的 SQL：SELECT * FROM "homeos_member" WHERE family_id = 7 AND id = 3 ORDER BY ... LIMIT 1

参数是变长参数（...，S1 讲过 slice 的 ... 展开，这里是同一件事的函数签名版），所以可以叠多层：Scopes(InFamily(fam), NotDeleted(), OnlyActive())。它比在每个方法里手写 where 强的地方在于——边界条件的字符串只存在一份，改列名、加软删过滤都只改一处。

3. 三层纪律：谁负责把 familyID 传下来

层职责禁止
handlerfam := c.GetInt64("familyID")，只从中间件写入的 context 键取禁止 c.Query("family_id")、禁止用 body 里的 family_id 当查询边界（客户端可伪造）
service把 familyID 作为显式首参传给 repo；跨家庭语义的错误一律 ErrNotFound禁止在 service 里手写家庭归属裸 SQL；禁止「先查后比」
repo每个家庭域查询都 Scopes(scope.InFamily(familyID))；方法签名带 familyID禁止 First(&x, id) 这种只按主键的写法出现在家庭域表上

签名带 familyID 是这套纪律里最硬的一环：编译器替你 review。哪天你新加一个 repo 方法忘了考虑家庭边界，调用点会直接编译不过，而不是等到线上出事故。

4. 两类表的边界不一样

  • 家庭域表（有 family_id 列：homeos_member、homeos_invite，以及 S6 起的全部 finance 表）→ 走 InFamily。
  • 全局表（homeos_user、homeos_refresh_token、内存验证码）→ 不带家庭边界，它们的边界是「你是谁」，由认证层管。
  • homeos_family 表自身是特例：它没有 family_id 列（它自己就是那个 id）。它的边界不能靠列，只能靠身份行——查家庭之前先确认你在其中有 status 在档的成员（昨天 FindActiveByUserAndFamily 干的就是这件事）。今天写 scope 的时候顺手把这条特例记进注释，别指望后人猜。

5. fam=0 为什么必须 fail-closed

上周 D5 说过：mid=0 的请求允许通过中间件（已注册未进家庭）。那时 fam 也是 0。如果 InFamily(0) 老老实实生成 where family_id = 0，逻辑上没问题（没有家庭的 id 是 0）；但万一将来某张表允许 family_id 为 NULL 或被误写成 0，这就成了一个「无主数据池」，所有 fam=0 的用户共享。所以 scope 里直接短路成 1 = 0：查询恒空，接口一律 404。边界函数宁可多拒绝，不可多放行——这句话适用于你以后写的每一个 guard。

步骤 1 · 新建 scope 包

可跑 · 完整 <repo>/server/internal/platform/scope/scope.go// Package scope 收纳跨模块复用的查询边界。家庭边界只有这一份实现：
// 任何家庭域查询都必须 db.Scopes(scope.InFamily(familyID))，不允许在 repo 里
// 手写 family_id 条件，也不允许「先按主键查、再比对家庭」。
package scope

import "gorm.io/gorm"

// InFamily 把查询限制在 familyID 这一个家庭内。
// familyID <= 0 表示「没有会话家庭」（已注册未进家庭，fam=0）：fail-closed，
// 用 1 = 0 让结果恒空，绝不放行成全表。
func InFamily(familyID int64) func(*gorm.DB) *gorm.DB {
    return func(db *gorm.DB) *gorm.DB {
        if familyID <= 0 {
            return db.Where("1 = 0")
        }
        return db.Where("family_id = ?", familyID)
    }
}

// InFamilyAs 同 InFamily，但列名带表名前缀。多表 JOIN 时两边都有 family_id，
// 不带前缀会报 column reference "family_id" is ambiguous。table 只允许传代码里
// 写死的常量表名，不接受任何来自请求的字符串。
func InFamilyAs(table string, familyID int64) func(*gorm.DB) *gorm.DB {
    return func(db *gorm.DB) *gorm.DB {
        if familyID <= 0 {
            return db.Where("1 = 0")
        }
        return db.Where(table+".family_id = ?", familyID)
    }
}

放在 internal/platform/ 而不是 internal/homeos/：从 S6 起，finance 面也要用同一个边界函数。platform 是跨面共用的地基，homeos 与 finance 都是它的住户——这个位置关系后面 D14 建 platform/authz 时还会用一次。

步骤 2 · repo 签名统一，查询换 scope

片段 · <repo>/server/internal/homeos/repo/member.go 改造（前置：昨天的 MemberRepo 与 response 哨兵）// 口径：家庭域方法一律 familyID 首参。全局表（user / refresh_token）不带。
type MemberRepo interface {
    FindByID(ctx context.Context, familyID, id int64) (*model.Member, error)
    ListInFamily(ctx context.Context, familyID int64) ([]model.Member, error)
    // FindActiveByID / FindActiveByUserAndFamily / ListActiveByUser 等按身份查的方法
    // 不带 familyID：它们的边界是 user_id / 主键，用于「确认你有没有这个家庭的身份」
    Create(ctx context.Context, m *model.Member) error
    Update(ctx context.Context, m *model.Member) error
    SoftDeleteInFamily(ctx context.Context, familyID, id, byMemberID int64) error
}

func (r *memberRepo) FindByID(ctx context.Context, familyID, id int64) (*model.Member, error) {
    var m model.Member
    err := r.db.WithContext(ctx).
        Scopes(scope.InFamily(familyID)). // 边界在查询里，不在 Go 代码里
        Where("id = ?", id).
        First(&m).Error
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, response.ErrNotFound // 别人家的行 = 不存在：1001 / 404
    }
    if err != nil {
        return nil, fmt.Errorf("find member: %w", err)
    }
    return &m, nil
}

func (r *memberRepo) ListInFamily(ctx context.Context, familyID int64) ([]model.Member, error) {
    var list []model.Member
    err := r.db.WithContext(ctx).
        Scopes(scope.InFamily(familyID)).
        Order("role ASC, id ASC"). // owner 排最前，前端不用再排一次
        Find(&list).Error
    if err != nil {
        return nil, fmt.Errorf("list members: %w", err)
    }
    return list, nil
}

homeos_invite 的 repo 同口径改造：FindByID(ctx, familyID, id)、SoftDeleteInFamily 里 UPDATE ... WHERE id = ? AND family_id = ? 交给 scope 生成，RowsAffected == 0 就返 ErrNotFound（撤销别人家的邀请 = 撤销一条不存在的邀请）。写操作也要 scope——Update/Delete 少了边界就是跨家庭改写，比读泄露更严重。

内存实现（repo/memory_*.go，S1·D5 起测试用的那套）同步改成按 familyID 过滤，两边口径必须一致，否则 make test 绿得毫无意义。

步骤 3 · service 与 handler 的取值口径

片段 · <repo>/server/internal/homeos/handler/member.go 改造（前置：D8 的 MemberHandler）// ListMembers 处理 GET /api/homeos/members：家庭上下文只从 context 取
func (h *MemberHandler) ListMembers(c *gin.Context) {
    fam := c.GetInt64("familyID") // 中间件写入；fam=0 时 scope 让结果恒空
    list, err := h.members.List(c.Request().Context(), fam)
    if err != nil {
        response.FailErr(c, err)
        return
    }
    response.OK(c, gin.H{"list": list})
}

唯一的例外是 POST /api/homeos/families/switch：它的 body 里有 family_id。但那里 family_id 是身份查询的入参（FindActiveByUserAndFamily 查不到就 3001），不是查询边界。除此之外，任何接口都不许从请求里读家庭上下文。

// TestFamilyScope 守一条口径：家庭域 repo 拿着别家的 familyID 查同一主键，
// 必须得到 ErrNotFound（→ 1001 / 404），既不是 ErrForbidden，也不是那一行数据。
// 内存实现与 GORM 实现共用这张表：两边口径不一致，这里就会红。
func TestFamilyScope(t *testing.T) {
    ctx := context.Background()
    members := repo.NewMemoryMemberRepo()
    const (
        famA = int64(1)
        famB = int64(2)
    )
    seedA := &model.Member{FamilyID: famA, Name: "爸爸", Relation: "爸爸",
        Role: model.RoleOwner, Status: model.StatusActive}
    seedB := &model.Member{FamilyID: famB, Name: "外公", Relation: "外公",
        Role: model.RoleOwner, Status: model.StatusActive}
    for _, m := range []*model.Member{seedA, seedB} {
        if err := members.Create(ctx, m); err != nil {
            t.Fatalf("seed: %v", err)
        }
    }

    tests := []struct {
        name             string
        queryFamily      int64
        id               int64
        wantNotFound     bool
    }{
        {"本家庭查本家庭的行：读得到", famA, seedA.ID, false},
        {"A 的家庭上下文查 B 的行：不存在", famA, seedB.ID, true},
        {"B 的家庭上下文查 A 的行：不存在", famB, seedA.ID, true},
        {"fam=0（未进家庭）查任何行：不存在", 0, seedA.ID, true},
        {"真不存在的主键：同样是不存在", famA, 999999, true},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := members.FindByID(ctx, tt.queryFamily, tt.id)
            if tt.wantNotFound {
                if !errors.Is(err, response.ErrNotFound) {
                    t.Fatalf("want ErrNotFound, got err=%v member=%+v", err, got)
                }
                if got != nil {
                    t.Fatalf("越权读竟然拿到了行：%+v", got)
                }
                return
            }
            if err != nil || got == nil {
                t.Fatalf("want row, got err=%v member=%v", err, got)
            }
        })
    }
}

卡壳时查什么

正文自足，只有三种情况出去查：

  • Scopes 的叠加顺序影响结果吗：不影响 where 的语义（AND 连接），但影响链式调用的可读性；gorm.DB.Scopes 文档（可选）。
  • context 六个键的类型与来源：回 S4·D5，那里有整张表——familyID 是 int64，由中间件写入。
  • 1001 / 1003 / 3001 到底怎么分工：回 S4·D9 第 2 节与 S4·D8 的邀请撤销段；明天的越权测试会把三者一次性钉死。

如果 make test 红了但看不出哪一层的问题，按这个顺序二分：先把测试里的 familyID 打出来（确认 context 取值没错），再把 repo 方法里的 SQL 用 ToSQL 打出来（确认边界进了 where），最后才怀疑 service 的错误映射。三层各自有一个打印点，比盯着代码猜快得多。
