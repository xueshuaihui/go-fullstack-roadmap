JWT 签发：claims、双密钥与 TTL

今天建 S4 的心脏：internal/platform/jwtutil。从此服务端不再用 session 记住「谁登录了」，而是把一份带签名的身份快照发给客户端——每次请求客户端带回来，服务端用密钥验签就知道你是谁、在哪个家庭、什么角色。昨天的占位 token 今天全部换真。

今日目标

知识讲义

1. JWT 是什么：一张防伪的身份证

JWT 是三段 base64url 字符串，用 . 连接：header（说明用什么算法，我们是 HS256）、payload（claims，即你的身份字段）、signature（用密钥对前两段做的 HMAC 签名）。任何人拿到 token 都能解出 payload 读内容——签名防的是「改」，不是「看」。篡改任何一个字节，验签必失败。所以：

  • payload 里不放敏感数据（密码、手机号、余额都不行——人人可读）；
  • payload 里放的是快照：签发那一刻的身份。它会过时（角色被改了、成员被移除了），所以需要 pver 与短 TTL 来兜底——这是今天最重要的一句话。

2. 六个 claim，一个都不多

claim含义为什么在 token 里
uid用户 id「你是谁」的最小答案；审计与作者标记都靠它
mid当前会话家庭里的成员 id业务数据的作者/负责人是成员不是用户；私密行可见性也按它判
fam当前会话家庭 id所有查询的 WHERE family_id = ? 从这来——不从请求参数来
role角色快照（owner/member/ward/guest）权限矩阵判定的输入；避免每个请求都查库拿角色
pver权限版本号角色一变就 +1，旧 token 验签通过但 pver 对不上 → 立刻失效（S4·D17 兑现）
typ"access" / "refresh"防止拿长效的 refresh 去调业务接口；Parse 必须校验 wantType

不放什么：手机号、密码哈希、家庭名称、成员列表、任何会变的业务数据。判据一句话：token 里的每个字段都必须是「签名背书、允许过时、过时了有兜底」的。放家庭名称进去，家庭改名后 token 里就是脏数据，而你没有任何手段清掉客户端手里那份。

3. 双密钥与两个 TTL：为什么 access 短、refresh 长

access token 每个请求都带，暴露面最大，所以只活 15 分钟；refresh token 只在续期时出现一次，活 7 天，负责「无感续命」。两把密钥分开（JWT_SECRET / JWT_REFRESH_SECRET，S3 的 config 已在读，确认 .env 里两条都有真随机值）：access 密钥泄露，攻击者也伪造不了 refresh；反之亦然。typ 校验是第三道保险——就算两把密钥配反了，refresh token 也过不了 Parse(secret, tok, "access")。

密钥怎么生成（放进 .env，绝不提交）：

可跑openssl rand -hex 32   # 跑两次，分别填 JWT_SECRET 与 JWT_REFRESH_SECRET

JWT 库用 github.com/golang-jwt/jwt/v5。老教程里的 dgrijalva/jwt-go 已停止维护，SigningMethodHS256 之外的算法一律不接受——库默认就防了经典的 alg:none 攻击，但你仍要在 Parse 时用 jwt.WithValidMethods 把白名单钉死为 HS256。

import (
    "errors"
    "fmt"
    "time"

    "github.com/golang-jwt/jwt/v5"

    "homecube/internal/homeos/model"
)

const (
    AccessTTL  = 15 * time.Minute
    RefreshTTL = 7 * 24 * time.Hour

    TypeAccess  = "access"
    TypeRefresh = "refresh"
)

// Claims 全站唯一的 token 载荷。六个键一个不多：uid/mid/fam/role/pver/typ。
type Claims struct {
    UserID   int64      `json:"uid"`
    MemberID int64      `json:"mid"`   // 当前会话家庭里的成员 id；无家庭时为 0
    FamilyID int64      `json:"fam"`   // 当前会话家庭；切换家庭 = 重签 token
    Role     model.Role `json:"role"`  // 角色快照
    Pver     int        `json:"pver"`  // 权限版本；角色变更即 +1，旧 token 失效
    Type     string     `json:"typ"`   // "access" / "refresh"
    jwt.RegisteredClaims
}

// ErrTokenInvalid 一切验签失败的统一哨兵 → 1005 / 401。
// 不区分「过期」「签名错」「类型错」——对客户端都是一个意思：重新登录或走 refresh。
var ErrTokenInvalid = errors.New("token invalid")

// Sign 按 typ 选 TTL 签发。secret 传错 = 另一类 token 验不过，这是故意的。
func Sign(secret string, c Claims) (string, error) {
    ttl := AccessTTL
    if c.Type == TypeRefresh {
        ttl = RefreshTTL
    }
    return signWithTTL(secret, c, ttl)
}

func signWithTTL(secret string, c Claims, ttl time.Duration) (string, error) {
    now := time.Now()
    c.IssuedAt = jwt.NewNumericDate(now)
    c.ExpiresAt = jwt.NewNumericDate(now.Add(ttl))
    tok := jwt.NewWithClaims(jwt.SigningMethodHS256, c)
    s, err := tok.SignedString([]byte(secret))
    if err != nil {
        return "", fmt.Errorf("sign token: %w", err)
    }
    return s, nil
}

// Parse 验签 + 验过期 + 验类型。wantType 必传：access 与 refresh 绝不混用。
func Parse(secret, tokenStr, wantType string) (*Claims, error) {
    var claims Claims
    _, err := jwt.ParseWithClaims(tokenStr, &claims,
        func(t *jwt.Token) (any, error) { return []byte(secret), nil },
        jwt.WithValidMethods([]string{"HS256"})) // 算法白名单钉死
    if err != nil {
        return nil, fmt.Errorf("%w: %v", ErrTokenInvalid, err)
    }
    if claims.Type != wantType {
        return nil, fmt.Errorf("%w: type %s, want %s", ErrTokenInvalid, claims.Type, wantType)
    }
    return &claims, nil
}

步骤 2 · login 换真签发

片段 · server/internal/homeos/service/auth.go 修改（前置：昨天的 Login 与 jwtutil）// AuthService 增加字段 accessSecret / refreshSecret string（从 config 注入）。

// issueTokens 按会话快照签发一对 token。login / refresh / switch / accept 共用。
func (s *AuthService) issueTokens(u *model.User, m *model.Member) (string, string, error) {
    base := jwtutil.Claims{UserID: u.ID}
    if m != nil { // 还没有家庭：mid/fam 为 0，只能调「家庭域」接口（S4·D7 起）
        base.MemberID = m.ID
        base.FamilyID = m.FamilyID
        base.Role = m.Role
        base.Pver = m.Pver
    }
    a := base; a.Type = jwtutil.TypeAccess
    r := base; r.Type = jwtutil.TypeRefresh
    access, err := jwtutil.Sign(s.accessSecret, a)
    if err != nil {
        return "", "", err
    }
    refresh, err := jwtutil.Sign(s.refreshSecret, r)
    if err != nil {
        return "", "", err
    }
    return access, refresh, nil
}

步骤 3 · 测试与验收

完整 · server/internal/platform/jwtutil/jwtutil_test.gopackage jwtutil

import (
    "errors"
    "testing"
    "time"

    "homecube/internal/homeos/model"
)

func TestSignParseRoundtrip(t *testing.T) {
    in := Claims{UserID: 1, MemberID: 2, FamilyID: 3, Role: model.RoleOwner, Pver: 4, Type: TypeAccess}
    tok, err := Sign("test-secret", in)
    if err != nil {
        t.Fatal(err)
    }
    out, err := Parse("test-secret", tok, TypeAccess)
    if err != nil {
        t.Fatal(err)
    }
    if out.UserID != 1 || out.MemberID != 2 || out.FamilyID != 3 || out.Role != model.RoleOwner || out.Pver != 4 {
        t.Fatalf("claims 回读不一致: %+v", out)
    }
}

func TestParseRejects(t *testing.T) {
    access, _ := Sign("s1", Claims{Type: TypeAccess})
    refresh, _ := Sign("s2", Claims{Type: TypeRefresh})
    expired, _ := signWithTTL("s1", Claims{Type: TypeAccess}, -time.Minute)

    cases := []struct{ name, secret, tok, want string }{
        {"密钥不对", "wrong", access, TypeAccess},
        {"refresh 冒充 access", "s2", refresh, TypeAccess},
        {"已过期", "s1", expired, TypeAccess},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            _, err := Parse(c.secret, c.tok, c.want)
            if !errors.Is(err, ErrTokenInvalid) {
                t.Fatalf("err = %v, want ErrTokenInvalid", err)
            }
        })
    }
}

「refresh 冒充 access」这条用例里密钥故意给对（s2 签的 refresh 用 s2 验）——验签会过，拦住它的是 wantType。这就是双保险的意义：任何单一机制失效，另一层还在。

常见坑（新手 100% 会踩）

坑现象正确姿势
把密钥提交进 gitPUBLIC 仓里人人可伪造你的 token密钥只进 .env；.env 在 .gitignore 里（S1·D1 就立好的规矩）
access 与 refresh 共用一把密钥泄露面翻倍；typ 成了唯一防线双密钥 + typ 校验，两层都要
Parse 不校验 wantType7 天有效的 refresh 被拿去调业务接口，短 TTL 白设Parse 强制传 wantType，没有默认值
payload 里塞手机号「方便前端显示」token 人人可解码，等于广播用户隐私展示数据走接口查，token 只放六个快照键
TTL 写死在业务代码里想调 15m→30m 得全仓找只认 jwtutil.AccessTTL / RefreshTTL 两个常量
角色变更只改库不管 token被降权的人拿着旧 token 继续干旧角色的事，最长 15 分钟这正是 pver 存在的理由：库里 +1，中间件比对不上就 1005（D5 接校验、S4·D17 兑现全链路）
用 == 比较签名错误类型库升级后错误包装变了，判断失灵统一 errors.Is(err, ErrTokenInvalid)（S1·D3 的老纪律）

术语一句话解释
JWTheader.payload.signature 三段式签名令牌；防改不防看
claimspayload 里的键值对；本项目固定六个：uid/mid/fam/role/pver/typ
HS256HMAC-SHA256 对称签名：签发与验证同一把密钥；算法白名单钉死只收它
双密钥JWT_SECRET（access）+ JWT_REFRESH_SECRET（refresh），泄露互不牵连

RefreshTTL 7drefresh 只续期时用一次、且要轮换（明天 D4），所以可以长命
pver权限版本号：角色/成员状态一变就 +1，让已签发的旧 token 立即作废
身份快照token 是签发那一刻的身份复制品；会过时，所以要有 pver 与短 TTL 兜底
无状态认证服务端不存 session，验签即认人；代价是「主动作废」要靠额外机制（pver、refresh 存库）
