S4 · DAY 17 预计 30 分钟 难度 ★★★★☆

角色变更：pver+1 使旧 token 失效

机制早就装好了。D5 的中间件里那一句 m.Pver != claims.Pver → deny() 当时只被一条测试用例喂过（库里 pver=2、票里 pver=1）；D12 转让完在两行 Updates 旁边写了一句「已知窗口：对方的 role 快照最长再活 15 分钟」；D14 又把「人还在档、角色变了」这一类单独记了一笔。今天提供变更点：全站唯一一条让库里 pver 跳起来的接口。它同时是 S4 权限侧的最后一块——D14 管「有没有这条边」、D16 管「这条边给看哪几列」、今天管「这张票还算不算数」。

今日目标

知识讲义

1. 两条失效通道：一个管「人还在不在」，一个管「身份变没变」

无状态 JWT 的先天缺陷是签出去的票收不回来。本阶段「不做什么」里明确写了不上 Redis 黑名单，所以我们用两次主键查询换撤销能力——D5 的中间件那一步里其实藏了两道门，今天必须把它们分开讲：

库里的变化谁治它旧票的下场出生那天
成员行被软删（owner 移除）FindActiveByID 捞不到行401 + 1005D12 写操作、D5 写校验
status 变成 left（本人退出）scope.OnFile 把它排除出「在档」401 + 1005D13
家庭行被软删（解散）m.FamilyID != claims.FamilyID（家没了，成员行也清了）401 + 1005D14
role 变了，行还在、还是 active只有 pver 比对401 + 1005今天：接口侧的变更点

前三行的共同点是「这一行不再是当初那一行」；第四行是「还是同一个人、同一个家，但身份换了」。前三类靠捞不到，第四类必须靠对不上——因为那个人还在档，中间件不能拒他，只能拒他手里那张写着旧角色的票。这就是为什么 role 快照不能靠 TTL 兜：15 分钟里被降权的前管理员照样能踢人、能改家庭资料。

一句话记住分工：在档校验答「你还在这个家吗」，pver 校验答「你手里这张票描述的还是现在的你吗」。前者是资格的地基，后者是票的有效期之外的第二重寿命。

2. 为什么 pver 必须在 token 里，而不是在服务端「切一下上下文」

基准把六个 claim 定死了：uid / mid / fam / role / pver / typ，并且立了一条禁令——切换家庭 = 重新签发 token，不做进程内切上下文。D9 在家庭维度上兑现过这条禁令；今天角色维度同一条理由再用一遍，四条：① 两份真相：进程内存里放一个「当前角色」，它就永远和 homeos_member 那一行分叉，重启即回原形；② 不可水平扩展：请求落到另一个实例就拿着旧值，加一台机器就多一份漂移；③ 伪造面：context 里的 role 是从票里解出来的，能改 context 就能改判定，等于把判定入口交给运行时；④ 无审计：改完内存谁也不知道，日志与库里都查不到这件事发生过。

正确姿势只有一个方向：改库 + 让票作废 + 让客户端重新认证。pver 是这条链上「让票作废」的那一环——它不是权限，它是权限的版本号：库里 homeos_member.pver INT NOT NULL DEFAULT 0，票里 pver 是签发那一刻的抄本，两者不等就是过期抄本，一律 1005。

今天仍然不许把 pver 逻辑塞进 authz——D14 那句话今天照样生效：一个是「有没有资格」（Allow，纯函数、不查库、不看请求），一个是「这张票还算不算数」（中间件与 refresh 的比对，要查库）。混在一起，authz 就有了第二个依赖方向，收工 grep 也会多一条红线。pver 的读在中间件（D5），写在今天的 repo 方法里，自增规则只有两处：改角色、转让主人。

3. 六道门的顺序：每一步的错误码都必须唯一说法

门的顺序不是审美问题，它是「越权探测拿不到额外信息」的构造方法（D11 立的口径：同一 familyID 上下文内先定界再判权）：

门问什么不成立的响应为什么这个码
① 认证票验签过了吗？票里的 pver 还对得上吗？401 + 1005中间件已经管完，路由级一行都不用写
② 定界这个 :id 在我这个家庭里、并且在档吗？404 + 1001别家的成员、已移除的成员与不存在同形——不解释、不发 403
③ 判权Allow(actor.Role, ActionMemberSetRole)403 + 1003「东西看得见，你没权力动」——只有本家庭内部才谈得上这句
④ 值域目标角色是 member/ward/guest 之一吗？400 + 1004role=1 不是参数能给的：owner 的唯一来源是建家庭（D7）与转让（D12）；0/5 不在枚举里，也进不到判定
⑤ 状态门target.IsOwner()？409 + 1010「这个家庭不能没有主人」——处境问题不是资格问题，所以是 1010 而不是 1003（D14 立的两个问法）
⑥ 写一条 UPDATE 落到几行？RowsAffected == 0 → 404 + 1001并发窗口里他被移除了：与不存在同形，不返回「改了两遍」的怪话

④ 那条值得单独背下来：升权通道只能有一条。如果 PUT .../role 收 role=1，那么 owner 就能凭空造出第二个主人，「owner 恒一条」这条不变式当场作废——而这条不变式是 D12 转让、D14 解散、D13 退出三处状态门的共同地基。要换主人，请走 POST /family/transfer-owner：它在一个事务里同时动两行（一升一降），总数守恒。D12 的第 8 步断言「PUT members/{id} 的 DTO 里没有 role 字段」和今天这条是同一件事的两半：改资料动不了 role，改 role 动不了 owner 那一格。

4. 原子性：一处成员行 + 一次 pver 自增，必须同一条语句 / 同一个事务

为什么站点基准把这条写成硬要求？因为拆成两条写会出两种坏中间态，而且两种都靠人肉发现：

拆开写的顺序崩溃点后果
先 role=3，再 pver=pver+1第一条落库后进程挂了永久漏洞：库里角色已是 ward，旧票的 role=1 且 pver 仍相等 → 中间件放行，最长到 RefreshTTL 7 天
先 pver=pver+1，再 role=3第一条落库后进程挂了误伤：此人所有票立刻 1005，但角色没变——他被自己的管理员「踢下线」了一次，而库里权限照旧

解法不是「加个补偿任务」，是让两条变化共用一条 UPDATE：今天改角色只动一行，就一条语句三个列（role、pver、version）；D12 转让动两行，就在同一个 Transaction 里各自带上 pver = pver + 1。version 那一列也顺手照 D12/D13 的写法带上（乐观锁计数，1009 的判据基础），别只写前两列。

另一半在 refresh：Refresh 用的 Claims 与 access 是同一个 struct（同样带 mid/pver，只是 typ=refresh），所以轮换时必须查一次成员行再比 pver。算一下就明白这一步多关键——只挡 access 的窗口是 15 分钟，不挡 refresh 的窗口是 7 天：被降权的人拿旧 refresh 每续一次命，还能拿到一张带着新角色的新票（因为签新票时读的是库里的当前角色），等于把降权变成了「重登一次就好」。这道门补上之后，D6 那三句「access 管性能、refresh 管撤销、TTL 管兜底」才真的成立：pver 管的是「身份变了」这一类，谁都得吃它。

被降权的那个人，我们不给他重签。D13 已经给过同族理由：发新票的前提是「会话继续存在」，而这里我们要的是这张票死掉；况且他是被动方，可能压根不在线，替一个不在场的人建立会话纯属多余。他要重新登录一次——这也是「权限被改过的人必须重新认证」的自然结果。对照 D12 的转让：那边要给发起人重签，因为他是主动方且会话继续（owner → member 是他自己按下的按钮）。

今日增量（在学习仓里落盘）

今天属增量类型 ②+③：新增一条路由（PUT /api/homeos/members/{id}/role）+ 给 refresh 补一道门 + 补失效链与负面表驱动测试。仓库根 = 你 clone 出来的学习仓根目录，命令一律 cd <你的学习仓根目录>，目录一律写 <repo>/。

步骤 2 · repo：一条 UPDATE 带三个列

完整 · <repo>/server/internal/homeos/repo/member.go 追加（形状抄 D13 的 MarkLeftInFamily）func (r *memberRepo) SetRoleAndBump(ctx context.Context, familyID, id int64, role model.Role) (*model.Member, error) {
    res := r.db.WithContext(ctx).
        Scopes(scope.InFamily(familyID), scope.OnFile(model.StatusActive)). // 定界 + 在档都在 WHERE 里
        Model(&model.Member{}).Where("id = ?", id).
        Updates(map[string]any{
            "role":    role,
            "pver":    gorm.Expr("pver + 1"), // 与 role 同一句：不给自己留「半更新」的余地
            "version": gorm.Expr("version + 1"),
        })
    if res.Error != nil {
        return nil, fmt.Errorf("set member role: %w", res.Error)
    }
    if res.RowsAffected == 0 {
        return nil, response.ErrNotFound // 并发窗口里被移除了 → 与不存在同形 404 + 1001
    }
    return r.FindByID(ctx, familyID, id) // 回读带新 pver 的行：响应里的 pver 是库里的真值
}

步骤 3 · service 六门 + handler + 一条路由

完整 · <repo>/server/internal/homeos/service/member_role.gopackage service

import (
    "context"

    "homecube/internal/homeos/model"
    "homecube/internal/platform/authz"
    "homecube/pkg/response"
)

// SetRole 全站唯一的 pver 自增点之一（另一处是 D12 的 TransferOwner，今天补上）。
// 六门顺序固定：定界 → 判权 → 值域 → 状态 → 写。认证那门在中间件，不在这里。
// 注意返回的是变更后的成员行（带新 pver），但绝不重签：被降权者的票该死不该换新。
func (s *MemberService) SetRole(ctx context.Context, familyID, targetID int64, role model.Role, actor *model.Member) (*model.Member, error) {
    target, err := s.members.FindByID(ctx, familyID, targetID) // ② 定界：别家 / 已移除 → ErrNotFound
    if err != nil {
        return nil, err                            // → 404 + 1001，同形，不解释
    }
    if !authz.Allow(actor.Role, authz.ActionMemberSetRole) {
        return nil, response.ErrForbidden       // ③ 判权 → 403 + 1003（本家庭内才谈得上）
    }
    if !role.Assignable() {
        return nil, response.ErrInvalidParam    // ④ 值域 → 400 + 1004：owner 不由这条接口产生
    }
    if target.IsOwner() {
        return nil, response.ErrStateNotAllowed // ⑤ 状态门 → 409 + 1010：先转让（D12），别把主人降没
    }
    if !target.OnFile() {
        return nil, response.ErrStateNotAllowed // 已退出的身份不复活：改角色不是「重新拉进门」
    }
    return s.members.SetRoleAndBump(ctx, familyID, targetID, role) // ⑥ 一行 role + 一次自增，同一条 UPDATE
}

响应里带 pver 是有意的：它是「你的票已作废」这件事唯一可机器读的凭据。前端拿到新 pver，就知道该提示对方重新登录，而不是猜。但它不是给客户端用来「更新本地会话」的——客户端没有把 pver 塞回旧票的能力（票由密钥签名），别为它做任何合并逻辑。

常见坑（新手 100% 会踩）

坑现象正确姿势
只改 role，忘了 pver测试全绿（没人测失效），被降权的人继续按旧角色干了 15 分钟，refresh 一续就是 7 天同一条 UPDATE 三列：role、pver、version；步骤 5 第 1 条断言就是 pver == before+1
拆成两条 UPDATE（或两个事务）崩溃留下「role 变了 pver 没变」的永久漏洞，或反过来误伤一次一个存储动作 = 一次变化集合；拆不动就写进同一个 Transaction 闭包
Updates 里写 mem.Pver+1 的算好的值并发两次改角色丢一次自增；丢掉那次就是旧票复活gorm.Expr("pver + 1")：让存储侧加，内存侧算的一律不许
收 role=1凭空造出第二个 owner，D12/D13/D14 三处状态门的基石碎掉值域只收 2/3/4（Assignable）；换主人走转让，那里一升一降同事务守恒
owner 行被降级「唯一 owner 不许降级」变成一句注释，库里 owner 数 = 0状态门在判权之后：用 target.IsOwner() 发 409 + 1010（处境问题，不是资格问题）
refresh 不加 pver 门access 那条门看着生效，实际上旧 refresh 每次都能续出一张带新角色的新票验签之后、撤旧之前插一道门；新票用这次查到的成员行签
「为了体验好一点」给被降权者重签一对票票刚死又被救活，pver 白加，还替他建立了一个会话响应只回 member_id/role/pver；他必须重新登录（同 D13 退出不返新票的理由）
转让的 IssueForSession 传事务前的 actor 对象A 转让后拿着响应里的新 token 打接口 → 401 + 1005，日志干净得可怕事务提交后重读成员行再签；用步骤 4 那个「故意红一次」验一遍
跨家庭/已移除也返回 403探测者用 403/404 的分布扫出「这个 id 在别家存在」定界在判权之前：别家、非在档一律 ErrNotFound → 404 + 1001（D11 的八条同族）
在 handler 里写 if role < 2 || role > 4值域检查长成了第二个角色分支，收工 grep 变红枚举谓词住 model（Assignable()），service 只问一句

今日名词卡

术语一句话解释
pver（权限版本）成员行上的整数列；票里带着签发那一刻的抄本，两值不等这张票就作废（401 + 1005）
失效通道让已签发的无状态 token 提前死去的手段；本项目两条：在档校验（D5/D13）与 pver 比对（今天接线）
变更点库里让 pver 自增的那两处代码：改角色（今天）与转让主人（今天补齐）
member:setrole矩阵第十二手术名：PUT members/{id}/role 这条边的名字，full 只有 owner，cond 为空
值域门 vs 判权门前者问「这个入参是不是一个合法角色名」（1004），后者问「你有没有这条边」（1003）——两问不能合成一个 if
状态门问「这一行现在的处境允许这件事吗」：唯一 owner 不许被干掉（1010），D12 的 assertRemovable 是同一族
同一条 UPDATE把一组必须同时成立的列变化压进一条语句；等价写法是一个 Transaction 闭包，不许拆两次
乐观锁 version与 pver 分开的一列：它管「读到的行被别人改过没有」（1009），pver 管「这张票还作不作数」（1005）
进程内切上下文被基准禁令的那种做法：在内存里换掉当前角色/家庭而不重签 token；会造成两份真相且重启即失
重签（IssueForSession）会话事实变了才用：签一对新票 + refresh 入库；调用必须在事务提交之后，且用事务后重读的成员行
