platform/authz：判定唯一实现

前六天你一直在欠同一笔账：每个接口都要问一句「这个角色能不能干这事」，而每一次都就地写了一个 if role != model.RoleOwner，后面挂一句 TODO(S4·D14)。今天还账。判定只有一份实现，住在 internal/platform/authz；业务代码只问「能不能」，不许自己算「能不能」。今天把它建起来、把六处散落点搬空并删掉注释，再用两条新接口验收这份地基：GET /api/homeos/permissions（把同一份矩阵导出给前端）与 POST /api/homeos/family/disband（矩阵里最重的那一行）。

2. 为什么要费这个劲

三份理由，一份比一份贵：

  1. 改一条口径要改六处。下周产品说「ward 也能自己改头像」，漏改一处就是线上口子；漏改的那处还特别难测——它的测试恰好在你没补的那条路径上。
  2. 测试测不到规则，只测到 handler。判定散在 handler 里，你得为每条路由各配一组角色用例；判定在一张表里，一组表驱动测试就把四级角色全扫完（明天 D15 就做这组）。
  3. 前端要同一份答案。GET /permissions 必须能从「那份实现」里导出，否则前端自己写一份 role===1 的判断——两份规则第一次分叉的那天，就是「按钮显示了、点了却 403」的那天。

反例长什么样，昨天已经写过一遍，今天给判据：业务包里出现角色比较就是违例。收工时跑两条 grep，两条都必须零命中：

grep -rn "TODO(S4·D14)" server/internal/
唯一的豁免是 platform/authz 自己，以及测试里为了 seed 出某个角色而写的赋值（赋值不是判定）。

3. 包的地基：一个类型、一张表、一个函数

位置在 internal/platform/authz——和 platform/scope 同层。这个位置关系昨天讲过：platform 是跨模块共用的地基，homeos 与 finance 都是它的住户。所以 S6 的财务导出闸、S7 的面可见判定，将来都是往这张表里加一行，而不是各自再建一份。

API 只有一个：Allow(role, act, conds ...bool) bool。第三个参数是调用方算好的事实（「是不是本人」「是不是他的监护人」），authz 不查库、不看请求，只把「角色 + 事实」折成一个布尔。这个形态从今天就定死，因为后面阶段要往矩阵里加需要事实的行——现在留好口子，将来 handler 只加一句调用。

conds 之间是 AND：全真才过。所以同一行里有几种合格关系时（本人、监护人），调用方先把它折成一个布尔再递进来：Allow(actor.Role, ActionMemberUpdate, 是本人 || 是监护人)。别把两组语义不同的条件并列递上去——那样「本人改自己」会因为「不是监护人」被拒，你会以为是矩阵写错了，其实是调用点把 AND 当成了 OR。

fail-closed 规则为什么
动作没登记在矩阵里 → false新增动作忘了加行，结果是「谁都干不了」而不是「谁都干得了」；忘加行的 bug 一秒就暴露
角色不在这一行里 → false四级封闭（D13），值域外的角色（比如没经过 Auth 取到的 0）必然被拒
这一行需要事实，但调用方一个都没递 → false最容易漏的一条：Allow(role, ActionMemberRemove) 少写了「是不是本人」，若空条件算通过，就等于 owner 之外的人也能删自己

4. 判定顺序里它站在哪一格

三道门从 D11 起就钉了顺序，今天加上第四道半：

  1. 认证（D5 中间件）：票不对 → 401 + 1005。
  2. 定界（D10 scope.InFamily，D13 scope.OnFile）：这行不在你的在档名单里 → 404 + 1001。家庭入口用 3001。
  3. 判权（今天 authz）：在你家里、在档，但矩阵没这条边 → 403 + 1003。
  4. 业务状态（S2 起）：有资格、行也对，但当前状态不允许 → 409 + 1010。

本站基准给的排序是三档：显式拒绝 > 角色默认矩阵 > 字段级可见性。今天落中间那档，前两档与第三档各归各位：「显式拒绝」在本阶段只有两个真实来源——不在档（D13 的 status）与访客限时只读（角色本身，矩阵里它就是只读一行），不需要额外一张拒绝表；「字段级可见性」是明天 D16 的正课。至于「家庭级覆盖」与「对象级 ACL」这两层，本站明确不做：一张家庭级开关表加一层对象级授权表，换来的是没人能一眼说出「这个人到底能不能干这件事」。

5. GET /permissions：导出的必须是同一份数据

它是前端「按钮该不该显示」的唯一来源，入参一个都没有——只答你自己（角色从 context 取，没有 member_id 入参；能问别人的权限就等于泄露别人的身份关系）。响应分两栏：

片段 · 响应形状（member 视角）{
  "code": 0, "message": "ok",
  "data": {
    "role": 2,
    "actions": ["finance:write", "member:leave"],     // 无条件可过
    "conditional": ["member:avatar", "member:update"] // 有资格，但要看对象是不是本人
  }
}

两栏的必要性：矩阵里有一类行是「member 仅本人」。只导出无条件那栏，前端会把「我能改自己的头像」显示成没入口；把条件行也算成放行，就等于前端替服务端做了判定——那才是第二份实现。正确分工：两栏都给，前端拿它画界面；真正写操作时服务端每次重跑 Allow，前端显示了不代表放行。

Go 的 map 遍历顺序随机，导出的两个列表必须排序，否则同样的角色每次返回不同顺序，前端快照测试天天红、日志 diff 天天有噪音。这是今天最容易漏的一行代码。

fam=0（注册了但还没进家庭）时，role 快照就是 0，两栏都是空数组——这不算错误，不返 3001。它答的是「你这个角色能干什么」，跟你在不在某个家庭无关；前端拿空数组画「还没进家庭」的空态。家庭入口那些接口（GET /family）才用 3001。

6. POST /family/disband：矩阵里最重的一行

owner 独有的动作。三条语义要钉死：

  • 先清场：除了发起人自己，家庭里还有别的在档成员 → 409 + 1010。要么移除（D12），要么让他们退出（D13）。不搞「连带解散全家」：一条接口顺手清掉六个身份，谁都没法在审计里解释这件事。
  • 解散只软删家庭行：给 homeos_family 写 deleted_at + deleted_by，成员行只把 owner 自己那条按 D12 的 repo 方法清掉。历史业务数据留在库里——「数据留家庭」这条从 D7 就立的规矩，不该被一个管理动作破掉。
  • 此后各接口怎么答：GET /family 查不到家庭行 → 404 + 3001（D9 早就写了这句口径，今天让它真的可达）；这个家庭里其他人的票 → 下一次请求 401 + 1005，因为他们的成员行已不在档。

和 D7 的 ErrFamilyLimit（3004）接得上：家庭数上限数的是「该用户名下在档成员行涉及的家庭」，解散后 owner 的身份行清了，名额就腾出来了，可以重建。「解散」不会把人从 homeos_user 上抹掉——账号是账号，身份是身份，这条分层是 D5 立的。

别忘了那笔 pver 的账：转让与解散都会让手里的 role 快照过时。今天能立刻作废靠的是在档校验（人不在档，票就死）。但「人还在档、角色变了」那一类（明天矩阵管不到它），要 pver+1 才治得住——那是 S4·D17 那条接口的正课，今天只记不修，不许提前把 pver 逻辑塞进 authz：一个是「有没有资格」，一个是「这张票还算不算数」，混在一起两边都讲不清。

完整 · <repo>/server/internal/platform/authz/authz.gopackage authz

import (
    "sort"

    "homecube/internal/homeos/model"
)

// Action 动作名。命名规则 模块:动作，小写，冒号分隔——它是契约字符串，
// 会出现在 GET /permissions 的响应里，改名等于改接口，别随手改。
type Action string

const (
    ActionInviteCreate   Action = "invite:create"
    ActionInviteRevoke   Action = "invite:revoke"
    ActionMemberUpdate   Action = "member:update"
    ActionMemberRemove   Action = "member:remove"
    ActionMemberAvatar   Action = "member:avatar"
    ActionMemberLeave    Action = "member:leave"
    ActionFamilyTransfer Action = "family:transfer"
    ActionFamilyDisband  Action = "family:disband"
)

// rule 矩阵一行。full = 这些角色无条件可过；cond = 这些角色要调用方递上来的
// 事实全为真才过（「是不是本人」「是不是他的监护人」）。
type rule struct {
    full []model.Role
    cond []model.Role
}

// matrix 全站唯一判定数据源。没登记的动作一律拒绝（fail-closed）。
// 明天的 D15 把「面配置」「时间与协作」两组行补进来，并给整张表配表驱动测试。
var matrix = map[Action]rule{
    ActionInviteCreate:   {full: []model.Role{model.RoleOwner}},
    ActionInviteRevoke:   {full: []model.Role{model.RoleOwner}},
    ActionMemberUpdate:   {full: []model.Role{model.RoleOwner}, cond: []model.Role{model.RoleMember, model.RoleWard}},
    ActionMemberRemove:   {full: []model.Role{model.RoleOwner}, cond: nil},
    ActionMemberAvatar:   {full: []model.Role{model.RoleOwner}, cond: []model.Role{model.RoleMember, model.RoleWard}},
    ActionMemberLeave:    {full: []model.Role{model.RoleMember}},
    ActionFamilyTransfer: {full: []model.Role{model.RoleOwner}},
    ActionFamilyDisband:  {full: []model.Role{model.RoleOwner}},
}

// Allow 全站唯一判定入口。handler/service 只调它，不自写角色分支。
func Allow(role model.Role, act Action, conds ...bool) bool {
    r, ok := matrix[act]
    if !ok {
        return false // 动作没登记：拒
    }
    if has(r.full, role) {
        return true
    }
    if has(r.cond, role) {
        if len(conds) == 0 {
            return false // 需要事实却没递：拒，绝不默认放行
        }
        for _, ok := range conds {
            if !ok {
                return false
            }
        }
        return true
    }
    return false
}

// Permit GET /permissions 的响应体。两栏分开：见讲义 5。
type Permit struct {
    Role        model.Role  `json:"role"`
    Actions     []Action  `json:"actions"`
    Conditional []Action  `json:"conditional"`
}

// Of 从同一张表导出某角色的动作集。这里不写第二份清单，只跑 Allow / 查行。
func Of(role model.Role) Permit {
    p := Permit{Role: role, Actions: []Action{}, Conditional: []Action{}}
    for act, r := range matrix {
        switch {
        case has(r.full, role):
            p.Actions = append(p.Actions, act)
        case has(r.cond, role):
            p.Conditional = append(p.Conditional, act)
        }
    }
    // map 遍历顺序随机：不排序就是「同一角色每次返回不同顺序」。
    sort.Slice(p.Actions, func(i, j int) bool { return p.Actions[i] < p.Actions[j] })
    sort.Slice(p.Conditional, func(i, j int) bool { return p.Conditional[i] < p.Conditional[j] })
    return p
}

func has(rs []model.Role, role model.Role) bool {
    for _, r := range rs {
        if r == role {
            return true
        }
    }
    return false
}

ActionMemberRemove 那行的 cond 留空是有意的：D12 定过「member/ward/guest 把自己移除 = 这条边不存在（1003）」，移除只有 owner 一个角色有资格，而 owner 删自己撞的是状态门 1010——留在 service，别塞进矩阵。

func canLeave(self *model.Member) error {
    if self.IsOwner() {
        return response.ErrStateNotAllowed // 处境：这个家庭不能没主人，先转让（D12）
    }
    if !authz.Allow(self.Role, authz.ActionMemberLeave) {
        return response.ErrForbidden       // 资格：ward/guest 没有「自己走」这条边
    }
    return nil

片段 · <repo>/server/internal/homeos/service/family.go 追加（前置：D7 的 FamilyService、D12 的 memberRepo.SoftDeleteInFamily）// Disband 解散：判权（authz）→ 状态门（先清场）→ 软删家庭行 + 清自己的身份行。
// familyID 只来自 token；一个入参都没有。
func (s *FamilyService) Disband(ctx context.Context, familyID, actorID int64, role model.Role) error {
    if familyID <= 0 {
        return response.ErrFamilyNoAccess // fam=0：家庭入口口径 → 404 + 3001
    }
    if !authz.Allow(role, authz.ActionFamilyDisband) {
        return response.ErrForbidden   // 判权 → 403 + 1003
    }
    if _, err := s.families.FindByID(ctx, familyID); err != nil {
        return response.ErrFamilyNoAccess // 已经解散过：GET /family 的同一口径
    }
    onFile, err := s.members.ListInFamily(ctx, familyID) // 已挂 scope.OnFile（D13）
    if err != nil {
        return err
    }
    if len(onFile) > 1 {
        return response.ErrStateNotAllowed // 状态门 → 409 + 1010：先移除或让其退出
    }
    if err := s.members.SoftDeleteInFamily(ctx, familyID, actorID, actorID); err != nil {
        return err // owner 自己的身份行走 D12 那条路：status=removed + 软删留痕
    }
    return s.families.SoftDelete(ctx, familyID, actorID) // deleted_at + deleted_by 成对
}

import (
    "testing"

    "homecube/internal/homeos/model"
)

// TestAllowMatrix 一张表扫完四级角色 × 八个动作。这就是判定收口后的红利：
// 规则在数据里，测试只比数据，不用为每条路由配一组用例。
func TestAllowMatrix(t *testing.T) {
    roles := []model.Role{model.RoleOwner, model.RoleMember, model.RoleWard, model.RoleGuest}
    cases := []struct {
        act   Action
        want  []bool // 依次对应 owner/member/ward/guest，无条件判定时 conds 传 true
    }{
        {ActionInviteCreate, []bool{true, false, false, false}},
        {ActionMemberLeave, []bool{false, true, false, false}},
        {ActionMemberRemove, []bool{true, false, false, false}},
        {ActionFamilyDisband, []bool{true, false, false, false}},
        {Action("not.registered"), []bool{false, false, false, false}}, // fail-closed
    }
    for _, tc := range cases {
        for i, role := range roles {
            if got := Allow(role, tc.act, true); got != tc.want[i] {
                t.Errorf("Allow(%d, %q) = %v, want %v", role, tc.act, got, tc.want[i])
            }
        }
    }
}

// TestAllowNeedsCond 第三条 fail-closed：cond 行没递事实必须拒。
func TestAllowNeedsCond(t *testing.T) {
    if Allow(model.RoleMember, ActionMemberUpdate) {
        t.Fatal("member 改别人：没递事实却放行了")
    }
    if !Allow(model.RoleMember, ActionMemberUpdate, true) {
        // 「是不是本人」为真才该过
        t.Fatal("member 改自己却被拒")
    }
    if Allow(model.RoleMember, ActionMemberUpdate, false) {
        t.Fatal("递了 false 还放行")
    }
    if Allow(model.Role(0), ActionFamilyDisband, true) {
        t.Fatal("零角色（没过 Auth）竟能解散")
    }
}

// TestOfSortedAndComplete 导出必须是矩阵的投影，不是第二份清单。
func TestOfSortedAndComplete(t *testing.T) {
    p := Of(model.RoleMember)
    if !isSorted(p.Actions) || !isSorted(p.Conditional) {

    for _, a := range p.Actions {
        if !Allow(model.RoleMember, a) {
            t.Fatalf("%s 在 actions 里却不该放行：导出与判定分叉了", a)
        }
    }
    for _, a := range p.Conditional {
        if Allow(model.RoleMember, a, false) {
            t.Fatalf("%s 在 conditional 里却是无条件放行", a)
        }
    }
}

isSorted 是测试侧五行内的小 helper（逐个比相邻元素）；别从生产包里借排序函数来断言——断言要比的正是「你有没有在自己的代码里排序」。接口侧再补三条 httptest 断言（用 D11 那套 fixture 与 envelope）：owner 打 disband 前先清场（200）与没清场（409 业务码 1010）、member 打（403 业务码 1003）、解散后 GET /family（404 业务码 3001）、解散后其他人的票打成员列表（401 业务码 1005）。

常见坑（新手 100% 会踩）

坑现象正确姿势
authz 里顺手查库「看看这行归谁」判权与定界糊在一起，1003 与 1001 的分工当天作废authz 只吃 role + 事实 bool；归属由 repo 的 scope 决定，事实由 service 算好递进来

cond 行调用时少递事实看起来在用它，实际走了 len(conds)==0 那条放行分支没递事实一律拒（第三条 fail-closed）+ TestAllowNeedsCond 钉住
