建家庭与成员建档

认证周结束了，但你的用户还是个「无家可归」的 uid——token 里 fam=0，什么业务数据都碰不到。今天开家庭域：POST /api/homeos/families 建家庭（创建者自动成为 owner 成员），POST /api/homeos/members 给还没有账号的家人建档。从今天的建家庭那一刻起，所有数据都有 family_id 了——这是下周隔离大戏的舞台。

今日目标

知识讲义

1. User 不是 Member：账号与身份分离

这是家庭域最重要的一个建模决定。homeos_user 是账号（手机号 + 密码哈希），全局一份；homeos_member 是某人在某家庭里的身份（角色、称谓、监护关系、pver、status），每个家庭一份。爸爸在自家是 owner，在爷爷家可能是 member——同一条 user，两条 member。所以：

  • token 里 uid 与 mid 并存：uid 回答「哪个账号」，mid 回答「这个家庭里的哪个身份」；
  • 业务数据的作者一律记 member_id，不记 user_id——数据属于家庭，人走了（status 变已退出）数据还留在这个家庭；
  • 成员可以没有账号：给两岁的孩子建档，她永远不会登录，但流水要记「买奶粉 → 给谁」。

2. relation：称谓的权威字段

relation 存的是家庭内称谓——「爸爸」「妈妈」「宝宝」「奶奶」。它是权威字段：首页成员区、流水的「协作对象」、通知文案，全部读它，不许各页面自己维护一套叫法。建档时必填，编辑时可改（本周六的 PUT 接口）。注意它和 role 是两根轴：relation 是亲情语义（给人看），role 是权限语义（给矩阵看）——「宝宝」通常配 ward 角色，但「爷爷」配什么角色由创建者决定，两者不互相推导。

3. 建家庭 = 一个事务两行数据

创建家庭绝不能只插 family 一行：创建者必须同时成为这个家庭的第一个成员（role = owner），否则家庭没有主人、你自己也进不去。两行必须同生共死——这就是 S3 事务那课的实战现场：任一行失败整体回滚。另外两条规则今天一起落：

  • 家庭数上限：一个账号至多加入 5 个家庭，超限 → 409 + 3004（今天先管「创建」这一侧，「受邀加入」侧明天在 accept 里同样拦截）；
  • 时区与币种：建家庭入参含 timezone（如 Asia/Shanghai）与 currency（如 CNY）——服务端只存不算（不做汇率换算），但字段从第一天就在，后补要迁移全表。

「新家庭必须选面、不允许 0 面家庭」是壳基座阶段面配置能力出生时才有的强制步骤——今天建家庭成功后不选面也合法，service 里留一个注释钩子即可，不要提前实现面配置（那是清单外接口）。

今日增量（在学习仓里落盘）

今天属增量类型 ②：加两条路由与 handler（真实现，不落假数据）。受保护组今天正式开张：families.POST("", ...) 与 members.POST("", ...) 都挂在 middleware.Auth 之后。

步骤 1 · service：CreateFamily

完整 · server/internal/homeos/service/family.gopackage service

import (
    "context"
    "errors"
    "fmt"

    "gorm.io/gorm"

    "homecube/internal/homeos/model"
    "homecube/internal/homeos/repo"
    "homecube/pkg/response"
)

const maxFamiliesPerUser = 5

type FamilyService struct {
    db      *gorm.DB          // 事务要拿 *gorm.DB；单表操作仍走 repo 接口
    members repo.MemberRepo
    auth    *AuthService      // 建家庭成功要重签 token（当前会话切到新家庭）
}

func NewFamilyService(db *gorm.DB, members repo.MemberRepo, auth *AuthService) *FamilyService {
    return &FamilyService{db: db, members: members, auth: auth}
}

type CreateFamilyInput struct {
    Name     string
    Timezone string
    Currency string
    Relation string // 创建者自己在这个家庭里的称谓
}

// CreateFamily 一个事务写两行：family + 创建者的 owner 成员。
func (s *FamilyService) CreateFamily(ctx context.Context, userID int64, in CreateFamilyInput) (*model.Family, *model.Member, error) {
    n, err := s.members.CountActiveByUser(ctx, userID)
    if err != nil {
        return nil, nil, fmt.Errorf("create family: count: %w", err)
    }
    if n >= maxFamiliesPerUser {
        return nil, nil, response.ErrFamilyLimit // → 3004 / 409
    }
    var fam model.Family
    var mem model.Member
    err = s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        fam = model.Family{Name: in.Name, Timezone: in.Timezone, Currency: in.Currency}
        if err := tx.Create(&fam).Error; err != nil {
            return fmt.Errorf("create family row: %w", err)
        }
        mem = model.Member{
            FamilyID: fam.ID, UserID: &userID, // 创建者必有账号：UserID 非空
            Name: in.Relation, Relation: in.Relation,
            Role: model.RoleOwner, Status: model.StatusActive, Pver: 0,
        }
        if err := tx.Create(&mem).Error; err != nil {
            return fmt.Errorf("create owner member: %w", err)
        }
        return nil
    })
    if err != nil {
        return nil, nil, err // 任一行失败：两行都没写进去（S3 事务课的第一次实战）
    }
    // 钩子：壳基座阶段面配置出生后，此处接「强制选面」流程；今天不实现
    return &fam, &mem, nil
}

成员建档 service 今天从简（同一个文件或 member.go）：校验 relation 必填、role 只收 ward/member（owner 只能由转让产生，明天邀请进来的默认 member）、ward 建议带 guardian_id（必须是同家庭在档成员，否则 1004）。无账号成员 user_id 为 NULL——model 里是 UserID *int64，指针表达可空（S1·D2 的指针语义第三次上岗）。

步骤 2 · handler：从 context 取身份

片段 · server/internal/homeos/handler/family.go（前置：昨天的 middleware 六键）type createFamilyReq struct {
    Name     string `json:"name" binding:"required,max=30"`
    Timezone string `json:"timezone" binding:"required"`
    Currency string `json:"currency" binding:"required,len=3"`
    Relation string `json:"relation" binding:"required,max=10"`
}

// CreateFamily 处理 POST /api/homeos/families（受保护）。
func (h *FamilyHandler) CreateFamily(c *gin.Context) {
    var req createFamilyReq
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Fail(c, 400, response.CodeInvalidParam, "参数错误")
        return
    }
    userID := c.GetInt64("userID") // 身份只从 context 来——参数里的 user_id 一律不信
    fam, mem, err := h.families.CreateFamily(c.Request().Context(), userID, service.CreateFamilyInput{
        Name: req.Name, Timezone: req.Timezone, Currency: req.Currency, Relation: req.Relation,
    })
    if err != nil {
        response.FailErr(c, err)
        return
    }
    // 建家庭成功 → 当前会话切到新家庭：重签 token（D3 的 issueTokens 复用）
    access, refresh, err := h.auth.IssueForSession(c.Request().Context(), userID, mem)
    if err != nil {
        response.FailErr(c, err)
        return
    }
    response.Created(c, gin.H{"family": fam, "member": mem,
        "access_token": access, "refresh_token": refresh})
}

IssueForSession 是把 D3 的 issueTokens 包一层公开方法（签一对 token + refresh 入库），下周切换家庭、接受邀请都复用它——「会话变了 = token 重签」从建家庭这天就是肌肉记忆。哨兵集补 ErrFamilyLimit（→ 3004 / 409）。成员建档 handler 同形，从 c.GetInt64("familyID") 取当前家庭，路由 members.POST("", ...)。

常见坑（新手 100% 会踩）

坑现象正确姿势
建家庭只插 family 一行家庭没有 owner，创建者自己 token 里 fam 还是 0，进不去门事务两行：family + owner member，同生共死
handler 从请求体读 user_id改一下 body 就能替别人建家庭身份只认 c.GetInt64("userID")；body 里出现身份字段直接 1004
member.UserID 用 int64 零值表示「无账号」0 到底是「没账号」还是「id=0 的用户」？永远说不清*int64：NULL 才是没有，指针表达可空
relation 存 role 的值（"owner"）首页给孩子显示「owner」relation 是称谓（爸爸/宝宝），role 是权限枚举，两根轴不混
建档时 role 随便传客户端传 role=1，人人自建 owner建档只收 ward/member；owner 唯一来源是建家庭与转让
先查上限再插入，不担心并发双击提交建出第 6 个家庭教学期接受（上限是软约束）；要严防就在事务里做 count，S5 并发课再回来加固
建家庭后不重签 token前端拿着 fam=0 的旧 token，看什么都是 404，以为隔离写坏了会话家庭一变就重签——今天的 IssueForSession 就是为这个存在的

今日名词卡

术语一句话解释

卡壳时查什么

正文自足，只有两种情况出去查：

  • GORM 事务 API 忘了：回 S3 阶段总览找事务与软删那张卡；db.Transaction(func(tx) error) 的返回 error 即回滚信号。
  • 指针字段与 NULL 的映射：同上，S3 的 GORM 关联/字段那课讲过 *int64 ↔ 可空列。

建家庭 500 时先看终端的 SQL 日志：十有八九是 member 表缺列（pver/status 上周补的迁移没跑）。make migrate-up（或你 S3 建的等价目标）重放一遍再试。
