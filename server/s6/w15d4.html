预算告警钩子：platform Notifier 占位

预算的最后一块拼图：用超阈值时触发 budget_alert 通知。麻烦在于——通知表、未读口径、通知接口全都是 S7 的活，今天一行都不能建。这正是全站跨模块纪律的实战现场：finance 不碰 homeos 的任何表，调用点收在 platform 的接口后面。今天定义 Notifier 接口 + 一个日志占位实现，把钩子钉在正确的位置；S7 建好通知表后，只换实现，finance 侧一个字不改。

今日目标

知识讲义

1. 钩子挂在哪：写路径，事务提交之后

告警的触发源是「新记了一笔支出，把 used 顶过了阈值」。所以钩子的正确位置在 POST /api/finance/transactions 的 service 写路径里：入账事务提交成功之后，调一次 budgetSvc.CheckAlert(ctx, familyID, tx)。三个「为什么不」：

候选位置为什么不行
GET budgets 聚合时顺带判定读路径产生副作用：没人打开预算页就永远不告警；一打开就重算，行为随访问漂移
入账事务内部通知发送失败会回滚入账——记账是主操作，告警是尽力而为的副产品，主从不能倒置
finance 里起定时器轮询定时器满天飞是 S7 到期中心要收编的反模式；预算告警根本不需要轮询，事件源就是写路径本身

S7 的伏笔今天埋好：CheckAlert 判定通过后调 Notifier.Send。S6 期它是同步的日志实现，快得可以忽略；S7 换成真通知（写 homeos 通知表 + 未读计数）时，要求实现方自己保证「不阻塞请求链路」——这是接口注释里写明的契约，不是 finance 的义务。

2. 阈值判定：整数运算，不碰浮点

阈值是百分比（默认 80，S6·D29 起从面内设置读）。判定「used 达到 limit 的 pct%」如果写成 float64(used) >= float64(limit)*0.8，就违反了金额禁浮点的全站纪律——比率也不例外，整数运算一样简单：

片段 · 阈值判定（used、limit 均为 int64 分，pct 为 0-100 整数；注意乘法放左边不会溢出：家庭级金额 ×100 离 int64 上限很远）func reached(used, limit int64, pct int) bool {
    return limit > 0 && used*100 >= limit*int64(pct)
}

3. 去重：alerted_at 落在预算行上

预算天然按周期一行（S6·D19 的归零口径），所以「同周期同预算只告警一次」不需要额外的告警记录表——给 finance_budget 加一列 alerted_at TIMESTAMPTZ NULL 就够了：

  • alerted_at IS NULL 且判定通过 → Send + 把 alerted_at 置为 now（一次 UPDATE）。
  • alerted_at 非空 → 跳过。周期翻篇自动「重置」，因为下个周期是另一行。
  • 昨天 PUT 调高 limit_cents 时把 alerted_at 复位为 NULL——昨天的 TODO 今天兑现：限额从 30 万调到 50 万后，used 再顶到 80% 应该重新告警一次。

并发口径：两笔流水同时入账、同时判定通过怎么办？UPDATE 带条件 WHERE alerted_at IS NULL，影响行数为 1 的那个请求才 Send——数据库替你做了裁判，不需要加锁。今天先按串行测试，-race 下并发用例是 S7 换真实现时的事。

4. Notifier 接口：占位不是假入口

「注册了但没实现」是明账里的反例，那 LogNotifier 算不算？不算——判据是行为是否真实、契约是否兑现：接口有真实实现（写结构化日志）、有测试断言、调用方行为完整；S7 换实现是演进，不是补坑。接口定义里把 S7 的要求写成注释契约：

片段 · server/internal/platform/notify/notify.go（新包；platform 是跨模块接口的唯一存放地）package notify

// Event 一次通知投递的最小载荷。Kind 取值 S7 定版：budget_alert / system / reminder。
type Event struct {
    FamilyID  int64
    Kind      string
    MemberIDs []int64          // 投递给哪些成员；空 = 家庭内全体成人
    Payload   map[string]any  // 如 {"budget_id":1,"period":"2026-10","used_cents":250000,"limit_cents":300000}
}

// Notifier 通知投递接口。实现方契约：
//  1. 不得阻塞调用方的请求链路（S7 真实现自行异步化）；
//  2. 返回 error 仅用于日志与测试，调用方不因 Send 失败回滚业务。
type Notifier interface {
    Send(ctx context.Context, e Event) error
}

跨模块红线复习：finance 里不许出现 INSERT INTO homeos_notification，甚至不许出现「通知表」这个词的 SQL。今天你写下的 notify.Notifier 依赖，就是 S4 的 FamilyDirectory 之后第二个收在 platform 后面的跨模块调用点。日后拆服务，换的只是这个接口的实现。

步骤 2 · LogNotifier 占位实现

完整 · server/internal/platform/notify/log_notifier.gopackage notify

import (
    "context"
    "log/slog"
)

// LogNotifier 是 S6 期占位实现：只写结构化日志。S7 建通知表后由 DBNotifier 替换，
// 替换点在装配根 cmd/homecube/main.go，业务模块无感。
type LogNotifier struct{ logger *slog.Logger }

func NewLogNotifier(l *slog.Logger) *LogNotifier { return &LogNotifier{logger: l} }

func (n *LogNotifier) Send(_ context.Context, e Event) error {
    n.logger.Info("notify placeholder",
        "kind", e.Kind, "family_id", e.FamilyID, "members", e.MemberIDs, "payload", e.Payload)
    return nil
}

步骤 3 · CheckAlert 与写路径挂钩

片段 · server/internal/finance/service/budget_service.go 追加（前置：notifier 由装配根注入 BudgetService；阈值先常量 80，S6·D29 改读设置）func (s *BudgetService) CheckAlert(ctx context.Context, famID int64, categoryID *int64, periodKey string) error {
    budgets, err := s.repo.FindByPeriod(ctx, famID, periodKey)
    if err != nil || len(budgets) == 0 { return err } // 未设预算：不告警、不折算（昨天的红线）
    start, end, locErr := s.bounds(ctx, famID, periodKey)
    if locErr != nil { return locErr }
    used, err := s.txRepo.SumExpenseByCategory(ctx, famID, start, end)
    if err != nil { return err }
    for _, b := range budgets {
        u := rollup(b.CategoryID, used, s.tree)
        if !reached(u, b.LimitCents, 80) { continue }
        // 条件 UPDATE 做并发裁判：抢到 alerted_at 的请求才发
        ok, err := s.repo.MarkAlerted(ctx, b.ID, b.FamilyID) // WHERE id=? AND family_id=? AND alerted_at IS NULL
        if err != nil { return err }
        if !ok { continue }
        _ = s.notifier.Send(ctx, notify.Event{
            FamilyID: famID, Kind: "budget_alert",
            Payload: map[string]any{"budget_id": b.ID, "period": periodKey,
                "used_cents": u, "limit_cents": b.LimitCents},
        }) // 尽力而为：Send 失败只记日志，不影响已入账的流水（故意忽略须注释，S1·D4 纪律）
    }
    return nil
}

调用点只有一处：流水创建的 service 在事务提交成功后，按流水的 category_id 与 occurred_at 算出所属周期键，调 CheckAlert。转账与收入直接跳过。
