乐观锁 version：并发编辑后到者 409+1009

家庭记账的真实并发场景：晚饭桌上，一个人打开电脑改一笔流水的金额，另一个人同时在手机上改同一笔的备注。没有乐观锁，后保存的人把先保存的人整个覆盖掉，谁也不知道发生了什么。今天给 PUT /api/finance/transactions/{id} 装上 version 乐观锁：请求必须带上「我读到的是第几版」，版本对不上就 409 + 1009，并把双版本信息放进 payload，让客户端能引导用户刷新重改。

今日目标

知识讲义

1. 丢失更新：先读后写的经典竞态

片段 · 没有乐观锁时的时间线T1: 设备A 读流水#7 (amount=3500, version=1)
T2: 设备B 读流水#7 (amount=3500, version=1)
T3: 设备A 提交 amount=4000   → 库里是 4000
T4: 设备B 提交 note="超市"   → 它带的整行还是基于 3500 的旧读，A 的 4000 被覆盖回 3500

T4 就是丢失更新：B 没有恶意，它只是拿着过期的读结果写回了全行。悲观锁（SELECT FOR UPDATE）能解，但家庭场景冲突率极低，为极低概率事件让每次编辑都排队拿锁，不划算。乐观锁的赌注正相反：先不锁，提交时验证「我读的版本还是不是当前版本」——是就写，不是就拒绝。

2. 验证必须原子：一条 UPDATE 完成

片段 · 乐观锁 UPDATE 的固定形状UPDATE finance_transaction
SET amount_cents = $1, note = $2, ...,
    version    = version + 1,
    updated_at = now()
WHERE id = $3 AND family_id = $4
  AND version = $5            -- 客户端带来的「我读到的版本」
  AND deleted_at IS NULL;
  • RowsAffected = 1：版本还匹配，写入成功，返回新对象（version 已 +1）。
  • RowsAffected = 0：三种可能——行不存在 / 越权 / 版本已被人抢先 +1。存在性一查即可区分：不存在或越权 → 404 + 1001；存在但版本不对 → 409 + 1009。

「先 SELECT 比版本、再 UPDATE」是错的：比较与写入之间有缝，两个请求可以都通过比较。判定必须写进 UPDATE 的 WHERE 里，让数据库在行锁内一次完成——这是 S5 讲原子更新时的同一个教训，昨天软删的 RowsAffected 状态机也是它。

3. 1009 的 payload：双版本 + 当前行

片段 · 冲突响应（HTTP 409）{
  "code": 1009,
  "message": "版本冲突：该流水已被其他人修改",
  "data": {
    "your_version": 1,
    "current_version": 2,
    "current": { "id": 7, "amount_cents": 4000, "note": "", "version": 2, "updated_at": "..." }
  }
}

为什么不能只回一句「冲突了」：客户端拿到双版本与当前行，才能做出体面的引导——「这笔账已被改为 ¥40.00，请基于最新数据重新编辑」，并直接用 current.version 发起第二次提交。冲突响应是给对方留的台阶，信息越全，重试路径越短。这也是错误码表把 1009 单独列出来的原因：它是唯一强制要求 payload 带结构化数据的错误码。

4. version 的全站口径

version INT NOT NULL DEFAULT 1 是 S3 起每张业务表的通用列，写一次 +1——昨天的软删与恢复也 +1 了（删除/恢复同样是「写」，并发恢复也要能被拦）。今天起它有了第一个消费方；账户（编辑）、分类（编辑）、面配置（S7）都走同一套。请求体里的 version 是必填字段：缺了就是 1004，不是「当 1 处理」。

今日增量（在学习仓里落盘）

今天属增量类型 ⑤+③：把 PUT 从无锁更新换成乐观锁更新 + 并发冲突测试。

步骤 1 · repo：原子 UPDATE

片段 · server/internal/finance/repo/transaction.go// UpdateWithVersion 返回 (是否命中, error)。命中=false 时上层再区分 1001/1009。
func (r *TxRepo) UpdateWithVersion(ctx context.Context, familyID, txID int64, ver int, patch map[string]any) (bool, error) {
    patch["version"] = gorm.Expr("version + 1")
    patch["updated_at"] = gorm.Expr("now()")
    res := r.db.WithContext(ctx).
        Model(&model.Transaction{}).
        Where("id = ? AND family_id = ? AND version = ? AND deleted_at IS NULL", txID, familyID, ver).
        Updates(patch)
    return res.RowsAffected == 1, res.Error
}

步骤 2 · service：三岔口 + 双版本 payload

片段 · server/internal/finance/service/transaction.go（前置：昨天的 SoftDelete/Restore 已在此文件）func (s *TxService) Update(ctx context.Context, a Actor, id int64, in *UpdateTxInput) (*model.Transaction, error) {
    ok, err := s.repo.UpdateWithVersion(ctx, a.FamilyID, id, in.Version, in.Patch())
    if err != nil { return nil, err }
    if ok { return s.repo.GetByID(ctx, a.FamilyID, id) }
    cur, err := s.repo.GetAnyByID(ctx, a.FamilyID, id) // 含软删行，仍限本家庭
    switch {
    case err != nil:              return nil, err
    case cur == nil:              return nil, response.ErrNotFound          // 404 + 1001
    case cur.DeletedAt != nil:    return nil, response.ErrNotFound          // 已删 = 业务视角不存在
    }
    return nil, &response.VersionConflictError{                            // 409 + 1009
        YourVersion: in.Version, CurrentVersion: cur.Version, Current: cur,
    }
}

VersionConflictError 是 pkg/response 里今天新补的一个带数据的哨兵（类型 ① 的顺手活）：FailErr 遇到它时，除了 409+1009 还把结构体塞进 data。哨兵错误从「一个值」升级成「一个类型」，为的就是携带冲突现场。

步骤 3 · 冲突测试 + 验收

完整 · server/internal/finance/service/transaction_version_test.gopackage service

import (
    "errors"
    "testing"

    "homecube/pkg/response"
)

func TestUpdateVersionConflict(t *testing.T) {
    svc, a := newTestTxService(t), Actor{FamilyID: 1, MemberID: 10}
    ctx := t.Context()
    tx := mustCreateTx(t, svc, a) // version=1

    // 设备A 基于 version=1 编辑成功 → 库里 version=2
    got, err := svc.Update(ctx, a, tx.ID, &UpdateTxInput{Version: 1, Note: "A改"})
    if err != nil || got.Version != 2 { t.Fatalf("首次编辑应成功且 version=2: %v %v", got, err) }

    // 设备B 仍拿 version=1 来改 → 409 + 1009，payload 双版本
    _, err = svc.Update(ctx, a, tx.ID, &UpdateTxInput{Version: 1, Note: "B改"})
    var vc *response.VersionConflictError
    if !errors.As(err, &vc) { t.Fatalf("应 1009，got %v", err) }
    if vc.YourVersion != 1 || vc.CurrentVersion != 2 {
        t.Fatalf("双版本 payload 错: your=%d current=%d", vc.YourVersion, vc.CurrentVersion)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
先 SELECT 比版本再 UPDATE并发下两个请求都通过比较，锁形同虚设版本判定写进 UPDATE 的 WHERE，看 RowsAffected
冲突只回 message 不回 payload客户端无法引导用户，只能让用户盲猜1009 必带 your_version/current_version/current
版本不匹配也回 1001「被别人改了」与「根本没有」混为一谈存在性一查后分岔：没有 → 1001；有但版本旧 → 1009
请求体缺 version 时默认按最新处理乐观锁被静默绕过，丢失更新复活version 必填，缺了 1004
软删/恢复忘了 version+1「删了又恢复」期间的并发编辑察觉不到变化任何写都 +1，口径全站唯一（昨天的 UPDATE 已经这么写了）
成功后返回内存里的旧对象响应里的 version 还是旧的，客户端下次提交必冲突成功后重读一次（或 RETURNING），返回库里真身

今日名词卡

术语一句话解释
丢失更新两个「先读后写」并发，后写者用过期读结果覆盖先写者的修改
乐观锁不预先加锁，提交时用版本号验证「读的还是不是最新」；适合低冲突场景
悲观锁读时就锁住（SELECT FOR UPDATE），写者排队；高冲突场景才值得
version通用列，DEFAULT 1，任何写 +1；客户端提交时必须回传读到的值
1009版本冲突（409），响应 data 必带双版本与当前行
双版本 payloadyour_version（你带来的）与 current_version（库里现在的），给重试留台阶
errors.As从错误链里取出目标类型的实例——带数据哨兵用 As，纯值哨兵用 Is（S1·D4 的延伸）
RowsAffected 状态机UPDATE 命中 0 行 ≠ 失败，是「条件不满足」的信号，再分流 1001/1009

卡壳时查什么

  • 竞态与原子更新的直觉：回 S5 并发周——「检查与执行之间的缝」是同一个主题。
  • errors.Is 与 errors.As 的区别：S1·D4 讲了 Is；今天第一次用 As 取带数据的错误类型，对照名词卡再读一遍包装链。
  • FailErr 怎么把哨兵映射成信封：S1·D6 的 response 包，今天给它加 VersionConflictError 分支。
  • 为什么成功路径要重读一次：看步骤 2 里 GetByID 的位置，响应必须反映库里真身。
