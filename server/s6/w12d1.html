流水表与创建：client_request_id 幂等三态

S6 进入财务功能面。表在 S3 就建好了、鉴权与幂等表在 S4 立好了、并发与工程化在 S5 练过了——从今天起把这些地基变成能记账的服务端。第一个端点就是最核心的写接口：POST /api/finance/transactions。它必须自带 client_request_id 幂等键：手机在电梯里超时重发一次，账不能记两笔。今天把幂等三态一次做对，后面所有写接口都抄这个骨架。

今日目标

知识讲义

1. 为什么创建流水必须幂等

移动端记账的真实链路：用户点「保存」→ 请求发出 → 地铁进隧道 → 客户端 10 秒超时 → 客户端自动重试。第一次请求可能已经在服务端落库成功，只是响应没回来。没有幂等键，重试就是第二笔一模一样的支出；用户看到重复流水，对账永远差一笔——这类「重复写入」是家庭记账类服务端最高频的数据正确性事故。

解法是把「这次操作」和「这次 HTTP 请求」解耦：客户端为每次操作生成一个 client_request_id（UUID 即可），重试时原样带上同一个 id 和同一个请求体。服务端以 (family_id, client_request_id) 为幂等键，保证同一次操作无论到达几次，只产生一条流水。

到达情况服务端动作响应
首次（幂等键没见过）创建流水 + 落幂等记录（同一个事务）201 + code 0 + 流水对象
重放，请求体哈希一致不创建，取出当时存的响应快照与首次完全相同（同状态码、同 body）
同键，请求体哈希不同拒绝：一个键只能对应一次操作409 + 1008（幂等冲突）

重放必须返回原结果，不是返回一个错。客户端重试时期望的就是「我上次那笔到底成没成」；返回原 201 响应，客户端无感知地拿到同一条流水 id。若返回 409，客户端就得再写一套「409 之后去查一遍」的逻辑——把复杂度推给每个调用方，是偷懒的服务端。

2. finance_transaction 列口径（S3 建表，今天对齐语义）

参考 · S3 迁移里的 DDL（今天不改表，只对齐口径）CREATE TABLE finance_transaction (
    id                BIGSERIAL PRIMARY KEY,
    family_id         BIGINT NOT NULL,
    type              TEXT NOT NULL,            -- income / expense / transfer，明天展开
    amount_cents      BIGINT NOT NULL,          -- 恒为正整数；方向由 type 表达，禁止存负数

    occurred_at       TIMESTAMPTZ NOT NULL,     -- 业务发生时间，与 created_at 分开
    is_private        BOOLEAN NOT NULL DEFAULT false,
    client_request_id TEXT NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at        TIMESTAMPTZ NULL,
    deleted_by        BIGINT NULL,
    version           INT NOT NULL DEFAULT 1
);
CREATE UNIQUE INDEX uq_fintx_idem  ON finance_transaction (family_id, client_request_id);
CREATE INDEX idx_fintx_query ON finance_transaction (family_id, occurred_at DESC, id DESC);
  • 金额一律 *_cents BIGINT、Go 侧 int64——禁浮点从 S3 第一条迁移起就是铁律，今天第一次真正写它。
  • amount_cents 恒为正：支出不存负数，方向由 type 表达。存负数会让「求和」「取绝对值」散落各处，口径必炸。
  • occurred_at 与 created_at 分离：补记上个月的账，业务时间是上个月，落库时间是现在。报表按 occurred_at 聚合。
  • 唯一索引 (family_id, client_request_id) 是幂等的数据库级兜底：即使应用层「先查后插」被两个并发请求同时穿过，第二个 INSERT 也会撞唯一约束——捕获它，按重放处理。

3. 幂等记录长什么样（复用 S4 建的幂等表）

S4 建幂等表时讲过原理，今天第一次在真业务里用它。每行存四样东西：

片段 · 幂等记录的关键字段family_id + client_request_id   -- 幂等键（联合唯一）
body_hash                       -- 请求体的 sha256，判「同体/异体」
resp_status + resp_body         -- 首次响应的快照，重放时原样吐回

「同体」的判定 = 整个请求体规范化后的哈希一致。客户端重试时本来就该原样重发，所以哈希天然相等；一旦有人拿旧 id 配新 body，哈希对不上，就是 1008。先插幂等记录占位、再写业务行、最后回填响应快照，三步收进同一个数据库事务——事务要么全成要么全无，不留「有流水没幂等记录」的缝隙。

为什么幂等表放 platform 不放 finance？因为账户、分类、设置……后面每个写接口都要幂等，它是横切设施，归 internal/platform；finance 通过接口调用它，不直查它的表（跨模块纪律）。

步骤 2 · service 层：幂等三态 + 创建

片段 · server/internal/finance/service/transaction.go（前置：model 与 platform 的 IdempotencyStore 接口已定义）func (s *TxService) Create(ctx context.Context, a Actor, in *model.CreateTxInput) (*model.Transaction, error) {
    hash := idem.HashBody(in)                       // sha256(规范化 JSON)
    rec, err := s.idem.Find(ctx, a.FamilyID, in.ClientRequestID)
    switch {
    case err == nil && rec.BodyHash == hash:       // ② 同体重放：吐回原结果
        return rec.ReplayTransaction()
    case err == nil:                                // ③ 同键异体：1008
        return nil, response.ErrIdempotentConflict
    case !errors.Is(err, platform.ErrIdemNotFound): // 真错误，别吞
        return nil, err
    }
    // ① 首次：校验 → 单事务内「插幂等记录 + 插流水」→ 回填响应快照
    if in.AmountCents <= 0 {
        return nil, response.ErrAmountInvalid      // 400 + 4001
    }
    tx, err := s.repo.InsertWithIdem(ctx, a, in)     // 撞唯一索引 → 转按重放处理
    if err != nil { return nil, err }
    _ = s.idem.SaveSnapshot(ctx, a.FamilyID, in.ClientRequestID, tx)
    return tx, nil
}

Actor 是 finance 自己的小结构体（FamilyID / MemberID / Role），由 handler 从 gin context 读出装配——c.GetInt64("familyID")、c.GetInt64("memberID")，角色用 c.MustGet("role").(model.Role)，这是 S4 立好的读取口径，禁止裸键。

常见坑（新手 100% 会踩）

坑现象正确姿势
重放时返回 409 或重新创建客户端重试收到「冲突」，或账记了两笔同体 = 原样吐回首次响应（同状态码同 body）；只有异体才 1008
「先查后插」不在事务里并发双击穿过查询，两条 INSERT 都成功幂等记录与流水同事务写入；唯一索引撞了按重放兜底
金额存了负数或浮点求和口径混乱、0.1+0.2 类误差amount_cents 恒为正 int64，方向由 type 表达
金额 ≤0 返回 1004参数错误与金额非法混在一起，前端没法针对性提示金额语义错误走 400 + 4001；请求体缺字段/格式烂才 1004
用 created_at 当业务时间补记历史账全堆在「今天」聚合与展示一律 occurred_at
幂等键做成全局唯一两个家庭撞了同一个 UUID（或恶意撞键）互相干扰键是 (family_id, client_request_id) 联合维度

今日名词卡

术语一句话解释
幂等（idempotent）同一操作执行一次与执行 N 次，系统状态与返回结果相同
client_request_id客户端为「一次操作」生成的唯一 id，重试原样重发；服务端幂等键的组成部分
幂等三态首次创建 / 同体重放返回原结果 / 同键异体 409+1008
body_hash请求体规范化后的 sha256，用来判「同体还是异体」
响应快照首次成功响应的存档，重放时原样吐回，保证两次响应逐字节一致
amount_cents金额的最小货币单位整数（int64），全站禁浮点
occurred_at业务发生时间，与落库时间 created_at 分离，聚合按它
双写窗口「查幂等记录」与「写业务行」之间的时间缝，并发会穿过去——用事务+唯一索引封死
1008幂等冲突：client_request_id 已用过且请求体不同（409）
4001金额非法：≤0、超出可用余额、转账两端同账户（400）

卡壳时查什么

  • 哨兵错误与 errors.Is 不熟：回 S1·D4（error 包装与哨兵集）。
