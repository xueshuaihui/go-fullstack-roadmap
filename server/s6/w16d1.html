报表三视图：趋势/分类/成员 SQL 聚合

B7 报表段开工。GET /api/finance/reports/summary 是施工清单里的一条接口，但它要喂饱三个视图：trend（趋势）/ category（分类占比）/ member（成员维度）。今天用 view 参数分发，把三个视图的聚合 SQL 全部写真（月档周期），明天升级五档分桶、后天加环比与累计。三个视图各有各的坑：趋势的桶、分类的树、成员的跨模块——今天一次踩平。

2. 共享 WHERE：一套过滤条件喂三个视图

三个视图的差别只在 GROUP BY 的维度，过滤条件是同一套，抽成一个函数拼进 GORM 查询（S5 报表并发段立下的「条件构建只有一份」纪律）：

片段 · server/internal/finance/repo/report_repo.go（前置：db 为 S3 的 GORM 实例；viewer 携带请求者的 memberID 与角色）func (r *ReportRepo) base(q *gorm.DB, famID int64, start, end time.Time, v Viewer) *gorm.DB {
    q = q.Table("finance_transaction").
        Where("family_id = ? AND deleted_at IS NULL AND occurred_at >= ? AND occurred_at < ?", famID, start, end)
    if !v.IsOwner {
        // 行级可见性：私密流水仅作者与 owner 可读——聚合也必须守，否则成员视图靠求和就能探测别人的私密金额
        q = q.Where("(NOT is_private OR author_member_id = ?)", v.MemberID)
    }
    return q
}

私密流水与聚合：S4 立的行级可见性红线在报表段最容易破。列表页过滤了 is_private，聚合 SQL 忘了过滤——成员视图里别人的「私密消费合计」就被一个 SUM 泄露了。口径：凡是我看不见的行，也不许以任何聚合形态出现在我的报表里。owner 例外（全站口径：owner 可见全部）。

3. 三个视图的 GROUP BY 与响应形状

viewGROUP BY响应行字段后处理
trend周期桶（今天只有 month 单桶；明天五档）period / income_cents / expense_cents / net_cents桶序列补齐空桶（没流水的周期给 0 行，不断档）
categorycategory_id（direction='expense'）category_id / name / amount_cents / share_bp叶子向一级分类归并（D20 的 rollup 复用）；name 查 finance 自己的分类表
memberauthor_member_idmember_id / name / amount_cents / share_bpname 走 platform 接口批量解析，见下

成员名的跨模块纪律：finance_transaction.author_member_id 只是个数。名字在 homeos 的成员表里——finance 不许 join，也不许直查。做法：聚合出 map[memberID]amount 后，调 S4 建好的 platform 家庭目录接口 Members(ctx, familyID) 拿全量成员（有界小集合），Go 侧拼名字；查不到的 id（已退出成员）显示「历史作者」占位，金额照算——数据留家庭，这是成员软删时定下的口径。

占比 share_bp：万分比整数。share_bp = amount * 10000 / total（整数除法），total 为 0 时全给 0。前端拿 bp 除以 100 显示百分号——金额与比率全程无浮点，D22 立过的规矩。

片段 · view=member 的响应 data（有界小集合：直接 list，无游标字段）{
  "view": "member", "period": "2026-10",
  "total_expense_cents": 312000,
  "list": [
    { "member_id": 11, "name": "爸爸", "amount_cents": 200000, "share_bp": 6410 },

注意 share_bp 整数除法会有舍入残差（6410+3590=10000 恰好凑满是运气不是保证）。口径：残差不修正，前端图表允许合计 9999 或 10001 bp——比「服务端偷偷给最大行加 1」诚实。

步骤 1 · repo 三条聚合

片段 · report_repo.go 追加（前置：上面的 base；三条查询只差 Select 与 Group）func (r *ReportRepo) TrendByMonth(ctx context.Context, famID int64, start, end time.Time, v Viewer) ([]TrendRow, error) {
    var rows []TrendRow
    err := r.base(r.db.WithContext(ctx), famID, start, end, v).
        Select(`COALESCE(SUM(amount_cents) FILTER (WHERE direction = 'income'), 0)  AS income_cents,
                COALESCE(SUM(amount_cents) FILTER (WHERE direction = 'expense'), 0) AS expense_cents`).
        Scan(&rows).Error
    return rows, err // 单桶；net_cents = income - expense 在 service 算，五档分桶明天来
}

func (r *ReportRepo) ByCategory(ctx context.Context, famID int64, start, end time.Time, v Viewer) ([]GroupRow, error) {
    var rows []GroupRow
    err := r.base(r.db.WithContext(ctx), famID, start, end, v).
        Select("category_id AS group_id, COALESCE(SUM(amount_cents), 0) AS amount_cents").
        Where("direction = 'expense'").
        Group("category_id").
        Scan(&rows).Error
    return rows, err
}

// ByMember 同形：Select("author_member_id AS group_id, …")，Group("author_member_id")，收支都算（成员维度看的是经手金额）。

FILTER (WHERE …) 是 Postgres 的标准聚合过滤语法，一条 SQL 同时出收入与支出两列，比 CASE WHEN 干净，也比跑两遍查询省一次往返。S5 并发聚合是「多个查询并行」，今天这是「一个查询多列」——先让单条 SQL 尽量能干，再谈并行。

步骤 2 · service 分发与后处理

片段 · server/internal/finance/service/report_service.go（前置：period.Parse 与家庭时区接口同 D20）func (s *ReportService) Summary(ctx context.Context, famID int64, view, periodKey string, v Viewer) (any, error) {
    p, err := period.Parse(periodKey)
    if err != nil { return nil, err } // ErrBadPeriod → 1007
    start, end, err := s.bounds(ctx, famID, p)
    if err != nil { return nil, err }
    switch view {
    case "trend":    return s.trend(ctx, famID, p, start, end, v)
    case "category": return s.category(ctx, famID, p, start, end, v) // 内含 rollup 归并 + share_bp
    case "member":   return s.member(ctx, famID, p, start, end, v)   // 内含 platform 目录接口拼名
    default:          return nil, response.ErrBadRequest          // 白名单外 → 1004，不回落
    }
}
