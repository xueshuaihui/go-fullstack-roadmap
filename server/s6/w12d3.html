余额计算口径：由流水推导，不维护余额列

「账户余额」有两种做法：维护列（账户表存 balance_cents，每笔流水同事务加减）或推导（余额 = 初始余额 + 流水聚合，现算）。今天把取舍讲透，然后选定推导式并落一个 BalanceOf 聚合查询。这个决定影响后面每一天：软删、恢复、改金额、归档校验，全都建立在「流水是唯一事实源」上。

今日目标

知识讲义

1. 两种口径的取舍

维护列（balance_cents 存账户表）推导式（本站选定）
读O(1)，一次行读一次 SUM 聚合，靠索引
写每笔流水都要同事务更新余额；编辑/软删/恢复都要写补偿逻辑只写流水本身，余额自动跟上
一致性两个事实源（流水 + 余额列），任何一条路径漏更新就对不上账，还要写对账任务单一事实源：余额永远等于流水的函数
适用规模海量流水（千万行级）、高频读余额中小数据量，聚合走索引毫秒级

本站是家庭记账：单家庭流水量级是「每年几千行」，(family_id, account_id, occurred_at) 索引下 SUM 是毫秒级；而软删（D4）、乐观锁编辑（D5）、恢复重算、归档校验（账户日）每一条都会改历史流水——维护列意味着每条路径都要记得补一刀余额，漏一刀就是错账。读便宜一点点，写复杂度翻倍，不值得。选定：余额 = 初始余额 + 未删除流水的聚合，现算。

推导式不是「没有代价」：每次读账户都要聚合一次。若日后数据量真上来，再加物化缓存（汇总表/缓存层）——那属于优化，事实源仍然是流水。教学期先把正确性钉死。

2. 聚合公式

片段 · 余额口径（以账户 a 为例，全部只算 deleted_at IS NULL 的行）balance(a) = a.initial_balance_cents
           + SUM(income   且 account_id = a)            -- 收入进本账户
           - SUM(expense  且 account_id = a)            -- 支出出本账户
           + SUM(transfer 且 to_account_id = a)         -- 转入加
           - SUM(transfer 且 account_id = a)            -- 转出减

一条 SQL 就能写完（FILTER 是 Postgres 的条件聚合语法，比 CASE WHEN 好读）：

片段 · BalanceOf 的 SQLSELECT
  COALESCE(SUM(amount_cents) FILTER (WHERE type = 'income'   AND account_id     = $1), 0)
- COALESCE(SUM(amount_cents) FILTER (WHERE type = 'expense'  AND account_id     = $1), 0)
+ COALESCE(SUM(amount_cents) FILTER (WHERE type = 'transfer' AND to_account_id  = $1), 0)
- COALESCE(SUM(amount_cents) FILTER (WHERE type = 'transfer' AND account_id     = $1), 0)
FROM finance_transaction
WHERE family_id = $2 AND deleted_at IS NULL
  AND (account_id = $1 OR to_account_id = $1);

再加账户自己的 initial_balance_cents（建户时录入的期初余额）就是最终余额。注意 WHERE 里转账两端都要命中：只按 account_id = $1 过滤会把「转入本账户」的钱漏掉。

3. 推导式与软删/编辑的化学反应

这是选推导式的真正回报，提前看一眼后两天会发生什么：

  • 软删一笔流水（明天）：只是给它盖 deleted_at，聚合的 WHERE 自动把它排除——余额自动回退，零补偿代码。
  • 从回收站恢复（明天）：清掉 deleted_at，该行重新参与聚合，余额自动回来。
  • 编辑金额（D5）：改流水行本身即可，不存在「忘了同步余额列」这种 bug 类别。
  • 归档账户前查余额（账户日）：直接调 BalanceOf，非 0 拒绝——判据与展示同一口径，不会互相打架。

今日增量（在学习仓里落盘）

今天属增量类型 ⑤+③：把账户余额从「没有/假的」换成真聚合查询 + 测试。只加 repo 方法与 service 封装，handler 到账户日再接。

步骤 1 · repo 聚合方法

片段 · server/internal/finance/repo/account.go（前置：repo 已持有 *gorm.DB，S3 起的老结构）// BalanceOf 返回账户当前余额（分）。推导式：初始余额 + 未删除流水聚合。
func (r *AccountRepo) BalanceOf(ctx context.Context, familyID, accountID int64) (int64, error) {
    var initial int64
    if err := r.db.WithContext(ctx).
        Table("finance_account").
        Where("family_id = ? AND id = ? AND deleted_at IS NULL", familyID, accountID).
        Pluck("initial_balance_cents", &initial).Error; err != nil {
        return 0, err
    }
    var flow int64
    sql := `SELECT
        COALESCE(SUM(amount_cents) FILTER (WHERE type='income'   AND account_id=?1),0)
      - COALESCE(SUM(amount_cents) FILTER (WHERE type='expense'  AND account_id=?1),0)
      + COALESCE(SUM(amount_cents) FILTER (WHERE type='transfer' AND to_account_id=?1),0)
      - COALESCE(SUM(amount_cents) FILTER (WHERE type='transfer' AND account_id=?1),0)
      FROM finance_transaction
      WHERE family_id=?2 AND deleted_at IS NULL AND (account_id=?1 OR to_account_id=?1)`
    if err := r.db.WithContext(ctx).Raw(sql, accountID, familyID).Scan(&flow).Error; err != nil {
        return 0, err
    }
    return initial + flow, nil
}

Raw 里只许出现占位符，familyID/accountID 全部参数化传入——家庭隔离条件与防注入是同一件事的两面。另外这条查询在 finance schema 内闭环，没有 join 任何 homeos 表，跨模块纪律无恙。

步骤 2 · 测试：五笔流水把公式钉死

完整 · server/internal/finance/repo/account_balance_test.go（测试库脚手架沿用 S3/S4）package repo

import "testing"

func TestBalanceOf(t *testing.T) {
    db := newTestDB(t) // 前置：S3 起的测试库脚手架，迁移已跑
    r := NewAccountRepo(db)
    seedAccount(t, db, 1 /*family*/, 1 /*acct*/, 10000 /*initial_cents*/)
    seedAccount(t, db, 1, 2, 0)
    // 收入 5000 进账户1；支出 3000 出账户1；转账 2000：账户1 → 账户2；
    // 再插一笔已软删的支出 9999（不应计入）
    seedTx(t, db, "income", 5000, 1, 0, false)
    seedTx(t, db, "expense", 3000, 1, 0, false)
    seedTx(t, db, "transfer", 2000, 1, 2, false)
    seedTx(t, db, "expense", 9999, 1, 0, true)

    got1, err := r.BalanceOf(t.Context(), 1, 1)
    if err != nil { t.Fatal(err) }
    if got1 != 10000+5000-3000-2000 { t.Fatalf("账户1余额 = %d, want 10000", got1) }

    got2, _ := r.BalanceOf(t.Context(), 1, 2)
    if got2 != 2000 { t.Fatalf("账户2余额 = %d, want 2000（转入也要命中）", got2) }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
聚合忘了排除软删行删了一笔支出，余额纹丝不动WHERE 必带 deleted_at IS NULL，与 family_id = ? 一样是每条查询的固定件
只按 account_id 过滤转入的钱永远不进余额条件是 account_id = ? OR to_account_id = ?
SUM 出 NULL账户一笔流水都没有时 Scan 出怪值COALESCE(..., 0) 包好每个 SUM
把初始余额忘进公式建户时的期初钱凭空消失余额 = initial_balance_cents + 流水聚合，两项缺一不可
偷偷加回余额列「先顶着」两个事实源开始漂移，对不上账口径已定：推导式。要提速日后加缓存层，事实源不变
金额字段用了 float64聚合结果出现 ...9999 尾差全链路 int64 分；显示层才除以 100

今日名词卡

术语一句话解释
单一事实源一个事实只存一处；余额是流水的函数，不是并列的第二份数据
推导式余额balance = 初始余额 + 未删除流水聚合，读时现算
维护列把结果存成列、写时同步更新——读快写险，本站不用
SUM ... FILTER (WHERE ...)Postgres 条件聚合：只对命中行求和，比 CASE WHEN 可读
COALESCENULL 兜底成 0；空账户的 SUM 是 NULL 不是 0
读放大推导式的代价：每次读余额都要聚合，靠索引压到毫秒级
补偿逻辑维护列口径下「改了流水还得记得改余额」的那类代码——推导式把它整个消灭
initial_balance_cents建户时录入的期初余额，聚合公式的常数项
物化缓存日后量级上来才考虑的加速层；事实源仍是流水

卡壳时查什么

  • Raw SQL 与 GORM 混用不熟：回 S3 换 DB 的那几天，repo 层的写法一脉相承。
  • 测试库脚手架怎么搭：回 S3 建迁移与测试库的那一课；seed 小函数照今天的形状补。
  • 为什么每条查询都带 family_id：S4 家庭隔离那一段，scope 条件是纪律不是优化。
  • FILTER 语法没见过：它是标准 SQL:2003 的条件聚合，Postgres 文档 Aggregate Expressions（可选）。
