CSV 导出：行数必须等于查询行数

某个真实记账产品出过这样的事故：列表页按「3 月 + 餐饮 + 支付宝」筛出 42 行，用户点导出，拿到的 CSV 却是全量流水——导出接口的后端根本没读筛选参数。用户在表格软件里对了一晚上账，越对越差，最后发现是服务端两处口径不一致。今天写 GET /api/finance/reports/export，把本站的硬判据立起来：同筛选条件下，导出行数 = 查询行数，字段列齐全，筛选参数全部生效。做到它的唯一正路：导出与列表共用同一份查询构造器。

今日目标

知识讲义

1. 事故的根源：两份查询逻辑

导出接口最常见的烂法是复制粘贴：列表查询一段 SQL，导出又手写一段「差不多」的 SQL。时间一长，列表加了筛选参数、加了可见性谓词，导出那份没人记得同步——两边悄悄分叉，直到用户拿着 CSV 来对账。根治手段只有一个：筛选条件的构造只有一份。D6 的 TxFilter + 昨天的 period 解析 + D13 的可见性谓词，全部长在同一个查询构造器上；列表与导出是它的两个出口：

列表（GET /transactions）导出（GET /reports/export）
筛选参数同一套、同一份解析代码：type / account_id / category_id / period / deleted
行数游标分页，每页 ≤ limit不分页，全量（同一 WHERE 的所有行）
排序同一个 ORDER BY，CSV 行序 = 列表页序
输出JSON 信封三键text/csv 文件流（失败仍是 JSON 信封）

于是「导出行数 = 查询行数」不再靠自觉，而是结构上必然成立：同一个 WHERE，数出来的行当然一样多。测试要做的就是把这个必然性钉住。

2. 「全量导出」与「不接受无上限返回」不矛盾

D6 说过列表禁止无上限返回——那是对分页 JSON 接口的约束（客户端一次消化不了 10 万行 JSON）。导出是另一物种：流式写文件，服务端逐行生成逐行写出去，内存里永远只有当前一行；客户端拿到的是文件不是响应体。但流式也要有闸：导出设一个硬上限（如 10 万行，超了 400 + 1004 并提示缩小时间窗），防止一个 period=2020 之外的「无 period 全量」把磁盘和连接拖死。教学期数据量小，闸门只是立个规矩。

3. CSV 的四个细节

  • 表头固定且齐全：id、时间、类型、金额（分）、账户、分类、备注、作者、私密标记……列集合是契约的一部分，「字段列齐全」是判据原文。
  • 金额导出为分（整数）：CSV 里也写 amount_cents 原值，不在服务端除以 100——一旦除，就有人用浮点接，禁浮点纪律从库到文件一以贯之。表头写明 amount_cents，用的人自然知道单位。
  • BOM：给表格软件打开中文不乱码，文件开头写 UTF-8 BOM（\xEF\xBB\xBF）。
  • 响应头：Content-Type: text/csv; charset=utf-8 + Content-Disposition: attachment; filename="transactions-….csv"。成功时不走 JSON 信封（文件流是全站唯一例外）；失败时仍是信封——参数错 1007/1004、越权 1003 照旧。

步骤 1 · 路由与 handler

func (h *ExportHandler) ExportCSV(c *gin.Context) {
    q, err := parseListQuery(c)          // ← 与 GET /transactions 同一个解析函数（含 period → 1007）
    if err != nil { response.FailErr(c, err); return }
    q.Limit = exportHardCap              // 全量口径：不分页，只留硬上限闸

    rows, err := h.svc.ListAll(c.Request.Context(), actorFrom(c), q) // 同一查询构造器
    if err != nil { response.FailErr(c, err); return }

    c.Header("Content-Type", "text/csv; charset=utf-8")
    c.Header("Content-Disposition", `attachment; filename="transactions.csv"`)
    _, _ = c.Writer.Write([]byte{0xEF, 0xBB, 0xBF}) // UTF-8 BOM
    w := csv.NewWriter(c.Writer)
    _ = w.Write(csvHeader)               // 固定表头，列集合即契约
    for _, r := range rows {
        _ = w.Write(toCSVRow(r))         // amount_cents 原值整数，不除 100
    }
    w.Flush()                            // 忘 Flush = 文件截尾，见坑表
}

步骤 2 · 行数一致性测试（本阶段判据本体）

import (
    "encoding/csv"
    "net/http/httptest"
    "strings"
    "testing"
)

func TestExportRowsEqualQueryRows(t *testing.T) {
    r, tokens := newTestRouter(t) // 前置：S4 登录态脚手架；家庭1 里 seed 跨两个月份、两个分类、含私密行的流水
    filter := "period=2026-03&category_id=7"

    // ① 查询侧：翻页数清同筛选条件下的总行数
    total, cursor := 0, ""
    for {
        u := "/api/finance/transactions?limit=5&" + filter
        if cursor != "" { u += "&cursor=" + cursor }
        body := doGet(t, r, tokens.MemberA, u)
        total += len(body.Data.List)
        if !body.Data.HasMore { break }
        cursor = body.Data.NextCursor
    }

    // ② 导出侧：同一筛选参数打导出接口，数 CSV 数据行
    w := httptest.NewRecorder()
    req := newAuthRequest(t, "GET", "/api/finance/reports/export?"+filter, tokens.MemberA)
    r.ServeHTTP(w, req)
    if w.Code != 200 || !strings.Contains(w.Header().Get("Content-Type"), "text/csv") {
        t.Fatalf("导出响应不对: %d %s", w.Code, w.Header().Get("Content-Type"))
    }
    rows, err := csv.NewReader(strings.NewReader(strings.TrimPrefix(w.Body.String(), "\ufeff"))).ReadAll()
    if err != nil { t.Fatal(err) }
    dataRows := len(rows) - 1 // 去表头

    // ③ 判据：两个数字必须相等；列数必须等于契约列数
    if dataRows != total { t.Fatalf("导出 %d 行 ≠ 查询 %d 行", dataRows, total) }
    if len(rows[0]) != len(csvHeader) { t.Fatalf("表头列数 %d ≠ 契约 %d", len(rows[0]), len(csvHeader)) }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
导出另写一份 SQL两边筛选悄悄分叉，行数对不上共用查询构造器，「行数相等」结构上必然
后端不读筛选参数用户筛 42 行、导出全量——今天的事故主角parseListQuery 两处同一函数；测试直接断言相等
忘 w.Flush()CSV 尾部截掉几行，且无报错csv.Writer 有缓冲，写完必 Flush（并检查 w.Error()）
服务端把分转成元再导出浮点、四舍五入、精度事故全套上门导出 amount_cents 原值整数，单位写进表头
无 BOM表格软件打开中文备注全乱码文件头写 UTF-8 BOM 三字节
失败也返回 CSV 头错误信息被当文件下载，用户打开看到一段 JSON 文本文件先跑完参数校验再写响应头；失败走 JSON 信封
导出不设上限全库导出拖死连接与磁盘硬上限闸 + 超限 1004 提示缩小时间窗

今日名词卡

术语一句话解释
行数一致性判据同筛选条件下导出行数 = 查询行数；S6 的硬判据，源自真实事故
查询构造器复用筛选/排序/可见性只有一份实现，列表与导出是两个出口
流式写出逐行生成逐行写响应，内存占用与总行数无关
csv.Writer.Flush把缓冲区推进底层 Writer；忘写 = 静默截尾
UTF-8 BOM文件头三字节 EF BB BF，让表格软件认对编码
Content-Dispositionattachment; filename=…：告诉客户端这是下载文件
文件流例外成功时不走 JSON 信封的唯一场景；失败仍是信封
导出硬上限流式也要有闸：超行数上限 400 + 1004，引导缩小时间窗
抽公共函数的时机第二个消费者出现那一刻——今天的 parseListQuery 就是例子
