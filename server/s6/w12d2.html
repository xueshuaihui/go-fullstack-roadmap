收入、支出、转账：to_account_id 与 4001

昨天 POST /api/finance/transactions 通了幂等，但 type=transfer 还是个空壳——收进来什么就存什么。今天补全三种类型的语义校验：收入/支出只碰一个账户；转账必须同时给 account_id 与 to_account_id，且两端不能是同一个账户。所有金额语义错误都走同一个出口：400 + 4001。

今日目标

知识讲义

1. 三种类型的字段矩阵

字段income 收入expense 支出transfer 转账
amount_cents三者都必须 > 0，否则 4001
account_id收款账户，必填付款账户，必填转出账户，必填
to_account_id必须为空必须为空必填，且 ≠ account_id
category_id必填（收入分类）必填（支出分类）可空（转账通常无分类）

「两端同账户」= 400 + 4001，不是 1004。它不是格式问题，是金额语义问题：自己转给自己在账目上是无意义操作，和「金额 ≤0」「超出可用余额」同族，错误码表里它们共用 4001。分类记错码，前端就没法给出「请先选择另一个账户」这类精准提示。

2. 转账为什么单独一种类型

把转账记成「一笔支出 + 一笔收入」是新手最常见的偷懒，代价惨重：两条流水各有一半真相，删一条留一条就凭空造钱或烧钱；报表里家庭总收入/总支出被内部挪动灌水。正确口径：转账是一条流水，同时挂两个账户，对家庭总资产的净影响为 0。明天算余额口径时你会看到，转账在两个账户上一负一正、在全家维度直接抵消。

还要防一个方向性错误：account_id 永远是转出方，to_account_id 永远是转入方。全站只有这一个约定，写反了余额就反了。

3. 校验放哪一层

字段矩阵校验放 service 层，不放 handler：binding tag 只能管「格式」（缺字段、类型错 → 1004），管不了「组合语义」（transfer 必须两端不同 → 4001）。分层口径从 S2 三层起没变过——handler 只做翻译（HTTP ↔ Go），业务规则全在 service，repo 只管存取。这样明天单测 service 不需要起 HTTP。

片段 · 组合语义校验的形状（伪码）validate(in):
    in.AmountCents <= 0                          → ErrAmountInvalid (4001)
    in.Type == transfer:
        in.ToAccountID == nil                    → ErrAmountInvalid (4001)
        *in.ToAccountID == in.AccountID          → ErrAmountInvalid (4001)
    in.Type != transfer && in.ToAccountID != nil → ErrAmountInvalid (4001)
    in.Type != transfer && in.CategoryID == nil  → ErrAmountInvalid? 不——这是参数缺失，走 1004

最后一条的分界值得停下来想：「钱」的语义错 → 4001；「请求体完整性」错 → 1004。收支缺 category_id 属于后者。错误码不是随手挑的，是每个码背后有一类可复用提示文案的分族。

步骤 1 · service 层补 validate

片段 · server/internal/finance/service/transaction.go（插在 Create 的「首次」分支里、写库之前）func validateCreate(in *model.CreateTxInput) error {
    if in.AmountCents <= 0 {
        return response.ErrAmountInvalid // 400 + 4001
    }
    switch in.Type {
    case model.TxTransfer:
        if in.ToAccountID == nil || *in.ToAccountID == in.AccountID {
            return response.ErrAmountInvalid // 缺转入账户 / 两端同账户，同族 4001
        }
    case model.TxIncome, model.TxExpense:
        if in.ToAccountID != nil {
            return response.ErrAmountInvalid
        }
        if in.CategoryID == nil {
            return response.ErrInvalidParam // 400 + 1004：请求体不完整
        }
    default:
        return response.ErrInvalidParam
    }
    return nil
}

步骤 2 · 表驱动测试

完整 · server/internal/finance/service/transaction_type_test.gopackage service

import (
    "errors"
    "testing"

    "homecube/internal/finance/model"
    "homecube/pkg/response"
)

func TestValidateCreate(t *testing.T) {
    two := int64(2)
    cat := int64(7)
    tests := []struct {
        name string
        in   model.CreateTxInput
        want error // nil = 应通过
    }{
        {"支出合法", model.CreateTxInput{Type: model.TxExpense, AmountCents: 100, AccountID: 1, CategoryID: &cat}, nil},
        {"收入合法", model.CreateTxInput{Type: model.TxIncome, AmountCents: 100, AccountID: 1, CategoryID: &cat}, nil},
        {"转账合法", model.CreateTxInput{Type: model.TxTransfer, AmountCents: 100, AccountID: 1, ToAccountID: &two}, nil},
        {"金额为0", model.CreateTxInput{Type: model.TxExpense, AmountCents: 0, AccountID: 1, CategoryID: &cat}, response.ErrAmountInvalid},
        {"两端同账户", model.CreateTxInput{Type: model.TxTransfer, AmountCents: 100, AccountID: 1, ToAccountID: &[]int64{1}[0]}, response.ErrAmountInvalid},
        {"转账缺转入", model.CreateTxInput{Type: model.TxTransfer, AmountCents: 100, AccountID: 1}, response.ErrAmountInvalid},
        {"支出缺分类", model.CreateTxInput{Type: model.TxExpense, AmountCents: 100, AccountID: 1}, response.ErrInvalidParam},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            err := validateCreate(&tt.in)
            if tt.want == nil && err != nil { t.Fatalf("应通过, got %v", err) }
            if tt.want != nil && !errors.Is(err, tt.want) { t.Fatalf("want %v, got %v", tt.want, err) }
        })
    }
}

&[]int64{1}[0] 这个写法丑得醒目——取一个字面量的地址。Go 不允许 &1，测试里造 *int64 就得这么绕一下（或者声明个变量，上面 two 就是正经写法）。

常见坑（新手 100% 会踩）

坑现象正确姿势
转账拆成一收一支两条流水删一半造出/烧掉一笔钱；报表被内部挪动灌水转账是一条流水挂两个账户，家庭总资产净变化为 0
支出存负数金额SUM 时正负抵消口径全靠脑补amount_cents 恒正，方向看 type
两端同账户返回 1004金额语义错混进参数错，前端提示不准4001 专管「钱」的语义：≤0 / 超余额 / 两端同账户
校验写进 handlerservice 单测测不到规则，换个入口（明天的导入、后天的周期入账）规则就丢了组合语义全在 service；handler 只管 HTTP 翻译
to_account_id 用 0 表示「没有」0 与「未填」分不清，外键校验全是洞可空外键用 *int64 + NULL，不用零值魔法
income/expense 也收 to_account_id存进去一个永远没人读的字段值非转账带了 to_account_id 直接 4001，口径收紧

术语一句话解释
