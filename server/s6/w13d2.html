票据附件上传：三条限额与 4002

记账不看小票，等于没记。今天给流水配票据附件：POST 上传、GET 读取，两条接口。规矩只有三条，全部走同一个错误码 400 + 4002：每笔流水 ≤3 张、单张 ≤5MB、格式仅 jpg / png / webp。文件落盘在 uploads/{family_id}/ 下——按家庭分目录，是隔离纪律在文件系统上的延伸。

今日目标

知识讲义

1. 三条限额，一个错误码

限额校验方式违反
每笔 ≤3 张上传前 COUNT 该流水已有附件行（带 family_id 与软删条件）400 + 4002
单张 ≤5MBhttp.MaxBytesReader 把请求体上限设成略大于 5MB，超限在读之前就断400 + 4002
jpg / png / webp扩展名白名单 + Content-Type 双查；更稳的一档是读文件头魔数（见坑表）400 + 4002

为什么三条共用 4002 而不是拆三个码：对客户端来说它们是同一类交互（「你传的文件不合格」），提示文案同一族；错误码表按用户可采取的动作分族，不按服务端实现细节分族。

2. 大小限制要在「读进内存之前」生效

新手写法是 c.FormFile("file") 拿到文件后看 f.Size——问题是这时 5MB（甚至 500MB）已经流过你的进程了。先给请求体戴上镣铐再解析：

片段 · MaxBytesReader 的位置（在解析 multipart 之前）c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, maxUploadBytes+oneMB)
// 超限后 ParseMultipartForm 直接报错，进程内存峰值被钉死

留 1MB 余量是因为 multipart 报文里除了文件还有边界串与表单字段。落盘用 c.SaveUploadedFile（内部是流式拷贝，不整文件进内存）。

3. 落盘路径与文件名：两条安全纪律

  • 目录按家庭分：$UPLOAD_DIR/{family_id}/{tx_id}/{随机名}.{ext}。UPLOAD_DIR 走环境变量（S6 起加入 config 清单），目录树与查询隔离同构——就算日后目录被静态挂载，一个家庭的路径也摸不到另一个家庭的文件。
  • 文件名必须服务端重新生成：客户端传来的 filename 是不可信输入，可能带 ../../ 路径穿越、可能带可执行后缀、可能撞名覆盖。一律丢弃，用 crypto/rand 生成随机名 + 白名单里的扩展名。用户看到的「原名」存附件表的 file_name 列，只做展示，永不参与路径拼接。

4. 附件表与流水的生命周期

附件行自己也有全套通用列（family_id、软删双戳、version）。删除一笔流水附件 = 软删附件行；流水本体被软删时附件不动——恢复流水时票据原样都在（D4 说过的口径）。文件本体在回收站窗口内不清理，教学期不做定时清扫，只在文档里留一句：真清理属运维策略。

步骤 2 · 上传 handler

片段 · server/internal/finance/handler/attachment.go（前置：service 已有 Attach/ListOf 两方法签名）const (
    maxAttachmentsPerTx = 3
    maxAttachmentBytes  = 5 << 20 // 5MB
)

var allowedExt = map[string]string{
    ".jpg": "image/jpeg", ".jpeg": "image/jpeg",
    ".png": "image/png", ".webp": "image/webp",
}

func (h *AttachHandler) Upload(c *gin.Context) {
    txID, err := strconv.ParseInt(c.Param("id"), 10, 64)
    if err != nil { response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "id 不合法"); return }

    c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, maxAttachmentBytes+1<<20)
    fh, err := c.FormFile("file")
    if err != nil { response.Fail(c, http.StatusBadRequest, response.CodeAttachmentLimit, "附件超限或不合法"); return } // 4002

    ext := strings.ToLower(filepath.Ext(fh.Filename))
    mime, ok := allowedExt[ext]
    if !ok || fh.Size > maxAttachmentBytes {
        response.Fail(c, http.StatusBadRequest, response.CodeAttachmentLimit, "附件超限或不合法"); return
    }
    att, err := h.svc.Attach(c.Request.Context(), actorFrom(c), txID, fh, mime) // 张数校验+落盘+写行在 service 内
    if err != nil { response.FailErr(c, err); return } // 超张数 → ErrAttachmentLimit → 4002；流水不存在 → 1001
    response.Created(c, att)
}
片段 · service.Attach 的落盘核心（随机名 + 家庭目录）rel := filepath.Join(strconv.FormatInt(a.FamilyID, 10), strconv.FormatInt(txID, 10), randomName()+ext)
abs := filepath.Join(cfg.UploadDir, rel)
os.MkdirAll(filepath.Dir(abs), 0o750)
c.SaveUploadedFile(fh, abs)   // 由 handler 传入；失败要回滚附件行——先写盘后写库，库失败删盘

顺序纪律：先落盘、后写附件行；写行失败就把刚落盘的文件删掉。反过来（先写行后落盘）失败时会留下一行指向不存在文件的「幽灵附件」，比孤儿文件更难查。

常见坑（新手 100% 会踩）

坑现象正确姿势
先解析再看大小超大文件已经吃掉内存/带宽才被拒MaxBytesReader 在解析前戴镣铐
信任客户端 filename../../etc/passwd 类路径穿越；同名覆盖随机名落盘，原名只进展示列
只看扩展名不看内容把 exe 改名 .jpg 传上来教学期扩展名 + Content-Type 双查；想更稳读文件头魔数（前 12 字节）
张数校验与写入之间有并发缝双击同时传，两请求都数到 2，都写入 → 4 张教学期可接受；要封死就把 COUNT+INSERT 收进一个可串行化事务（S5 的隔离级课程）
附件目录进了 git仓库膨胀、票据泄漏/uploads/ 在 S1·D1 的 .gitignore 里就有，今天验证它还生效
先写附件行后落盘落盘失败留下幽灵附件行先盘后库，库失败删盘
UPLOAD_DIR 写死绝对路径换机器/容器即崩环境变量进 config（S6 起清单含 UPLOAD_DIR），带默认值 ./uploads

今日名词卡

术语一句话解释
multipart/form-data文件上传的报文格式：边界串分隔多个部分，Gin 用 FormFile 取
http.MaxBytesReader给请求体设字节上限，超了在读的阶段就报错——限额的第一道闸
4002附件超限（>3 张 / 单张 >5MB / 格式非 jpg·png·webp），400
路径穿越用 ../ 把写入位置逃出目标目录的攻击；靠「服务端生成文件名」根除
魔数（magic number）文件格式的头部特征字节，比扩展名与 Content-Type 都难伪造
stored_path vs file_name真实落盘相对路径（参与 I/O）与用户侧原名（仅展示），永不混用
幽灵附件库里有行、盘上无文件的孤儿记录；「先盘后库」的顺序防它
UPLOAD_DIR附件根目录环境变量，S6 起进 config 清单
