私密流水 is_private：行级可见性过滤

家庭共账，但总有一两笔不想让全家看见的流水——给父母的红包、个人体检费。is_private 列从 S3 建表起就在 finance_transaction 里躺着，今天让它活过来：命中 is_private 的行，仅作者本人与家庭 owner 可读。这是全站权限体系里唯一一个「行级」例外——角色矩阵管到「能不能进这个面」，行级可见性管到「这一行给不给你看」，两层必须分开实现、互不混淆。

今日目标

知识讲义

1. 可见性规则表（今天的唯一需求）

读者 \ 行非私密行私密行（作者是 M）
作者 M 本人可读可读
家庭 owner可读可读
其他 member / ward可读不可读 → 404 + 1001（与不存在同形）
guest（限时只读）可读不可读 → 404 + 1001

写口径顺带钉死：非私密流水家庭内共写（member 可改可删，S4 的角色矩阵早已放行）；私密流水的改/删仅作者与 owner，其他成员动手 → 403 + 1003（「非作者改他人数据」就是错误码表里 1003 的登记场景之一）。读藏存在性、写明确拒绝——读写不同形，是全站一贯口径。

2. 谓词进 SQL，而不是进 handler 的 if

错误做法：查出来再在 Go 里逐行过滤。两个致命伤：分页被过滤打穿（一页 20 行滤剩 13 行，游标推进全乱）、COUNT/聚合与列表口径不一致。正确做法：谓词拼进 WHERE，让数据库在分页与聚合之前就把不可见行排除——D6 的游标分页、D3 的余额聚合、后面的导出，天然拿到同一份「可读行集合」。

片段 · 可见性谓词（判定逻辑只有一份，住在 platform/authz）// authz.TxReadPredicate 返回一段 SQL 与参数：调用方拼进自己的 WHERE。
func TxReadPredicate(memberID int64, role model.Role) (string, []any) {
    if role == model.RoleOwner {
        return "1 = 1", nil            // owner 全可见，谓词恒真
    }
    return "(is_private = false OR member_id = ?)", []any{memberID}
}

两条纪律：① 判定只有一份实现，住在 internal/platform/authz——finance 的 handler/service 里不许出现 if role == owner 的自写分支（角色判定散落 = 改一处漏三处）。② finance 拿到的是「谓词字符串 + 参数」，不 import authz 的内部规则细节；跨模块调用点收在 platform 接口后面，老规矩。

3. 接入点清单：哪些查询要吃这个谓词

  • 列表（D6 的 List，含回收站视角）：WHERE 追加谓词——别人的私密行连回收站都不给你看。
  • 单条（D7 的 GetByID）：谓词进 WHERE，查不到 → 1001，与不存在同形。
  • 余额聚合（D3 的 BalanceOf）：不吃谓词。私密行的钱是真实的钱，账户余额与归档判据必须含它——可见性管「看见哪些行」，不管「钱算不算数」。这一条今天专门写进测试，防止顺手把谓词也塞进聚合。
  • 附件读取、导出：附件跟随主流水的可见性（今天顺手接）；导出在本阶段后半接，届时同一谓词。

今日增量（在学习仓里落盘）

今天属增量类型 ⑤+③：把列表/单条/附件查询从「不过滤」换成「按谓词过滤」+ 可见性矩阵测试。

步骤 2 · 可见性矩阵测试

完整 · server/internal/finance/service/tx_visibility_test.gopackage service

import (
    "errors"
    "testing"

    "homecube/pkg/response"
)

func TestPrivateTxVisibilityMatrix(t *testing.T) {
    svc := newTestTxService(t)
    ctx := t.Context()
    author := Actor{FamilyID: 1, MemberID: 10, Role: memberRole()}
    owner  := Actor{FamilyID: 1, MemberID: 11, Role: ownerRole()}
    peer   := Actor{FamilyID: 1, MemberID: 12, Role: memberRole()}

    priv := mustCreatePrivateTx(t, svc, author)   // is_private=true，作者 author
    pub  := mustCreateTx(t, svc, author)          // 非私密

    // 单条：作者/owner 可读，peer 与「不存在」同形
    if _, err := svc.Get(ctx, author, priv.ID); err != nil { t.Fatalf("作者应可读: %v", err) }
    if _, err := svc.Get(ctx, owner, priv.ID); err != nil { t.Fatalf("owner 应可读: %v", err) }
    if _, err := svc.Get(ctx, peer, priv.ID); !errors.Is(err, response.ErrNotFound) {
        t.Fatalf("peer 读私密行应与不存在同形 1001: %v", err)
    }
    if _, err := svc.Get(ctx, peer, pub.ID); err != nil { t.Fatalf("非私密行家庭内可读: %v", err) }

    // 列表：peer 的列表里没有私密行，作者与 owner 都有
    peerPage, _ := svc.List(ctx, peer, ListQuery{Limit: 10})
    if len(peerPage.Items) != 1 { t.Fatalf("peer 应只见 1 行非私密, got %d", len(peerPage.Items)) }
    ownerPage, _ := svc.List(ctx, owner, ListQuery{Limit: 10})
    if len(ownerPage.Items) != 2 { t.Fatalf("owner 应见 2 行, got %d", len(ownerPage.Items)) }

    // 余额：私密行的钱照常计入（谓词不进聚合）
    bal, _ := svc.BalanceOfAccount(ctx, author, priv.AccountID)
    if bal == 0 { t.Fatal("私密支出必须计入余额，可见性不管钱的账") }

    // 写：peer 改作者私密行 → 403 + 1003
    _, err := svc.Update(ctx, peer, priv.ID, &UpdateTxInput{Version: 1, Note: "偷改"})
    if !errors.Is(err, response.ErrForbidden) { t.Fatalf("非作者改私密行应 1003: %v", err) }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
查出来再在 Go 里过滤一页 20 行滤剩 13 行，游标推进错乱谓词进 WHERE，分页与聚合之前生效
handler 里写 if role == owner判定散落，改规则漏改判定只有一份，住 platform/authz
越权读私密行回 403泄露「这行存在且是私密的」读 → 404 + 1001 同形；写才 403 + 1003
余额聚合也吃谓词私密支出从余额消失，归档判据跟着错聚合不看可见性：钱是真的，只是行不给你看
回收站漏接谓词别人的私密删除行在你回收站里裸奔deleted=true 视角同一 WHERE，一个口子都不留
按 user_id 而不是 member_id 判作者多家庭下同一用户在不同家庭身份混淆作者 = 会话家庭里的 member_id，与 claims 口径一致

今日名词卡

术语一句话解释
行级可见性权限判定细到单行：同一接口，不同读者看到不同行集合
is_private流水的私密标记；命中行仅作者与 owner 可读
可见性谓词is_private = false OR member_id = ? OR 我是 owner 的 SQL 片段，拼进 WHERE
判定单一实现规则只写在 platform/authz 一处；业务模块消费谓词，不复制逻辑
读藏写拒越权读 404+1001（藏存在性），越权写 403+1003（明确拒绝）
作者（member_id）会话家庭内的成员身份，不是全局 user——多家庭下同一人有两个 member_id
可见性 ≠ 记账口径私密行的钱照常进余额与统计；藏的是行，不是钱
owner家庭管理员，唯一可转让；行级可见性的第二个例外读方

卡壳时查什么

  • 角色矩阵与 authz 包的结构：回 S4 权限判定收口的那一天——今天给它的规则库加一条行级谓词。
  • claims 里的 memberID 与 role 怎么读：S4 中间件与 context 键口径（c.GetInt64("memberID")、c.MustGet("role").(model.Role)）。
  • 谓词为什么必须进 WHERE 而不是后过滤：S6·D6 的游标分页——分页正确性依赖「数据库看到的行集合」。
  • 越权同形 1001 的论证：S6·D7 的三类 404。
