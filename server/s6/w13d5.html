分类二级树收尾：停用、恢复、排序

分类是全站第一个业务域：S2 拿它走通三层、S3 换真库，六条接口里创建、编辑、查询早就在了。今天把最后三条补齐——停用（PUT /{id}/archive）、恢复（POST /{id}/restore）、排序（PUT /categories/sort）——并钉死一个容易被做错的语义：停用只影响「以后还能不能选」，不影响「以前记的账」：历史流水照常可筛、可统计、可编辑。

今日目标

知识讲义

1. 停用的语义边界：管选择器，不管历史

「不再用『宠物』这个分类了」的正确表达是停用，而不是删除，更不是把历史流水的 category_id 抹掉。三条推论：

  • 历史流水原样保留：分类停用后，去年那 40 笔宠物开销还挂在原分类上，筛选（D6 的 category_id 参数）、报表聚合照常命中——聚合 SQL 按 category_id join，根本不关心分类现在什么状态。
  • 选择器只出未停用项：记新账、编辑旧账时的分类下拉，不再出现「宠物」。编辑一笔历史流水时它仍显示自己原分类（值还在，只是选不了新的）。
  • 恢复即回到选择器：清状态戳，无需动任何流水。

反面做法一：停用时级联把历史流水的分类清空——历史统计瞬间失真。反面做法二：干脆给分类做 DELETE——挂着的流水外键悬空。分类只有停用，没有删除；真要「删除」一个从未用过的分类，先确认无流水（有流水 → 409 + 1010，错误码表里「删除有子级或有流水的分类」就是这一族）。

2. 二级树与两个视图

GET /api/finance/categories 返回两级树（父级 → children），非分页小集合口径 {"list":[…]}，排序即服务端返回顺序（今天排序接口的消费现场）。同一个接口两个视图：

视图参数内容给谁用
管理视图（默认）—全量，含停用项，每项带 archived 标记分类管理页：能看到、能恢复
选择器视图?view=selector仅未停用项记账页、编辑页的分类下拉

停用的状态机与账户归档同款（D10 的模式第三次用）：停用父级时，若它还有未停用的子级 → 409 + 1010——树不允许「父死子活」的悬空态，先停用子级（或把子级挪走）再来。恢复父级不强制连恢复子级：子级各自有状态，选择器过滤时两级都查。

3. 排序：全量重排，一次事务

PUT /api/finance/categories/sort，请求体是同一父级下的完整 id 序列：

片段 · 排序请求体与实现口径{"parent_id": 0, "ordered_ids": [12, 9, 15, 3]}   // parent_id=0 表示一级分类

// 服务端：校验 ordered_ids 与库中该父级的未删子节点集合完全相等（缺一个多一个都 1004）
// 一个事务里按序写 sort_order = 10, 20, 30, 40（留缝，方便日后插队）

为什么要求「全量且集合相等」：拖拽排序的客户端天然持有完整列表，全量重排让服务端无状态、幂等（同一请求发两次结果一样）；增量式「把 3 挪到 12 前面」则要处理相对位置的碎片化，得不偿失。集合不相等说明客户端拿的是过期树——1004 拒掉，让它重拉再排。

今日增量（在学习仓里落盘）

今天属增量类型 ②+③：三条路由真实现 + 树语义测试。archived_at/sort_order 两列 S3 建分类表时就该在（当时按通用列 + 排序一次建对）；翻你的迁移确认，缺了就先补一条 up/down 再开工。

步骤 1 · 停用与恢复

片段 · server/internal/finance/service/category.go（前置：CategoryRepo 已有 GetAlive/CountActiveChildren/UpdateStatus）func (s *CategoryService) Archive(ctx context.Context, a Actor, id int64) error {
    cat, err := s.repo.GetAlive(ctx, a.FamilyID, id)
    switch {
    case err != nil:            return err
    case cat == nil:            return response.ErrNotFound        // 404 + 1001（含越权同形）
    case cat.ArchivedAt != nil: return response.ErrStateNotAllowed // 已停用
    }
    n, err := s.repo.CountActiveChildren(ctx, a.FamilyID, id)
    if err != nil { return err }
    if n > 0 { return response.ErrStateNotAllowed } // 父死子活不允许，先处理子级
    ok, err := s.repo.MarkArchived(ctx, a.FamilyID, id) // WHERE archived_at IS NULL，RowsAffected 判定
    if err != nil { return err }
    if !ok { return response.ErrStateNotAllowed }
    return nil
}
// Restore 对称：未停用 → ErrStateNotAllowed；成功清 archived_at、version+1。

步骤 2 · 排序与树视图

片段 · Sort 的事务骨架func (s *CategoryService) Sort(ctx context.Context, a Actor, parentID int64, orderedIDs []int64) error {
    siblings, err := s.repo.ListChildren(ctx, a.FamilyID, parentID) // 未删子节点全量
    if err != nil { return err }
    if !sameIDSet(siblings, orderedIDs) { return response.ErrInvalidParam } // 集合不等 → 400 + 1004
    return s.db.Transaction(func(tx *gorm.DB) error {
        for i, id := range orderedIDs {
            if err := tx.Model(&model.Category{}).
                Where("id = ? AND family_id = ?", id, a.FamilyID).
                Updates(map[string]any{"sort_order": (i + 1) * 10, "updated_at": gorm.Expr("now()")}).Error; err != nil {
                return err
            }
        }
        return nil
    })
}

Gin 路由里 /categories/sort 与 /categories/:id 同层——静态段 sort 与通配 :id 冲突时 Gin 优先静态段，行为正确，但 PUT /categories/sort 永远不会进 :id 的 handler；反过来若你的框架版本报冲突 panic，把排序路径收进 /categories:sort 之类是不行的——正路是升级 Gin 或把排序挂到 /category-sort。以跑通为准，路径一旦定了就全站一致。

常见坑（新手 100% 会踩）

坑现象正确姿势
停用级联改历史流水历史统计瞬间失真，恢复也救不回原值状态只过滤选择器；流水一个字节不动
给分类做 DELETE流水外键悬空，报表 join 丢行分类只有停用；有流水的分类连删除的念头都 1010 拦死
父级停用不管子级选择器里孤零零挂着一排「父已死」的子分类有未停用子级 → 1010，先处理子级
排序做成增量挪位相对位置碎片化，两次拖拽后顺序不可预测同级全量重排，集合不等 1004 让客户端重拉
sort_order 用 1,2,3 连号日后插队要整段重排步长 10 留缝；真不够再重排一次也不贵
管理视图漏了 archived 标记前端只能靠「在不在选择器里」猜状态管理视图每项显式带 archived
树组装在客户端做各端排序口径漂移服务端返回顺序即最终顺序（排序由服务端返回顺序表达）

今日名词卡

术语一句话解释
停用（archive）分类退出选择器，历史与统计不受影响；与账户归档同一状态机模式
两个视图管理视图全量含 archived 标记；?view=selector 只出未停用项

sort_order 步长10、20、30……留缝便于插队；服务端返回顺序 = 排序权威
二级树父级 → children 两层封顶；预置默认树 family_id 为 NULL（S3 口径），自定义行非空
1010 族新成员父级有活子级停用、恢复未停用项、删除有流水的分类，都是「业务状态不允许」
静态段优先Gin 同层里 /categories/sort 胜过 /categories/:id，排序路由不会被吞

卡壳时查什么

  • 分类域三层结构：回 S2 拿分类走通三层的那一周，今天的 service 直接长在它上面。
  • 预置分类树与 NULL family_id：S3 讲预置数据的那一天——查询是 family_id = ? OR family_id IS NULL。
  • 状态机与 RowsAffected：S6·D4/D10，今天是同一模式在树上的第三次复用。
  • 历史流水筛选为什么不受停用影响：S6·D6 的 List 实现——WHERE 里只有 category_id，没有分类状态。
