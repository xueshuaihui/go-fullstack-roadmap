账户归档与恢复：余额非 0 拒绝归档

销卡的卡、停用的钱包不该一直躺在记账选择器里，但它也不能删——历史流水还挂在它身上。这就是归档：archived_at 盖上戳，账户退出日常动线，历史照常可查可统计。今天做 archive/restore 两条接口，核心是一条硬规则：余额非 0 的账户拒绝归档，返回 409 + 1010，并提示先把钱转走——否则归档一个还有 300 块的账户，那 300 块就从家庭资产视野里消失了，这是账目正确性问题，不是交互洁癖。

今日目标

知识讲义

1. 归档 ≠ 软删 ≠ 硬删

软删（deleted_at）归档（archived_at）
语义「这条数据删了」「这个账户不再使用」
历史流水流水自己的软删与账户无关原样保留，查询、报表、余额全部照常计算
列表默认口径排除（回收站才见）仍返回，带 archived_at 标记，前端归进「已归档」分组
新流水—拒绝在归档账户上新建流水（1010）
恢复动作restore 清 deleted_atrestore 清 archived_at，账户回到动线

账户表没有进回收站的概念：删账户这个操作根本不存在（历史流水的外键要指着它）。用户想「去掉」一个账户，唯一正路就是归档。

2. 归档前置检查链

片段 · archive 的状态机（自上而下短路）① 行不存在 / 别的家庭 / 已软删        → 404 + 1001（同形，D7 的老口径）
② archived_at 已经非 NULL（重复归档）   → 409 + 1010
③ is_default = true（默认账户）         → 409 + 1010，提示先把默认设给别的账户
④ BalanceOf(...) ≠ 0（余额非 0）        → 409 + 1010，提示「先转账清零再归档」
⑤ 全过 → UPDATE archived_at = now(), version = version + 1
  • ③ 是 ④ 的姊妹规则：默认账户是「新建流水的落脚点」，把它归档会让默认指向一个不能用的账户。先转移默认，再归档。
  • ④ 的余额用 D3 的 BalanceOf 现算——推导式口径的红利 again：判据（能不能归档）与展示（列表里的余额）是同一个函数，永远不会「显示 0 却拒归档」。
  • 校验与写入之间的并发缝：查完余额到 UPDATE 之间可能有人记了一笔。教学期口径：⑤ 的 UPDATE 用 WHERE archived_at IS NULL 原子推进（RowsAffected 状态机，D4/D5 的老朋友），余额缝属于极低概率、且事后仍可恢复归档再处理，不为此上锁；想把缝焊死（可串行化事务）属选做。

3. restore 与「归档账户不能记新账」

POST restore 对称：不存在 → 1001；没归档 → 1010（业务状态不允许）；成功清 archived_at、version+1。另一头，昨天流水 Create 的校验链里今天补一环：account_id 或 to_account_id 命中已归档账户 → 409 + 1010。转账两端只要有一端归档就整笔拒绝——钱不能从/向停用的口袋流动。

今日增量（在学习仓里落盘）

今天属增量类型 ④+②：一条迁移（账户表加 archived_at）+ archive/restore 两条路由，顺手给流水 Create 补归档账户检查（类型 ⑤ 的小尾巴）。

步骤 1 · 迁移

完整 · server/migrations/finance/finance_000X_add_account_archived.up.sql（编号接现有最大号）ALTER TABLE finance_account ADD COLUMN archived_at TIMESTAMPTZ NULL;

步骤 2 · service 状态机

片段 · server/internal/finance/service/account.gofunc (s *AccountService) Archive(ctx context.Context, a Actor, id int64) error {
    acct, err := s.repo.GetAlive(ctx, a.FamilyID, id)
    switch {
    case err != nil:       return err
    case acct == nil:      return response.ErrNotFound              // 404 + 1001
    case acct.ArchivedAt != nil: return response.ErrStateNotAllowed // 已归档
    case acct.IsDefault:   return response.ErrStateNotAllowed       // 先转移默认
    }
    bal, err := s.txRepo.BalanceOf(ctx, a.FamilyID, id)
    if err != nil { return err }
    if bal != 0 {
        return response.ErrStateNotAllowed // message 层给「请先将余额转账清零」；409 + 1010
    }
    ok, err := s.repo.MarkArchived(ctx, a.FamilyID, id) // WHERE archived_at IS NULL，RowsAffected 判定
    switch {
    case err != nil: return err
    case !ok:        return response.ErrStateNotAllowed // 并发抢先归档
    }
    return nil
}

// Restore 对称：acct.ArchivedAt == nil → ErrStateNotAllowed；否则清戳。

常见坑（新手 100% 会踩）

坑现象正确姿势
归档实现成软删账户从列表消失，历史流水的账户名成了悬空引用归档是独立状态列；列表仍返回，带 archived_at 标记
余额非 0 也放行归档那笔钱退出家庭资产视野，对账永远差一块409 + 1010，message 引导「先转账清零」
余额判断用了另一套算法列表显示 0、归档却说非 0判据与展示同用 BalanceOf，一个函数一个口径
默认账户直接归档新流水的默认落脚点是死的默认账户先转移默认再归档，否则 1010
归档账户还能记新账「不再使用」名不副实，余额又开始动流水 Create 检查两端账户状态，归档 → 1010
先 SELECT 判状态再 UPDATE 无 WHERE 兜底并发双击归档互相踩UPDATE 带 WHERE archived_at IS NULL，看 RowsAffected

今日名词卡

术语一句话解释
归档（archive）业务停用状态：退出日常动线，历史与统计原样保留
archived_at归档时间戳列；NULL = 在用。与软删双戳是两套互不相干的列
1010业务状态不允许（409）：余额非 0 归档、恢复未归档/未删除的行、取消唯一默认等同族
前置检查链1001 → 状态类 1010 → 余额 1010 的短路顺序；越靠前的检查越便宜
清零再归档把余额转账到在用账户，是归档前的唯一正路；服务端只拦不代做
判据展示同源能不能归档与列表显示的余额调用同一个 BalanceOf，永不分叉
RowsAffected 状态机UPDATE 的 WHERE 带状态条件，用命中行数区分并发抢先（D4/D5 传下来）
迁移可回滚down 真能把 up 撤干净；ALTER 加列的 down 就是 DROP COLUMN

卡壳时查什么

  • BalanceOf 与推导式口径：S6·D3——今天的判据整个建立在它上。
  • RowsAffected 状态机与原子 UPDATE：S6·D4（软删）与 S6·D5（乐观锁），同一个模式第三次用。
  • 1001 同形口径：S6·D7 单条查询的三类 404。
  • 迁移编号与成对规则：S3 迁移周；编号接 finance 序列现有最大号。
