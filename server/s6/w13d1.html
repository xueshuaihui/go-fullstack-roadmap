流水单条查询与编辑的正确流程

七条流水接口还剩一条没做：GET /api/finance/transactions/{id}。它看着最简单，却是必须显式存在的一条——没有它，编辑页只剩一条歪路：把整月列表拉下来，在客户端按 id 匹配出要编辑的那笔。今天写这个接口，顺便把「编辑流程」的完整闭环钉死：拉单条（带 version）→ 用户改 → PUT 带 version 提交 → 冲突 1009 重拉。

今日目标

知识讲义

1. 「拉整月再匹配」是怎么发生的，为什么必须禁

缺了单条接口时，编辑页的开发者会这么绕：进编辑页 → 调列表接口（带当月的时间筛选）→ 在返回的 list 里 find(t => t.id === id)。三个致命处：

  • 列表是被筛选过的。用户从「支出 + 某账户」的筛选视图点进一笔转账，这笔转账根本不在那份 list 里——匹配不到，编辑页白屏。
  • 时效。列表是几分钟前拉的缓存，version 已过期；拿旧 version 去 PUT 必然 1009，用户莫名被弹「冲突」。
  • 流量与语义。为了 1 行数据拉 100 行，还把「编辑」这个语义藏进了列表接口，服务端日志里完全看不出用户在编辑。

正确流程只有一条：编辑页进场先 GET 单条，拿到最新全量字段与当前 version，再渲染表单。

2. 单条查询的 404 口径

情形返回为什么
id 在本家庭不存在404 + 1001本义
id 存在但属于别的家庭404 + 1001越权读与不存在同形，不泄露「这个 id 存在」这一事实（S4 老纪律）
id 存在但已软删404 + 1001业务视角已删 = 不存在；回收站视角走 ?deleted=true 列表

实现上三者共用一条 SQL：WHERE id = ? AND family_id = ? AND deleted_at IS NULL，查不到就是 1001——不需要（也不允许）分支判断「到底是哪种没有」再回不同错误。同形的意义就在于响应没有任何可区分的细节。

3. 编辑闭环全时序（把 D5 串起来）

片段 · 编辑一笔流水的完整对话① GET  /api/finance/transactions/7        → 200, data.version = 3
② 用户改金额，客户端提交
   PUT  /api/finance/transactions/7       body: {"version":3, "amount_cents":4200, ...}
③a 没人动过 → 200, data.version = 4，编辑页关闭
③b 有人抢先改过 → 409 + 1009, data = {your_version:3, current_version:4, current:{...}}
   客户端提示「已被改为 ¥…」，用 current 重渲染表单，用户重改后带 version=4 再 PUT

注意 ④ 的伏笔：私密流水（is_private）的行级可见性会在本阶段后半接入这条 GET——届时「别人建的私密流水」对你也是 404 + 1001 同形，今天先把单条查询的骨架立正。

步骤 1 · repo / service / handler

片段 · server/internal/finance/repo/transaction.go// GetByID 业务视角单条：不存在/越权/已软删统一查不到。
func (r *TxRepo) GetByID(ctx context.Context, familyID, id int64) (*model.Transaction, error) {
    var tx model.Transaction
    err := r.db.WithContext(ctx).
        Where("id = ? AND family_id = ? AND deleted_at IS NULL", id, familyID).
        First(&tx).Error
    if errors.Is(err, gorm.ErrRecordNotFound) { return nil, nil } // nil,nil = 没有；上层回 1001
    if err != nil { return nil, err }
    return &tx, nil
}
片段 · handler 与路由注册func (h *TxHandler) Get(c *gin.Context) {
    id, err := strconv.ParseInt(c.Param("id"), 10, 64)
    if err != nil {
        response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "id 不合法") // 400 + 1004
        return
    }
    tx, err := h.svc.Get(c.Request.Context(), actorFrom(c), id)
    if err != nil { response.FailErr(c, err); return } // svc 查不到时回 ErrNotFound → 404 + 1001
    response.OK(c, tx)
}

fin.GET("/transactions/:id", txh.Get)

常见坑（新手 100% 会踩）

坑现象正确姿势
用列表接口凑合编辑页筛选视图里点进来的行匹配不到；version 过期连环 1009编辑页进场必拉单条
越权读回 403泄露「此 id 存在」，可被枚举探测越权读一律 404 + 1001 同形；403+1003 只留给越权写
已软删行还能 GET 到回收站语义泄漏进业务视角单条查询 WHERE 带 deleted_at IS NULL
单条响应裁字段（不返回 version）客户端没法带版本提交，乐观锁被绕死单条响应给全量字段，version 必在其中
Gin 同层参数名不一致启动 panic：wildcard segment conflicts同一路径层的通配名全站统一叫 :id
id 解析失败回 404/transactions/abc 被当成「不存在」，掩盖了格式错误解析失败是 400 + 1004；查不到才是 1001

今日名词卡

术语一句话解释
单条查询（GET by id）编辑/详情页的唯一正当数据源；列表接口不为它代劳
拉整月再匹配缺单条接口时的客户端歪路：流量大、版本旧、筛选视图下必失败
同形 404不存在、越权、已软删三种情形返回完全相同的 404 + 1001，不可区分
越权读 vs 越权写读 → 404+1001（藏存在性）；写 → 403+1003（明确拒绝）
编辑闭环GET 单条(带 version) → PUT(带 version) → 1009 时用 current 重来
c.Param("id")Gin 取路径参数，string 类型，自己 ParseInt 并处理 1004
nil, nil 约定repo 层「查询成功但没有行」的表达；错误留给真的错误
枚举探测攻击者用不同 id 扫接口，凭响应差异推断哪些资源存在——同形 404 就是防它
