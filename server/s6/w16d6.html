周六 · S6 收口：30 条划掉与三条判据自测

S6 的最后一天，不写新功能。这是全站最长阶段（五周 30 张卡）的收口：施工清单 B 段 30 条逐条核对划掉、一条端到端收口测试把五周串成一个闭环、三条红线判据逐条自测。S1 收口时说过「今天的产物不是代码，是确定性」——30 天后这句话更成立了：财务面是全站第一个「完整业务域」，它的收口质量决定 S7 壳基座是在地基上盖楼还是在沙上盖楼。

今日目标

知识讲义

1. 划掉一条接口的标准：三条全满足

「做完了」不是感觉，是核对。每条接口过三关：

  1. 路由在表里：GET /api/finance/… 出现在你的路由清单（README 那张表）里，路径与施工清单逐字符一致——多一个 /v1、少一个 s 都算不过。
  2. 真实现：handler 里没有假数据、没有 TODO 悬空（D21 那种「有主有卡号且已兑现」的除外——今天它必须已兑现）。「注册了但没实现」是明账反例，收口日就是它的死期。
  3. 有测试：成功路径 + 至少一条失败路径（错误码断言到具体数字）。没有测试的接口 = 没有做完。

30 条对照表在 S6 阶段总览，逐条打勾。发现没做完的怎么办？记进 notes 的欠账清单，不许今天现补大功能——收口日加新功能就是「收口变开口」。欠账在明天的周日后半复盘时排期，落后不追赶，顺延不裁剪判据。

2. 三条红线判据：每条都要能指认护栏

#判据护栏测试（指出名字才算过）手工验证

3. 端到端收口测试：五周一个闭环

TestS6Acceptance 不是新逻辑，是把 30 天里各自为战的测试串成一条用户视角的故事线。它同时是 S8 冒烟脚本的雏形——今天用 httptest 写，S8 换成 docker compose 起真服务跑同一脚本。

片段 · server/internal/finance/acceptance_test.go（前置：httptest.NewRecorder + S4 测试 token helper + 各 repo 种子直插）// TestS6Acceptance 一条链跑完 B 段五块：
//  1. POST accounts 建两个账户（初始余额各 500000 分）→ 201
//  2. POST budgets 给 2026-10 设总预算 300000 → 201；重复 POST → 409+1006
//  3. POST transactions 记 3 笔支出（带 client_request_id；重放同一请求 → 幂等成功不重复入账）
//     其中一笔顶过 80% → fakeNotifier 收到 1 条 budget_alert（D22 钩子）
//  4. POST recurring 建一条月规则（anchor_day=31），RunDue(1-31) → 流水 +1；再 RunDue → 不重复（D24）
//  5. GET budgets?period=2026-10 → used 精确等于全部支出和（含自动入账那笔）
//     GET budgets?period=2026-Q4 → budget_unset:true（红线 3）
//  6. GET reports/summary view=trend period=2026-Q4 → 单桶 == 10/11/12 三查之和（红线 2）；
//     running 差值自洽逐桶成立
//  7. GET reports/export?period=2026-10 → CSV 数据行数 == 流水列表游标翻到底行数（红线 1）
//  8. PUT settings 阈值 90 → 再顶一笔到 85%：不告警（活配置生效）

链条里每一步都在复用已有 service，测试本身不写业务——如果某一步发现「没有可复用的函数、只能重写一遍逻辑」，那说明该逻辑长在了 handler 里而不是 service 里，这正是收口日该抓的分层腐化。修它（小重构属于收口范畴），记进 notes。
