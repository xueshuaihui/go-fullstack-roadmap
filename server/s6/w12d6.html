周六 · 流水查询：筛选与游标分页

本周把「写」做完了：创建带幂等（D1）、三类型校验（D2）、余额推导（D3）、软删与恢复（D4）、乐观锁编辑（D5）。周六做「读」，把七条流水接口的最后两条补上：列表查询（筛选 + 游标分页）与回收站列表（?deleted=true，恢复路径的数据源——没有它，D4 的 restore 就是断头路）。今天的判据只有一句话：翻页不重复、不漏、能续读。

今日目标

知识讲义

1. offset 分页的必然事故

LIMIT 10 OFFSET 20 的语义是「跳过前 20 行」——但「前 20 行」是每次查询现算的。你翻到第 3 页的瞬间，另一位家庭成员新记了一笔（按时间倒序它插在最前面），所有行整体后移一位：第 3 页的第一行就是第 2 页的最后一行，重复。反过来，翻页间隙删了一行，就会有一行被跳过，漏。记账 App 的列表页恰恰是「一边翻一边有人写」的场景，offset 分页在这里不是性能问题，是正确性问题。本站全站禁 offset。

2. 游标分页：把「位置」编码进游标

思路：不数「跳过几行」，而是记住「上一页最后一行是谁」，下一页从它之后继续。流水按 (occurred_at DESC, id DESC) 排序，「之后」就是一个行值比较：

片段 · 续读条件（排序键值对比较）WHERE family_id = ? AND deleted_at IS NULL
  AND (occurred_at, id) < ($cursor_time, $cursor_id)   -- Postgres 行值比较，一次写对方向
ORDER BY occurred_at DESC, id DESC
LIMIT $limit_plus_one                                   -- 多取 1 行探测 has_more
  • 为什么排序键要带 id：同一秒可以有多笔流水，只按 occurred_at 排序则同秒行序不稳定，翻页会抖。id 补上最后一位，排序全序、游标唯一。
  • 游标不透明：服务端把 (occurred_at, id) base64 编码成字符串发给客户端；客户端不得解析、不得自造、原样带回。日后想换排序或加密游标，只改服务端。
  • has_more 的探法：请求 limit=20 就查 21 行；查到 21 行说明还有下一页，返回前 20 行 + 用第 20 行生成 next_cursor；≤20 行则 has_more=false、next_cursor 为空。
  • limit 有上限：默认 20、最大 100。不接受无上限返回——一次拉全表会把手机和服务端一起拖死。
片段 · 列表信封（全站统一，不是流水专属）{"code":0,"message":"ok","data":{"list":[…],"next_cursor":"…","has_more":true}}

对照口径：非分页的小集合（分类树、账户列表、成员列表）直接 {"list":[…]}，不带 next_cursor/has_more。别把游标三件套滥发到小集合上，也别给大列表省掉它。

3. 回收站：同一查询的另一个开关

GET /api/finance/transactions?deleted=true 不是新接口路径，是列表接口的一个查询参数——回收站页与流水页共用筛选、分页、排序的全部逻辑，唯一差别是把固定件 deleted_at IS NULL 翻成 deleted_at IS NOT NULL。D4 说过软删三件套：DELETE、restore 都有了，今天补上第三件，恢复路径闭环：回收站列表 → 用户挑一行 → restore → 回业务列表。

步骤 1 · 游标编解码（不透明）

完整 · server/internal/finance/service/cursor.gopackage service

import (
    "encoding/base64"
    "strconv"
    "strings"
    "time"
)

// EncodeCursor 把 (排序键, id) 编成不透明字符串。客户端不得解析。
func EncodeCursor(occurredAt time.Time, id int64) string {
    raw := strconv.FormatInt(occurredAt.UnixMilli(), 10) + "_" + strconv.FormatInt(id, 10)
    return base64.RawURLEncoding.EncodeToString([]byte(raw))
}

// DecodeCursor 解回 (时间, id)；解不开就是客户端伪造/损坏 → 上层回 400 + 1004。
func DecodeCursor(s string) (time.Time, int64, error) {
    raw, err := base64.RawURLEncoding.DecodeString(s)
    if err != nil { return time.Time{}, 0, err }
    ms, idStr, ok := strings.Cut(string(raw), "_")
    if !ok { return time.Time{}, 0, strconv.ErrSyntax }
    msVal, err := strconv.ParseInt(ms, 10, 64)
    if err != nil { return time.Time{}, 0, err }
    id, err := strconv.ParseInt(idStr, 10, 64)
    if err != nil { return time.Time{}, 0, err }
    return time.UnixMilli(msVal), id, nil
}

步骤 2 · repo 查询与 handler

片段 · repo 的 List（前置：TxFilter 结构体含 Type/AccountID/CategoryID/Deleted/Cursor时间/CursorID/Limit）func (r *TxRepo) List(ctx context.Context, familyID int64, f TxFilter) ([]model.Transaction, error) {
    q := r.db.WithContext(ctx).Model(&model.Transaction{}).Where("family_id = ?", familyID)
    if f.Deleted { q = q.Where("deleted_at IS NOT NULL") } else { q = q.Where("deleted_at IS NULL") }
    if f.Type != ""        { q = q.Where("type = ?", f.Type) }
    if f.AccountID != 0    { q = q.Where("account_id = ? OR to_account_id = ?", f.AccountID, f.AccountID) }
    if f.CategoryID != 0   { q = q.Where("category_id = ?", f.CategoryID) }
    if !f.CursorTime.IsZero() {
        q = q.Where("(occurred_at, id) < (?, ?)", f.CursorTime, f.CursorID)
    }
    var rows []model.Transaction
    err := q.Order("occurred_at DESC, id DESC").Limit(f.Limit + 1).Find(&rows).Error
    return rows, err // service 层裁第 limit+1 行定 has_more，并用第 limit 行编 next_cursor
}

步骤 3 · 不重不漏测试（今天的判据本体）

import "testing"

func TestListPagingNoDupNoLoss(t *testing.T) {
    svc, a := newTestTxService(t), Actor{FamilyID: 1, MemberID: 10}
    ctx := t.Context()
    want := map[int64]bool{}
    for i := 0; i < 25; i++ { // 25 笔金额各不相同的支出
        tx := mustCreateTxAmount(t, svc, a, int64(100+i))
        want[tx.ID] = true
    }
    seen, cursor, pages := map[int64]int{}, "", 0
    for {
        page, err := svc.List(ctx, a, ListQuery{Limit: 10, Cursor: cursor})
        if err != nil { t.Fatal(err) }
        pages++
        for _, tx := range page.Items {
            seen[tx.ID]++
            if seen[tx.ID] > 1 { t.Fatalf("重复: id=%d 出现 %d 次", tx.ID, seen[tx.ID]) }
        }
        if !page.HasMore { break }
        cursor = page.NextCursor
        if pages > 10 { t.Fatal("翻不完，游标没有推进") }
    }
    if len(seen) != len(want) { t.Fatalf("漏行: 读到 %d, 应有 %d", len(seen), len(want)) }
    for id := range want {
        if seen[id] != 1 { t.Fatalf("id=%d 计数 %d, want 1", id, seen[id]) }
    }
}

func TestListTrashIsolation(t *testing.T) {
    svc, a := newTestTxService(t), Actor{FamilyID: 1, MemberID: 10}
    ctx := t.Context()
    tx := mustCreateTx(t, svc, a)
    _ = svc.Delete(ctx, a, tx.ID)
    live, _ := svc.List(ctx, a, ListQuery{Limit: 10})
    trash, _ := svc.List(ctx, a, ListQuery{Limit: 10, Deleted: true})
    if len(live.Items) != 0 || len(trash.Items) != 1 {
        t.Fatalf("软删行应只在回收站: live=%d trash=%d", len(live.Items), len(trash.Items))
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
排序键不带 id同秒多行时翻页抖动、重复ORDER BY occurred_at DESC, id DESC，游标也编这对值
游标做成明文 ?after_id=123客户端开始自造游标、按 id 排序的假设被焊死base64 不透明游标；换排序只改服务端
has_more 用「恰好 limit 行」判定最后一页恰好满员时多翻一次空页查 limit+1 行探测，多的那行不返回
limit 不设上限?limit=999999 一发，服务与手机一起卡死缺省 20、上限 100，越界 1004
回收站另写一个接口路径筛选分页逻辑两份，改一处漏一处同一路径 + deleted=true 开关，WHERE 翻面而已
回收站查询忘了 family_id看到别人家庭的删除行，隔离被打穿family_id = ? 是任何查询的第一固定件，回收站不例外
伪造游标直接 500base64 解码错误没接住解不开一律 400 + 1004，不许把解析错误漏成服务器错误

今日名词卡

术语一句话解释
offset 分页「跳过 N 行」式分页；边翻边写必重复或漏，本站禁用
游标分页记住上一页末行位置，下一页从它之后续读；信封 {list, next_cursor, has_more}
不透明游标base64 编码的 (排序键, id)；客户端不解析、不自造、原样带回
行值比较(occurred_at, id) < (?, ?)：Postgres 按字典序比较元组，续读条件一行写对
limit+1 探测多取一行判断 has_more，避免为「还有没有」单独发一次 COUNT
不重复、不漏、能续读分页正确性的三条判据，前端下拉刷新/触底加载也按它验收
回收站列表?deleted=true 的同一查询；软删三件套的第三件，restore 的数据源
小集合口径分类树/账户列表等非分页集合直接 {"list":[…]}，不带游标三件套
