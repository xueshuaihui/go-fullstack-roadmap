软删与回收站：deleted_at 必须配恢复

删除流水今天做，但只许做成软删：盖时间戳、记操作人，行还在。同时必须立刻配一个恢复入口——某个真实记账产品就栽在这里：表里有 deleted_at 列，却没有任何接口和页面能把行捞回来，用户误删的账进了黑洞，不可逆。软删与恢复是一对，拆开出任何一个都是半成品事故。回收站列表（?deleted=true）周六随查询一起做。

今日目标

知识讲义

1. 软删的三条纪律

  • 成对写：deleted_at = now() 的同时 deleted_by = 当前 member_id。谁删的是审计的一半；只盖时间戳不记人，家庭里两个成人互相猜是谁删的账。
  • 查询默认排除：业务查询的固定件从 WHERE family_id = ? 变成 WHERE family_id = ? AND deleted_at IS NULL。昨天的余额聚合已经这么写了——今天起所有流水查询统一。
  • 恢复是清戳，不是复制：restore 把 deleted_at/deleted_by 清回 NULL，同一行复活，id 不变、附件还在、历史连续。不许实现成「按旧数据新建一条」——那会断掉附件与审计链。

2. 黑洞事故：软删没有恢复入口

复盘一个真实事故模式：服务端有 deleted_at 列、DELETE 接口也做了软删，看起来「很规范」；但恢复接口没做、回收站页面没做。于是：用户误删 → 前端列表消失 → 数据库里行还在却没有任何路径能碰它 → 用户以为删了就补记一笔 → 某天导数据发现同一笔账两条（一条 deleted 一条活的）。软删的价值 100% 兑现在「可恢复」上；不配恢复入口的软删，比硬删更坏——硬删至少诚实，软删是给用户一个假的安全感。

所以本站的口径：DELETE（软删）、restore（恢复）、?deleted=true（回收站列表，恢复路径的数据源）三件套是一个整体，今天做前两件，周六补第三件，一天都不许欠。

3. 软删与恢复的边界规则

操作对象状态结果
DELETE 已删除的行deleted_at 非 NULL404 + 1001（业务查询视角它已不存在，与真不存在同形）
restore 活着的行deleted_at 为 NULL409 + 1010（业务状态不允许：没删过谈何恢复）
restore 别人家庭的行family_id 不匹配404 + 1001（越权读与不存在同形，S4 的老纪律）
restore 成功—清双戳、version+1、余额自动回来（推导式红利）

恢复后「预算与统计按当前时间窗重算」不需要任何代码——报表和余额都是流水的函数，行一复活，下一次读就自动包含它。这就是昨天选推导式的复利。

步骤 1 · repo：两条 UPDATE

片段 · server/internal/finance/repo/transaction.go// SoftDelete 盖双戳。RowsAffected==0 说明行不存在/已删/不属于本家庭 → 上层回 1001。
func (r *TxRepo) SoftDelete(ctx context.Context, familyID, txID, memberID int64) (bool, error) {
    res := r.db.WithContext(ctx).
        Model(&model.Transaction{}).
        Where("id = ? AND family_id = ? AND deleted_at IS NULL", txID, familyID).
        Updates(map[string]any{
            "deleted_at": gorm.Expr("now()"),
            "deleted_by": memberID,
            "version":    gorm.Expr("version + 1"),
            "updated_at": gorm.Expr("now()"),
        })
    return res.RowsAffected == 1, res.Error
}

// Restore 清双戳。RowsAffected==0 且行存在 → 没删过，上层回 1010。
func (r *TxRepo) Restore(ctx context.Context, familyID, txID int64) (bool, error) {
    res := r.db.WithContext(ctx).
        Model(&model.Transaction{}).
        Where("id = ? AND family_id = ? AND deleted_at IS NOT NULL", txID, familyID).
        Updates(map[string]any{
            "deleted_at": nil, "deleted_by": nil,
            "version": gorm.Expr("version + 1"), "updated_at": gorm.Expr("now()"),
        })
    return res.RowsAffected == 1, res.Error
}

注意 WHERE 里直接带状态条件（deleted_at IS NULL / IS NOT NULL），用 RowsAffected 区分「没命中」与「状态不对」——一条 UPDATE 原子完成判定与写入，不存在「先 SELECT 再 UPDATE」的竞态窗口。这是 S5 并发课的直接应用。

步骤 2 · service 与路由

片段 · service 分支 + main.go 注册// service：删/恢复的状态机，对着讲义第 3 节的表格直译
func (s *TxService) Delete(ctx context.Context, a Actor, id int64) error {
    ok, err := s.repo.SoftDelete(ctx, a.FamilyID, id, a.MemberID)
    switch {
    case err != nil: return err
    case !ok:        return response.ErrNotFound // 404 + 1001（含越权同形）
    }
    return nil
}

func (s *TxService) Restore(ctx context.Context, a Actor, id int64) error {
    ok, err := s.repo.Restore(ctx, a.FamilyID, id)
    switch {
    case err != nil: return err
    case !ok:
        // 区分「真没有」与「活着不让恢复」：存在性一查（仍带 family_id）
        exists, e2 := s.repo.ExistsAny(ctx, a.FamilyID, id)
        if e2 != nil { return e2 }
        if !exists { return response.ErrNotFound }        // 404 + 1001
        return response.ErrStateNotAllowed               // 409 + 1010
    }
    return nil
}

fin.DELETE("/transactions/:id", txh.Delete)
fin.POST("/transactions/:id/restore", txh.Restore)

常见坑（新手 100% 会踩）

坑现象正确姿势
只写 deleted_at 不写 deleted_by审计断了一半，「谁删的」永远查不到双戳成对，同一条 UPDATE 里写
恢复实现成「新建一条」id 变了、附件孤儿、幂等键冲突恢复 = 清双戳复活原行
先 SELECT 判状态再 UPDATE两个并发删除/恢复互相踩WHERE 里带状态条件，看 RowsAffected（S5 的老课）
DELETE 已删行返回 1010暴露了「这行存在过」，与越权同形原则打架业务视角已删 = 不存在，404 + 1001
软删行的附件也「顺手」删了恢复后附件黑洞附件跟随主流水生命周期，回收站 30 天窗口后才谈清理
做了 DELETE 就收工黑洞事故复刻：删得掉、捞不回DELETE / restore / 回收站列表三件套是一个整体

今日名词卡

术语一句话解释
软删（soft delete）盖 deleted_at 标记删除，行仍物理存在，可恢复
deleted_by操作人 member_id，与 deleted_at 成对写入，审计的另一半
黑洞事故有软删列、无恢复入口：数据进得去出不来，比硬删更坏
回收站?deleted=true 的流水列表，恢复路径的唯一数据源（周六做）
清戳复活restore 把双戳清回 NULL，同一行、同一 id、附件不动
RowsAffected 状态机UPDATE 的 WHERE 带状态条件，用命中行数区分 1001/1010，免掉先查后改的竞态
1010业务状态不允许（409）：没删过的行不可恢复、非 0 余额不可归档等同族
回收站 30 天软删行的保留窗口；窗口内可恢复，过期清理属运维策略，教学期只留口径不做定时任务
