周六 · 周期记账的幂等自动入账

本周串联日。D19-D23 攒下的五块——预算行、已用聚合、budget_unset 红线、告警钩子、规则表——今天由一条链路穿起来：到点 → 按规则生成流水 → 幂等键挡住重复 → 入账顺带触发预算告警。落掉 B6 的最后一条接口 PUT /api/finance/recurring/{id}，写出 RunDue，并用测试证明一件事：同一期无论触发几次，只入账一次。

今日目标

知识讲义

1. 自动入账的完整链路

结构 · RunDue 一次执行做的事（S7 起由到期中心调用；S6 期间测试直接调）RunDue(ctx, now)
  ├── 查规则：enabled = true AND next_run_at <= now AND deleted_at IS NULL（带 family 维度逐家庭跑）
  └── 对每条规则（单条一个事务）：
        ├── periodKey = 应执行日所在周期（月档：next_run_at 那天，不是 now 那天！）
        ├── 幂等键   = "recurring:{ruleID}:{periodKey}"
        ├── 建流水   = 复用 D2 的入账 service（金额/账户/分类来自规则，备注带规则名）
        │              └── client_request_id 唯一约束挡住重复 → 冲突即「已入过账」，跳过
        ├── 推进     = next_run_at = nextMonthly/nextWeekly(应执行日, 锚点)
        └── 告警钩子 = 提交后调 CheckAlert（D22 的写路径钩子，自动入账与手工记账同待遇）

三个设计决策，每个都对应一种真实事故：

决策不这么做会怎样
periodKey 用应执行日，不用执行时刻服务器停机三天，1 月 31 日的房租 2 月 3 日补跑；若用 now 算周期，键变成 2 月的，将来 2 月 28 日锚点规则再跑就是两笔
入账与推进 next_run_at 同一事务入账成功、推进失败 → 下次扫描重复触发（虽有幂等键兜底，但 next_run_at 永远追不上，扫描越积越多）
幂等冲突 = 成功跳过，不是报错把「已入过账」当失败上报告警，运维天天查假事故

2. 幂等键的两种冲突，只有一个算错误

D2 建的幂等机制今天迎来最正式的用法。回忆口径：

  • 同键 + 同请求体：重放。返回幂等成功（首次创建的结果），自动入账链路里体现为「跳过，继续下一条规则」。这不是错误。
  • 同键 + 不同请求体：键被挪用了，409 + 1008。自动入账不该触发它——因为键确定、体也由规则确定；一旦触发，说明有人手改流水的 client_request_id，属于要查的 bug。

为什么键里不放执行时间戳：幂等键的全部价值来自「同一件事算出同一个键」。掺进 time.Now()，每次执行键都不同，唯一约束形同虚设——重复入账照样发生，只是每次换了个马甲。「确定性」三个字是这条链路的命根子。

3. PUT /api/finance/recurring/{id}：编辑与启停

可改字段：title、amount_cents、account_id、category_id、锚点、enabled；freq 不可改（周改月等于换一条规则，删旧建新，历史流水的出处才清晰）。老三步乐观锁：请求带 version → 条件 UPDATE → 影响行数 0 时区分 1001（不存在/跨家庭）与 1009（版本冲突，双版本 payload）。两个特殊口径：

  • 停用（enabled=false）：next_run_at 保留不动。它是「如果重新启用，从哪儿接着算」的锚；S7 的到期中心按 enabled 撤销注册，不靠清这一列。
  • 改金额/账户：只影响将来。已生成的历史流水一个都不改——自动入账的流水生成那一刻起就是普通流水，编辑走流水自己的 PUT（S6·D4），与规则解耦。

金额校验照旧 4001；改完后重算 next_run_at（锚点变了要跟着变），并复位什么吗？——规则没有 alerted_at，预算告警的状态在预算行上，规则编辑不碰它。

4. 本周串联复盘（周日下午正式做，今天先对一遍）

对着仓库说出每块是哪天的产物：D19 给了预算行与唯一索引，D20 给了已用聚合与 rollup，D21 把「未设」变成显式标记，D22 的 CheckAlert 今天被 RunDue 复用，D23 的 nextMonthly 今天既管创建也管推进。自动入账的流水同样进 D20 的聚合——房租入账把「居住」分类顶过 80%，告警照发。说不出这条闭环的哪一环，周日就补哪一环。

步骤 2 · RunDue service

片段 · server/internal/finance/service/recurring_service.go 追加（前置：入账 service CreateTx 是 D1-D6 串好的那条；periodKeyOf 复用周期解析包）// RunDue 扫描到点规则并逐条入账。now 由调用方给：S6 是测试，S7 是到期中心。
func (s *RecurringService) RunDue(ctx context.Context, now time.Time) (int, error) {
    rules, err := s.repo.FindDue(ctx, now) // enabled AND next_run_at <= now AND deleted_at IS NULL，逐家庭 scope
    if err != nil { return 0, err }
    posted := 0
    for _, r := range rules {
        ok, err := s.runOne(ctx, r)   // 单规则单事务：入账 + 推进 next_run_at
        if err != nil { return posted, err }
        if ok { posted++ }
    }
    return posted, nil
}

func (s *RecurringService) runOne(ctx context.Context, r model.RecurringRule) (bool, error) {
    periodKey := period.KeyOf(r.NextRunAt, period.Month)          // 应执行日所在月，不是 now！
    idemKey := fmt.Sprintf("recurring:%d:%s", r.ID, periodKey)  // 确定性幂等键
    return s.tx.WithinTx(ctx, func(ctx context.Context) (bool, error) {
        created, err := s.txSvc.CreateWithIdemKey(ctx, r.FamilyID, createFromRule(r), idemKey)
        if err != nil { return false, err }   // 幂等冲突在 CreateWithIdemKey 内消化成 created=false, err=nil
        next := advance(r)                       // 从应执行日推进一期（weekly/monthly 各自纯函数）
        if err := s.repo.AdvanceNextRun(ctx, r.ID, r.FamilyID, next); err != nil {
            return false, err
        }
        return created, nil
    })
    // 事务提交后（runOne 返回 created=true 时）调 s.budgets.CheckAlert(…)——D22 钩子，写路径待遇一致。
}

advance 必须从 r.NextRunAt（应执行日）推进，不能从 now 推进。停机三天补跑时：应执行日 1-31 → 下一期 2-28；若从 now（2-3）推进，nextMonthly 会给出 2-28 没错，但 periodKey 已经错了——两个「用 now」的错误会互相掩护，测试必须分别钉死。

常见坑（新手 100% 会踩）

坑现象正确姿势
幂等键掺 time.Now()每次执行键都不同，重复入账照旧键 = 规则 id + 应执行周期，纯确定性
periodKey 用执行时刻算补跑入错周期，月度统计错位用 next_run_at（应执行日）算周期
推进 next_run_at 在事务外入账成功推进失败，扫描队列越积越多同事务：要么全成，要么全不成
幂等跳过当错误上报日志里全是假事故同键同体 = 幂等成功，安静跳过
编辑规则顺手改历史流水「把上月房租也改成 3600」——历史被篡改，对不上账规则只管将来；历史流水走流水自己的 PUT
停用规则清掉 next_run_at重新启用后不知道从哪儿接着算保留 next_run_at，靠 enabled 控启停

今日名词卡

术语一句话解释
确定性幂等键同一件事永远算出同一个键：recurring:{ruleID}:{periodKey}
RunDue扫描到点规则并逐条入账的 service 函数；调用方 S6 是测试、S7 是到期中心
应执行日 vs 执行时刻next_run_at 与 now；周期归属、推进基点全看前者
补跑（catch-up）停机后处理积压的到点规则；幂等键保证补跑安全
1008同键不同体的幂等冲突，409；同键同体不是错误
事务边界单规则单事务：入账 + 推进；一条失败不拖垮整批
启停（enabled）停用不删行不清 next_run_at；历史可追溯、重启可接续
规则与流水解耦流水生成那刻起独立存在；改规则不改历史
