时间窗五档桶：ISO 周与季/年边界

昨天 trend 视图只有月档单桶，今天升满五档：day / week / month / quarter / year。五档里真正要动脑的是两个：week——「一周」到底从哪天算起、跨年那周归谁；quarter/year——桶边界怎么切才能和月档对得上。第二条直接连着本阶段三条红线之一：季/年 = 月桶之和。今天把这句话从口号变成实现。

2. ISO 周：别自己算，交给标准库

「2026 年第 42 周」听着无歧义，其实全是坑：周日开头还是周一开头？1 月 1 日所在的那半截周算第 1 周还是上一年最后一周？ISO 8601 把这两件事钉死了：周一是一周的第一天；一年的第 1 周是包含该年第一个星期四的那一周（等价说法：包含 1 月 4 日的那周）。推论：12 月 29-31 日有可能属于下一年的 W01，1 月 1-3 日也可能属于上一年的 W52/W53。

Go 的 t.ISOWeek() 返回的 (year, week) 就是按这套规则算的——注意它返回的 year 可能不等于 t.Year()。手写 t.Year() 拼 int(t.YearDay()/7)+1 之类的算法，跨年夜必错。编码格式化只有一种写法：

片段 · 周期键格式化（放进周期解析包，全站唯一实现）y, w := t.ISOWeek()
key := fmt.Sprintf("%04d-W%02d", y, w) // 2026-W42；week 必须补零两位，否则字典序 ≠ 时间序

Postgres 侧同口径：date_trunc('week', …) 恰好就是 ISO 周一零点，两边天然一致——但今天之后你其实不再需要它，原因见下节。

3. 红线「季/年 = 月桶之和」：为什么不是显然的

数学上，SUM(10 月)+SUM(11 月)+SUM(12 月) 和 date_trunc('quarter') 直接分组当然相等。那红线红在哪？红在工程上它们是两条代码路径：直接按季分组意味着季档有自己的一套 SQL、自己的边界函数、自己的过滤条件拷贝——今天相等，三个月后某人给月档加了个过滤条件忘了同步季档，数字就悄悄分家了，而且没有测试能发现，因为两条路径各自都「对」。

实现口径：月桶是唯一的 SQL 产物。quarter/year 档的实现 = 查出覆盖范围的月桶 → Go 侧按 3 个/12 个月一组整数相加 → 输出季/年桶。week/day 档才真正按自己的粒度分组。这样「季 = 月之和」不是数学巧合，是代码结构保证：

4. 桶序列生成：纯函数 + playground 验证

「period=2026-Q4 且 span=2 → 要查哪几个月」这类推算全部收进纯函数 BucketRange(p Period, span int) (from, to Period, keys []string)。playground 先跑通边界用例：

可跑 · server/playground/d26/main.go（独立 go.mod；跑通后函数搬进周期解析包，目录删除）package main

import (
    "fmt"
    "time"
)

// isoWeekKey 返回 t 所在 ISO 周的编码。
func isoWeekKey(t time.Time) string {
    y, w := t.ISOWeek()
    return fmt.Sprintf("%04d-W%02d", y, w)
}

func main() {
    tz := time.FixedZone("CST", 8*3600)
    fmt.Println(isoWeekKey(time.Date(2026, 10, 13, 12, 0, 0, 0, tz))) // 2026-W42
    fmt.Println(isoWeekKey(time.Date(2026, 12, 31, 12, 0, 0, 0, tz))) // 2026-W53
    fmt.Println(isoWeekKey(time.Date(2027, 1, 1, 12, 0, 0, 0, tz)))  // 2026-W53：元旦属于上一年最后一周
    // 月桶推进：从 1 号 AddDate，永不规整化溢出
    cur := time.Date(2026, 11, 1, 0, 0, 0, 0, tz)
    for i := 0; i < 3; i++ {
        fmt.Println(cur.Format("2006-01")) // 2026-11、2026-12、2027-01：跨年自然衔接
        cur = cur.AddDate(0, 1, 0)
    }
}

时区口径不变：桶边界一律按家庭时区（platform 接口拿 *time.Location）换算成 UTC 进 SQL。ISOWeek() 必须在「家庭时区的那个时刻」上调用——同一绝对时刻在 UTC 和东八区可能差出一整周（周一 00:30 CST = 周日 16:30 UTC）。

常见坑（新手 100% 会踩）

坑现象正确姿势
手算周号（YearDay/7）跨年周归属错，W53 消失或多出 W00只认 ISOWeek()
周编码不补零（2026-W5）字典序乱掉，游标排序跟着乱%04d-W%02d 固定格式
quarter 档直接 SQL 分组与月档两条代码路径，将来悄悄分家季/年只消费月桶，整数归并
在 UTC 时刻上调 ISOWeek东八区周一凌晨的账归了上一周先换家庭时区再算桶
月推进用「当前日 +1 月」1 月 31 日 AddDate 规整成 3 月 3 日桶推进永远从 1 号走（D23 同款坑）
空桶不补季档只有 2 个月有流水，折线图少一个点fillGaps 按键序列补 0 行

今日名词卡

术语一句话解释
ISO 8601 周周一起始；第 1 周 = 包含该年第一个星期四的周；跨年周有明确归属
ISOWeek()Go 标准库的 ISO 周年/周号；返回的 year 可能不等于日历年
date_trunc('week')Postgres 的截断函数，恰好是 ISO 周一零点
月桶同源month/quarter/year 三档共用同一份月桶 SQL 产物
整数归并季桶 = 3 个月桶逐项 int64 相加；不重查、不折算
BucketRange周期 + span → 桶键序列的纯函数；补桶与排序都靠它
fillGaps按桶键序列补 0 行，保证输出不断档、键序即时间序
1007时间窗编码非法专码；不回落任何默认档

卡壳时查什么

  • ISO 周的原始定义：Wikipedia ISO week date（可选，图表很直观）。
  • date_trunc 支持的粒度：Postgres 官方文档 Date/Time Functions（可选）。
  • AT TIME ZONE 的语义：同一文档页；记住一句就够——对 TIMESTAMPTZ 列用它，得到的是「那个时区墙钟时间」的 timestamp，正好用来分桶。
