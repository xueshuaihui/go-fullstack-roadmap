结构化日志：slog 与 request-id 串成一条线

S1·D9 立过一条硬要求：「每条日志都带 request-id」，当时用 log 包凑合，欠条写着 S5 兑现——今天还。工具是标准库的 log/slog（Go 1.21 起进标准库，不用装第三方包）：日志从「给人读的一行字」升级成「给机器检索的一组键值对」。事故排查的画面从此变成：用户报障带着响应头里的 request-id，你拿它一搜，那次请求经过的每一条日志一字排开。

今日目标

知识讲义

1. 同一件事的两种写法

对比 · log 包 vs slog// 旧：一行给人读的字。想统计「所有超时请求的耗时分布」？只能正则捞大海。
log.Printf("聚合完成 request_id=%s categories=%d total=%d", rid, n, total)

// 新：msg 只说「发生了什么」，其余全部进键值对字段。机器可检索、可统计。
slog.Info("聚合完成", "request_id", rid, "categories", n, "total_cents", total)

JSONHandler 下第二行输出长这样（一行一个 JSON 对象）：

输出 · 一条结构化日志{"time":"…","level":"INFO","msg":"聚合完成","request_id":"9f3c…","categories":6,"total_cents":418200}

slog 的角色分工一句话：Logger 决定「记什么」，Handler 决定「长什么样」。换 Handler（JSON → Text → 将来接采集器）不动任何调用点——跟 pkg/response 收口响应契约是同一个思想。

2. 四档级别与红线

级别用在哪例子
Debug开发期才看的细节；生产级别设 Info 就自动闭嘴解析出的每行导入数据
Info正常业务里程碑访问日志、「聚合完成」「导入完成」
Warn没出事但不正常ctx 超时中止了半截聚合、优雅关闭强关
Error出事且需要人看返回 5000 之前必有一条 Error 带原始错误

两条红线：① 敏感信息不进日志——密码、token、验证码、完整手机号，一个都不行（日志比响应体的传播面广得多）。② 错误细节进日志、不进响应体——这是 S1·D6 FailErr 的另一半：认不出的错误对外一律 500 + 5000，原始 err 与堆栈只在日志里现身，靠 request_id 把两边串起来。

3. request-id 串线：从中间件到每条日志

零件都是现成的：S1·D9/S2 的 RequestID 中间件已经生成 id、写进 c.Set("request_id", …) 并回写响应头。今天接上线：

  • 访问日志（AccessLog 中间件）：每请求一条 Info，自动带 request_id、method、path、status、耗时。
  • 业务日志（handler/service 里）：slog.Default().With("request_id", c.GetString("request_id")) 先预绑定再打——With 返回一个「自带这组字段」的子 Logger，后面每条都自动携带。
  • 后台任务（safego 兜住的 goroutine）：没有请求上下文，panic 日志带堆栈即可；有任务 id 就 With 任务 id。

AccessLog 里会用到 c.ClientIP()。它可信与否取决于 Gin 的 SetTrustedProxies 配置——决定信不信 X-Forwarded-For 这类代理头，配错了任何人都能伪造来源 IP。本站现在只提这一句，S8 部署（服务挂到 Nginx 后面）时正式兑现，今天不动它。

步骤 1 · logger 包：全站唯一装配口

完整 · server/internal/platform/logger/logger.go// Package logger 装配全站唯一的结构化日志口。
// 装配只做一次（main 里），其余代码一律 slog.Info/Warn/Error 或 slog.Default().With(…)。
package logger

import (
    "log/slog"
    "os"
    "strings"
)

// Init 按运行模式装配 *slog.Logger 并设为 slog 默认。
// debug 模式放到 Debug 级，其余从 Info 起——不新增环境变量，沿用 GIN_MODE
//（环境变量表全站唯一、禁别名，明天 D10 定稿时你会再见到这条纪律）。
func Init(ginMode string) *slog.Logger {
    level := slog.LevelInfo
    if strings.EqualFold(ginMode, "debug") {
        level = slog.LevelDebug
    }
    l := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level}))
    slog.SetDefault(l)
    return l
}

步骤 2 · AccessLog 中间件

完整 · server/internal/platform/middleware/access_log.gopackage middleware

import (
    "log/slog"
    "time"

    "github.com/gin-gonic/gin"
)

// AccessLog 每请求一条结构化访问日志。
// request_id 读的是 RequestID 中间件（S2）写进 context 的那个键，全站统一叫 "request_id"。
// 注册顺序：RequestID 在前、AccessLog 在后——先有 id 才能带 id。
func AccessLog() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        c.Next()                            // 先放行；洋葱出来的时候才有 status 与耗时
        slog.Info("request",
            "method", c.Request.Method,
            "path", c.Request.URL.Path,
            "status", c.Writer.Status(),
            "latency_ms", time.Since(start).Milliseconds(),
            "request_id", c.GetString("request_id"),
            "client_ip", c.ClientIP(),      // 可信度取决于 SetTrustedProxies，S8 兑现
        )
    }
}
完整 · server/internal/platform/middleware/access_log_test.gopackage middleware

import (
    "bytes"
    "encoding/json"
    "log/slog"
    "net/http"
    "net/http/httptest"
    "testing"

    "github.com/gin-gonic/gin"
)

func TestAccessLogCarriesRequestID(t *testing.T) {
    var buf bytes.Buffer
    old := slog.Default()
    slog.SetDefault(slog.New(slog.NewJSONHandler(&buf, nil)))
    t.Cleanup(func() { slog.SetDefault(old) })

    gin.SetMode(gin.TestMode)
    r := gin.New()
    r.Use(RequestID(), AccessLog())  // RequestID 以你仓库 S2 落的名字为准，键统一是 "request_id"
    r.GET("/healthz", func(c *gin.Context) { c.JSON(http.StatusOK, gin.H{"status": "ok"}) })

    w := httptest.NewRecorder()               // 进程内测试用 Recorder——D11 才轮到 NewServer
    r.ServeHTTP(w, httptest.NewRequest("GET", "/healthz", nil))

    var entry map[string]any
    if err := json.Unmarshal(buf.Bytes(), &entry); err != nil {
        t.Fatalf("访问日志不是合法 JSON: %v (%s)", err, buf.String())
    }
    rid, _ := entry["request_id"].(string)
    if rid == "" {
        t.Fatalf("访问日志没带 request_id: %s", buf.String())
    }
    if entry["path"] != "/healthz" || entry["status"] != float64(200) {
        t.Fatalf("字段不对: %s", buf.String())   // JSON 数字解出来是 float64，别惊讶
    }
    if w.Header().Get("X-Request-ID") != rid {
        t.Fatalf("响应头与日志的 request_id 对不上: %q vs %q", w.Header().Get("X-Request-ID"), rid)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
键值对写了奇数个日志里冒出 !BADKEY 字段slog 按「key, value」成对消费参数；写完数一遍，或用 slog.String("k", v) 显式 Attr
fmt.Sprintf 把字段拼进 msgJSON 是 JSON 了，但字段全糊在 msg 里没法检索msg 只说发生了什么；一切变量进键值对
密码/token 顺手进了日志日志文件成了泄密现场红线：敏感字段永不进日志；拿不准就不打
测试改了 slog 默认不还原别的用例输出被劫持，断言莫名其妙红t.Cleanup 还原 SetDefault，示例已示范
AccessLog 注册在 RequestID 之前访问日志的 request_id 恒为空串中间件顺序即数据顺序：先有 id 再带 id
业务代码各自 slog.New格式、级别、输出地各行其是装配只做一次（logger.Init），其余全走 slog 默认或 With 派生
拿 Debug 记错误生产级别 Info 下错误日志直接消失级别按「谁需要看见」选：要人处理的至少 Warn
JSON 解出数字用 int 接类型断言失败，测试红encoding/json 的数字默认 float64；断言时写 float64(200)

卡壳时查什么

正文自足，只有两种情况出去查：

  • slog 的完整 API：log/slog 文档（可选，读包顶部示例与 Handler 接口两节）。
  • Gin 中间件顺序的影响：回 S2 的中间件卡——洋葱模型里 c.Next() 前后各是半个世界。

排查「日志没带 request_id」的顺序：先看响应头有没有 X-Request-ID（没有 → RequestID 中间件没生效）；再看 AccessLog 的注册顺序（在 RequestID 之后吗）；最后才怀疑 handler 里 c.GetString 的键名——全站统一 "request_id"，写错一个字母就是空串。
