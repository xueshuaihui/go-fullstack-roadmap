S5 · 并发与工程化

这两周干两件事。前一半把四个从 S1 起就只在名词卡里露面的名字变成肌肉：goroutine、channel、Mutex、context——集中教、集中练、集中用 -race 验收。后一半给服务补上工程化四件套：config 定稿、结构化日志、优雅关闭、CI。同时立一条本阶段的铁律：S5 不新增任何业务接口——聚合与导入只做 service 层骨架，它们的路由挂载点属于 S6 才登记的报表/流水接口。

为什么并发排在这里

S1·D9 说过：net/http 为每个请求起一个 goroutine——过去四个阶段你一直在「被并发」，只是每个请求各干各的，互不碰共享数据，所以没出事。S6 起不一样：报表要一个请求内并行聚合多个账户/分类，批量导入要逐行校验收集错误——这些并发是你自己写的，共享内存也是你自己引入的，数据竞争的锅只能你自己背。所以本阶段先把手写并发的全套规矩立好，S6 的业务才敢放开跑。另一个信号：-race 从 S1·D1 就写在 Makefile 里躺着，今天它才正式成为主角。

阶段判据（全过才算 S5 通过）

不通过就原地重做，不跳阶段。S5 的空洞全部在 S6 结账：报表聚合的并发写、批量导入的错误收集、导出大文件的内存纪律，全踩在这两周的地基上。数据竞争最阴险的地方在于「测试恰好绿了」——判据只认 -race，不认运气。

本阶段不做什么（明确划掉，免得手滑）

  • 不新增任何业务接口——聚合与导入只是 service 层骨架，路由与落库属 S6 登记的报表/流水接口；/healthz 之外不注册任何东西
  • 不引入 Redis、消息队列、事件总线（课程范围外，只作前瞻句）
  • 不做覆盖率、不做压测——CI 只有 build + test -race 两步，S8 再升级
  • 不动前端。web/ 这两周归 F4 的周日卡管
  • 不写一条 SQL 聚合——真正的聚合查询属 S6；本阶段的「聚合」拿假数据行练并发骨架
