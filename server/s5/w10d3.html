Mutex/RWMutex 与 -race：亲手抓一次数据竞争

D1 你已经远远看过一次 WARNING: DATA RACE，今天走到近处：一个百分百能复现的竞争样例、一次逐行阅读 WARNING、一个「先红后绿」的完整修复，再把 RWMutex 这档「读多写少」的变体装上。-race 从 S1·D1 就在 Makefile 里躺着，今天它正式成为主角——本阶段的判据「能指出自己代码里的数据竞争并用 -race 证明修好了」，就在这一天兑现。

1. 一个百分百能复现的竞争

D1 的 counter++ 要碰运气才丢数，今天这个样例把冲突概率拉满：两个 goroutine 各加十万次，无锁版几乎必然丢，-race 必报：

可跑 · server/playground/s5d3/race/main.go（自带 go.mod）package main

import (
    "fmt"
    "sync"
)

type UnsafeCounter struct {
    n int            // 共享状态，裸奔
}

func main() {
    c := UnsafeCounter{}
    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 100000; j++ {
                c.n++          // 读-改-写，两个 goroutine 同时进来就互相踩
            }
        }()
    }
    wg.Wait()
    fmt.Println("c.n =", c.n)  // 经常 < 200000，且每次不一样
}

读法就一句话：「Write at」和「Previous write/read at」是同一块内存的两次无同步访问，两段堆栈直接告诉你冲突双方的代码行。修它：

可跑 · server/playground/s5d3/fixed/main.go（自带 go.mod）package main

import (
    "fmt"
    "sync"
)

type Counter struct {
    mu sync.RWMutex      // 含锁 → 整个 struct 按指针用（S1·D3 军规第 3 条）
    n  int
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()   // Lock 的下一行就是 defer Unlock——肌肉记忆
    c.n++
}

func (c *Counter) Value() int {
    c.mu.RLock()            // 只读走读锁：多个读者可同时进
    defer c.mu.RUnlock()
    return c.n
}

func main() {
    c := &Counter{}
    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 100000; j++ {
                c.Inc()
            }
        }()
    }
    wg.Add(1)
    go func() {             // 再加一个纯读者，验证读写并发也干净
        defer wg.Done()
        for j := 0; j < 1000; j++ {
            _ = c.Value()
        }
    }()
    wg.Wait()
    fmt.Println("c.Value() =", c.Value()) // 恒等于 200000
}
可跑cd server/playground/s5d3/fixed
go mod init s5d3fixed && go run -race .   # 恒 200000，零 WARNING

2. Mutex 三条纪律 + RWMutex 的账

  • defer Unlock：中途 return、panic 都不会把锁忘在手里。
  • Go 的锁不可重入：同一个 goroutine 对着已持有的锁再 Lock，当场死锁。方法 A（持锁）调方法 B（也 Lock）是经典自杀——把公共部分抽成不加锁的私有函数。
  • 含锁 struct 只按指针流转：复制 struct = 复制出一把新锁，保护失效（go vet 的 copylocks 会拦）。

RWMutex 把锁分两档：RLock 读者之间共享，Lock 写者独占（挡住一切读写）。账要这么算：读远多于写（内存仓储的 FindByID vs Save）时 RWMutex 划算；写频繁时它的内部记账反而比 Mutex 慢。两条硬规矩：不存在「读锁升级写锁」（RUnlock 后重新 Lock，中间状态可能已变）；持有写锁时再 RLock 也是死锁。

3. -race 的原理与边界：为什么「绿」不等于「没有」

-race 在编译期给每次内存访问插桩，运行时维护「happens-before」关系：两次访问同一地址、至少一个是写、又没有任何同步关系（锁、channel、WaitGroup 都算同步）——就报。边界必须背下来：

性质含义
只报「这次真跑出来的」竞争代码没被并发执行到，就不报。绿 ≠ 无竞争，红 = 铁证有竞争
零漏报换不来，零误报做得到它报出来的每一条都是真问题，不用怀疑「是不是检测器错了」
代价：慢 5-10 倍、吃内存所以生产构建不开、make test 恒开——测试就该慢一点换确定性
覆盖靠测试设计想让 -race 帮你，测试必须真的并发（D1 的 100 路 Save、今天的并发聚合）；串行测试跑一万遍也抓不到

还有一种连 -race 都来不及报的死法：fatal error: concurrent map writes——map 自带的自我保护，直接崩进程，recover 都兜不住（S1·D9）。看到它和看到 DATA RACE 同等对待：你的共享 map 裸奔了。

步骤 1 · 无锁版收集器（本地实验用，先红）

片段 · server/internal/finance/service/agg_concurrent.go 的第一版package service

import (
    "sort"
    "sync"
)

// CategoryIDs 提取去重后的分类 id，升序返回——并发版与串行版共用同一份维度清单。
func CategoryIDs(rows []AggInput) []int64 {
    seen := map[int64]bool{}
    ids := []int64{}
    for _, r := range rows {
        if !seen[r.CategoryID] {
            seen[r.CategoryID] = true
            ids = append(ids, r.CategoryID)
        }
    }
    sort.Slice(ids, func(i, j int) bool { return ids[i] < ids[j] })
    return ids
}

// SumByCategoryConcurrent 每个分类一个 goroutine，结果并进共享 map。
// ！！！第一版故意不给 totals 上锁——让 -race 抓一次现行。
func SumByCategoryConcurrent(rows []AggInput) []AggResult {
    ids := CategoryIDs(rows)
    totals := map[int64]int64{}
    var wg sync.WaitGroup
    for _, id := range ids {
        wg.Add(1)
        go func() {
            defer wg.Done()
            var sum int64
            for _, r := range rows {     // rows 只读不写，多 goroutine 共读是安全的
                if r.CategoryID == id {
                    sum += r.AmountCents
                }
            }
            totals[id] = sum              // ← 无锁写共享 map：事故就在这一行
        }()
    }
    wg.Wait()

    out := make([]AggResult, 0, len(totals))
    for id, cents := range totals {
        out = append(out, AggResult{ID: id, TotalCents: cents})
    }
    sort.Slice(out, func(i, j int) bool { return out[i].ID < out[j].ID })
    return out
}

import (
    "reflect"
    "testing"
)

// fakeRows 生成确定性假数据：4 个账户 × 6 个分类 × 每类 50 行。
// 假数据只活在测试里（S5 纪律：不碰接口、不碰库）。
func fakeRows() []AggInput {
    rows := []AggInput{}
    for acc := int64(1); acc <= 4; acc++ {
        for cat := int64(10); cat <= 15; cat++ {
            for k := 0; k < 50; k++ {
                rows = append(rows, AggInput{
                    AccountID:   acc,
                    CategoryID:  cat,
                    AmountCents: acc*1000 + cat*100 + int64(k),
                })
            }
        }
    }
    return rows
}

func TestSumByCategoryConcurrentMatchesSerial(t *testing.T) {
    rows := fakeRows()
    want := SumByCategory(rows)          // D2 的串行对照组
    got := SumByCategoryConcurrent(rows)
    if !reflect.DeepEqual(got, want) {
        t.Fatalf("并发版与串行版不一致:\ngot  %+v\nwant %+v", got, want)
    }
}

步骤 2 · 上锁修复（后绿）

只动 SumByCategoryConcurrent 两处——加一把锁、圈住写：

片段 · 修复后的差异部分totals := map[int64]int64{}
var mu sync.Mutex                 // ① 给共享 map 配站岗的
...
        // goroutine 里，totals[id] = sum 改成：
        mu.Lock()
        totals[id] = sum              // ② 临界区只圈写这一行，求和过程不持锁
        mu.Unlock()

临界区越小越好：求和那 300 次循环是各算各的，不需要锁；只有并入共享 map 的一瞬间需要。锁圈大了不出错但白排队，圈小了才既对又快。这里没用 defer Unlock 是因为临界区只有一行且不会 panic——两行的地方 defer 也行，风格统一即可。

步骤 3 · 选做：内存仓储读路径换 RWMutex

常见坑（新手 100% 会踩）

坑现象正确姿势
持锁再 Lock（重入）当场死锁，所有 goroutine asleepGo 的锁不可重入；持锁方法要调别的加锁方法，先抽无锁私有函数
锁了写没锁读-race 照样报：读写冲突也是冲突同一块共享内存的所有访问路径都要在同一把锁下
RLock 里想升级成 Lock死锁或竞态，Go 不提供升级RUnlock → Lock 重新来，且要重查状态（中间可能被人改过）
写频繁还用 RWMutex比 Mutex 还慢（内部记账更贵）读远多于写才换 RWMutex；拿不准就 Mutex
-race 绿了就宣布没竞争上线换个调度顺序照样炸绿只说明「这次没跑到」；判据是并发测试设计得够狠 + 恒开 -race
把含锁 struct 按值传递go vet 报 copylocks；锁被复制保护失效指针流转（S1·D3 军规），make lint 恒查
无锁版红着就 commit 了仓库带病过夜，违反「收工必须绿」先红后绿是本地实验流程；进 git 的永远是绿的那版

卡壳时查什么
