goroutine 与 WaitGroup：内存 repo 为什么需要锁

S1·D5 那天你往内存仓储里照抄了一把 sync.Mutex，卡片上写着「S5 正式讲」——就是今天。这 30 分钟要回答三个问题：goroutine 是什么、怎么等一群 goroutine 全部干完（WaitGroup）、以及为什么不加锁的并发写会出事。锁本身的机理（Mutex/RWMutex、-race 方法论）后天 D3 展开，今天先把「为什么需要它」亲眼看到。

今日目标

知识讲义

1. goroutine：一个关键字的并发

在任何函数调用前加 go，它就在一个新的 goroutine 里执行，当前函数不等它，继续往下走：

片段go fetchBalance(accountID)   // 起一个 goroutine 去干活，我不等
fmt.Println("我先走了")          // 立刻执行，跟上面那行没有先后保证

goroutine 由 Go 运行时调度：初始栈只有几 KB，一个进程开几十万个都撑得住，调度器把它们复用到少量操作系统线程上。给 React 开发者的对照：

JSGo差别
单线程 + 事件循环，async/await 手动让出多 goroutine 真并行，调度器自动抢占Go 不需要 await——但代价是共享数据真的会被同时碰，JS 里几乎不存在的数据竞争在 Go 里是一等公民 bug
Promise.all 等一组任务sync.WaitGroup 等一组 goroutine今天的主角
channel 没有对应物chan：goroutine 间的传送带明天 D2 讲

你其实早就在 goroutine 里了：S1·D9 讲过，net/http 为每个请求起一个 goroutine。你的每个 handler 一直跑在独立 goroutine 里——过去没出事，是因为请求之间不碰共享内存。今天开始，你要自己写「碰共享内存」的并发了。

main 函数返回，进程就结束，所有还在跑的 goroutine 当场陪葬——没有「等后台任务跑完」这回事。所以并发的第一课不是怎么起，是怎么等。

2. WaitGroup：等一群 goroutine 到齐

WaitGroup 是个计数器：Add(n) 加 n、每个 goroutine 干完 Done() 减一、Wait() 阻塞到归零。三条纪律：

  • Add 必须写在 go 之前。写在新 goroutine 里面的话，主 goroutine 可能已经 Wait() 完走人了——计数还是 0，等个寂寞。
  • defer wg.Done() 放 goroutine 第一行。中途 panic 也算干完了，计数不会卡死。
  • WaitGroup 含锁，不能复制——传指针或让闭包捕获外层变量（S1·D3 军规第 3 条，今天又见面了）。
可跑 · server/playground/s5d1/main.go（自带 go.mod，练完即弃）package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 5; i++ {
        wg.Add(1)                // 纪律一：Add 在 go 之前
        go func() {
            defer wg.Done()      // 纪律二：第一行 defer Done
            fmt.Println("worker 干完:", i)
        }()
    }
    wg.Wait()                     // 阻塞到计数归零
    fmt.Println("全部到齐，主 goroutine 收工")
}
可跑cd server/playground/s5d1
go mod init s5d1 && go run .   # S5 的练习目录命名 s5d1…s5d5，跟 S1 的 d1…d5 错开，各自独立 go.mod

闭包里直接用循环变量 i 是安全的：Go 1.22 起每轮迭代都是一个新变量。老教程让你写 go func(i int) 传参，那是 1.22 之前的补丁——本站 go.mod 是 1.24，不需要。但读老代码时要认得出这个模式。

3. 为什么内存 repo 需要锁：把 S1·D4 的警告变成事故现场

S1·D4 说过「两个 goroutine 同时读写同一个 map 直接 fatal error」。今天看更隐蔽的一种：不崩，但数字悄悄错了。counter++ 看着是一步，实际是三步：读出来、加一、写回去。两个 goroutine 同时读到 7，各自加一写回 8——两次自增只留下一次。

可跑 · server/playground/s5d1/race/main.go（独立目录，自带 go.mod）package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    counter := 0                       // 共享变量，没有任何保护——故意的
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++                  // 读-改-写三步，随时可能被另一个 goroutine 插队
        }()
    }
    wg.Wait()
    fmt.Println("counter =", counter) // 大概率 < 1000，每次跑还不一样
}
可跑go run .        # 多跑几次：987、994、1000……数字漂移就是事故本身
go run -race .  # 竞态检测器上场：WARNING: DATA RACE，两段冲突的 goroutine 堆栈直接拍脸上

这就是 S1·D5 那把锁存在的全部理由：MemoryFamilyRepo 的 data map 被所有请求共享，而每个请求都在自己的 goroutine 里。没有 mu.Lock() 站岗，轻则数字漂移，重则 fatal error: concurrent map writes——那种崩连 recover 都兜不住（S1·D9 的警告）。把上面例子修好只需三行，锁的机理 D3 细讲，今天先当成既成事实用：

片段 · race/main.go 的修法（D3 会正式展开）var mu sync.Mutex
// goroutine 里：
mu.Lock()
counter++
mu.Unlock()   // 同一时刻只有一个 goroutine 能进这三行——「临界区」

步骤 1 · 并发 Save 测试

完整 · server/internal/homeos/repository/concurrent_test.gopackage repository

import (
    "fmt"
    "sync"
    "testing"

    "homecube/internal/homeos/model"
)

// TestMemoryFamilyRepo_ConcurrentSave 用 100 个 goroutine 并行写同一份仓储。
// 没有 mu 站岗的话，-race 会当场报 DATA RACE，map 甚至可能直接 fatal。
func TestMemoryFamilyRepo_ConcurrentSave(t *testing.T) {
    repo := NewMemoryFamilyRepo()
    const n = 100

    var wg sync.WaitGroup
    for i := 0; i < n; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            f := &model.Family{ID: int64(i), Name: fmt.Sprintf("家庭-%d", i), OwnerID: int64(i)}
            if err := repo.Save(f); err != nil {
                t.Errorf("Save(%d): %v", i, err) // goroutine 里只能 Errorf，不能 Fatalf——见常见坑
            }
        }()
    }
    wg.Wait()

    for i := 0; i < n; i++ {
        if _, err := repo.FindByID(int64(i)); err != nil {
            t.Errorf("FindByID(%d): %v", i, err) // 100 条一条都不能少
        }
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
wg.Add(1) 写在 goroutine 里面Wait() 提前返回，任务被拦腰截断；或报 negative WaitGroup counterAdd 永远在 go 之前、由发起方执行
起了 goroutine 就忘 Waitmain 返回，后台任务集体陪葬，输出时有时无每个 go 都要回答「谁等它」：WaitGroup、channel 或 ctx（D2/D4）
goroutine 里调 t.Fatalf测试行为诡异：Fatalf 只结束当前 goroutine，主测试继续跑goroutine 里一律 t.Errorf；要提前终止用 channel 通知主 goroutine
把 WaitGroup 按值传给函数go vet 警告 copylocks；计数对不上，Wait 永挂或早退传 *sync.WaitGroup，或让闭包直接捕获外层变量
以为 counter++ 是原子的数字悄悄变小，测试「偶尔」红读-改-写三步就要保护；D3 给完整方法论
测试偶尔绿就以为没竞争调度顺序天天变，今天绿明天红只认 -race；本站 make test 恒带 -race，这就是 S1·D1 把它写进 Makefile 的原因
照老教程给闭包传 i不算错，但多余Go 1.22 起循环变量每轮新建；读老代码认识它，写新代码不必跟

今日名词卡

术语一句话解释
goroutinego f() 起的轻量执行流，由运行时调度到线程上；名词卡里躺了四个阶段，今天正式上岗
调度器（GMP）把海量 goroutine 复用到少量 OS 线程的运行时机制；本课程不展开，知道「开十万个不心疼」即可
sync.WaitGroupgoroutine 计数器：Add 加、Done 减、Wait 阻塞到归零；含锁不可复制
数据竞争（data race）两个 goroutine 无同步地碰同一块内存且至少一个是写；未定义行为，可能不崩但结果错
临界区Lock 与 Unlock 之间那段「同一时刻只许一人进」的代码
sync.Mutex互斥锁，给共享内存站岗。机理与 RWMutex 后天 D3 正式讲
-race竞态检测器：只报「这次真跑出来的」竞争，绿了不等于没有（D3 展开）
并发 vs 并行并发是「同时应对多件事」的结构，并行是「同时执行」的物理状态；单核也能并发
channelgoroutine 间传数据的管道。明天 D2 正式讲
context取消与超时的信号线。D4 正式讲，今天只需知道它存在
