channel 与 select：goroutine 之间不共享、只传递

昨天靠锁保护共享内存，今天学另一条路：干脆不共享——数据从一个 goroutine 手里经 channel「递」给另一个，任一时刻只有一个持有者。Go 有句谚语：不要通过共享内存来通信，而要通过通信来共享内存。今天把 channel 的收发规则、close 与 range、select 多路复用一次立起来，并在 finance/service 落下两个 struct 与串行版聚合——它是本周所有并发版本的对照组。

今日目标

知识讲义

1. channel：带类型的传送带

make(chan T) 造一条传送带，ch <- v 放上去，v := <-ch 取下来。核心规则只有「谁等谁」：

操作无缓冲 make(chan T)带缓冲 make(chan T, 3)
发送 ch <- v阻塞，直到有人接收——一手交钱一手交货缓冲没满就不阻塞；满了才等
接收 <-ch阻塞，直到有人发送缓冲空了就等
close(ch) 后接收立刻返回已缓冲的值；取完后返回零值，v, ok := <-ch 的 ok 为 false
close(ch) 后发送panic。重复 close 也 panic——close 是发送方的专属动作，且只做一次

for v := range ch 会一直收，直到 channel 被 close——所以「发完了」必须由发送方显式 close，接收方才知道该收工。方向可以写进类型里：chan<- int 只能发、<-chan int 只能收，函数签名里用上，编译器帮你拦住手滑。

2. select：同时等多条传送带

select 长得像 switch，等的却是多个 channel 操作：哪个先就绪走哪个；同时就绪则随机挑一个（防止饿死）；带 default 就变成「都没就绪立刻返回」（非阻塞探测）；不带 default 就阻塞到有一个就绪。配 time.After 就是最经典的超时模式：

可跑 · server/playground/s5d2/main.go（自带 go.mod）package main

import (
    "fmt"
    "time"
)

func main() {
    results := make(chan string, 3)       // 带缓冲：3 个 worker 交作业时不用等谁在收
    names := []string{"分类A", "分类B", "分类C"}
    for _, name := range names {
        go func() {
            time.Sleep(100 * time.Millisecond) // 假装在干活
            results <- name + " 聚合完成"
        }()
    }

    for i := 0; i < len(names); i++ {          // 收满 3 份作业就走，不 range——没人 close
        select {
        case r := <-results:
            fmt.Println("收到:", r)
        case <-time.After(2 * time.Second):
            fmt.Println("超时：有 worker 没交作业")
            return
        }
    }
    fmt.Println("三份作业齐了（注意顺序每次可能不同）")
}
可跑cd server/playground/s5d2
go mod init s5d2 && go run .   # 多跑几次：完成的顺序是乱的——并发没有先后保证

D4 会把 time.After 那一路换成 ctx.Done()——同样的 select 骨架，超时信号从「一次性定时器」升级为「可传播、可级联的取消信号」。今天先把形状练熟。

3. channel 还是 Mutex：先给直觉，D3 给判据

  • 传递数据的所有权（作业队列、结果收集、worker 间接力）→ channel。
  • 保护一份大家都要就地读写的状态（内存 map、计数器、缓存）→ Mutex。

两条路不互斥：今天的增量里，串行版用普通 map；D3 的并发版会用 Mutex 保护汇总 map；D5 的 worker pool 会用 channel 派活、再汇总。同一个问题里两者各司其职是常态。

4. 今日增量的业务形状：聚合的输入与输出

S6 的报表接口要做「按分类/按账户汇总金额」。本阶段不碰接口，只把它的并发骨架练出来：输入是一批流水行（金额一律 *_cents int64，S3 起的老规矩），输出是每个维度一个合计。今天先落 struct 与串行版——串行版是本周所有并发版本的对照组：并发算出来的结果必须和它分毫不差，这是 D6 验收的第一条。

步骤 1 · service 包与串行聚合

完整 · server/internal/finance/service/agg.gopackage service

import "sort"

// AggInput 是被聚合的一行流水：账户、分类、金额（分）。
// S5 只有并发骨架；S6 起由报表 handler 从库里取真行喂进来。
type AggInput struct {
    AccountID   int64
    CategoryID  int64
    AmountCents int64
}

// AggResult 是一个维度（某分类或某账户）的聚合结果。
type AggResult struct {
    ID         int64
    TotalCents int64
}

// SumByCategory 按分类分组求和：串行版，S5 全期的对照组。
// 输出按 ID 升序——map 遍历顺序是乱的（S1·D4），不排序就没法和并发版对拍。
func SumByCategory(rows []AggInput) []AggResult {
    totals := map[int64]int64{}
    for _, r := range rows {
        totals[r.CategoryID] += r.AmountCents
    }
    out := make([]AggResult, 0, len(totals))
    for id, cents := range totals {
        out = append(out, AggResult{ID: id, TotalCents: cents})
    }
    sort.Slice(out, func(i, j int) bool { return out[i].ID < out[j].ID })
    return out
}

import (
    "reflect"
    "testing"
)

func TestSumByCategory(t *testing.T) {
    tests := []struct {
        name string
        rows []AggInput
        want []AggResult
    }{
        {"空输入", nil, []AggResult{}},
        {"单分类多行", []AggInput{
            {AccountID: 1, CategoryID: 10, AmountCents: 1500},
            {AccountID: 2, CategoryID: 10, AmountCents: 2500},
        }, []AggResult{{ID: 10, TotalCents: 4000}}},
        {"多分类乱序", []AggInput{
            {AccountID: 1, CategoryID: 20, AmountCents: 100},
            {AccountID: 1, CategoryID: 10, AmountCents: 200},
            {AccountID: 2, CategoryID: 20, AmountCents: 300},
        }, []AggResult{{ID: 10, TotalCents: 200}, {ID: 20, TotalCents: 400}}},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := SumByCategory(tt.rows); !reflect.DeepEqual(got, tt.want) {
                t.Fatalf("SumByCategory() = %+v, want %+v", got, tt.want)
            }
        })
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
range 一个没人 close 的 channel收完已有的值后永久阻塞，测试超时死掉发送方发完必须 close；或像今天例子一样按已知数量收
向已 close 的 channel 发送panic: send on closed channel规矩：谁发送谁 close，只 close 一次；多个发送方就别 close，交给计数（D5 的 closer goroutine 模式）
无缓冲 channel 发了没人收发送方 goroutine 永久阻塞——泄漏发送前先回答「谁在另一头收」；收不到就用带缓冲 + select 超时
以为带缓冲能保顺序输出顺序依旧随调度漂移缓冲只解决「等不等」，不解决「谁先到」；要有序就收完再排序（对照组已示范）
select 一个 case 都不写编译不过或空转select 必须至少一个 case；想非阻塞加 default
在循环里滥用 time.After每轮都造一个定时器，高频循环下内存堆积低频场景无所谓；高频等 D4 换 ctx，或复用 time.Timer
用 channel 硬做互斥「令牌 channel」能跑但绕晕队友保护就地读写的状态用 Mutex（D3）；channel 用于传递所有权

今日名词卡

术语一句话解释
channel（chan）goroutine 间的类型化传送带；收发即同步点
无缓冲 vs 带缓冲无缓冲 = 面对面交接（双方必须同时到场）；带缓冲 = 放进取出可异步，满了/空了才阻塞
close发送方宣布「没有更多了」；接收方靠它退出 range。close 后发送 = panic
comma-ok 接收v, ok := <-ch：ok 为 false 表示 channel 已关且取空
方向类型chan<- T 只发、<-chan T 只收；签名即文档，编译器站岗
select等多个 channel 操作，谁先就绪走谁，同时就绪随机挑；default 变非阻塞
time.After返回一个只读 channel，到点送一个值——select 里的超时兜底
goroutine 泄漏goroutine 阻塞在永远等不到的收发上，再也回不来；D4 的 ctx 是解药
对照组（serial baseline）串行正确版本；并发版必须与它结果全等，否则并发白做
errgroup带错误传播与取消的 WaitGroup 增强版。D5 正式讲

卡壳时查什么

正文自足，只有两种情况出去查：

  • close 后收发行为的权威描述：Go 语言规范 · Channel types（可选，表格背不下来时来对答案）。
  • select 的完整语义：Go 语言规范 · Select statements（可选，重点读「uniformly at random」那句）。

卡死类 bug 的调试顺序：先看进程还活着吗（阻塞死锁 Go 会直接报 all goroutines are asleep - deadlock!），再数一遍「每个发送有没有对应的接收、每个 close 是不是恰好一次」。channel 的死锁九成是收发账目对不上。
