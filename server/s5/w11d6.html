周六 · S5 收口：CI 最小版与判据自测

十二张卡走到头。这两周你亲手做过的事：让 100 路 goroutine 打一个内存仓储（D1）、用 channel 和 select 传数据（D2）、抓了一次真数据竞争再修掉（D3）、给聚合链路装上超时（D4）、池化 + errgroup + safego（D5）、串成完整 Aggregate（D6）、批量导入的部分失败语义（D7）、全站日志结构化并串上 request-id（D8）、SIGTERM 三步曲（D9）、config 定稿（D10）、50 路并发接口测试（D11）。今天三件事：把「记得跑 -race」变成 CI 的自动动作、干净检出验证仓库不依赖你本机、判据六题费曼自测。收口日不写新代码——CI 那一小段 YAML 除外。

今日目标

知识讲义

1. 为什么 CI 是 S5 的收口动作

-race 全量回归靠的是什么？靠你记得敲 make test。凡是靠记性的纪律，都会在某个赶时间的晚上失守——而数据竞争恰恰是「测试恰好绿了」也照样存在的病（D11）。CI（持续集成）把记性换成机器：每次 push，云端自动跑一遍 build + test -race，红了直接亮在你的提交旁边。从今天的判据（s5o6）起，「CI 绿灯」成为每个收工日的硬门槛。

最小版纪律：只做两步——go build ./... 和 go test -race -count=1 ./...。不加覆盖率、不加 lint 矩阵、不加多版本 Go——这些是 S8 部署季的升级项（届时还会加 docker compose 全套复现）。CI 第一天就贪多，的下场是红灯没人看得懂、三天后没人再看。

为什么现在不需要数据库服务？本阶段所有测试——并发聚合、导入解析、slog、关闭、50 路 /healthz——全是纯函数或 httptest，不碰真 DB，CI 里自然不用起 Postgres。S6 给财务接口接上 DB 测试后，workflow 里要加 postgres 服务容器——那是 S6 的增量，今天不预支。

2. workflow 逐行读

片段含义
on: push / pull_request触发条件：推任何分支、开任何 PR 都跑——收口期不挑分支
runs-on: ubuntu-latest云端执行环境（runner）；本机是别的系统也无所谓，干净 Linux 才算数
working-directory: serverGo 模块在 server/ 子目录——命令都在那里跑，和 Makefile 的视角一致
actions/checkout@v4官方动作：把你的仓库检出到 runner 上
actions/setup-go@v5 + go-version: "1.24"官方动作：装指定版本 Go；与 go.mod 的声明对齐
go test -race -count=1 ./...-count=1 关掉测试缓存——CI 每次必须真跑，缓存绿不算绿

3. 干净检出：抓两类「本机才绿」的事故

S1 收口日立下的传统（今天是第三次执行）：git clone 到 /tmp 临时目录跑三件套。它专抓两类事故：① 忘了提交的文件——本机有、仓库没有，CI 与干净检出都会红；② 依赖了本机环境——手动 export 过的变量、装在本机却没进声明的工具。S8 会升级成 docker compose 全套复现，手法同源。

4. 费曼自测：判据只认「讲出来」

规则不变：不看任何资料（包括本站），对着空气把题目讲一遍。磕磕绊绊 = 没懂，回对应日卡重读再讲。「读了一遍感觉会了」是认出来（recognition），判据只认讲出来（recall）。六道题就是 S5 阶段总览的判据清单：

步骤 1 · CI workflow 最小版

完整 · .github/workflows/ci.yml（仓库根目录；S8 升级为全量 -race + 覆盖率 + compose 复现）name: ci

on:
  push:
  pull_request:

jobs:
  build-test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: server
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.24"
      - name: build
        run: go build ./...
      - name: test (-race)
        run: go test -race -count=1 ./...

落盘后先在本地过一遍同等命令（cd <你的学习仓根目录>/server && go build ./... && go test -race -count=1 ./...），本地不绿就别推——CI 不是替你调试的，是替你守门的。

常见坑（收口日专属）

坑现象正确姿势
本机绿、CI 红忘提交的文件、本机 export 过的变量在 runner 上不存在干净检出验证就是抓这个的；红了先看 CI 日志缺什么，再回本机 git status
测试缓存吃掉 -race全部 (cached)，一秒「跑」完，其实什么都没测CI 命令必须带 -count=1；本机 make test 同理
CI 命令与 Makefile 语义漂移本机 make test 带 -race，CI 里只写了 go test ./...两步命令与 Makefile 对齐：build ./... 与 test -race -count=1 ./...
CI 第一天就贪多覆盖率 + lint 矩阵 + 多版本 Go，红灯一片没人看得懂最小版两步；S8 再升级——门槛先立起来，再慢慢加高
workflow 只在本地没推远端Actions 页空空如也，以为 CI 坏了CI 只认远端仓库：git push 之后去 Actions 页看运行记录
自测表全勾「应该会」认出来冒充讲出来，判据形同虚设只认开口讲；卡壳点写进明细，回卡重读再讲一遍
收官提交夹带私货git add -A 把临时脚本、本地配置一起打包按名 add 三个（类）文件；git status 核对后再 commit

卡壳时查什么

正文自足，只有两种情况出去查：

  • workflow 语法细节：GitHub Docs · Writing workflows（可选；本站这 20 行已覆盖最小版全部语法）。
  • CI 红灯的具体报错：先看 Actions 日志里红的那一步的完整输出，把它复制到本机复现（go test -race -count=1 ./...）——CI 红、本机也红，就回对应日卡；CI 红、本机绿，九成是干净检出那两类事故。

费曼自测卡壳没有捷径：回表里指的日卡，重读「知识讲义」一节，合上再讲。第二遍还卡，就把卡住的那句话抄进 s5-review.md 的明细里——写下来的困惑比讲过去的顺畅更值钱。
