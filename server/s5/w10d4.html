context：超时与取消

D2 的 worker 要是卡住不交作业，select + time.After 只能让等的人先走，干活的 goroutine 还傻在原地——这就是 goroutine 泄漏。今天学真正的解药：context，一根从调用源头贯穿到每个 goroutine 的信号线，超时或取消时沿线广播「都别干了」。它是四个「S1 名词卡常客」里的最后一个，也是 S6 报表聚合、S8 优雅关闭都要用到的地基。

今日目标

知识讲义

1. ctx 是什么：一根可以掐断的信号线

context.Context 是个只有四个方法的接口，今天只用其中两个：

片段 · 只需读type Context interface {
    Done() <-struct{}          // 被取消/超时时，这个 channel 会关闭——D2 的知识接上了
    Err() error                // 为什么结束：context.Canceled 或 context.DeadlineExceeded
    Deadline() (time.Time, bool) // 有没有、什么时候到期
    Value(key any) any          // 请求域元数据（如 request_id），不是传参通道
}

三种造法：context.Background() 是根（main、测试里用）；WithCancel 给你一根手动掐断的线；WithTimeout 到点自动掐。后两个都返回 (ctx, cancel) 一对——cancel 必须 defer 调用，哪怕你笃定会超时：它负责释放定时器等资源，不 defer 就是泄漏。

可跑 · server/playground/s5d4/main.go（自带 go.mod）package main

import (
    "context"
    "fmt"
    "time"
)

// worker 不停干活往外送，直到信号线被掐断。
func worker(ctx context.Context, out chan<- int) {
    for {
        select {
        case <-ctx.Done():                 // 检查点：信号线断了就回家
            fmt.Println("worker 收工:", ctx.Err())
            return
        case out <- 42:                    // 干活：送一个结果
            time.Sleep(50 * time.Millisecond)
        }
    }
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
    defer cancel()                        // 肌肉记忆：WithTimeout 的下一行就是 defer cancel

    out := make(chan int)
    go worker(ctx, out)

    got := 0
    for {
        select {
        case v := <-out:
            got += v
        case <-ctx.Done():
            fmt.Println("超时收工:", ctx.Err(), "，共收到", got)
            return                            // worker 也在同一根线上，会自己退出——不泄漏
        }
    }
}
可跑cd server/playground/s5d4
go mod init s5d4 && go run .   # 输出：超时收工: context deadline exceeded ，共收到 1xx 附近

对比 D2 的 time.After 版：那边超时后 worker 还阻塞在 results <- … 上永远回不来；这边双方听同一根信号线，主 goroutine 一走，worker 下一个 select 就收到 Done 自己收工。这就是「取消要可传播」的意义。

2. 三站链路与 ctx 树

  • 创建：请求入口（handler 里用 c.Request.Context()，客户端断开它会自动取消）、测试里 context.Background() 派生 WithTimeout。
  • 传递：ctx 永远是第一个参数，func SumByCategoryCtx(ctx context.Context, …)；不存进 struct、不用 nil（拿不准传什么就 context.TODO()，它是「欠着一根线」的显式欠条）。
  • 检查点：阻塞处用 select { case <-ctx.Done(): … }；长循环里每隔一段查一次 ctx.Err() != nil。取消是协作式的：ctx 不会替你杀 goroutine，不检查点的代码永远感知不到取消。

ctx 是树：从 Background 派生 WithTimeout，再从它派生子 ctx——掐断任何一个节点，它整棵子树全部断开。这就是「一个请求超时，它派生的所有聚合 goroutine 集体收工」的原理，也是 D5 errgroup 的底层机制。

3. 超时之后对外说什么

ctx.Err() 只有两个值：context.Canceled（手动取消/客户端断开）与 context.DeadlineExceeded（超时）。映射到全站错误契约：聚合超时属服务器侧没干完活，业务码走 5000；HTTP 状态可以按语义细化成 504（契约允许「HTTP 状态按语义细化，业务码仍走唯一表」）。包装时用 %w 把 ctx.Err() 裹进去（S1·D4 的手艺），上层 errors.Is(err, context.DeadlineExceeded) 认得出来。

本站红线（写进判据的）：并发组与对照组不共享同一条超时 ctx。对拍测试里，超时用例的 ctx 已经被掐死了，对照组再用它就「莫名其妙」立刻失败，你会误判成聚合逻辑错了。对照组永远自己拿一条干净的 context.Background()。

步骤 1 · ctx 贯穿的单分类求和

完整 · server/internal/finance/service/agg_ctx.gopackage service

import (
    "context"
    "fmt"
    "time"
)

// sumOneCategory 对单个分类求和；rows 只读，可多 goroutine 共享。
// time.Sleep 模拟一次慢 IO——S6 起这里会是真查询，检查点的位置不变。
func sumOneCategory(ctx context.Context, id int64, rows []AggInput) (AggResult, error) {
    select {                            // 开工前先听一次信号：已取消就别白干
    case <-ctx.Done():
        return AggResult{}, fmt.Errorf("聚合分类 %d: %w", id, ctx.Err())
    default:
    }
    time.Sleep(20 * time.Millisecond) // 模拟 IO

    var total int64
    for _, r := range rows {
        if r.CategoryID == id {
            total += r.AmountCents
        }
    }
    return AggResult{ID: id, TotalCents: total}, nil
}

// SumByCategoryCtx 串行遍历分类，但 ctx 已贯穿——D5 把它池化成真并发。
func SumByCategoryCtx(ctx context.Context, rows []AggInput) ([]AggResult, error) {
    out := []AggResult{}
    for _, id := range CategoryIDs(rows) {
        res, err := sumOneCategory(ctx, id, rows)
        if err != nil {
            return nil, err            // 一处超时，整批中止——部分结果没有意义
        }
        out = append(out, res)
    }
    return out, nil                    // CategoryIDs 已排序，输出天然有序
}

步骤 2 · 超时中止测试 + 对照组（各自独立 ctx）

完整 · server/internal/finance/service/agg_ctx_test.gopackage service

import (
    "context"
    "errors"
    "testing"
    "time"
)

func TestSumByCategoryCtx_Timeout(t *testing.T) {
    rows := fakeRows()                    // D3 的确定性假数据：6 个分类 × 每类 20ms，串行要 120ms
    ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
    defer cancel()

    _, err := SumByCategoryCtx(ctx, rows)
    if !errors.Is(err, context.DeadlineExceeded) {
        t.Fatalf("err = %v, want DeadlineExceeded", err)
    }
}

func TestSumByCategoryCtx_Success(t *testing.T) {
    rows := fakeRows()
    // 对照组纪律：这里自己拿一条全新的 Background，绝不复用上面那条已超时的 ctx。
    got, err := SumByCategoryCtx(context.Background(), rows)
    if err != nil {
        t.Fatalf("不该出错: %v", err)
    }
    if want := SumByCategory(rows); !equalResults(got, want) {
        t.Fatalf("ctx 版与串行对照组不一致:\ngot  %+v\nwant %+v", got, want)
    }
}

// equalResults 逐项对拍。不用 reflect.DeepEqual 是为了失败时能打出具体哪一项歪了。
func equalResults(got, want []AggResult) bool {
    if len(got) != len(want) {
        return false
    }
    for i := range got {
        if got[i] != want[i] {
            return false
        }
    }
    return true
}

时序账算给你看：6 个分类 × 20ms 串行 ≈ 120ms，超时设 50ms——第 3 个分类开工前信号线必断，测试确定性命中超时分支，不靠运气。设计超时测试的诀窍就是这个：让「干活总时长」明显大于「超时预算」。

常见坑（新手 100% 会踩）

坑现象正确姿势
超时 ctx 共享给对照组对照用例「莫名」秒失败，误判聚合逻辑有 bug本站红线：每个用例自己创建 ctx，谁也不借谁的
WithTimeout 不 defer cancelgo vet 报 lostcancel；定时器资源泄漏下一行就 defer cancel()，没有例外
把 ctx 存进 struct 字段生命周期错位：struct 活得比请求长，拿着死线早过的 ctx 干活ctx 只做参数流动；struct 里出现的都该是数据
不写检查点取消了但 goroutine 照跑到底，超时形同虚设取消是协作式的：阻塞处 select Done，长循环定期查 Err
吞掉 ctx.Err() 返回 nil上层以为成功，拿着半截结果继续算中止就是中止：return nil, fmt.Errorf("…: %w", ctx.Err())
用 WithValue 传业务参数签名失去文档性，类型全变 any，编译期零保护Value 只放请求域元数据（request_id 这类）；业务参数老老实实写进签名
超时预算层层加码外层 3s、内层各 5s，外层早死了内层还在跑子 ctx 的 deadline 只会更早不会更晚——预算从源头定，派生自动收紧

卡壳时查什么

正文自足，只有两种情况出去查：

  • ctx 的官方使用范式：context 包文档（可选，包顶部那段注释就是官方的三站链路说法）。
  • 取消传播的设计思路：Go 官方博客的 "Go Concurrency Patterns: Context"（可选，读图不读码）。

调试顺序：超时类问题先画时序账——每个环节花多久、预算多少、在哪一站断的。把 ctx.Err() 的值打出来（Canceled 还是 DeadlineExceeded，两回事），再决定是加预算还是砍工作量。 goroutine 疑似泄漏时用 runtime.NumGoroutine() 在测试前后各打一次，数字不回落就是漏了。
