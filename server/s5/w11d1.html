批量导入流水：部分失败语义

新的一周从批量导入开始。它是上周知识的反面应用：报表聚合用 errgroup 式「一损俱损」，导入却必须收集每一行的下场——第 3 行金额是负数，不该让第 4 行陪葬，更不该被静默吞掉。「部分失败语义」这三条不变式（行行有结果、失败必带行号与码、坏行不拖累好行）今天用并发骨架立起来。老规矩：不注册路由、不写库——导入的落库与挂载点属 S6 的流水域，今天只做「解析 → 校验 → 报错」这半程。

今日目标

知识讲义

1. 部分失败语义：整批不静默吞

批量操作有三种收场方式，导入必须选第三种：

语义行为适用
全或无（事务）一行坏，整批回滚转账这类一致性优先的写；导入选它 = 用户改一行要重传整份文件
快速失败（errgroup）第一个错误出现即取消其余聚合这类「缺一块就没意义」的读；导入选它 = 用户只看到第一个错，修完再传又爆第二个，折磨人
部分失败（今天）行行独立判定，好坏各自记账，最后交完整报告导入：用户一次拿到全部问题清单，改一遍就能全对

「静默吞」是部分失败的头号天敌：if err != nil { continue } 一行代码就能把用户的 200 条数据吞成 187 条还报「导入成功」。三条不变式钉死它：

  • 行行有结果：Total == len(Accepted) + len(Failures)，测试里直接断言这个等式。
  • 失败必带行号与码：没有行号的错误等于没说；码只许用全站唯一错误码表里的——行级失败也是接口语言的一部分。
  • 坏行不拖累好行：任何一行的错误都不改变其他行的判定结果。

2. 行级错误码怎么选（只用唯一表）

行的毛病码常量（S1·D4 已落）
段数不对、整数解析失败等格式问题1004response.CodeInvalidParam
金额 ≤ 04001response.CodeAmountInvalid
分类 id 不在合法集合里1001response.CodeNotFound

注意最后一条的口径：越权与不存在同形的纪律（S4）在这里的体现是——不管这个分类是「真没有」还是「别的家庭的」，行级报告一律 1001「分类不存在」，不泄露存在性。S6 接线时，合法分类集合从分类仓储按 WHERE family_id = ? 取，天然只有本家庭的。

3. 「各写各的格子」：一种不需要锁的并发收集

上周收集结果用了两条路：Mutex 保护共享 map（D3）、channel 汇总（D5）。今天给第三条：预分配一个与输入等长的结果切片，每个 goroutine 只写自己索引的槽位。不同索引是不同的内存地址，各写各的、互不相碰——没有共享写就没有竞争，-race 自然安静。收集完再串行压缩成 Accepted/Failures 两摞，输出天然按行号有序，连排序都省了。适用条件背下来：任务数事先已知、结果与任务一一对应。任务数未知（流式读文件）就回 channel 那路。

那为什么还要并发？校验是纯 CPU 活，十行八行确实不值得。但 S6 的真实导入里每行要查分类、查账户（IO），几千行文件串行校验会让请求超时——今天把骨架立对，到时候只换 validateLine 的内脏。这是「骨架先行」的又一次演练。

步骤 1 · 三件套 struct 与逐行校验

完整 · server/internal/finance/service/import.gopackage service

import (
    "strconv"
    "strings"
    "sync"

    "homecube/pkg/response"
)

// ImportRow 是一行解析合格的导入数据。金额一律 *_cents int64（S3 起的老规矩）。
type ImportRow struct {
    Line        int
    OccurredAt  string // 原样保留日期串；入库解析属 S6，今天只校验格式段数
    CategoryID  int64
    AmountCents int64
}

// ImportFailure 是一行的失败下场：行号 + 全站唯一表里的业务码 + 人话。
type ImportFailure struct {
    Line    int    `json:"line"`
    Code    int    `json:"code"`
    Message string `json:"message"`
}

// ImportReport 是整批的报告。不变式：Total == len(Accepted) + len(Failures)。
type ImportReport struct {
    Total    int             `json:"total"`
    Accepted []ImportRow     `json:"accepted"`
    Failures []ImportFailure `json:"failures"`
}

// lineOutcome 是单行判定的中间形态：ok 决定进哪一摞。
type lineOutcome struct {
    row     ImportRow
    failure ImportFailure
    ok      bool
}

func failLine(lineNo, code int, msg string) lineOutcome {
    return lineOutcome{failure: ImportFailure{Line: lineNo, Code: code, Message: msg}}
}

// validateLine 单行判定：格式 1004、金额 4001、分类 1001——只用唯一表里的码。
func validateLine(lineNo int, raw string, knownCategories map[int64]bool) lineOutcome {
    fields := strings.Split(raw, ",")
    if len(fields) != 3 {
        return failLine(lineNo, response.CodeInvalidParam, "应为 occurred_at,category_id,amount_cents 三段")
    }
    categoryID, err := strconv.ParseInt(strings.TrimSpace(fields[1]), 10, 64)
    if err != nil {
        return failLine(lineNo, response.CodeInvalidParam, "分类 id 必须是整数")
    }
    amountCents, err := strconv.ParseInt(strings.TrimSpace(fields[2]), 10, 64)
    if err != nil {
        return failLine(lineNo, response.CodeInvalidParam, "金额必须是整数（分）")
    }
    if amountCents <= 0 {
        return failLine(lineNo, response.CodeAmountInvalid, "金额必须大于 0")
    }
    if !knownCategories[categoryID] {
        // 「真没有」与「不是本家庭的」同形返回 1001——不泄露存在性
        return failLine(lineNo, response.CodeNotFound, "分类不存在")
    }
    return lineOutcome{row: ImportRow{
        Line:        lineNo,
        OccurredAt:  strings.TrimSpace(fields[0]),
        CategoryID:  categoryID,
        AmountCents: amountCents,
    }, ok: true}
}

步骤 2 · ParseImport：各写各的格子

完整 · server/internal/finance/service/import.go（续，同一个文件）// ParseImport 并发校验整批行，返回完整报告。
// 并发模式：预分配 outcomes，每个 goroutine 只写自己索引的槽位——
// 不同索引是不同内存地址，无共享写即无竞争，不需要锁也不需要 channel。
func ParseImport(lines []string, knownCategories map[int64]bool) *ImportReport {
    outcomes := make([]lineOutcome, len(lines))
    var wg sync.WaitGroup
    for i, line := range lines {
        wg.Add(1)
        go func() {
            defer wg.Done()
            outcomes[i] = validateLine(i+1, line, knownCategories) // 行号从 1 起，跟用户的文件对齐
        }()
    }
    wg.Wait()

    rep := &ImportReport{Total: len(lines), Accepted: []ImportRow{}, Failures: []ImportFailure{}}
    for _, o := range outcomes {   // 串行压缩：天然按行号有序，不用排序
        if o.ok {
            rep.Accepted = append(rep.Accepted, o.row)
        } else {
            rep.Failures = append(rep.Failures, o.failure)
        }
    }
    return rep
}

步骤 3 · 部分失败测试：坏 4 行，行行有下场

完整 · server/internal/finance/service/import_test.gopackage service

import (
    "testing"

    "homecube/pkg/response"
)

func TestParseImportPartialFailure(t *testing.T) {
    known := map[int64]bool{10: true, 11: true}
    lines := []string{
        "2026-01-01,10,1500",   // 行1 好
        "2026-01-02,11,2500",   // 行2 好
        "2026-01-03,10,-5",     // 行3 坏：金额 ≤ 0 → 4001
        "2026-01-04,99,800",    // 行4 坏：分类不存在 → 1001
        "2026-01-05,10,1200",   // 行5 好
        "2026-01-06,11",        // 行6 坏：段数不对 → 1004
        "2026-01-07,10,900",    // 行7 好
        "2026-01-08,11,abc",    // 行8 坏：金额不是整数 → 1004
        "2026-01-09,10,700",    // 行9 好
        "2026-01-10,11,600",    // 行10 好
    }

    rep := ParseImport(lines, known)

    // 不变式一：行行有结果，整批不静默吞
    if rep.Total != len(rep.Accepted)+len(rep.Failures) {
        t.Fatalf("Total=%d 但 Accepted=%d + Failures=%d 对不上", rep.Total, len(rep.Accepted), len(rep.Failures))
    }
    // 不变式二：坏行不拖累好行——6 好 4 坏，一条不多一条不少
    if len(rep.Accepted) != 6 || len(rep.Failures) != 4 {
        t.Fatalf("Accepted=%d(want 6) Failures=%d(want 4)", len(rep.Accepted), len(rep.Failures))
    }
    // 不变式三：失败必带行号与码，且码来自唯一表
    wantFailures := []ImportFailure{
        {Line: 3, Code: response.CodeAmountInvalid},
        {Line: 4, Code: response.CodeNotFound},
        {Line: 6, Code: response.CodeInvalidParam},
        {Line: 8, Code: response.CodeInvalidParam},
    }
    for i, want := range wantFailures {
        got := rep.Failures[i]
        if got.Line != want.Line || got.Code != want.Code {
            t.Fatalf("Failures[%d] = {行%d 码%d}, want {行%d 码%d}", i, got.Line, got.Code, want.Line, want.Code)
        }
        if got.Message == "" {
            t.Fatalf("行 %d 的失败没有人话 message", got.Line)
        }
    }
    // 输出有序：失败按行号升序（各写各的格子 + 串行压缩的自然结果）
    for i := 1; i < len(rep.Failures); i++ {
        if rep.Failures[i-1].Line >= rep.Failures[i].Line {
            t.Fatalf("Failures 未按行号升序")
        }
    }
}

func TestParseImportEmpty(t *testing.T) {
    rep := ParseImport(nil, nil)
    if rep.Total != 0 || len(rep.Accepted) != 0 || len(rep.Failures) != 0 {
        t.Fatalf("空输入应得到空报告: %+v", rep)
    }
}

S6 接线时，这份 ImportReport 会原样进统一响应信封的 data：HTTP 200 + code 0——「有坏行」不是接口失败，报告本身就是成功的响应；用户界面按 failures 逐行标红。真正 400 + 1004 的是「整个文件没法读」这类批级错误，两层语义别搅在一起。

常见坑（新手 100% 会踩）

坑现象正确姿势
if err != nil { continue }坏行凭空消失，Total 对不上账错误也是结果：进 Failures，带行号带码
只报「失败了 N 行」用户不知道是哪 N 行、为什么行号 + 码 + 人话三件套缺一不可
并发 append 共享切片不加锁-race 报 DATA RACE，或数据悄悄丢append 不是原子的；用「各写各的格子」或 Mutex/channel
自造行级错误码（如 6001）错误码表失去唯一性，前端映射表崩了行级码也只从全站唯一表里选：1004/4001/1001
拿 errgroup 收集行错误只拿到第一个错，其余行白跑快速失败与全量收集是两种语义；导入永远选后者
把「有坏行」当成接口失败返回 400好行也一起被拒，用户以为全没导入批级 200 + 报告；400 留给「文件根本没法读」
行号从 0 起用户对着编辑器的第 1 行找「行 0」行号永远跟用户的文件对齐：从 1 起

术语一句话解释
部分失败语义行行独立判定、好坏各自记账、交完整报告；批量导入的唯一正确姿势

卡壳时查什么

正文自足，只有两种情况出去查：

  • ParseInt 的签名细节：strconv · ParseInt（可选，bitSize 64 对应 int64）。
  • 错误码常量对不上：翻你仓库的 server/pkg/response/code.go（S1·D4 落的全表）——数值是唯一权威，常量名以仓里为准。

部分失败类 bug 的调试顺序：先断言不变式一（Total 等式），它红了说明有行被吞；再对 Failures 逐条打印行号与码，跟输入文件逐行比对。把「账」对齐了，逻辑错误藏不住。
