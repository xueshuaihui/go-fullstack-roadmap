并发模式：worker pool 与 errgroup

D3 的并发版是「每个分类一个 goroutine」——6 个分类没事，6 万个分类就是 6 万个 goroutine 一起冲向数据库。今天学限流：固定几个 worker 排队消费任务，这就是 worker pool。再学它的成品库版本 errgroup：WaitGroup + 「第一个错误 + 级联取消」。最后兑现 S1·D9 欠下的一条纪律——自己起的 goroutine 要在边界装 recover。

今日目标

知识讲义

1. worker pool：把「开多少」从数据量手里夺回来

形状固定：一条 jobs channel 派活，N 个 worker 抢活，一条 outcomes channel 交活。N 是你说了算的常量（CPU 核数、或数据库连接池的一半之类），跟任务总量无关——100 万个任务也只有 N 个 goroutine 在跑。判断「要不要池化」就一句话：每个任务都会碰有限资源（DB 连接、下游接口、文件句柄）吗？会，就池化。

2. 三角色解剖 + closer goroutine

今天增量里的池子长这样（先看图再看代码）：

结构 · 数据流向dispatcher goroutine ──(jobs chan int64)──▶ N 个 worker ──(outcomes chan)──▶ main 收集
        │ 派完 close(jobs)                        │ 抢不到活自然退出（range 结束）
        └── ctx.Done() 提前撤                     └── wg.Done()
                                   closer goroutine：wg.Wait() 后 close(outcomes) ← main 的 range 才能结束

最容易被忽略的是右下角那个 closer goroutine：outcomes 有 N 个发送者，谁都不能擅自 close（D2 的规矩：多发送方不 close）。于是加一个不干活的 goroutine，专门 wg.Wait() 等所有 worker 收工，然后 close 一次——main 里 for range outcomes 才有确定的终点。这个「Wait 后 close」模式是本阶段必背图形。

3. errgroup：WaitGroup 的成品增强版

golang.org/x/sync/errgroup（官方扩展库，不是第三方野包）解决的是另一类需求：一组任务里任何一个失败，整组就没必要继续了。三个要点：

  • errgroup.WithContext(ctx) 返回 (g, gctx)：第一个非 nil 错误出现时，gctx 自动取消——D4 的 ctx 树级联，errgroup 替你掐线。
  • g.Go(func() error) 起任务（自带 wg.Add/Done），g.SetLimit(n) 限并发——它就是个带错误传播的池。
  • g.Wait() 等全体结束，只返回第一个错误。想要「所有错误」它给不了——那是下周一 D7 批量导入的场景，得自己收集。
可跑 · server/playground/s5d5/main.go（自带 go.mod，需先 go get）package main

import (
    "context"
    "errors"
    "fmt"
    "time"

    "golang.org/x/sync/errgroup"
)

func main() {
    g, ctx := errgroup.WithContext(context.Background())
    g.SetLimit(4)                          // 池化：最多 4 个同时跑
    for i := 0; i < 10; i++ {
        g.Go(func() error {
            select {
            case <-ctx.Done():               // 别的任务闯祸后，这条线被掐，剩余任务提前收工
                return ctx.Err()
            default:
            }
            time.Sleep(50 * time.Millisecond)
            if i == 3 {
                return fmt.Errorf("任务 %d 失败（演示）: %w", i, errors.New("boom"))
            }
            fmt.Println("完成", i)
            return nil
        })
    }
    if err := g.Wait(); err != nil {
        fmt.Println("errgroup 返回:", err)   // 只有第一个错误：任务 3 失败（演示）: boom
    }
}

工具等法错误语义本项目用在哪
sync.WaitGroup等全体不管错误，自己想办法收D1/D3 的基础件
手写 pool（今天）等全体全部收集，第一个当返回聚合骨架；D7 导入的收集思想同源
errgroup等全体（但失败即掐线）快速失败：只给第一个错误「一损俱损」的并行子任务（S6 报表多段拼装）

4. SafeGo：兑现「goroutine 边界装 recover」

S1·D9 的原话：net/http 替每个请求兜了 panic，但你自己 spawn 的 goroutine 没有任何人兜底——那里一个 panic 就是全进程阵亡。HTTP 边界的 recover 中间件 S2 装了，今天装 goroutine 边界的：全站后台任务一律经 safego.Go 起飞。errgroup 和 WaitGroup 都不替你 recover，这条纪律只能自己守。

步骤 1 · SumByCategoryPool

完整 · server/internal/finance/service/agg_pool.gopackage service

import (
    "context"
    "sort"
    "sync"
)

// SumByCategoryPool 用固定 workers 个 goroutine 并行聚合各分类。
// 三角色：jobs 派活、workers 干活、outcomes 交活；closer 负责恰好一次 close。
func SumByCategoryPool(ctx context.Context, workers int, rows []AggInput) ([]AggResult, error) {
    if workers < 1 {
        workers = 1
    }
    ids := CategoryIDs(rows)
    jobs := make(chan int64)

    type outcome struct {
        res AggResult
        err error
    }
    outcomes := make(chan outcome)

    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {                       // worker：抢活干，jobs 关了自然收工
            defer wg.Done()
            for id := range jobs {
                res, err := sumOneCategory(ctx, id, rows)
                select {
                case outcomes <- outcome{res, err}:
                case <-ctx.Done():         // 收集方已撤（超时）：别堵在发送上泄漏
                    return
                }
                if err != nil {
                    return               // 信号线断了，不再领新活
                }
            }
        }()
    }

    go func() {                            // dispatcher：派完关 jobs
        defer close(jobs)
        for _, id := range ids {
            select {
            case jobs <- id:
            case <-ctx.Done():
                return
            }
        }
    }()

    go func() {                            // closer：全体收工后恰好一次 close(outcomes)
        wg.Wait()
        close(outcomes)
    }()

    out := []AggResult{}
    var firstErr error
    for o := range outcomes {               // 必须排干：否则 worker 堵在发送上永远退不出
        if o.err != nil {
            if firstErr == nil {
                firstErr = o.err
            }
            continue
        }
        out = append(out, o.res)
    }
    if firstErr != nil {
        return nil, firstErr
    }
    sort.Slice(out, func(i, j int) bool { return out[i].ID < out[j].ID })
    return out, nil
}

步骤 3 · safego 包（goroutine 边界的 recover）

完整 · server/internal/platform/safego/safego.go// Package safego 提供带边界兜底的后台 goroutine 起飞口。
// S1·D9 的纪律：HTTP 边界有 recover 中间件，自起的 goroutine 边界也得有。
package safego

import (
    "log"
    "runtime/debug"
)

// Go 起一个后台 goroutine；panic 被边界 recover，记日志，不带走进程。
// 日志先用标准库 log；D8 换 slog 后这里会带上结构化字段。
func Go(fn func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("后台任务 panic: %v\n%s", r, debug.Stack())
            }
        }()
        fn()
    }()
}
完整 · server/internal/platform/safego/safego_test.gopackage safego

import (
    "sync"
    "testing"
)

func TestGoRecoversPanic(t *testing.T) {
    var wg sync.WaitGroup
    wg.Add(1)
    Go(func() {
        defer wg.Done()
        panic("boom")          // 没有边界 recover 的话，这一行会杀死整个测试进程
    })
    wg.Wait()
    // 走到这里 = 进程还活着 = 测试通过。panic 的堆栈会打在测试输出里，属正常。
}

注意顺序：defer wg.Done() 在 panic 任务里先注册、recover 在外层 Go 的函数里——两层 defer 各干各的。wg.Done 照常执行（defer 在 panic 解卷时也会跑，S1·D9 讲过），recover 在更外一层接住。

常见坑（新手 100% 会踩）

坑现象正确姿势
workers 传 0没人消费 jobs，dispatcher 堵死，测试超时入口钳到 ≥1（代码里已做）；池大小是设计决策不是运气
忘了 closer goroutinefor range outcomes 永远等不到 close，测试挂死多发送者的 channel 由「wg.Wait 后 close」的专职 goroutine 收口
main 提前 return 不排干 outcomesworker 堵在发送上泄漏；-race 测试偶发挂起收集方要么排干、要么 select ctx.Done 让 worker 有退路——两边都写了才闭环
以为 errgroup 会 recover panic一个任务 panic，全进程阵亡errgroup 只管 error；panic 边界靠 safego.Go 这类包裹
拿 errgroup 做导入收集只拿到第一个错误，其余行的问题全丢「收集所有错误」场景自己拿 Mutex/channel 收——D7 批量导入就是它
每行数据一个 goroutine，不池化十万行 = 十万 goroutine 冲 DB，连接池瞬间打爆碰有限资源的任务一律限并发：pool 或 SetLimit
SetLimit 后又无限 g.Go不报错，但 g.Go 本身会阻塞等额度，主流程卡住知道 SetLimit 的阻塞语义；要「超额就跳过」用 TryGo

卡壳时查什么

正文自足，只有两种情况出去查：

  • errgroup 的完整 API：errgroup 文档（可选，读 Group.Go 与 SetLimit 的注释即可）。
  • 池化模式的其他写法：Go 官方博客 "Pipelines and cancellation"（可选，明天 D6 串起来之前读收益最大）。

死锁类卡死的调试顺序：先 Ctrl+\（SIGQUIT）让 Go 进程吐出全部 goroutine 堆栈，找「chan send / chan receive 卡住」的那些——堆栈会直接指出堵在哪条 channel 上。比盯代码快十倍。
