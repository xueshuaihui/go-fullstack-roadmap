优雅关闭：SIGTERM 三步曲

S1·D6 的名词卡写过：「优雅关闭——http.Server.Shutdown 收完存量请求再退出。S5 正式讲，今天 log.Fatal 即可」。今天还这张欠条。现在的 main.go 被 Ctrl+C 掐死时：正在处理到一半的请求被拦腰斩断（客户端拿到半截响应）、DB 连接池没关、后台 goroutine 集体蒸发。优雅关闭把「死」变成一个有序流程：停收新请求 → 等存量跑完 → 关 DB 与后台任务。这也是 D4 的 ctx 与 D5 的 safego 之后，工程化拼图里「生命周期」那一块。

今日目标

知识讲义

1. 三个信号，两种死法

信号谁发的能接住吗
SIGINT终端里的 Ctrl+C能——今天接
SIGTERMkill 的默认信号；容器编排停容器时先发它能——今天接
SIGKILL（kill -9）操作系统强制执行不能。进程没有遗言，直接蒸发

容器世界的规矩：「停止」= 先礼后兵——发 SIGTERM，等一个宽限期（常见默认 10 秒），到点还没退再 SIGKILL。所以你的三步曲必须在宽限期内跑完：这就是 Shutdown 自己要带超时 ctx 的原因——存量请求里若混着一个长轮询，不能让它把整个宽限期耗光，超时就 Close() 强制断开剩余连接，保住「体面退出」的大局。

2. Shutdown 到底做了什么

srv.Shutdown(ctx) 两步：① 立刻关闭监听——新连接进不来（客户端收到 connection refused）；② 等存量请求自然跑完——已建立的连接不打断，handler 该查库查库、该写响应写响应，全部结束（或 ctx 超时）才返回。配套细节三条：

  • Shutdown 触发后，另一头的 ListenAndServe/Serve 会返回 http.ErrServerShutdown——这是关闭的正常回声，不是事故，要用 errors.Is 把它从真错误里择出来。
  • DB 必须最后关：Shutdown 等待期间，存量 handler 还在查库；先关 DB = 亲手把存量请求全打成 5000。
  • 后台 goroutine（比如聚合任务）不走 HTTP 那条命：让它们监听同一根信号线（notify ctx 的 Done），收到就自己收工——D4 的协作式取消在生命周期上的应用。

3. signal.NotifyContext：把信号变成 ctx

老写法要自己开 channel 调 signal.Notify；现在的标准姿势一行：ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)——信号一到，ctx 被取消，<-ctx.Done() 放行，三步曲开跑。stop() 负责注销监听（defer 上）。主 goroutine 从此只干一件事：等信号。

结构 · 三步曲时序main ── ListenAndServe(go) ──▶ 正常服务中…
  │
  ├─ <-ctx.Done()            ← SIGTERM/SIGINT 到达（第一步：接住信号）
  ├─ srv.Shutdown(10s ctx)   ← 第二步：停收新请求 + 等存量；超时则 srv.Close() 强关
  ├─ sqlDB.Close()           ← 第三步：最后关 DB（存量已经不需要它了）
  └─ return                  ← main 返回，进程体面退场，退出码 0

步骤 1 · main.go 生命周期版

完整 · server/cmd/homecube/main.go（覆盖旧版；装配函数名以你仓库为准）package main

import (
    "context"
    "errors"
    "log/slog"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"

    "homecube/internal/platform/config"
    "homecube/internal/platform/logger"
)

func main() {
    cfg := config.Load()               // S3 建的 config；明天 D10 定稿。若签名不同，以仓里为准
    logger.Init(cfg.GinMode)           // D8 的装配口；字段名不同就传 gin.Mode()
    db := platform.MustOpenDB(cfg)     // S3 的 DB 装配点，函数名以仓里为准

    srv := &http.Server{
        Addr:    ":" + cfg.Port,       // S1·D6 写死的 ":8080" 从今天起活在配置里
        Handler: newRouter(db),        // gin 引擎本身就是 http.Handler（S1·D6 的接口思想）
    }

    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    go func() {                        // 监听循环让位给主 goroutine，main 专职等信号
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerShutdown) {
            slog.Error("服务启动失败", "err", err)
            os.Exit(1)                // 起不来就别装体面：立刻死给进程管理器看
        }
    }()
    slog.Info("homecube listening", "port", cfg.Port)

    <-ctx.Done()                       // 第一步：SIGINT/SIGTERM 到达
    slog.Info("优雅关闭：停收新请求，等待存量请求")

    shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil {   // 第二步：等存量
        slog.Warn("等待存量超时，强制关闭剩余连接", "err", err)
        _ = srv.Close()               // Close 不等任何人，直接断——宽限期内的最后手段
    }

    if sqlDB, err := db.DB(); err == nil {
        _ = sqlDB.Close()              // 第三步：最后关 DB——此刻已没有存量请求要用它
    }
    slog.Info("关闭完成，再见")
}

os.Exit(1) 会跳过所有 defer（包括 stop()）——这里无所谓：进程都没了，注销不注销监听毫无意义。但记住这条规则：os.Exit 与 defer 不共存，需要清理的场合用 error 返回或 log.Fatal 之外的路径。

步骤 2 · 「存量被等完、新请求被拒」测试

完整 · server/cmd/homecube/shutdown_test.gopackage main

import (
    "context"
    "io"
    "net"
    "net/http"
    "sync"
    "testing"
    "time"

    "github.com/gin-gonic/gin"
)

func TestShutdownWaitsInflightThenRefuses(t *testing.T) {
    gin.SetMode(gin.TestMode)
    r := gin.New()
    r.GET("/slow-for-test", func(c *gin.Context) {
        time.Sleep(300 * time.Millisecond) // 模拟慢请求。测试专用路由，不进产品路由——不违反「S5 不新增接口」
        c.String(http.StatusOK, "done")
    })

    ln, err := net.Listen("tcp", "127.0.0.1:0") // 端口 0：让系统随机分配，测试永不撞车
    if err != nil {
        t.Fatal(err)
    }
    srv := &http.Server{Handler: r}
    go func() { _ = srv.Serve(ln) }()          // Serve 会返回 ErrServerShutdown，测试里忽略即可
    base := "http://" + ln.Addr().String()

    // 存量请求：300ms 的慢活
    var (
        wg         sync.WaitGroup
        inflightErr error
        body        string
    )
    wg.Add(1)
    go func() {
        defer wg.Done()
        resp, err := http.Get(base + "/slow-for-test")
        if err != nil {
            inflightErr = err
            return
        }
        defer resp.Body.Close()
        b, _ := io.ReadAll(resp.Body)
        body = string(b)
    }()

    time.Sleep(50 * time.Millisecond)          // 确保慢请求已进入 handler，成为「存量」

    shutdownCtx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil {
        t.Fatalf("Shutdown: %v", err)
    }

    wg.Wait()                                   // WaitGroup 建立 happens-before：下面读 body 无竞争（D3）
    if inflightErr != nil {
        t.Fatalf("存量请求被腰斩: %v", inflightErr)
    }
    if body != "done" {
        t.Fatalf("存量响应 = %q, want done", body)
    }
    if _, err := http.Get(base + "/slow-for-test"); err == nil {
        t.Fatal("Shutdown 之后新请求应被拒绝")
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
把 ErrServerShutdown 当事故每次正常关闭都打一条 Error 日志，狼来了errors.Is(err, http.ErrServerShutdown) 择出来，静默或 Info
Shutdown 不带超时一个长连接卡住，宽限期耗尽后被 SIGKILL——比不优雅更不优雅Shutdown 必须带自己的 ctx（本站 10s），超时 Close() 兜底
先关 DB 再 Shutdown存量请求集体 5000，日志一片「database is closed」顺序铁律：HTTP → 后台任务 → DB，最后关的才是最底层的
后台 goroutine 不听信号HTTP 关了，聚合任务还在库里写后台任务监听同一根 notify ctx 的 Done（D4 的协作式取消）
试图接 SIGKILL接不住，白写代码SIGKILL 是操作系统强制执行，没有商量；体面只存在于宽限期内
测试写死端口两个测试并行或端口被占，CI 时红时绿net.Listen("tcp", "127.0.0.1:0") 让系统分配
Shutdown 后又调 ListenAndServe返回 ErrServerShutdown，服务再也起不来Server 是一次性的；重启 = 新 Server 对象

今日名词卡

术语一句话解释
SIGINT / SIGTERM / SIGKILLCtrl+C / 「请你退下」（可接住）/ 「强制执行」（接不住）
宽限期容器编排发 SIGTERM 到 SIGKILL 之间的等待窗口；三步曲要在窗口内跑完
signal.NotifyContext把信号到达翻译成 ctx 取消；返回的 stop 负责注销监听
srv.Shutdown(ctx)关监听 + 等存量；ctx 超时则返回错误，由你决定是否 Close 强关
srv.Close()不等任何人，立刻断开全部连接——最后手段
http.ErrServerShutdownShutdown 后监听循环的正常返回值，不是事故
存量请求（in-flight）信号到达时正在处理中的请求；优雅关闭等的就是它们
net.Listen(":0")系统随机分配端口；测试永不撞车的标准手法
退出码体面退场 0、启动失败 1；进程管理器只看这个数字
探活摘流（前瞻）S8 部署后，编排系统靠 /healthz 摘流量再发 SIGTERM——今天的第一步会更从容

卡壳时查什么

正文自足，只有两种情况出去查：

  • Shutdown/Close 的权威语义：net/http · Server.Shutdown（可选，注释里把关监听与等存量两步写得明明白白）。
  • signal 包的用法细节：os/signal · NotifyContext（可选）。

关闭类问题的调试顺序：先看进程退出码与最后几条日志（三步曲走到哪一步断的），再手工 kill -TERM 复现一次，最后才怀疑代码。日志就是三步曲的脚印——这也是昨天 D8 把日志换成结构化的回报：每步一条 Info，谁没打出来谁就是卡点。
