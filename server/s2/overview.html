S2 · Gin 与三层

S1 你手写了 HTTP 的每一块零件：路由、解析、信封、中间件。这两周做两件事：把零件换成 Gin 这台机器——你会亲眼看到框架替你做了哪些活；把代码从「一个 handler 打天下」拆成 handler / service / repo 三层——并用 72 条接口里的第一批业务接口（B4「分类」6 条）把三层完整走通。存储还是内存 map，数据库是 S3 的事；今天换框架、立分层，S3 换存储时业务代码才能一行不动。

为什么 S2 先换 Gin、先立三层，却不接数据库

一次只换一块地基。S2 同时动「框架」和「分层」两件事已经够满了；如果再把 Postgres 塞进来，出了问题你分不清是 Gin 的锅、分层的锅还是 SQL 的锅。内存 map 存储恰好是一面镜子：它让三层的接缝（CategoryRepository 接口）清清楚楚——S3 把内存实现换成 GORM 实现时，service 一行不改，你会真正体会到「接口是替换的接缝」这句话的分量。反过来，如果 S2 直接上数据库，接缝就被 SQL 细节糊住了。

阶段判据（全过才算 S2 通过）

不通过就原地重做，不跳阶段。S3 会把这 6 条接口的存储从内存 map 换成 Postgres——换的只是 repository 的实现，service 与 handler 原封不动。如果你的三层是糊在一起的，S3 每写一条 SQL 都在往 handler 里渗，空洞会从 S3 一直漏到 S6。

本阶段不做什么（明确划掉，免得手滑）

  • 不接数据库——Postgres、GORM、迁移全是 S3 的事；这两周存储就是内存 map，重启丢数据是特性不是 bug
  • 不做鉴权与家庭隔离——S4 才建登录态；S2 期间 familyID 是写死的教学值，但 repo 的每个方法都已带上这个参数，S4 只是把值的来源换掉
  • 72 条接口只做 B4「分类」6 条（/api/finance/categories*）——其余 66 条一条都不许出现，包括「顺手加一个」
  • 不做游标分页——分类是「非分页小集合」，响应就是 {"list":[…]}，不带 next_cursor / has_more；游标分页 S3 随流水列表登场
  • 不起 goroutine、不做并发压测（S5）；不写前端、web/ 目录这两周仍不存在
  • 路由不加版本段——分域就是 /api/homeos 与 /api/finance 两个，任何 /api/v1 字样都是违规
