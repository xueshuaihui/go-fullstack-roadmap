分类的二级树与排序字段

周六把 6 条走通了，但走的是「直路」：列表是平铺的、创建时父级只查存在、排序不分组。今天给分类补上它的两笔真语义——树只有两级（父级必须是一级、收支必须与父级一致）与排序只在同父同类型内重排——并让 GET 返回真正的二级树。「先走通、再加深」，这正是 6 条接口三次加深（S2 骨架 → S3 换库 → S6 补全）里第二次的开场。

今日目标

知识讲义

1. 平铺存储、树形输出

分类是两级树，但存储里从来没有「树」这个数据结构——每行就是一个 Category，靠 ParentID 指认父亲（0 = 一级）。树是响应前组装出来的视图。为什么不直接存嵌套结构？因为平铺行让每个操作都简单：改一个名字 = 改一行；查一个分类 = 按 id 取一行；S3 建表时它就是一张普通表 + 一列 parent_id。嵌套存储则会让「改中间一个节点」变成「改一整坨」。

组装算法两遍扫描（输入已按 (Sort, ID) 排好）：第一遍收全部一级进 roots，顺手记「一级 id → 在 roots 里的下标」；第二遍把每个二级按父级下标塞进对应的 Children。因为输入有序，children 内部自然也有序。

2. 树的形状就是合同

片段 · GET /api/finance/categories 的响应 data（D7 起）{
  "list": [
    {
      "id": 1, "parent_id": 0, "name": "餐饮", "kind": "expense",
      "sort": 20, "archived": false, "version": 2, "icon": "food",
      "children": [
        { "id": 2, "parent_id": 1, "name": "早餐", "kind": "expense",
          "sort": 10, "archived": false, "version": 1, "icon": "",
          "children": [] }
      ]
    }
  ]
}

两个合同细节：

  • children 永远存在：一级的 children 装着二级，二级的 children 是空数组 []——绝不输出 null。客户端对 null 和 [] 的处理是两套代码（前端 v-for 遇 null 直接报错），服务端把歧义掐死在源头。Go 侧的对应纪律：Children 字段必须显式初始化为空 slice，nil slice 序列化出来就是 null。
  • 排序由服务端返回顺序表达：同级内按 (Sort, ID) 升序，客户端拿到什么顺序就展示什么顺序，不自己排。

树节点 CategoryNode 是响应形状 → 它是 DTO，住 handler 包（D5 的分家纪律）。它用匿名嵌入复用 CategoryResp 的八个字段：嵌入后外层直接「继承」内层全部字段，JSON 序列化也平铺展开——新语法，照抄即可，今天只需读懂。

3. 父级三规则：树只有两级的守门员

规则违反时码
父级必须存在（且属于本家庭）挂在不存在的分类下404 + 1001（repo 的 ErrNotFound 直接透传）
父级必须是一级（ParentID == 0）挂出第三级400 + 1004
收支类型必须与父级一致支出二级挂进收入一级400 + 1004

另有一条自反规则顺手钉死：parent_id 不能是自己（Update 时把 :id 传进 body）。三规则抽成 validateParent 一个函数，Create 与 Update 共用——规则只有一份实现，将来改规则不会漏掉某个入口。

4. sort 的约束：同父同类型、整组、不重不漏

周六的 sort 是「给谁排谁」，今天收紧成完整语义：ids 必须是同一父级、同一收支类型下的一整组分类（含已停用的），不重复、不遗漏，否则 400 + 1004。为什么整组？因为「排序」的含义是确立这一组的完整顺序——允许半组重排的话，没提到的成员落在哪就说不清了，顺序合同立刻含糊。校验通过后照旧落 Sort = 10, 20, 30…（间隙留给将来的插入）。

还有一类数据今天不做、但要知道它存在：系统预置的默认分类树（新家庭开箱即有的「餐饮/交通/日用…」）。真实系统里它们是 family_id 为空的可空预置数据，查询时「本家庭的 + 预置的」一起返回——S3 建表时用可空列正式落地。今天的内存版只有家庭自建分类。

完整 · server/internal/finance/service/service.go（覆盖 D6 版本）package service

import (
    "fmt"
    "sort"

    "homecube/internal/finance/model"
    "homecube/internal/finance/repository"
    "homecube/pkg/response"
)

type CategoryService struct {
    repo repository.CategoryRepository
}

func NewCategoryService(r repository.CategoryRepository) *CategoryService {
    return &CategoryService{repo: r}
}

// List 返回全部分类（含已停用），按 (Sort, ID) 升序。
func (s *CategoryService) List(familyID int64) ([]model.Category, error) {
    cs, err := s.repo.List(familyID)
    if err != nil {
        return nil, err
    }
    sort.Slice(cs, func(i, j int) bool {
        if cs[i].Sort != cs[j].Sort {
            return cs[i].Sort < cs[j].Sort
        }
        return cs[i].ID < cs[j].ID
    })
    return cs, nil
}

// validateParent 父级三规则：存在、必须一级、收支一致；外加「不能挂自己」。
// selfID 在 Create 时传 0（还没有 id），Update 时传自己的 id。
func (s *CategoryService) validateParent(familyID, parentID, selfID int64, kind string) error {
    if parentID == 0 {
        return nil // 一级分类，没有父级要校验
    }
    if parentID == selfID {
        return fmt.Errorf("分类 %d 不能挂在自己下面: %w", selfID, response.ErrInvalidParam)
    }
    parent, err := s.repo.Get(familyID, parentID)
    if err != nil {
        return err // 规则①：父级存在（查无 → ErrNotFound → 404+1001）
    }
    if parent.ParentID != 0 {
        return fmt.Errorf("父级 %d 不是一级分类，树只有两级: %w", parentID, response.ErrInvalidParam)
    }
    if parent.Kind != kind {
        return fmt.Errorf("收支类型与父级不一致: %w", response.ErrInvalidParam)
    }
    return nil
}

func (s *CategoryService) Create(familyID int64, c model.Category) (model.Category, error) {
    c.FamilyID = familyID
    if err := s.validateParent(familyID, c.ParentID, 0, c.Kind); err != nil {
        return model.Category{}, err
    }
    if err := s.repo.Create(&c); err != nil {
        return model.Category{}, err
    }
    return c, nil
}

// Update 只允许改 Name/Icon/Kind/ParentID；改父级同样过三规则，
// 且「有子级的分类不许改父级」——否则它的孩子们会变成第三级。
func (s *CategoryService) Update(familyID, id int64, in model.Category) (model.Category, error) {
    old, err := s.repo.Get(familyID, id)
    if err != nil {
        return model.Category{}, err
    }
    if err := s.validateParent(familyID, in.ParentID, id, in.Kind); err != nil {
        return model.Category{}, err
    }
    if in.ParentID != old.ParentID {
        all, err := s.repo.List(familyID)
        if err != nil {
            return model.Category{}, err
        }
        for _, c := range all {
            if c.ParentID == id {
                return model.Category{}, fmt.Errorf(
                    "分类 %d 有子级，不能改挂父级: %w", id, response.ErrInvalidParam)
            }
        }
    }
    old.Name, old.Icon, old.Kind, old.ParentID = in.Name, in.Icon, in.Kind, in.ParentID
    if err := s.repo.Update(old); err != nil {
        return model.Category{}, err
    }
    return s.repo.Get(familyID, id)
}

// Archive / Restore 与 setArchived：与 D6 逐字一致，今天不动（规则 D8 加）。
func (s *CategoryService) Archive(familyID, id int64) (model.Category, error) {
    return s.setArchived(familyID, id, true)
}

func (s *CategoryService) Restore(familyID, id int64) (model.Category, error) {
    return s.setArchived(familyID, id, false)
}

func (s *CategoryService) setArchived(familyID, id int64, v bool) (model.Category, error) {
    c, err := s.repo.Get(familyID, id)
    if err != nil {
        return model.Category{}, err
    }
    c.Archived = v
    if err := s.repo.Update(c); err != nil {
        return model.Category{}, err
    }
    return s.repo.Get(familyID, id)
}

// Sort 收紧版：ids 必须是「同父同类型」的一整组，不重不漏。
func (s *CategoryService) Sort(familyID int64, ids []int64) error {
    if len(ids) == 0 {
        return fmt.Errorf("ids 为空: %w", response.ErrInvalidParam)
    }
    first, err := s.repo.Get(familyID, ids[0])
    if err != nil {
        return err
    }
    // 该组的「应有名单」：同父同类型的全部成员（含已停用）
    all, err := s.repo.List(familyID)
    if err != nil {
        return err
    }
    want := make(map[int64]bool, len(all))
    for _, c := range all {
        if c.ParentID == first.ParentID && c.Kind == first.Kind {
            want[c.ID] = true
        }
    }
    // 逐个核对：同组、不重复；最后核对不漏
    seen := make(map[int64]bool, len(ids))
    for _, id := range ids {
        c, err := s.repo.Get(familyID, id)
        if err != nil {
            return err
        }
        if c.ParentID != first.ParentID || c.Kind != first.Kind {
            return fmt.Errorf(
                "排序只允许同父级同收支类型: %w", response.ErrInvalidParam)
        }
        if seen[id] {
            return fmt.Errorf("排序 ids 重复: %d: %w", id, response.ErrInvalidParam)
        }
        seen[id] = true
    }
    if len(seen) != len(want) {
        return fmt.Errorf(
            "排序必须覆盖该组全部 %d 个分类: %w", len(want), response.ErrInvalidParam)
    }
    // 落地：Sort = 10, 20, 30…（间隙留给将来的插入）
    for i, id := range ids {
        c, err := s.repo.Get(familyID, id)
        if err != nil {
            return err
        }
        c.Sort = (i + 1) * 10
        if err := s.repo.Update(c); err != nil {
            return err
        }
    }
    return nil
}

步骤 2 · handler：CategoryNode 与组树

片段 · dto.go 追加（前置：D5 版本；树是响应形状，所以住 handler 包）// CategoryNode 二级树的响应节点。
// 匿名嵌入 CategoryResp：外层直接「继承」内层全部字段，JSON 也平铺展开（照抄即可）。
type CategoryNode struct {
    CategoryResp
    Children []CategoryNode `json:"children"`
}

// BuildTree 把平铺列表（已按 (Sort, ID) 排序）组装成二级树。
// 两遍扫描：先收一级并记下标，再把二级塞进对应 Children。
func BuildTree(flat []CategoryResp) []CategoryNode {
    roots := []CategoryNode{}
    indexOf := make(map[int64]int, len(flat)) // 一级 id → roots 下标
    for _, r := range flat {
        if r.ParentID == 0 {
            indexOf[r.ID] = len(roots)
            roots = append(roots, CategoryNode{
                CategoryResp: r,
                Children:   []CategoryNode{}, // 显式空数组：绝不输出 null
            })
        }
    }
    for _, r := range flat {
        if r.ParentID != 0 {
            if i, ok := indexOf[r.ParentID]; ok { // service 已保证父级合法，兜底跳过孤儿
                roots[i].Children = append(roots[i].Children, CategoryNode{
                    CategoryResp: r,
                    Children:   []CategoryNode{},
                })
            }
        }
    }
    return roots
}
片段 · handler.go 的 list 改动（前置：D6 版本，一行换血）func (h *CategoryHandler) list(c *gin.Context) {

步骤 3 · 测试：树的形状与四条拒绝

片段 · handler_test.go 追加（前置：D6 的 newTestRouter 与 do）func TestCategoryTreeAndParentRules(t *testing.T) {
    r := newTestRouter()

    // 一级「餐饮」+ 二级「早餐」
    do(r, "POST", "/api/finance/categories", `{"name":"餐饮","kind":"expense"}`)
    do(r, "POST", "/api/finance/categories", `{"name":"早餐","kind":"expense","parent_id":1}`)

    // 列表是树：一级带 children，二级的 children 是空数组不是 null
    w := do(r, "GET", "/api/finance/categories", "")
    body := w.Body.String()
    if !strings.Contains(body, `"children":[{"id":2`) {
        t.Fatalf("二级应嵌在一级的 children 里: %s", body)
    }
    if strings.Contains(body, `"children":null`) {
        t.Fatalf("children 绝不允许为 null: %s", body)
    }

    // 拒绝第三级：父级 2 号是二级 → 400 + 1004
    w = do(r, "POST", "/api/finance/categories", `{"name":"豆浆","kind":"expense","parent_id":2}`)
    if w.Code != 400 || !strings.Contains(w.Body.String(), `"code":1004`) {
        t.Fatalf("第三级应被拒: %d %s", w.Code, w.Body.String())
    }

    // 拒绝收支不一致：收入二级挂进支出一级 → 400 + 1004
    w = do(r, "POST", "/api/finance/categories", `{"name":"工资","kind":"income","parent_id":1}`)
    if w.Code != 400 || !strings.Contains(w.Body.String(), `"code":1004`) {
        t.Fatalf("收支不一致应被拒: %d %s", w.Code, w.Body.String())
    }

    // sort 半组重排：先再建一条一级「交通」，让「一级支出组」有两个成员，
    // 然后只给一个 id → 400 + 1004
    do(r, "POST", "/api/finance/categories", `{"name":"交通","kind":"expense"}`)
    w = do(r, "PUT", "/api/finance/categories/sort", `{"ids":[1]}`)
    if w.Code != 400 || !strings.Contains(w.Body.String(), `"code":1004`) {
        t.Fatalf("半组重排应被拒: %d %s", w.Code, w.Body.String())
    }
}

注意 sort 用例的分组口径：2 号的 parent_id 是 1，它和 1 号不同组——1 号在「一级支出组」（parent_id=0），2 号在「1 号的子级组」。所以若不先建「交通」，{"ids":[1]} 恰好是完整一组、会成功；建了之后组里有两个成员，只给一个才构成「半组」，断言才真正钉死整组语义。分组的钥匙是 (parent_id, kind) 这个二元组，不是「有没有孩子」。

常见坑（新手 100% 会踩）

坑现象正确姿势
Children 忘了初始化JSON 输出 "children":null，前端 v-for 报错组装时显式 []CategoryNode{}；测试里钉一条「不许出现 null」的断言
对 nil slice 用下标改元素roots[i].Children = append(…) 前先确认 roots 是 slice 而非 map 值——map 的 value 不可寻址，改不动本片用「slice + 下标索引 map」组合；若换成 map 存节点，值类型要用指针
只在 Create 校验父级，Update 忘了编辑时把二级改成三级，树被凿穿validateParent 一份实现两个入口共用；「有子级不许改挂」也钉在 Update
sort 允许半组重排没提到的成员顺序悬空，列表顺序不可解释整组、不重、不漏，三缺一就是 1004
组树逻辑写进 service响应形状（children 字段）渗进业务层service 给排好序的平铺列表，组树是 handler/DTO 的活
匿名嵌入后手写 resp.CategoryResp.ID 又写 resp.ID两种写法都对，代码里混用可读性差统一直接 resp.ID（字段已被提升）；只有内外字段重名才写全路径
用 == 比较 Kind 的裸字符串散落各处改拼写时漏改一处引用 model.KindExpense / model.KindIncome 常量（D4 立的规矩）

卡壳时查什么

正文自足，只有两种情况出去查：

  • 匿名嵌入的字段提升规则：Effective Go · Embedding（可选，两页短文，正好覆盖今天用到的全部行为）。
  • map 遍历无序又忘了：回 S1·D4 的 map 一节；今天的「应有名单」用了两个 map 做集合，只查键不依赖顺序，是安全的。

树类 bug 的调试铁律：先把平铺列表打出来，再看组装。curl 一次 GET，把 data.list 摊平检查：顺序对不对（service 的排序）、parent_id 对不对（数据本身）；平铺没问题而树不对，才去查 BuildTree 的两遍扫描。分层之后，「打印中间形状」比盯着最终响应猜快得多。
