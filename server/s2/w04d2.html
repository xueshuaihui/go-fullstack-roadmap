分类停用与恢复：archived 的语义

周六的 archive/restore 只是「把旗子翻个面」，什么规则都没有。今天给 archived 补上它的真语义：停用不是删除（分类没有 DELETE 接口，永远不会物理消失）、停用有守门规则（一级下还有活着的二级时不许停用），并让错误体系第一次「生长」——新增第六个哨兵 ErrStateNotAllowed，对上码表里 S1 就预留好的 1010。

今日目标

知识讲义

1. 停用 ≠ 删除：被引用的数据不许消失

先看一个事实：分类的 6 条接口里没有 DELETE，这是合同而不是遗漏。原因在 S6——每笔流水都挂着一个分类 id。如果允许删除分类，历史流水就会指向一个不存在的 id：报表按分类汇总时这笔钱算谁的？这叫数据黑洞：删掉的瞬间看似干净，之后每个读它的地方都在漏。

所以分类只有生命周期开关：archived:false（在用，可以被新流水选择）⇄ archived:true(停用，新流水不能再选它，但历史流水照常引用、照常统计、照常在报表里出现)。GET 列表永远返回全部（含已停用、带 archived 标记），前端据此决定「记账选分类时过滤掉、看历史时正常显示」。

还要分清第三个词：软删（deleted_at）。那是 S3 数据库层的另一回事——整行标记删除、默认查询排除，用于「用户真的想撤掉一条数据」的场景。分类不用软删，用状态旗：停用是它的正常业务状态，不是「这条数据作废了」。

2. 状态不许 → 1010，参数不对 → 1004

今天出现第三类失败，先摆清楚三兄弟的分界：

码HTTP含义分类里的例子
1004400请求本身不合法：参数缺失、越界、枚举不对name 空、kind 拼错、挂出第三级
1006409唯一约束冲突：换个名字/换个时机就能成（S6 账户名重名用它；分类今天没有唯一约束）
1010409业务状态不允许：请求合法、资源也在，但「现在」不行一级下还有未停用子级，却要停用这个一级

判断口诀：把请求原样重发一遍，有没有可能成功？1004 永远不可能（请求就是错的）；1010 可能——先把子级停用了再发，就成功了。「状态」是资源的属性，不是请求的属性，所以 1010 用 409（Conflict：请求与资源当前状态冲突），不用 400。

码表侧不用动：CodeStateNotAllowed = 1010 和它的 409 映射 S1·D4 就写好了。今天缺的是哨兵——service 往上抛错误时需要一个「内部通用语」，让 FailErr 认出这是状态问题。

3. 哨兵第一次生长

S1·D4 立哨兵时只给了 5 个（NotFound/Forbidden/InvalidParam/Conflict/Internal），并写明约定：码表是对外契约，一次定死；哨兵是内部词汇，随阶段生长。今天第一次兑现：新增 ErrStateNotAllowed，并在 CodeOf 里补一条 errors.Is 分支。生长是「加一个 var + 加一个 case」，不是改契约——1010 从 S1 起就在码表里等着。

4. 停用的守门规则，恢复的自由

停用有一条规则：一级分类下还有未停用的二级时，不许停用它。为什么？否则树上会出现「父已死、子还活」的悬空状态——记账时这个二级还能被选中，可它的父级已经停用了，前端展示与筛选逻辑全得为这种畸形状态写特例。规则逼用户按顺序来：先停子级，再停父级。

恢复则什么规则都没有，也不联动：恢复父级不会自动恢复它的子级。两个理由：其一，联动 = 一次点击悄悄改了一堆数据，用户没要求的不做；其二，恢复顺序无关紧要——父级恢复后，仍停用的子级在树上照常显示（带标记），不产生悬空。每个节点的状态由用户逐个、显式地管理。

「有子级不可停用」的检查今天用 repo.List 全量扫描实现——内存 map 时代这是最直白的写法。S3 换成数据库后，它会变成一条 WHERE parent_id = ? AND archived = false LIMIT 1 的存在性查询，规则本身一个字不改：规则住在 service，存储怎么查是 repo 的事（D4 分层的回报）。

今日增量（在学习仓里落盘）

今天属增量类型 ①：加哨兵与状态规则——ErrStateNotAllowed 进 pkg/response，CodeOf 扩一条分支，service 的 setArchived 加停用守门规则。handler 一行不改：错误从 service 抛上来，FailErr 自动翻译成 409 + 1010。

步骤 1 · 哨兵生长：errors.go

完整 · server/pkg/response/errors.go（覆盖 S1·D4 版本；code.go 不动）package response

import "errors"

// 哨兵错误集：repo/service 层往上抛的就是这些值，
// FailErr 用 errors.Is 认出它们并翻译成对应错误码。
// 码表是对外契约一次定死；哨兵是内部词汇，随阶段生长（S2·D8 第一次生长）。
var (
    ErrNotFound         = errors.New("not found")          // → 1001 / 404
    ErrForbidden        = errors.New("forbidden")          // → 1003 / 403
    ErrInvalidParam     = errors.New("invalid param")      // → 1004 / 400
    ErrConflict         = errors.New("conflict")           // → 1006 / 409
    ErrStateNotAllowed  = errors.New("state not allowed")  // → 1010 / 409
    ErrInternal         = errors.New("internal error")     // → 5000 / 500
)

// CodeOf 把哨兵错误翻译成业务码；认不出来的一律 5000。
// 注意 errors.Is 而不是 ==——链被包装过也要认得出来。
func CodeOf(err error) int {
    switch {
    case err == nil:
        return CodeOK
    case errors.Is(err, ErrNotFound):
        return CodeNotFound
    case errors.Is(err, ErrForbidden):
        return CodeForbidden
    case errors.Is(err, ErrInvalidParam):
        return CodeInvalidParam
    case errors.Is(err, ErrConflict):
        return CodeConflict
    case errors.Is(err, ErrStateNotAllowed):
        return CodeStateNotAllowed
    default:
        return CodeInternal
    }
}

步骤 2 · service：停用守门规则

setArchived 只在停用分支（v == true）加检查；恢复分支原样直通。Archive/Restore 两个入口函数不动。

片段 · service.go 的 setArchived 改动（前置：D7 版本，整函数替换）// setArchived 停用带守门规则；恢复无条件、不联动子级。
func (s *CategoryService) setArchived(familyID, id int64, v bool) (model.Category, error) {
    c, err := s.repo.Get(familyID, id)
    if err != nil {
        return model.Category{}, err
    }
    if v { // 只有「停用」需要守门：有未停用子级 → 1010
        all, err := s.repo.List(familyID)
        if err != nil {
            return model.Category{}, err
        }
        for _, child := range all {
            if child.ParentID == id && !child.Archived {
                return model.Category{}, fmt.Errorf(
                    "分类 %d 下有未停用子级 %d，不能停用: %w",
                    id, child.ID, response.ErrStateNotAllowed)
            }
        }
    }
    c.Archived = v
    if err := s.repo.Update(c); err != nil {
        return model.Category{}, err
    }
    return s.repo.Get(familyID, id)
}

步骤 3 · 测试：一条链走完状态语义

片段 · handler_test.go 追加（前置：D6 的 newTestRouter 与 do）func TestCategoryArchiveRules(t *testing.T) {
    r := newTestRouter()
    do(r, "POST", "/api/finance/categories", `{"name":"餐饮","kind":"expense"}`)
    do(r, "POST", "/api/finance/categories", `{"name":"早餐","kind":"expense","parent_id":1}`)

    // 子级还活着，停用父级 → 409 + 1010
    w := do(r, "PUT", "/api/finance/categories/1/archive", "")
    if w.Code != 409 || !strings.Contains(w.Body.String(), `"code":1010`) {
        t.Fatalf("有活子级应拒绝停用: %d %s", w.Code, w.Body.String())
    }

    // 先停子级，再停父级 → 都成功
    if w := do(r, "PUT", "/api/finance/categories/2/archive", ""); w.Code != 200 {
        t.Fatalf("停用子级应成功: %d %s", w.Code, w.Body.String())
    }
    if w := do(r, "PUT", "/api/finance/categories/1/archive", ""); w.Code != 200 {
        t.Fatalf("子级已停用后父级应可停用: %d %s", w.Code, w.Body.String())
    }

    // 恢复父级：成功，且不联动——子级仍是 archived:true
    w = do(r, "POST", "/api/finance/categories/1/restore", "")
    if w.Code != 200 || !strings.Contains(w.Body.String(), `"archived":false`) {
        t.Fatalf("恢复应成功: %d %s", w.Code, w.Body.String())
    }
    w = do(r, "GET", "/api/finance/categories", "")
    body := w.Body.String()
    // 此刻全树只应有一个 archived:true——就是没被联动的 2 号（1 号刚恢复成 false）
    if n := strings.Count(body, `"archived":true`); n != 1 {
        t.Fatalf("恢复父级不应联动子级，archived:true 应恰好 1 个，实得 %d: %s", n, body)
    }

    // 不存在的 id：停用与恢复都是 404 + 1001
    w = do(r, "PUT", "/api/finance/categories/999/archive", "")
    if w.Code != 404 || !strings.Contains(w.Body.String(), `"code":1001`) {
        t.Fatalf("停用不存在应为 404+1001: %d %s", w.Code, w.Body.String())
    }
}

「恢复不联动」这条断言用了 strings.Count 数 "archived":true 的个数——它成立的前提是你知道此刻全树的状态（1 号刚恢复、2 号仍停用）。字符串断言写多了会变成「猜 body 长什么样」，脆且难读。D9 会换成主力写法：把 body 解码进 response.Body 再逐字段断言，今天先用 Count 顶住。

常见坑（新手 100% 会踩）

坑现象正确姿势
给分类加 DELETE 接口「顺手清理」历史流水指向消失的分类，报表出洞（S6 兑现时爆雷）被引用的主数据只有停用；物理删除永远不进合同
状态拒绝用 1004 / 400客户端把「先停子级」当成「参数写错了」，提示语全错请求合法但状态不允许 → 409 + 1010；参数错 → 400 + 1004
子级检查忘了 !child.Archived子级已停用，父级仍被挡——永远停不掉只有「未停用子级」才拦；已停用的子级不构成障碍
把检查也写进恢复分支「父级停用了就不许恢复子级」之类没人要求的规则冒出来恢复无条件、不联动；规则只在停用一侧
抛错时用 %v 拼哨兵链断了，errors.Is 认不出，1010 回落成 5000/500一律 fmt.Errorf("…: %w", response.ErrStateNotAllowed)
在 handler 里自己 errors.Is 判码翻译逻辑散落两处，与 FailErr 打架handler 的错误出口只有 response.FailErr(c, err) 一个
以为 Version 会保持不变停用/恢复走 repo.Update，version 照涨停用也是修改，涨版本是对的；D10 的乐观锁会用到它

今日名词卡

术语一句话解释
archived（停用）生命周期开关：新流水不能再选它，历史流水照常引用与统计
数据黑洞删除被引用的数据后，所有读它的地方开始漏——分类不设 DELETE 的原因
软删（deleted_at）整行标记删除、默认排除，S3 数据库层的另一回事；与状态旗不是一回事
ErrStateNotAllowed第六个哨兵：业务状态不允许 → 1010 / 409；哨兵随阶段生长的第一次兑现
1010 vs 1004 vs 1006状态不允许（重发可能成）/ 参数不合法（重发永远不成）/ 唯一约束冲突
守门规则（guard）状态迁移的前置条件：停用父级前必须先停用它的全部子级
恢复不联动恢复只改自己一个节点；用户没要求的批量修改不做
对外契约 vs 内部词汇码表一次定死（1010 早在 S1 就位）；哨兵按需生长（今天补上）

卡壳时查什么

正文自足，只有两种情况出去查：

  • errors.Is 的认链规则：回 S1·D4 的哨兵一节——「%w 包装仍认出、%v 拍扁即断链」那两条测试用例就是答案。
  • 409 Conflict 的原始语义：MDN · 409（可选，重点读「与服务器当前资源状态冲突」这句，正好覆盖 1006/1009/1010 三兄弟）。

状态类 bug 的调试铁律：先 GET 把当前状态打出来，再试操作。409 的含义是「请求没错、时机不对」——所以排错不是改请求，而是看资源现在处于什么状态、哪条守门规则拦住了它。curl 一次 GET，对着树上的 archived 标记读一遍，答案通常就在那里。
