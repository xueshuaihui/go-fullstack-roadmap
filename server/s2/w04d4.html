错误处理收口：FailErr 与哨兵映射

D5 埋的 version 字段今天启用。上半场讲一个真实到不能再真实的问题——丢失更新，并用乐观锁解决它：第七个哨兵 ErrVersionConflict 落地，PUT 带上版本凭据，不匹配就是 409 + 1009。下半场把这两个星期长出来的错误处理收口成纪律：错误在内层产生、在边界翻译，翻译点全站只有一个——FailErr。

今日目标

知识讲义

1. 丢失更新：两个写者的故事

妈妈在手机上打开「餐饮」的编辑页（看到 version:1），把名字改成「美食」；同一时刻爸爸在电脑上打开同一个编辑页（也看到 version:1），把图标改成 food。妈妈先提交，成功，version 变 2；爸爸随后提交——如果服务端来者不拒，爸爸的请求体里没有妈妈改的名字，落库后「美食」被覆盖回「餐饮」。妈妈的修改无声消失，没有任何报错。这就是丢失更新（lost update）：两个写者都基于同一份旧数据修改，后写的把先写的抹掉了。

注意它和 D8 的 1010 不同：1010 是「资源状态不允许这个操作」，规则写在业务里；丢失更新是「资源在你编辑期间被别人动过」，服务端需要知道你手里的数据是哪一版才能察觉。

2. 乐观锁：带着凭据来写

解法就是把「你看到的是哪一版」随请求带上：每次读响应里都有 version；PUT 时把它原样放回请求体；服务端写回前比对——凭据与当前版本一致才放行（写入后 version +1），不一致说明有人先你一步改过，拒绝：409 + 1009。客户端的闭环动作也定死：收到 1009 → 重新 GET 最新数据 → 把用户的新意图合并上去 → 带新凭据重试，绝不拿着旧凭据硬重试。

为什么叫「乐观」？因为它不提前上锁，乐观地假设冲突很少发生，冲突真来了再拒绝——对家庭系统这种低并发场景是最划算的选择。悲观锁（先锁住再编辑）会让「打开编辑页」变成一个持有资源的操作，复杂且没必要。

今天 service 的实现是「读出来 → 比对 → 写回」三步，check 与 write 之间理论上还有一条极窄的竞态缝（两个请求同时通过比对）。教学期单进程内存版可以接受；S3 换成数据库后，这条缝被一条原子语句焊死：UPDATE … SET version = version + 1 WHERE id = ? AND version = ?——影响行数为 0 就是冲突。规则不变，缝隙消失，这正是分层的好处：今天把规则立对，将来只换 repo 的实现。

兼容窗口：expectedVersion == 0（客户端没带凭据，binding 是 omitempty,gt=0）时跳过比对。这是给旧测试与教学脚本留的过渡；S4 契约成熟后，PUT 不带 version 将直接 400。今天起，自己写的每个 PUT 都必须带凭据。

3. 收口：错误的产生、传递、翻译各在一层

两周下来错误处理已经长成一套体系，今天把它说破、然后用 grep 钉死：

环节住在哪纪律
产生service / repo只造错误：fmt.Errorf("…: %w", 哨兵)；不 import gin，不 import net/http——内层不知道 HTTP 的存在
传递逐层 return每层用 %w 补上下文再抛；禁止 %v 拍扁断链
翻译handler 边界拿着 error 的出口只有 response.FailErr(c, err)：CodeOf 认哨兵 → 码，HTTPStatus 码 → 状态

response.Fail(c, …) 手写码的合法场合只剩两处，共同点是手里根本没有 error：装配根的 NoRoute（路由没命中，无人抛错）和 pathID 的解析失败（strconv 的错不值得进哨兵体系，就地写 400 + 1004）。除此之外 handler 里出现 response.Fail( 即为违纪。

收口的价值在 S3 会兑现：换存储时如果错误翻译散落在 repo 里（比如 repo 直接写 HTTP 响应），换一次库就得重译一遍；而现在 repo 只抛哨兵，换库换不掉错误契约。

4. 哨兵集成熟：七个够了

哨兵码 / HTTP什么时候抛
ErrNotFound1001 / 404按 id 查无此物（或不属于本家庭）
ErrForbidden1003 / 403越权（S4 鉴权后大量使用）
ErrInvalidParam1004 / 400业务规则拒绝：第三级、半组重排、收支不一致…
ErrConflict1006 / 409唯一约束冲突（S6 账户名重名）
ErrVersionConflict1009 / 409乐观锁凭据对不上（今天落地）
ErrStateNotAllowed1010 / 409业务状态不允许（D8 停用守门）
ErrInternal5000 / 500内部故障；认不出的错误也回落到这

到此哨兵集成熟收口：S2 剩余两天不再生长；S3/S4 若需要新哨兵（比如领域专属错误），照 D8 的生长流程办——加一个 var、加一个 case、补测试，码表始终不动。

步骤 1 · 第七个哨兵

完整 · server/pkg/response/errors.go（覆盖 D8 版本；code.go 依旧不动）package response

import "errors"

// 哨兵错误集：repo/service 层往上抛的就是这些值，
// FailErr 用 errors.Is 认出它们并翻译成对应错误码。
// 码表是对外契约一次定死；哨兵是内部词汇，S2·D10 起成熟收口（七个）。
var (
    ErrNotFound        = errors.New("not found")         // → 1001 / 404
    ErrForbidden       = errors.New("forbidden")         // → 1003 / 403
    ErrInvalidParam    = errors.New("invalid param")     // → 1004 / 400
    ErrConflict        = errors.New("conflict")          // → 1006 / 409
    ErrVersionConflict = errors.New("version conflict") // → 1009 / 409
    ErrStateNotAllowed = errors.New("state not allowed") // → 1010 / 409
    ErrInternal        = errors.New("internal error")    // → 5000 / 500
)

// CodeOf 把哨兵错误翻译成业务码；认不出来的一律 5000。
// 注意 errors.Is 而不是 ==——链被包装过也要认得出来。
func CodeOf(err error) int {
    switch {
    case err == nil:
        return CodeOK
    case errors.Is(err, ErrNotFound):
        return CodeNotFound
    case errors.Is(err, ErrForbidden):
        return CodeForbidden
    case errors.Is(err, ErrInvalidParam):
        return CodeInvalidParam
    case errors.Is(err, ErrConflict):
        return CodeConflict
    case errors.Is(err, ErrVersionConflict):
        return CodeVersionConflict
    case errors.Is(err, ErrStateNotAllowed):
        return CodeStateNotAllowed
    default:
        return CodeInternal
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
把 version 当「编辑次数」随便填客户端回传 version:99 想「跳过检查」，收 409 一头雾水凭据只能来自最近一次读响应，原样回传；对不上就重拉
收 1009 后拿旧凭据硬重试永远 409，死循环闭环是「重新 GET → 合并意图 → 带新凭据重试」
版本比对放在规则校验之后凭据明明是旧的，却先收到 1004 规则错，客户端误判顺序：存在（1001）→ 凭据（1009）→ 规则（1004）
repo.Update 里也做版本比对同一规则两处实现，改一漏一规则住 service；repo 只管存取（S3 的条件 UPDATE 是原子性加固，不是第二份规则）
handler 里手写 Fail(c, 409, 1009, …)翻译逻辑散落，与 FailErr 打架；改映射时漏改拿着 error 只走 FailErr；Fail 只留给 NoRoute 与 pathID
service 里 import net/http 判状态码内层被 HTTP 词汇污染，S3 换存储时错误契约跟着晃内层只认哨兵；今天起 grep 纪律检查兜底
抛 1009 时用 %v 拼哨兵链断，回落 5000/500，客户端把「版本冲突」当「服务器炸了」fmt.Errorf("…: %w", response.ErrVersionConflict)

今日名词卡

术语一句话解释
丢失更新（lost update）两写者基于同一旧数据修改，后写者无声覆盖先写者
乐观锁不提前上锁，写回时比对版本凭据，冲突了再拒绝——低并发场景最划算
版本凭据（version）「我编辑时看到的是第几版」；随 PUT 原样回传，写入成功则 +1
ErrVersionConflict第七个哨兵：凭据对不上 → 1009 / 409
1009 客户端闭环重新 GET → 合并用户意图 → 带新凭据重试；绝不旧凭据硬重试
错误收口产生（内层 %w 包哨兵）→ 传递（逐层 return）→ 翻译（边界 FailErr 唯一出口）
Fail 的两处合法场合NoRoute 与 pathID：共同点是手里没有 error
先验存在、再验凭据、后验规则Update 的检查顺序：1001 → 1009 → 1004

卡壳时查什么

正文自足，只有两种情况出去查：

  • 乐观锁在真实系统里的形态：回 S1·D4 的码表——1009 的注释「乐观锁 version 不匹配」从第一天就在合同里，今天是它第一次有血有肉。
  • errors.Is 与 %w 的链：errors 包文档（可选，重点读 wrap/unwrap 一段）。

版本类 bug 的调试铁律：把两边的 version 都打出来。409 的本质是「凭据 ≠ 当前」，service 的错误信息里两个数都带着（这正是 %w 包装时把上下文写足的回报）；对着日志读一眼，立刻知道是客户端没重拉数据，还是服务端哪次写入多涨/少涨了版本。
