DTO 与领域模型：为什么要分开

昨天立了干干净净的 Category 领域模型（零标签），前天写了带 binding 标签的临时 categoryReq。今天把两者正式接起来：DTO（数据传输对象）管线上形状，领域模型管业务概念，转换函数是两者之间唯一的桥。「直接拿 model 绑定请求、拿 model 序列化响应」看起来省两个文件，实际是把三张不同的合同糊成一张——今天讲清楚为什么。

今日目标

知识讲义

1. 不分家会发生什么：三份合同糊成一份

一个 struct 直接既当 model、又当请求体、又当响应体，等于让三份本应独立的合同共用一张纸：

合同和谁签的变化节奏
存储形状和数据库（S3 起加列、改类型）随业务演进
请求形状和调用方的「能改什么」随权限与安全策略
响应形状和客户端的「能看什么」一旦发布就要向后兼容

糊在一起的直接后果：S3 给表加一列，model 加一个字段，响应 JSON 立刻多出一个键——客户端没同意过这个变更；反过来，客户端要求响应里 parent_id 改名，你改 json 标签时顺手把存储映射也改了。分家之后：model 归 model，DTO 归 DTO，谁变都不惊动谁。

2. 四条理由，逐条过

  • 合同稳定：接口契约（响应字段名）一经客户端使用就不能随便动；领域模型随 DB 与业务变。分开后，model 改名不影响 API，API 改版不动存储。
  • 字段白名单（安全）：请求 DTO 里没有 ID、FamilyID、Archived、Sort 这些字段——客户端想传都没处传。若直接绑定 model，攻击者发一个 {"name":"x","family_id":2,"id":99} 就可能把数据写进别人家庭。这类漏洞有个名字：批量赋值（mass assignment）；白名单式 ToModel 是它的标准解法。
  • 关注点分离：binding 标签是 HTTP 校验概念、json 标签是序列化概念——写在 model 上，等于领域模型「认识」了 HTTP。昨天的 grep 纪律（finance 下无 gin）今天延伸一步：model 下也无任何标签。
  • 形状自由：Go 用 PascalCase、线上契约用 snake_case；响应有时要拼树（D7 的 children）、有时要裁剪字段。DTO 层让「线上长什么样」成为一个可以独立设计的决定。

3. 请求一个 struct、响应一个 struct，不复用

CategoryReq 与 CategoryResp 字段高度重叠，也不合并成一个。因为两个方向的合同本来就不同：请求里有 version（乐观锁凭据，D10 启用）但没有 id/archived；响应里有 id/archived/sort 但客户端改不了它们。省一个文件的代价是「哪个字段哪个方向有效」全靠脑记——不省。

4. 转换函数住在哪、写什么

转换是 HTTP 边界的事，所以住在 handler 包（model 包谁也不 import，昨天立的）。写法就一个原则：显式逐字段，不用反射魔法。多写十行，换来「每个字段的去向都能用眼睛审计」。

今日增量（在学习仓里落盘）

步骤 1 · dto.go

完整 · server/internal/finance/handler/dto.gopackage handler

import "homecube/internal/finance/model"

// CategoryReq 创建/编辑分类的请求 DTO。
// binding 标签只允许出现在这一层。注意这里没有 ID/FamilyID/Sort/Archived——
// 客户端无权指定的字段，在请求形状里就不该存在（白名单，挡批量赋值）。
type CategoryReq struct {
    Name     string `json:"name" binding:"required,min=1,max=32"`
    Icon     string `json:"icon" binding:"omitempty,max=64"`
    Kind     string `json:"kind" binding:"required,oneof=expense income"`
    ParentID int64  `json:"parent_id" binding:"omitempty,gt=0"`
    Version  int    `json:"version" binding:"omitempty,gt=0"` // PUT 的乐观锁凭据，D10 启用校验
}

// CategoryResp 分类的响应 DTO。线上契约：snake_case，字段一个不多一个不少。
type CategoryResp struct {
    ID       int64  `json:"id"`
    ParentID int64  `json:"parent_id"`
    Name     string `json:"name"`
    Icon     string `json:"icon"`
    Kind     string `json:"kind"`
    Sort     int    `json:"sort"`
    Archived bool   `json:"archived"`
    Version  int    `json:"version"`
}

// ToModel 请求 DTO → 领域模型。只搬「客户端有权指定」的字段；
// ID/Sort/Archived/Version/时间戳由服务端决定，绝不从请求带入。
func ToModel(req CategoryReq, familyID int64) model.Category {
    return model.Category{
        FamilyID: familyID,
        ParentID: req.ParentID,
        Name:     req.Name,
        Icon:     req.Icon,
        Kind:     req.Kind,
    }
}

// ToResp 领域模型 → 响应 DTO。FamilyID、时间戳不出门：客户端不需要，也不该拿到。
func ToResp(c model.Category) CategoryResp {
    return CategoryResp{
        ID:       c.ID,
        ParentID: c.ParentID,
        Name:     c.Name,
        Icon:     c.Icon,
        Kind:     c.Kind,
        Sort:     c.Sort,
        Archived: c.Archived,
        Version:  c.Version,
    }
}

// ToRespList 批量转换：保持入参顺序（service 已排好）。
func ToRespList(cs []model.Category) []CategoryResp {
    out := make([]CategoryResp, 0, len(cs))
    for _, c := range cs {
        out = append(out, ToResp(c))
    }
    return out
}

常见坑（新手 100% 会踩）

坑现象正确姿势
直接拿 model 绑定请求客户端能指定 id/family_id/archived——批量赋值漏洞请求只进 CategoryReq，经 ToModel 白名单转换
请求/响应复用一个 DTO「这个字段这个方向有效吗」全靠脑记，文档没法写Req 与 Resp 各一个，字段差异摆在明面上
json 标签拼错parentId 混进 snake_case 契约，客户端解析到 undefined契约统一 snake_case；D9 的测试会把响应字段名钉死
model 加了字段忘改 ToResp新字段永远不出现在响应里，编译器不报错纪律：model 加字段 → 同一次提交里过一遍 ToModel/ToResp；D9 的形状断言兜底
把转换函数放进 model 包model 开始 import handler 的概念，依赖方向倒转（或循环 import）转换住 handler 包；model 谁也不 import
用反射库「自动转换」字段映射躲进反射，改名不报错、白名单失守显式逐字段；十行样板换全字段可审计
ToResp 把 FamilyID 也带出去内部标识外泄，将来想改家庭隔离实现都被客户端盯着响应字段 = 客户端需要的最小集合

今日名词卡

术语一句话解释
DTO（数据传输对象）描述「线上形状」的 struct：请求一个、响应一个，标签只在这层
领域模型描述业务概念的 struct（昨天的 Category），零标签、谁也不 import
批量赋值（mass assignment）攻击者多传内部字段（family_id/id）试图越权写入；白名单 DTO 使其无处落脚
白名单式转换ToModel 只搬「客户端有权指定」的字段，其余服务端说了算
snake_case 契约线上 JSON 字段全小写下划线；Go 侧 PascalCase，由 json 标签桥接
omitempty（json 侧）序列化时零值省略字段。本站响应 DTO 不用它——契约字段必须每次都在，客户端才能无脑解析
version 字段请求里是乐观锁凭据（D10 启用）；响应里是当前版本号，客户端改完要带回来
archived 字段响应里的停用标记（D8 讲语义）；请求里没有——停用走专门接口

卡壳时查什么

正文自足，只有两种情况出去查：

  • json 标签的完整语法：encoding/json · Marshal（可选，读「The encoding of each struct field」一段就够）。
  • 批量赋值的经典案例：搜「mass assignment vulnerability」（可选，看别人怎么栽的，比正面教材记得牢）。

形状类 bug 的调试铁律：把响应的 body 原文打出来逐键对照 DTO——多了哪个键（model 漏进来了？）、少了哪个键（ToResp 漏搬了？）、名字不对（json 标签拼错？），三种病一眼分清。D2 的表驱动测试加一条「响应必含八个键」的断言，这类 bug 就再也过不了夜。
