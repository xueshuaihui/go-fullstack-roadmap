Gin 中间件：request-id、recovery 与请求日志

S1·D9 你手写过标准库版中间件：func(http.Handler) http.Handler，洋葱模型，request-id 和 recover 两件套。今天把它们换成 Gin 原生形态——签名从「包 handler」变成「gin.HandlerFunc + c.Next()」，洋葱还是那颗洋葱。顺手补上第三件：请求日志（AccessLog），每条请求记方法、路径、状态、耗时、request-id。旧的标准库版今天删除——死代码也是反例③的亲戚。

今日目标

知识讲义

1. 两种形态，一颗洋葱

标准库版（S1·D9）Gin 版（今天）
中间件是什么func(http.Handler) http.Handler：收一个 handler，返回包了皮的 handlerfunc(c *gin.Context)：engine 把它排进 handler 链
「放行给里层」next.ServeHTTP(w, r)c.Next()
洋葱前半 / 后半调用 next 之前 / 之后c.Next() 之前 / 之后，完全同构
装配方式手工嵌套 withA(withB(mux))engine.Use(A(), B())，顺序 = 从外到内

一个容易误会的细节：Gin 中间件里就算忘了调 c.Next()，后面的 handler 也会执行（函数返回后引擎继续走链）——但你的「后半段」代码会在 handler 之前跑完，耗时统计直接归零。所以纪律是：凡是想在响应阶段干活的中间件，必须显式 c.Next()，后半段代码写在它后面。另有 c.Abort()：拦住后续 handler 不再执行（S4 鉴权拒绝时用它），但它不会中断当前函数——Abort 之后该 return 还是要 return。

2. 为什么自写 Recovery，不用 Gin 内置的

panic/recover 的机制 S1·D9 补过半页教学，这里只复习结论：recover 只在 defer 里生效；没人兜住的 panic 崩掉整个进程。Gin 内置的 Recovery() 确实能兜住，但它兜住之后返回的是裸文本 500——客户端拿不到三键信封，解析直接炸；它打的日志也是自己的格式，不带我们的 request-id。所以自写：

  • 兜住 panic → 500 + 5000 统一信封（response.Fail 写）；
  • 堆栈 debug.Stack() 进服务端日志，绝不进响应——内部细节外泄是事故报告写给自己看的部分。

3. AccessLog：一条请求一行账

S1 的请求日志靠 net/http 之外的手工打印，不成体系。今天起每个请求进出都记一行：方法、路径、状态码、耗时、request-id。实现就是标准洋葱：c.Next() 前记开始时间，之后算 time.Since(start) 并读 c.Status()。time.Now/time.Since 照抄即可（S5 讲并发时 time 会再次上场）。这一行账就是将来排查「用户说接口 500 了」的第一现场：拿用户报的 request-id 在日志里一搜，方法路径状态耗时全在。

4. 注册顺序：每个位置都有理由

片段 · 前置：三个中间件已定义engine.Use(middleware.RequestID(), middleware.AccessLog(), middleware.Recovery())
// 洋葱从外到内：RequestID → AccessLog → Recovery → 路由与 handler
  • RequestID 最外层：它要在任何响应头发出之前盖好 X-Request-ID——包括 panic 的 500。和 S1·D9 的理由一致。
  • Recovery 最内层（紧贴 handler）：handler panic 时它先兜住、写好 500 信封再正常返回——于是外层的 AccessLog 后半段照常执行，这条 500 也能被记进日志。把 Recovery 放到 AccessLog 外面试试？panic 会穿透 AccessLog 的后半段，日志里恰恰丢掉最该记的那条 500。
  • 顺序口诀：身份证最外，账本次之，保命符最里。

5. c.Set：gin.Context 的随身背包

RequestID 中间件除了写响应头，还要 c.Set("request_id", id)——把 id 塞进 Context 的键值背包，后面的 AccessLog、handler（S4 起还有鉴权写入的 userID/familyID）都用 c.GetString/c.GetInt64 取。键名是全站约定，不许自创缩写：将来在别处取不到值，十有八九是键名打错了。

步骤 1 · Gin 版三件套

完整 · server/internal/platform/middleware/gin.gopackage middleware

import (
    "crypto/rand"
    "encoding/hex"
    "log"
    "net/http"
    "runtime/debug"
    "time"

    "github.com/gin-gonic/gin"

    "homecube/pkg/response"
)

// RequestID 给每个响应盖 X-Request-ID：客户端带了合法的就沿用，否则生成。
// 同时塞进 Context 背包（键名 request_id 是全站约定），供日志与后续 handler 取用。
func RequestID() gin.HandlerFunc {
    return func(c *gin.Context) {
        id := c.GetHeader("X-Request-ID")
        if id == "" || len(id) > 64 {
            id = newRequestID()
        }
        c.Header("X-Request-ID", id) // 必须在任何响应写出之前——洋葱最外层的意义
        c.Set("request_id", id)
        c.Next()
    }
}

// newRequestID 生成 8 字节随机数的十六进制串（16 个字符）。身份类随机一律 crypto/rand。
func newRequestID() string {
    b := make([]byte, 8)
    if _, err := rand.Read(b); err != nil {
        panic(err) // 系统级随机源故障，属于「程序没法继续」级别的事故
    }
    return hex.EncodeToString(b)
}

// AccessLog 一条请求一行账：方法、路径、状态、耗时、request-id。
// 后半段写在 c.Next() 之后——那里才拿得到最终状态码。
func AccessLog() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()          // time 照抄即可，S5 再正式打交道
        c.Next()
        log.Printf("%s %s %d %s rid=%s",
            c.Request.Method, c.Request.URL.Path,
            c.Status(), time.Since(start),
            c.GetString("request_id"))
    }
}

// Recovery 是 HTTP 边界的保命符：兜住 panic，换 500 + 5000 统一信封，堆栈进日志。
// 注册在最内层（紧贴 handler），兜住后外层 AccessLog 仍能记下这条 500。
func Recovery() gin.HandlerFunc {
    return func(c *gin.Context) {
        defer func() { // recover 只能活在 defer 里（S1·D9）
            if e := recover(); e != nil {
                log.Printf("panic: %s %s: %v\n%s",
                    c.Request.Method, c.Request.URL.Path, e, debug.Stack())
                response.Fail(c, http.StatusInternalServerError,
                    response.CodeInternal, "服务器内部错误")
            }
        }()
        c.Next()
    }
}

步骤 3 · Gin 版测试

完整 · server/internal/platform/middleware/gin_test.gopackage middleware

import (
    "net/http/httptest"
    "strings"
    "testing"

    "github.com/gin-gonic/gin"
)

// newTestEngine 组装一个和生产同顺序的测试引擎。
// gin.TestMode：让测试输出不刷 debug 警告（D11 起由 env 的 GIN_MODE 统一管理）。
func newTestEngine() *gin.Engine {
    gin.SetMode(gin.TestMode)
    e := gin.New()
    e.Use(RequestID(), AccessLog(), Recovery())
    return e
}

func TestRecoveryKeepsEnvelope(t *testing.T) {
    e := newTestEngine()
    e.GET("/boom", func(c *gin.Context) { panic("boom") }) // 只活在测试里的炸弹

    w := httptest.NewRecorder()
    e.ServeHTTP(w, httptest.NewRequest("GET", "/boom", nil))

    if w.Code != 500 {
        t.Fatalf("状态码 = %d, want 500", w.Code)
    }
    if !strings.Contains(w.Body.String(), `"code":5000`) {
        t.Fatalf("body = %s, want 三键信封 + 5000", w.Body.String())
    }
    if w.Header().Get("X-Request-ID") == "" {
        t.Fatal("panic 的 500 也必须带 X-Request-ID")
    }
}

func TestRequestIDReuseAndGenerate(t *testing.T) {
    e := newTestEngine()
    e.GET("/ok", func(c *gin.Context) { c.Status(204) })

    w := httptest.NewRecorder()
    e.ServeHTTP(w, httptest.NewRequest("GET", "/ok", nil))
    if got := w.Header().Get("X-Request-ID"); len(got) != 16 {
        t.Fatalf("生成的 X-Request-ID = %q, want 16 个十六进制字符", got)
    }

    w2 := httptest.NewRecorder()
    req := httptest.NewRequest("GET", "/ok", nil)
    req.Header.Set("X-Request-ID", "trace-me-002")
    e.ServeHTTP(w2, req)
    if got := w2.Header().Get("X-Request-ID"); got != "trace-me-002" {
        t.Fatalf("客户端传入的 id 应被沿用，got %q", got)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
忘了 c.Next() 却在函数尾部统计耗时日志里耗时恒为 0、状态码恒为 200——后半段在 handler 之前就跑完了响应阶段的活写在 c.Next() 之后
Recovery 装在 AccessLog 外层handler panic 时日志里恰恰没有那条 500（panic 穿透了 AccessLog 的后半段）顺序：RequestID → AccessLog → Recovery；保命符紧贴 handler
用 gin.Default() 又 Use 自己的三件套Logger/Recovery 双份，日志重复、500 响应可能被写两次New() + 只装自己的一套
c.Abort() 后不 returnAbort 只拦后续 handler，当前函数剩下的代码照跑，可能把响应写第二遍c.Abort() 紧跟 return（S4 鉴权会用到）
在 c.Next() 之后改响应头静默无效——头早随 body 发出了（S1·D6 的笔顺依旧成立）中间件后半段只做日志、统计这类不碰响应的事
删了旧中间件没删旧测试undefined: WithRequestID，编译红实现与测试同一次提交里删干净
测试里不设 gin.TestMode输出刷满 [GIN-debug] 警告，断言淹没在噪音里gin.SetMode(gin.TestMode) 放测试引擎工厂里

今日名词卡

术语一句话解释
gin.HandlerFuncGin 中间件/handler 的统一签名 func(*gin.Context)；洋葱模型与标准库版同构
c.Next()放行给链上的下一层；它之前是洋葱前半，之后是后半
c.Abort()拦住后续 handler；不中断当前函数，后面要手动 return。S4 鉴权正式用
c.Set / c.GetStringContext 的随身背包：跨中间件传值；键名 request_id 是全站约定
AccessLog请求日志中间件：方法、路径、状态、耗时、request-id 一行账
time.Since(start)= time.Now().Sub(start)，耗时统计的标准写法（照抄，S5 再深交）
c.Status()当前已写出的 HTTP 状态码；没写过时是默认 200
gin.TestModeGin 的测试运行模式：静音 debug 输出；D11 起由 GIN_MODE 环境变量管理
结构化日志每条日志带 request-id 等可检索字段。S5 正式建；今天的 AccessLog 是它的前身

卡壳时查什么

正文自足，只有两种情况出去查：

  • Gin 中间件的官方口径：Gin 文档 · Using Middleware（可选，十分钟，和今天的自写版对照读）。
  • panic/recover 机制忘了：回 S1·D9 的「半页最小教学」一节重读，再回来。

中间件类 bug 的调试铁律照旧：把洋葱一层层剥开单独测——Use 里只留一个中间件跑测试，逐层加回去，哪一层加进去断言碎了，问题就在哪层。顺序类 bug 则在纸上画洋葱：标出 panic 从哪层冒出来、被哪层兜住、哪几层的后半段还会执行。
