S2 · DAY 4 预计 30 分钟 难度 ★★☆☆☆

项目分层：handler / service / repo 各管什么

S1·D11 把 handler 从 main.go 归置进 internal/，那是分层的雏形：一层。本周六要落地 6 条真业务接口，一层不够用了——分类有规则（父级校验、停用约束、排序），规则不能长在 HTTP 翻译代码里。今天正式开三层：handler 翻译、service 规则、repo 存取，并落盘第一个业务模块 internal/finance 的领域模型与仓储接口。S1·D5 立的 FamilyRepository 模式，今天在真业务里第二次登场。

今日目标

知识讲义

1. 为什么要三层：一种变化只砸中一层

软件分层的唯一理由是变化。看这个模块接下来两周会发生的三种变化：

  • HTTP 形状变了（加字段、改校验）→ 只该砸中 handler；
  • 业务规则变了（停用约束调整）→ 只该砸中 service；
  • 存储换了（S3：内存 map → Postgres）→ 只该砸中 repo 的实现。

如果不分层，三种变化全砸进同一个函数：一个 handler 里既有绑定校验、又有业务 if、又有 map 读写——S1 的 ping 骨架就是这样，20 行还行，6 条接口就是 6 坨。分层的成本是多写几个文件和转换函数，回报是每次变化的影响范围可预期。

2. 三层职责表（背下来）

层负责允许依赖禁止
handler（翻译层）HTTP ↔ 业务的双向翻译：绑定请求（D2）、DTO 转换（D5）、调 service、把 error 翻译成统一信封service、model、pkg/response、gin写业务规则；碰存储细节
service（规则层）业务规则的全部所在：父级校验、停用约束（D8）、排序规则（D7）、乐观锁（D10）repo 接口、model、pkg/response（只为哨兵错误）import gin 或 net/http；知道「请求」「响应」为何物
repo（存取层）存取词汇表：List/Get/Create/Update，今天内存 map、S3 换 Postgresmodel、pkg/response（哨兵）import gin；写业务规则；返回 HTTP 状态码

横切住户依旧是 internal/platform/（中间件、D11 的 config）——它不属于任何业务模块。而 model（领域模型）谁都可以依赖，它自己不依赖任何人。

3. 依赖方向：接口是「换实现」的接缝

结构 · 依赖方向（箭头 = import）main.go（装配根）
   │ 组装：repo实现 → service → handler → 路由
   ▼
handler ──▶ service ──▶ CategoryRepository（接口，住在 repository 包）
                              ▲
                              │ 满足（隐式实现，S1·D5）
              MemoryCategoryRepo（D6 落盘；S3 再加一个 GORM 实现）

service 只认接口这份「存取词汇表」，不认具体实现。S3 换 Postgres 时，新写一个满足同一接口的实现、在装配根换一行 New——service 与 handler 一行不改。这就是 S1·D5 那句「S3 换数据库时只写一个新实现」的完整机制。另外注意 repo 的错误词汇是哨兵不是状态码：查无此行返回 %w 包装的 ErrNotFound，翻译成 404 + 1001 是 handler（FailErr）的事——repo 压根不知道 HTTP 为何物。

4. Category 领域模型：每个字段都有来历

字段说明
ID int64主键；Go 侧全期 int64（S3 对 DB 的 BIGSERIAL）
FamilyID int64数据属于哪个家庭。S2 教学期固定为 1；S4 起由登录态注入，且每条查询必带——今天先把它做成 repo 每个方法的参数，习惯先于机制
ParentID int640 = 一级分类；非 0 = 挂在某个一级下。树只有两级，规则 D7 落地
Name / Icon / Kind名称、图标、收支类型（expense/income 二选一）
Sort int同级内排序，越小越靠前；D7 讲透
Archived bool停用标记：不删数据，历史流水仍可引用；D8 讲透
Version int乐观锁：写一次 +1，防止「拿旧数据覆盖新数据」；D10 启用校验
CreatedAt / UpdatedAttime.Time，照抄即可；S3 建表时对上 TIMESTAMPTZ 列再正式讲

领域模型上没有任何标签——没有 json、没有 binding、没有 gorm。它只描述业务概念本身；「怎么上线」「怎么进库」是 DTO（明天）和 repo 实现（S3）的事。

步骤 1 · 领域模型

完整 · server/internal/finance/model/category.gopackage model

import "time" // time.Time 照抄即可，S3 建表时正式讲

// Category 财务分类的领域模型。
// 身上没有任何 json/binding/gorm 标签：它只描述业务概念，
// 「怎么上线」是 DTO 的事（D5），「怎么进库」是 repo 实现的事（S3）。
type Category struct {
    ID        int64
    FamilyID  int64 // S2 教学期固定为 1；S4 起由登录态注入
    ParentID  int64 // 0 = 一级分类；树只有两级
    Name      string
    Icon      string
    Kind      string // "expense" 支出 / "income" 收入，二选一
    Sort      int    // 同级内排序，越小越靠前
    Archived  bool   // 停用标记：不删数据（D8）
    Version   int    // 乐观锁：写一次 +1（D10 启用校验）
    CreatedAt time.Time
    UpdatedAt time.Time
}

// Kind 的两个合法值落成常量，全仓引用它，不许手写裸字符串。
const (
    KindExpense = "expense"
    KindIncome  = "income"
)

D2 的 binding 标签里 oneof=expense income 是字符串字面量——标签里没法引用常量，这是 Go 标签的局限；但 Go 代码里（service 的校验、测试的断言）一律用 model.KindExpense，改拼写时编译器替你全仓点名。

步骤 2 · 仓储接口

完整 · server/internal/finance/repository/category.gopackage repository

import "homecube/internal/finance/model"

// CategoryRepository 约定「分类」的存取词汇表。
// 只谈存取，不谈 HTTP、不谈业务规则。每个方法都带 familyID——
// S4 之前它是教学常量，S4 之后它来自登录态，但「查询必带家庭」的习惯从今天养成。
type CategoryRepository interface {
    // List 返回该家庭全部分类（含已停用）。顺序不保证——排序是 service 的职责。
    List(familyID int64) ([]model.Category, error)

    // Get 按 id 取一条；查无或不属于该家庭，返回 %w 包装的 response.ErrNotFound。
    Get(familyID, id int64) (model.Category, error)

    // Create 存入新分类；实现负责分配 ID、置 Version=1、盖时间戳（写入 c 后带回）。
    Create(c *model.Category) error

    // Update 整行更新；实现负责 Version +1、刷 UpdatedAt、保留 CreatedAt。
    Update(c model.Category) error
}

接口注释里写清错误词汇（哪个方法在什么情况下返回什么哨兵）——接口是契约，契约就得把失败分支也写进去，这是 S1·D4「error 是值、要包装」在接口设计上的延伸。

常见坑（新手 100% 会踩）

坑现象正确姿势
service 里 import gin「顺手」用 c.GetInt64 取参数——业务规则从此绑死 HTTPservice 的方法签名只收普通参数（familyID、id、model），HTTP 的事 handler 全包
repo 返回 HTTP 状态码repo 里出现 404、return nil, errors.New("404")repo 只说哨兵词汇（ErrNotFound），翻译是 handler/FailErr 的事
handler 越过 service 直调 repo「就查一下，没必要过 service」——两周后规则无处安放handler 只认 service；查询也是业务（谁能看、看什么顺序）
给 model 加 json 标签领域模型开始「知道」线上形状，D5 的 DTO 白分家标签只出现在 DTO 上；model 干干净净
为每个 struct 都抽接口满仓库单实现接口，纯增噪音（S1·D5 的老坑）repo 抽接口是因为 S3 要换实现；service 今天就是具体 struct
三层变「三层转发」后删掉 service「service 只是转调 repo，没用」——D7/D8/D10 的规则一来，全塞回 handler薄是阶段性的；规则会长出来，位置先留好
循环 importmodel import repository、repository import model，编译直接报错依赖只朝一个方向：repository → model；model 谁也不 import

今日名词卡

术语一句话解释
三层架构handler（翻译）/ service（规则）/ repo（存取）；一种变化只砸中一层
领域模型（domain model）只描述业务概念的 struct，无任何框架标签；今天的是 Category
仓储接口（Repository）存取词汇表；接口在包 repository，实现可换（内存 → Postgres）
依赖方向handler → service → repo 接口 ← 实现；箭头只朝下，model 在最底
装配根main.go：唯一知道「具体实现是谁」的地方，负责把三层接起来
哨兵错误词汇repo/service 用 %w 包装的 response.ErrXxx 表达失败；不出现状态码
乐观锁 version写一次 +1 的版本号；D10 启用「版本不符拒改」（1009）
familyID数据归属的家庭；S2 教学期为常量 1，S4 起来自登录态、查询必带
横切关注点不属于任何业务模块的事（中间件、config），住 internal/platform/

卡壳时查什么

正文自足，只有两种情况出去查：

  • 接口与隐式实现忘了：回 S1·D5 重读「方法集」与「Repository 模式」两节——今天的接口就是那个模式的第二次落地。
  • 分层与「整洁架构」的关系：网上说法五花八门（可选）。本站口径就一张职责表，不引入更多层名词；够用两周，也够用两年。

分层类困惑的调试铁律：拿一个具体变化问「它该砸中哪层」。「把分类名上限从 32 改成 64」→ handler 的 binding 标签；「禁止停用还有子级的分类」→ service 的规则；「map 换成数据表」→ repo 的实现。如果某个变化你找不到唯一归属层，说明有代码住错了地方。
