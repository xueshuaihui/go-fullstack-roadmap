请求绑定与 validator

S1·D8 你手写过请求解析：json.NewDecoder 解码、逐字段 if 校验、手写 400。今天看 Gin 怎么把这两步合成一步——c.ShouldBindJSON：解码 + 按 binding 标签自动校验。落地的骨架是周六的主角之一：POST /api/finance/categories（创建分类），今天先让它「绑得对、错得整齐」，业务逻辑周六接上。

今日目标

知识讲义

1. ShouldBindJSON = 解码 + 校验一步到位

对照 S1·D8 的手写版，Gin 的绑定做了同样的两件事，但把第二件也接管了：

步骤S1 手写（标准库）Gin
解码 body 到 structjson.NewDecoder(r.Body).Decode(&req)c.ShouldBindJSON(&req) 一个调用
逐字段校验手写一串 if req.Name == "" { … }

校验规则不再写成 if 语句，而是声明在 struct 标签里——Gin 内置了 go-playground/validator 这个校验库，读的就是 binding 标签。Gin 里每个绑定函数都有两族：

  • ShouldBindJSON(&req)：出错只返回 error，响应写什么由你决定。
  • BindJSON(&req)：出错时自动写一个 400——但格式是 Gin 自己的，不是我们的三键信封。

全站纪律：只用 Should* 一族。理由和昨天不用 gin.Default() 一模一样——响应的形状必须收在 pkg/response 手里，任何「框架自动写响应」的行为都是信封合同的漏洞。

2. 五个标签够用两周

片段 · 前置：无，直接读type categoryReq struct {
    Name     string `json:"name" binding:"required,min=1,max=32"`
    Icon     string `json:"icon" binding:"omitempty,max=64"`
    Kind     string `json:"kind" binding:"required,oneof=expense income"`
    ParentID int64  `json:"parent_id" binding:"omitempty,gt=0"`
}
标签行为注意
required字段必须「非零值」零值陷阱：对 int 来说 0 就是零值——客户端明明传了 "parent_id": 0 也会被判「没传」
omitempty是零值就跳过后面所有规则；非零值才继续校验「可选字段」的正确写法，常与别的标签搭配
min=1,max=32对 string 是长度，对数字是值一个标签两副面孔，写之前先想字段类型
oneof=expense income枚举：值必须是空格分隔列表中的一个分类的收支类型只有这两个合法值
gt=0大于 0（还有 gte/lt/lte）omitempty,gt=0 连读 = 「可以不传；传了必须 > 0」

逗号 = AND：一条标签里所有规则都要过。标签之间用引号包成一个字符串，写在 binding:"…" 里——注意和 json:"…" 是两个独立的标签，一个管线上字段名，一个管校验规则。

3. 绑定失败的收口：1004，且不外泄原始报错

validator 的原始报错长这样：Key: 'categoryReq.Name' Error:Field validation for 'Name' failed on the 'required' tag——英文、带 struct 名、带内部字段路径。直接甩给客户端等于把内部结构画给外人看。收口纪律：

  • 客户端拿到：400 + 1004 + 「参数错误」（码表里的固定文案）。
  • 服务端日志：log.Printf 记下原始报错——D3 的请求日志中间件上岗后，这条日志还会带上 request-id，排查时能对上号。

和 S1·D8 的「解析失败一律 400 + 1004」是同一条纪律，只是校验从手写 if 换成了声明式标签。

4. 骨架的豁免窗口只到周六

今天的 handler 绑定成功后返回一份假数据（固定 id 的分类）。这踩在反例③的边上——但它是被明确豁免的：假数据只允许活在 d1-d5 的 handler 骨架与测试里，本周六（D6）之前必须换成真实现。今天提交信息里它是「骨架」，周六它要是还活着，就是「注册了但没实现的假入口」。

今日增量（在学习仓里落盘）

今天属增量类型 ②：加一条路由 + handler 骨架——POST /api/finance/categories，绑定走真规则、业务返回假数据。临时结构体 categoryReq 先放 cmd/homecube（D5 会把它升级成正式 DTO 并归置进 internal/finance/handler，和 S1 先写 main.go 再 D11 归置是同一个节奏）。

步骤 1 · main.go 挂上分组与骨架 handler

完整 · server/cmd/homecube/main.go（覆盖 D1 版本）package main

import (
    "log"
    "net/http"

    "github.com/gin-gonic/gin"

    "homecube/internal/platform/middleware"
    "homecube/pkg/response"
)

// categoryReq 创建分类的请求结构（临时版：D5 升级为正式 DTO）。
// binding 标签 = 声明式校验规则，由 ShouldBindJSON 内置的 validator 执行。
type categoryReq struct {
    Name     string `json:"name" binding:"required,min=1,max=32"`
    Icon     string `json:"icon" binding:"omitempty,max=64"`
    Kind     string `json:"kind" binding:"required,oneof=expense income"`
    ParentID int64  `json:"parent_id" binding:"omitempty,gt=0"`
}

func newRouter() http.Handler {
    engine := gin.New()

    engine.GET("/healthz", func(c *gin.Context) {
        response.OK(c, map[string]string{"status": "ok"})
    })

    finance := engine.Group("/api/finance")
    finance.POST("/categories", func(c *gin.Context) {
        var req categoryReq
        if err := c.ShouldBindJSON(&req); err != nil {
            log.Printf("bind create category: %v", err) // 细节进日志，不进响应
            response.Fail(c, http.StatusBadRequest, response.CodeInvalidParam, "参数错误")
            return
        }
        // 假数据（骨架期豁免）：D6 换成 service 真实现，届时本行必须消失
        response.Created(c, gin.H{"id": 1, "name": req.Name, "kind": req.Kind})
    })

    engine.NoRoute(func(c *gin.Context) {
        response.Fail(c, http.StatusNotFound, response.CodeNotFound, "资源不存在")
    })

    return middleware.WithRequestID(middleware.WithRecover(engine))
}

func main() {
    addr := ":8080"
    log.Println("homecube listening on", addr)
    if err := http.ListenAndServe(addr, newRouter()); err != nil {
        log.Fatal(err)
    }
}

gin.H 就是 map[string]any 的别名，临时拼响应数据用；D5 之后正式响应一律走 CategoryResp 这样的 DTO struct，字段名拼错的 map 编译器救不了你，struct 能。

步骤 2 · 表驱动测试：一条合法 + 三条非法

完整 · server/cmd/homecube/categories_test.gopackage main

import (
    "net/http/httptest"
    "strings"
    "testing"
)

// postCategories 发一个 JSON body 的 POST，返回记录好的响应。
func postCategories(body string) *httptest.ResponseRecorder {
    w := httptest.NewRecorder()
    req := httptest.NewRequest("POST", "/api/finance/categories", strings.NewReader(body))
    req.Header.Set("Content-Type", "application/json")
    newRouter().ServeHTTP(w, req)
    return w
}

func TestCreateCategoryBinding(t *testing.T) {
    cases := []struct {
        name     string
        body     string
        wantHTTP int
        wantBiz  string // 响应体里必须出现的片段
    }{
        {"合法创建", `{"name":"餐饮","kind":"expense"}`, 201, `"code":0`},
        {"缺 name", `{"kind":"expense"}`, 400, `"code":1004`},
        {"kind 非法", `{"name":"餐饮","kind":"foo"}`, 400, `"code":1004`},
        {"name 超长", `{"name":"` + strings.Repeat("长", 33) + `","kind":"expense"}`, 400, `"code":1004`},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            w := postCategories(tc.body)
            if w.Code != tc.wantHTTP {
                t.Fatalf("HTTP = %d, want %d, body = %s", w.Code, tc.wantHTTP, w.Body.String())
            }
            if !strings.Contains(w.Body.String(), tc.wantBiz) {
                t.Fatalf("body = %s, want contains %s", w.Body.String(), tc.wantBiz)
            }
        })
    }
}

注意 max=32 数的是字符数（rune）不是字节数，所以用例里用 33 个汉字才刚好越界——这本身就是 validator 值得信任的一个细节。

常见坑（新手 100% 会踩）

坑现象正确姿势
给数字字段标 required客户端传 "parent_id": 0 被判「没传」，400 得莫名其妙可选数字用 omitempty,gt=0；required 认的是「非零值」不是「有出现」
用 BindJSON失败时 Gin 自动写裸 400，三键信封没了只用 Should* 一族，响应自己写
把 validator 原始报错返回给客户端响应里出现 struct 名与内部字段路径1004 + 「参数错误」给客户端，原始报错 log.Printf 进日志
min/max 想当然给 string 标 min=1 以为是「值至少 1」，给 int 标 max=100 以为是「长度」string 数长度、数字比值——写标签前先念一遍字段类型
标签写在 json:"…" 里json:"name,required" 完全不生效，校验静默丢失json 管字段名，binding 管规则，两个标签各写各的
用 ShouldBind 测 POST 却忘设 Content-TypeShouldBind 按 Content-Type 推断绑定器，缺头时推断错明确知道 body 是 JSON 就直接用 ShouldBindJSON，不靠推断
假数据活过周六骨架 handler 一直返回固定 id，反例③复活D6 换成 service 真实现；今天先在心里记一笔

今日名词卡

术语一句话解释
绑定（binding）「解码 + 校验」的合称；Gin 的 ShouldBindJSON 一个调用完成两步

卡壳时查什么

正文自足，只有两种情况出去查：

  • validator 还有哪些标签：validator 文档（可选，看「Baked In Validations」一节的标签清单，今天我们用的五个只是子集）。
  • Gin 绑定族的全家福：gin · Context 的绑定方法（可选，看清 ShouldBind / ShouldBindJSON / ShouldBindQuery 的分工）。

绑定类 bug 的调试铁律：先看服务端日志里的原始报错——validator 的错误信息精确到「哪个字段、哪条标签」，比对着 curl 猜快十倍。日志里没有 bind 报错却还是 400？那就是根本没进 handler，检查路径和方法。
