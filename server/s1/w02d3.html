响应写出与中间件：标准库怎么包 handler

中间件是「每个请求都要过、但和业务无关」的那层代码：打 request-id、兜 panic、记日志、验 token（S4）。Gin 有现成的中间件机制，而标准库的答案漂亮得近乎寒酸：中间件就是一个函数，收一个 http.Handler，返回一个包了皮的 http.Handler。今天手写两个——request-id 与 panic recover——顺便把 D2 埋的 panic 补上最小教学。

今日目标

知识讲义

1. 中间件 = 函数包装，没有魔法

回忆 D6：http.Handler 是接口，ServeHTTP(w, r)；http.HandlerFunc 把函数适配成 Handler。中间件利用同一套零件：

片段 · 前置：import "net/http"// withXxx 收一个 Handler，返回一个新 Handler：新 Handler 的 ServeHTTP =
// 「先干点自己的事 → 调用被包的 next → 回来再干点事（可选）」
func withXxx(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 请求进来时执行（洋葱：从外往内）
        next.ServeHTTP(w, r)   // 放行给里层
        // 响应回去时执行（洋葱：从内往外）——注意：body 一旦写过就改不了了
    })
}

包装可以层层套：withA(withB(withC(mux)))。执行顺序就是洋葱：A 的前半 → B 的前半 → C 的前半 → 路由与 handler → C 的后半 → B 的后半 → A 的后半。最外层的代码最先碰到请求、最后碰到响应——所以「每个响应都必须有的东西」（request-id）放最外层。

这里唯一的新语法是闭包：返回的那个函数字面量捕获了参数 next。你在 JS 里写过一万个闭包，Go 的一模一样。S2 的 Gin 中间件签名 func(*gin.Context) 不同，但洋葱模型原封不动搬过去。

2. panic 与 recover：半页最小教学（欠账今天还）

D2 只说了一句「panic = 程序崩掉」，今天补全机制：

  • panic 发生时：当前函数立刻停止正常执行，开始「解卷」——沿调用栈往回退，沿途每个已注册的 defer 都会执行，退到 goroutine 顶端还没人管，就打印堆栈并终止整个进程。
  • recover 的唯一生效位置是 defer 里：defer func(){ if e := recover(); e != nil { … } }()。它把 panic 的值接住，让解卷停在当前函数，程序从 defer 之后正常返回。写在非 defer 位置的 recover 是无效语句。
  • goroutine：可以并发执行的函数调用（S5 正式讲，今天记住一句就够）——「没人兜住的 panic 崩的是整个进程，不管它发生在哪个 goroutine」。

一个诚实的技术细节：net/http 恰好为每个请求起了一个 goroutine 并自己兜了 panic——所以标准库服务里 handler panic 时进程不会死，但那条连接会当场断掉：客户端拿到半截响应或空响应，你的统一信封荡然无存，日志里只有一行框架口吻的 http: panic serving。而 S5 起你自己 spawn 的 goroutine（后台聚合、批量导入）没有任何人兜底——那里一个 panic 就是全进程阵亡。所以纪律是：在边界处 recover——HTTP 边界今天装，goroutine 边界 S5 装。指望框架的内置兜底，等于把「500 + 5000 + request-id + 堆栈日志」这套标准事故报告让位给一行裸日志。

3. request-id：一个请求的身份证

规则三行：客户端带了合法的 X-Request-ID 就沿用（跨服务排查时全链路同一个 id）；没带就生成一个随机十六进制串；写进响应头，让客户端、日志（S5）、事故报告（用户截图里带 id）都能引用同一次请求。S5 的结构化日志会把「每条日志都带 request-id」做成硬要求，今天先把 id 的生成与透传立起来。

步骤 1 · 两个中间件

完整 · server/cmd/homecube/middleware.gopackage main

import (
    "crypto/rand"
    "encoding/hex"
    "log"
    "net/http"
    "runtime/debug"

    "homecube/pkg/response"
)

// withRequestID 给每个响应盖 X-Request-ID：客户端带了合法的就沿用，否则生成。
func withRequestID(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := r.Header.Get("X-Request-ID")
        if id == "" || len(id) > 64 {
            id = newRequestID()
        }
        w.Header().Set("X-Request-ID", id) // 必须在任何 Write 之前——D6 的笔顺
        next.ServeHTTP(w, r)
    })
}

// newRequestID 生成 8 字节随机数的十六进制串（16 个字符）。
// crypto/rand 是密码学安全随机源；读取失败几乎只可能是系统级故障，直接 panic 合理。
func newRequestID() string {
    b := make([]byte, 8)
    if _, err := rand.Read(b); err != nil {
        panic(err)
    }
    return hex.EncodeToString(b)
}

// withRecover 是 HTTP 边界的最后一道闸：兜住 handler 的 panic，
// 换成 500 + 5000 的统一信封，并把堆栈记进日志。
func withRecover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {                        // recover 只能活在 defer 里
            if e := recover(); e != nil {
                log.Printf("panic: %v %s: %v\n%s",
                    r.Method, r.URL.Path, e, debug.Stack()) // 堆栈进日志，不进响应
                response.Fail(w, http.StatusInternalServerError,
                    response.CodeInternal, "服务器内部错误")
            }
        }()
        next.ServeHTTP(w, r)
    })
}

withRecover 有一个救不了的场景：handler 已经写了一半响应才 panic——状态码早发出去了，500 写不进去（会看到 superfluous WriteHeader 日志）。这是物理限制不是 bug；对策是把「可能 panic 的活」放在写响应之前干完，S5 之后你的 handler 会自然长成这样。

步骤 2 · 装配：洋葱的顺序

片段 · main.go 的 newRouter 尾部改动（前置：D8 的 newRouter）func newRouter() http.Handler {
    mux := http.NewServeMux()
    // …D8 的全部注册原样保留…

    // 洋葱从内往外包：requestID 在最外层（每个响应必有 id），recover 次之
    return withRequestID(withRecover(mux))
}

为什么这个顺序？想一个 handler panic 的场景：recover 兜住后要写 500 信封，而 X-Request-ID 头必须还在——requestID 在最外层，头早在放行前就设好了，稳。

步骤 3 · 测试：panic 不许漏出去

生产路由里不能埋会 panic 的 handler，所以测试自己搭一个小路由来验证 recover——这正是「中间件是普通函数」的好处：单测不需要全站装配。

完整 · server/cmd/homecube/middleware_test.gopackage main

import (
    "net/http"
    "net/http/httptest"
    "strings"
    "testing"
)

func TestWithRecover(t *testing.T) {
    boom := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        panic("boom")
    })
    h := withRequestID(withRecover(boom))

    w := httptest.NewRecorder()
    h.ServeHTTP(w, httptest.NewRequest("GET", "/", nil))

    if w.Code != 500 {
        t.Fatalf("状态码 = %d, want 500", w.Code)
    }
    if !strings.Contains(w.Body.String(), `"code":5000`) {
        t.Fatalf("body = %s", w.Body.String())
    }
    if w.Header().Get("X-Request-ID") == "" {
        t.Fatal("panic 响应也必须带 X-Request-ID")
    }
}

func TestWithRequestID(t *testing.T) {
    h := withRequestID(newRouter())

    w := httptest.NewRecorder()
    h.ServeHTTP(w, httptest.NewRequest("GET", "/healthz", nil))
    if got := w.Header().Get("X-Request-ID"); len(got) != 16 {
        t.Fatalf("生成的 X-Request-ID = %q, want 16 个十六进制字符", got)
    }

    w2 := httptest.NewRecorder()
    req2 := httptest.NewRequest("GET", "/healthz", nil)
    req2.Header.Set("X-Request-ID", "trace-me-001")
    h.ServeHTTP(w2, req2)
    if got := w2.Header().Get("X-Request-ID"); got != "trace-me-001" {
        t.Fatalf("客户端传入的 id 应被沿用，got %q", got)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
recover 写在 defer 外面无效语句，panic 照崩defer func(){ recover() }() 一体三件套，背下来
以为 net/http 兜了 panic 就万事大吉连接断掉、响应半截、日志只有一行框架格式自己 recover：统一信封 + 堆栈日志。且你自起的 goroutine（S5）根本没人兜
包装顺序写反panic 响应上没有 X-Request-ID，排查时找不到事故报告编号最外层 = 每个响应都必须有的东西；画洋葱图确认再写
在 next.ServeHTTP 之后改响应头静默无效body 写过 = 头已发出（D6 笔顺）。中间件的「后半段」只能做日志、统计这类不碰 w 的事
用 math/rand 生成 request-id可预测；多实例可能撞身份类随机一律 crypto/rand
无条件信任客户端传入的 X-Request-ID超长串/控制字符进日志限长（今天 64）+ 只当标识用，不做任何决策依据
把业务错误也 panic 出去recover 兜住变 500，客户端明明只是参数错可预期的失败走 error 返回值（D4）；panic 只留给「程序写错了」级别的事故

今日名词卡

术语一句话解释
中间件（middleware）包在 handler 外面的横切层；标准库形态 = func(http.Handler) http.Handler
洋葱模型请求从外往里穿、响应从里往外穿；最外层最先见请求、最后见响应
闭包捕获了外层变量的函数字面量；与 JS 的闭包同一概念
panic不可恢复错误的「崩」路径：解卷 + 执行 defer + 没人兜就终止进程
recover只在 defer 里生效的「接住 panic」；接住后当前函数正常返回
debug.Stack()runtime/debug 提供的当前堆栈快照；panic 日志的标配
goroutine可并发执行的函数调用；net/http 每请求一个。S5 正式讲
X-Request-ID一次请求的身份证：客户端带则沿用，否则生成；响应头必回
crypto/rand密码学安全随机源；身份/密钥类随机只用它，不用 math/rand
结构化日志每条日志带 request-id 等字段、机器可检索。S5 正式建，今天先用 log 包凑合
