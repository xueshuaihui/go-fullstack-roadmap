结构体、方法与接收者

昨天你把「一切传参皆复制」刻进了脑子，今天马上见到它的用武之地：struct 传值 = 复制整个结构体。由此引出 Go 里第二个重要决策——方法的接收者用值还是用指针。今天的增量是第一批真正的领域代码：User / Family / Member 三个结构体加 Role 四级枚举，它们会一直陪到 S8。

今日目标

知识讲义

1. struct：Go 的「对象」，但没有继承

片段 · 前置：无，直接读type User struct {
    ID    int64  `json:"id"`
    Name  string `json:"name"`
    phone string          // 小写 = 包外不可见，也不会被 json 序列化
}

u := User{ID: 1, Name: "shuai"}   // 永远写字段名，别按位置初始化
p := &User{ID: 2}                  // 直接得到 *User，不需要先建再取地址
fmt.Println(u.Name, p.Name)         // 指针访问字段不用写 (*p).Name，Go 自动解

对照你熟悉的东西：struct ≈ TS 的 interface 描述的「数据形状」+ 可以挂方法。反引号里的 json:"id" 叫 struct tag，是给序列化工具看的元数据——D6 写统一响应体时它会真正上场，今天先混个脸熟。

传 struct = 复制整个 struct。昨天的规则今天兑现：func f(u User) 拿到的是完整副本，字段再多也照复制不误。这就是接收者选型的起点。

2. 方法：带接收者的函数

Go 没有 class。方法是「多了一个特殊参数的函数」，这个参数叫接收者，写在 func 和方法名之间：

可跑package main

import "fmt"

type Counter struct{ n int }

func (c Counter) ShowVal()  { fmt.Println("值接收者读到", c.n) }
func (c *Counter) IncVal() { c.n++ }   // 指针接收者：改的是原件

func main() {
    c := Counter{}          // 零值 {n:0}，直接可用
    c.IncVal()              // 编译器自动改写成 (&c).IncVal()
    c.ShowVal()             // 值接收者读到 1
}

如果把 IncVal 的接收者改成值接收者 (c Counter)，c.n++ 改的就是副本，main 里的 c 永远是 0——不报错，静默失效，这是今天最需要记住的坑。

接收者选型三条军规（满足任何一条就用指针）：

#情况原因
1方法要修改接收者值接收者改的是副本，白改
2结构体大（字段多、含数组）每次调用复制一遍，纯浪费
3结构体含锁（如 sync.Mutex）复制锁 = 复制出两把不同的锁，保护失效。sync.Mutex 本身 S5 正式讲，今天记住结论；D5 的内存仓储会照抄一次

拿不准就全用指针接收者——本项目对领域 struct 一律如此。混用值/指针接收者是 lint 工具都会警告的坏味道：同一个类型的方法集应该长得一样。

3. 用 type + const 造枚举

Go 没有 enum 关键字，惯例是「自定义整数类型 + 一组常量」。本项目的角色是全站的权限地基，四级，一个不多：

片段 · 前置：type Role int8const (
    RoleOwner  Role = 1  // 管理员：唯一可转让/解散；不能移除自己
    RoleMember Role = 2  // 成人成员：默认角色，可写业务数据，不能管成员与邀请
    RoleWard   Role = 3  // 儿童/老人：可无账号；有账号时仅有限写权限
    RoleGuest  Role = 4  // 访客：限时只读，可撤销，不可导出
)

「已退出成员」不是第五个角色。退出是 Member.Status 字段的一个取值：成员退出家庭后，历史记账数据留在家庭里、作者标记不变，只是状态翻成「已退出」。把「状态」建成「角色」，权限矩阵就会多出一整行说不清道不明的规则——这是数据建模的经典错误，S4 建权限矩阵时会回头验证今天这个决定。

为什么显式写 = 1 而不用 iota 自动编号？因为这些值将进数据库。用 iota 的话，日后有人在中间插一个常量，全体数值顺移，库里的历史数据瞬间集体变脸。显式赋值，一个萝卜一个坑。

4. model 包只是「形状」，先不碰数据库

今天的 struct 只定义 Go 侧的形状与字段类型；created_at 之类的通用列、表名、外键，都是 S3 接 Postgres 时的事（届时会讲为什么 id 用 int64、金额为什么用「分」）。不要提前发明字段——S3 的迁移文件才是字段的唯一户口。

今日增量（在学习仓里落盘）

今天属增量类型 ①：加 struct 与枚举。落盘位置 server/internal/homeos/model/，包名 model，四个文件。

步骤 1 · Role 枚举

完整 · server/internal/homeos/model/role.gopackage model

// Role 是家庭内成员角色，四级封闭枚举：owner=1 / member=2 / ward=3 / guest=4。
// 数值将进数据库（S3），显式赋值，禁止 iota，禁止插入第五个角色。
// 「已退出成员」不是角色，是 MemberStatus 的取值。
type Role int8

const (
    RoleOwner  Role = 1
    RoleMember Role = 2
    RoleWard   Role = 3
    RoleGuest  Role = 4
)

// Valid 报告 r 是否为合法角色。指针接收者？不——Role 是个 int8，
// 复制成本为零且不改接收者，用值接收者。（三条军规一条都不沾。）
func (r Role) Valid() bool {
    return r >= RoleOwner && r <= RoleGuest
}

// String 让 fmt 打印角色时输出可读名。这个方法为什么特殊，D5 揭晓。
func (r Role) String() string {
    switch r {
    case RoleOwner:
        return "owner"
    case RoleMember:
        return "member"
    case RoleWard:
        return "ward"
    case RoleGuest:
        return "guest"
    default:
        return "unknown"
    }
}

步骤 2 · 成员状态枚举

完整 · server/internal/homeos/model/member_status.gopackage model

// MemberStatus 是成员在家庭内的状态。与 Role 正交：
// 「已退出」的成员仍然是它退出前的那个角色（历史数据的作者标记不变）。
type MemberStatus int8

const (
    MemberStatusActive MemberStatus = 1 // 在家庭中
    MemberStatusLeft   MemberStatus = 2 // 已退出：数据留家庭，成员不可再操作
)

步骤 3 · 三个 struct

完整 · server/internal/homeos/model/user.gopackage model

// User 是全局账号（一个人一个），与「某家庭里的身份」（Member）分离。
// 时间列与数据库通用列 S3 再加，今天只立形状。
type User struct {
    ID           int64  `json:"id"`
    Nickname     string `json:"nickname"`
    Phone        string `json:"phone"`
    PasswordHash string `json:"-"` // json:"-" = 永不序列化出去，S4 讲为什么
}

// DisplayName 值接收者行不行？行——User 字段少且只读不改。
// 但本项目对领域 struct 统一用指针接收者，保持方法集一致。
func (u *User) DisplayName() string {
    if u.Nickname != "" {
        return u.Nickname
    }
    return u.Phone
}
完整 · server/internal/homeos/model/family.gopackage model

// Family 是租户单位：全站业务数据都挂在某个家庭之下（S3 起每表带 family_id）。
type Family struct {
    ID         int64  `json:"id"`
    Name       string `json:"name"`
    OwnerID    int64  `json:"owner_id"`    // 唯一 owner；转让 = 改这个字段 + S4 的一串联动
    InviteCode string `json:"invite_code"` // 邀请码，S4 用
    Version    int    `json:"version"`     // 乐观锁：写一次 +1，S6 正式兑现
}
完整 · server/internal/homeos/model/member.gopackage model

// Member = 「某个 User 在某个 Family 里的身份」。一个人可以有多个 Member
// （多家庭），角色与状态都挂在 Member 上，不挂在 User 上。
type Member struct {
    ID       int64        `json:"id"`
    FamilyID int64        `json:"family_id"`
    UserID   int64        `json:"user_id"`   // 被监护人（ward）可以没有账号，此时为 0
    Nickname string       `json:"nickname"`  // 家庭内昵称，可与账号昵称不同
    Role     Role         `json:"role"`
    Status   MemberStatus `json:"status"`
}

// Promote 升级为 owner：要改接收者 → 必须指针接收者（军规第 1 条）。
func (m *Member) Promote() {
    m.Role = RoleOwner
}

// IsActive 只读不改 → 值接收者本可以，但保持与 Promote 一致，仍用指针。
func (m *Member) IsActive() bool {
    return m.Status == MemberStatusActive
}

常见坑（新手 100% 会踩）

坑现象正确姿势
值接收者里改字段改完没效果，不报错要改接收者 → 指针接收者。军规第 1 条
同一类型混用值/指针接收者能跑，但方法集不一致，D5 讲接口时会突然编译失败一个类型的方法接收者风格统一；本项目领域 struct 一律指针
按位置初始化 User{1, "x", …}加一个字段全体错位永远写字段名：User{ID: 1}
map 里存 struct 值再改字段m["k"].Name = "x" 编译失败 cannot assignmap 的 value 不可寻址。存 *User 指针，或整体取出改完放回。明天 D4 讲 map 时再撞一次
用 iota 给要进库的枚举编号日后插一个常量，库里历史数据集体变含义进数据库的枚举显式赋值
把「已退出」建成第五个角色权限矩阵多一行永远说不清的规则角色与状态正交：Role 四级封闭，退出走 Status
循环里 + 拼字符串量大时慢strings.Builder（S5 兑现）。今天先在 playground 感受：拼 10 万次对比一下

今日名词卡

术语一句话解释
struct字段捆绑成的自定义类型；传值 = 整体复制
接收者（receiver）方法的那个特殊参数；值 = 操作副本，指针 = 操作原件
导出（exported）首字母大写才出得了包。字段、方法、类型同理
struct tag反引号里的元数据，如 json:"id"；D6 序列化响应体时上场
枚举模式type X int8 + 具名常量。进库的枚举显式赋值，不用 iota
Role 四级owner=1 / member=2 / ward=3 / guest=4，封闭集合，S4 权限矩阵的行
MemberStatus成员状态（active/left）。「已退出」住在这里，不住在 Role 里
sync.Mutex互斥锁。含锁的 struct 必须指针接收者；锁本身 S5 正式讲，D5 照抄一次
error 包装（%w / errors.Is）错误链：包一层还能被认出来。明天 D4 正式讲
接口（interface）方法名约定。D5 正式讲——今天的 String() 方法届时给你一个惊喜

卡壳时查什么

正文自足，只有两种情况出去查：

  • 接收者到底选哪个拿不准：Go Code Review Comments · Receiver Type（可选，官方社区共识，两段话）。
  • struct tag 的语法看着眼晕：不用深究，D6 用到时只需照抄 json:"xxx" 一种形态。
