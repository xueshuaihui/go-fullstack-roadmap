internal/ 分层与收口前的重构

main.go 已经胖了：路由、五个 handler、两个中间件、DTO 全挤在一个包里。明天就收口，今天做 S1 唯一一次纯重构——不加任何新功能，只把代码搬进它该住的房间，顺便把「三层」这件事一次讲清。三层的完整教学（service 层、DTO 与模型分离、依赖注入）在 S2；今天的目标是讲清 + 归置，让你明天收口时看到的仓库长得像 S2 要用的样子。

今日目标

知识讲义

1. 三层：翻译层、规则层、存取层

一个请求从进来到落库，经过三种性质完全不同的工作。把它们混在一个函数里，就是「大泥球」的起点；分成三层，每层只干一种事：

层职责允许 import禁止
handler（翻译层）HTTP ↔ 业务的双向翻译：解析请求（D8）、调 service、把 error 翻译成统一信封（D6/D7）service、model、pkg/response、net/http写业务规则、碰数据存储细节
service（规则层）业务规则的唯一住所：「余额非 0 不许归档」「唯一 owner 不许移除」都住这里repo 接口、modelimport net/http、认识 response.Body——它只说 error，不说 HTTP
repo（存取层）数据存取：S1 是内存 map（D5），S3 换 Postgres，接口不变model写业务规则、import net/http

依赖方向永远从外往里：handler → service → repo → model。内层不知道外层存在——repo 不知道自己被 Gin 还是 net/http 调用，这正是 S3「换数据库只写一个新实现」与 S2「换框架只动 handler」的底层原理（D5 讲接口时说过的「消费方约定」，今天落成目录）。

今天你只有两层：handler（D6-D9 写的那些函数）与 repo（D5 的 FamilyRepository）。service 层 S2 才出生——现在没有业务规则，凭空造一个空的 service 层是过度设计。分层是「规则长出来时给它准备的房间」，不是仪式。

还有一个横切住户：middleware。它不属于任何业务模块（homeos / finance 都要用），所以归 internal/platform/——D1 的目录骨架里 platform 的定位「配置、日志、鉴权、跨模块」今天落进第一件实物。

2. internal/ 不只是「藏」，是编译器执法

D1 说过 internal/ 外部模块 import 会编译失败。今天看它的第二重意义：分层纪律有了执法者。约定「repo 不许碰 HTTP」如果只写在文档里，三个月后一定被违反；而当 repo 住在 internal/、handler 住在另一个包，跨层乱 import 至少要在文件头上留下一行明晃晃的证据，review 时一眼抓获。Go 社区的共识：目录结构就是架构文档，编译器就是架构警察。

顺带认识一个新敌人：import cycle（循环依赖）。Go 禁止 A import B、B 又 import A——哪怕只是间接的。循环依赖几乎总是分层被打破的信号（service 反过来 import handler 之类），编译器会在你犯错的第一时间拦下。前端里循环 import 常常悄悄活着，Go 里它活不过编译。

3. 搬代码的标准三步

  • 改包名：文件挪进新目录后，第一行 package 必须等于新目录名（一个目录一个包，D1）。同目录的文件是一家人，互相直接用，不 import。
  • 改导出：搬家前是小写（包内私有）的名字，要被别的包用就得改成大写——withRecover 变 WithRecover。搬完 make build，编译器会把所有「你忘了导出」的地方逐个报错给你看，照着改。
  • 测试跟着代码走：middleware_test.go 和 middleware.go 住同一个包。删掉原文件，别让旧副本留下重复定义的编译错误。

步骤 1 · 中间件搬进 platform

片段 · server/internal/platform/middleware/middleware.go（函数体与 D9 逐字一致，只改包名与导出名）package middleware

import (
    "crypto/rand"
    "encoding/hex"
    "log"
    "net/http"
    "runtime/debug"

    "homecube/pkg/response"
)

// WithRequestID 给每个响应盖 X-Request-ID：客户端带了合法的就沿用，否则生成。
// （实现与 D9 完全一致，仅改包名与导出——搬家的纪律：不顺手改逻辑。）
func WithRequestID(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := r.Header.Get("X-Request-ID")
        if id == "" || len(id) > 64 {
            id = newRequestID()
        }
        w.Header().Set("X-Request-ID", id)
        next.ServeHTTP(w, r)
    })
}

func newRequestID() string { /* 小写：包内私有，没变 */ }

// WithRecover 兜住 handler 的 panic → 500 + 5000 统一信封 + 堆栈进日志。
func WithRecover(next http.Handler) http.Handler { /* 实现与 D9 一致 */ }

把 D9 的两个函数体原样拷进对应位置（上面为省篇幅折叠了两处），middleware_test.go 一并搬来、改包名为 middleware、函数名改大写引用。唯一实质改动：原 TestWithRequestID 里借用了 newRouter()——它住在 cmd 包，搬过来就够不着了（也不该够：middleware 不该知道全站路由长什么样）。换成哑 handler：

片段 · middleware_test.go 里的替换（前置：搬来的测试文件）h := WithRequestID(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    response.OK(w, nil)
}))   // 测中间件只需要一个「必定 200」的哑 handler——这就是层与层解耦后的测试自由

然后删除 cmd/homecube/middleware.go 与 cmd/homecube/middleware_test.go。

步骤 3 · main.go 瘦成装配

完整 · server/cmd/homecube/main.go（覆盖 D8 版本）package main

import (
    "log"
    "net/http"

    "homecube/internal/homeos/handler"
    "homecube/internal/platform/middleware"
)

func newRouter() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /healthz", handler.Healthz)

    // —— 教学期练手路由：S2·D1 删除 ——
    mux.HandleFunc("GET /api/ping", handler.Ping)
    mux.HandleFunc("GET /api/ping/{id}", handler.PingByID)
    mux.HandleFunc("POST /api/ping/echo", handler.PingEcho)

    mux.HandleFunc("/", handler.NotFound)
    return middleware.WithRequestID(middleware.WithRecover(mux))
}

func main() {
    addr := ":8080"
    log.Println("homecube listening on", addr)
    if err := http.ListenAndServe(addr, newRouter()); err != nil {
        log.Fatal(err)
    }
}

数一下：main.go 只剩 40 行不到，没有一行业务。这就是 cmd/ 的岗位说明书（D1）：「读配置 → 连库 → 装配路由 → 启动」，S3 加配置、S5 加优雅关闭，加的全是装配动作。

坑现象正确姿势
搬了文件忘删原件withRecover redeclared in this block搬家 = 复制 + 删除；git status 里新旧文件应一一对应
忘了改导出main.go 里 undefined: handler.Healthz（或反过来 undefined: handler.healthz）跨包使用的名字必须大写；编译器会逐个报给你
包名 ≠ 目录名found packages middleware and main in …一个目录一个包；测试文件的包名也要跟目录走

今日名词卡

术语一句话解释
三层架构handler（翻译）→ service（规则）→ repo（存取）；S2 完整教学，今天归置出雏形
依赖方向只许从外往里；内层不认识外层，才能被随便替换
装配根（composition root）唯一知道「全部零件」的地方 = main.go；只有它做拼装
横切关注点不属于任何模块的事（中间件、日志、配置），住 internal/platform/
import cycle循环依赖，Go 编译期禁止；几乎总是分层被打破的信号
导出（复习）首字母大写跨包可见；搬家后编译器帮你清点该导出谁
重构只改结构不改行为；测试全绿是重构完成的唯一标准
哑 handler（stub）测试中间件用的最小替身；层解耦后测试才这么轻
大泥球（big ball of mud）所有逻辑纠缠在一个包/文件里的反模式；今天搬的家就是防它

卡壳时查什么

正文自足，只有两种情况出去查：

  • internal 机制的官方说明：Go 1.4 Release Notes · internal packages（可选，三段话，讲清编译器执法的来历）。
  • 项目布局想看看别人怎么摆：golang-standards/project-layout（可选，只看不抄——它面向大项目，本项目的目录以 D1 骨架为准，别被带偏）。

搬家类重构出错的调试铁律：一次只搬一个包，搬完立刻 make test。全搬完才跑测试，红了就是五处嫌疑人站一排。今天先搬 middleware（带测试）、绿了、再搬 handler、再绿——两次小步永远比一次大步便宜。
