接口与隐式实现

Go 的接口是全站架构的承重墙：明天 D6 的 http.Handler 是它，S2 三层的 service 依赖 repo 靠它，S4 跨模块调用收在接口后面还是它。今天把三件事吃透——隐式实现（没有 implements 关键字）、方法集（值与指针谁能进接口）、接口变量为 nil 的坑（面试和线上事故的双料常客）。增量是第一个 Repository 接口与内存实现。

今日目标

知识讲义

1. 隐式实现：鸭子类型的编译期版本

接口就是一组方法签名的约定。任何类型只要拥有接口要求的全部方法，就自动算实现了它——没有 implements，没有 extends，两边甚至不需要知道对方存在：

可跑package main

import "fmt"

type Speaker interface {
    Speak() string
}

type Dog struct{}
func (d *Dog) Speak() string { return "woof" } // 齐了。Dog 没说它实现谁

func announce(s Speaker) { fmt.Println(s.Speak()) }

func main() {
    announce(&Dog{})   // *Dog 有 Speak 方法 → *Dog 自动满足 Speaker
}

揭晓昨天埋的彩蛋：Role.String() 为什么特殊？因为标准库有个 fmt.Stringer 接口（只有一个 String() string 方法），你写了这个方法，fmt.Println(role) 就自动打印 "owner" 而不是 1——你「实现」了一个你从没 import 过的接口。这就是隐式实现的威力：约定在使用方，不在定义方。

对照 TS：interface 也是结构化类型（形状对了就兼容），这点像。不像的两处：① TS 的接口主要用于类型检查期，编译后消失；Go 的接口是运行时真实存在的值；② Go 的方法必须显式写在类型上，不能像 TS 那样随手给个对象字面量算数。

2. 接口值与「非 nil 的 nil」

接口变量在运行时是一个两字宽的结构：(动态类型, 动态值)。赋 nil 给它 = 两位都空。坑就出在「类型位有值、值位是 nil」：

片段 · 前置：import "fmt"，MyErr 为任意 error 实现type MyErr struct{}
func (e *MyErr) Error() string { return "boom" }

func do() error {
    var p *MyErr = nil   // p 是 nil 指针
    return p                 // 装进 error 接口：类型位=*MyErr，值位=nil
}

func main() {
    err := do()
    fmt.Println(err == nil)   // false！接口本身不是 nil（类型位有东西）
}

防坑口诀：返回 error 的函数，出错就 return err / return fmt.Errorf(…%w…)，不出错就字面量 return nil。永远不要把一个「具体类型的 nil 指针」返回成 error。这个坑在 S3 的 repo 层（返回 *model.Family, error）出现频率最高，今天先在 playground/d5 亲手复现一次。

3. 方法集：值与指针谁能进接口

规则两句话：值接收者的方法，T 和 *T 的方法集里都有；指针接收者的方法，只在 *T 的方法集里。后果：

片段 · 前置：上面的 Dog（指针接收者 Speak）var s Speaker
s = &Dog{}   // ✅ *Dog 的方法集含 Speak
s = Dog{}     // ❌ 编译失败：Dog does not implement Speaker
              //    （Speak 是指针接收者，值的方法集里没有它）

这解释了 D3 军规的补充条款「同一类型接收者风格要统一」：混用时，某些调用点能进接口、某些不能，编译器报错位置还离病根很远。

4. 空接口 any：什么都能装，代价是什么都不知道

any 是 interface{} 的别名——零个方法的接口，所有类型都满足它。明天 D6 的统一响应体 Body.Data 字段就是 any：响应信封形状固定，装什么由每个接口自己定，这正是空接口的正确用途。从 any 取回具体类型靠类型断言：

片段 · 前置：无var v any = "hello"
s, ok := v.(string)   // comma-ok：断言失败 ok=false，不 panic
switch x := v.(type) { // type switch：按类型分支
case string: fmt.Println("字符串", x)
}

any 把类型检查从编译期推迟到运行时，用多了等于放弃 Go 最强的保护。纪律：业务代码里不用 any 传来传去，它只出现在响应信封、JSON 解码这类「形状未知」的边界上。

5. Repository：接口应该长在「用的人」那边

今天的增量是一个经典模式：Repository（仓储）——把「存取数据」抽象成接口，业务代码只依赖接口，不关心数据在内存、文件还是 Postgres。S3 换数据库时，只写一个新实现，业务代码一行不改。

Go 的惯例：接口定义在消费方（谁用谁定义），而不是实现方——这与 Java 的「先定接口再写实现」相反。本项目 S1 先简单点，接口与内存实现放同一个包；S2·D4 讲三层时会把它按消费方原则重新归置，并解释内存实现为什么值得留着（测试替身）。

今日增量（在学习仓里落盘）

今天属增量类型 ②：加骨架——FamilyRepository 接口 + 内存实现。位置 server/internal/homeos/repository/，包名 repository。内存实现里的 sync.Mutex 今天照抄，S5 正式讲（D4 说过：并发读写 map 会崩，锁就是给 map 站岗的）。

步骤 1 · 接口定义

完整 · server/internal/homeos/repository/family.gopackage repository

import (
    "homecube/internal/homeos/model"
    "homecube/pkg/response"
)

// FamilyRepository 约定「家庭」的存取能力。
// S1 用内存实现；S3 换 Postgres 实现，业务代码不改一行。
type FamilyRepository interface {
    // Save 存入或更新一个家庭。
    Save(f *model.Family) error
    // FindByID 按 id 查找；查不到必须返回 response.ErrNotFound（可用 %w 包装）。
    FindByID(id int64) (*model.Family, error)
}

步骤 2 · 内存实现（Mutex 照抄，S5 正式讲）

完整 · server/internal/homeos/repository/memory.gopackage repository

import (
    "fmt"
    "sync"

    "homecube/internal/homeos/model"
    "homecube/pkg/response"
)

// MemoryFamilyRepo 是 FamilyRepository 的内存实现。
// 含 sync.Mutex → 整个 struct 必须按指针使用（D3 军规第 3 条）。
// mu 的用法今天照抄：进出临界区各一行，成对出现。S5 正式讲。
type MemoryFamilyRepo struct {
    mu   sync.Mutex
    data map[int64]*model.Family
}

// NewMemoryFamilyRepo 构造函数。map 必须 make，否则写入 panic（D4 的坑）。
func NewMemoryFamilyRepo() *MemoryFamilyRepo {
    return &MemoryFamilyRepo{data: make(map[int64]*model.Family)}
}

func (r *MemoryFamilyRepo) Save(f *model.Family) error {
    if f == nil {
        return fmt.Errorf("save family: %w", response.ErrInvalidParam)
    }
    r.mu.Lock()
    defer r.mu.Unlock()   // D4 的肌肉记忆：Lock 的下一行就是 defer Unlock
    r.data[f.ID] = f
    return nil
}

func (r *MemoryFamilyRepo) FindByID(id int64) (*model.Family, error) {
    r.mu.Lock()
    defer r.mu.Unlock()
    f, ok := r.data[id]      // comma-ok（D4）
    if !ok {
        // 哨兵错误 + %w 包装（D4）：上层用 errors.Is 认得出
        return nil, fmt.Errorf("find family %d: %w", id, response.ErrNotFound)
    }
    return f, nil            // 出错分支才 return nil, err；成功就字面量 return
}

看一眼 import：homecube/internal/homeos/model、homecube/pkg/response——D1 讲的「import 路径 = 模块名 + 相对目录」第一次真枪实弹。internal 包能被本模块 import，畅通无阻；换成别人的模块来 import 就会编译失败。

步骤 3 · 测试：接口、哨兵、errors.Is 一锅端

完整 · server/internal/homeos/repository/memory_test.gopackage repository

import (
    "errors"
    "testing"

    "homecube/internal/homeos/model"
    "homecube/pkg/response"
)

func TestMemoryFamilyRepo(t *testing.T) {
    var repo FamilyRepository = NewMemoryFamilyRepo()   // 编译期检查：实现不满足接口，这一行直接报错
    fam := &model.Family{ID: 1, Name: "我们家", OwnerID: 100}

    if err := repo.Save(fam); err != nil {
        t.Fatalf("Save: %v", err)
    }
    got, err := repo.FindByID(1)
    if err != nil || got.Name != "我们家" {
        t.Fatalf("FindByID(1) = %+v, %v", got, err)
    }

    _, err = repo.FindByID(404)
    if !errors.Is(err, response.ErrNotFound) {
        t.Fatalf("FindByID(404) 应返回 ErrNotFound，实际 %v", err)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
把「具体类型的 nil 指针」return 成 error上层 err == nil 是 false，明明没出错却走了错误分支成功路径永远字面量 return nil；今天 playground 里先复现一次
值类型赋给指针接收者的接口Dog does not implement Speaker，报错在赋值处，病根在方法定义处看报错最后一行 (method Speak has pointer receiver)，它直接告诉你病根
到处用 any 传业务数据编译全过，运行时类型断言 panicany 只出现在信封/解码等边界；业务参数用具体类型或接口
类型断言不用 comma-okv.(string) 断言失败直接 panics, ok := v.(string)；多分支用 type switch
一上来就为所有 struct 抽接口满仓库单实现接口，纯增噪音接口在需要替换或需要测试替身时才抽。Repository 符合条件：S3 要换 Postgres
含 Mutex 的 struct 按值传递能编译（go vet 会警告），锁被复制后保护失效含锁 struct 只以指针流转；make lint 里的 go vet 就是抓这个的

卡壳时查什么

正文自足，只有两种情况出去查：

  • 接口与 nil 的坑想再确认一遍：Go FAQ · Why is my nil error value not equal to nil?（可选，官方对这个坑的正面回答）。
  • 方法集规则记不住：不用背。go vet 与编译器会在你犯错时把规则原文贴你脸上，错了再读比先背有效。

自测方法：合上页面，口头回答「S3 换成 Postgres 时，为什么业务代码一行不用改？」——答案里必须出现「依赖接口不依赖实现」「方法集齐就满足」两个要素。答不利索就回讲义 §5 重读。
