前端构建产物与 nginx：静态资源、前端路由与反向代理

昨天你把服务端变成了一个二十兆的镜像。今天把 web/ 也变成一个镜像，并且顺手解决一个你迟早会遇到的问题：浏览器直接访问 /finance/tx/list 或者在那个页面按 F5，为什么会 404。答案在 nginx 的一行 try_files 里。今天写三个文件：web/Dockerfile、web/.dockerignore、web/nginx.conf。

今日目标

课前须知：nginx 是什么，以及它在本站拓扑里的唯一职责

nginx 是一个事件驱动的高性能 HTTP 服务器。它干两类活：发静态文件（把磁盘上的 .html/.js/.css 直接吐给浏览器）和反向代理（把收到的请求转给后面另一个进程，再把响应转回来）。

「反向」是相对「正向」说的：正向代理替客户端出去访问别人（你熟悉的科学上网），反向代理替服务端接客户。浏览器以为自己只在跟一个地址说话，其实后面站着两个容器。

本站的拓扑只有一种，记住它就够了：浏览器 → web 容器的 nginx（80 端口）→ 静态文件直接返回，或者 /api/* 转给 server 容器（8080 端口）。nginx 不做业务判断、不改响应体、不认识 code 字段。

配置文件是一棵嵌套的树：http { server { location { ... } } }。server 块对应「一个站点/一个监听端口」，location 块对应「一类 URL 路径」。今天你只需要写一个 server 块和四个 location。

知识讲义

1. 构建产物是静态文件，所以运行镜像里不需要 Node

web/ 是 Vue 3 + uni-app 项目。npm run build:h5 之后，产物落在 web/dist/build/h5/，里面是一堆 index.html、带内容哈希的 assets/*.js、*.css、图片。这些文件的执行者是浏览器，不是服务器——服务器唯一要做的事是把它们原样发出去。

需要 Node 的时期不需要 Node 的时期
什么时候npm ci 装依赖、npm run build:h5 编译打包、npm run dev:h5 起本地开发服务器构建结束之后的全部时间
在哪Dockerfile 的 builder 阶段（node:20-alpine）Dockerfile 的 runtime 阶段（nginx:1.27-alpine）
镜像体积量级约 200 MB（Node 运行时 + node_modules）约 25 MB（nginx + 你的 dist）

这和昨天服务端那条道理完全同源：Go 二进制不需要 Go 工具链，前端产物不需要 Node。多阶段构建就是把「造东西的环境」和「跑东西的环境」彻底分开，只把成品搬过去。

有人会给前端配一个 Node 的 SSR 服务器（node server.js）来发页面。本项目不需要：uni-app 的 H5 产物是客户端渲染，首屏之后所有数据都走 /api。真要上 SSR，那是一个独立的架构决定，不是部署脚本里顺手加的一行。

2. try_files：前端路由的 404 是怎么来的，又是怎么没的

浏览器请求 /finance/tx/list 时，nginx 默认行为是去磁盘上找 /usr/share/nginx/html/finance/tx/list 这个文件。它当然不存在——这个「路由」只活在 Vue Router 里，是 JavaScript 运行时概念，磁盘上没有对应文件。于是 nginx 返回自己的 404 页面（一个白底黑字的 HTML，不走你的三键信封）。

片段 · 一行解决location / {
    try_files $uri $uri/ /index.html;
}

try_files 按顺序试：$uri（当成文件找）→ $uri/（当成目录找，配合 index 指令）→ 都没有就内部转发到 /index.html。注意最后这个是「内部转发」：浏览器地址栏不变，也不会多一次 302 往返，nginx 只是把 index.html 的内容当作这次请求的响应发出去。Vue Router 拿到页面后自己解析地址栏，渲染出正确的页面。

这也是为什么只有 SPA 需要这一行：多页应用每个路由都有真实的 HTML 文件，磁盘上找得到。

3. /api 反向代理：三个必须写对的细节

细节一：proxy_pass 结尾那个斜杠会吃掉路径。

写法请求 /api/finance/accounts 被转成结果
proxy_pass http://server:8080;/api/finance/accounts正确。你的路由分域前缀 /api/finance/* 原样到达 Gin
proxy_pass http://server:8080/;/finance/accounts错。/api 前缀被替换掉了，Gin 找不到路由，返回 404 + 1001，而前端只会看到「接口全挂了」

规则：proxy_pass 后面带了 URI 部分（哪怕只是一个 /）就会替换掉 location 匹配的那段路径；不带 URI 部分就原样透传。本站路由自带 /api/homeos、/api/finance 前缀，所以要的是「原样透传」。

细节二：用变量形式的 proxy_pass，让 nginx 不在启动时解析上游。如果写死 proxy_pass http://server:8080;，nginx 会在启动那一刻解析 server 这个名字。解析不到（server 容器还没起、或者你今天单独调试 web 容器）就直接启动失败，日志里是 host not found in upstream "server"。而且解析结果会被长期缓存：server 容器重建后换了 IP，nginx 还往旧 IP 发，于是一片 502，直到你重启 nginx。

片段 · 延迟解析resolver 127.0.0.11 valid=10s ipv6=off;   # Docker 内置 DNS，容器编排下固定是这个地址
set $backend "http://server:8080";          # 放进变量 → 解析推迟到每次请求
proxy_pass $backend$request_uri;           # 用变量时必须自己把原始 URI 带上

最后一行的 $request_uri 不能省。一旦 proxy_pass 里出现变量，nginx 就不再自动拼接「location 匹配后剩下的那段路径」，你不显式给 URI，转过去的就是一个空路径。$request_uri 是未经改写的原始请求行（含查询串），正好是我们要的。

细节三：client_max_body_size 默认只有 1 MB。你的附件接口允许单张 5 MB、一笔最多 3 张。nginx 会在请求体还没转给后端之前就先拒掉，返回 413，而且是 nginx 自己的 HTML 错误页——统一响应体、4002 这些一个都不会出现，前端拦截器直接懵。反代层的限额必须放宽到业务限额之上，让后端成为唯一的裁决者（后端该返回 400 + 4002 就返回）。这里设 12m。

4. gzip 与两套完全不同的缓存策略

gzip：文本类资源（HTML/CSS/JS/JSON/SVG）压缩率通常 60%-80%，一个 800 KB 的 vendor bundle 能压到 200 KB 上下。图片和 .wgt 这类已压缩格式不要再压，白费 CPU。注意 gzip 是在 nginx 发响应的那一刻实时压的，所以 gzip_types 里必须显式列出 application/json——你的 /api 响应也是走这个 server 块出去的，报表接口返回几百行流水时差别很明显。

缓存要分两套，混一套必出事故：

资源特征策略为什么
/assets/*.js、*.css文件名带内容哈希，改一个字节就换一个名字max-age=31536000, immutable内容变则名变，所以可以放心缓存一年；浏览器连「问一下有没有更新」的请求都不发
/index.html文件名永远不变，但里面引用着那些带哈希的名字no-cache它是唯一的入口。缓存住了，用户拿到的就是旧的哈希文件名，你的新版本永远发不出去（发版后「用户说要清缓存才生效」就是这个原因）

no-cache 不等于 no-store。no-cache 是「可以存，但每次用之前必须回源确认」（配合 ETag，通常得到一个 304，几乎不花流量）；no-store 是「根本不许存」。入口 HTML 要的是前者。

5. /healthz 与 /metrics 故意不经过 nginx

这两个路径不写进 nginx 配置：

  • /healthz 是给容器编排与负载均衡看的（S8·D3 的 healthcheck 直接在 server 容器内部访问 localhost:8080/healthz），不需要暴露到公网。暴露了也无害，但会被各种扫描器天天打，污染你的日志与指标。
  • /metrics（S8·D9 才实现）里是全站的请求量与延迟分布，属于内部信息，绝不上公网。它只在容器网络内可达，本机通过 server 容器的 127.0.0.1:8081 端口映射看。

原则一句话：nginx 是产品的正门，只开正门需要的两样——页面和 /api。运维用的门走内部网络。

今日增量（在学习仓里落盘）

今天属增量类型 ⑥：工程化收口产物。三个文件都在 web/ 下——因为前端镜像的构建上下文是 ./web，.dockerignore 与 nginx.conf 必须和 Dockerfile 在同一个上下文里。收工时 make build / make test 仍必须绿。

步骤 1 · web/Dockerfile

完整 · web/Dockerfile# ---------- 阶段一：builder（Node 只活在这里） ----------
FROM node:20-alpine AS builder
WORKDIR /web

# 先只拷依赖清单：package.json / 锁文件不变，npm ci 就命中缓存
COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build:h5

# ---------- 阶段二：runtime（nginx 发静态文件，没有 Node） ----------
FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /web/dist/build/h5/ /usr/share/nginx/html/
EXPOSE 80
  • 覆盖 /etc/nginx/conf.d/default.conf 而不是改 /etc/nginx/nginx.conf：官方镜像的主配置已经 include /etc/nginx/conf.d/*.conf，你只需要提供那个 server 块。改动面越小，将来升级 nginx 版本越省事。
  • 包管理器不是 npm 就把 COPY package*.json 与 npm ci 换成对应物（pnpm 是 COPY package.json pnpm-lock.yaml ./ + pnpm install --frozen-lockfile，构建命令 pnpm build:h5）。锁文件必须进镜像构建，否则每次构建装到的依赖版本都可能不一样，「昨天还能跑」就来了。

步骤 2 · web/.dockerignore

完整 · web/.dockerignorenode_modules
dist
unpackage
.hbuilderx
.git
*.log

node_modules 是这里的头等目标：不挡的话每次构建都要把几万个小文件打包发给 Docker 引擎，而且它会让 npm ci 那一层的缓存彻底失效（COPY . . 的内容变了）。dist 与 unpackage 是本机构建产物，容器里会重新生成，本机的旧产物混进去只会造成「镜像里是上一次的页面」这种极难查的假象。

步骤 3 · web/nginx.conf

完整 · web/nginx.confserver {
    listen       80;
    server_name  _;
    root         /usr/share/nginx/html;
    index        index.html;

    # 附件上传：nginx 默认 1m 会抢在后端之前返回 413（还不是统一响应体）
    client_max_body_size 12m;

    # 文本类实时压缩；application/json 必须列进来，/api 的响应也走这里
    gzip            on;
    gzip_vary       on;
    gzip_min_length 1024;
    gzip_comp_level 5;
    gzip_types      text/plain text/css application/javascript application/json
                    image/svg+xml;

    # Docker 内置 DNS。放进变量 → 上游解析推迟到每次请求，
    # 于是 server 容器还没起时 nginx 也能正常启动
    resolver 127.0.0.11 valid=10s ipv6=off;

    # ---- 后端接口：原样透传 /api 前缀，不替换路径 ----
    location /api/ {
        set $backend "http://server:8080";
        proxy_pass $backend$request_uri;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 导出接口要跑聚合再拼 CSV，60s 比默认的 60s 读超时更明确地写在这
        proxy_connect_timeout 5s;
        proxy_read_timeout    60s;
    }

    # ---- 带内容哈希的静态资源：强缓存一年 ----
    location /assets/ {
        expires    1y;
        add_header Cache-Control "public, max-age=31536000, immutable";
        try_files  $uri =404;
    }

    # ---- 入口 HTML：可以存，但每次必须回源确认 ----
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # ---- 前端路由：磁盘上找不到就回落到 index.html，交给 Vue Router ----
    location / {
        try_files $uri $uri/ /index.html;
    }
}

四个 X-* 请求头今天先照抄，S8·D5 会正式讲它们：nginx 是代理，后端直接看到的对端 IP 是 nginx 容器的 IP，不是用户的真实 IP；真实 IP 只能靠 X-Forwarded-For 传递，而后端要不要相信这个头，取决于你有没有告诉它「谁是可信代理」。这是昨天埋的伏笔，两天后兑现。

坑现象正确姿势
proxy_pass 结尾多了个 /所有接口 404 + 1001，前端只报「请求失败」不带 URI 部分（或用 $request_uri 显式透传），让 /api 前缀原样到达 Gin

今日名词卡

术语一句话解释
反向代理替服务端接客户：浏览器以为只跟一个地址说话，后面其实站着多个容器
上游 upstream反向代理要转过去的那个后端。这里是 server 容器的 8080
try_files按顺序在磁盘上找，都找不到就内部转发到最后一个参数；SPA 前端路由的兜底
内部转发nginx 自己换个路径重新处理，浏览器无感、地址栏不变、不多一次往返
$uri / $request_uri前者是规范化并解码后的路径（不含查询串），后者是客户端发来的原始请求行（含查询串）
proxy_set_header转发时补上的请求头。X-Forwarded-For 携带真实客户端 IP 链，S8·D5 正式讲
resolvernginx 自己用的 DNS 服务器。Docker 内置 DNS 固定是 127.0.0.11
内容哈希文件名index-a1b2c3.js：内容变则名变，是「强缓存一年」能成立的前提
no-cache vs no-store前者「存了但每次回源确认」，后者「根本不许存」。入口 HTML 用前者
immutable告诉浏览器这个资源在有效期内绝不会变，连刷新都不必回源确认
gzip响应体实时压缩，文本类省六到八成流量；已压缩格式（图片）不要再压
413请求体超限。反代层的 413 不走统一响应体，所以要把限额放宽到后端之上
