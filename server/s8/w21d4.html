S8 · DAY 4 预计 30 分钟 难度 ★★★★☆

容器内执行迁移：两套 schema、启动前跑还是启动时跑

昨天 migrate 服务的 command 还只是一个 -version 占位。今天把它变成真家伙：在一个一次性容器里，把 homeos 与 finance 两套各自独立计数的迁移跑到最新，并且要能一步退回、能证明退回是真的。顺带回答一个上线必问的问题：迁移失败了，服务该不该起？

今日目标

知识讲义

1. golang-migrate 的心智模型：一个版本号 + 两个 SQL 文件

它的模型极简，三条就讲完了：

  • 迁移文件成对存在：N_标题.up.sql 与 N_标题.down.sql。N 是整数版本号，必须递增且唯一。
  • 数据库里有一张版本记录表（默认叫 schema_migrations），只有两列：version BIGINT（当前跑到第几版）与 dirty BOOLEAN（上一次迁移是否半途失败）。
  • up = 从当前 version 往上，依次执行所有更高版本的 .up.sql；down 1 = 执行当前版本的 .down.sql 并把 version 减一。没有「智能比对」，它只做加减法。

命令行形态：

片段 · CLI 形态migrate -path <迁移目录> -database "<DSN>" <命令>

# 命令一览（今天会用到前四个）
up                 # 跑到最新
up 2               # 只往上跑两步
down 1             # 退回一步（不带数字的 down 会一路退到空库，非常危险）
version            # 打印当前版本与 dirty 状态
force 7            # dirty 时手工把版本钉到 7（修完数据之后用）
goto 5             # 不管方向，直接迁移到第 5 版

down 不带数字 = 一路退到版本 0 = 把库清空。在容器里手滑敲一次，昨天上传的附件记录、这周记的流水全没了。所有脚本里都写 down 1，永远不写裸 down。

2. 两套 schema 各自独立计数，所以必须有两张版本表

你的迁移目录是两个，序号各自从 0001 起：

结构<repo>/server/migrations/
├── homeos/    homeos_0001_*.up.sql / .down.sql, homeos_0002_*, …
└── finance/   finance_0001_*.up.sql / .down.sql, finance_0002_*, …

如果两套都往同一个 schema_migrations 里写版本号，会发生什么？跑完 homeos 到第 9 版，表里记着 version=9；接着跑 finance，它一看「已经第 9 版了，我的 1-9 都不用跑」，直接退出——finance 一张表都没建，而命令返回 0。这是编排里最阴的一类故障：绿灯，但什么都没发生。

本站的解法：用 DSN 的 search_path 参数把两套迁移彻底隔开。search_path 是 Postgres 的「默认 schema 搜索路径」，未加限定的表名会按它解析。所以：

片段 · 两条 DSN，只差一个参数# homeos 一套：版本表落在 homeos.schema_migrations
postgres://homecube:homecube123@postgres:5432/homecube?sslmode=disable&search_path=homeos

# finance 一套：版本表落在 finance.schema_migrations
postgres://homecube:homecube123@postgres:5432/homecube?sslmode=disable&search_path=finance

两条 DSN 连的是同一个库，但会话的默认 schema 不同，于是各自建各自的 schema_migrations，版本号互不干扰。homeos 跑到 9、finance 跑到 12，两张表各记各的，完全合法。

一个先后依赖必须先解决：search_path=homeos 要求 homeos 这个 schema 已经存在，否则 migrate 一上来建版本表就会报 no schema has been selected to create in。而「建 schema」这件事你又不想塞进某一条业务迁移里（它属于库的初始化，不属于任何一个 code）。本站口径：交给 postgres 官方镜像的初始化钩子——把 /docker-entrypoint-initdb.d/ 里的 .sql 文件在库第一次初始化时自动执行一次。今天多写一个两行的 SQL 文件解决它。

这也解释了「不跨 schema join」这条纪律在部署层的对应物：两套迁移在物理上就是两条独立的演进线，一条能单独 up、单独 down，另一条不受影响。将来真要把 finance 拆成独立服务、搬去另一个库，迁移文件一行都不用改。

3. 文件名与工具解析规则的冲突，以及怎么处理

golang-migrate 解析文件名时，取第一个 . 之前的部分当版本号，并要求它是纯整数。homeos_0001_init_user.up.sql 的第一段是 homeos_0001_init_user，转不成整数，它要么报错要么直接忽略这些文件（表现是「跑完了但一版都没跑」，又一个绿灯陷阱）。

两条出路，选一条并写进 README，不要两条都留：

出路做法代价
A · 暂存改名（今天采用）保持仓库里的文件名不动，迁移脚本在容器内把它们复制到临时目录，复制时剥掉 {code}_ 前缀（目录本身已经说明了 code，前缀在文件名里是冗余信息），再让 migrate 读临时目录多一层「仓库文件名 ≠ 工具看到的文件名」的间接性，排查问题时要记得这一层
B · 改命名规则把迁移文件统一改成 0001_init_user.up.sql，靠所在目录区分 code要重命名 S3 以来积累的几十对文件，且与既有的命名约定不一致

今天走 A，因为它是纯增量、不动历史文件、十行 shell 就能收口。脚本里那句剥前缀的参数展开是这段的核心，值得看懂：${base#${1}_} 的意思是「从 $base 开头删掉最短匹配的 {code}_ 前缀」——# 是删前缀，% 是删后缀，一个 # 最短匹配、两个 ## 最长匹配。

4. 启动前显式迁移 vs 启动时 AUTO_MIGRATE

S3 起你的 config 里有一个 AUTO_MIGRATE 开关，它驱动的是 GORM 的 AutoMigrate：读你的 struct 定义，比对数据库现状，把缺的表和缺的列补上。开发期它非常好用——改个 struct，重启就有了。但它不是迁移工具：

能力AutoMigrate（启动时）golang-migrate（启动前显式跑）
加表、加列会会（你写在 up.sql 里的）
删列、改列类型、重命名基本不做（怕丢数据），于 schema 会长期漂移成「struct 与库里不一样」你做，且写在文件里、可 review
回滚没有 down 这个概念down 1
版本记录无。你无法回答「这个库现在是第几版」schema_migrations
数据迁移（不只是 DDL）做不了。回填一列历史数据这种活它无能为力up.sql 里想写什么写什么
多副本同时启动两个进程同时 AutoMigrate 会互相踩，偶发 DDL 死锁迁移是一个独立的一次性容器，跑完退出，业务副本才起
可审计性「谁改的表、什么时候、为什么」全无痕迹git 历史就是答案

取舍结论，也是本站口径：

  • 本机开发：AUTO_MIGRATE=true，图快。make run 一把起。
  • 容器编排与任何「给别人跑」的场景：AUTO_MIGRATE=false（昨天 compose 里已经这么写了），schema 只由 migrate 服务改。两条路不能同时开，否则你分不清某个列是谁加的，也永远复现不出别人机器上的 schema。

5. 迁移失败，容器该不该起？

不该。理由不是洁癖：schema 落后于代码时，服务起来之后每一条查询都在报错，而用户看到的是「登录不上」「列表空白」，你要花很久才定位到「其实是迁移没跑完」。让失败在启动阶段就炸掉、炸得响亮，是最便宜的可用性。

三种实现方式，本站选第一种：

方式怎么写为什么选/不选
Makefile 里用 && 串起来（本站）migrate up && compose up -d短路是 shell 的原生语义，迁移非 0 退出就不起服务。简单、可见、好解释
depends_on + service_completed_successfullyserver 等 migrate 成功退出更「编排原生」，但它要求 migrate 在 up 时也被纳入；而 migrate 挂着 profiles，被依赖的服务与 profile 的激活行为在不同 compose 版本上表现不一致。教学期不赌这种隐式行为
server 启动时自己跑迁移进程内调 migrate 库多副本会同时跑；且「业务进程」与「改 schema 的特权动作」耦合在一起，上线后想单独控制迁移就没抓手了

还有一层：迁移失败之后，版本表可能停在 dirty=true。此时任何 up / down 都会被拒绝，报 Dirty database version N. Fix and force version。这是设计如此——它不猜你那条 SQL 执行到哪一半了。处置顺序永远是：① 看日志找到失败的那条 SQL；② 手工把数据修到「这一版要么完全生效、要么完全没生效」的确定状态；③ force 到那个确定的版本号；④ 重新 up。直接 force 而不修数据，等于把脏数据合法化。

想让 dirty 尽量少出现，有个便宜的技巧：一条迁移里如果有多个 DDL，Postgres 的 DDL 是可以在事务里回滚的，所以把一条 .up.sql 的内容用 BEGIN; … COMMIT; 包起来（或依赖 migrate 的 -multi-statement 行为前先确认版本），失败时整条自动回滚，不会留下半张表。这条不是今天的必做项，但值得记进 notes/。

6. down 真能回滚吗？只有跑过才知道

S3 就把「每条 down 必须真能回滚」列为判据，但那时你是手工 up/down 验证的。今天把它变成脚本，理由很实际：down 文件是全套代码里最容易腐烂的部分——你写 up 的时候会认真想，写 down 的时候只想赶紧收工，而它可能几个月都不会被执行一次，直到某天你真的要回滚。判定标准只有两条：

  • 版本号真的退了：读 {code}.schema_migrations 的 version，down 1 之后必须比之前小。这一条对任何迁移都成立，是通用断言。
  • 那条迁移建的东西真的没了：查 information_schema.tables。这一条只对「建表」类迁移成立，所以做成可选参数，由你指定要断言哪张表。

跑完 down 一定要再 up 回去，把库恢复到最新——否则明天的开发会在一个落后一版的 schema 上进行，而你会以为代码有 bug。

步骤 1 · 让两个 schema 先存在

完整 · deploy/initdb/01-schemas.sql-- postgres 官方镜像会在「数据目录为空的第一次初始化」时，
-- 按文件名顺序自动执行本目录下的 .sql / .sh。
-- 这里只做一件事：把两个业务 schema 建出来，
-- 好让 golang-migrate 的 search_path 有落点、版本表有地方待。
CREATE SCHEMA IF NOT EXISTS homeos;
CREATE SCHEMA IF NOT EXISTS finance;

这个钩子只在库第一次初始化时执行（和 POSTGRES_* 那套变量同一个前提：数据目录为空）。如果你的数据卷已经建过了，它不会再跑。补救很简单，因为脚本是幂等的：docker compose exec postgres psql -U homecube -d homecube -f /docker-entrypoint-initdb.d/01-schemas.sql，或者干脆 make nuke 重来（开发期数据不值钱，但要知道自己在做什么）。

步骤 2 · 容器内跑的迁移脚本

完整 · deploy/migrate.sh#!/bin/sh
# 在 migrate 容器内执行。用法：migrate.sh up | down 1 | version
set -eu

# 没有 set -o pipefail 的 sh，用显式判断兜住；关键是 set -e：任何一步失败立刻退出非 0
ACTION="${1:-up}"
shift || true

# DB_* 由 docker-compose.yml 注入，名字是钉死的那一套
DSN_BASE="postgres://$DB_USER:$DB_PASS@$DB_HOST:$DB_PORT/$DB_NAME?sslmode=$DB_SSLMODE"

# ---- 把 {code}_{seq}_{desc}.up.sql 暂存改名为 {seq}_{desc}.up.sql ----
# golang-migrate 要求文件名第一段是纯整数版本号，带 code 前缀它解析不了。
# 目录已经说明了 code，前缀在文件名里是冗余的，剥掉即可。
stage() {
  code="$1"
  rm -rf "/tmp/$code"
  mkdir -p "/tmp/$code"
  for f in "/migrations/$code"/*.sql; do
    [ -e "$f" ] || continue
    base=$(basename "$f")
    rest=${base#${code}_}                 # 删掉最短匹配的 "{code}_" 前缀
    cp "$f" "/tmp/$code/$rest"
  done
}

# ---- 对两套 schema 各执行一次同一个动作 ----
run_both() {
  for code in homeos finance; do
    stage "$code"
    echo "== [$code] migrate $ACTION $*"
    migrate -path "/tmp/$code" \
            -database "$DSN_BASE&search_path=$code" \
            "$ACTION" "$@"
  done
}

case "$ACTION" in
  up)      run_both up ;;
  down)    run_both down "$@" ;;      # 必须带步数，例如 down 1
  version) run_both version ;;
  force)   run_both force "$@" ;;
  *) echo "用法: migrate.sh up | down 1 | version | force N"; exit 2 ;;
esac

三条要点：

  • set -eu 是脚本的底线。-e 让任何一步失败立刻以非 0 退出（这样 && 才能短路、compose 才能报红），-u 让引用未定义变量直接报错而不是当空字符串——后者在 DSN 里是灾难性的：DB_PASS 拼空了，你会连到一个不存在的用户，报的却是「认证失败」。
  • version 也走同一个循环：它会把两套 schema 的当前版本各打印一次，一眼看出哪一套落后了。
  • down 的步数用 "$@" 透传，脚本自己不填默认值。宁可因为忘了带参数而报错，也不要默认「退到底」。

步骤 4 · 往返验证脚本

完整 · scripts/migrate-roundtrip.sh#!/usr/bin/env bash
# 判据：down 1 之后版本号真的退了、指定的表真的没了，然后 up 回去。
# 用法：scripts/migrate-roundtrip.sh [schema] [该版应删除的表名]
#   例：scripts/migrate-roundtrip.sh homeos homeos_user
set -euo pipefail

SCHEMA="${1:-homeos}"
TABLE="${2:-}"
PSQL="docker compose exec -T postgres psql -U homecube -d homecube -Atq"

version() { $PSQL -c "SELECT version FROM $SCHEMA.schema_migrations"; }
dirty()   { $PSQL -c "SELECT dirty   FROM $SCHEMA.schema_migrations"; }
exists()  { $PSQL -c "SELECT count(*) FROM information_schema.tables \
                      WHERE table_schema='$SCHEMA' AND table_name='$1'"; }
fail()    { echo "[FAIL] $1"; exit 1; }

before=$(version)
echo "[before] $SCHEMA version=$before dirty=$(dirty)"
[ "$(dirty)" = "f" ] || fail "起始状态是 dirty，先修数据再 force，别在脏库上做往返验证"

docker compose --profile tools run --rm migrate sh /migrate.sh down 1
after=$(version)
echo "[after down 1] $SCHEMA version=$after"
[ "$after" -lt "$before" ] || fail "版本号没有退（$before → $after），down 是摆设"

if [ -n "$TABLE" ]; then
  [ "$(exists "$TABLE")" = "0" ] || fail "$SCHEMA.$TABLE 在 down 之后仍然存在"
  echo "[ok] $SCHEMA.$TABLE 已被删除"
fi

docker compose --profile tools run --rm migrate sh /migrate.sh up
[ "$(version)" = "$before" ] || fail "up 回去之后版本不等于 $before"
echo "[ok] 往返验证通过，库已恢复到 version=$before"

search_path会话级的默认 schema 搜索路径；未加限定的表名按它解析。可写在 DSN 的查询参数里
schema_migrationsgolang-migrate 的版本记录表，两列：version 与 dirty
dirty「上一次迁移半途失败」的标记。为真时一切 up/down 被拒，必须先修数据再 force
force N手工把版本号钉到 N，不改任何数据。修完脏状态后用它重新对齐
独立序列两个 code 的迁移序号各自从 0001 起，互不影响；对应两张版本表
down 步数down 1 退一版；不带数字的 down 退到版本 0（清库）
AutoMigrateGORM 的 struct→DDL 对齐工具，只加不减、无版本无回滚，不是迁移工具
初始化钩子官方 postgres 镜像在数据目录为空时自动执行 /docker-entrypoint-initdb.d/ 下的 .sql/.sh
information_schemaPostgres 的元数据视图集合，查「某 schema 下有没有某张表」用它，不用 \dt 那套交互命令
参数展开 ${v#前缀}shell 里删掉最短匹配的前缀（## 是最长、%>/<%% 是后缀），今天的改名脚本靠它
set -eu任何一步失败即退出、引用未定义变量即报错。所有部署脚本的第一行都该有它
