S8 · 收口与部署

这两周一条接口都不新增，只做一件事：把前 20 周写完的东西变成别人能跑起来的东西。判据只有一句——在一台干净机器上，照着 README 只敲一条命令，全套服务起到 healthy，冒烟脚本连跑两次都绿。做不到就说明前面某个阶段留了「只有你本机跑得通」的隐性依赖，而那是这门课最贵的一种失败。

为什么部署放在最后，而且只给两周

部署物提前引入会让「每天可跑」变成「每天等构建」——这也是本阶段独享第六类增量（工程化收口产物）的原因：Dockerfile、compose、nginx 配置、CI workflow、对账与冒烟脚本，这些在 S1-S7 出现一律违规。而两周够用的前提是 S1-S7 一直把仓库保持绿：迁移能 up→down→up、测试带 -race、config 只有一张变量表。S8 是照镜子，不是补课。

阶段判据（全过才算 S8 通过，也才算毕业）

不通过就原地重做，不跳阶段。S8 的每一项判据都是「别人能不能复现」的形状。代码写完不等于交付完成——历史反例里最贵的一类不是接口写错，而是「作者机器上能跑」。

本阶段不做什么（明确划掉，免得手滑）

  • 不新增一条业务接口——72 条的分母在 S7 结束时就锁死了
  • 不上 Kubernetes、不做 Helm chart、不搞多机编排；单机 compose 是本阶段的全部拓扑
  • 不做监控告警平台、不做链路追踪。request_id 串起日志就到此为止
  • 不做蓝绿/灰度发布——回退能力靠镜像 tag 和 up→down→up 可重放的迁移，不靠编排系统
  • 不引入 Redis、消息队列、事件总线（课程范围外，只作前瞻句）
  • 不追覆盖率数字。门槛是棘轮：只防倒退，不冲指标
