兑现两条伏笔：可信代理、跨域收口与 /healthz 的依赖就绪态

今天不加任何新功能，专门收三笔旧账。它们都是「本机跑得好好的、一上容器就变味」的典型：真实客户端 IP 变成了容器网段地址、跨域白名单里那个 localhost:5173 再也没人用了、/healthz 在数据库挂掉之后依然理直气壮地返回 ok。三笔账都有测试可以钉死，今天一并结清。

今日目标

知识讲义

1. 伏笔一：SetTrustedProxies 与那个你照抄了两天的 X-Forwarded-For

S8·D2 你在 nginx 里照抄了四行 proxy_set_header，其中一行是：

片段 · 昨天抄的那行proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

先讲清这个头的来历。HTTP 请求经过代理转发之后，后端用 TCP 连接看到的对端地址是代理的地址，不是用户的。为了让后端还能知道原始客户端，业界约定了一个头：X-Forwarded-For，格式是一条逗号分隔的 IP 链，最左边是最原始的那个客户端，往右每经过一个代理追加一个。

问题来了：这个头是客户端自己也能发的普通请求头。任何人 curl -H 'X-Forwarded-For: 1.2.3.4' 就能伪造。所以后端不能无脑相信它，必须先回答一个问题：「这个请求是从我的可信代理来的吗？」只有是，才去读它带的 X-Forwarded-For；不是，就只认 TCP 对端地址。Gin 里回答这个问题的 API 就是 SetTrustedProxies。

不设会怎样？Gin 的默认行为是信任所有代理，也就是无条件采信 X-Forwarded-For 的最左值。在你的编排里，这会得到两个都不对的结果：

场景c.ClientIP() 拿到什么为什么不对
浏览器 → nginx → server（正常路径）不设可信代理时：用户真实 IP（运气好）
设了可信代理但没把 nginx 网段列进去：172.28.0.2 这类容器网段地址		前者是「靠运气的安全」——任何人都能伪造；后者是「日志里全是容器 IP」，看不到用户
恶意请求带 X-Forwarded-For: 1.2.3.41.2.3.4伪造成功。你按 IP 做的限流、风控、审计全部作废

这不是理论风险，你的清单里就有一条会被它打穿的接口。验证码发送接口 POST /api/homeos/auth/sms-code 要按来源限流（否则谁都能拿你的手机号刷短信）。如果 c.ClientIP() 可被请求头左右，攻击者每换一个伪造 IP 就能再发一次；反过来，如果它恒等于 nginx 容器的 IP，那么全家所有人共享同一个限流桶——你妈发一次验证码，你就发不了了。两种都是事故。

正确做法分三步，缺一不可：

  1. 把容器网络的网段固定下来。compose 默认会随机分配一个 172.x.0.0/16，每次重建可能不一样，你没法写进配置。显式指定一个子网（下面用 172.28.0.0/16）。
  2. 只把这个网段列为可信代理。nginx 容器一定在这个网段里，所以它加的 X-Forwarded-For 可信；来自公网的直连请求不可能源自闭网段，伪造的头会被忽略。
  3. 默认值必须是「不信任何代理」，也就是 SetTrustedProxies(nil)。这样即使忘了配环境变量，行为也是保守的（拿到容器 IP，日志难看但不会被打穿），而不是危险的。

Gin 在你没调用 SetTrustedProxies 时会在启动日志里打一条 [WARNING]，大意是「你正在用默认的可信代理配置，建议显式设置」。这条警告不是噪音，它是本节内容的官方提示。今天之后，你的启动日志里不该再有它。

2. 伏笔二：CORS_ORIGIN 在容器编排下怎么收口

先把「同源」的定义钉死：协议、域名、端口三者全同才叫同源。差任何一个都是跨源，浏览器就会启动 CORS 那套检查。

S7 你加 CORS_ORIGIN 时，它的值一定是 http://localhost:5173 之类的本机开发服务器地址——因为那时前端跑在 dev server 上，后端跑在 8080，端口不同就是跨源。容器编排把这个前提整个换掉了：

本机开发（S7 时的状态）容器编排（今天的状态）
页面从哪来dev server，http://localhost:5173nginx，http://localhost:8080
接口发到哪http://localhost:8080/api/...http://localhost:8080/api/...（nginx 内部转给 server）
浏览器看到的源两个，跨源一个，同源
需要 CORS 吗需要根本不会触发。反向代理最大的好处之一就是这个

那 CORS_ORIGIN 是不是就可以随便填了？不行，它是保险丝：一旦哪天你在本机起 dev server 直连容器端口调试、或者把它部署到真域名下、或者有第三方页面想嵌你的接口，起作用的还是它。收口四条规则：

  • 填对外入口的源，不是后端自己的地址。容器口径就是 http://localhost:8080（本机演示）或你的正式域名。填 http://localhost:8081（server 那个只绑回环的端口）是常见笔误——那个地址浏览器从来不访问。
  • 绝不用 *。两个理由：① Access-Control-Allow-Origin: * 与「允许携带凭证」是互斥的，浏览器会直接拒绝这类组合；② 它等于放弃白名单，任何网站都能带着用户的浏览器来调你的接口。
  • 空值表示「不挂 CORS 中间件」，不表示「允许所有」。同源部署下这是正常状态，也是本站口径。把「没配」和「全放」区分开，是一个很小但很值的设计决定。
  • CORS 中间件必须注册在鉴权中间件之前。浏览器对非简单请求会先发一个 OPTIONS 预检，不带任何业务凭证。如果鉴权在前面，预检会被拦成 401 + 1005，而浏览器只会告诉你一句「CORS 错误」——服务端日志里干干净净，你会往前端方向查半天。

3. /healthz：从「进程活着」到「依赖就绪」

S1·D6 你写的第一个端点就是 /healthz，它当时返回：

片段 · 静态版（S1 起沿用至今）{"code":0,"message":"ok","data":{"status":"ok"}}

这个版本的语义是「我的 HTTP 循环还在转」。在昨天的编排里它被拿去当 healthcheck 用，于是出现了一个荒谬的组合：数据库挂了，server 依然报健康，web 依然正常起，用户看到一片 500 + 5000。编排系统被你骗了。

今天升级语义为依赖就绪：不仅进程活着，还要「我吃饭的家伙能用」。判据刻意收窄到最小——只查自己那两个 schema 在不在、连接通不通：

  • 查一条不涉及任何业务表的元数据查询，超时 1 秒。不许查业务数据（那是巡检，不是就绪探测），也不许查外部服务（短信通道挂了不该让你的健康检查变红，那是降级而不是不可用）。
  • 就绪 → 200 + code 0 + data.status = "ok"（响应体形状一个字不改，前端与脚本都不用动）。
  • 未就绪 → 503 + code 5000。业务码仍走错误码表，HTTP 状态按语义细化——这是既定口径，503 比 500 更准确地告诉编排系统「我是暂时不可用，别把我当成崩溃」。

它和编排的联动是自动的：healthcheck 用 wget，非 2xx 退出码非 0 → server 转 unhealthy → 依赖 service_healthy 的 web 起不来（或者已经在跑的会被标红）。你终于有了一个能反映真实状态的信号灯。

为什么只有一个端点，不拆成「存活探针」和「就绪探针」两个？成熟部署里这两者通常分开：存活探针只看进程是否卡死（挂了才重启），就绪探针看依赖（不就绪就摘流量、但不重启）。本站只允许 /healthz 与 /metrics 两个非业务路由，所以两者合一，语义取就绪。代价要说清楚：库抖一下，编排会认为服务不健康——如果将来接了自动重启策略，就可能把本来能自愈的进程也重启掉。这也是昨天故意不加 restart 的另一个理由。

实现上用接口注入，这是 S1·D5 那条伏笔（接口与隐式实现）在部署层的兑现：handler 依赖一个 Prober 接口，不依赖 *gorm.DB。于是测试可以塞一个假实现，不需要真数据库就能测「就绪」与「未就绪」两条分支。

// splitList 把 "a, b,,c" 变成 ["a","b","c"]：逐项 TrimSpace，丢掉空串
func splitList(raw string) []string {
    var out []string
    for _, item := range strings.Split(raw, ",") {
        if s := strings.TrimSpace(item); s != "" {
            out = append(out, s)
        }
    }
    return out
}

读取处照旧用 os.Getenv：cfg.TrustedProxies = splitList(os.Getenv("TRUSTED_PROXIES"))，cfg.CORSOrigins = splitList(os.Getenv("CORS_ORIGIN"))。变量名沿用 CORS_ORIGIN（单数），不自创别名——多值就用逗号写在同一个变量里。

步骤 2 · 健康检查：接口 + 两个实现

完整 · internal/platform/healthz/healthz.gopackage healthz

import (
    "context"
    "fmt"
    "net/http"
    "time"

    "github.com/gin-gonic/gin"
    "gorm.io/gorm"

    "homecube/pkg/response"
)

// Prober 是「依赖就绪吗」这一个问题的抽象。
// handler 只依赖它，不依赖 *gorm.DB —— 所以测试能塞假实现。
type Prober interface {
    Probe(ctx context.Context) error
}

const probeTimeout = 1 * time.Second

// Handler 返回 GET /healthz 的处理器。
// 就绪：200 + code 0 + {"status":"ok"}（响应体形状与 S1 完全一致）
// 未就绪：503 + code 5000
func Handler(p Prober) gin.HandlerFunc {
    return func(c *gin.Context) {
        ctx, cancel := context.WithTimeout(c.Request.Context(), probeTimeout)
        defer cancel()

        if err := p.Probe(ctx); err != nil {
            c.Error(err) // 进日志，但不进响应体：健康检查不泄露内部细节给调用方
            response.Fail(c, http.StatusServiceUnavailable,
                response.CodeInternal, "依赖未就绪")
            return
        }
        response.OK(c, gin.H{"status": "ok"})
    }
}

// schemaProber 是生产实现：只证明「连接可用 + 两个 schema 都在」。
// 不查任何业务表，也不查外部服务。
type schemaProber struct{ db *gorm.DB }

func NewSchemaProber(db *gorm.DB) Prober { return schemaProber{db: db} }

const probeSQL = `SELECT count(*) FROM pg_namespace WHERE nspname IN ('homeos','finance')`

func (p schemaProber) Probe(ctx context.Context) error {
    var n int
    if err := p.db.WithContext(ctx).Raw(probeSQL).Scan(&n).Error; err != nil {
        return fmt.Errorf("数据库连接不可用: %w", err)
    }
    if n != 2 {
        return fmt.Errorf("schema 未就绪: 期望 2 个，实际 %d 个（迁移跑了吗？）", n)
    }
    return nil
}

response.CodeInternal 这个常量名以你 S1 落的那张错误码表为准（值必须是 5000）。c.Error(err) 只是把错误交给 Gin 的错误收集，配合请求日志中间件打出来；响应体里不带 err 文本，因为 /healthz 可能被任何能访问到端口的人调用。
