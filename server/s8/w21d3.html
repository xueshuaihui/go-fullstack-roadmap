docker-compose 编排：四个服务、健康检查与两段变量

前两天你有了两个镜像，但它们各自孤岛。今天用一份 docker-compose.yml 把 postgres / server / web / migrate 四个服务连成一个能一起起、一起停、互相知道对方在哪的整体。今天最难的不是语法，是两件事：「起来了」不等于「能用了」（healthcheck 与 depends_on 的全部意义），以及「同一个数据库口令要写两遍，而且两遍的变量名不一样」。

今日目标

知识讲义

1. compose 是什么：一份 YAML 描述「一组容器怎么活」

docker run 一次只能起一个容器，参数全靠命令行传。docker compose 把「起哪几个容器、用哪个镜像、挂哪些卷、端口怎么映射、环境变量是什么、谁等谁」写进一份 docker-compose.yml，然后 docker compose up 一把拉起。

它还顺手给了你三样免费的东西，这三样是今天配置能成立的底层原因：

免费的东西具体表现你会在哪里用到
一个专属网络所有服务自动加入同一个网络（默认叫 <项目名>_default）不需要 -p 就能互通
内置 DNS服务名就是主机名。server 这个服务在别的容器里可以用 http://server:8080 访问昨天 nginx 配置里那句 set $backend "http://server:8080"；今天 DB_HOST: postgres
一个项目命名空间容器名、卷名、网络名都带项目前缀，多个项目互不干扰name: homecube 这一行决定了前缀

常用命令就五条，今天全部会用到：up -d（后台起）、ps（看状态与健康度）、logs -f <服务>（看日志）、exec <服务> <命令>（进容器执行）、down（停并删容器与网络，加 -v 才会删数据卷）。

2. 四个服务，四种生命周期

服务镜像生命周期职责边界
postgrespostgres:16-alpine（官方）常驻，数据落在命名卷只管存储。不做业务、不写 SQL 逻辑
migratemigrate/migrate（官方）一次性，跑完就退出（exit 0）只管改 schema。挂了 profiles: ["tools"]，日常 up 不会起它
server你昨天构建的 homecube-server常驻72 条接口 + /healthz + /metrics。不开端口给公网，只开给本机回环
web你前天构建的 homecube-web常驻唯一的正门。发静态资源、把 /api 转给 server

端口口径今天定死，后面九天不再变：web 占 8080（对外入口，浏览器访问的就是它），server 占 127.0.0.1:8081（只绑本机回环，给你 curl /healthz 与 /metrics 用），postgres 占 127.0.0.1:5432（只绑回环，给你的数据库客户端用）。

绑 127.0.0.1 与不绑是两件事。"5432:5432" 意味着局域网里任何人都能连你的数据库，而口令是 .env 里那个。"127.0.0.1:5432:5432" 才是「只允许这台机器连」。开发期一律用后者。

3. 「起来了」不等于「能用了」：healthcheck 与 depends_on 的三种条件

这是编排里最贵的一课。Postgres 容器进程启动到「能接受连接」之间有几百毫秒到几秒（要跑初始化、要恢复 WAL）。你的 server 容器如果在这期间连库，会失败退出——而 compose 默认认为「容器进程起来了」就等于「依赖就绪了」。

条件含义用在哪
service_started（默认）对方进程起来了就算数几乎不该用它。这是「连接被拒」类偶发故障的根源
service_healthy对方的 healthcheck 连续通过才算数server 等 postgres、web 等 server、migrate 等 postgres
service_completed_successfully对方成功退出（exit 0）才算数一次性任务。S8·D4 会讲它在迁移上的用法与取舍

service_healthy 要求对方定义了 healthcheck。healthcheck 就是「容器内周期性执行一条命令，退出码 0 = 健康」：

片段 · 两种 healthcheck# postgres：官方镜像自带 pg_isready，它比「TCP 端口通了」严格——
# 端口通但还在恢复期的时候，pg_isready 会明确回绝
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U homecube -d homecube"]
  interval: 5s        # 多久查一次
  timeout: 3s         # 单次超时
  retries: 12         # 连续失败几次才判定 unhealthy
  start_period: 10s   # 启动宽限期：这期间的失败不计入 retries

# server：容器内访问自己的 /healthz。alpine 自带 busybox wget，
# 非 2xx 时它退出码非 0，正好是我们要的判定
healthcheck:
  test: ["CMD", "wget", "-qO-", "http://localhost:8080/healthz"]
  interval: 5s
  timeout: 3s
  retries: 12
  start_period: 10s

start_period 不是可有可无的装饰。没有它，容器刚起那几秒的失败会累进 retries，一个明明正在正常启动的服务会被标成 unhealthy，然后依赖它的服务永远不起——你会以为编排写错了，其实是宽限期没给。

healthcheck 还有第二个用途，S8·D5 会兑现：它是「依赖就绪态」的载体。今天的 /healthz 还是 S1 那个静态返回 {"status":"ok"} 的版本，也就是说「进程活着」就等于「健康」。第 5 天会把它升级成「自己那两个 schema 真的连得上」才算健康——那时 healthcheck 才第一次有了实质含义。

4. profiles：让 migrate 成为「按需工具」而不是「常驻服务」

迁移是一次性动作，不该在 docker compose up 时自己冒出来跑一遍（尤其不该在你只想改一行前端样式时跑）。给它挂上 profiles: ["tools"] 之后：

  • docker compose up -d：不会起 migrate，ps 里也看不到它。
  • docker compose --profile tools run --rm migrate：显式点名，跑完自动删容器（--rm）。
  • docker compose --profile tools up -d：把它一起纳入编排。

run 与 up 的差别值得记一下：up 是「按编排把服务拉起来并保持」，run 是「起一个一次性的容器执行命令，执行完就结束」——一次性任务用 run，而且它同样会尊重 depends_on（会先把 postgres 拉起来并等到 healthy）。

5. 两段变量：POSTGRES_* 与 DB_*，同一个口令写两遍

这是本站最容易搞错、也最容易在半夜debug 两小时的一处。它们不是同一套东西，不能混用，也不能只写一套。

POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DBDB_USER / DB_PASS / DB_NAME / DB_HOST / DB_PORT / DB_SSLMODE
谁读它官方 postgres 镜像的初始化脚本你的 Go config（S3 起钉死的名字）
什么时候生效只在数据目录为空的第一次启动生效。之后改了它，库里的角色和口令不会跟着变每次容器启动都读
作用「建一个什么样的库」「怎么连上那个库」
能不能改别名不能，是镜像规定的不能。禁止 DB_PASSWORD / POSTGRES_DSN / SERVER_PORT 这类自创名——config 只认钉死的那几个

两套值必须一致，而「改了 POSTGRES_PASSWORD 却连不上」的经典原因是：数据卷已经初始化过了，镜像的初始化脚本这一次根本不会执行，库里的口令还是旧的那个。处置办法只有一个：docker compose down -v 删掉数据卷重来（会丢数据），或者进容器用 ALTER ROLE 手工改。开发期用前者，上线后必须用后者。

还有一处必须写死、不许交给变量插值的东西：DB_HOST。你本机 make run 时它是 localhost；容器里它必须是服务名 postgres（compose 的内置 DNS 才认识）。所以 compose 的 environment 段要显式覆盖它——environment 的优先级高于 env_file，正好用来做这种「同一个变量、两套取值」的覆盖。

6. 密钥不进 compose 文件：env_file 与 .env.example

docker-compose.yml 是要提交进 git 的。里面不许出现任何真密钥——JWT_SECRET 与 JWT_REFRESH_SECRET 一律通过 env_file: [.env] 从本机文件注入，而 .env 昨天已经进了 .gitignore 与 .dockerignore。

但别人 clone 你的仓库之后，得知道要填哪些变量。所以今天多写一个文件：.env.example——只有变量名与占位值、没有真密钥，它要提交。README 里的第一步就是 cp .env.example .env 然后改掉两个密钥。

.env 在这套体系里其实身兼两职：① compose 会自动读项目根目录的 .env 来插值 compose 文件里的 ${VAR}；② 通过 env_file: 被原样灌进容器当环境变量。本站口径：.env 里只写死值，不要指望在里面写 A=${B} 能被展开——插值只发生在 compose 文件自身。

7. restart 策略：教学期故意不加

restart: unless-stopped 能让崩溃的容器自动重启，上线是要加的。但教学期不加：一个启动就崩的 server 会被无限重启，ps 里看着像「一直在跑」，日志翻起来是一屏重复的报错，你要花更久才发现它从来没成功过。migrate 则显式写 restart: "no"——一次性任务失败了就该躺着让你看见，绝不能自己重试。

今日增量（在学习仓里落盘）

今天属增量类型 ⑥：工程化收口产物。四个文件：仓库根 docker-compose.yml（覆盖 S1 那个占位文件）、.env.example、Makefile 追加编排目标、.gitignore 补一条。收工时 make build / make test 仍必须绿。

步骤 1 · docker-compose.yml

完整 · docker-compose.yml（仓库根）name: homecube

services:

  # ==========================================================
  # 数据层。POSTGRES_* 是【官方镜像自己的初始化变量】，
  # 只在数据卷为空的第一次启动生效，作用 = 建库建角色设口令。
  # 它不是后端读的变量，别拿它去改后端行为。
  # ==========================================================
  postgres:
    image: postgres:16-alpine
    container_name: homecube-postgres
    environment:
      POSTGRES_USER:     ${DB_USER:-homecube}
      POSTGRES_PASSWORD: ${DB_PASS:-homecube123}
      POSTGRES_DB:       ${DB_NAME:-homecube}
    ports:
      - "127.0.0.1:5432:5432"      # 只绑回环：给本机的数据库客户端用，不给局域网
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER:-homecube} -d ${DB_NAME:-homecube}"]
      interval: 5s
      timeout: 3s
      retries: 12
      start_period: 10s

  # ==========================================================
  # 一次性工具：schema 迁移。挂了 profile，日常 up 不会起它。
  # 真正的两套 schema 迁移命令在 S8·D4 填，今天先验证接线。
  # ==========================================================
  migrate:
    image: migrate/migrate:v4.17.1
    container_name: homecube-migrate
    profiles: ["tools"]
    restart: "no"                   # 失败了就躺着，绝不自己重试
    depends_on:
      postgres:
        condition: service_healthy
    volumes:
      - ./server/migrations:/migrations:ro   # 只读挂载：迁移文件不打进镜像
    environment:
      # ---- 后端变量段（与 server 同一套名字）----
      DB_HOST: postgres
      DB_PORT: "5432"
      DB_USER: ${DB_USER:-homecube}
      DB_PASS: ${DB_PASS:-homecube123}
      DB_NAME: ${DB_NAME:-homecube}
      DB_SSLMODE: disable
    command: ["-version"]            # 占位：证明镜像能拉、卷能挂、能等到库健康

  # ==========================================================
  # 服务端。DB_* 是【你的 Go config 读的变量】，名字 S3 起钉死，
  # 禁止 DB_PASSWORD / POSTGRES_DSN / SERVER_PORT 这类自创别名。
  # 密钥只从 .env 注入，本文件里不许出现真值。
  # ==========================================================
  server:
    build:
      context: .                     # 上下文是仓库根，见 S8·D1
      dockerfile: server/Dockerfile
    image: homecube-server:dev
    container_name: homecube-server
    depends_on:
      postgres:
        condition: service_healthy
    env_file:
      - .env                         # JWT_SECRET / JWT_REFRESH_SECRET 从这里来
    environment:
      # environment 优先级高于 env_file，专门用来覆盖「同名不同值」的项
      PORT: "8080"
      GIN_MODE: release
      DB_HOST: postgres              # 覆盖 .env 里的 localhost：容器内用服务名
      DB_PORT: "5432"
      DB_USER: ${DB_USER:-homecube}
      DB_PASS: ${DB_PASS:-homecube123}
      DB_NAME: ${DB_NAME:-homecube}
      DB_SSLMODE: disable
      AUTO_MIGRATE: "false"           # 部署口径：迁移由 migrate 显式执行，理由见 S8·D4
      UPLOAD_DIR: /app/uploads
      CORS_ORIGIN: http://localhost:8080   # 不再是本机 dev server 的地址，理由见 S8·D5
    ports:
      - "127.0.0.1:8081:8080"        # 只绑回环：给你 curl /healthz 与 /metrics
    volumes:
      - uploads:/app/uploads         # 附件必须落卷，否则容器一重建就全没了
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/healthz"]
      interval: 5s
      timeout: 3s
      retries: 12
      start_period: 10s

  # ==========================================================
  # 正门。浏览器只认这一个端口。
  # ==========================================================
  web:
    build:
      context: ./web
    image: homecube-web:dev
    container_name: homecube-web
    depends_on:
      server:
        condition: service_healthy
    ports:
      - "8080:80"

volumes:
  pgdata:
  uploads:

步骤 3 · Makefile 追加编排目标

片段 · Makefile 追加（缩进是真 TAB）.PHONY: up down ps logs nuke

up:
	docker compose --profile tools run --rm migrate
	docker compose up -d --build

down:
	docker compose down

ps:
	docker compose ps

logs:
	docker compose logs -f server

# 危险：连数据卷一起删（库里的数据全没）。只在需要重置时用
nuke:
	docker compose down -v --rmi local

up 目标里两行是有顺序的，但 make 默认不会因为前一行失败就停下——它会继续执行下一行。今天 migrate 只是 -version 无所谓；S8·D4 换成真迁移命令时，必须把两行用 && 串成一条，让「迁移红了就不起服务」成为机器保证而不是靠你记性。这个坑那天会正式讲。

今日名词卡

术语一句话解释
compose 项目一份 docker-compose.yml 定义的一组服务，共享网络与命名空间；name: 决定前缀
服务 servicecompose 里的一个条目 = 「一类容器」的定义（镜像、卷、环境、端口）
命名卷 named volume由 Docker 管理的持久化存储，容器删了它还在。down -v 才会删它
绑定挂载 bind mount把宿主机的目录直接挂进容器（./server/migrations:/migrations:ro），改文件即时生效
healthcheck容器内周期执行一条命令，退出码 0 = healthy；是「就绪」的唯一可靠信号
start_period启动宽限期，期间的失败不计入 retries
depends_on 条件service_started（进程起了）/ service_healthy（体检过了）/ service_completed_successfully（成功退出）
profiles给服务分组，只有显式带上该 profile 的命令才会纳入它；migrate 用 tools
run vs uprun 起一次性容器执行完就结束；up 拉起并保持常驻服务
env_file把一个文件里的键值对原样灌进容器当环境变量；environment 段优先级更高，用来覆盖
变量插值compose 文件里的 ${VAR:-默认值} 由 shell 环境与项目根 .env 提供取值
pg_isready官方镜像自带的探测工具，比「端口通了」严格：恢复期它会明确回绝
