S3 的收官日。过去十二个工作日，数据从进程内存搬进了 Postgres：compose 起了库、双 schema 与两个专属账号（D1）、GORM 与 TranslateError（D2）、迁移工具与 down 纪律（D3/D4）、关联与 Preload（D5）、分类域换 DB（D6）、软删与事务（D7）、游标分页原语（D8）、*_cents BIGINT（D9）、scoped/visible 谓词收口（D10）、连接池与 DB_* 配置收口（D11）。今天不写新功能、不新增迁移——把这条链验收成一条能被复放、能被陌生人从 clone 跑起来、能被你徒手讲清的地基：两套 schema 各跑一遍 up→down→up、双专属账号各守各的、分类 6 条接口一行不改跑真 Postgres。收口四件事：全链重放、账号与跨码巡检、真库全剧本、判据自测。

1. 「收口」收的是地基，不是零件清单

资产清点标准是哪几天的产物
基础设施compose 起 16、双 schema、两个迁移专属账号、数据卷 + 健康检查D1
迁移链homeos 两条 / finance 两条，每条成对 up/down、两个 code 各自独立计数、可重放D3-D6、D9

2. 全链重放：D4 的判据此刻站在四条迁移上

D4 立的三步重放判据，当时只有一条 homeos_0001 撑着；今天它是整条链的验收：① up 到顶记基线 → ② down 到底 → ③ 再 up 逐项对回基线。两条链各自独立跑，谁也不碰谁的账本——这正是 search_path 钉死各自 schema 的意义：

链当前成员down 到底应看到再 up 到顶应看到
homeos0001_init_user、0002_init_family_member除 schema_migrations 外 0 表（user/family/member 全退）3 张业务表齐、外键与 CHECK 在位、version=2 / dirty=f
finance0001_init_category、0002_init_account除 schema_migrations 外 0 表（category/account 退、0001 的 6 行预置种子随表没）2 张业务表齐、version=2 / dirty=f、支出预置 6 行由种子重建

重放的是结构，不是数据。down 会把途中一切行洗掉（D4 那句判据今天再念一遍）。所以收口重放要在测试库或 down -v 重置的环境上做，别拿你有真实业务行的库试手。数据恢复靠备份，与回滚是两条生命线。

3. 双专属账号：纪律长在数据库权限上，不在口头约定里

D1 建了 homeos_app / finance_app，D3 让它们随 HOMEOS_MIGRATE_URL / FINANCE_MIGRATE_URL 上岗（各自 URL 里 search_path 钉自己的 schema）。今天验的不是「能不能跑」，是「越界了会不会被拒」：

  • 账号与 schema 对得上：homeos 链的迁移由 homeos_app 执行、finance 链由 finance_app 执行——表属主应当与账号同名（pg_tables.tableowner 逐行核对）。
  • 跨 schema 被物理拒绝：finance_app 去 CREATE TABLE homeos.probe / DROP TABLE homeos.homeos_user，数据库直接 permission denied；反向同理。这比任何 grep 都硬。
  • 迁移源码不许跨 code 引用：grep -rn "homeos\." server/migrations/finance/ 与反向各零命中——哪怕权限挡住了运行时，源码里出现别人的 schema 名也是设计越界。

应用运行账号（homecube，DB_USER）与迁移账号是三套身份里的另一套：迁移账号只有本 schema 的 DDL 权限，应用账号做 CRUD——两者都别混用 root 心态。顺带钉一句：连接串的变量口径全站唯一由 platform/config 从 DB_* 拼（D11 之后统一），别自造 DB_PASSWORD、SERVER_PORT 之类的别名。

4. 一行不改的真相：契约没变，语义多了预置段

D6 换存储那天立的口号「接口与 HTTP 契约一行不改」，今天要在真库上兑现到语义层——不只是路径/方法/DTO/信封没变，还有预置数据带来的读写不对称。分类 6 条接口今天的验收面：

场景期望守它的判据
GET /categories（family 1）200，list 里既有 6 行支出预置（餐饮/交通/购物 + 餐饮下早餐/午餐/晚餐）也有本家庭自定义行读带预置：family_id = ? OR family_id IS NULL
在预置一级「餐饮」下 POST 建自定义二级201，新行 family_id=当前家庭D10 的 visible 取父级；写只落本家庭
对自定义行 PUT 带旧 version409 + 1009乐观锁 + zeroRowCause 分因
对有活子级的自定义一级 PUT …/archive409 + 1010业务状态规则
对预置行 PUT / archive404 + 1001（与真不存在同形）写只认本家庭：scoped 把 NULL 挡在写范围外
跨家庭读别家自定义行 / NoRoute404 + 1001D10 越权读同形 + NoRoute（自 S2 沿用）

最后一格最关键：预置行读得到、动不得——这不是 S2 契约里的新错误码，是错误码表里早就有的 1001 复用（越权读一律 404+1001，不泄露存在性）。判据第 6 条说「错误码与 S2 完全一致」，指的就是这套语义在原码位上跑通，不新造码。收工时重启进程再 GET 一次，自定义行还在——地基第一次真「记住」了东西。

题合格线回看
为什么建表权只归迁移、不归 AutoMigrate说出 AutoMigrate 只加不减、无版本、无回滚、多环境各跑各的病灶；本站靠 migrations/ + schema_migrations 治它，AUTO_MIGRATE 恒关D2、D3、总览
