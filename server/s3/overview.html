S3 · Postgres 与迁移

这两周把「数据」从进程内存搬进 Postgres 16。S2 结束时，分类域 6 条接口跑在内存 map 上——进程一停，数据灰飞烟灭。S3 的终点是：表全部由 golang-migrate 建、分类域 repo 换成 GORM 实现而 HTTP 契约一行不改、每条查询都带 family_id、软删与游标分页的原语全部就位并 tested。这是后面所有阶段（鉴权、并发、财务面）的地基。

为什么建表权只归迁移，不归 AutoMigrate

GORM 的 AutoMigrate 很诱人：模型 tag 一改，表自动跟上。但它只加不减、类型变更保守、没有版本记录、没有回滚、多环境各跑各的——三个月后没人说得清生产表长什么样、为什么长这样。本站纪律：建表权只在 migrations/，每条迁移带 up/down、可重放、进 git 被 review；GORM 只负责 CRUD，不碰 DDL。S3·D2 会用一次 AutoMigrate 作对照实验，然后亲手把它关掉。

本阶段不做什么（明确划掉，免得手滑）

  • 不写鉴权：没有 JWT、没有登录、没有权限中间件（S4）。repo 的 familyID 先由 handler 的临时桩传入，S4 换成 token 解出的真值
  • 不新增任何接口：接口分母仍只有分类 6 条（/api/finance/categories 家族）。游标分页只做 repo 层原语与测试，不上路由——分类树是小集合，契约本就是全量返回
  • 不做报表、统计、导出、附件（S6）；不起 goroutine、不谈并发（S5）
  • 不写前端。web/ 是 agent 脚手架的产物，你的判据在 F2 周日卡上
