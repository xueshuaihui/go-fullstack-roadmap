down 怎么写才真能回滚：up→down→up 重放判据

写 up 是创造，写 down 是负责。大量项目的 down 文件是空壳——真到要回滚那天，发现退不回去，只能连夜手改生产库。今天只干一件事：把「down 必须真能回滚」从口号变成可执行的重放判据，并用昨天的 homeos_0001 完整验收一遍。

今日目标

↑ 这四条是「学习目标」。页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

知识讲义

1. down 三规则

规则内容反例
① 逆依赖顺序清理up 是「先建被引用的，再建引用的」；down 严格反着来：先 DROP 引用方（或先删外键约束），再 DROP 被引用方up 建了 A、B（B 引用 A），down 先 DROP A → 被依赖挡住或留下悬空引用
② DROP 与 TRUNCATE 分工结构回滚用 DROP TABLE（连结构带数据一起退回去）；TRUNCATE 只清数据、不动结构，那是种子脚本的活，不是 down 的活down 里写 TRUNCATE：结构留下了，账本却退了版本，下次 up 撞「已存在」
③ 不许假 down空文件、只有注释、SELECT 1;——工具不报错，但回滚是假的。成对纪律的意义就在真回滚「这条 up 没法逆，down 留空吧」→ 那这条 up 本身就该重新设计

2. 重放判据：什么叫「down 真能回滚」

本站的验收口径，三步一条链：

  1. up 到顶：全部迁移执行完，记下 schema 里的对象清单（表数、索引数）与账本版本；
  2. down 到底：整条链退干净——账本回到无版本状态，业务表一张不剩（schema_migrations 与 schema 本身留下，它们是容器不是内容）；
  3. 再 up 到顶：对象清单与第 1 步逐项一致，账本版本回到最新，全程无 dirty。

重放的是结构，不是数据。down 会销毁途中的一切行——迁移链承诺的是「schema 可以退回去再建回来」，从不承诺「数据能恢复」。数据的恢复靠备份，这是两条完全不同的生命线。混为一谈的人，会在第一次真回滚时丢掉全部家当。

3. 为什么 down 值得认真写：它是设计检验器

写不出 down，几乎总是 up 设计有问题的信号：依赖缠成环、一条迁移干了三件事、往不该动的表里塞了副作用。down 逼你把每条迁移切成原子的一步——这一步恰好也是「出事了敢不敢回滚」的底气来源。教学期你还会天天用到它：down -v 重置环境比手工 DROP 干净得多。

4. 已发布的迁移不许修改

纪律：迁移文件一旦提交（未来的队友或另一台机器可能已执行过），内容就冻结了。发现 0002 写错列名？不是改 0002，而是发 0003 去修正。原因很朴素：账本只记版本号不记内容哈希，改已执行过的文件，会让「执行过旧版的环境」和「执行过新版的环境」结构漂移——又回到 AutoMigrate 的病。教学期你一个人的仓库，重置成本低（down -v 重放），可以放宽；但从 S4 多人视角演练起，这条纪律当真。

步骤 1 · 给 down.sql 补上「逆序与成对」的书面约定

昨天的 homeos_0001_init_user.down.sql 只有一张表，逆序还看不出来；今天把头注写明约定，从 homeos_0002（明天，两张表 + 外键）起它就是强制的：

完整 · server/migrations/homeos/homeos_0001_init_user.down.sql（覆盖）-- down 三规则：① 与 up 严格逆序（本条只有一张表，索引随表走）
--              ② 结构回滚用 DROP，不用 TRUNCATE
--              ③ 不许假 down：本文件必须能把 up 的效果退干净
-- 提醒：down 销毁途中数据。重放的是结构，数据恢复靠备份。
DROP TABLE IF EXISTS homeos.homeos_user;

步骤 2 · 把重放判据跑成验收命令

可跑 · 验收命令（全程留意有无 dirty 与报错）cd <你的学习仓根目录>
docker compose up -d postgres

# ① up 到顶，记录基线
make migrate-homeos-up
docker compose exec postgres psql -U homecube -d homecube -c \
  "SELECT count(*) AS tables FROM pg_tables WHERE schemaname = 'homeos';"
docker compose exec postgres psql -U homecube -d homecube -c \
  "SELECT count(*) AS indexes FROM pg_indexes WHERE schemaname = 'homeos';"
docker compose exec postgres psql -U homecube -d homecube -c 'SELECT * FROM homeos.schema_migrations;'

# 插一行数据，亲眼看它随 down 消失（重放的是结构，不是数据）
docker compose exec postgres psql -U homecube -d homecube -c \
  "INSERT INTO homeos.homeos_user (phone, nickname) VALUES ('13800000001', '重放见证人');"

# ② down 到底：退干净
make migrate-homeos-down
docker compose exec postgres psql -U homecube -d homecube -c '\dt homeos.*'
                                           # 只剩 schema_migrations，homeos_user 没了

# ③ 再 up 到顶：结构与 ① 的基线逐项一致
make migrate-homeos-up
docker compose exec postgres psql -U homecube -d homecube -c \
  "SELECT count(*) AS tables FROM pg_tables WHERE schemaname = 'homeos';"
docker compose exec postgres psql -U homecube -d homecube -c \
  "SELECT count(*) AS indexes FROM pg_indexes WHERE schemaname = 'homeos';"
docker compose exec postgres psql -U homecube -d homecube -c \
  "SELECT count(*) AS rows FROM homeos.homeos_user;"
                                           # rows = 0：结构回来了，数据没回来——正是判据要证明的事

git add server/migrations
git status
git commit -m "docs(s3d4): down 三规则落进头注，up→down→up 重放判据验收通过"

常见坑（新手 100% 会踩）

坑现象正确姿势
down 里 TRUNCATE 代替 DROP版本退了、结构还在；下次 up 报 relation already existsdown 退结构用 DROP；清数据是种子脚本/开发重置的事
逆序写反多表迁移 down 时报 cannot drop ... because other objects depend on it先删引用方再删被引用方；拿不准就画一下 up 的依赖箭头，倒着走
down 忘删 up 顺手建的对象重放后索引数比基线多，判据第 ③ 步对不上up 建了什么，down 就要能退什么（随表 DROP 的索引除外）；用基线计数验收
修改已提交的迁移文件两台机器结构漂移，账本却都显示同一版本只发新号修正；教学期要改先 down -v 重置再改，并重新全链重放
以为 down 能保住数据回滚后数据没了，才想起没备份重放的是结构；任何真实环境回滚前，先备份
IF EXISTS 省掉后 down 变脆半程失败再 down，报「对象不存在」把清理也挡住down 里的 DROP 一律带 IF EXISTS，让清理尽量走完全程

术语一句话解释
