docker-compose 起 Postgres 16：双 schema 与两个专属账号

S3 第一天不写一行 Go。今天把数据库这台「外部依赖」立起来：docker compose up -d 一条命令起一个 Postgres 16，里面有两个 schema（homeos / finance）和两个只有本 schema 权限的迁移专属账号。这套地基定下来，后面 11 天的迁移、GORM、repo 纪律才有地方落。

知识讲义

1. 数据库 → schema → 表：三层命名空间

Postgres 的层级是 database → schema → table。schema 是 database 内部的命名空间：同一个库里，homeos.homeos_user 和 finance.finance_category 互不打扰。本站的规矩（S1·D1 就埋过）：两个业务模块两个 schema，不跨 schema join——日后要拆服务，schema 边界就是天然的切割线。

层本站取值说明
databasehomecube一个库装下全部，模块化单体
schemahomeos / finance业务模块各占一个；表名前缀与 schema 同名（七类命名同源）
tablehomeos_user / finance_category …表名 {code}_{snake}，S3·D3 起由迁移建

2. 为什么用 compose，不用本机裸装

  • 版本钉死：镜像写 postgres:16，你机器上和队友机器上是同一个大版本；本机裸装最容易「我这能跑你那不能跑」。
  • 初始化即代码：建 schema、建账号的 SQL 放 docker-entrypoint-initdb.d，数据库第一次初始化时自动执行——环境是声明出来的，不是手点出来的。
  • 随时推倒重来：docker compose down -v 删掉数据卷，再 up 就是一个崭新的库。S3 你会反复用到这个「重置键」。

init 脚本只在数据卷第一次初始化时执行。改了 01_init.sql 再 up，什么都不会发生——因为卷已经存在。想让改动生效：docker compose down -v（删卷）再 up。这是今天最常见的一坑。

3. 两段变量、三个账号：谁连库、用什么身份

compose 里会出现两段环境变量，注释必须写清，不许混：

段变量谁在用
镜像变量（Postgres 官方入口脚本认的）POSTGRES_DB / POSTGRES_USER / POSTGRES_PASSWORD容器初始化时建库建管理员账号
后端变量（本站口径，S3·D11 的 config 认的）DB_HOST / DB_PORT / DB_USER / DB_PASS / DB_NAME / DB_SSLMODEGo 进程拼 DSN 连库；禁止自造 DB_PASSWORD、SERVER_PORT 之流的别名

库里有三个账号，职责不同：

  • homecube：镜像建的管理员，后端应用连库用它（DB_USER=homecube）。
  • homeos_app：homeos schema 专属的迁移账号，只有 homeos 的权限。
  • finance_app：finance schema 专属的迁移账号，只有 finance 的权限。

为什么要两个「弱势」账号跑迁移？因为纪律要长在数据库上：finance 的迁移脚本里哪怕手滑写了一句 DROP TABLE homeos.homeos_user，执行时直接 permission denied——「不跨 code 引用」从口头约定变成物理约束。S3·D3 接 golang-migrate 时它们正式上岗。

4. 数据卷：容器是牲口，卷是家产

容器删了重建，里面的文件全没。数据要活在命名卷（named volume）里：compose 顶层声明 pgdata，挂到容器的 /var/lib/postgresql/data。docker compose down 不删卷，down -v 才删。加一个 healthcheck（pg_isready），后面 migrate 服务用 depends_on: condition: service_healthy 等它就绪，不用睡等。

步骤 1 · init 脚本：双 schema 与两个专属账号

结构<repo>/
├── scripts/
│   └── postgres-init/
│       └── 01_init.sql        首次初始化时自动执行（按文件名序）
├── server/                    （S1 起已有）
├── Makefile
├── .env                       本机真实口令，已被 .gitignore 拦住
├── .env.example               进仓的模板，值与本站口径一致
└── docker-compose.yml
完整 · scripts/postgres-init/01_init.sql-- 双 schema：命名空间级隔离。「不跨 schema join」从第一天就没有顺手写出来的机会。
CREATE SCHEMA IF NOT EXISTS homeos;
CREATE SCHEMA IF NOT EXISTS finance;

-- 两个迁移专属账号：各自只有本 schema 的权限。
-- finance 的迁移想动 homeos 的表？数据库直接拒绝——纪律长在权限上。
CREATE ROLE homeos_app LOGIN PASSWORD 'homeos_app123';
CREATE ROLE finance_app LOGIN PASSWORD 'finance_app123';

GRANT USAGE, CREATE ON SCHEMA homeos TO homeos_app;
GRANT USAGE, CREATE ON SCHEMA finance TO finance_app;

步骤 2 · docker-compose.yml

完整 · docker-compose.yml# 本站 compose 口径：name 固定 homecube；服务名 postgres / server / web / migrate。
# S3 先立 postgres（migrate 在 S3·D3 加入）；server / web 到 S8 部署时补全。
name: homecube

services:
  postgres:
    image: postgres:16            # 版本钉死大版本，不用 latest
    container_name: homecube-postgres
    environment:
      # —— 第一段：Postgres 官方镜像变量（只在初始化数据卷时用）——
      POSTGRES_DB: homecube
      POSTGRES_USER: homecube
      POSTGRES_PASSWORD: homecube123
    ports:
      - "5432:5432"               # 本机直连调试用；容器之间走服务名，不走这个口
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./scripts/postgres-init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U homecube -d homecube"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:

常见坑（新手 100% 会踩）

坑现象正确姿势
改了 init 脚本不生效脚本改完 up，schema/账号还是旧的init 只在卷首次初始化时跑。docker compose down -v 删卷再 up
镜像不钉版本写 postgres:latest，某天拉到 17，行为悄悄变了钉 postgres:16。大版本升级是刻意决策，不是惊喜
两段变量混写把 POSTGRES_PASSWORD 塞进后端段，或自造 DB_PASSWORD镜像变量归镜像、DB_* 归后端；别名一个都不许有
psql 连不上要口令psql -U homeos_app 卡在密码提示容器内非当前用户要 -e PGPASSWORD=... 传口令（验收命令里已给）
5432 被占bind: address already is allocated本机装过 Postgres 或旧容器没停：lsof -i :5432 找到进程处理掉
把 .env 提交了口令进了 git 历史，删掉也还在只提交 .env.example；commit 前 git status 过目（S1·D1 的老规矩）
用 root 心态到处连库拿 homecube 管理员账号跑一切，权限设计形同虚设迁移用专属账号（S3·D3 接入）；应用账号与迁移账号分开，是今天账号设计的本意

今日名词卡

术语一句话解释
database / schema / tablePostgres 三层命名空间；本站一个库 homecube，两个 schema homeos/finance
ROLE / GRANTPostgres 的账号与授权；USAGE, CREATE ON SCHEMA 决定谁能进、谁能建表
命名卷（named volume）由 Docker 管理的数据卷；容器可弃，卷是家产。down -v 才会删
docker-entrypoint-initdb.d官方镜像约定：该目录下的 .sql/.sh 在数据卷首次初始化时按文件名序执行
POSTGRES_* 镜像变量官方入口脚本认的初始化变量，只在建卷那一刻用
DB_* 后端变量本站 Go 进程的环境变量口径，S3·D11 由 config 统一读取拼 DSN
DSN连接串：postgres://用户:口令@主机:端口/库?sslmode=...。今天先认识，D2 用它连库
healthcheck / pg_isready容器级健康探测；配合 depends_on: service_healthy 让依赖方等库就绪
psql 元命令\dn 列 schema、\dt 列表、\d 表名 看列——反斜杠开头，psql 自己的命令不是 SQL
sslmode=disable本机回环连接不启用 TLS；生产口径 S8 部署时再谈

卡壳时查什么

正文自足，只有两种情况出去查：

  • compose 文件字段拿不准：Compose file reference（可选，查 healthcheck/profiles 语法用）。
  • psql 元命令忘了：容器里 psql -U homecube -d homecube -c '\?' 直接列出全部。
