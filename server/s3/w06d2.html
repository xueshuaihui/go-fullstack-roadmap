游标分页：(排序键,id) 不透明游标

S3 判据里有一条「能解释游标 vs offset」，今天把它挣到手。载体还是分类 repo：给它加一个 ListPage，用 (sort, id) 组成的 base64 不透明游标翻页，全站从此禁 offset。HTTP 契约今天不动——分类 6 条接口的集合很小，List 照旧全量返回；ListPage 是 repo 层原语，S6 流水列表（一个家庭几千上万行）上线时直接挂 HTTP。今天先把原理、代码、测试三样都落袋。

知识讲义

1. offset 的三宗罪

LIMIT 10 OFFSET 2000 看着人畜无害，实际是三笔债：

罪状发生了什么
① 越翻越慢OFFSET 不是「跳过」，是数着走过去：数据库要先取出并丢弃前 2000 行，再给你 10 行。页码越深，白干的活越多
② 重读漏读（漂移）你停在第 2 页时，别人在头部插入/删除了一行——第 3 页的内容整体平移一格，于是有一行你看了两遍，另一行你永远看不到
③ 深翻页灾难移动端无限滚动一路翻到底，OFFSET 一路涨到几万，每页都是一次全量扫描前缀；列表页把数据库拖垮是最经典的生产事故之一

offset 的本质问题：它用「行号」定位，而行号在活的表里随时会变。游标分页换一个定位方式——用「上一页最后一行本身」定位。

2. 游标（keyset）分页：记住读到哪，从那里往后拿

客户端把上一页最后一行的位置交回来，服务端翻译成一条 where：

片段 · 第 1 页 vs 第 N 页，只差一个 keyset 条件-- 第 1 页（没有游标）
SELECT * FROM finance.finance_category
WHERE (family_id = 921 OR family_id IS NULL)
ORDER BY sort ASC, id ASC
LIMIT 11;                      -- 要 10 行，多拿 1 行探 has_more

-- 第 N 页（游标 = 上页末行的 (sort, id)，比如 (3, 107)）
SELECT * FROM finance.finance_category
WHERE (family_id = 921 OR family_id IS NULL)
  AND (sort, id) > (3, 107)   -- 行值比较：先比 sort，再比 id
ORDER BY sort ASC, id ASC
LIMIT 11;

(sort, id) > (?, ?) 是 Postgres 的行值比较，语义等同 sort > ? OR (sort = ? AND id > ?)，但写法短、且能直接吃 (sort, id) 复合索引——定位是索引上的一次跳跃，不是数行，第 1 页和第 1000 页一样快，罪状①③当场消失。罪状②也免疫：头部插入的新行位置在游标之前，不会把后面的内容挤平移——你顶多「这一轮看不到新行」，绝不会重读或漏读已有行。

3. 游标里为什么是 (sort, id) 两个值，还要 base64

为什么带 id：排序键 sort 不唯一（一堆分类可以同 sort）。只用 sort 做 >，同值的行会被整批跳过或整批重放；带上唯一列 id 之后，(sort, id) 在表内全序且唯一——任何两行都能分出先后，「从某行之后」才有确定含义。这个 id 叫决胜键（tie-breaker），游标分页的每条 ORDER BY 都必须以唯一列收尾。

为什么 base64：游标对客户端必须是不透明的——一个原样交回的字符串，不承诺内部结构。明文传 sort=3&id=107 有两个坏处：客户端会忍不住依赖字段自己拼（契约被悄悄放大）；篡改后的怪值会渗进 where。本站做法：{"s":3,"i":107} JSON 序列化后 base64.RawURLEncoding 编码（URL 安全字母表、无 = 填充），解码失败或字段不合法一律 ErrBadCursor → 上层 1004。顺带说明：就算有人解码后改成别家的 (sort,id) 也无害——family_id 的 where 照样把它圈在本家庭内，游标只决定「从哪继续」，不决定「能看谁」。

4. Limit(n+1) 探针与响应信封

「还有没有下一页」不值得为它单独跑一次 COUNT——多要一行就够了：LIMIT n+1，真拿回 n+1 行说明后面还有（has_more=true，把多的那行丢掉）；只拿回 ≤n 行说明到底了。游标分页的响应信封固定三件套：

字段含义
list本页数据（≤ limit 行）
next_cursor下一页的游标（由截断后的末行生成）；没有下一页时为空
has_more是否还有下一页；前端无限滚动只看它

信封里没有 total，也没有页码。「共 137 页，跳到第 8 页」是 offset 世界观的产物：算 total 要全表 COUNT（大表上很慢且随即过期），跳页在游标世界观里根本不存在——只能顺着读。产品上要「大概多少条」，用近似统计或缓存另算，别把 COUNT 塞进列表接口。

5. 在本站的定位

分类集合小（一个家庭几十条封顶），B4 的 GET /api/finance/categories 维持 D6 的全量 {"list":[...]} 契约不变，今天不加任何 HTTP 分页参数。ListPage 落在 repo 层，是替 S6 的流水列表预制的原语——那时信封三件套才第一次出现在 HTTP 响应里。一个 repo 同时留 List（全量）与 ListPage（分页）不矛盾：按调用方的真实数据量选，不预先泛化。

步骤 1 · 游标的编解码（全站唯一，之后所有分页都 import 它）

完整 · server/internal/platform/paging/paging.gopackage paging

import (
    "encoding/base64"
    "encoding/json"
    "errors"
    "fmt"
)

// ErrBadCursor 游标不合法（不是本站发出去的、或被改坏了）。
// 上层把它映射成 response.ErrInvalidParam → 400 + 1004，绝不当 5000 处理。
var ErrBadCursor = errors.New("bad cursor")

const (
    DefaultLimit = 20  // 调用方不传 limit 时的兜底
    MaxLimit     = 100 // 上限：防止 ?limit=999999 变成变相全量拖库
)

// Cursor 记录「上一页最后一行」在排序上的位置。
// JSON 字段刻意取短名：游标会进 URL，每个字节都算钱。
type Cursor struct {
    Sort int   `json:"s"`
    ID   int64 `json:"i"`
}

// Encode 序列化 + base64（RawURLEncoding：URL 安全字母表、无 = 填充）。
func Encode(c Cursor) string {
    b, _ := json.Marshal(c) // 两个数值字段，Marshal 不会失败
    return base64.RawURLEncoding.EncodeToString(b)
}

// Decode 是 Encode 的逆运算；任何一步不对劲都归为 ErrBadCursor。
func Decode(s string) (Cursor, error) {
    var c Cursor
    b, err := base64.RawURLEncoding.DecodeString(s)
    if err != nil {
        return c, fmt.Errorf("%w: base64: %v", ErrBadCursor, err)
    }
    if err := json.Unmarshal(b, &c); err != nil {
        return c, fmt.Errorf("%w: json: %v", ErrBadCursor, err)
    }
    return c, nil
}

步骤 2 · repo 的 ListPage：keyset 条件 + Limit(n+1) 探针

完整 · server/internal/finance/repository/category_paging.gopackage repository

import (
    "context"
    "errors"
    "fmt"

    "homecube/internal/finance/model"
    "homecube/internal/platform/paging"
    "homecube/pkg/response"
)

// Page 游标分页的 repo 层信封。S6 挂 HTTP 时，handler 把它翻译成
// {"list":..., "next_cursor":..., "has_more":...} 的 JSON 响应。
type Page struct {
    List    []model.Category
    Next    string // 空 = 没有下一页
    HasMore bool
}

// ListPage 游标分页读分类：排序 (sort ASC, id ASC)，游标 = 上页末行的 (sort, id)。
// cursor 为空表示读第一页。坏游标 → response.ErrInvalidParam（上层 400+1004）。
func (r *GormCategoryRepo) ListPage(ctx context.Context, familyID int64, cursor string, limit int) (Page, error) {
    if limit <= 0 {
        limit = paging.DefaultLimit
    }
    if limit > paging.MaxLimit {
        limit = paging.MaxLimit
    }

    q := r.db.WithContext(ctx).Model(&model.Category{}).
        Where("(family_id = ? OR family_id IS NULL)", familyID) // 与 List 同一可见范围：本家庭 + 预置

    if cursor != "" {
        c, err := paging.Decode(cursor)
        if err != nil {
            if errors.Is(err, paging.ErrBadCursor) {
                return Page{}, fmt.Errorf("list page: %w", response.ErrInvalidParam)
            }
            return Page{}, fmt.Errorf("list page: %w", err)
        }
        q = q.Where("(sort, id) > (?, ?)", c.Sort, c.ID) // keyset：从游标位置之后接着读
    }

    var rows []model.Category
    if err := q.Order("sort ASC, id ASC").Limit(limit + 1). // 多拿 1 行当探针
        Find(&rows).Error; err != nil {
        return Page{}, fmt.Errorf("list page: %w", err)
    }

    p := Page{List: rows}
    if len(rows) > limit { // 探针命中：还有下一页
        p.HasMore = true
        p.List = rows[:limit] // 探针行丢掉，不泄漏给调用方
        last := p.List[len(p.List)-1]
        p.Next = paging.Encode(paging.Cursor{Sort: last.Sort, ID: last.ID}) // 由截断后的末行生成
    }
    return p, nil
}

两个 GORM 细节：① 每个 Where 会被 GORM 用 AND 串接，但不要赌它替你加括号——含 OR 的条件自己在字符串里带上括号，keyset 条件同理，这是肌肉记忆级的好习惯；② 模型带 gorm.DeletedAt，默认作用域自动追加 deleted_at IS NULL，软删的行不会混进任何一页（昨天的软删三件套在这里白捡一个正确性）。

步骤 3 · 翻页读穿测试：25 行种子，不重不漏

完整 · server/internal/finance/repository/category_paging_test.gopackage repository

import (
    "context"
    "errors"
    "fmt"
    "testing"

    "homecube/internal/finance/model"
    "homecube/pkg/response"
)

func TestListPageWalkThrough(t *testing.T) {
    gdb := openTestDB(t) // S3·D6 的 skip 助手，同包直接用
    repo := NewGormCategoryRepo(gdb)
    ctx := context.Background()
    const fam = int64(921)
    t.Cleanup(func() {
        gdb.Unscoped().Where("family_id = ?", fam).Delete(&model.Category{})
    })

    // 种 25 行，sort 刻意只取 0..4 循环——大量并列，逼 (sort,id) 的 id 出来决胜
    seeded := make(map[int64]bool, 25)
    for i := 0; i < 25; i++ {
        cat, err := repo.Create(ctx, fam, model.CategoryInput{
            Name: fmt.Sprintf("分页小白鼠%02d", i),
            Kind: "expense",
            Sort: i % 5,
        })
        if err != nil {
            t.Fatalf("seed %d: %v", i, err)
        }
        seeded[cat.ID] = true
    }

    // 顺着游标一路翻到底，收集所有见过的 id
    seen := make(map[int64]int) // id → 出现次数，抓重复
    cursor := ""
    pages := 0
    for {
        p, err := repo.ListPage(ctx, fam, cursor, 10)
        if err != nil {
            t.Fatalf("page %d: %v", pages+1, err)
        }
        if len(p.List) > 10 {
            t.Fatalf("第 %d 页给了 %d 行, 超过 limit", pages+1, len(p.List))
        }
        for _, c := range p.List {
            seen[c.ID]++
        }
        pages++
        if !p.HasMore {
            if p.Next != "" {
                t.Fatalf("最后一页 next 必须为空, got %q", p.Next)
            }
            break
        }
        cursor = p.Next
        if pages > 10 {
            t.Fatal("翻了 10 页还没到底——游标没在推进，死循环保护")
        }
    }

    // ① 不重：每个 id 恰好出现一次
    for id, n := range seen {
        if n != 1 {
            t.Fatalf("id %d 出现了 %d 次——翻页重读", id, n)
        }
    }
    // ② 不漏：25 行种子一个不少（预置行也在流里，总数只会 ≥ 25+预置数，不硬编码）
    for id := range seeded {
        if seen[id] == 0 {
            t.Fatalf("种子 id %d 从没出现——翻页漏读", id)
        }
    }
    // ③ 至少翻了 3 页（25 行 + 6 条预置，limit 10）
    if pages < 3 {
        t.Fatalf("只翻了 %d 页, want ≥ 3", pages)
    }

    // ④ 坏游标 → ErrInvalidParam（上层 400+1004），不是 panic 也不是 5000
    for _, bad := range []string{"@@不是base64@@", "e30" /* {} 解得出但字段全零值也算合法，见下 */, "eyJzIjoiYSJ9" /* s 是字符串 */} {
        if bad == "e30" {
            continue // 全零游标是合法位置（从头读），不该报错——写下来防止自己想当然
        }
        if _, err := repo.ListPage(ctx, fam, bad, 10); !errors.Is(err, response.ErrInvalidParam) {
            t.Fatalf("坏游标 %q 应 ErrInvalidParam, got %v", bad, err)
        }
    }
}

测试里那个 "e30"（{} 的 base64）特意留了一手：解码成功、字段全零值，它是合法游标——语义等于「从 (0,0) 之后读」，也就是从头读。不透明 ≠ 不可预测：合法的零值位置不该报错，只有解不出来的才报 1004。把这条边界写进测试，好过在代码评审里吵。

常见坑（新手 100% 会踩）

坑现象正确姿势
游标里只放排序键，不放 idsort 并列的行翻页时整批重复或整批消失ORDER BY 必须以唯一列收尾，游标带上它——(sort, id) 才是全序
忘写 Limit(n+1) 探针恰好整页时 has_more 靠猜：多翻一页空的，或提前断流多拿一行：拿满 n+1 才有下一页，探针行截掉不外泄
next 游标用未截断的末行（探针行）生成下一页开头凭空跳过一行——漏读先截断到 n 行，再用截断后的末行生成 next
base64 用 StdEncoding游标里的 + 被 URL 当空格、= 要转义，解回来是坏值RawURLEncoding：URL 安全字母表 + 无填充
坏游标当内部错误处理用户改了个 URL 参数，你返回 5000 还打了告警解码失败 → ErrInvalidParam → 400 + 1004，客户端的错就明说
含 OR 的条件不加括号，与 keyset 条件混拼AND/OR 优先级把 where 拼歪，预置行或软删行漏进结果每个 Where 的字符串自带括号，不赌框架行为
给游标分页硬加 total / 页码每页多一次全表 COUNT，大表上列表接口慢成狗信封就三件套 list/next_cursor/has_more；要总数另做缓存统计

今日名词卡

术语一句话解释
offset 分页用行号定位（LIMIT n OFFSET m）；越翻越慢、并发下重读漏读，本站禁用
游标分页（keyset pagination）用「上页末行的位置」定位：WHERE (排序键…) > 游标，索引跳跃，页页等速
不透明游标（opaque cursor）对客户端只是一个原样交回的字符串，不承诺内部结构；本站 = base64 的 (sort, id)
行值比较(a, b) > (x, y)：先比 a 再比 b 的字典序；Postgres 原生支持且吃复合索引
决胜键（tie-breaker）ORDER BY 末尾的唯一列（本站是 id）；没有它，「从某行之后」无确定含义
Limit(n+1) 探针多要一行探测 has_more，替代单独的 COUNT 查询
信封三件套{list, next_cursor, has_more}；没有 total、没有页码
RawURLEncodingbase64 的 URL 安全无填充变体：-_ 字母表、无 =，可直接进查询串
ErrBadCursor → 1004游标解不出来是客户端输入错误：400 + 1004，不是 5000
漂移（drift）offset 分页在并发增删下内容平移导致的重读/漏读；游标分页天然免疫

卡壳时查什么

正文自足，只有两种情况出去查：

  • 行值比较的精确语义：PostgreSQL 16 · Row and Array Comparisons（可选，看 ROW 比较那一小节即可）。
  • 复合索引怎么建才吃得到 keyset：今天不建——分类表数据量小，全表扫也快；S6 流水表的 (family_id, occurred_at DESC, id DESC) 索引会正式兑现这件事（本周六收口时你会先见到它）。

站内回看：repo 的 List 全量版在 S3·D6；ErrInvalidParam/1004 与 errors.Is 的哨兵错误机制在 S1·D4；软删默认作用域为什么让分页「白捡正确性」在 S3·D7。
