事务与软删：deleted_at 语义、Unscoped 与恢复入口

周六的 Reorder 里你照抄了一个 Transaction，今天把账算清：事务到底保证了什么、回调返回 error 时发生了什么。另一半主题是软删——通用列里的 deleted_at/deleted_by 从 D3 建表起就一直躺着，今天让它们上岗：NULL = 活着、成对写入、必须有恢复入口。练手载体仍是分类 repo；HTTP 契约不动（分类 6 条里没有 DELETE，这三个方法是给 S6 流水回收站预备的原语）。

知识讲义

1. 事务：要么全成，要么当没发生

事务把多条写语句捆成一个原子单位：全部成功才生效，任何一步失败就整体回滚——数据库回到这捆操作开始前的样子。典型场景就是周六的 Reorder：改 10 行 sort，第 7 行不属于本家庭，前 6 行的改动必须退回去，否则排序变成半新半旧的鬼样子。

GORM 的写法是回调式：把操作写进 Transaction(func(tx *gorm.DB) error {...})，回调返回 nil 就 COMMIT，返回 error 就 ROLLBACK。纪律两条：回调内部一律用参数 tx（不是外层的 r.db——用了外层，那条语句就在事务外面裸奔）；回调里不要吞 error，该往上返回就返回。

片段 · 前置：周六 Reorder 的形状，今天看懂每一行err := r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    if err := tx.Model(...).Updates(...).Error; err != nil {
        return err          // ← 返回 error：整个事务 ROLLBACK
    }
    return nil              // ← 返回 nil：COMMIT
})                            // err 即回调的返回值（回滚时通常再包一层上下文）

2. 软删：不删行，只给行盖「已删」戳

硬删（DELETE FROM）把行物理抹掉；软删只写 deleted_at = now()，行还在库里。为什么记账类应用必须软删：历史流水的作者标记、统计口径、误删可救，全都要求「删掉的东西还能找到」。GORM 对软删有一整套自动行为，触发条件就一个——模型上有 gorm.DeletedAt 类型的字段：

你写的GORM 实际干的
Find / First / Count自动追加 WHERE deleted_at IS NULL（默认作用域：尸体自动隐藏）
Delete(&row)不发 DELETE，发 UPDATE ... SET deleted_at = now()
Unscoped() + 查询关掉默认作用域：软删的行也返回
Unscoped() + Delete真·物理删除（本站只在测试清场用）

3. 为什么本站不用 GORM 的 Delete()：deleted_by 会被丢下

GORM 的 Delete() 只写 deleted_at，不知道「谁删的」——而本站的通用列纪律是软删必须成对：deleted_at 与 deleted_by 同时写。所以软删走手写 Updates（两列一起 SET，顺带 version+1），并包在事务里。恢复同理：deleted_at 与 deleted_by 一起清回 NULL——只清时间不清人，留下一具「不知谁删的复活尸」，审计链一样是断的。

4. 恢复入口为什么必须有

真实项目里反复出现的事故形态：软删做了，恢复没做。删除接口一上，误删的行就进了黑洞——库里有、界面无、谁也捞不回来，等于用软删的成本买了硬删的后果。本站的规矩从原语层就钉死：有 SoftDelete 就必须有 Restore 与 ListDeleted（回收站的数据源），三件套一起落盘、一起测试。S6 做流水时，DELETE /api/finance/transactions/{id}、?deleted=true 回收站列表、POST .../restore 三条接口就是今天三件套的 HTTP 化——恢复后预算与统计按当前时间窗重算，那时再讲。

5. 软删与两个近邻的边界

概念字段语义
停用（archived）archived BOOLEAN业务状态：选择器不再出现，但历史流水仍可筛可统计；行是「活的」
软删deleted_at/deleted_by行级下架：默认作用域内一切查询不可见，进回收站，可恢复
物理删—本站业务代码禁用；只出现在测试清场（Unscoped().Delete）

再看一眼 D3 埋的伏笔：uq_homeos_user_phone 是部分唯一索引（WHERE deleted_at IS NULL)——唯一约束只管活行，软删行让出手机号，注销过的号码才能重新注册。软删语义与约束设计的交点，就长这样。

步骤 1 · 软删三件套

完整 · server/internal/finance/repository/category_softdelete.gopackage repository

import (
    "context"
    "fmt"

    "gorm.io/gorm"

    "homecube/internal/finance/model"
    "homecube/pkg/response"
)

// SoftDelete 软删本家庭的一行：deleted_at 与 deleted_by 在同一个事务里成对写入。
// 不用 GORM 的 Delete()——它只写 deleted_at，deleted_by 会被丢下，审计断头。
// 模型带 gorm.DeletedAt，Updates 自动追加 deleted_at IS NULL：已删的行不会被「再删一次」。
func (r *GormCategoryRepo) SoftDelete(ctx context.Context, familyID, id, operatorID int64) error {
    return r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        res := tx.Model(&model.Category{}).
            Where("id = ? AND family_id = ?", id, familyID). // 写路径只认本家庭，预置行碰不到
            Updates(map[string]any{
                "deleted_at": gorm.Expr("now()"),
                "deleted_by": operatorID,
                "updated_at": gorm.Expr("now()"),
                "version":    gorm.Expr("version + 1"),
            })
        if res.Error != nil {
            return fmt.Errorf("soft delete category %d: %w", id, res.Error)
        }
        if res.RowsAffected == 0 {
            return fmt.Errorf("soft delete category %d: %w", id, response.ErrNotFound)
        }
        return nil
    })
}

// Restore 恢复：deleted_at 与 deleted_by 一起清回 NULL——只清时间不清人，审计链一样是断的。
func (r *GormCategoryRepo) Restore(ctx context.Context, familyID, id, operatorID int64) error {
    return r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        res := tx.Unscoped().Model(&model.Category{}). // 默认作用域看不见尸体，恢复必须 Unscoped
            Where("id = ? AND family_id = ? AND deleted_at IS NOT NULL", id, familyID).
            Updates(map[string]any{
                "deleted_at": nil,
                "deleted_by": nil,
                "updated_at": gorm.Expr("now()"),
                "version":    gorm.Expr("version + 1"),
            })
        if res.Error != nil {
            return fmt.Errorf("restore category %d: %w", id, res.Error)
        }
        if res.RowsAffected == 0 {
            return fmt.Errorf("restore category %d: %w", id, response.ErrNotFound)
        }
        return nil
    })
}

// ListDeleted 回收站的数据源：只看本家庭的软删行，按删除时间倒序。
// 注意不带 OR family_id IS NULL——预置行永远不会被软删，回收站里没有它的事。
func (r *GormCategoryRepo) ListDeleted(ctx context.Context, familyID int64) ([]model.Category, error) {
    var rows []model.Category
    err := r.db.WithContext(ctx).Unscoped().
        Where("family_id = ? AND deleted_at IS NOT NULL", familyID).
        Order("deleted_at DESC, id DESC").
        Find(&rows).Error
    if err != nil {
        return nil, fmt.Errorf("list deleted categories: %w", err)
    }
    return rows, nil
}

步骤 2 · 全链路测试：删 → 藏 → 见尸 → 复活

完整 · server/internal/finance/repository/category_softdelete_test.gopackage repository

import (
    "context"
    "errors"
    "testing"

    "homecube/internal/finance/model"
    "homecube/pkg/response"
)

func TestSoftDeleteRestoreCycle(t *testing.T) {
    gdb := openTestDB(t) // S3·D6 的 skip 助手，同包直接用
    repo := NewGormCategoryRepo(gdb)
    ctx := context.Background()
    const famA = int64(911)
    t.Cleanup(func() {
        gdb.Unscoped().Where("family_id = ?", famA).Delete(&model.Category{}) // 测试清场才许物理删
    })

    cat, err := repo.Create(ctx, famA, model.CategoryInput{Name: "软删小白鼠", Kind: "expense"})
    if err != nil {
        t.Fatalf("create: %v", err)
    }

    // ① 软删：成功
    if err := repo.SoftDelete(ctx, famA, cat.ID, 42); err != nil {
        t.Fatalf("soft delete: %v", err)
    }

    // ② 藏：默认作用域里彻底不可见（GetByID → ErrNotFound → 上层 404+1001）
    if _, err := repo.GetByID(ctx, famA, cat.ID); !errors.Is(err, response.ErrNotFound) {
        t.Fatalf("软删后 GetByID 应 ErrNotFound, got %v", err)
    }

    // ③ 见尸：psql 里行还在，deleted_at/deleted_by 成对；ListDeleted 能捞到
    var raw model.Category
    if err := gdb.Unscoped().First(&raw, cat.ID).Error; err != nil {
        t.Fatalf("Unscoped First: %v", err)
    }
    if !raw.DeletedAt.Valid || raw.DeletedBy == nil || *raw.DeletedBy != 42 {
        t.Fatalf("deleted_at/deleted_by 必须成对: %+v", raw)
    }
    deleted, err := repo.ListDeleted(ctx, famA)
    if err != nil || len(deleted) != 1 {
        t.Fatalf("ListDeleted = %d 条, want 1, err %v", len(deleted), err)
    }

    // ④ 复活：Restore 后两列一起归 NULL，默认作用域重新可见
    if err := repo.Restore(ctx, famA, cat.ID, 42); err != nil {
        t.Fatalf("restore: %v", err)
    }
    alive, err := repo.GetByID(ctx, famA, cat.ID)
    if err != nil || alive.DeletedBy != nil {
        t.Fatalf("复活后应可见且 deleted_by 清空: %v %+v", err, alive)
    }

    // ⑤ 跨家庭软删被拒：ErrNotFound，且行安然无恙
    if err := repo.SoftDelete(ctx, 912, cat.ID, 42); !errors.Is(err, response.ErrNotFound) {
        t.Fatalf("跨家庭软删应 ErrNotFound, got %v", err)
    }
    if _, err := repo.GetByID(ctx, famA, cat.ID); err != nil {
        t.Fatalf("被拒后行应还活着: %v", err)
    }
}

常见坑（新手 100% 会踩）

坑现象正确姿势
事务回调里用 r.db 而不是 tx回滚时那条语句的改动竟然留下了回调内一律 tx；r.db 在事务外裸奔
回调用 GORM 的 Delete() 图省事deleted_by 永远是 NULL，审计断头软删走手写 Updates，两列成对 + version+1
恢复只清 deleted_at复活的行背着「不知谁删的」旧戳两列一起清回 NULL
忘了 Unscoped() 去恢复/查尸Restore 报 ErrNotFound——默认作用域根本看不见软删行凡是要「看见尸体」的查询，先 Unscoped
回收站查询带 OR family_id IS NULL把系统预置行也列进回收站预置行永不软删；ListDeleted 只查 family_id = ?
把 archived 当软删用停用的分类从所有统计里消失，历史流水筛不出archived 是业务状态、行是活的；软删才走默认作用域隐藏
以为软删就不用唯一约束设计注销用户的手机号被部分索引外的旧行占着，重新注册报 1006唯一索引带 WHERE deleted_at IS NULL（D3 的部分索引）

今日名词卡

术语一句话解释
事务（transaction）多条写捆成原子单位：全成才生效，一步败即整体回滚
COMMIT / ROLLBACK事务的两个结局；GORM 回调返回 nil/error 分别对应
软删（soft delete）写 deleted_at 盖戳不删行；本站必须与 deleted_by 成对
默认作用域模型带 gorm.DeletedAt 后，GORM 给一切查询自动加的 deleted_at IS NULL
Unscoped()关掉默认作用域的开关：查尸、恢复、测试清场三处用
恢复入口与软删成对出现的能力（Restore + ListDeleted）；缺了它，软删就是数据黑洞
回收站软删行的用户可见出口；S6 的流水回收站 = 今天三件套的 HTTP 化
部分唯一索引WHERE deleted_at IS NULL 的唯一约束：只管活行
gorm.Expr("now()")让时间戳由数据库统一打，不依赖各应用机器的钟
