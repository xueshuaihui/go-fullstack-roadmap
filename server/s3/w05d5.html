GORM 一对多关联与 Preload：family→members

一个家庭有多个成员，一个成员只属于一个家庭——项目里第一个一对多关联今天出生：迁移 homeos_0002_init_family_member 建两张表（这次 down 要真刀真枪逆序了），GORM 模型用 Members []Member + Preload 把「查家庭顺手带出成员」变成两条干净的 SELECT，顺带认识性能杀手 N+1。

今日目标

↑ 这四条是「学习目标」。页面底部还有 5 条「完成检查」，全部勾掉今天才算结束。

知识讲义

1. 表设计：外键、角色列与「已退出不是第五个角色」

homeos_member 是 user 与 family 之间的归属表：一个 user 可以在多个家庭各有一行 member（上限 5 个家庭，S4 的 3004 管这件事）。三列值得停下来看：

  • role SMALLINT：对应 S1·D3 的 Role 枚举（1=owner 2=member 3=ward 4=guest）。Go 侧 int8，库里 SMALLINT，宽度对齐。
  • user_id 可空：无账号被记录成员（儿童/老人）可以先建档不绑账号，日后邀请激活再回填。
  • status：「已退出成员」不是第五个角色，是 status 的一个取值——退出后历史作者标记还要用，数据留在家庭。

外键纪律：同 schema 内可以建 REFERENCES（member→family、member→user 都在 homeos 里）；跨 schema 的外键一律禁止（finance 的表不许 REFERENCES homeos 的表）——模块边界不许被数据库约束偷偷缝合，跨模块的事走 platform 的接口（S4 建第一个）。

2. GORM 的 has many：三要素

片段 · 前置：model 包内；Member 今天同步补 gorm tagtype Family struct {
    // …通用列略（同 User 的样式）…
    Members []Member `gorm:"foreignKey:FamilyID" json:"members"`
}

type Member struct {
    ID       int64 `gorm:"column:id;primaryKey"`
    FamilyID int64 `gorm:"column:family_id"`   // ← foreignKey 指的是「对方（Member）身上的这个字段」
    // …其余列略…
}

三要素：① 子表身上有外键字段（Member.FamilyID）；② 父表身上有切片字段（Family.Members）；③ tag 里 foreignKey:FamilyID 点名用哪个字段连。注意方向：has many 的 foreignKey 写的是子表的字段——很多人第一次都写反。

关联字段只是「装载位」，不是「触发器」。GORM 查 Family 时默认不填 Members——不写 Preload，它就是个空切片，且不会多发一条 SQL。这是刻意设计：默认便宜，加载显式。

3. Preload 与 N+1

db.Preload("Members").First(&fam, id) 实际发两条 SQL：

片段 · 开 logger.Info 能在日志里看到的两条SELECT * FROM homeos.homeos_family WHERE id = $1 ORDER BY id LIMIT 1;
SELECT * FROM homeos.homeos_member WHERE family_id IN ($1);   -- IN 一把捞，不是逐个查

对照组是新手最常见的写法：查出 10 个家庭，再循环里逐个查成员——1 + 10 条 SQL，这就是 N+1 问题；数据一多，数据库先于业务逻辑被打死。Preload 把「N 次单查」压成「1 次 IN 批量查」，总量恒为 2 条。本站纪律：列表接口需要关联数据时一律 Preload，禁止在循环里发查询。

4. down 逆序第一次实战

up 顺序：先 homeos_family（被引用方），后 homeos_member（引用方，外键指着 family 和 user）。down 严格镜像：先 DROP member，再 DROP family。写反了会怎样？cannot drop table homeos.homeos_family because other objects depend on it——数据库替你把昨天的规则①复习了一遍。

步骤 1 · 迁移 homeos_0002_init_family_member

完整 · server/migrations/homeos/homeos_0002_init_family_member.up.sql-- up 顺序：先被引用方（family），后引用方（member）。
CREATE TABLE homeos.homeos_family (
    id         BIGSERIAL PRIMARY KEY,
    family_id  BIGINT,                              -- 自身即「家庭」本体：恒 NULL，本表 id 就是他表的 family_id
    name       TEXT NOT NULL,
    timezone   TEXT NOT NULL DEFAULT 'Asia/Shanghai',
    currency   TEXT NOT NULL DEFAULT 'CNY',          -- 只存不算汇率
    avatar     TEXT NOT NULL DEFAULT '',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at TIMESTAMPTZ,
    deleted_by BIGINT,
    version    INT NOT NULL DEFAULT 1
);

CREATE TABLE homeos.homeos_member (
    id          BIGSERIAL PRIMARY KEY,
    family_id   BIGINT NOT NULL REFERENCES homeos.homeos_family (id), -- 同 schema 外键：允许
    user_id     BIGINT REFERENCES homeos.homeos_user (id),            -- 可空：无账号被记录成员
    name        TEXT NOT NULL,
    relation    TEXT NOT NULL DEFAULT '',           -- 家庭内称谓的权威字段
    role        SMALLINT NOT NULL DEFAULT 2 CHECK (role IN (1, 2, 3, 4)),
    guardian_id BIGINT,                              -- ward 的监护人，指向本表 id；应用层校验，不建自引用外键
    status      TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'left')),
    avatar      TEXT NOT NULL DEFAULT '',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at  TIMESTAMPTZ,
    deleted_by  BIGINT,
    version     INT NOT NULL DEFAULT 1
);

CREATE INDEX idx_homeos_member_family ON homeos.homeos_member (family_id);
CREATE INDEX idx_homeos_member_user ON homeos.homeos_member (user_id);
完整 · server/migrations/homeos/homeos_0002_init_family_member.down.sql-- 与 up 严格逆序：先删引用方 member，再删被引用方 family。
DROP TABLE IF EXISTS homeos.homeos_member;
DROP TABLE IF EXISTS homeos.homeos_family;

步骤 2 · Family/Member 模型补关联与 tag

完整 · server/internal/homeos/model/family_member.gopackage model

import (
    "time"

    "gorm.io/gorm"
)

type Family struct {
    ID        int64          `gorm:"column:id;primaryKey" json:"id"`
    FamilyID  *int64         `gorm:"column:family_id" json:"family_id"` // 家庭本体：恒 NULL
    Name      string         `gorm:"column:name" json:"name"`
    Timezone  string         `gorm:"column:timezone" json:"timezone"`
    Currency  string         `gorm:"column:currency" json:"currency"`
    Avatar    string         `gorm:"column:avatar" json:"avatar"`
    CreatedAt time.Time      `gorm:"column:created_at" json:"created_at"`
    UpdatedAt time.Time      `gorm:"column:updated_at" json:"updated_at"`
    DeletedAt gorm.DeletedAt `gorm:"column:deleted_at" json:"-"`
    DeletedBy *int64         `gorm:"column:deleted_by" json:"deleted_by"`
    Version   int            `gorm:"column:version" json:"version"`

    // Members 一对多装载位：默认不加载，Preload("Members") 显式带出。
    Members []Member `gorm:"foreignKey:FamilyID" json:"members"`
}

func (Family) TableName() string { return "homeos.homeos_family" }

type Member struct {
    ID         int64          `gorm:"column:id;primaryKey" json:"id"`
    FamilyID   int64          `gorm:"column:family_id" json:"family_id"` // 归属表：NOT NULL，非指针
    UserID     *int64         `gorm:"column:user_id" json:"user_id"`     // 可空：无账号成员
    Name       string         `gorm:"column:name" json:"name"`
    Relation   string         `gorm:"column:relation" json:"relation"`
    Role       Role           `gorm:"column:role" json:"role"`           // S1·D3 的 int8 枚举
    GuardianID *int64         `gorm:"column:guardian_id" json:"guardian_id"`
    Status     string         `gorm:"column:status" json:"status"`       // active / left：已退出不是第五个角色
    Avatar     string         `gorm:"column:avatar" json:"avatar"`
    CreatedAt  time.Time      `gorm:"column:created_at" json:"created_at"`
    UpdatedAt  time.Time      `gorm:"column:updated_at" json:"updated_at"`
    DeletedAt  gorm.DeletedAt `gorm:"column:deleted_at" json:"-"`
    DeletedBy  *int64         `gorm:"column:deleted_by" json:"deleted_by"`
    Version    int            `gorm:"column:version" json:"version"`
}

func (Member) TableName() string { return "homeos.homeos_member" }

步骤 3 · Preload 测试（真库测试，无库自动 Skip）

完整 · server/internal/homeos/model/family_preload_test.gopackage model

import (
    "fmt"
    "os"
    "testing"

    "gorm.io/gorm"

    "homecube/internal/platform/db"
)

// 复用 S3·D2 的口径：DB_* 不全就 Skip，仓库在无库机器上依然绿。
func openTestDB(t *testing.T) *gorm.DB {
    t.Helper()
    if os.Getenv("DB_NAME") == "" {
        t.Skip("未设置 DB_NAME，跳过真库测试")
    }
    dsn := fmt.Sprintf("postgres://%s:%s@%s:%s/%s?sslmode=%s",
        os.Getenv("DB_USER"), os.Getenv("DB_PASS"),
        os.Getenv("DB_HOST"), os.Getenv("DB_PORT"),
        os.Getenv("DB_NAME"), os.Getenv("DB_SSLMODE"))
    gdb, err := db.Open(dsn)
    if err != nil {
        t.Skipf("库未就绪（先 make migrate-homeos-up）: %v", err)
    }
    return gdb
}

func TestFamilyPreloadMembers(t *testing.T) {
    h := openTestDB(t)

    // 造数：一个家庭两个成员（Create 会沿关联一并写入 Members——GORM 的 upsert 关联行为）
    fam := Family{Name: "preload 测试家庭", Members: []Member{
        {Name: "家长", Role: RoleOwner, Status: "active"},
        {Name: "娃", Role: RoleWard, Status: "active"},
    }}
    if err := h.Create(&fam).Error; err != nil {
        t.Fatalf("create: %v", err)
    }

    // 不带 Preload：Members 是空切片，且没有多余 SQL（开 logger.Info 亲眼确认）
    var plain Family
    if err := h.First(&plain, fam.ID).Error; err != nil {
        t.Fatalf("first: %v", err)
    }
    if len(plain.Members) != 0 {
        t.Fatalf("未 Preload 时 Members 应为空, got %d", len(plain.Members))
    }

    // 带 Preload：两条 SQL 带出全家
    var loaded Family
    if err := h.Preload("Members").First(&loaded, fam.ID).Error; err != nil {
        t.Fatalf("preload first: %v", err)
    }
    if len(loaded.Members) != 2 {
        t.Fatalf("Preload 后 Members = %d, want 2", len(loaded.Members))
    }
    for _, m := range loaded.Members {
        if m.FamilyID != fam.ID {
            t.Fatalf("member %d 的 FamilyID = %d, want %d", m.ID, m.FamilyID, fam.ID)
        }
    }

    // 清场：测试数据不过夜（先删子后删父，人肉逆序）
    h.Where("family_id = ?", fam.ID).Delete(&Member{})
    h.Delete(&loaded)
}

注意清场用的是 Delete：模型带 gorm.DeletedAt 时它已经是软删语义（行还在、deleted_at 被写上），下周一（S3·D7）专门收拾这件事，今天先知道「测试数据是软删掉的」，重放判据不受影响。

常见坑（新手 100% 会踩）

坑现象正确姿势
foreignKey 方向写反写 foreignKey:ID 或指向父表字段，Preload 出来永远空has many 的 foreignKey 指子表的外键字段（Member.FamilyID）
忘了 Preload 却断言 Members测试红：Members = 0, want 2，以为关联坏了关联默认不加载是特性；要就显式 Preload("Members")
循环里逐个查成员列表一大，SQL 条数 = 1 + N，库先跪N+1 的解药是 Preload（IN 批量）；循环发查询在本站是纪律级禁令
down 先删 familycannot drop ... other objects depend on it逆序：先 member 后 family（规则①第一次真刀真枪）
跨 schema 建外键finance 表 REFERENCES homeos 表，模块边界被约束缝死跨 schema 外键一律禁止；跨模块走 platform 接口（S4）
Member.FamilyID 用了指针归属列本就不许 NULL，指针让「没归属」这种非法状态可以表达NOT NULL 的列用值类型；可空才用指针——类型系统替你守约
测试数据不清场跑几遍后库里全是「preload 测试家庭」，断言数量开始随缘测试尾部清场；断言只针对自己造的那行 id，不数全表

今日名词卡

术语一句话解释
一对多（has many）父表一行对应子表多行；GORM 里 = 父表切片字段 + 子表外键 + foreignKey tag
Preload显式加载关联：额外一条 WHERE ... IN 批量查询，把结果装进装载位
N+1 问题1 条列表查询 + N 条循环单查；Preload 把 N 压成 1
外键（REFERENCES）数据库级引用约束；本站只许同 schema 内建
CHECK 约束列级取值白名单（role ∈ {1,2,3,4}、status ∈ {active,left}），非法值根本存不进去
归属表homeos_member：user×family 的多对多桥，还携带 role/status/relation 等「这段关系」的属性
无账号被记录成员user_id NULL 的 member：先建档、后激活，儿童/老人场景
status ≠ 角色「已退出」是 member.status 的取值，不是第五个角色；数据留家庭
软删的 Delete模型带 gorm.DeletedAt 后，GORM 的 Delete 变 UPDATE deleted_at（S3·D7 正式讲）

卡壳时查什么

正文自足，只有两种情况出去查：

  • 外键与 CHECK 的 SQL 细节：PostgreSQL 16 · Constraints（可选）。
