知识讲义

1. 迁移 = 编号的、成对的、可重放的 DDL

一条迁移就是一对 SQL 文件：up 把 schema 往前推一步，down 把这一步退回去。工具在库里记一张版本表，知道「现在推到第几号」；up 只执行比当前版本新的文件，按序号升序；down 反着来。命名规则本站钉死：

结构server/migrations/
├── homeos/
│   ├── homeos_0001_init_user.up.sql
│   └── homeos_0001_init_user.down.sql
└── finance/
    └── （S3·D6 起出现：finance_0001_init_category…）
  • seq 四位，从 0001 起，字典序 = 执行序；
  • 两个 code 各自独立计数：homeos 到 0003 时 finance 可能才 0001，互不相干；
  • 成对出现：写了 up 就必须写 down（明天整天讲 down 怎么写才不是摆设）；
  • 不跨 code 引用：finance 的迁移里不许出现 homeos_*——昨天的专属账号让这条纪律物理化。

2. schema_migrations：版本账本，一 code 一张

golang-migrate 在目标 schema 里维护一张 schema_migrations（就两列：version 与 dirty）。因为两个 code 独立计数，一个库里必须有两张账本：homeos 的在 homeos schema、finance 的在 finance schema——靠连接串里的 search_path 各归各位。dirty=true 表示某次迁移执行到一半失败：账本卡住，后续 up/down 全被拒绝，要先人工查清现场再用 force 复位。dirty 不是日常，出现即事故，处理要留记录。

3. 通用列：每张业务表的标准七件套

列类型与默认为什么
idBIGSERIAL PRIMARY KEYGo 侧 int64，全期不换 uint；游标分页要拿它当决胜键（S3·D8）
family_idBIGINT家庭隔离的根。业务表 NOT NULL；两类例外可空：身份表（user/family，归属在 member）与系统预置数据（NULL = 全局可见）
created_at / updated_atTIMESTAMPTZ NOT NULL DEFAULT now()带时区的时间戳；updated_at 由 repo 写路径显式刷新
deleted_atTIMESTAMPTZ NULL软删标记，NULL = 活着（S3·D7 正式讲）
deleted_byBIGINT NULL谁删的。软删必须成对：只写时间不写人，审计断头
versionINT NOT NULL DEFAULT 1乐观锁，写一次 +1；冲突走错误码 1009（S3·D6 分类更新就用它）

4. migrate 怎么跑：compose 里的工具服务

迁移不进业务进程——它是运维动作，本站用 compose 的 migrate 服务（挂 profiles: ["tools"]，up -d 不会把它带起来，只在显式 run 时出场）。它挂载 server/migrations 目录，以专属账号连库，URL 里带 search_path：建出来的表、记出来的账本，全落在自己的 schema 里。Makefile 包四个目标（migrate-homeos-up/down、migrate-finance-up/down），日常你只敲 make。

今天属增量类型 ④：写一条迁移的 up 与 down（外加让它能跑的 compose 服务与 Makefile 目标——接线是这条增量的组成部分）。收工时 make build / make test 仍绿。

步骤 1 · compose 加 migrate 服务

片段 · docker-compose.yml 的 services: 下追加  migrate:
    image: migrate/migrate:v4.18.1        # CLI 镜像，版本钉死
    container_name: homecube-migrate
    profiles: ["tools"]                   # 工具服务：up -d 不自动起，只在 make migrate-* 时 run
    volumes:
      - ./server/migrations:/migrations:ro
    environment:
      # —— 迁移专用连接（与后端 DB_* 两段分开）：专属账号 + search_path 钉 schema ——
      HOMEOS_MIGRATE_URL: postgres://homeos_app:homeos_app123@postgres:5432/homecube?sslmode=disable&search_path=homeos
      FINANCE_MIGRATE_URL: postgres://finance_app:finance_app123@postgres:5432/homecube?sslmode=disable&search_path=finance
    depends_on:
      postgres:
        condition: service_healthy

步骤 2 · Makefile 加四个目标

片段 · Makefile 追加（缩进是真 TAB）.PHONY: migrate-homeos-up migrate-homeos-down migrate-finance-up migrate-finance-down

# --entrypoint sh：借容器里的 shell 展开环境变量；$$ 是给 make 看的转义
migrate-homeos-up:
	docker compose run --rm --entrypoint sh migrate -c \
	  'migrate -path /migrations/homeos -database "$$HOMEOS_MIGRATE_URL" up'

migrate-homeos-down:
	docker compose run --rm --entrypoint sh migrate -c \
	  'migrate -path /migrations/homeos -database "$$HOMEOS_MIGRATE_URL" down'

migrate-finance-up:
	docker compose run --rm --entrypoint sh migrate -c \
	  'migrate -path /migrations/finance -database "$$FINANCE_MIGRATE_URL" up'

migrate-finance-down:
	docker compose run --rm --entrypoint sh migrate -c \
	  'migrate -path /migrations/finance -database "$$FINANCE_MIGRATE_URL" down'

步骤 3 · 第一条迁移：homeos_0001_init_user

完整 · server/migrations/homeos/homeos_0001_init_user.up.sql-- homeos_0001_init_user：全局账号（身份表）。
-- family_id 可空是身份表例外：一个用户可属多个家庭，归属记录在 homeos_member（S3·D5 建）。
CREATE TABLE homeos.homeos_user (
    id            BIGSERIAL PRIMARY KEY,
    family_id     BIGINT,                                -- 身份表例外：恒 NULL
    phone         TEXT NOT NULL,
    password_hash TEXT NOT NULL DEFAULT '',              -- S4 注册起写入 bcrypt 哈希
    nickname      TEXT NOT NULL DEFAULT '',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at    TIMESTAMPTZ,                           -- 软删标记，NULL = 活着
    deleted_by    BIGINT,                                -- 与 deleted_at 成对出现
    version       INT NOT NULL DEFAULT 1                 -- 乐观锁
);

-- 手机号唯一（对应错误码 1006）；部分索引把软删行排除在外，
-- 注销后的号码允许重新注册——软删语义与唯一约束的交点，S3·D7 再回来看。
CREATE UNIQUE INDEX uq_homeos_user_phone
    ON homeos.homeos_user (phone)
    WHERE deleted_at IS NULL;
完整 · server/migrations/homeos/homeos_0001_init_user.down.sql-- down 必须真能回滚：索引随表走，DROP TABLE 一条即净（明天专门讲 down 的写法）。
DROP TABLE IF EXISTS homeos.homeos_user;

常见坑（新手 100% 会踩）

坑现象正确姿势
连接串漏 search_pathschema_migrations 建到了 public，两个 code 共一张账本，版本号互相踩每个 code 的 URL 必须带自己的 search_path；发现建错位就 down -v 重置重来
seq 不补零homeos_1_... 排在 homeos_10_... 后面，执行序错乱四位补零：0001。两位数的日子比你想象的来得快
只写 up 不写 down回滚时发现 down 缺失，migrate 直接报错成对提交；没有 down 的迁移不许合入（明天的主题）
用迁移账号之外的身份建表表的 owner 不对，专属账号之后动不了它建表只经 make migrate-*；psql 手工连进去只读不写
把 BIGSERIAL 写成 INTGo 侧 int64 与库侧 32 位对不上，量大后溢出本站主键统一 BIGSERIAL，Go 侧统一 int64
时间列用 TIMESTAMP（无时区）跨时区家庭的时间窗统计错一天一律 TIMESTAMPTZ；时间窗五档的账要它来算
dirty 了硬闯迁移半途失败后继续 up/down，全被拒绝，然后随手 force 掩盖现场先读报错、查现场（表建了一半？），修复后 force 到正确版本，并把过程记进 notes/

今日名词卡

术语一句话解释
迁移（migration）编号、成对、可重放的 schema 变更记录；本站建表权的唯一入口
golang-migrate迁移 CLI 工具：按序执行 up/down，用 schema_migrations 记账
schema_migrations版本账本表（version + dirty 两列）；一个 code 一张，靠 search_path 落进各自 schema
dirty 状态某次迁移执行中途失败留下的「现场封锁」标记；人工查清后 force 复位
BIGSERIAL自增 64 位主键类型；配 Go 侧 int64，全期不换
TIMESTAMPTZ带时区时间戳；本站所有时间列的唯一选择
部分索引（partial index）带 WHERE 的索引：WHERE deleted_at IS NULL 让唯一约束只管活行
通用列七件套id/family_id/created_at/updated_at/deleted_at/deleted_by/version；每条迁移的固定开场
compose profiles服务分组开关；tools 组的服务不被 up -d 拉起，只按需 run
幂等的 up「再执行一次 = no change」：账本挡住重复执行，这是重放判据的地基

卡壳时查什么

正文自足，只有两种情况出去查：

  • migrate CLI 的子命令与 URL 参数：golang-migrate · CLI 文档（可选，查 force/version/goto 时用）。
  • Postgres DDL 语法拿不准：PostgreSQL 16 · CREATE TABLE（可选，权威且好读）。

错误码 1006（唯一约束冲突）与哨兵 ErrConflict 的映射在 S1·D4；%w 包装纪律同页。昨天 TranslateError 埋的伏笔（gorm.ErrDuplicatedKey → 1006）在 S3·D6 的分类 repo 里兑现。
